## 1. Story Header

### Title
[FRONTEND] Allocation Shortage Resolution (Backorder / Substitute / External) — UI Capture + Moqui Proxy Integration

### Primary Persona
Service Advisor

### Business Value
Prevent work stoppage and reduce customer wait time by presenting actionable shortage resolutions (substitute, external availability, backorder) when an allocation request exceeds available-to-promise (ATP), while capturing an auditable decision that downstream domains can act on.

---

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** shortage handling during part allocation that suggests substitutes, external availability, or backorder options,  
**so that** I can choose how to proceed and keep work moving with a recorded, auditable decision.

### In-scope
- Detecting/displaying an allocation shortage in the POS UI when ATP is insufficient for an allocation attempt.
- Calling Moqui proxy endpoints (same-origin) to:
  - attempt allocation (or check shortage) and receive shortage options
  - submit a shortage resolution decision for audit/event emission
- Rendering substitute / external availability / backorder options in the deterministic order provided by backend.
- Capturing the user’s decision (including cancel/no-submit) and submitting it to backend.
- UI degradation behavior when dependent option categories fail (banner + remaining options).
- Persisting and showing “shortage pending” state on the affected allocation line until resolved (UI representation; backend is SoR).

### Out-of-scope
- Defining substitution rules (owned by Product domain).
- Computing external availability (owned by Positivity domain).
- Updating work order/estimate contents (owned by Work Execution domain) beyond submitting the resolution decision.
- Inventory valuation/costing decisions beyond displaying provided cost impact fields.
- Backorder lead-time sourcing logic beyond displaying provided fields (SoR backend).
- Any frontend computation of ATP/availability quantities (Inventory services are authoritative for availability views; UI displays only).

### Entry points
- From the Work Order screen where parts are allocated (e.g., “Add Part” / “Allocate” action on a parts line).
- From an existing parts line marked as “Shortage/Pending Resolution” (re-open resolution dialog).

### Screens to create/modify
- **Modify** existing Work Order Allocation screen to:
  - intercept allocation submit when backend returns a shortage response
  - display shortage indicator on the line item
  - provide “Resolve shortage” action to reopen the dialog
- **Create** a shortage resolution dialog/screen fragment:
  - `AllocationShortageResolve` (modal/popup or sub-screen within Work Order context)

### Navigation context
- User remains in the Work Order context (`workOrderId` in screen path or parameters).
- Shortage resolution occurs without losing unsaved work on the Work Order screen.

### User workflows (happy + alternate)
**Happy path**
1. Service Advisor requests allocation of part (qty > ATP).
2. UI receives shortage response with ordered options.
3. UI opens Shortage Resolution dialog showing:
   - shortage summary (requested, ATP, shortfall) as provided by backend
   - options grouped by type (Substitute, External, Backorder) in backend-provided order
4. User selects an option and confirms.
5. UI submits decision; on success:
   - dialog closes
   - affected parts line updates to reflect backend result
   - shortage flag cleared.

**Alternate paths**
- Partial options: dialog shows banner “Some availability options could not be retrieved at this time.” and still shows remaining options.
- User cancels dialog: dialog closes; no decision submitted; line remains “Shortage/Pending” per backend state.
- No options: dialog shows blocking empty state and offers Close.

## 6. Functional Behavior

### Triggers
- User clicks “Allocate” / “Confirm allocation” for a part line with requested quantity.
- User opens shortage resolution dialog from a flagged line.

### UI actions
- On allocation submit:
  - Call Moqui proxy “attempt allocation” endpoint.
  - If success without shortage: proceed as normal.
  - If shortage response: render shortage dialog with options.
- In shortage dialog:
  - Select option (single selection).
  - Confirm decision → submit resolution.
  - Cancel → close dialog, do not submit.

### State changes
- Parts line shows `shortageStatus=PENDING` when backend indicates shortage detected and unresolved.
- After successful resolution submit:
  - update line to reflect backend result (resolved / backordered / substituted / external purchase requested)
  - clear pending shortage UI markers as appropriate.

### Service interactions
- `AttemptAllocationOrCheckShortage` returns either:
  - normal allocation success, or
  - shortage payload including ordered `resolutionOptions` and shortage details.
- `SubmitShortageResolution` records decision (audit) and returns updated allocation/workorder line representation.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- User must select exactly one resolution option before enabling “Confirm”.
- UI must not compute ATP/shortfall; it displays backend-provided values. If backend omits a display field, UI shows “—” and still allows selection/submit unless the option itself is malformed.
- Option rendering guards:
  - If an option is missing fields required to render/submit that option type, hide that option and show a non-blocking warning banner: “Some options could not be displayed due to missing data.”
  - If all options are hidden/invalid, show blocking empty state: “No resolution options available.”

### Enable/disable rules
- Confirm disabled until an option is selected.
- Confirm disabled while submit is in-flight (double-submit protection).
- If backend indicates no valid options: only Close is available.

### Visibility rules
- Show option categories only when present.
- Do not fabricate options (no synthetic backorder/substitute/external).
- Show informational banner when backend indicates partial option retrieval failure.

### Error messaging expectations
- Client validation errors: inline (“Please select an option to continue.”).
- Backend 4xx with field errors: map to fields when possible; otherwise show banner with backend message and correlation ID in technical details.
- Backend 5xx/network/timeout: show “Unable to resolve shortage right now. Try again.” with Retry; preserve selected option.

## 9. Service Contracts (Frontend Perspective)

**Integration constraint:** UI calls Moqui proxy endpoints only; no direct Vue → downstream services. (DECISION-INVENTORY-002)

> **Integration gap:** Inventory contracts now describe shortage option retrieval, but the exact Moqui endpoint/service names for this work-order-facing flow still need to be mapped once domain ownership is clarified.

### Load/view calls
1. **Load allocation line (for reopen)**
   - Route: `GET /workexec/work-orders/{workOrderId}/allocations/{allocationLineId}`
   - Output: allocation line including shortage status and (optionally) last shortage context snapshot.

### Create/update calls
2. **Attempt allocation (may return shortage)**
   - Route: `POST /workexec/work-orders/{workOrderId}/allocations/attempt`
   - Input (JSON): `{ allocationLineId?, productSku|productId, quantity, locationId?, clientRequestId }`
   - Output (success): updated allocation line
   - Output (shortage): shortage context + `resolutionOptions[]` + `partialOptionsWarning`

### Submit/transition calls
3. **Submit shortage resolution decision**
   - Route: `POST /workexec/work-orders/{workOrderId}/allocations/{allocationLineId}/shortage-resolution`
   - Input (JSON): `{ optionId, decisionType, quantity, clientRequestId, note? }`
   - Output: updated allocation line + resolution summary + audit reference (if available)

### Error handling expectations
- Error schema: deterministic plain JSON; unknown shapes fall back to generic error. (DECISION-INVENTORY-003)
- 400/422: validation errors; map to fields when possible.
- 401: route to login/session refresh per app convention; do not show partial data. (DECISION-INVENTORY-012)
- 403: show forbidden state; do not leak option payloads; keep dialog open but read-only. (DECISION-INVENTORY-012)
- 409: concurrency conflict; show “This allocation changed. Refresh options.” with Refresh action.
- 5xx/timeout: show retry; do not auto-retry mutations.

**Observability**
- Send `X-Correlation-Id` header on all requests; display it in error technical details when present. (DECISION-INVENTORY-012)
- Do not log sensitive quantities/payloads to console/telemetry. (DECISION-INVENTORY-011)

## 10. State Model & Transitions

### Allowed states (frontend-visible)
For an allocation line (as mapped from backend fields):
- `ALLOCATED` (normal)
- `SHORTAGE_PENDING` (shortage detected; decision not recorded)
- `SHORTAGE_RESOLVED_SUBSTITUTE`
- `SHORTAGE_RESOLVED_EXTERNAL`
- `SHORTAGE_RESOLVED_BACKORDER`

> Backend is SoR for actual statuses; UI must map from backend response fields and not invent transitions.

### Role-based transitions
- Authorized user may transition:
  - `SHORTAGE_PENDING` → one of resolved states via submit decision
- Unauthorized user:
  - cannot submit; may view depending on backend response; UI must handle 403 gracefully.

### UI behavior per state
- `SHORTAGE_PENDING`: show badge/flag on line + “Resolve” action opens dialog.
- Resolved states: show resolution summary (type and key details like resulting SKU/source/lead time) as provided by backend.

## 11. Alternate / Error Flows

### Validation failures
- No option selected → prevent submit and show inline message.
- Malformed option → hide option; if all options invalid → blocking empty state.

### Concurrency conflicts
- Backend returns 409 on submit:
  - show conflict message
  - provide Refresh which re-calls attempt/check endpoint and re-renders options.

### Unauthorized access
- Backend 403 on submit:
  - dialog remains open in read-only mode
  - show “You don’t have permission to resolve shortages.”
  - do not mark shortage as resolved in UI.

### Empty states
- Backend returns shortage with empty options:
  - show “No resolution options available.” and Close.
- Reopen dialog but backend no longer indicates shortage:
  - close dialog and refresh line state.

## 12. Acceptance Criteria

### Scenario 1: Shortage flagged and options shown in deterministic order
**Given** a Service Advisor is allocating a part to a work order  
**And** the backend determines the requested quantity exceeds ATP  
**When** the user submits the allocation attempt  
**Then** the UI must display a shortage resolution dialog  
**And** the allocation line must be visibly flagged as shortage pending  
**And** options must be displayed in the exact order provided by the backend response  
**And** options must be grouped by type without re-sorting across types.

### Scenario 2: Only backorder available
**Given** a shortage occurs  
**And** the backend returns only one option of type `BACKORDER`  
**When** the shortage dialog is shown  
**Then** only that backorder option is displayed  
**And** selecting it enables Confirm  
**And** confirming submits the decision and updates the line to a backorder-resolved state based on backend response.

### Scenario 3: Partial option retrieval warning
**Given** a shortage occurs  
**And** the backend returns `partialOptionsWarning=true`  
**When** the shortage dialog is shown  
**Then** the UI must show the banner message “Some availability options could not be retrieved at this time.”  
**And** the UI must still allow selecting and confirming among the returned options.

### Scenario 4: User cancels without decision
**Given** a shortage dialog is displayed  
**When** the user clicks Cancel/Close  
**Then** no submit-decision call is made  
**And** the allocation line remains in shortage pending state until backend indicates otherwise.

### Scenario 5: Submit decision includes idempotency and traceability
**Given** a shortage dialog is displayed with options  
**When** the user selects an option and confirms  
**Then** the UI must call the submit-decision endpoint including `workOrderId`, `allocationLineId`, `optionId`, `decisionType`, and a frontend-generated `clientRequestId`  
**And** on success the UI must render the updated allocation line state and resolution summary returned by backend.

### Scenario 6: Unauthorized submit is blocked
**Given** the user lacks permission to resolve shortages  
**When** the user attempts to confirm a selected option  
**Then** the UI must display a permission error state  
**And** must not mark the shortage as resolved in the UI  
**And** must not display any additional option payload fields if the backend responds with 403.

### Scenario 7: Concurrency conflict on submit
**Given** a shortage dialog is displayed  
**And** the allocation line changes on the server before the user submits  
**When** the user confirms a selection  
**And** the backend responds with HTTP 409  
**Then** the UI must show “This allocation changed. Refresh options.”  
**And** provide a Refresh action that re-fetches the latest shortage/options and re-renders the dialog.
