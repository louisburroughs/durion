## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Timekeeping: Record Break Start/End (Mechanic)

**Primary Persona:** Mechanic (authenticated employee user)

**Business Value:** Ensures mechanic timecards accurately reflect worked vs break time, improving payroll accuracy and compliance and reducing manager correction effort.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Mechanic  
- **I want** to start and end breaks during my workday (with a break type)  
- **So that** my timecard reflects actual working time and breaks are properly audited

### In-scope
- Frontend UI to **start a break** with required `breakType` and optional `notes`
- Frontend UI to **end the current break**
- Display of current break state (in progress vs none) and recent break entries for the day
- Enforcement via UI gating + backend error handling for:
  - exactly one active break at a time (no overlap)
  - cannot start/end break without an active clock-in session (server-derived)
  - cannot start when a break already in progress
  - cannot end when no break is in progress
- Basic audit visibility (start/end timestamps; `autoEnded` indicator if returned)

### Out-of-scope
- Clock-in / clock-out UI (assumed existing elsewhere)
- Manager approval flows for time entries
- Editing/deleting historical breaks
- Payroll calculations
- Any client-side inference of “active session/timecard identifiers” (must be server-derived)

---

## 3. Actors & Stakeholders

- **Mechanic (Primary):** starts/ends their own breaks.
- **Shop Manager (Stakeholder):** consumes break data indirectly via timecard review/approvals (not implemented here).
- **People domain services (System):** validates break rules and persists break records; derives identity/session from auth context.

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated.
- User is an employee user allowed to record their own breaks (authorization enforced by backend; UI gates by capability flags/permissions when available).

### Dependencies
- People-domain backend must expose break operations and “current break context” under People REST conventions:
  - Break start/end derives identity and current session from the authenticated user (no client-provided timecard/session IDs). (DECISION-PEOPLE-022)
  - Exactly one active break at a time; conflicts return 409 and require refresh. (DECISION-PEOPLE-007, DECISION-PEOPLE-022)
  - Error schema is standardized for 400/409. (DECISION-PEOPLE-018)
  - Lists/paging conventions follow People API conventions. (DECISION-PEOPLE-021)

**Decision rationale applied:** The People domain rules explicitly resolve prior contract ambiguities: break identity/session is auth-derived; 409 is refresh-required; break types are fixed enum; notes are optional; timezone display rules are defined.

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From the mechanic’s “Timekeeping / My Day / Clock” screen (existing mechanic-facing timekeeping area).
- Optional secondary entry: a compact “Break” action area on mechanic home/dashboard, linking to the same timekeeping screen section.

### Screens to create/modify
- **Modify** an existing mechanic timekeeping screen to include:
  - Current break status panel (none vs in-progress)
  - Actions: Start Break / End Break
  - “Today’s breaks” list (read-only)
- **Create** a small modal/dialog screen (or inline form) for “Start Break”:
  - Break type picker
  - Notes field (optional; prompted when type=OTHER)

### Navigation context
- Implement as a Moqui screen with transitions:
  - `startBreak` transition: submit start request then return to same screen (PRG pattern).
  - `endBreak` transition: submit end request then return to same screen (PRG pattern).
- After any mutation, the screen must reload current context from server to reflect authoritative state (including auto-ended changes).

### User workflows (happy + alternate paths)

**Happy path — Start break**
1. Mechanic opens timekeeping screen.
2. UI loads current context: clocked-in status + active break (if any) + today’s breaks.
3. Mechanic clicks “Start Break”.
4. Mechanic selects `breakType` (MEAL/REST/OTHER); optionally enters notes.
5. Submit → server starts break.
6. UI reloads context and shows break “In progress”.

**Happy path — End break**
1. Mechanic clicks “End Break”.
2. Submit → server ends the active break.
3. UI reloads context and shows no active break; completed break appears in today list.

**Alternate paths**
- Not clocked in: Start/End actions disabled; guidance shown.
- Break already in progress: Start disabled; active break details shown.
- 409 conflict on start/end (state changed elsewhere or auto-ended): show conflict message and reload context.
- 403 forbidden: show access denied; hide/disable actions.

- User clicks **End Break**

### UI actions

- `ui.lastError: { code?, message, requestId? }|null`

### Service interactions
- Always treat server as source of truth:
  - After start/end, reload context rather than assuming local state transitions.
  - On 409, reload context and re-render.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `breakType` is required to start a break. (DECISION-PEOPLE-007)
- `breakType` allowed values: `MEAL`, `REST`, `OTHER`. (DECISION-PEOPLE-007)
- Notes:
  - Notes are **optional** for all break types.
  - For `breakType=OTHER`, notes are **optional but recommended**; UI should prompt with helper text but must not block submission. (DECISION-PEOPLE-016)

### Enable/disable rules
- **Start Break** enabled only when:
  - `context.isClockedIn == true`
  - `context.activeBreak == null`
- **End Break** enabled only when:
  - `context.activeBreak != null`
  - (Do not additionally require `isClockedIn` client-side unless the context endpoint indicates it; server remains authoritative.)

### Visibility rules
- If `activeBreak != null`:
  - Show active break summary (type, startedAt, timezone label).
  - Show “End Break”; hide or disable “Start Break”.
- If `activeBreak == null`:
  - Show “Start Break”.
  - Show today’s breaks list (may be empty).

### Error messaging expectations (standardized)
- Render errors using standardized schema. (DECISION-PEOPLE-018)
  - **400**: show field errors inline (e.g., breakType missing/invalid).
  - **409**: show conflict banner/toast with “Refresh applied” messaging; then reload context. (DECISION-PEOPLE-022)
  - **403**: show access denied; disable/hide actions.
  - **401**: redirect to login/session-expired flow (per app standard).
  - **5xx/network**: show retryable error; keep last known context visible.

**Decision rationale applied:** UI must not become the policy engine; it gates by context/capabilities and defers enforcement to backend, handling 409 as refresh-required.

## 8. Data Requirements

### Entities involved
- **Break** (People domain timekeeping record; may be represented as a TimeEntry subtype in backend, but UI treats it as Break per contract). (DECISION-PEOPLE-022, DECISION-PEOPLE-007)

### Fields (types, required, defaults)
**Break (read model for UI)**
- `breakId: string` (required, read-only)
- `personId: string` (optional in response; if present, read-only; UI must not display tenantId) (DECISION-PEOPLE-019)
- `breakType: 'MEAL'|'REST'|'OTHER'` (required)
- `startedAt: string (ISO-8601 UTC instant)` (required)
- `endedAt: string|null (ISO-8601 UTC instant)` (nullable)
- `autoEnded: boolean` (optional; default false if absent) (DECISION-PEOPLE-007)
- `notes: string|null` (optional; captured at start only)
- `locationId: string|null` (optional; used only for timezone fallback if user timezone absent) (DECISION-PEOPLE-015)
- `createdAt/lastUpdatedAt: string` (optional; if provided, read-only)

**CurrentBreakContext**
- `isClockedIn: boolean` (required)
- `activeBreak: Break|null` (required)
- `breaksToday: Break[]` (required; may be empty)
- `displayTimezone: string` (optional but recommended; e.g., `America/Chicago`) (DECISION-PEOPLE-015)

### Read-only vs editable by state/role
- Mechanic can:
  - Start a break: submit `breakType` and optional `notes`
  - End a break: no payload fields required by default
- Mechanic cannot:
  - Edit completed breaks
  - Edit timestamps
  - Delete breaks

### Derived/calculated fields
- `elapsedDuration` for active break: computed client-side from `startedAt` and “now” for display only.
- Display timezone:
  - Use user profile timezone when available; otherwise fall back to location timezone for the record/context. (DECISION-PEOPLE-015)
  - UI must label which timezone is being used (e.g., “Times shown in America/Chicago”).

## 9. Service Contracts (Frontend Perspective)

> Contracts below are aligned to People REST conventions and domain decisions; exact endpoint names may be adjusted to match repo conventions, but shapes and semantics must remain consistent. (DECISION-PEOPLE-021)

### Load/view calls

1) **Get current break context**
- **Method/Path (default):** `GET /rest/api/v1/people/timekeeping/breaks/context`
- **Query params:** none
- **Response 200:**
  ```json
  {
    "isClockedIn": true,
    "activeBreak": {
      "breakId": "brk_123",
      "breakType": "MEAL",
      "startedAt": "2026-01-21T16:00:00Z",
      "endedAt": null,
      "autoEnded": false,
      "notes": null,
      "locationId": "loc_1"
    },
    "breaksToday": [],
    "displayTimezone": "America/Chicago"
  }
  ```
- **Errors:** 401/403 per auth; 5xx.

2) **List today’s breaks (optional if context includes breaksToday)**
- **Method/Path (default):** `GET /rest/api/v1/people/timekeeping/breaks`
- **Query params (default):** `from`, `thru`, `page`, `pageSize`
- **Response 200 (paged):**
  ```json
  { "items": [/* Break */], "page": 1, "pageSize": 50, "total": 0 }
  ```

### Create/update calls

3) **Start break**
- **Method/Path (default):** `POST /rest/api/v1/people/timekeeping/breaks/start`
- **Request:**
  ```json
  { "breakType": "MEAL", "notes": "optional" }
  ```
- **Response 200/201 (recommended to return created break):**
  ```json
  {
    "breakId": "brk_123",
    "breakType": "MEAL",
    "startedAt": "2026-01-21T16:00:00Z",
    "endedAt": null,
    "autoEnded": false
  }
  ```
- **Errors:**
  - 400 with `fieldErrors` (missing/invalid breakType) (DECISION-PEOPLE-018)
  - 409 if break already in progress or not clocked in / state conflict (DECISION-PEOPLE-022)
  - 403 if not permitted

4) **End break**
- **Method/Path (default):** `POST /rest/api/v1/people/timekeeping/breaks/end`
- **Request:** `{}` (auth-derived active break) (DECISION-PEOPLE-022)
- **Response 200 (recommended to return ended break):**
  ```json
  {
    "breakId": "brk_123",
    "breakType": "MEAL",
    "startedAt": "2026-01-21T16:00:00Z",
    "endedAt": "2026-01-21T16:30:00Z",
    "autoEnded": false
  }
  ```
- **Errors:**
  - 409 if no active break / already ended / state conflict (DECISION-PEOPLE-022)
  - 403 if not permitted

### Submit/transition calls (Moqui screens)
- Screen transitions should call REST via Moqui tools or call internal services exposed similarly:
  - `transition name="startBreak"` → service-call → redirect back to same screen with message
  - `transition name="endBreak"` → service-call → redirect back to same screen with message
- Use PRG to prevent duplicate submissions on refresh.

### Error handling expectations
- Use standardized error schema. (DECISION-PEOPLE-018)
  - **400 example:**
    ```json
    { "errorCode":"VALIDATION_ERROR","message":"Invalid request","fieldErrors":{"breakType":"Required"} }
    ```
  - **409 example:**
    ```json
    { "errorCode":"BREAK_ALREADY_IN_PROGRESS","message":"A break is already in progress" }
    ```
- UI must:
  - Render `fieldErrors` inline
  - On 409: show message and reload context automatically
  - Surface `requestId`/correlation id if present in headers/body (see Audit & Observability)

## 10. State Model & Transitions

### Allowed states (break)
- `IN_PROGRESS` (represented by `endedAt == null`)
- `COMPLETED` (represented by `endedAt != null`)

### Role-based transitions
- Mechanic:
  - No active break → Start Break → active break exists
  - Active break exists → End Break → no active break
- System:
  - Active break → auto-end at clock-out; `autoEnded=true` (DECISION-PEOPLE-007)

### UI behavior per state
- **No active break**
  - Enable Start Break (if clocked in)
  - Disable End Break
- **Active break**
  - Disable Start Break
  - Enable End Break
  - Show active break details and elapsed time (display-only)
- **Auto-ended break observed**
  - In list, show indicator “Auto-ended at clock-out” when `autoEnded=true`

## 11. Alternate / Error Flows

### Validation failures (400)
- Missing `breakType`:
  - UI blocks submit client-side (required field).
  - If server still returns 400, render `fieldErrors.breakType`.
- Invalid enum:
  - Render server message; keep modal open for correction.

### Concurrency conflicts / state mismatch (409)
- Start break while break already started elsewhere:
  - Show conflict message.
  - Close modal (optional) and reload context.
- End break when already ended (manual or auto-ended):
  - Show conflict message (“No active break to end” or server-provided message).
  - Reload context.

### Unauthorized access (401/403)
- 401: route to login/session-expired.
- 403: show access denied; hide/disable break actions; still allow viewing break list if context endpoint permits (server decides).

### Empty states
- No breaks today:
  - Show “No breaks recorded today.”
- Context endpoint returns `breaksToday=[]` and `activeBreak=null`:
  - Render stable empty state; no errors.

## 12. Acceptance Criteria

### Scenario 1: Start break successfully
**Given** I am authenticated as a Mechanic  
**And** the break context indicates I am clocked in  
**And** the break context indicates I have no active break  
**When** I choose `breakType = MEAL` and submit “Start Break”  
**Then** the UI shows a success confirmation  
**And** the UI reloads break context  
**And** the UI shows an active break in progress with the returned start time  
**And** the “Start Break” action is disabled and “End Break” is enabled

### Scenario 2: End break successfully
**Given** I am authenticated as a Mechanic  
**And** the break context indicates I have an active break  
**When** I click “End Break”  
**Then** the UI shows a success confirmation  
**And** the UI reloads break context  
**And** the UI shows no active break  
**And** the completed break appears in today’s break list with an end time

### Scenario 3: Prevent overlapping / duplicate start (409 refresh-required)
**Given** I am authenticated as a Mechanic  
**And** I attempt to start a break while a break is already in progress (server state)  
**When** the start-break request returns HTTP 409 with `errorCode=BREAK_ALREADY_IN_PROGRESS`  
**Then** the UI displays the server message (or a mapped friendly message)  
**And** the UI reloads break context automatically  
**And** the UI shows the existing active break and does not show a newly created break

### Scenario 4: Require break type on start (client-side + server-side)
**Given** I am authenticated as a Mechanic  
**And** I am clocked in  
**When** I open “Start Break” and submit without selecting a break type  
**Then** the UI shows an inline validation error indicating break type is required  
**And** no start-break request is sent  
**And** if a request is sent and the server returns 400 with `fieldErrors.breakType`, the UI renders that field error inline

### Scenario 5: Cannot start break when not clocked in
**Given** I am authenticated as a Mechanic  
**And** the break context indicates I am not clocked in  
**When** I view the timekeeping screen  
**Then** the “Start Break” control is disabled  
**And** the UI explains I must be clocked in to start a break  
**And** if I still invoke the start action and the server returns 409/400 indicating not clocked in, the UI displays the message and reloads break context

### Scenario 6: Cannot end break when none is active (409 refresh-required)
**Given** I am authenticated as a Mechanic  
**And** the break context indicates I have no active break  
**When** I attempt to end a break  
**Then** the UI disables “End Break”  
**And** if the end-break request returns HTTP 409 (no active break / already ended), the UI displays the server message and reloads break context

### Scenario 7: `breakType=OTHER` notes are optional but prompted
**Given** I am authenticated as a Mechanic  
**And** I am clocked in and have no active break  
**When** I select `breakType=OTHER`  
**Then** the UI displays helper text prompting for notes  
**And** I can submit without notes  
**And** the break is started successfully if the server accepts it

### Scenario 8: Auto-ended breaks are visible
**Given** I have a completed break in today’s list with `autoEnded=true`  
**When** I view today’s breaks  
**Then** the UI displays an “Auto-ended” indicator for that break  
**And** the UI does not offer any edit action for that break

### Scenario 9: Timezone display rule is applied and labeled
**Given** the break context response includes `displayTimezone`  
**When** I view break start/end times  
**Then** the UI displays times in that timezone  
**And** the UI labels the timezone used (e.g., “Times shown in America/Chicago”)
