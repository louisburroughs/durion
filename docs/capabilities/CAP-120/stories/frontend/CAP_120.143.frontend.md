## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Timekeeping: Export Approved Time for Accounting/Payroll

### Primary Persona
Accounting Clerk (Accounting user)

### Business Value
Enable payroll and cost accounting processing by exporting **only** approved time entries with payroll-facing identifiers, with a complete audit trail of export activity.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Accounting Clerk  
- **I want** to export approved time entries by date range and location(s) in CSV or JSON  
- **So that** payroll processing and cost accounting can be performed using payroll-facing identifiers and a stable definition of “APPROVED”.

### In-scope
- A Moqui screen flow to:
  - Choose **date range** (inclusive) and **one or more locations**
  - Choose **format** (CSV or JSON)
  - Request an **asynchronous** export job
  - Poll/refresh status and download the resulting file when ready
- Display export outcome:
  - records exported count
  - records skipped count due to missing mappings (if provided)
  - `exportId` (always) and correlation/trace identifiers (if provided)
- User-visible audit visibility:
  - “Export requested by/when/parameters/status”
  - History list of prior export requests (via backend history endpoint)

### Out-of-scope
- Creating/maintaining payroll identity mappings (employee/location → payroll IDs)
- Approving/unapproving time entries
- Scheduling recurring exports
- Editing/exporting non-approved time entries
- Building backend export logic (frontend consumes `/accounting/export/*` endpoints only)
- Downloadable “skipped entries detail report” (counts only in this story; see Open Questions for optional future enhancement)

---

## 3. Actors & Stakeholders
- **Primary Actor:** Accounting Clerk
- **Stakeholders:**
  - Payroll processors (downstream consumers of export file)
  - Cost accounting analysts
  - Auditors/Compliance (require immutable audit record)
  - People/Timekeeping domain owners (system of record for time entry + approval)
  - Location domain owners (system of record for locations and user-authorized location visibility)

## 4. Preconditions & Dependencies
- User is authenticated in the Moqui frontend.
- User has permission(s):
  - View screen: `accounting:time-export:view`
  - Execute export: `accounting:time-export:execute` (**Decision AD-013**)
- Backend provides Accounting export capability:
  - `POST /accounting/export/request`
  - `GET  /accounting/export/status?exportId=...`
  - `GET  /accounting/export/download?exportId=...`
  - `GET  /accounting/export/history` (recommended and in-scope for this story) (**Decision AD-005**)
- Locations list is available to the frontend from the Location domain and is already filtered by user authorization:
  - Only active locations
  - Only locations the user is authorized to view/select (**Decision B4**)
- Timezone semantics:
  - Export date range is interpreted in the **location timezone**; UI must label this clearly (**Decision AD-015**)
- Identifier strategy:
  - `exportId` is UUIDv7; UI validates UUID format client-side (**Decision AD-006**)
- Correlation/tracing:
  - Frontend propagates W3C Trace Context headers (`traceparent`, `tracestate`) unchanged; generate `traceparent` only if absent (**Decision AD-008**)

   - Parameter form (date range, locations, format)
   - “Request export” action
   - Current/last request status panel (exportId, status, counts, timestamps)
   - Download action when READY
2. **New Screen (in-scope):** `Accounting/Timekeeping/ExportHistory.xml`
   - List of prior export requests (paged)
   - Link to detail (either inline expand or navigate back to ExportApprovedTime with exportId preloaded)
3. **Optional (if preferred by repo patterns):** `Accounting/Timekeeping/ExportDetail.xml`
   - Dedicated detail view for a single exportId (status, counts, parameters, download)

### Navigation context
- Breadcrumb: Accounting → Timekeeping Exports → Export Approved Time
- From Export Approved Time:
  - Run a new export
  - Navigate to Export History
- From Export History:
  - View export detail and download if READY

### User workflows (happy + alternate paths)

**Happy path (async job):**
1. User opens Export Approved Time screen.
2. Selects `startDate`, `endDate`, one-or-more `locationIds`, and `format`.
3. Clicks **Request Export**.
4. UI validates inputs client-side and submits `POST /accounting/export/request`.
5. Backend returns `exportId` and initial `status=QUEUED` (or `PROCESSING`).
6. UI shows status and begins polling (or offers manual refresh).
7. When status becomes `READY`, UI enables **Download**.
8. User downloads file via `GET /accounting/export/download?exportId=...`.
9. UI shows completion summary (exported/skipped counts) and retains exportId for audit.

**Alternate path (FAILED):**
- Status becomes `FAILED`; UI shows backend `errorCode`/message (user-safe), keeps parameters for retry, and provides a “Request new export” action (new exportId).

**Alternate path (empty dataset):**
- Export completes with `READY` and `recordsExportedCount=0`; download still available and UI indicates 0 exported.

**Alternate path (no locations available):**
- Location selector loads empty; UI blocks request and shows “No authorized active locations available.”

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `startDate` required.
- `endDate` required.
- `endDate >= startDate` (inclusive).
- `locationIds` required; must contain at least 1 locationId.
- `format` required and constrained to `CSV` or `JSON`.
- `exportId` inputs (when manually entered or deep-linked) must be valid UUIDv7 format; block invalid input with inline error (**Decision AD-006**).

### Enable/disable rules
- If user lacks `accounting:time-export:execute`:
  - Hide/disable **Request Export** and show read-only messaging.
- Disable **Request Export** while `REQUESTING` is in flight.
- Disable **Download** unless `status == READY`.
- Disable polling when:
  - `status == READY` or `status == FAILED`
  - user navigates away
- If no locations available:
  - Disable **Request Export** and show blocking empty state.

### Visibility rules
- Always show timezone note:
  - “Dates interpreted in selected location timezone(s).” (**Decision AD-015**)
  - If multiple locations selected with different timezones, show a warning banner: “Multiple location timezones selected; export uses each location’s local timezone semantics as defined by backend.” (No conversion performed in UI.)
- Skipped entries:
  - Show counts only (`recordsSkippedCount`) and a generic reason label if backend provides one.
  - Do not display per-entry details in this story (PII minimization; optional future enhancement).

### Error messaging expectations
- Use backend error schema `{errorCode, message, details?}`:
  - Inline field errors when `details` maps to known fields (`startDate`, `endDate`, `locationIds`, `format`, `exportId`).
  - Otherwise show top-level error banner with `message` and include `errorCode` for support.
- 403:
  - “You do not have permission to export approved time.”
- 404:
  - For status/download by exportId: “Export not found or you do not have access.”
- 409:
  - Show “Conflict. Refresh status and try again.” (Do not claim “already in progress” unless backend explicitly returns that meaning.)
- 5xx/timeout:
  - Show retry guidance; preserve user inputs; do not clear exportId if already created.

- Response: paged list with rows (see Data Requirements)

### Create/update calls

1. **Request export (async only)**
- `POST /accounting/export/request`
- Request body:
  ```json
  {
    "startDate": "YYYY-MM-DD",
    "endDate": "YYYY-MM-DD",
    "locationIds": ["<UUIDv7>", "..."],
    "format": "CSV"
  }
  ```
- Response body:
  ```json
  {
    "exportId": "<UUIDv7>",
    "status": "QUEUED"
  }
  ```

### Submit/transition calls

1. **Download export artifact**
- `GET /accounting/export/download?exportId=<UUIDv7>`
- Expected behavior:
  - Only valid when status is `READY`
  - Returns a binary stream with appropriate `Content-Type` and `Content-Disposition` filename
- UI behavior:
  - Use browser download handling; do not attempt to render file contents in UI.

### Error handling expectations
- Standard error schema:
  ```json
  { "errorCode": "SOME_CODE", "message": "User-safe message", "details": { } }
  ```
- Map:
  - 400/422 → inline errors when possible; otherwise banner
  - 401/403 → access denied (no existence leakage)
  - 404 → not found or no access (safe message)
  - 409 → conflict; prompt refresh/retry
  - 5xx/timeouts → retry guidance; preserve inputs and last known exportId

### Correlation/tracing headers
- Propagate `traceparent` and `tracestate` on all calls; generate `traceparent` only if absent (**Decision AD-008**).

## 10. State Model & Transitions

### Allowed states
Backend export status (authoritative):
- `QUEUED`
- `PROCESSING`
- `READY`
- `FAILED` (**Decision AD-005**)

Frontend-local UI states:
- `IDLE`
- `VALIDATION_ERROR`
- `REQUESTING`
- `POLLING`
- `DOWNLOADING`

### Role-based transitions
- Only users with `accounting:time-export:execute` can initiate `REQUESTING` (request export).
- Users with `accounting:time-export:view` can view status/history and download if READY (download permission is implied by view; if backend enforces separate permission, UI must follow backend 403).

### UI behavior per state
- `IDLE`: show form; if last exportId exists, show last status.
- `REQUESTING`: disable form submit; show spinner.
- `POLLING`: show “Last checked at …”; allow manual refresh; stop polling on READY/FAILED.
- `READY`: enable Download; show counts.
- `FAILED`: show errorCode/message; allow requesting a new export.

## 11. Alternate / Error Flows

### Validation failures
- Missing dates, invalid range, no locations selected:
  - Prevent submit; show inline errors and summary.
- Invalid exportId (when user pastes/enters one on history/detail):
  - Block status/download calls; show “Invalid ID format (UUID required).”

### Concurrency conflicts
- If status changes between refreshes:
  - UI always displays latest backend status; no optimistic assumptions.
- If backend returns 409 on request:
  - Show conflict banner and keep inputs; user may retry.
  - Do not claim idempotency semantics unless backend documents them for exports.

### Unauthorized access
- If user lacks `accounting:time-export:view`:
  - Screen entry point hidden; direct navigation results in safe “Not authorized.”
- If user has view but not execute:
  - Show screen read-only; hide/disable Request Export; allow history/status viewing.

### Empty states
- No locations returned:
  - Blocking empty state; no export possible.
- History empty:
  - Show “No exports yet” with guidance to request one (if execute permission present).

## 12. Acceptance Criteria

### Scenario 1: Request export (CSV) creates async job and becomes downloadable when READY
**Given** the user has `accounting:time-export:view` and `accounting:time-export:execute`  
**And** the user selects a valid inclusive date range, at least one authorized location, and `format = CSV`  
**When** the user clicks Request Export  
**Then** the UI sends `POST /accounting/export/request` with the selected parameters  
**And** the UI displays the returned `exportId` and initial `status`  
**And** the UI refreshes status via `GET /accounting/export/status` until the status is `READY` or `FAILED`  
**And** when status is `READY`, the Download action is enabled.

### Scenario 2: Download is only available when READY
**Given** an export exists with `status = PROCESSING`  
**When** the user views the export status panel  
**Then** the Download action is disabled/hidden  
**And** when the status becomes `READY`, the Download action becomes enabled  
**And** clicking Download calls `GET /accounting/export/download?exportId=...` and triggers a browser file download.

### Scenario 3: Export succeeds with empty dataset
**Given** the user has execute permission  
**And** the backend determines there are zero APPROVED time entries for the selected range/locations  
**When** the user requests an export  
**Then** the export reaches `READY`  
**And** the UI displays `recordsExportedCount = 0`  
**And** the user can still download the export artifact.

### Scenario 4: Client blocks invalid date range
**Given** the user is on the Export Approved Time screen  
**When** the user sets `endDate` earlier than `startDate` and clicks Request Export  
**Then** the UI prevents submission  
**And** shows an inline validation error that end date must be on or after start date.

### Scenario 5: Missing mapping causes skipped entries (counts only)
**Given** the backend reports `recordsSkippedCount > 0` for an export in READY state  
**When** the user views the export results  
**Then** the UI displays the skipped count  
**And** the UI does not display per-entry skipped details in this story.

### Scenario 6: Unauthorized user cannot execute export
**Given** the user has `accounting:time-export:view` but lacks `accounting:time-export:execute`  
**When** the user navigates to Export Approved Time  
**Then** the UI does not allow requesting an export (button hidden/disabled)  
**And** the user can still view history/status if available.

### Scenario 7: Export history is visible and navigable
**Given** the user has `accounting:time-export:view`  
**When** the user opens Export History  
**Then** the UI loads history via `GET /accounting/export/history` with pagination parameters  
**And** each row shows `exportId`, status, requestedAt, parameters, and counts when available  
**And** the user can navigate to a specific export to view status and download if READY.
