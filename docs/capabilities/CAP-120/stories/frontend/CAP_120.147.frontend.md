## Issue Body

## Title
**[FRONTEND] Timekeeping: Manager Approves/Rejects Time Entries (Period-Atomic)**

## Primary Persona
**Manager** (authorized to approve time for direct reports)

## Business Value
Finalizes employee time for a pay period with an auditable decision record, enabling payroll export and downstream reconciliation while preventing unauthorized or inconsistent edits.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Manager  
- **I want** to review an employee’s time entries for a selected pay period and approve or reject them in one atomic action  
- **So that** time is finalized (approved = locked) or returned for correction (rejected), with a complete audit trail.

## In-Scope
- Manager UI to:
  - Select an employee (direct report / authorized scope) and a pay period
  - View timekeeping entries and their statuses for that period
  - Approve all entries in `PENDING_APPROVAL` for the period (atomic)
  - Reject all entries in `PENDING_APPROVAL` for the period (atomic) with optional comments
  - View decision history (period-level approvals/rejections; append-only)
- Frontend enforcement of read-only behavior for approved entries (no edit controls in this manager view).
- Correct handling of backend validation errors (`400`), authorization (`403`), conflicts (`409`), and not-found (`404`).
- Optimistic concurrency handling when backend provides a concurrency token (prefer `lastUpdatedStamp`) for approval actions or underlying aggregates.

## Out-of-Scope
- Employee-side time entry editing/resubmission flow after rejection.
- “Controlled adjustments” workflow UI (TimeEntryAdjustment create/approve).
- Defining reporting relationships, role inheritance, or permission matrix (must be provided by backend/security).
- Payroll export UX.

---

# 3. Actors & Stakeholders
- **Manager (Primary Actor):** reviews and decides for employee/time period.
- **Employee (Indirect):** impacted by approval (locks) or rejection (returns to pending correction workflow outside this story).
- **HR/People Ops (Stakeholder):** needs auditable records.
- **Payroll System (Stakeholder):** consumes approved time (downstream).
- **Work Execution / Shop Management (Stakeholder):** source of timekeeping ingestion; may consume approved job time for posting (read-only integration point).

---

# 4. Preconditions & Dependencies
- User is authenticated in the frontend session.
- Backend enforces authorization; UI gates actions using named permissions/capabilities.
  - **Decision rationale:** Approval authorization is permission-based and server-enforced (DECISION-PEOPLE-010, DECISION-PEOPLE-013).
- User has permission **`TIME_APPROVE`** (canonical for time approvals).
  - **Decision rationale:** Explicit permission required for approvals (DECISION-PEOPLE-010). (Do not rely on role-name heuristics.)
- Backend provides:
  - List of employees the manager may act on (scope filtered; no leakage)
  - List of time periods and their status (`OPEN`, `SUBMISSION_CLOSED`, `PAYROLL_CLOSED`)
  - Ability to fetch timekeeping entries for `{personId, timePeriodId}`
  - Action endpoints to approve/reject (period-atomic) and return appropriate status codes and error payloads (DECISION-PEOPLE-006, DECISION-PEOPLE-018, DECISION-PEOPLE-021)
- Time period gating is enforced by backend; UI may pre-disable actions but must not be the policy engine.
- Timezone display: backend stores instants in UTC; UI displays in user profile timezone when available, else location timezone (DECISION-PEOPLE-015).

## Entry points
- From Manager menu: **People → Timekeeping → Approvals**
- Deep link supported: `/people/timekeeping/approvals?personId=&timePeriodId=`

## Screens to create/modify

   - Purpose: selection controls + results panel (entries + history) + actions
2. **Subscreen (optional):** `apps/pos/people/timekeeping/approvals/detail.xml` (optional)
   - Purpose: isolate detail rendering and allow deep-linking cleanly
3. Forms/widgets:
   - Selection form (employee/person + pay period)
   - Entries list (read-only)
   - Decision history list (read-only)
   - Reject dialog form (optional comments)

## Navigation context
- Breadcrumb: `People > Timekeeping > Approvals`

## User workflows (happy + alternate)

### Happy path: Approve
1. Manager opens Approvals screen.
2. Manager selects Employee + Pay Period (or arrives via deep link).
3. System loads entries and approval history.
4. If eligible, Manager clicks **Approve Period** and confirms.
5. UI calls approve action; on success refreshes entries and history; shows success message.

### Happy path: Reject
1. Manager clicks **Reject Period**.
2. UI opens dialog with optional comments (not required by default).
3. Submit triggers reject action; on success refreshes entries and history; shows success message.

### Alternate paths
- Period not eligible (`OPEN`): decision buttons disabled with explanatory message; entries/history still viewable.
- Mixed statuses / already decided: decision buttons disabled; if action attempted (e.g., stale UI), API returns `409` and UI prompts refresh.
- Unauthorized: UI shows “Not authorized” and hides decision controls; do not reveal whether a person is a direct report.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- **Period-atomic decisioning:** Approve/reject applies to **all** entries in the period for the selected person; no partial selection UI.
  - **Decision rationale:** Period-level atomic approvals with append-only history (DECISION-PEOPLE-006).
- **Reject metadata:** `comments` (or `notes`) is **optional** by default.
  - **Decision rationale:** Domain decision specifies comments as optional in approval record examples; no People decision requires a rejection reason code for time approvals (DECISION-PEOPLE-006). The prior “required reason” is removed to avoid inventing policy.
- Client-side validation:
  - Require `personId` and `timePeriodId` before loading detail/actions.
  - If reject dialog includes an optional comments field, enforce max length if backend provides constraints; otherwise allow empty.
- Server-side validation handling:
  - `400` with `fieldErrors` must be rendered without losing user input (DECISION-PEOPLE-018).

## Enable/disable rules
- Disable Approve/Reject if:
  - No person or no pay period selected
  - Detail not loaded
  - `actionInFlight=true`
  - Period status is `OPEN` (show message: “Approval available after submission closes.”)
  - Period status is `PAYROLL_CLOSED` (show message: “Payroll is closed for this period.”)
  - Any entry status != `PENDING_APPROVAL` (show message: “All entries must be Pending Approval to decide this period.”)
- Additionally, if backend returns capability flags (preferred), UI must honor them:
  - Example: `canApprove=false` or `canReject=false` disables respective action even if local checks pass.
  - **Decision rationale:** UI gates by named permissions and backend-provided capabilities (DECISION-PEOPLE-013).

## Visibility rules
- If user lacks `TIME_APPROVE` (as indicated by auth context/capabilities), hide decision buttons; still allow viewing if backend permits view.
- Decision history panel visible when selection is made; show empty state if none.

## Error messaging expectations
- `400`: show field-level errors (reject dialog if applicable) and keep dialog open.
- `403`: show generic authorization message; do not reveal whether person exists or is in scope.
- `404`: show “Not found” for the selection; offer to clear selection.
- `409`: show conflict banner “Time entries changed or were already decided. Please refresh.” If response includes `blockingIds`, list them as entry IDs (no extra lookup unless already available).
- Include request/correlation ID in error UI when present (observability requirement).

# 9. Service Contracts (Frontend Perspective)

## Load/view calls
All endpoints follow People REST conventions (DECISION-PEOPLE-021) and error schema (DECISION-PEOPLE-018). Use paging for lists.

1. **List manager-authorized people (direct reports / scope)**
   - `GET /rest/api/v1/people/timekeeping/approvals/people`
   - Query: `page`, `pageSize`, optional `q` (search by name/employeeNumber)
   - Response:
     ```json
     { "items":[{"personId":"...","displayName":"...","employeeNumber":"..."}], "page":1, "pageSize":25, "total":123 }
     ```
   - Notes:
     - Backend must scope-filter; UI must not infer relationships.

2. **List time periods**
   - `GET /rest/api/v1/people/timekeeping/time-periods`
   - Query: `page`, `pageSize`, optional `status` filter
   - Response:
     ```json
     { "items":[{"id":"...","status":"SUBMISSION_CLOSED","periodStartAt":"...","periodEndAt":"..."}], "page":1, "pageSize":25, "total":10 }
     ```

3. **List timekeeping entries for person + period**
   - `GET /rest/api/v1/people/timekeeping/timekeeping-entries`
   - Query: `personId` (required), `timePeriodId` (required), `page`, `pageSize`
   - Response:
     ```json
     { "items":[{ "id":"...","personId":"...","timePeriodId":"...","status":"PENDING_APPROVAL","clockInAt":"...","clockOutAt":"..." }], "page":1, "pageSize":100, "total":12 }
     ```

4. **List approval history for person + period**
   - `GET /rest/api/v1/people/timekeeping/time-period-approvals`
   - Query: `personId` (required), `timePeriodId` (required), `page`, `pageSize`
   - Response:
     ```json
     { "items":[{ "id":"...","outcome":"APPROVED","approvedAt":"...","approvedByUserId":"...","entryCount":12,"comments":null }], "page":1, "pageSize":25, "total":2 }
     ```

5. **Load capabilities for current selection (optional but preferred)**
   - Option A: included in list responses as top-level `capabilities`
   - Option B: separate endpoint:
     - `GET /rest/api/v1/people/timekeeping/approvals/capabilities?personId=&timePeriodId=`
   - Response example:
     ```json
     { "canApprove": true, "canReject": true, "reasons": null }
     ```

## Submit/transition calls (actions)
1. **Approve period (atomic)**
   - `POST /rest/api/v1/people/timekeeping/time-periods/{timePeriodId}/people/{personId}/approve`
   - Body (optional):
     ```json
     { "requestId":"<uuid>", "lastUpdatedStamp":"<optional>" }
     ```
   - Success `200 OK`:
     - Preferred: lightweight response with resulting approval record:
       ```json
       { "approval": { "id":"...","outcome":"APPROVED","approvedAt":"...","entryCount":12 }, "warnings":[] }
       ```
     - UI behavior: always re-fetch entries + history after success (do not rely on returned lists).
   - Idempotency:
     - UI sends `requestId` and treats repeated submissions as safe; backend may dedupe by `requestId` if implemented.

2. **Reject period (atomic)**
   - `POST /rest/api/v1/people/timekeeping/time-periods/{timePeriodId}/people/{personId}/reject`
   - Body:
     ```json
     { "requestId":"<uuid>", "comments":"<optional>", "lastUpdatedStamp":"<optional>" }
     ```
   - Success `200 OK`:
     ```json
     { "approval": { "id":"...","outcome":"REJECTED","approvedAt":"...","entryCount":12,"comments":"..." }, "warnings":[] }
     ```
   - UI behavior: re-fetch entries + history after success.

## Error handling expectations
- `400`:
  ```json
  { "errorCode":"VALIDATION_ERROR","message":"...","fieldErrors":[{"field":"comments","message":"..."}] }
  ```
- `403`:
  ```json
  { "errorCode":"FORBIDDEN","message":"Not authorized" }
  ```
- `404`:
  ```json
  { "errorCode":"NOT_FOUND","message":"Not found" }
  ```
- `409`:
  ```json
  { "errorCode":"CONFLICT","message":"...","blockingIds":["<timekeepingEntryId>"],"details":{...} }
  ```
- Optimistic concurrency:
  - If backend requires `lastUpdatedStamp`, missing or stale token returns `409` (DECISION-PEOPLE-017).

# 10. State Model & Transitions

## Allowed states
### TimekeepingEntry.status (line-level)
- `DRAFT`
- `SUBMITTED`
- `PENDING_APPROVAL`
- `APPROVED`

### TimePeriod.status (gating)
- `OPEN`
- `SUBMISSION_CLOSED`
- `PAYROLL_CLOSED`

### TimePeriodApproval.outcome (history)
- `APPROVED`
- `REJECTED`

## Role-based transitions
- **Manager / Approver (has `TIME_APPROVE` and scope):**
  - Approve: all `PENDING_APPROVAL → APPROVED` (period-atomic)
  - Reject: records `REJECTED` in history and returns entries to a non-approved state as defined by backend (UI expects `DRAFT` or `SUBMITTED`; see below)
    - **Decision rationale:** Period-atomic approvals with append-only history; approved entries are immutable (DECISION-PEOPLE-006).

## UI behavior per state
- If any entries are `APPROVED`: show read-only; disable decisions (not all pending).
- If period status `OPEN`: show entries/history; disable decisions due to gating.
- If period status `PAYROLL_CLOSED`: disable decisions; backend must enforce.

> Note on reject resulting status:
> - UI will not hardcode the post-reject status; it will re-fetch and display whatever statuses backend sets, while still treating `APPROVED` as immutable/read-only.
> - **Decision rationale:** UI must not invent state transitions beyond People decisions; backend is SoR for workflow (DECISION-PEOPLE-006, DECISION-PEOPLE-013).

# 11. Alternate / Error Flows

## Validation failures (400)
- Reject submit with invalid payload (e.g., comments too long):
  - Keep dialog open
  - Render `fieldErrors` inline
  - Preserve user input

## Concurrency conflicts (409)
- Approve/reject returns `409` due to:
  - entry status changed since load
  - period closed/opened state changed
  - optimistic concurrency token mismatch
- UI behavior:
  - Show banner “Time entries changed. Please refresh.”
  - Provide **Refresh** action
  - After refresh, recompute eligibility and update UI

## Unauthorized access (403)
- If list/detail endpoints return `403`:
  - Show authorization error state
  - Do not render employee list details beyond generic message
  - Do not attempt fallback lookups that could leak existence

## Not found (404)
- If deep link references missing/unauthorized resources:
  - Show “Not found” state
  - Offer to clear selection and return to pickers

## Empty states
- No employees returned: show “No employees available for approval.”
- No entries for selection: show empty table and disable decisions.
- No history: show “No approval decisions recorded for this period.”

# 12. Acceptance Criteria

## Scenario 1: Manager views entries and history for an employee and period
**Given** I am authenticated as a user with permission `TIME_APPROVE`  
**And** I select a person I am authorized to manage  
**And** I select a time period  
**When** the approvals view loads  
**Then** I see timekeeping entries for that `{personId,timePeriodId}` (paged)  
**And** I see each entry’s status  
**And** I see the period decision history (or an empty-state message)

## Scenario 2: Approve period succeeds (atomic)
**Given** all timekeeping entries for `{personId,timePeriodId}` are `PENDING_APPROVAL`  
**And** the selected `TimePeriod.status` is `SUBMISSION_CLOSED`  
**When** I click “Approve Period” and confirm  
**Then** the UI calls the approve endpoint once with a generated `requestId`  
**And** on success the UI re-fetches entries and history  
**And** I see entries in `APPROVED` status (as returned by the server)  
**And** the decision history shows a new record with `outcome=APPROVED` and `approvedAt`

## Scenario 3: Reject period succeeds with optional comments (atomic)
**Given** all timekeeping entries for `{personId,timePeriodId}` are `PENDING_APPROVAL`  
**And** the selected `TimePeriod.status` is `SUBMISSION_CLOSED`  
**When** I click “Reject Period”  
**And** I submit the rejection with optional comments  
**Then** the UI calls the reject endpoint once with a generated `requestId`  
**And** on success the UI re-fetches entries and history  
**And** the decision history shows a new record with `outcome=REJECTED` and any comments returned by the server

## Scenario 4: Period not eligible disables decisions
**Given** I have selected a person and a time period with `status=OPEN`  
**When** the detail loads  
**Then** the Approve and Reject actions are disabled  
**And** I see a message indicating approval is available after submission closes

## Scenario 5: Mixed statuses prevent decision (conflict)
**Given** at least one timekeeping entry in the period is not `PENDING_APPROVAL`  
**When** I attempt to approve or reject (via stale UI or deep link)  
**Then** the API returns `409 Conflict`  
**And** the UI displays a conflict message prompting refresh  
**And** if `blockingIds` are provided, they are displayed as the blocking entry IDs

## Scenario 6: Unauthorized user cannot decide and does not see relationship details
**Given** I am authenticated but not authorized to approve time for the selected person  
**When** I attempt to load or decide on the period  
**Then** the API returns `403 Forbidden`  
**And** the UI shows a generic “Not authorized” message  
**And** the UI does not expose whether the person exists or is a direct report

## Scenario 7: Optimistic concurrency conflict is handled
**Given** the backend requires `lastUpdatedStamp` for approve/reject  
**And** my loaded token is stale  
**When** I submit approve or reject  
**Then** the API returns `409 Conflict`  
**And** the UI prompts me to refresh  
**And** after refresh I can retry the action if still eligible
