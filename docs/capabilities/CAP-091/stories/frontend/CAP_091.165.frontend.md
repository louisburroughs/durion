Provide an **operational UI in Moqui** to view and troubleshoot `VehicleUpdated` event ingestion outcomes (success/duplicate/error/pending review), enabling faster resolution of data sync issues and ensuring CRM vehicle data accuracy over time.

## 2. Story Intent

### As a / I want / So that
- **As a** CRM Data Steward / Support Engineer  
- **I want** a Moqui screen to search and inspect VehicleUpdated event processing logs (by vehicleId/workorderId/eventId/status/time) and drill into the affected Vehicle  
- **So that** I can audit ingestion, detect duplicates/errors, and take appropriate follow-up actions when conflicts or not-found errors occur.

### In-scope
- Moqui **screens + forms + transitions** for:
  - Listing/searching ingestion processing records (**ProcessingLog**) for `eventType=VehicleUpdated`
  - Viewing a single processing record’s details
  - Linking to a Vehicle detail view (read-only for this story; may reuse existing vehicle screen)
- UI handling for empty states, loading, and error responses
- Role/permission-gated access to these operational screens
- Redaction-safe rendering of `details` and payload-related fields (no raw payload)

### Out-of-scope
- Implementing the actual event consumer / ingestion logic (backend responsibility)
- Manual remediation actions (e.g., “reprocess event”, “override vehicle”, “mark resolved”)
- Defining thresholds for “significant mileage decrease” (configurable backend policy; UI displays reason codes only)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUID fields (`eventId`, `processingLogId`, `vehicleId`, `workorderId`, `estimateId`) must match UUID format before submitting.
- Date range validation: `receivedAtFrom <= receivedAtTo`.
- Correlation filter semantics:
  - Support **exact** and **prefix** only.
  - If user selects/enters a “contains” search, UI must block submission and explain “Contains search is not supported for correlationId” (DECISION-INVENTORY-008).
- Minimum filter requirements:
  - No minimum required; list may be loaded with only date range defaults (see Applied Safe Defaults). This is UI ergonomics only and does not change backend behavior.

### Enable/disable rules
- “View Vehicle” link/button is enabled only when `vehicleId` is present in the DTO.
- If navigation to vehicle results in 404/409 (merged/other) from vehicle screen, vehicle screen handles it; this story only guarantees the link is conditionally shown.

### Visibility rules
- Entry points and screens are visible only with explicit permission:
  - Proposed permission key: `crm.integrations.processingLogs.read` (DECISION-INVENTORY-007 taxonomy guidance; exact role mapping is security-owned and safe-to-defer).
- Sensitive fields:
  - UI must never display raw payload; only `payloadSummary` and `redactedPayload` if provided (DECISION-INVENTORY-006).
  - UI must not log `details`, `redactedPayload`, VIN, or license plate to client telemetry (DECISION-INVENTORY-006, DECISION-INVENTORY-004).

### Error messaging expectations
- 400 validation error: show inline field errors when provided; otherwise show banner with backend `message`.
- 401/403: show “Access denied” state; do not render any partial list/detail.
- 404 on detail: show “Processing log not found” with a back link to list (preserving prior filters if possible).
- 5xx/network: show retryable error banner and preserve user-entered filters.

## 9. Service Contracts (Frontend Perspective)

## 10. State Model & Transitions

### Allowed states (ProcessingLog.status)
UI must treat status as backend-owned enum; at minimum support rendering these known values:
- `SUCCESS`
- `DUPLICATE`
- `ERROR_VALIDATION`
- `ERROR_NOT_FOUND`
- `PENDING_REVIEW` (DECISION-INVENTORY-011)

If an unknown status is returned, UI displays it as “UNKNOWN(<value>)” without breaking.

### Role-based transitions
- None.

### UI behavior per state
- `SUCCESS`: standard row; detail shows timestamps.
- `DUPLICATE`: show informational badge; detail should still show `eventId` and received time.
- `ERROR_VALIDATION` / `ERROR_NOT_FOUND`: show error badge; detail shows `payloadSummary`/`details` (redacted).
- `PENDING_REVIEW`: show prominent notice “Pending review” and display `reasonCode` and conflict metadata (if provided). UI must not imply it can resolve the review.

## 12. Acceptance Criteria

### Scenario 1: View recent VehicleUpdated processing logs
**Given** I am an authorized CRM support user with permission `crm.integrations.processingLogs.read`  
**When** I navigate to CRM → Integrations → VehicleUpdated Processing Logs  
**Then** I see a paginated list of ProcessingLog records scoped to `eventType=VehicleUpdated`  
**And** the list is sorted by `receivedAt` descending by default  
**And** each row shows `eventId`, `status`, `receivedAt`, and any present of `vehicleId`, `workorderId`, `estimateId`

### Scenario 2: Filter logs by status and vehicleId
**Given** I am on the VehicleUpdated Processing Logs screen  
**When** I filter by `status = ERROR_NOT_FOUND` and `vehicleId = <valid-uuid>` and submit  
**Then** only matching records are shown  
**And** the active filters remain visible after results load  
**And** pagination reflects the backend `total`

### Scenario 3: Correlation filter supports prefix but not contains
**Given** I am on the VehicleUpdated Processing Logs screen  
**When** I enter `correlationIdPrefix = "ESTIMATE:"` and submit  
**Then** the request is executed and results are shown (if any)  
**When** I attempt to use a “contains” correlation search  
**Then** the UI blocks submission and shows “Contains search is not supported; use exact match or starts with”

### Scenario 4: View processing log detail and copy identifiers
**Given** a ProcessingLog record exists with `processingLogId = <uuid>`  
**When** I open the record detail view  
**Then** I see all returned fields including `eventId`, `status`, `receivedAt`, and any present of `workorderId`, `estimateId`, `vehicleId`, `reasonCode`  
**And** I can copy `processingLogId` and `eventId` from the page

### Scenario 5: Pending review shows reason code and does not offer actions
**Given** I am viewing a ProcessingLog detail with `status = PENDING_REVIEW`  
**When** the detail loads  
**Then** I see a “Pending review” notice  
**And** I see `reasonCode` and any provided conflict metadata (redacted)  
**And** there are no buttons to retry/reprocess/resolve the event

### Scenario 6: Redaction and payload handling
**Given** a ProcessingLog detail includes `payloadSummary` and `redactedPayload`  
**When** I view the detail  
**Then** I can view `payloadSummary` and `redactedPayload`  
**And** there is no UI control to view raw/unredacted payload  
**And** the UI renders payload/details as text/JSON only (no HTML rendering)

### Scenario 7: Client-side validation prevents invalid UUID search
**Given** I am on the VehicleUpdated Processing Logs screen  
**When** I enter `eventId = "not-a-uuid"` and submit  
**Then** the search is not executed  
**And** I see an inline validation message indicating the UUID format requirement

### Scenario 8: Access control enforced
**Given** I am authenticated but do not have permission `crm.integrations.processingLogs.read`  
**When** I navigate to the VehicleUpdated Processing Logs URL or a detail URL directly  
**Then** the backend returns 403  
**And** the UI shows an access denied state  
**And** no ProcessingLog data is displayed
