## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Vehicle: Store Vehicle Care Preferences (Capture, Edit, View, and Audit)

**Primary Persona:** Service Advisor

**Business Value:** Ensure vehicle service is consistently performed according to customer/vehicle-specific expectations (tire brand, rotation interval, alignment preference, torque notes, and general notes), and make these preferences visible wherever service decisions are made (estimate and work order), with an auditable change history.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to add and update vehicle-specific care preferences and service notes from the vehicle context  
- **So that** technicians and advisors can reliably see and follow these preferences during estimating and execution, reducing rework and improving customer satisfaction.

### In-scope
- A vehicle-level UI section to **view**, **create**, and **update** care preferences + service notes.
- Preferences displayed **read-only** in:
  - Estimate view (when vehicle present)
  - Work Order view (when vehicle present)
- **Audit visibility** of changes (at minimum: who/when; before/after when provided).
- Validation and error handling on save.
- Optimistic locking handling (409 conflict) using a backend-provided `version`. (DECISION-INVENTORY-012)

### Out-of-scope
- Defining/implementing CRM backend data model/services (frontend consumes).
- Deduplication/merge rules, customer identity rules.
- Workflow/state logic inside Workorder Execution beyond *displaying* the preferences.
- Bulk-edit across vehicles or importing preferences.
- Any operator actions beyond read-only audit viewing (no “revert”, no “retry”). (DECISION-INVENTORY-009)

---

## 3. Actors & Stakeholders
- **Service Advisor (Primary):** Captures/updates preferences and notes.
- **Technician/Mechanic (Secondary):** Consumes preferences on work order during execution.
- **Shop Manager (Stakeholder):** Wants consistency and accountability (audit).
- **CRM System (SoR):** Stores vehicle preferences/notes and audit trail. (DECISION-INVENTORY-012)
- **Workorder Execution UI (Downstream consumer):** Displays preferences within Estimate/WO context.

## 4. Preconditions & Dependencies
1. User is authenticated in the POS frontend.
2. User has authorization to:
   - View vehicle record
   - Edit vehicle care preferences (permission key defined below; backend must enforce). (DECISION-INVENTORY-007)
3. A **Vehicle** record exists and user can navigate to it (`vehicleId` available in route params).
4. Backend endpoints exist/are exposed for:
   - Loading vehicle care preferences by `vehicleId`
   - Upserting vehicle care preferences by `vehicleId` with optimistic locking
   - Loading audit history for vehicle care preferences
5. Estimate/Work Order screens can access `vehicleId` (or derive it from estimate/WO header) to load preferences for display.

**Decision rationale applied (binding):**
- Fixed schema + optimistic locking + audit history are required for vehicle care preferences. (DECISION-INVENTORY-012)
- Error payloads include `errorCode`, `message`, `fieldErrors`. (DECISION-INVENTORY-012)
- Permissions must be explicit and fail-closed; UI may hide entry points but backend enforces. (DECISION-INVENTORY-007)

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side mirrors backend; backend remains authoritative)
- Fixed schema only; unknown fields must never be sent. (DECISION-INVENTORY-012)
- `rotationInterval`:
  - Optional
  - If provided: integer 1–100000 inclusive. (DECISION-INVENTORY-012)
- `rotationIntervalUnit`:
  - Enum: `MILES` or `KM`. (DECISION-INVENTORY-012)
  - Required when `rotationInterval` is provided. (DECISION-INVENTORY-012)
- Notes fields (`torqueSpecNotes`, `serviceNotes`) are treated as plain text:
  - UI must not render as HTML.
  - UI must not log contents to client telemetry/console. (DECISION-INVENTORY-006)

### Enable/disable rules
- Edit controls enabled only if user has edit permission (see permissions below); backend must enforce. (DECISION-INVENTORY-007)
- Save button disabled when:
  - Form is pristine (no changes), OR
  - Currently saving, OR
  - Client-side validation fails:
    - rotationInterval not an integer
    - rotationInterval outside 1–100000
    - rotationInterval provided but unit missing
    - unit not in `MILES|KM`

### Visibility rules
- Vehicle profile: section visible when `vehicleId` is present and vehicle exists.
- Estimate/WO: section visible if vehicle exists on the document.
- If no preferences exist: show “No vehicle preferences recorded” and hide empty structured fields; show notes as “None” (or omit) per UI ergonomics.

### Error messaging expectations
- Field-specific errors:
  - rotationInterval invalid: “Rotation interval must be a whole number between 1 and 100000.”
  - rotationIntervalUnit missing when interval set: “Unit is required when rotation interval is set.”
  - rotationIntervalUnit invalid: “Unit must be MILES or KM.”
- Backend validation errors:
  - If backend returns `fieldErrors`, map to field-level messages.
  - Otherwise show a non-technical banner/toast using backend `message` when safe.

- `preferredTireBrand` (string) — optional
- `preferredTireLine` (string) — optional
- `rotationInterval` (integer) — optional; constraints 1–100000 (DECISION-INVENTORY-012)
- `rotationIntervalUnit` (enum string) — optional unless interval present; `MILES|KM` (DECISION-INVENTORY-012)
- `alignmentPreference` (string) — optional
- `torqueSpecNotes` (string) — optional (short text)
- `serviceNotes` (string) — optional (multi-line)
- `lastUpdatedAt` (datetime, ISO-8601) — read-only (if provided)
- `lastUpdatedByUserId` (string) — read-only (if provided)

**Audit entry DTO (read-only)**

- `changedByUserId` (string) — required
- `changedByDisplayName` (string) — optional

### Derived/calculated fields

  - If interval present but unit missing (should not happen if backend valid): display interval and show “(unit missing)” in a non-blocking warning style.
- “Last updated summary” derived from `lastUpdatedAt`/`lastUpdatedByDisplayName` if provided; otherwise omit.

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation must call backend services/resources; exact artifact names may vary. This story defines the required contract shape and behaviors so UI can be implemented deterministically. (DECISION-INVENTORY-012)

### Load/view calls
1. **Get vehicle care preferences**
   - Method: `GET`
   - Path (default contract): `/rest/api/v1/crm/vehicles/{vehicleId}/care-preferences`
   - Input: `vehicleId` (UUID)
   - Output (200): `VehicleCarePreference` DTO
   - Output (404): not found → UI treats as empty state
   - Output (403): forbidden → UI shows access denied for viewing (if view permission is separate)

2. **Get vehicle care preferences audit history**
   - Method: `GET`
   - Path (default contract): `/rest/api/v1/crm/vehicles/{vehicleId}/care-preferences/audit`
   - Query params: `pageIndex`, `pageSize`, optional `from`, `to`
   - Output (200): `{ items: AuditEntry[], pageIndex, pageSize, total }`
   - Output (403): forbidden → UI shows access denied for audit

### Create/update calls
1. **Upsert vehicle care preferences (create or update)**
   - Method: `PUT`
   - Path (default contract): `/rest/api/v1/crm/vehicles/{vehicleId}/care-preferences`
   - Input body:
     - Fixed schema fields only (see Data Requirements)
     - Include `version` when updating an existing record
   - Output (200/201): saved DTO including updated `version` and metadata
   - Errors:
     - 400 validation error:
       - Shape: `{ errorCode, message, fieldErrors }` (DECISION-INVENTORY-012)
     - 403 forbidden:
       - Shape: `{ errorCode:"FORBIDDEN", message }`
     - 409 conflict (optimistic locking):
       - Shape: `{ errorCode:"CONFLICT", message, currentVersion, currentRecord? }` (currentRecord optional)
     - 500 unexpected:
       - Shape: `{ errorCode, message }` without sensitive data

### Submit/transition calls
- None (no lifecycle state transitions defined for preferences).

### Error handling expectations (frontend)
- 404 on GET preferences: show empty state (not an error).
- 400 on PUT: show banner “Please correct the highlighted fields.” and map `fieldErrors`.
- 403 on any call: show access denied state; do not show partial data.
- 409 on PUT:
  - Keep user in edit mode.
  - Show blocking banner: “Preferences were updated by someone else. Reload to continue.”
  - Provide “Reload” action that re-fetches preferences and resets form to latest.
- Never render backend strings as HTML; treat as plain text. (DECISION-INVENTORY-006)

## 10. State Model & Transitions

### Allowed states (UI)
- `EMPTY` (no preference record exists)
- `VIEW` (record exists, read-only)
- `EDIT` (record being edited)
- `SAVING`
- `ERROR_LOADING`
- `ERROR_SAVING`
- `CONFLICT` (409 on save)

### Role-based transitions
- Users with edit permission:
  - `EMPTY/VIEW -> EDIT` via Add/Edit
  - `EDIT -> SAVING -> VIEW/EMPTY` via Save (EMPTY only if backend returns empty/cleared record; otherwise VIEW)
  - `SAVING -> CONFLICT` on 409
- Users without edit permission:
  - Cannot enter EDIT; always VIEW/EMPTY read-only

### UI behavior per state
- `EMPTY`: show CTA to add (if permitted) else show message only.
- `VIEW`: show fields in read-only plus “Edit” (if permitted).
- `EDIT`: inputs enabled, Save/Cancel shown; store `version` from last load.
- `SAVING`: disable inputs and buttons; show local spinner.
- `ERROR_LOADING`: show inline error and retry.
- `ERROR_SAVING`: keep user in EDIT with inline banner; do not discard changes.
- `CONFLICT`: keep user in EDIT but disable Save until reload OR allow Save after reload only (preferred: require reload to avoid overwriting).

## 11. Alternate / Error Flows

1. **Validation failure (client-side)**
   - rotationInterval contains non-numeric characters OR outside range OR unit missing
   - Prevent save; show field message; keep in edit mode.

2. **Validation failure (backend)**
   - Backend returns 400 with `fieldErrors`
   - Display banner “Please correct the highlighted fields.”
   - Apply field errors; keep in edit mode.

3. **Vehicle not found**
   - Vehicle profile route has invalid `vehicleId`
   - Vehicle screen handles “Vehicle not found”; preferences section must not attempt save and must show “Vehicle not found” within section if vehicle context is missing.

4. **Concurrent update (optimistic locking)**
   - Backend returns 409 with `currentVersion`
   - Show conflict banner and require reload; do not silently overwrite. (DECISION-INVENTORY-012)

5. **Unauthorized access**
   - If user lacks view permission: preferences section shows access denied and does not fetch further details.
   - If user can view but cannot edit: hide edit actions; if save attempted (e.g., via devtools), backend returns 403 and UI shows permission error.

6. **Empty state on Estimate/WO**
   - If no preferences exist, show “No vehicle preferences recorded” (read-only).

**And** I see a success confirmation message

**And** the updated values are persisted and displayed in read-only mode  
**And** the response includes an updated `version` that the UI stores for the next edit

**And** a Work Order exists that references that vehicle  
**When** I view the Work Order  
**Then** I see the vehicle care preferences and notes displayed read-only on the Work Order screen  
**And** I do not see any edit controls

**Given** a vehicle has had its care preferences created or updated  
**And** I have permission `crm.vehicles.carePreferences.audit.read`  
**When** I open “Change history” from the vehicle preferences section  
**Then** the UI calls `GET /crm/vehicles/{vehicleId}/care-preferences/audit?pageIndex=0&pageSize=25`
