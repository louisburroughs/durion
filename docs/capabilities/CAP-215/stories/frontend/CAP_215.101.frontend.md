## Issue Body

## 1. Story Header

**Title:** [FRONTEND] Inventory Ledger: View Append-Only Stock Movements (List + Detail) with Deep-Linking and Cursor Pagination

**Primary Persona:** Inventory Manager

**Persona Metadata**
- `primary_persona`: `Inventory Manager`
- `canonical_persona`: `Inventory Control Manager`
- `persona_family`: `Inventory Management`
- `actor_type`: `human`
**Business Value:** Provide an auditable, explainable history of on-hand changes by product/location/bin, enabling operational troubleshooting and compliance/audit review, and allowing downstream consumers (e.g., Work Execution) to deep-link into movement history tied to source transactions.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Inventory Manager  
- **I want** to view all stock movements in an append-only inventory ledger (filterable by product SKU, location/bin, movement type, date range, and source transaction/work order references)  
- **So that** on-hand can be audited/explained and I can trace what changed, when, by whom, and why.

### In-scope
- Moqui screen flow to **list and view** immutable `InventoryLedgerEntry` records with:
  - Filtering/search: `productSku`, `locationId`, optional `storageLocationId`, `movementType`, date range, `sourceTransactionId`, `workOrderId`, `workOrderLineId`
  - Cursor pagination (`pageSize`, `pageToken` → `nextPageToken`)
  - Row-level details: from/to site/bin, quantity change, UOM, actor, timestamp, reason code, source linkage fields
  - Clear empty/loading/error states
- UI-level enforcement of **immutability** (no edit/delete actions; no mutation endpoints called)
- Deep-linking via URL query params for common filters (canonical param names; see Business Rules)

### Out-of-scope
- Implementing backend ledger creation/atomicity/replay logic (backend responsibility)
- Any ledger mutation (edit/delete), exports (CSV/PDF), or client-side on-hand computation
- Inventory Adjustment create/post UI (separate story; adjustments are create-only and post immediately in v1, but this story is ledger view only)
- Creating movement flows (Receive/PutAway/Pick/Consume/Return/Transfer)

---

## 3. Actors & Stakeholders
- **Inventory Manager (primary user):** audits movements; investigates discrepancies.
- **Parts Counter / Staff (secondary):** views movement history to answer “what happened”.
- **Auditor (stakeholder):** needs immutable, traceable history.
- **Work Execution users/system (consumer):** deep-links from work order line to movement history (view-only).
- **System actor:** some ledger entries are system-generated; UI must display actor fields accordingly.

---

## 4. Preconditions & Dependencies
- User is authenticated in the Moqui frontend and has an active session.
- Moqui frontend calls **Moqui proxy endpoints** only (no direct Vue → inventory backend). (DECISION-INVENTORY-002)
- Backend (via Moqui proxy) exposes:
  - `GET /inventory/ledger` (cursor pagination; deterministic error schema) (DECISION-INVENTORY-003, DECISION-INVENTORY-005)
  - `GET /inventory/ledger/{ledgerEntryId}` (detail)
  - `GET /inventory/locations` for LocationRef picker (site) (DECISION-INVENTORY-001, DECISION-INVENTORY-008)
  - `GET /inventory/storage-locations?locationId=...` for StorageLocation picker (bin) (DECISION-INVENTORY-007)
- Permission discovery is available to the UI via existing Moqui/POS convention (security context or permissions endpoint). This story uses permission gating only for viewing ledger screens.

## 6. Functional Behavior

### Triggers
- Ledger list screen:
  - On initial load: do **not** auto-query unless deep-link params are present (see Business Rules).
  - On filter submit: query `GET /inventory/ledger`.
  - On “Load more”: query next page using `nextPageToken`.
- Ledger detail screen:
  - On load: query `GET /inventory/ledger/{ledgerEntryId}`.

### UI actions
- **Filter controls**
  - `productSku` (text input; trimmed; optional)
  - `locationId` (LocationRef picker; optional)
  - `storageLocationId` (StorageLocation picker filtered by `locationId`; optional; disabled until `locationId` selected) (DECISION-INVENTORY-001, DECISION-INVENTORY-007)
  - `movementType` (multi-select enum; optional)
  - `dateFrom`, `dateTo` (optional; ISO timestamps; validated)
  - `sourceTransactionId` (text; optional)
  - `workOrderId` (text; optional)
  - `workOrderLineId` (text; optional)
  - Actions: Submit/Search, Clear filters
- **Results list**
  - Default sort: `-timestamp` (descending)
  - Row click navigates to detail screen
  - “Load more” uses cursor pagination; no total count displayed
- **Detail view**
  - Read-only display of all fields returned by backend
  - Show linkage fields (sourceTransactionId/workOrderId/workOrderLineId) when present
  - Render nullable fields safely (show “—”)

### State changes (frontend)
- List screen maintains:
  - `filters` state
  - `results[]`
  - `pageToken` / `nextPageToken`
  - `loading` / `error` states
- No client-side mutation of ledger records.

### Service interactions
- `GET /inventory/ledger` (list with filters + cursor pagination)
- `GET /inventory/ledger/{ledgerEntryId}` (detail)
- `GET /inventory/locations` (picker)
- `GET /inventory/storage-locations?locationId=...` (picker)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Date range**
  - If both provided, enforce `dateFrom <= dateTo`; otherwise block submit and show inline error.
- **productSku**
  - Trim; reject whitespace-only when provided.
- **Location/bin topology**
  - `storageLocationId` cannot be selected unless `locationId` is selected.
  - When both are selected, UI must only allow bins belonging to the selected `locationId` (picker filtered by `locationId`). (DECISION-INVENTORY-001)
- **No client-side quantity calculations**
  - UI must not compute on-hand/ATP from ledger; ledger is display-only. (DECISION-INVENTORY-005)

### Enable/disable rules
- Screen access:
  - Ledger list/detail require permission `inventory:ledger:view` (UI gates when permission info is available; backend remains authoritative). (DECISION-INVENTORY-010)
- Filter submit disabled when validation fails (date range invalid; whitespace-only productSku).

### Visibility rules
- Always show that ledger is append-only/immutable (static helper text).
- If `locationId` filter is set, show helper text: “Matches entries where From OR To equals the selected location.” (DECISION-INVENTORY-005)
- Nullable fields (`fromLocationId`, `toLocationId`, `storageLocationId`, `reasonCode`, linkage fields) render as “—” when absent.

### Error messaging expectations
- Deterministic error schema parsing (plain JSON). (DECISION-INVENTORY-003)
- Auth behavior:
  - **401**: route to login/session refresh per app convention. (DECISION-INVENTORY-012)
  - **403**: show forbidden state without leaking data; do not render partial results. (DECISION-INVENTORY-012)
- Other common statuses:
  - **400/422**: show validation message; map field errors to fields when possible.
  - **404** (detail): show “Ledger entry not found.”
  - **5xx/timeout**: show retry affordance; include correlation ID in technical details when available. (DECISION-INVENTORY-004, DECISION-INVENTORY-012)

## 11. Alternate / Error Flows

### Validation failures
- Invalid date range:
  - Block submit; show inline error near date fields.
- Whitespace-only productSku:
  - Block submit; show inline error.

### Concurrency conflicts
- Not applicable (read-only screens).

### Unauthorized access
- If user lacks permission and navigates directly:
  - If UI knows permissions: show forbidden state without calling list/detail.
  - If UI does not know permissions: call may return 403; show forbidden state and do not render partial data. (DECISION-INVENTORY-012)

- No ledger entries match filters:
  - Show “No movements found for the selected criteria.”
  - Provide “Clear filters” action.

  - Storage locations for a site: show “No storage locations for this site.”

### Timeout / offline
- If request exceeds 8 seconds:
  - Show timeout message with Retry; do not auto-retry. (DECISION-INVENTORY-004)

## 12. Acceptance Criteria

### Scenario 1: View ledger list (permission-gated) and open detail
**Given** I am authenticated  
**And** I have permission `inventory:ledger:view`  
**When** I navigate to Inventory → Ledger  
**Then** I can submit filters and see a list of ledger entries sorted by timestamp descending  
**And** I can open an entry to view its read-only details  
**And** I do not see any Edit or Delete actions for ledger entries

### Scenario 2: Location filter uses OR semantics (from OR to)
**Given** ledger entries exist involving `locationId=L1` as either From or To  
**When** I filter the ledger by `locationId=L1`  
**Then** the results include entries where `fromLocationId = L1` **or** `toLocationId = L1`  
**And** the UI displays helper text indicating the From/To OR semantics

### Scenario 3: Storage location picker is constrained by selected site
**Given** I am on the Ledger filter form  
**When** I have not selected a `locationId`  
**Then** the `storageLocationId` control is disabled  
**When** I select `locationId=L1`  
**Then** the `storageLocationId` picker only lists storage locations whose `locationId` is `L1`

### Scenario 4: Cursor pagination (no total count dependency)
**Given** the ledger query returns `items` and `nextPageToken`  
**When** I click “Load more”  
**Then** the UI requests `GET /inventory/ledger` with `pageToken=<nextPageToken>`  
**And** appends the returned items to the existing list  
**And** the UI does not display or rely on a total count

### Scenario 5: Deep-linking pre-fills filters and auto-runs once
**Given** I open `/inventory/ledger?locationId=L1&productSku=SKU-123`  
**When** the Ledger screen loads  
**Then** the filter form is pre-filled with `locationId=L1` and `productSku=SKU-123`  
**And** the ledger query runs automatically exactly once on initial load  
**And** changing a filter does not trigger a query until I submit (no auto-refresh loop)

### Scenario 6: Detail view renders nullable fields safely
**Given** a ledger entry exists with `fromLocationId = null` and `toLocationId = L1`  
**When** I open the ledger entry detail screen  
**Then** the UI displays missing fields as “—”  
**And** no client error occurs

### Scenario 7: 401 vs 403 behavior and correlation ID display
**Given** I request the ledger list and the server responds with 401  
**Then** I am redirected to login/session refresh per app convention  
**Given** I request the ledger list and the server responds with 403 and header `X-Correlation-Id=abc`  
**Then** I see a forbidden state  
**And** I see `abc` in “Technical details”  
**And** no ledger data is displayed
