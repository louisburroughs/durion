## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Putaway: Execute Put-away Move (Staging → Storage)

### Primary Persona
Stock Clerk (warehouse/mobile user)

### Business Value
Accurately moves received inventory from staging to storage so it becomes available for picking, with an auditable, immutable inventory ledger trail and completed putaway tasks.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Stock Clerk  
- **I want** to execute a confirmed put-away move by scanning source and destination locations (and the item/pallet when required)  
- **So that** the system posts an immutable inventory movement entry and marks the putaway task complete for downstream picking accuracy.

### In-scope
- Moqui/Vue/Quasar frontend flow to **execute** a putaway move for an existing `PutawayTask`
- Guided scan/entry of:
  - **source** (staging) location
  - **destination** (storage) location
  - **item/pallet identifier** *only when the task requires it* (see Data Requirements)
- Confirmation summary and submit (single atomic execute call)
- Display success/failure outcomes and reflect task completion
- Permission-aware handling of validation/authorization errors returned by backend
- Correlation ID propagation and safe error display (no sensitive logging)

### Out-of-scope
- Creating putaway tasks, assigning tasks, or planning/suggesting destination locations (unless backend already provides suggestions in task payload)
- Inventory reconciliation/cycle count/adjustment flows (only link/navigate if such screens exist; otherwise show actionable guidance)
- Any client-side computation of on-hand/ATP/availability (inventory backend is authoritative; UI displays only)
- Implementing backend services/entities (frontend integrates only)
- Any approval workflow/state machine for putaway execution (not defined here)

---

## 3. Actors & Stakeholders
- **Stock Clerk (Primary user):** performs scanning and confirmation
- **Inventory Services via Moqui Proxy (System):** validates locations/SKU, posts ledger entry, updates on-hand and task status (DECISION-INVENTORY-002)
- **Work Execution (Stakeholder):** depends on accurate pick locations and availability
- **Inventory Manager (Stakeholder):** cares about auditability and exception handling

---

## 4. Preconditions & Dependencies
- User is authenticated in the frontend (Moqui session)
- User has permission to view and execute putaway tasks (exact permission strings for putaway are not defined in provided inventory rules; backend remains authoritative)
- A `PutawayTask` exists and is in an executable state (see State Model)
- Moqui proxy endpoints exist and are same-origin to the UI runtime (DECISION-INVENTORY-002)
- Barcode/location scanning capability exists in frontend (camera scanner or hardware wedge) with manual entry fallback
- Location selection must use pickers (no free-text UUID entry in normal user flows) (DECISION-INVENTORY-001)
- Correlation ID header `X-Correlation-Id` is supported and surfaced on errors (DECISION-INVENTORY-012)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From a Putaway Task list screen: “Execute” action on a selected task
- Direct route with task id parameter (deep link): `/inventory/putaway/tasks/{putawayTaskId}/execute`
  - Note: query param conventions in inventory domain are canonical for availability (`productSku`, `locationId`, `storageLocationId`) (DECISION-INVENTORY-014). This putaway route uses a path param and does not introduce new canonical query params.

### Screens to create/modify (Moqui screens)
1. **Screen: `inventory/Putaway/TaskList`** (create if missing; otherwise modify)
   - List tasks with status filter and “Execute” action
2. **Screen: `inventory/Putaway/TaskExecute`** (create)
   - Guided scan workflow (source → item/pallet (conditional) → destination → confirm)
3. **Screen: `inventory/Putaway/TaskDetail`** (optional; modify if exists)
   - Shows task status and completion reference (transaction/ledger reference) after completion

### Navigation context
- Inventory → Putaway → Tasks → Execute
- After success: navigate to Task Detail (preferred) or back to Task List with the task marked `COMPLETED`

### User workflows (happy + alternate)
**Happy path**
1. Open Execute for a task
2. Confirm/scan **source** (staging) location (pre-filled if task provides it; user must match/confirm)
3. If required by task, scan/enter **item/pallet identifier**
4. Scan/select **destination** (storage) location
5. Review summary and **Confirm Putaway**
6. See success with reference ID; task shown as `COMPLETED`

**Alternate paths**
- Destination invalid/incompatible → show blocking error; allow rescan destination
- Destination capacity/full → show blocking error; allow rescan destination (no split in UI unless backend explicitly supports it)
- Source has insufficient on-hand → show blocking error; provide next-step guidance (reconciliation required) without attempting to “fix” in UI
- Unauthorized (403) → show forbidden state; disable confirm action
- Task already completed/changed (409) → prompt reload; after reload show completed view

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI-level, before calling backend)
- Required before enabling “Confirm Putaway”:
  - `putawayTaskId` present (from route)
  - source selected (see Data Requirements for allowed shapes)
  - destination selected
  - if task indicates `requiresItemOrPallet=true`, then `itemOrPalletCode` is required and must be trimmed non-empty
- Prevent submission while `isSubmitting=true` (double-submit guard)
- If destination includes a `storageLocationId`, it must belong to the selected destination `locationId` (enforced by picker filtering; backend remains authoritative) (DECISION-INVENTORY-001)
- If the selected site (`locationId`) is `INACTIVE` or `PENDING`, block execution and show a message that movements are not allowed for inactive/pending sites (DECISION-INVENTORY-009)
  - Note: this rule is inventory-wide for “new movement” flows; putaway is a movement flow.

### Enable/disable rules
- “Confirm Putaway” disabled unless:
  - required fields present and valid
  - task status is executable (not completed/cancelled/unknown)
  - not currently submitting
- If backend returns 403 on execute, disable confirm until user reloads or navigates away (prevents repeated attempts)

### Visibility rules
- Task immutable info (SKU, qty, expected source) is read-only
- If task already `COMPLETED`, show read-only completion summary and hide/disable confirm controls
- If user lacks permission to view payload-like fields (if any exist), hide them and show “Not authorized” placeholders (pattern consistent with payload gating) (DECISION-INVENTORY-010, DECISION-INVENTORY-011)

### Error messaging expectations (deterministic mapping)
- UI must render backend errors using deterministic schema (plain JSON) (DECISION-INVENTORY-003)
- Minimum handled error cases:
  - `LOCATION_NOT_VALID_FOR_SKU` → “Destination location is not valid for this item. Select a different storage location.”
  - `NO_ON_HAND_AT_SOURCE_LOCATION` → “No on-hand quantity at the source location. Reconciliation is required before putaway.”
  - `LOCATION_INACTIVE_OR_PENDING` (or equivalent) → “This location is not active. Inventory movements are not allowed.”
  - Capacity full (backend code) → “Destination location cannot accept this quantity. Select a different location.”
- Unknown error codes:
  - show generic message + correlation ID in technical details (DECISION-INVENTORY-012)
- Do not log quantities or raw payloads to console/telemetry (DECISION-INVENTORY-011)

**Decision rationale used to resolve prior TBDs**
- Item/pallet requirement is conditional because the inventory domain rules do not mandate it universally; enforcing it always would be a domain policy guess (SAFE_DEFAULTS denylist). Therefore, the UI requires it only when the task payload indicates it is required; otherwise optional.
- Capacity error code is not defined in provided inventory decisions; UI must treat it as a generic deterministic validation error and display a safe message without implementing split logic.

## 8. Data Requirements

- `LocationRef` (site/shop) (DECISION-INVENTORY-001, DECISION-INVENTORY-008)
- `StorageLocation` (bin) (DECISION-INVENTORY-001, DECISION-INVENTORY-007)
- `InventoryLedgerEntry` reference (read-only display of returned reference; ledger itself is immutable) (DECISION-INVENTORY-005)

### Fields (type, required, defaults)

**PutawayTask (read) — minimum required by UI**
- `putawayTaskId` (string/UUID, required)
- `status` (string/enum, required)
- `productSku` (string, required)  
  - Note: product master data is out of inventory scope; UI displays SKU as provided (Inventory boundary)
- `quantity` (number/decimal string, required)
- `source` (object, required)
  - `locationId` (string/UUID, required)
  - `storageLocationId` (string/UUID, optional; if task is bin-specific)
  - `displayLabel` (string, optional)
- `requiresItemOrPallet` (boolean, required; default false if absent)
- `expectedItemOrPalletCode` (string, optional; if task binds to a specific container)
- `completedAt` (ISO-8601 string, optional)
- `completionReferenceId` (string, optional; e.g., ledgerEntryId or transactionId)

**Execute Putaway request (submit) — frontend contract**
- `putawayTaskId` (string, required)
- `from` (object, required)
  - `locationId` (string, required)
  - `storageLocationId` (string, optional)
- `to` (object, required)
  - `locationId` (string, required)
  - `storageLocationId` (string, optional)
- `itemOrPalletCode` (string, conditionally required when `requiresItemOrPallet=true`)
- `quantity` (**not sent by default**)  
  - Rationale: quantity is task-owned; sending quantity risks mismatch and implies split/partial behavior not defined. UI relies on task quantity unless backend explicitly requires a quantity field.

**Execute Putaway response (read)**
- `putawayTaskId` (string, required)
- `status` (string/enum, required; expected `COMPLETED` on success)
- `completionReferenceId` (string, required; displayed to user)
- `completedAt` (ISO-8601 string, optional)

### Read-only vs editable by state/role
- Read-only always: task SKU, task quantity, task status, expected source (if provided)
- Editable until submit: destination selection; item/pallet code (if required)
- Source selection:
  - If task provides a specific source, UI should pre-fill and require user confirmation/match (editable only if backend allows; otherwise treat as read-only and validate scanned source matches)
- No override fields are shown in v1 (no override contract provided)

### Derived/calculated fields
- Display-only “Move summary” assembled from task + selections
- No client-side availability calculations (DECISION-INVENTORY-004)

## 9. Service Contracts (Frontend Perspective)

> Integration rule: Vue calls Moqui proxy endpoints only; responses are plain JSON (DECISION-INVENTORY-002, DECISION-INVENTORY-003). Endpoint paths below are Moqui proxy routes; Moqui may internally call inventory backend services.

### Load/view calls
1. **Get Putaway Task**
   - `GET /inventory/putaway/tasks/{putawayTaskId}`
   - Success: returns `PutawayTask` fields listed above
   - Errors:
     - 401: not authenticated (handle per app convention) (DECISION-INVENTORY-012)
     - 403: forbidden (show access denied) (DECISION-INVENTORY-012)
     - 404: not found (show not found + link back)

2. **Pickers / topology**
   - Sites:
     - `GET /inventory/locations?pageSize=&pageToken=` (cursor pagination) (DECISION-INVENTORY-003, DECISION-INVENTORY-008)
   - Storage locations by site:
     - `GET /inventory/storage-locations?locationId={locationId}&pageSize=&pageToken=` (cursor pagination) (DECISION-INVENTORY-007)
   - Storage location detail (optional for resolve):
     - `GET /inventory/storage-locations/{storageLocationId}` (DECISION-INVENTORY-007)

3. **(Optional) Resolve scanned location code/barcode**
   - If Moqui provides a resolve endpoint, it must return a `LocationRef` or `StorageLocation` reference without requiring free-text UUID entry.
   - If not available, UI uses picker search and requires user selection.

### Create/update calls
- None directly; execution is a command

### Submit/transition calls
1. **Execute Putaway**
   - `POST /inventory/putaway/execute`
   - Body: `Execute Putaway request` (see Data Requirements)
   - Success (200/201): returns `completionReferenceId` and updated task status
   - Errors (deterministic schema) (DECISION-INVENTORY-003):
     - 400/422: validation error with machine-readable `code` and optional `fieldErrors`
     - 401: unauthenticated (redirect/login) (DECISION-INVENTORY-012)
     - 403: forbidden (show forbidden state) (DECISION-INVENTORY-012)
     - 409: conflict (task already completed/changed; prompt reload)
     - 5xx: server error (show generic + retry)

### Error handling expectations
- Parse deterministic error schema; map `fieldErrors` to the relevant step field when possible
- Always display `X-Correlation-Id` (from response header or error payload) in “Technical details” (DECISION-INVENTORY-012)
- Do not log request/response bodies containing quantities or payload-like fields (DECISION-INVENTORY-011)

## 10. State Model & Transitions

### Allowed states (PutawayTask)
- `PENDING_EXECUTION` (executable)
- `IN_PROGRESS` (executable)
- `COMPLETED` (non-executable; read-only)

Additional states may exist (e.g., `CANCELLED`, `ON_HOLD`). UI must treat unknown states as non-executable and show a clear message.

### Role-based transitions
- Stock Clerk can transition executable → `COMPLETED` only via successful Execute Putaway call
- No override transitions are implemented in this story (no contract provided)

### UI behavior per state
- Executable: show scan workflow and confirm
- Completed: show completion summary and completion reference; disable scans/confirm
- Unknown/non-executable: show read-only task info and message “This task cannot be executed in its current status.”

## 11. Alternate / Error Flows

### Validation failures
- Missing required inputs → client-side block; show inline required markers
- Backend `LOCATION_NOT_VALID_FOR_SKU` → remain on Destination step; clear destination selection; prompt to select another destination
- Backend `NO_ON_HAND_AT_SOURCE_LOCATION` → show blocking error; keep user on Confirm step; provide guidance text (no automatic adjustment)
- Backend indicates inactive/pending location:
  - If detected via picker metadata: block before submit
  - If returned by backend: show blocking error and keep user on selection step

### Concurrency conflicts
- 409 on execute:
  - show banner “Task was updated elsewhere. Reload required.”
  - provide Reload action (re-call Get Putaway Task)
  - if status becomes `COMPLETED`, switch to completed view

### Unauthorized access
- 401:
  - follow app convention (session refresh/login) (DECISION-INVENTORY-012)
- 403 on load:
  - show forbidden state and link back to list
- 403 on execute:
  - show forbidden banner/state; disable confirm until reload/navigation

### Empty states
- Task list empty: show “No putaway tasks available” and allow refresh
- Picker empty (no storage locations for selected site): show “No storage locations available for this site” and block confirm

### Timeout / network failure
- Show loading indicator within 100ms; if request exceeds 8 seconds, show timeout state with Retry (DECISION-INVENTORY-004)
- Do not auto-retry mutations; retry only on explicit user action

## 12. Acceptance Criteria

### Scenario 1: Successful Put-away move completes task
**Given** a PutawayTask is in status `IN_PROGRESS` for quantity `10` of SKU `ABC-123` from source location `STAGING-01`  
**And** the user opens the Execute Putaway screen for that task  
**When** the user confirms the source location matches the task source  
**And** selects/scans destination `A-01-B-03`  
**And** clicks “Confirm Putaway”  
**Then** the frontend calls `POST /inventory/putaway/execute` exactly once  
**And** the response includes a non-empty `completionReferenceId`  
**And** the UI displays the task as `COMPLETED` and hides/disables execute controls.

### Scenario 2: Task requires item/pallet identifier
**Given** an executable PutawayTask is loaded with `requiresItemOrPallet=true`  
**When** the user attempts to proceed without entering `itemOrPalletCode`  
**Then** the UI blocks progression/submit and shows a required-field error  
**When** the user enters a non-empty `itemOrPalletCode` and submits  
**Then** the execute request includes `itemOrPalletCode`.

### Scenario 3: Destination invalid for SKU blocks move
**Given** an executable PutawayTask is loaded  
**When** the user submits and the backend returns a deterministic validation error with code `LOCATION_NOT_VALID_FOR_SKU`  
**Then** the UI displays “Destination location is not valid for this item. Select a different storage location.”  
**And** the destination selection is cleared  
**And** the user can select a different destination and retry.

### Scenario 4: Source has zero on-hand blocks move
**Given** an executable PutawayTask is loaded  
**When** the user submits and the backend returns code `NO_ON_HAND_AT_SOURCE_LOCATION`  
**Then** the UI displays a blocking error explaining reconciliation is required  
**And** the UI does not attempt to create inventory or adjust quantities  
**And** the user remains on the execute screen with the ability to reload the task.

### Scenario 5: Task already completed (concurrency)
**Given** the user has the Execute screen open for a PutawayTask  
**When** the backend responds `409 Conflict` indicating the task is already completed or changed  
**Then** the UI prompts the user to reload  
**And** after reload the task is displayed as `COMPLETED` and the execute controls are hidden/disabled.

### Scenario 6: Unauthorized user cannot execute
**Given** a user attempts to confirm putaway  
**When** the backend responds `403 Forbidden`  
**Then** the UI shows a forbidden/access denied message  
**And** does not show success  
**And** disables Confirm to prevent repeated submissions until reload/navigation.

### Scenario 7: Correlation ID is shown on error
**Given** an execute attempt fails with any non-2xx response  
**When** the response includes header `X-Correlation-Id`  
**Then** the UI displays that correlation ID in “Technical details”  
**And** does not log quantities or payloads to console/telemetry.
