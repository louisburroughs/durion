## Issue Body

## 1. Story Header

**Title**  
[FRONTEND] [STORY] Dispatch: Determine Mechanic Availability for a Time Window

**Primary Persona**  
Dispatcher

**Business Value**  
Enables dispatchers to assign work without double-booking by showing mechanic availability for a requested time window with explainable conflict reason codes, while degrading gracefully if People/HR availability signals are unavailable.

---

## 2. Story Intent

**As a** Dispatcher  
**I want** to query and view mechanic availability for a specific time window (optionally filtered to selected mechanics)  
**So that** I can schedule/assign work confidently and understand why a mechanic is unavailable.

### In-scope
- UI to input a time window and location, optionally select mechanic(s)
- Calling an availability API and presenting results per mechanic
- Displaying overall availability status and conflict blocks with standardized reason codes
- Handling API failures (including upstream People/HR dependency failures) and invalid input validation
- Timezone semantics per workexec rules: display in user timezone; day/window interpretation uses shop timezone when applicable and labeled

### Out-of-scope
- Creating/editing shifts, PTO, assignments, or travel blocks (People domain SoR)
- Persisting new travel blocks from the frontend
- Implementing backend aggregation logic (assumed provided by backend)
- Notification/event subscription UI (e.g., consuming AvailabilityChanged events)
- Any time-entry CRUD (explicitly out of workexec per DECISION-INVENTORY-009)

---

## 3. Actors & Stakeholders

- **Dispatcher (primary user):** performs availability checks to plan assignments
- **Service Advisor / Shop Manager (stakeholders):** rely on accurate scheduling outcomes
- **Mechanic (subject):** schedule is queried; no direct interaction in this story
- **People/HR system(s) (dependency):** provides shift/PTO/availability signals (surfaced via backend; may be partially unavailable)

### Preconditions
- User is authenticated in the POS frontend.
- User has explicit permission to view dispatch board/dispatch functions (capability-gated; backend enforces).
  - Decision rationale: Dispatch views require explicit permission + location membership (DECISION-INVENTORY-013).

### Dependencies
- A read-only dispatch view exists in Moqui workexec screens (canonical screen: `WorkOrderBoard.xml`) and/or a REST endpoint exists for availability.
  - Decision rationale: Canonical workexec screens are `WorkOrderBoard.xml`, `WorkOrderEdit.xml`, `EstimateEdit.xml` (DECISION-INVENTORY-002).
- People availability may be provided either:
  1) aggregated server-side into the dispatch view/read model (preferred), or  
  2) via a separate People availability endpoint fetched in parallel (allowed), with graceful degradation on failure.
  - Decision rationale: Prefer server-side aggregation; if separate, UI must not block core view on People failure (DECISION-INVENTORY-009).
- Standard error envelope is used for REST calls (DECISION-INVENTORY-011).
- IDs are opaque strings; UI must not validate UUID/numeric formats (DECISION-INVENTORY-003).

## 6. Functional Behavior

### Triggers
- User clicks “Check Availability” in the Availability Check panel.
- Optional: auto-run if the panel is opened with prefilled valid params (locationId, start, end). If implemented, it must not auto-run without explicit user intent unless the app already uses this pattern.

### UI actions
- Client-side validation before calling backend:
  - `locationId` required
  - `startTime` required
  - `endTime` required
  - `startTime < endTime`
- Convert displayed datetimes (user timezone input) to UTC ISO-8601 for request payload.
  - Decision rationale: Display in user timezone; interpret operational day buckets in shop timezone when applicable; requests/processing should be UTC (DECISION-INVENTORY-016).
- Submit request to availability service (see Service Contracts).
- While in-flight:
  - disable submit
  - show loading indicator
- On success:
  - Render results sorted deterministically:
    - primary: `displayName` (if provided)
    - fallback: `mechanicId` (opaque string)
  - For each mechanic:
    - show `overallStatus`
    - show conflicts sorted by `startTime` ascending
- On error:
  - Show error banner with message mapped from standard error envelope / HTTP status
  - Keep form inputs intact for retry
  - If prior results exist, keep them visible but label them as “Last successful result at <timestamp>” only if the response provides an `asOf` timestamp; otherwise do not imply staleness.

### State changes (frontend)
- Local UI state only:
  - query model
  - loading flag
  - results model
  - error model (banner + optional per-field errors)

### Service interactions
- Availability query call (workexec or aggregated dispatch read model).
- Optional mechanic directory call (People domain) to populate mechanic filter; must be non-blocking for the availability query if mechanicIds are not required.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Time window validity:** if `startTime ≥ endTime`, block submit and show inline error: “Start time must be before end time.”
- **Required location:** block submit and show inline error: “Location is required.”
- **Opaque IDs:** do not validate ID formats; treat as strings (DECISION-INVENTORY-003).

### Enable/disable rules
- Disable “Check Availability” while request is in-flight.
- Disable mechanic selector until location is chosen (prevents cross-location confusion), unless the mechanic list endpoint is explicitly global (not assumed).

### Visibility rules
- Conflicts list is shown when `conflicts.length > 0`; otherwise show “No conflicts in window.”
- If People availability dependency fails (503 or dependency error code), show a non-blocking warning in the availability panel; do not block the rest of the dispatch board (DECISION-INVENTORY-009).

### Error messaging expectations
- Errors should be normalized to the standard envelope when using REST (DECISION-INVENTORY-011):
  - 400: show “Invalid request. Please review the time window and try again.” and map `fieldErrors[]` if present
  - 401: follow app convention (redirect to login or show session expired)
  - 403: “You don’t have access to view mechanic availability.”
  - 404: “Availability service not found.”
  - 409: “Availability changed; please retry.” (only if returned)
  - 503: “Availability is temporarily unavailable because a required scheduling system is down. Please try again later.”

## 8. Data Requirements

### Entities involved (frontend models)
- `AvailabilityQuery`
- `AvailabilityResult`
- `MechanicOption` (for filter dropdown)

### Fields (types, required, defaults)

**AvailabilityQuery (request)**
- `locationId` (id string, required; opaque)
- `startTimeUtc` (datetime string, required; ISO-8601 UTC)
- `endTimeUtc` (datetime string, required; ISO-8601 UTC)
- `mechanicIds` (array<id string>, optional; opaque)
- `includeUnavailable` (boolean, optional; default `false`)
  - Note: This is allowed only if backend supports it; otherwise omit. (See Service Contracts.)

**AvailabilityResult (response)**
- `asOfUtc` (datetime string, optional but strongly recommended)
- `queryWindow.startTimeUtc` (datetime string, required)
- `queryWindow.endTimeUtc` (datetime string, required)
- `mechanicAvailabilities[]` (array, required; may be empty)
  - `mechanicId` (id string, required)
  - `displayName` (string, optional)
  - `overallStatus` (enum string, required): `AVAILABLE` | `UNAVAILABLE` | `PARTIALLY_AVAILABLE`
  - `conflicts[]` (array, required; may be empty)
    - `startTimeUtc` (datetime string, required)
    - `endTimeUtc` (datetime string, required)
    - `reasonCode` (string, required; treat as open enum)
    - `referenceId` (id string, optional; e.g., workOrderId/appointmentId if provided)
    - `referenceType` (string, optional; e.g., `WORK_ORDER`, `APPOINTMENT`, `PTO`, `SHIFT`, `TRAVEL_BLOCK`)

**MechanicOption (for filter)**
- `mechanicId` (id string, required)
- `displayName` (string, required)

### Read-only vs editable by state/role
- All returned availability data is read-only.
- Filter inputs are editable for any user who can view the panel; backend enforces access.

### Derived/calculated fields
- UI derives only display formatting:
  - Convert UTC timestamps to user timezone for display (DECISION-INVENTORY-016).
  - Do not compute “free time” or scheduling suggestions beyond listing conflicts.

## 9. Service Contracts (Frontend Perspective)

> Moqui screen implementation may call services directly rather than REST. This story supports either approach, but the contract below must be satisfied by whichever integration is used.

### Load/view calls

1) **Mechanic directory for location (optional)**
- If available via People domain:
  - `GET /rest/api/v1/people/mechanics?locationId=<id>&pageIndex=0&pageSize=50&query=<optional>`
- Response (example):
```json
{
  "pageIndex": 0,
  "pageSize": 50,
  "totalCount": 2,
  "data": [
    {"mechanicId":"M-1","displayName":"Alex Rivera"},
    {"mechanicId":"M-2","displayName":"Sam Lee"}
  ]
}
```
- Failure handling:
  - If this call fails, the availability query must still be usable (mechanic filter becomes “unavailable”; user can run without selecting mechanics).

### Create/update calls
- None.

### Submit/transition calls

2) **Availability query (required)**
- Preferred REST contract (if available):
  - `POST /rest/api/v1/workexec/availability:query`
  - Headers:
    - `Content-Type: application/json`
    - `Idempotency-Key`: **not required** (query-only; DECISION-INVENTORY-012 applies to mutations)
- Request body:
```json
{
  "locationId":"LOC-1",
  "startTimeUtc":"2026-01-19T14:00:00Z",
  "endTimeUtc":"2026-01-19T16:00:00Z",
  "mechanicIds":["M-1","M-2"]
}
```
- Response 200 body:
```json
{
  "asOfUtc":"2026-01-19T13:59:58Z",
  "queryWindow":{"startTimeUtc":"2026-01-19T14:00:00Z","endTimeUtc":"2026-01-19T16:00:00Z"},
  "mechanicAvailabilities":[
    {
      "mechanicId":"M-1",
      "displayName":"Alex Rivera",
      "overallStatus":"PARTIALLY_AVAILABLE",
      "conflicts":[
        {"startTimeUtc":"2026-01-19T14:30:00Z","endTimeUtc":"2026-01-19T15:00:00Z","reasonCode":"ASSIGNED_WORK_ORDER","referenceType":"WORK_ORDER","referenceId":"WO-123"}
      ]
    }
  ]
}
```

- Error handling expectations:
  - REST errors use standard envelope (DECISION-INVENTORY-011):
```json
{
  "code":"VALIDATION_ERROR",
  "message":"Start must be before end",
  "correlationId":"c-123",
  "fieldErrors":[{"field":"startTimeUtc","message":"Must be before endTimeUtc"}]
}
```

### Moqui screen/service integration note
- If implemented as a Moqui service call from `WorkOrderBoard.xml`, the service must return the same logical fields as `AvailabilityResult` above so the UI behavior and tests remain stable.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing required fields: prevent submit; show inline errors.
- Invalid window: prevent submit; no request sent.

### Backend validation failure (400)
- Show banner with `message`.
- If `fieldErrors[]` present, map to corresponding fields.

### Concurrency conflicts (409)
- Show “Availability changed; please retry.”
- Keep inputs; allow retry.

### Unauthorized access
- 401: follow app convention (redirect/login).
- 403: show access denied; do not show results.

### Empty states
- No mechanics returned: show empty state with suggestion to adjust filters or confirm location.
- Mechanics returned with empty conflicts: show as available.

### Partial outage / external dependency failure
- If People availability is fetched separately and fails:
  - Show warning in availability panel: “Some availability signals are unavailable; results may be incomplete.”
  - Do not block board rendering (DECISION-INVENTORY-009).
- If the availability query endpoint itself returns 503:
  - Show dependency-down error; no new results displayed.

## 12. Acceptance Criteria

### Scenario 1: Available mechanic, no conflicts
**Given** I am an authenticated Dispatcher with `WORKEXEC_DISPATCH_VIEW` permission and access to the selected location  
**And** I select a location and enter a valid start and end time window  
**When** I submit the availability check  
**And** the API returns a mechanic with `overallStatus` = `AVAILABLE` and `conflicts` = `[]`  
**Then** the UI shows that mechanic as Available  
**And** the UI shows “No conflicts in window” for that mechanic

### Scenario 2: Unavailable due to PTO
**Given** I submit a valid availability check  
**When** the API returns a mechanic with `overallStatus` = `UNAVAILABLE`  
**And** at least one conflict with `reasonCode` = `ON_PTO` and a start/end time  
**Then** the UI shows that mechanic as Unavailable  
**And** the UI lists the PTO conflict with its time range and reason code

### Scenario 3: Partially available due to assignment
**Given** I submit a valid availability check  
**When** the API returns a mechanic with `overallStatus` = `PARTIALLY_AVAILABLE`  
**And** a conflict block with `reasonCode` = `ASSIGNED_WORK_ORDER`  
**Then** the UI shows that mechanic as Partially available  
**And** the UI lists conflict blocks in chronological order by start time

### Scenario 4: Invalid time window blocked client-side
**Given** I am on the Availability Check panel  
**When** I enter a start time that is after or equal to the end time  
**Then** the Check Availability action is blocked  
**And** I see an inline validation error stating “Start time must be before end time.”  
**And** no availability API request is sent

### Scenario 5: Upstream People/HR dependency down (availability query returns 503)
**Given** I submit a valid availability check  
**When** the availability API responds with HTTP 503  
**Then** the UI shows an error banner explaining availability cannot be determined right now  
**And** the UI provides a Retry action  
**And** the form inputs remain populated

### Scenario 6: Permission denied
**Given** I submit a valid availability check  
**When** the API responds with HTTP 403  
**Then** the UI shows an access denied message  
**And** results are not displayed

### Scenario 7: People availability fetched separately fails but board remains usable (graceful degradation)
**Given** the Work Order Board loads successfully  
**And** the UI attempts to load mechanic options or People availability signals in parallel  
**When** the People endpoint responds with HTTP 500 or times out  
**Then** the Work Order Board remains visible and usable  
**And** the Availability Check panel shows a non-blocking warning and a Retry action for the People-dependent data

### Scenario 8: Unknown reason code is displayed safely
**Given** I submit a valid availability check  
**When** the API returns a conflict with `reasonCode` = `SOME_NEW_CODE`  
**Then** the UI displays the conflict time range  
**And** the UI displays the raw reason code text (without failing or hiding the conflict)
