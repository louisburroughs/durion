## Issue Body

## Title
[FRONTEND] Enforce Billing Checkout Policy: PO Capture (Write-Once), PO Override (Elevation Token), and Credit/Terms Gating

## Primary Persona
POS Clerk / Service Advisor

## Business Value
Prevent non-compliant commercial checkouts by enforcing Billing-owned checkout policy (PO requirement/override and credit/terms gating) at the point of sale, with auditable override approvals and deterministic blocking reasons to reduce AR risk and downstream reconciliation effort.

---

# 2. Story Intent

## As a / I want / So that
- **As a** POS Clerk / Service Advisor  
- **I want** the checkout flow to evaluate Billing checkout policy and enforce PO capture/override and credit/terms gating before finalization  
- **So that** commercial accounts comply with contractual terms and finance can audit who captured/overrode requirements and why.

## In-scope
- Call Billing checkout policy evaluation for the active checkout context (BILL-DEC-009).
- Render evaluation results (`messages[]`, PO requirement/format/uniqueness scope, override requirements, credit/terms gating) and block finalization when policy returns blockers.
- Capture PO number via Billing endpoint as **write-once** (BILL-DEC-009).
- Support PO override workflow using:
  - explicit permission checks (BILL-DEC-008),
  - reason code selection (BILL-DEC-009),
  - step-up authentication to obtain an **elevation token** (BILL-DEC-010),
  - optional second approver when policy requires it (BILL-DEC-009/010).
- Persist and display read-only audit metadata returned by Billing (policy version, reason code, approver identity/ies, timestamps).
- Moqui screen/form/service wiring to the Billing HTTP endpoints (BILL-DEC-009/010/015/016).

## Out-of-scope
- Admin UI to define/change BillingRules (handled by BillingRules stories; BILL-DEC-006/007).
- Accounting GL posting and reconciliation workflows.
- Payment gateway capture/void/refund behavior (except displaying Billing evaluation results that reference payment/terms eligibility).
- Implementing policy logic client-side (frontend must not hardcode thresholds; BILL-DEC-009).
- Implementing receipt delivery/reprint (separate receipts story; BILL-DEC-011).

# 3. Actors & Stakeholders
- **POS Clerk / Service Advisor (primary):** initiates finalization; enters PO; requests override.
- **Manager / Supervisor (approver):** provides step-up auth (elevation token) and may be required as second approver.
- **Finance / AR:** audits overrides and policy adherence; needs traceability and stable reason codes.
- **Billing domain services (SoR):** evaluates checkout policy; enforces write-once PO; records override audit (BILL-DEC-009/010).
- **POS Checkout/Order service (integrated):** owns checkout lifecycle/finalization; must respect Billing blocking results.
- **CRM (integrated):** customer/account master data; not authoritative for enforcement.

# 4. Preconditions & Dependencies
- User is authenticated in POS; frontend has access to current user identity and permission claims (or can query them).
- A checkout context exists with a stable `checkoutId` (preferred) or equivalent identifier used by Billing checkout endpoints (BILL-DEC-009).
- Billing endpoints are available:
  - `POST /billing/checkout/{checkoutId}/evaluate`
  - `POST /billing/checkout/{checkoutId}/po` (write-once)
  - `POST /billing/checkout/{checkoutId}/po-override`
  - `POST /billing/auth/elevate` (for elevation token; BILL-DEC-010)
  - `GET /billing/meta/reason-codes?category=PO_OVERRIDE` (BILL-DEC-007)
- POS finalization endpoint exists and returns blocking validation errors (422/409) when Billing policy is not satisfied.
- W3C Trace Context headers are propagated on all calls (BILL-DEC-015).

**Dependency note:** This story consumes Billing’s normative checkout contracts (BILL-DEC-009/010). It must not invent alternate identifiers, override semantics, or policy thresholds.

# 5. UX Summary (Moqui-Oriented)

## Entry points
- From the existing POS checkout screen for an in-progress checkout: user clicks **Finalize** (or equivalent).

## Screens to create/modify
- **Modify existing Checkout screen** (POS checkout screen tree):
  - Add a **Billing Requirements** panel that renders the latest Billing evaluation:
    - PO requirement status and any format guidance
    - credit/terms gating messages
    - `messages[]` from Billing evaluation (severity-aware)
  - Add a **PO Capture** modal/dialog (write-once submission).
  - Add a **PO Override** modal/dialog:
    - reason code selection (from discovery endpoint)
    - optional reason notes (only if backend requires; otherwise omit)
    - step-up auth flow to obtain `elevationToken`
    - optional second approver step if policy requires it
- **Modify existing Checkout Summary/Details** area:
  - Display read-only PO/override audit metadata returned by Billing (policyVersion, approvers, timestamps).

## Navigation context
- User remains on checkout screen. Blocking conditions are shown inline in the Billing Requirements panel and/or via modal prompts. Successful PO capture/override returns to checkout and enables finalization.

## User workflows (happy + alternate)

### Happy path A: PO required → capture PO → finalize
1. Clerk clicks Finalize.
2. UI calls `POST /billing/checkout/{checkoutId}/evaluate`.
3. If `poRequired=true` and PO not present, UI blocks finalization and opens PO Capture modal.
4. Clerk enters PO and submits → `POST /billing/checkout/{checkoutId}/po`.
5. UI refreshes evaluation and/or checkout state; Finalize succeeds on retry.

### Happy path B: PO not required → finalize
1. Clerk clicks Finalize.
2. UI evaluates; `poRequired=false` and no other blockers.
3. UI proceeds to finalize checkout.

### Alternate path C: PO required but override allowed → override with elevation token → finalize
1. Clerk clicks Finalize; evaluation indicates PO required and override allowed.
2. Clerk selects Override; chooses reason code.
3. UI performs step-up auth to obtain `elevationToken` (BILL-DEC-010).
4. UI submits override → `POST /billing/checkout/{checkoutId}/po-override` with reason code + elevation token (+ second approver token if required).
5. UI refreshes evaluation; Finalize succeeds on retry.

### Alternate path D: Credit/terms gating blocks charge account
1. Clerk clicks Finalize; evaluation indicates `chargeAccountEligible=false` or `creditLimitExceeded=true` (when provided).
2. UI blocks finalization and shows Billing-provided message(s).
3. Clerk changes payment method (if supported by existing POS flow) and retries; otherwise checkout cannot be finalized.

# 6. Functional Behavior

## Triggers
- User clicks **Finalize**.
- User submits **PO Capture**.
- User submits **PO Override**.
- User clicks **Retry** after an evaluation/load failure.

## UI actions (required)
1. **On Finalize click (required):**
   - Call `POST /billing/checkout/{checkoutId}/evaluate`.
   - Render returned `messages[]` and enforcement flags.
   - If evaluation indicates blockers, do not call POS finalize; instead guide user to PO capture/override or payment method change.
2. **Optional on screen load (non-blocking optimization):**
   - Preload evaluation to show requirements early, but Finalize must always re-evaluate to avoid stale policy decisions.
3. **PO capture (write-once):**
   - If `poRequired=true` and PO missing, show PO Capture modal.
   - Submit to `POST /billing/checkout/{checkoutId}/po`.
   - On success, lock PO UI (read-only) and refresh evaluation.
4. **PO override:**
   - Show Override action only if evaluation indicates `overrideAllowed=true` and user has `billing:checkout:po:override`.
   - Load reason codes from `GET /billing/meta/reason-codes?category=PO_OVERRIDE`.
   - Require step-up auth to obtain `elevationToken` when policy indicates elevation is required (BILL-DEC-010). (If backend always requires elevation for override, treat as required.)
   - Submit to `POST /billing/checkout/{checkoutId}/po-override`.
   - On success, display override audit metadata read-only and refresh evaluation.
5. **Finalize:**
   - Only attempt POS finalize after Billing evaluation indicates no blockers (or after successful PO capture/override).
   - If POS finalize returns 422/409 with Billing-related errors, display them and refresh Billing evaluation.

## State changes (frontend-visible)
- Checkout gains one of:
  - `poNumber` captured (write-once) with capture audit metadata, OR
  - `poOverridden=true` with override audit metadata.
- Checkout retains `policyVersion` (from evaluation) and any override policy version used, as returned by Billing.

## Service interactions (frontend)
- Billing:
  - `POST /billing/checkout/{checkoutId}/evaluate`
  - `POST /billing/checkout/{checkoutId}/po`
  - `POST /billing/checkout/{checkoutId}/po-override`
  - `POST /billing/auth/elevate` (step-up auth; BILL-DEC-010)
  - `GET /billing/meta/reason-codes?category=PO_OVERRIDE` (BILL-DEC-007)
- POS:
  - Existing finalize endpoint/service for checkout (name/path depends on POS domain; integrated dependency).

# 7. Business Rules (Translated to UI Behavior)

## Validation
- **Server authoritative:** PO validation (format + uniqueness scope) is enforced server-side (BILL-DEC-009).
- **Client pre-validation (optional):** UI may provide basic format hinting only when `poFormatRegex` is provided in evaluation; otherwise do not enforce a regex client-side.
- **Write-once:** Once PO is successfully captured, UI must not offer editing; any subsequent attempt must be prevented client-side and will be rejected server-side (BILL-DEC-009).

## Enable/disable rules
- Finalize must be blocked when Billing evaluation indicates any blocking condition, including:
  - `poRequired=true` and no PO and no override recorded
  - `chargeAccountEligible=false` (when attempting charge account)
  - `creditLimitExceeded=true` (when provided)
  - any `messages[]` with severity indicating “BLOCK” (exact severity mapping depends on DTO; see Open Questions)
- Override action must be hidden/disabled unless:
  - evaluation returns `overrideAllowed=true`, AND
  - user has `billing:checkout:po:override` (BILL-DEC-008).
- Elevation step must be required when policy indicates it (BILL-DEC-010). UI must not accept shared “manager codes”.

## Visibility rules
- Billing Requirements panel is visible whenever a `customerAccountId` is present on checkout (commercial vs consumer determination is based on evaluation content; UI must not infer from CRM).
- PO Capture modal appears only when evaluation indicates PO is required and missing.
- PO Override modal appears only when evaluation indicates override is allowed.

## Error messaging expectations
- Prefer Billing-provided `messages[]` text for policy outcomes to avoid UI drift.
- For generic UI messages (when backend provides only codes), use:
  - Missing PO: “PO number required for this customer. Enter PO or request override.”
  - Unauthorized override: “Insufficient permissions to override PO requirement. Contact a manager.”
  - Service unavailable: “Billing service unavailable. Try again.”
- When backend provides `correlationId`, show it in an expandable details area (BILL-DEC-015).
- Do not display sensitive internals; do not log tokens/credentials (BILL-DEC-010/015).

# 8. Data Requirements

## Entities involved (frontend perspective)
- **Checkout context** (POS-owned): `checkoutId` (preferred), plus `customerAccountId` if available.
- **BillingRuleEvaluation** (Billing-owned DTO; BILL-DEC-009).
- **PO capture record** (Billing-owned, attached to checkout context; write-once).
- **PO override audit record** (Billing-owned, attached to checkout context).

## Fields (type, required, defaults)

### BillingRuleEvaluation (read-only DTO; from `POST /billing/checkout/{checkoutId}/evaluate`)
Required fields per Billing domain guide:
- `policyVersion` (string, required)
- PO policy:
  - `poRequired` (boolean, required)
  - `poFormatRegex` (string, optional)
  - `poUniquenessScope` (enum, required when `poRequired=true`)
- Override policy:
  - `overrideAllowed` (boolean, required)
  - `overrideRequiresSecondApprover` (boolean, required)
  - `overrideReasonCodeRequired` (boolean, required)
- Credit/terms gating:
  - `chargeAccountEligible` (boolean, required)
  - `creditLimitExceeded` (boolean, optional)
- `messages[]` (array, optional) with `{code, severity, text}`

**Note:** Any additional fields (e.g., credit limit amounts, terms display) may be present but are not required for this story unless already available in the checkout UI.

### PO Capture (write-once; via `POST /billing/checkout/{checkoutId}/po`)
- Request:
  - `poNumber` (string, required)
- Response (read-only display fields; exact shape depends on backend but must include enough for audit display):
  - `poNumber` (string)
  - `capturedAt` (datetime, server-set)
  - `capturedByUserId` (string/UUID, server-set)
  - `policyVersion` (string, server-set or echoed)

### PO Override (write-once; via `POST /billing/checkout/{checkoutId}/po-override`)
- Request:
  - `reasonCode` (string, required when `overrideReasonCodeRequired=true`)
  - `elevationToken` (string, required when policy requires elevation; BILL-DEC-010)
  - `secondApproverElevationToken` (string, required when `overrideRequiresSecondApprover=true`) **(Open Question: exact field name)**
  - `reasonNotes` (string, optional) **only if backend requires**
- Response (read-only display fields):
  - `overriddenAt` (datetime, server-set)
  - `overriddenByUserId` (string/UUID, server-set)
  - `secondApproverUserId` (string/UUID, optional)
  - `reasonCode` (string)
  - `policyVersion` (string)

## Read-only vs editable by state/role
- PO number: editable only until capture succeeds; then read-only for all roles.
- Override inputs: editable only within modal prior to submission; after success read-only.
- Audit metadata visibility:
  - Visible to users with `billing:checkout:po:capture` and/or `billing:checkout:po:override` (exact UI gating may follow existing POS patterns; backend remains authoritative).

## Derived/calculated fields
- Whether second approver is required is derived from evaluation (`overrideRequiresSecondApprover`); UI must not compute it.

# 9. Service Contracts (Frontend Perspective)

> Moqui implementation note: Moqui screen actions should call a thin integration service that proxies to the Billing HTTP endpoints and propagates W3C trace headers (BILL-DEC-015). Do not hardcode frontend routes in payloads (BILL-DEC-016).

## Load/view calls
1. **Evaluate checkout policy**
   - HTTP: `POST /billing/checkout/{checkoutId}/evaluate`
   - Input: `{}` (checkoutId in path)
   - Output: `BillingRuleEvaluation`
   - Errors:
     - `403` if user lacks view permission for checkout billing evaluation (if enforced)
     - `404` if checkoutId unknown/inaccessible
     - `503` Billing unavailable

2. **Load reason codes**
   - HTTP: `GET /billing/meta/reason-codes?category=PO_OVERRIDE`
   - Output: list of `{code, displayName, description?}` (exact shape depends on backend discovery contract)

## Create/update calls
3. **Capture PO (write-once)**
   - HTTP: `POST /billing/checkout/{checkoutId}/po`
   - Request: `{ "poNumber": "string" }`
   - Errors:
     - `422` validation failure (invalid format/missing)
     - `409` conflict (already captured; or uniqueness violation depending on backend mapping)
     - `403` lacks `billing:checkout:po:capture`

4. **Override PO requirement**
   - HTTP: `POST /billing/checkout/{checkoutId}/po-override`
   - Request (minimum):
     - `{ "reasonCode": "string", "elevationToken": "string", "secondApproverElevationToken": "string?" }`
   - Errors:
     - `403` lacks `billing:checkout:po:override` or elevation not permitted
     - `422` missing reason code / missing second approver token when required
     - `409` conflict (PO already captured; checkout already finalized; override already recorded)

5. **Step-up auth (elevation token)**
   - HTTP: `POST /billing/auth/elevate`
   - Request: manager credentials per established POS auth UX (PIN/password/SSO step-up)
   - Response: `{ "elevationToken": "string", "expiresAt": "datetime" }` (shape may vary)
   - Security:
     - UI must never log credentials or tokens (BILL-DEC-010/015).

## Submit/transition calls
6. **Finalize checkout (POS-owned)**
   - Existing POS endpoint/service (not defined by Billing domain).
   - Expected errors:
     - `422` with Billing-related blocker codes/messages if finalization attempted while non-compliant
     - `409` if checkout state changed/already finalized

## Error handling expectations
- For Billing endpoints:
  - `422`: show field-level errors for PO input or override reason; show blocker messages in Billing Requirements panel.
  - `409`: show deterministic conflict message and refresh evaluation.
  - `403`: show “Contact a manager” and hide override/capture actions.
  - `503`: show blocking “Billing unavailable” state with Retry.
- Always propagate and surface `correlationId` when provided; include in support copy flow (BILL-DEC-015).
- Never log signed URLs/tokens/credentials (BILL-DEC-005/010/015).

# 10. State Model & Transitions

## Allowed states (checkout lifecycle — only those relevant to UI gating)
- POS-owned checkout states are not defined in Billing domain. For this story, treat checkout as:
  - **In Progress** (finalization allowed if Billing evaluation has no blockers)
  - **Finalized** (read-only)

## Role-based transitions
- User with `billing:checkout:po:capture` can capture PO.
- User with `billing:checkout:po:override` can request override.
- User with `billing:auth:elevate` can perform step-up auth to produce an elevation token (BILL-DEC-010).
- Second approver requirement is enforced by Billing evaluation and server-side validation.

## UI behavior per state
- In Progress:
  - show Billing Requirements panel; allow PO capture/override per evaluation + permissions.
- Finalized:
  - show PO/override audit metadata read-only; disable capture/override actions; evaluation may still be viewable for audit but must not enable changes.

# 11. Alternate / Error Flows

## Validation failures
- PO capture returns 422:
  - Keep PO modal open; show server message; focus PO field.
- Override returns 422:
  - Keep override modal open; highlight missing reason code or missing second approver step.

## Concurrency conflicts
- PO captured by another user while modal open:
  - Capture returns 409; UI closes modal, refreshes evaluation, shows “PO already captured; no changes made.”
- Checkout finalized elsewhere:
  - Any capture/override returns 409; UI refreshes checkout state and disables actions.

## Unauthorized access
- Attempt to capture PO without `billing:checkout:po:capture`:
  - Billing returns 403; UI shows “Insufficient permissions” and disables PO capture action.
- Attempt to override without `billing:checkout:po:override`:
  - Billing returns 403; UI shows “Contact a manager” and disables override action.

## Empty states
- Evaluation fails (503/network):
  - Show blocking state: “Unable to load billing requirements. Finalization is disabled.” with Retry.
- Reason codes fail to load:
  - Override modal cannot be submitted; show “Unable to load override reasons. Try again.”

# 12. Acceptance Criteria

## Scenario 1: PO required blocks finalization until captured
**Given** an in-progress checkout with `checkoutId`  
**And** Billing evaluation returns `poRequired=true`  
**And** no PO is currently recorded and no override is recorded  
**When** the POS Clerk clicks “Finalize”  
**Then** the UI calls `POST /billing/checkout/{checkoutId}/evaluate`  
**And** the UI blocks finalization and prompts for PO entry  
**And** the UI does not call POS finalize until PO is captured or override succeeds.

## Scenario 2: Valid PO is accepted and becomes immutable (write-once)
**Given** Billing evaluation returns `poRequired=true` and PO is missing  
**When** the clerk submits a PO number via the PO Capture modal  
**Then** the UI calls `POST /billing/checkout/{checkoutId}/po` with `poNumber`  
**And** on success the UI displays the PO as read-only (no edit action)  
**And** the UI refreshes evaluation and allows finalization if no other blockers remain.

## Scenario 3: Invalid PO is rejected with server validation
**Given** Billing evaluation returns `poRequired=true`  
**When** the clerk submits a PO that fails server validation  
**Then** the PO capture call returns `422`  
**And** the UI shows the server-provided validation message and keeps the modal open  
**And** finalization remains blocked.

## Scenario 4: PO uniqueness conflict is shown and finalization remains blocked
**Given** Billing evaluation returns `poRequired=true` and a `poUniquenessScope` that enforces uniqueness  
**When** the clerk submits a PO that violates uniqueness  
**Then** the PO capture call returns a conflict (`409`) or validation (`422`) per backend contract  
**And** the UI shows the backend-provided message  
**And** finalization remains blocked.

## Scenario 5: Override action is not available without permission
**Given** Billing evaluation returns `poRequired=true` and `overrideAllowed=true`  
**And** the current user does not have `billing:checkout:po:override`  
**When** the checkout screen is displayed  
**Then** the UI does not show an enabled “Override PO requirement” action  
**And** if the user attempts override via direct action, the backend returns `403` and the UI shows “Contact a manager.”

## Scenario 6: Override succeeds with elevation token when allowed
**Given** Billing evaluation returns `poRequired=true`, `overrideAllowed=true`, and `overrideReasonCodeRequired=true`  
**When** an authorized user selects a reason code and completes step-up auth to obtain an `elevationToken`  
**And** submits the override  
**Then** the UI calls `POST /billing/checkout/{checkoutId}/po-override` with `reasonCode` and `elevationToken`  
**And** on success the UI displays override audit metadata read-only  
**And** the UI refreshes evaluation and allows finalization if no other blockers remain.

## Scenario 7: Second approver required is enforced
**Given** Billing evaluation returns `overrideRequiresSecondApprover=true`  
**When** the user submits override without completing the second approver step  
**Then** the override call returns `422` indicating second approver is required  
**And** the UI does not mark the checkout as overridden  
**When** the user completes second approver step-up auth and provides the required second approver token  
**Then** override submission succeeds and both approvers are reflected in returned audit metadata.

## Scenario 8: Billing service unavailable blocks finalization (fail-safe)
**Given** the Billing evaluation endpoint is unavailable (`503`)  
**When** the POS Clerk clicks “Finalize”  
**Then** the UI blocks finalization  
**And** shows a retryable error state  
**And** does not call POS finalize while Billing evaluation cannot be obtained.

## Scenario 9: Credit/terms gating blocks charge account when indicated
**Given** Billing evaluation indicates `chargeAccountEligible=false` **or** `creditLimitExceeded=true`  
**When** the POS Clerk clicks “Finalize”  
**Then** the UI blocks finalization  
**And** displays Billing-provided message(s) explaining the gating condition  
**And** does not capture PO or submit override as a side effect.

# 13. Audit & Observability

## User-visible audit data
- Display (read-only) on checkout screen:
  - `policyVersion` from Billing evaluation
  - PO capture audit fields (capturedAt, capturedByUserId) when PO captured
  - Override audit fields (reasonCode, overriddenAt, overriddenByUserId, secondApproverUserId when present)
- Provide “Copy correlation ID” action when available for support.

## Status history
- UI derives a simple compliance indicator from evaluation + recorded PO/override:
  - `COMPLIANT` (PO not required or PO captured)
  - `OVERRIDDEN` (override recorded)
  - `BLOCKED` (evaluation indicates blockers)
- Do not invent additional billing states.

## Traceability expectations
- Propagate W3C `traceparent` (and `tracestate` if present) on all Billing calls (BILL-DEC-015).
- Client logs (non-PII) include:
  - `checkoutId`, `customerAccountId` (if present), `policyVersion`, `correlationId`
- Never log:
  - credentials, elevation tokens, or any bearer tokens (BILL-DEC-010/015).
