## Title
[FRONTEND] [STORY] CRM Snapshot Panel: Load Customer + Vehicle Context (Read-only) for Order Flow

## Primary Persona
Service Advisor (POS user creating/managing an order)

## Business Value
Provide fast, consistent, read-only access to CRM-owned customer and vehicle context (and CRM-provided billing-related configuration fields) during order creation, enabling correct communication choices and downstream order flow decisions without duplicative lookups.

---

# 2. Story Intent

## As a / I want / So that
As a **Service Advisor**, I want to **load and view a CRM Customer Snapshot** (party, contacts, vehicles, and CRM-provided billing-related configuration fields) for the selected customer so that **order creation can reference the latest customer context** and I can validate the context quickly.

## In-scope
- Frontend screen/component(s) to fetch and display a **CustomerSnapshot** for a selected `partyId` (canonical identifier; DECISION-INVENTORY-001).
- Display (read-only):
  - Party/account metadata
  - Contact points / contacts (including primary indicators per kind and preferred contact method where provided)
  - Vehicles (lightweight list)
  - Billing-related configuration fields as provided by CRM snapshot (read-only; UI does not enforce policy)
- Explicit “Refresh” behavior.
- Visible snapshot metadata: retrieved timestamp, source, stale indicator (DECISION-INVENTORY-004).
- Deterministic handling for 403/404/409/5xx and empty states.
- Moqui screen routing + transitions + service calls (frontend perspective).
- Provide a **read-only context object** to the order flow (in-memory only) for downstream screens to reference (no persistence in this story).

## Out-of-scope
- Editing customer/contact/vehicle/billing configuration (CRM is SoR; read-only here).
- Implementing enforcement of billing policies (e.g., blocking checkout if PO missing).
- Customer search/selection UI (this story starts from a known/selected `partyId`).
- Vehicle service history, attachments, warranty, etc.
- Event-driven cache invalidation (backend-owned); frontend uses metadata + manual refresh only.
- Any browser-direct calls to snapshot services (must be Moqui-proxied; DECISION-INVENTORY-004).

# 6. Functional Behavior

## Triggers
- Screen enter with `partyId`.
- `partyId` changes (user selects a different customer).
- User clicks “Refresh snapshot”.

## UI actions
- Show loading state while fetching.
- Render snapshot sections when loaded.
- Refresh re-fetches snapshot (server-side; no client cache assumptions).
- Provide a “Copy identifiers” action **only** for non-PII identifiers (e.g., `partyId`, `vehicleId`) if consistent with existing POS patterns; must not copy VIN/license plate by default.

## State changes
- `snapshotLoadState`: `idle | loading | loaded | error`
- `snapshot`: last successful DTO (cleared on party change before load completes to prevent leakage).
- `lastError`: structured error info for display.
- `orderContext.customerSnapshot` (in-memory only): set on successful load; cleared on party change and on 403/404.

## Service interactions (frontend ↔ Moqui ↔ CRM)
- Frontend calls **Moqui** endpoint/service to fetch snapshot by `partyId` (DECISION-INVENTORY-004).
- Moqui proxies to CRM snapshot service, injecting correlation headers (`X-Correlation-Id`, `traceparent`) (DECISION-INVENTORY-004).
- Handle responses:
  - 200: render payload.
  - 403: show access denied; do not render any snapshot fields.
  - 404: show not found; do not render prior snapshot.
  - 409 `PARTY_MERGED`: show merged message and offer “Load merged party” action using `mergedToPartyId` (DECISION-INVENTORY-014).
  - 5xx/timeout: show error; if response still includes a snapshot with `metadata.stale=true`, render it with warning.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- `partyId` is required and must be UUID-shaped before calling load service (DECISION-INVENTORY-001).
  - If missing/invalid: do not call backend; show inline error “Customer is required”.
- UI must not infer or compute billing policy; it only displays fields provided.
- Snapshot must be retrieved via Moqui proxy; no browser direct calls (DECISION-INVENTORY-004).

## Enable/disable rules
- “Refresh snapshot” enabled only when:
  - `partyId` present AND not currently loading.
- On 403:
  - Disable refresh and hide all customer details; show only permission message.

## Visibility rules
- Contacts section always visible; empty state if none.
- Vehicles section always visible; empty state if none.
- Billing-related configuration section visible; missing fields show “Unavailable”.
- Stale indicator visible when `metadata.stale=true`; show `staleSince` if provided.

## Error messaging expectations
- 404: “Customer not found. Verify the selected customer.”
- 403: “You do not have permission to view this customer.”
- 409 `PARTY_MERGED`: “This customer was merged into another record.” + show `mergedToPartyId` and action to load it.
- Network/5xx: “Unable to load customer details. Try again.” Provide correlation id if available; no stack traces.

# 9. Service Contracts (Frontend Perspective)

> Contracts below are implementation targets for Moqui endpoints/services. Exact names/paths must be confirmed in codebase; UI must call Moqui, not CRM directly (DECISION-INVENTORY-004).

## Load/view calls
### Operation: Get customer snapshot (Moqui-proxied)

- **Input params**:

### Error payload shape (required)

- `message`: string (required)

## Create/update calls
- none

## Submit/transition calls
- none (snapshot context is in-memory only for this story)

## Error handling expectations
- 400: invalid `partyId` format → show inline validation error.
- 403: forbidden → show access denied; clear any prior snapshot.
- 404: not found → show not found; clear any prior snapshot.

# 10. State Model & Transitions

## Allowed states (UI component)
- `idle`: no party selected or invalid partyId.
- `loading`: fetching snapshot.
- `loaded`: snapshot displayed.
- `error`: load failed (with error type).

## Role-based transitions
- Service Advisor (with permission):
  - `idle → loading` on valid party selection.
  - `loaded → loading` on refresh.
- Unauthorized user:
  - `loading → error(forbidden)`; details remain hidden.

## UI behavior per state
- `idle`: “Select a customer to view details.”
- `loading`: disable refresh; show loading indicator.
- `loaded`: show sections + metadata badges (source/stale).
- `error`:
  - forbidden: show access denied; no retry unless party changes.
  - not found: show not found; allow party change.
  - merged: show merged message; allow “Load merged party”.
  - transient: show retry/refresh.

# 11. Alternate / Error Flows

## Validation failures
- Missing/invalid `partyId`:
  - No backend call.
  - Panel remains `idle` with inline validation message.

## Concurrency conflicts
- If backend returns 409 non-merge conflict:
  - Show message “Customer data changed; refresh snapshot.”
  - Refresh remains available.

## Unauthorized access
- On 403:
  - Clear any previously loaded snapshot from UI state immediately (prevent leakage when switching parties).
  - Show permission message only.

## Empty states
- Contacts empty: show “No contacts on file.”
- Vehicles empty: show “No vehicles associated.”
- Billing config missing: show “Billing configuration unavailable.”

## Party merged
- On 409 `PARTY_MERGED` with `mergedToPartyId`:
  - Show merged message.
  - Provide action “Load merged customer” which triggers load with `mergedToPartyId` (DECISION-INVENTORY-014).

# 12. Acceptance Criteria

## Scenario 1: Load snapshot on customer selection (success)
Given I am a Service Advisor with permission to view customer party A  
And I navigate to an order draft where party A is selected with a valid partyId  
When the Customer Snapshot panel loads  
Then the UI requests the customer snapshot via a Moqui-proxied endpoint using partyId A  
And displays party metadata, contacts (may be empty), vehicles (may be empty), and billing configuration fields when present  
And displays snapshot metadata including retrievedAt and source (CACHE or CRM_API) and stale indicator

## Scenario 2: Refresh snapshot
Given a customer snapshot for party A is displayed  
When I click “Refresh snapshot”  
Then the UI re-requests the snapshot for party A  
And shows a loading state while the request is in progress  
And updates the displayed data and metadata to match the latest response

## Scenario 3: Customer not found (404)
Given I attempt to load a snapshot for partyId X that does not exist  
When the backend responds with 404  
Then the UI shows “Customer not found. Verify the selected customer.”  
And does not display any prior customer’s snapshot data

## Scenario 4: Unauthorized (403)
Given I do not have permission to view party A  
When the UI requests the snapshot for party A  
And the backend responds with 403  
Then the UI shows “You do not have permission to view this customer.”  
And no customer details (contacts/vehicles/billing configuration) are rendered  
And any previously loaded snapshot data is cleared from the panel state

## Scenario 5: Party merged (409 PARTY_MERGED)
Given party A has been merged into party B  
When the UI requests the snapshot for party A  
And the backend responds with 409 and errorCode PARTY_MERGED and mergedToPartyId B  
Then the UI shows a merged message including mergedToPartyId B  
When I choose “Load merged customer”  
Then the UI requests the snapshot for party B and renders it if permitted

## Scenario 6: Backend returns stale snapshot
Given the backend returns a snapshot response where metadata.stale is true  
When the UI renders the snapshot  
Then the UI shows a clear warning that the data is stale  
And displays staleSince when provided  
And still renders available snapshot sections

## Scenario 7: Network/5xx failure without snapshot
Given the backend is unavailable and no snapshot payload is returned  
When the snapshot request fails  
Then the UI shows a recoverable error message and a retry/refresh action  
And the UI surfaces correlation information if available (e.g., X-Correlation-Id)  
And the UI does not log or display PII values (contacts, VIN, license plate)
