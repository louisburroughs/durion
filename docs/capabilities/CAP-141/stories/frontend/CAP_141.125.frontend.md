## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Audit: View/Search Audit Trail for Schedule & Assignment Changes

### Primary Persona
Shop Manager

### Business Value
Provide a persistent, immutable, and searchable audit history of scheduling and mechanic assignment changes so Shop Managers can investigate discrepancies, resolve disputes, and support compliance/accountability.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Shop Manager
- **I want** to view and search audit history for schedule and mechanic assignment changes (including who/when/what changed and why)
- **So that** I can explain conflicts, resolve disputes, and demonstrate operational accountability.

### In-scope
- New/updated Moqui **screens** in the frontend to:
  - Search audit logs using **mandatory UTC date range** plus **at least one indexed filter** (AUD-SEC-005).
  - View audit log list results (reverse chronological).
  - View audit log detail (including normalized fields; raw payload only when authorized).
- UI handling for immutability (read-only) and authorization failures.
- UI deep-link/drilldown behavior using **structured link metadata** (no hardcoded URLs) when present (AUD-SEC-011).
- Location scoping behavior:
  - Default to current POS location context.
  - Allow cross-location search only when explicitly permitted and explicitly filtered (AUD-SEC-002/003).

### Out-of-scope
- Producing audit events (workexec outbox/eventing) and audit persistence/retention enforcement (backend responsibility).
- Creating/updating/deleting audit records (must not exist in UI).
- Managing reason code registry (admin UI) (`audit:reason-code:manage` not in scope).
- Any claim of cryptographic verification of proof fields (hash/signature) unless backend provides explicit verification result (AUD-SEC-009).

## 3. Actors & Stakeholders
- **Shop Manager (primary):** Searches and reviews audit history for their location.
- **Compliance Auditor (secondary):** Uses the same UI for investigations; may export and view pricing evidence if separately permitted.
- **Support/Operations (secondary):** Uses the same UI for investigations; raw payload only if explicitly granted.
- **Service Advisor / Dispatcher / Mechanic (implicit):** Appears as “actor” on audit entries.
- **System (Audit domain):** System of record for audit entries; enforces tenant/location isolation, guardrails, and permissions.

## 4. Preconditions & Dependencies
- User is authenticated and has an active **tenant** context (AUD-SEC-001).
- User has a current **location context** in the POS session.
- Backend capability endpoints exist and enforce security/guardrails (normative):
  - `GET /audit/logs/search`
  - `GET /audit/logs/detail?eventId=...`
  - `GET /audit/meta/eventTypes`
  - `GET /audit/meta/reasonCodes` (optional for display metadata)
  - `GET /audit/meta/locations` (required only if cross-location UI is enabled)
- Authorization is permission-string based (AUD-SEC-003). Screens must not ship without explicit permission checks:
  - Search/list: `audit:log:view`
  - Detail: `audit:log:view-detail`
  - Raw payload: `audit:payload:view`
  - Cross-location: `audit:scope:cross-location`
  - Proof fields: `audit:proof:view` (display-only)
  - Export (not in this story unless added later): `audit:export:execute`, `audit:export:download`
- Backend returns audit fields required for rendering and safe rendering requirements are met:
  - Raw payload and any restricted fields are already redacted/marked by backend; UI must not infer redaction (AUD-SEC-004).
  - UI must render raw payload as escaped text (AUD-SEC-004).
- Query guardrails are enforced server-side and mirrored in UI:
  - Mandatory date range (`fromUtc`, `toUtc`)
  - Max window 90 days (default)
  - At least one indexed filter beyond date range (AUD-SEC-005)

  - Work Order detail → “View Audit History” (prefill `workOrderId`)
  - Appointment detail → “View Audit History” (prefill `appointmentId`)
  - Mechanic profile/detail → “View Audit History” (prefill `mechanicId`)
  - (Optional) Schedule/assignment UI surfaces → “View Audit History” (prefill relevant IDs)
  - These links pass identifiers only; destination enforces authorization (AUD-SEC-011).

### Screens to create/modify
- **Create** `apps/pos/screen/audit/AuditLogSearch.xml`
  - Search form + results list/grid.
- **Create** `apps/pos/screen/audit/AuditLogDetail.xml`
  - Read-only audit entry detail view.
- **Modify** POS navigation/menu screen to add “Audit Logs” entry under Administration/Compliance with permission gating.

### Navigation context
- `AuditLogSearch` → selecting a result navigates to `AuditLogDetail` with `eventId`.
- `AuditLogDetail` includes “Back to results” preserving prior search parameters (Moqui parameter pass-through).
- Deep links from detail use structured metadata and route resolution in frontend; do not embed URLs in audit data (AUD-SEC-011).

### User workflows (happy + alternate paths)

**Happy path (search + view):**
1. User opens Audit Logs.
2. User sets **From (UTC)** and **To (UTC)** within 90 days.
3. User provides at least one indexed filter (e.g., `workOrderId` or `appointmentId` or `mechanicId` or `eventType`).
4. User runs search; sees results newest-first.
5. User opens an entry; sees normalized fields, summary/patch, reason fields, correlation id, and optional deep links.
6. If authorized, user can expand raw payload (escaped text).

**Alternate paths:**
- No results → show empty state with guidance to adjust filters.
- Cross-location user → can select multiple locations only if permitted; otherwise location is implicit.
- Unauthorized → show access denied without leaking existence of records.
- Guardrail violation → show inline validation errors before submit; if backend rejects, map field errors.

**Results list actions:**

**Detail view actions:**

- Show “Show raw payload” toggle/section only if user has `audit:payload:view` and backend returned `rawPayload` (AUD-SEC-004).
- Show proof fields section only if user has `audit:proof:view` and fields exist (AUD-SEC-009).

- On search submit:
  - Call `GET /audit/logs/search` with validated params.
- On detail load:
  - Call `GET /audit/logs/detail?eventId=...`.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Mandatory date range (AUD-SEC-005):**
  - `fromUtc` and `toUtc` are required.
  - Validate `fromUtc <= toUtc`.
  - Validate `(toUtc - fromUtc) <= 90 days` (default max window). If tenant policy lowers max, backend may reject; UI should display backend field error.
- **Mandatory indexed filter (AUD-SEC-005):**
  - Require at least one of the indexed filters listed in Functional Behavior before enabling submit.
  - If user clears all indexed filters, disable Search and show inline message: “Add at least one filter (e.g., Work Order ID, Appointment ID, Mechanic ID, Event Type).”
- **Location scoping (AUD-SEC-002/003):**
  - If user has `audit:scope:cross-location` and selects “All/Multiple locations” mode, require at least one `locationId` selected; send `locationIds[]`.
  - If user lacks cross-location permission, do not allow specifying `locationIds[]` in UI.
- **Identifier semantics (AUD-SEC-007):**
  - Treat identifiers as opaque exact-match strings; no formatting assumptions.
  - Support product search by `productId`, `sku`, `partNumber` (even if not used in this story’s primary flows).
- **Raw payload safety (AUD-SEC-004):**
  - Raw payload and any JSON-like fields must be rendered as escaped text (never HTML).
  - UI must not attempt to “unredact” or infer hidden fields.

### Enable/disable rules
- Disable “Search” until:
  - date range valid, AND
  - max window valid, AND
  - at least one indexed filter provided, AND
  - if cross-location mode is used, at least one location selected.
- Disable/hide “Show raw payload” unless user has `audit:payload:view`.

### Visibility rules
- Show `changePatch` section when present; otherwise show `changeSummaryText` if present.
- Show both if both exist.
- Show deep-link actions only when link metadata exists.
- Show proof fields only when present and user has `audit:proof:view`; label as “Provided (not verified)” unless backend provides explicit verification status (AUD-SEC-009).

### Error messaging expectations
- 400 validation errors:
  - Map backend field errors to inline messages on corresponding fields (`fromUtc`, `toUtc`, filters, `locationIds`).
- 401:
  - Redirect to login/session restore per POS standard.
- 403:
  - Show access denied message without revealing whether specific `eventId` exists.
- 404 (detail):
  - Show “Audit record not found” without additional hints.
- 429:
  - Show rate limit message and allow retry after a short delay.
- 5xx/timeouts:
  - Show generic retryable error; do not display raw payload in error logs.

- Auth: requires `audit:log:view` (or stricter if backend chooses)
- Response: `reasonCodes[]` with `{ code, displayName?, description? }`
- UI behavior: if endpoint unavailable, allow free-text reasonCode filter and display codes as-is.

3) **Locations (only for cross-location users)**
- `GET /audit/meta/locations`
- Auth: requires `audit:scope:cross-location`
- Response: `locations[]` with `{ locationId, displayName }`
- UI behavior: show multi-select only when permitted; do not call endpoint otherwise (AUD-SEC-002/003).

### Create/update calls
- None (immutability; no create/update/delete UI).

### Submit/transition calls
1) **Search/list audit logs**
- `GET /audit/logs/search`
- Auth: requires `audit:log:view`
- Request params (AND semantics):
  - `fromUtc` (required)
  - `toUtc` (required)
  - At least one indexed filter (required): one or more of
    - `workOrderId`, `appointmentId`, `mechanicId`, `movementId`, `productId`, `sku`, `partNumber`, `actorId`, `eventType`, `aggregateId`, `correlationId`, `reasonCode`
  - `locationIds[]` (required only for cross-location searches; requires `audit:scope:cross-location`)
  - Pagination:
    - Prefer cursor-based: `pageToken` (optional) and `pageSize` (optional)
    - If backend uses offset: `pageIndex` + `pageSize`
- Response:
  - `results[]` (array of AuditLog summary records)
  - Pagination metadata:
    - Either `{ nextPageToken }` OR `{ totalCount, pageIndex, pageSize }`
  - Backend may include `isTruncated` for safety; UI should display “Results truncated; refine filters” if present.

2) **Get audit log detail**
- `GET /audit/logs/detail?eventId=...`
- Auth: requires `audit:log:view-detail`
- Request:
  - `eventId` (required)
- Response:

- 401:

- 403:
  - Forbidden; show access denied without leaking record existence.
- 404:
  - Detail not found; show not found state.
- 429:

## 11. Alternate / Error Flows

### Validation failures
- Missing `fromUtc`/`toUtc` → block submit; inline errors.
- `toUtc < fromUtc` → block submit; inline error.
- Date range > 90 days → block submit; inline error: “Date range must be 90 days or less.”
- No indexed filter provided → block submit; inline error.
- Cross-location:
  - User selects cross-location mode but no locations selected → block submit; inline error.
  - User without permission attempts to access cross-location via URL params → ignore params client-side; backend should also reject.

### Concurrency conflicts
- Not applicable (read-only). If record disappears between list and detail:
  - Detail returns 404 → show not found state and allow return to results.

### Unauthorized access
- Search screen without `audit:log:view`:
  - Show access denied; do not call meta/search endpoints.
- Detail screen without `audit:log:view-detail`:
  - Show access denied; do not call detail endpoint.
- Raw payload:
  - If user toggles raw payload but lacks permission, do not show; if backend returns 403 for payload-including detail, show forbidden and do not retry.

### Empty states
- No results:
  - Show “No audit entries found for selected filters.”
  - Provide actions: “Adjust date range” and “Clear filters” (retains date range unless user clears explicitly).
