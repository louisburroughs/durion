## Issue Body

## Title
[FRONTEND] [STORY] Security: RBAC Admin UI — Manage Roles and Role↔Permission Grants

## Primary Persona
System Administrator / Admin (authorized to manage RBAC)

## Business Value
Enable administrators to manage tenant-scoped roles and assign predefined permissions so protected POS operations are enforced consistently (deny-by-default) and RBAC changes are auditable and supportable via correlation IDs.

---

# 2. Story Intent

## As a / I want / So that
**As an** Admin,  
**I want** to create roles, update role metadata (non-identifier fields), and grant/revoke predefined permissions to roles,  
**So that** access to sensitive actions is controlled by explicit grants and RBAC configuration changes are traceable.

## In-scope
- Moqui frontend screens to:
  - List roles (paged)
  - Create role
  - View role details (including granted permissions)
  - Edit role description (roleName is immutable)
  - Grant/revoke permissions to a role (idempotent; supports retry)
  - View permission registry (read-only list/search)
- UI route/menu gating and server-enforced handling for authorization:
  - Deny-by-default behavior when unauthorized (hide where possible; always handle 401/403)
- Tenant-scoped behavior:
  - UI does not accept tenantId/locationId inputs; tenant context is derived from auth/request context (trusted)

## Out-of-scope
- Creating/editing permission keys in UI (permission registry is code-first and UI read-only) (DECISION-INVENTORY-006)
- Principal↔Role assignment UI (PrincipalRole/UserRole management) (DECISION-INVENTORY-007)
- Location-scoped RBAC/ABAC (DECISION-INVENTORY-008)
- Approvals/workflow state machines (owned by workexec) (DECISION-INVENTORY-014)
- Financial exception audit UI (owned by audit domain; security only gates access) (DECISION-INVENTORY-012)

# 5. UX Summary (Moqui-Oriented)

## Entry points
- Admin navigation: **Security → Roles**
- Admin navigation: **Security → Permissions** (read-only registry)

## Screens to create/modify (Moqui)
1. `apps/pos/security/RoleList.xml`
   - Paged list of roles; search by roleName; link to detail; create action.
2. `apps/pos/security/RoleCreate.xml`
   - Create role form (roleName, description).
3. `apps/pos/security/RoleDetail.xml`
   - Read-only role metadata + granted permissions list; actions: Edit Description, Manage Permissions.
4. `apps/pos/security/RoleEdit.xml`
   - Edit role description only (roleName read-only/disabled); link to Manage Permissions section.
5. `apps/pos/security/RolePermissions.xml` (can be a separate screen or a section within RoleEdit)
   - Grant/revoke permissions for a role using a dual-list or checklist pattern; save applies changes.
6. `apps/pos/security/PermissionList.xml`
   - Read-only permission registry list/search (no create/edit).

## Navigation context
- Breadcrumbs:
  - Security → Roles → {roleName}
  - Security → Permissions
- Deep links use `roleId` (immutable identifier) in the URL/parameters. (DECISION-INVENTORY-004)

## User workflows (happy + alternate)
### Happy path: create role, then grant permissions
1. Admin opens Role List.
2. Admin selects Create Role.
3. Admin enters roleName and optional description; submits.
4. UI navigates to Role Detail for returned `roleId`.
5. Admin opens Manage Permissions.
6. UI loads permission registry + current grants; admin selects permissions; saves.
7. UI shows updated grants and success confirmation.

### Alternate path: update description only
1. Admin opens Role Detail → Edit.
2. Admin updates description; saves.
3. UI reloads role and shows updated description.

### Alternate path: revoke permissions
1. Admin opens Manage Permissions.
2. Admin deselects one or more permissions; saves.
3. UI confirms and reflects updated grants.

### Unauthorized path
- User without required permission hits any RBAC route:
  - UI shows Access Denied (no data leakage) and provides a link back to a safe landing page.

# 6. Functional Behavior

## Triggers
- Enter Role List / Role Detail / Permission List routes
- Submit Create Role form
- Submit Update Role (description) form
- Submit permission grant/revoke changes

## UI actions (explicit)
### Role List
- Search input (roleName contains match)
- Pagination controls (pageIndex/pageSize)
- Row click → Role Detail (roleId)
- Create button → Role Create (requires `security:role:create`)

### Role Create
- Inputs:
  - roleName (required)
  - description (optional)
- Save:
  - Calls create role endpoint
  - On success, transitions to Role Detail for returned roleId
- Cancel: returns to Role List

### Role Detail
- Displays:
  - roleName (read-only)
  - description
  - granted permissions (list)
- Actions:
  - Edit Description (requires `security:role:update`)
  - Manage Permissions (requires `security:role_permission:grant` and/or `security:role_permission:revoke` to save; view requires `security:permission:view` and `security:role:view`)

### Role Edit (description)
- roleName field is displayed but disabled/read-only (immutable) (DECISION-INVENTORY-004)
- description editable
- Save calls update role endpoint; on success returns to Role Detail

### Role Permissions (grant/revoke)
- Loads:
  - Permission registry (read-only) (DECISION-INVENTORY-006)
  - Current role grants
- Admin selects desired permissions
- Save behavior:
  - Preferred: compute diff and call grant/revoke endpoints per change (idempotent under retry) (DECISION-INVENTORY-005)
  - Optional: if backend supports replace-set endpoint, UI may call replace-set with full desired set (requires `security:role_permission:replace`)
- After save success:
  - UI reloads role grants from server and updates display

### Permission List (registry)
- Search by permissionKey and/or description
- Read-only; no create/edit actions

## State changes
- Role created
- Role description updated (roleName unchanged)
- RolePermission grants added/removed

## Service interactions (Moqui)
- Moqui screens use REST calls to `/api/v1/security/*` (via configured gateway) and map responses into screen context.
- All mutation calls must surface returned `correlationId` on success toast and on error banner for support traceability. (DECISION-INVENTORY-015)

# 7. Business Rules (Translated to UI Behavior)

## Validation
### Role name
- Required on create.
- UI performs basic required validation; backend is authoritative.
- Role name uniqueness is enforced on normalized form: trim + collapse whitespace + lowercase. (DECISION-INVENTORY-003)
  - If backend returns `409 ROLE_NAME_TAKEN`, UI highlights roleName and shows: “Role name already exists.”

### Role name immutability
- UI must not allow editing roleName after creation (disabled field). (DECISION-INVENTORY-004)
- If backend returns `ROLE_NAME_IMMUTABLE` (or similar) on update, UI shows error and keeps user on form.

### Permission keys
- Permission keys are immutable and formatted `domain:resource:action` in snake_case. (DECISION-INVENTORY-002)
- UI must not accept free-text permission keys; selection only from registry list. (DECISION-INVENTORY-006)

### Tenant scoping
- UI must not display or accept tenantId/locationId fields.
- Any cross-tenant access attempts should result in `404 NOT_FOUND` (preferred) or `403 FORBIDDEN`; UI displays “Not found” or “Access denied” without leaking existence. (DECISION-INVENTORY-008)

## Enable/disable rules
- Disable Save buttons while request is in-flight.
- Role Permissions Save enabled only when selection differs from loaded grants (diff-based), OR allow idempotent save if implemented as replace-set; if using grant/revoke diff, require diff to enable.

## Visibility rules
- Menu items:
  - Show “Security → Roles” only if user has `security:role:view`.
  - Show “Security → Permissions” only if user has `security:permission:view`.
- Screen-level:
  - Even if menu hidden, direct navigation must handle 401/403/404 safely.

## Error messaging expectations (canonical envelope)
- 401 → “Your session has expired. Please sign in again.” + show correlationId
- 403 (`code=FORBIDDEN`) → “Access denied.” + correlationId
- 404 (`code=NOT_FOUND`) → “Not found.” + correlationId
- 409 (`ROLE_NAME_TAKEN`, `EMAIL_MISMATCH` not applicable here) → show conflict message + correlationId
- 400 (`VALIDATION_FAILED`) → show fieldErrors inline when present; otherwise banner + correlationId
- Network/5xx → “Something went wrong. Try again.” + correlationId if available

# 9. Service Contracts (Frontend Perspective)

All endpoints are under `/api/v1/security/*` and return canonical error envelopes on non-2xx. (DECISION-INVENTORY-015)

## Load/view calls
### List Roles
- `GET /api/v1/security/roles?pageIndex={n}&pageSize={n}&search={string?}`
- Response:
  - `items: [{ roleId, roleName, description }]`
  - `pageIndex`, `pageSize`, `totalCount`

### Get Role
- `GET /api/v1/security/roles/{roleId}`
- Response: `{ roleId, roleName, description, createdAt?, updatedAt? }`

### List Permissions (registry)
- `GET /api/v1/security/permissions?pageIndex={n}&pageSize={n}&search={string?}`
- Response:
  - `items: [{ permissionKey, description? }]`
  - `pageIndex`, `pageSize`, `totalCount`

### Get Role Permissions (grants)
- `GET /api/v1/security/roles/{roleId}/permissions`
- Response: `{ roleId, permissionKeys: [string] }` OR `{ items: [{permissionKey,...}] }` (frontend must support either by adapter; see Open Questions if backend differs)

## Create/update calls
### Create Role
- `POST /api/v1/security/roles`
- Request: `{ roleName: string, description?: string }`
- Success (201/200): `{ roleId, roleName, description }`
- Errors:
  - 400 `VALIDATION_FAILED` with `fieldErrors`
  - 409 `ROLE_NAME_TAKEN`

### Update Role (description only)
- `PUT /api/v1/security/roles/{roleId}`
- Request: `{ description?: string }`
- Success: `{ roleId, roleName, description }`
- Errors:
  - 400 `VALIDATION_FAILED`
  - 404 `NOT_FOUND`
  - 409 `ROLE_NAME_IMMUTABLE` if roleName attempted (UI should not send roleName)

## Submit/transition calls
### Grant permission to role (idempotent)
- `POST /api/v1/security/roles/{roleId}/permissions/grant`
- Request: `{ permissionKey: string }`
- Success: 200/204

### Revoke permission from role (idempotent)
- `POST /api/v1/security/roles/{roleId}/permissions/revoke`
- Request: `{ permissionKey: string }`
- Success: 200/204

### Optional: Replace-set semantics (if supported)
- `PUT /api/v1/security/roles/{roleId}/permissions`
- Request: `{ permissionKeys: [string] }`
- Success: `{ roleId, permissionKeys: [string] }` or 204
- Note: This is optional; grant/revoke must exist. (DECISION-INVENTORY-005)

## Error handling expectations
- All non-2xx responses include `correlationId` (DECISION-INVENTORY-015)
- UI maps:
  - `fieldErrors[]` to inline field messages
  - otherwise show banner with `message` and `correlationId`
- After any failed grant/revoke batch, UI must reload current grants from server to avoid drift.

# 10. State Model & Transitions

## Allowed states
- Roles have no UI-managed lifecycle state in v1 (existence implies active).
- Permissions are registry entries (read-only).

## Role-based transitions (permission-gated)
- View roles list/detail:
  - Requires `security:role:view`
- Create role:
  - Requires `security:role:create`
- Update role description:
  - Requires `security:role:update`
- View permission registry:
  - Requires `security:permission:view`
- Manage role permissions:
  - Viewing selection UI requires `security:permission:view` + `security:role:view`
  - Saving changes requires:
    - `security:role_permission:grant` for additions
    - `security:role_permission:revoke` for removals
    - If using replace-set endpoint: `security:role_permission:replace`

## UI behavior per state
- Unauthorized (401/403): show access denied/session expired; do not render tables with cached data.
- Not found (404): show not found; do not reveal whether role exists in another tenant.
- Loading: show loading indicator; disable actions.
- Saving: disable submit; show progress; on success show toast with correlationId.

# 11. Alternate / Error Flows

## Validation failures
- Create Role with empty roleName:
  - Client blocks submit; if server returns 400, show inline error from `fieldErrors`.
- Create Role with duplicate normalized name:
  - Server returns 409 `ROLE_NAME_TAKEN`; UI highlights roleName and preserves entered values.

## Concurrency conflicts
- Permission grants are idempotent; repeated grant/revoke calls are safe under retry. (DECISION-INVENTORY-005)
- If backend returns 409 for concurrent updates (rare for grant/revoke), UI shows: “Changes could not be applied due to a conflict. Reload and try again.” then reloads grants.

## Unauthorized access
- Direct URL access without permission:
  - Backend returns 403; UI shows Access Denied and provides navigation back.

## Empty states
- No roles:
  - Show empty state with Create Role CTA (only if `security:role:create`).
- No permissions returned:
  - Show “No permissions available” and disable Manage Permissions save.

## Partial failure during batch grant/revoke
- If multiple grant/revoke calls are made and one fails:
  - UI shows error banner with correlationId
  - UI reloads grants from server and re-computes diff (user may retry)

# 12. Acceptance Criteria

## Scenario 1: Authorized admin can view roles list (paged)

**And** I see a paged list of roles (roleName visible)  
**And** I can open a role detail screen via its `roleId`

## Scenario 2: Unauthorized user is blocked from Roles screens (deny-by-default)
**Given** I am authenticated and do not have permission `security:role:view`  
**When** I navigate directly to the Roles URL  
**Then** the backend responds with 403 and a canonical error envelope including `correlationId`  
**And** the UI shows “Access denied”  
**And** no role data is displayed

## Scenario 3: Admin can create a role (roleName normalized uniqueness)
**Given** I am authenticated and have permission `security:role:create`  
**When** I create a role with roleName “Shop Manager” and description “Manages shop operations”  
**Then** the UI calls `POST /api/v1/security/roles` with that payload  
**And** on success I am navigated to Role Detail for the returned `roleId`  
**And** the roleName is displayed and is not editable

## Scenario 4: Duplicate role name is rejected using normalized uniqueness
**Given** I am authenticated and have permission `security:role:create`  
**And** a role exists with roleName “manager”  
**When** I attempt to create a role with roleName “  MANAGER  ”  
**Then** the backend responds 409 with `code=ROLE_NAME_TAKEN` and `correlationId`  
**And** the UI highlights the roleName field and shows “Role name already exists.”  
**And** my entered description remains visible

## Scenario 5: Admin can update role description but not roleName
**Given** I am authenticated and have permission `security:role:update`  
**And** a role exists with roleId R and roleName “ShopManager”  
**When** I open Role Edit for roleId R  
**Then** roleName is displayed as read-only/disabled  
**When** I change the description and save  
**Then** the UI calls `PUT /api/v1/security/roles/R` without sending roleName  
**And** the updated description is shown on Role Detail after reload

## Scenario 6: Admin can grant permissions to a role (idempotent)
**Given** I am authenticated and have permissions `security:permission:view` and `security:role_permission:grant`  
**And** a role exists with roleId R  
**And** the permission registry includes `security:role:view` and `security:role:update`  
**When** I open Manage Permissions for roleId R  
**And** I select `security:role:view` and `security:role:update` and save  
**Then** the UI calls the grant endpoint(s) for each added permissionKey  
**And** the UI reloads role grants from `GET /api/v1/security/roles/R/permissions`  
**And** Role Detail shows those permissions as granted after a page reload

## Scenario 7: Admin can revoke permissions from a role (idempotent)
**Given** I am authenticated and have permissions `security:permission:view` and `security:role_permission:revoke`  
**And** a role exists with roleId R that currently has permission `security:role:update` granted  
**When** I deselect `security:role:update` and save  
**Then** the UI calls the revoke endpoint for `security:role:update`  
**And** after reload the permission is no longer listed as granted

## Scenario 8: Canonical error envelope is surfaced with correlationId
**Given** I am authenticated and have permission to access a screen in this story  
**When** the backend returns any non-2xx response  
**Then** the UI reads `code`, `message`, and `correlationId` from the response  
**And** displays an error banner including the correlationId  
**And** maps any `fieldErrors[]` to inline field messages when present
