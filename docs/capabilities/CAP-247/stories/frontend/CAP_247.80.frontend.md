## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Catalog: View Product Details with Price and Availability Signals

### Primary Persona
Service Advisor

### Business Value
Enable a Service Advisor to quickly explain product options, price, and availability signals to customers for a selected location, while safely handling partial backend outages via explicit component “status” indicators and null-safe numeric rendering.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** a product detail view that shows master details plus location-scoped pricing and availability signals (with explicit component status)  
- **So that** I can confidently explain options and availability without stitching multiple calls or misrepresenting unknown data.

### In-scope
- Product detail screen that:
  - Loads `ProductDetailView` from a single aggregated backend endpoint owned by `positivity`. (DECISION-POSITIVITY-004)
  - Requires a selected `locationId` from app-level “location context” and always calls the endpoint with `location_id=<locationId>` query param. (DECISION-POSITIVITY-005)
  - Displays product master data, pricing (MSRP/store price/currency), availability (on-hand/ATP), lead time, and substitutions.
  - Treats `pricing.status` and `availability.status` as **opaque strings** and only special-cases `status == "OK"` vs non-OK. (DECISION-POSITIVITY-011)
  - Handles graceful degradation:
    - Catalog 404 is fail-fast (show not found). (DECISION-POSITIVITY-009)
    - Pricing/Inventory failures return `200` with non-OK status and **null numeric fields**; UI must not render null as 0. (DECISION-POSITIVITY-006)
  - Supports “Retry” for transient failures and degraded states.
  - Preserves `generatedAt` and component `asOf` for diagnostics; not shown by default, but accessible via an optional details view. (DECISION-POSITIVITY-007)
- Moqui screen routing and guards to mount a Vue component under a Moqui-hosted screen. (DECISION-POSITIVITY-004)

### Out-of-scope
- Checkout/cart/quote commit flows that require “price finalization”.
- Any edits to product data, pricing, or inventory (read-only UI).
- Direct frontend calls to Catalog/Pricing/Inventory services (must use aggregated endpoint only). (DECISION-POSITIVITY-004)
- Designing new permission models; this story wires to the required permission string and relies on server-side enforcement. (DECISION-POSITIVITY-013)

## 4. Preconditions & Dependencies
- User is authenticated in the POS frontend (Moqui session/auth).
- User has permission `positivity:product_detail:read`. (DECISION-POSITIVITY-013)
- User is authorized for the selected location (server-side enforced; deny by default). (DECISION-POSITIVITY-013)
- App-level “location context” exists and provides a selected `locationId` (UUID). Deep links may include `location_id`, but app state is the source of truth. (DECISION-POSITIVITY-005)
- Backend endpoint is available:
  - `GET /api/v1/products/{productId}?location_id={locationId}` (DECISION-POSITIVITY-004)
- Frontend HTTP client layer can forward W3C trace headers when present and capture `X-Correlation-Id` response header for logging. (DECISION-POSITIVITY-014)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From catalog search/browse results: “View details” navigates to product detail for the selected product.
- From substitutions list: selecting a substitute navigates to that product’s detail view (same screen, new `productId`).

### Screens to create/modify
- **Create** Moqui screen: `Catalog/ProductDetail`
  - Path param: `productId`
  - Optional query param: `location_id` (accepted for deep link, but the screen uses app location context as the primary source of truth; if query differs, app context wins). (DECISION-POSITIVITY-005)
  - Mounts a Vue component responsible for:
    - Reading `productId` from route
    - Reading `locationId` from global location context
    - Calling the aggregated endpoint and rendering the view (DECISION-POSITIVITY-004)
  - Enforces authentication via Moqui screen auth.
  - Enforces permission gate:
    - If a frontend capability/permission check exists, block navigation early; otherwise rely on backend `401/403` handling and show appropriate UI state. (DECISION-POSITIVITY-013)
- **Modify** existing catalog browse/search screen(s) to link to `Catalog/ProductDetail` (only if those screens exist in this repo; otherwise track separately).

### Navigation context
- Provide a “Back” action that returns to the prior catalog list/search without losing the current location context.
- Display the current location context (at least the location name/identifier) as the scope for pricing/availability.

### User workflows (happy + alternate paths)
**Happy path**
1. Service Advisor opens product detail from catalog list.
2. UI confirms a location is selected (from global location context).
3. UI loads `ProductDetailView` for `{productId, locationId}`.
4. UI renders:
   - description + specs
   - pricing section (status OK) with currency-aware formatting
   - availability section (status OK) with quantities and lead time (if present)
   - substitutions list (if any)

**Alternate paths**
- No location selected:
  - UI blocks the API call and prompts user to select a location; once selected, auto-load.
- Pricing non-OK:
  - UI shows “Price unavailable” and does not render numeric prices.
- Availability non-OK:
  - UI shows “Availability unknown” and does not render numeric quantities or “in stock/out of stock” claims.
- Product not found (404):
  - UI shows “Product not found” and provides a way back to catalog.
- Unauthorized/forbidden (401/403):
  - UI shows access error; no partial data is displayed.

## 6. Functional Behavior

### Triggers
- Screen load for `Catalog/ProductDetail` with `productId`.
- Location context change while on the product detail screen.
- User navigates to a substitution product from the substitutions list.

### UI actions
- On screen mount:
  - Validate `productId` is UUID-shaped.
  - If no selected `locationId`, show “Select a location to view pricing and availability” and do not call backend.
  - Otherwise call the backend endpoint and bind response to view state.
- On location change:
  - Re-fetch product detail for the same `productId` and new `locationId`.
  - Ensure “latest request wins” to prevent mismatched rendering.
- Provide “Retry” action for:
  - transient errors (network/5xx/timeouts)
  - degraded responses (optional; still `200`, but user may retry to recover)
- Provide an optional “Details” drawer/section (or equivalent) that reveals:
  - `generatedAt`
  - `pricing.asOf` and `availability.asOf` when present (DECISION-POSITIVITY-007)

### State changes (frontend)
- Local view state transitions:
  - `idle` → `needs_location` (if no location selected)
  - `idle|needs_location` → `loading` (when prerequisites satisfied and request starts)
  - `loading` → `loaded` (200)
  - `loading` → `error` (400/401/403/404/5xx/network)
  - `loaded` includes derived flags `pricingNonOk`, `availabilityNonOk` based on status gating

### Service interactions
- Single read interaction:
  - `GET /api/v1/products/{productId}?location_id={locationId}`
- No write operations.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `productId` must be present and UUID-shaped:
  - If invalid: do not call backend; show “Invalid product id” and provide navigation back.
- `locationId` must be present and UUID-shaped:
  - If missing: do not call backend; show “Select a location to view pricing and availability”.
  - If present but backend returns `400`: treat as invalid location selection and prompt to re-select. (DECISION-POSITIVITY-005)

### Enable/disable rules
- Read-only screen: no purchase/commit actions.
- Status gating:
  - Only treat `status === "OK"` as OK; any other string is non-OK. (DECISION-POSITIVITY-011)
  - If `pricing.status !== "OK"`:
    - Do not display numeric `msrp`/`storePrice` (they must be null when non-OK). (DECISION-POSITIVITY-006)
    - Do not format currency; show a non-numeric fallback (e.g., “Price unavailable”). (DECISION-POSITIVITY-012)
  - If `availability.status !== "OK"`:
    - Do not display numeric quantities (must be null when non-OK). (DECISION-POSITIVITY-006)
    - Do not label as “in stock/out of stock”; show “Availability unknown” (or equivalent).

### Visibility rules
- Pricing:
  - If `pricing.status === "OK"`:
    - `pricing.currency` must be present and non-empty; format money using locale-aware currency formatting with the provided ISO-4217 code. (DECISION-POSITIVITY-012)
  - Else:
    - Show pricing unavailable message; hide numeric fields.
- Availability:
  - If `availability.status === "OK"`:
    - Show `onHandQuantity` and `availableToPromiseQuantity` when present.
    - Show `leadTime` if present (UI renders returned object; does not compute precedence). (DECISION-POSITIVITY-010)
  - Else:
    - Show availability unknown message; hide numeric fields.
- Substitutions:
  - If empty: show “No substitutions available”.
  - If non-empty: list items; selecting navigates to that product’s detail.

### Error messaging expectations
- `404`: “Product not found” (no partial rendering). (DECISION-POSITIVITY-009)
- `400`: “Invalid location selected” (prompt to select a valid location). (DECISION-POSITIVITY-005)
- `401/403`: “You don’t have access” (no partial data). (DECISION-POSITIVITY-013)
- Network/`5xx`: “Unable to load product details right now” with Retry.

## 8. Data Requirements

### Entities involved (frontend view models)
- `ProductDetailView` (response DTO from backend; composed read model)
  - `productId`, `description`, `specifications[]`, `generatedAt`, `pricing{...}`, `availability{...}`, `substitutions[]`
- `PricingComponent` (nested)
- `AvailabilityComponent` (nested)
- `SubstituteHint` (nested)

### Fields (type, required, defaults)

**Route/Input**
- `productId`: string (UUID), **required**
- `locationId`: string (UUID), **required** (from app-level location context; query param may exist for deep link but does not override app context). (DECISION-POSITIVITY-005)

**Response: ProductDetailView (200)**
- `productId`: string, required
- `description`: string, required (may be empty string)
- `specifications`: array of `{ name: string, value: string }`, required (may be empty)
- `generatedAt`: ISO-8601 datetime string, required (composition time; preserved across caching). (DECISION-POSITIVITY-007)

**pricing**
- `pricing.status`: string, required (opaque; gate only on `"OK"`). (DECISION-POSITIVITY-011)
- `pricing.asOf`: ISO-8601 datetime string, optional
- `pricing.msrp`: decimal number, nullable
- `pricing.storePrice`: decimal number, nullable
- `pricing.currency`: string (ISO-4217), required when `pricing.status === "OK"`, otherwise null. (DECISION-POSITIVITY-012)
- Nullability invariant:
  - When `pricing.status !== "OK"`, numeric fields must be null (never 0). UI must treat null as “unknown/unavailable”. (DECISION-POSITIVITY-006)

**availability**
- `availability.status`: string, required (opaque; gate only on `"OK"`). (DECISION-POSITIVITY-011)
- `availability.asOf`: ISO-8601 datetime string, optional
- `availability.onHandQuantity`: integer, nullable
- `availability.availableToPromiseQuantity`: integer, nullable
- `availability.leadTime`: optional object:
  - `minDays`: integer, optional (non-negative when present)
  - `maxDays`: integer, optional (non-negative when present)
  - `asOf`: ISO-8601 datetime string, optional
  - (Other fields may exist; UI must be tolerant and only render known fields)
- Nullability invariant:
  - When `availability.status !== "OK"`, quantity fields must be null (never 0). (DECISION-POSITIVITY-006)

**substitutions**
- array of `{ productId: string, reason: string }`, required (may be empty)

### Read-only vs editable by state/role
- All fields are read-only in UI for this story.

### Derived/calculated fields
- `pricingNonOk = (pricing.status !== "OK")`
- `availabilityNonOk = (availability.status !== "OK")`
- `isDegraded = pricingNonOk || availabilityNonOk`
- Lead time display:
  - Render `availability.leadTime` if present; do not infer/merge with catalog hints (backend already applies precedence). (DECISION-POSITIVITY-010)

## 10. State Model & Transitions

### Allowed states (frontend screen state)
- `needs_location` (no selected location; blocked from calling backend)
- `loading`
- `loaded_ok` (pricing.status="OK" and availability.status="OK")
- `loaded_degraded_pricing` (pricing.status!="OK", availability.status="OK")
- `loaded_degraded_availability` (availability.status!="OK", pricing.status="OK")
- `loaded_degraded_both` (both != "OK")
- `error_invalid_params` (invalid productId format)
- `error_invalid_location` (400)
- `error_not_found` (404)
- `error_unauthorized` (401/403)
- `error_transient` (network/5xx)

### Role-based transitions
- Access requires:
  - Authenticated session
  - Permission `positivity:product_detail:read` (enforced server-side; optionally guarded client-side if capability check exists). (DECISION-POSITIVITY-013)

### UI behavior per state
- `needs_location`: show prompt to select location; no backend call.
- `loading`: show loading indicator; allow location change; ensure latest request wins.
- `loaded_*`: render master data; render pricing/availability sections according to status gating; show optional details drawer for timestamps.
- `error_*`: show error message and appropriate next action (retry, change location, back).

## 11. Alternate / Error Flows

### Validation failures
- Missing/invalid `productId`:
  - Do not call backend.
  - Show invalid parameter error with navigation back.
- Missing `locationId`:
  - Do not call backend.
  - Prompt user to select location; once selected, auto-load.

### Concurrency conflicts
- Rapid location changes:
  - Latest request wins (cancel/ignore older responses).
  - UI must not show mismatched location-scoped data.

### Unauthorized access
- `401`:
  - Follow Moqui app convention (redirect to login or show login-required state).
- `403`:
  - Show forbidden/access denied.
- In both cases:
  - Clear/hide previously loaded product detail data to avoid cross-user leakage.

### Empty states
- No specifications: show “No specifications provided”.
- No substitutions: show “No substitutions available”.

### Scenario 2: No location selected blocks request until location is chosen
**Given** I navigate to the product detail screen for product `<productId>`  
**And** no location is selected in the app location context  
**When** the screen renders  
**Then** the UI does not call the backend endpoint  
**And** the UI prompts me to select a location to view pricing and availability  
**When** I select a valid location `<locationId>`  
**Then** the UI requests `GET /api/v1/products/<productId>?location_id=<locationId>`.

### Scenario 3: Location change reloads price and availability and latest request wins
**Given** I am viewing product `<productId>` at location `<locationA>`  
**When** I change the selected location to `<locationB>`  
**Then** the UI requests `GET /api/v1/products/<productId>?location_id=<locationB>`  
**And** the UI ultimately renders data for `<locationB>` even if the `<locationA>` request returns after the `<locationB>` request.

### Scenario 4: Pricing non-OK shows explicit unavailable state and no numeric prices
**Given** the backend returns `200` for product `<productId>` and location `<locationId>`  
**And** the response contains `pricing.status="<nonOkStatus>"` where `<nonOkStatus>` is not `"OK"`  
**When** the UI renders the product detail  
**Then** the UI displays a “Price unavailable” indicator  
**And** the UI does not display numeric MSRP/store price values (does not render null as 0)  
**And** if `availability.status` is `"OK"` the UI still displays availability quantities.

### Scenario 5: Availability non-OK shows unknown state and no stock claims
**Given** the backend returns `200`  
**And** the response contains `availability.status="<nonOkStatus>"` where `<nonOkStatus>` is not `"OK"`  
**When** the UI renders the product detail  
**Then** the UI displays an “Availability unknown” indicator  
**And** the UI does not display on-hand or ATP numeric quantities  
**And** the UI does not label the product as “in stock” or “out of stock”.

### Scenario 6: Product not found is fail-fast
**Given** I navigate to product `<productId>` that does not exist in Catalog  
**When** the backend responds `404 Not Found`  
**Then** the UI displays “Product not found”  
**And** the UI does not display pricing or availability sections with stale/partial data  
**And** the UI provides a way to return to the catalog list/search.

### Scenario 7: Invalid location id returns 400 and prompts re-select
**Given** I have selected a location `<locationId>` that is invalid or not accepted by the backend  
**When** the UI requests `GET /api/v1/products/<productId>?location_id=<locationId>`  
**And** the backend responds `400 Bad Request`  
**Then** the UI displays an “Invalid location selected” error  
**And** the UI allows me to select a different location and retry.

### Scenario 8: Forbidden location access returns 403 with no partial data
**Given** I am authenticated and have permission `positivity:product_detail:read`  
**But** I am not authorized for location `<locationId>`  
**When** the UI requests `GET /api/v1/products/<productId>?location_id=<locationId>`  
**And** the backend responds `403 Forbidden`  
**Then** the UI displays an access denied message  
**And** the UI does not render any product detail payload from that response.
