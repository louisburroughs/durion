## Issue Body

## Title
[FRONTEND] [STORY] Audit: Ledger Traceability & Explainability Viewer (JE ↔ Ledger Lines ↔ Source Event ↔ Mapping/Rule Versions)

## Primary Persona
Financial Controller / Auditor

## Business Value
Enable audit, reconciliation, and compliance workflows by providing an internal, read-only, end-to-end traceability view from any posted Journal Entry or Ledger Line back to the originating business event and the accounting configuration versions (mapping/rules) used—without allowing any mutation of posted accounting records.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Financial Controller / Auditor  
- **I want** a read-only “Explainability” view that shows the chain **Source Event → Mapping Version → Rule Version → Journal Entry → Ledger Lines** (and reversal relationships)  
- **So that** I can explain how a financial posting was produced, prove immutability, and trace any GL impact back to its source business document/event.

## In-scope
- Moqui frontend screens to **search and view** posted Journal Entries and Ledger Lines with:
  - Traceability identifiers: `sourceEventId`, `sourceEventType`, `mappingVersionId`, `ruleVersionId`
  - Immutable `sourceEventSnapshot` (rendered read-only)
  - Reversal linkage via `originalJournalEntryId` and/or `reversalJournalEntryId` (if present)
- UI affordances that make immutability explicit (read-only forms, no edit/delete actions for POSTED records)
- Navigation/drilldown between:
  - JE detail → ledger lines list
  - JE detail → mapping version detail (read-only) **if backend supports**
  - JE detail → rule version detail (read-only) **if backend supports**
  - JE detail → referenced original JE (reversal chain)
  - Ledger line detail → parent JE
- Frontend handling of backend immutability errors (e.g., attempted mutation returns 409) by ensuring the UI does not present mutation actions.

## Out-of-scope
- Creating/reversing/posting Journal Entries (command operations)
- Public-facing explainability endpoint design (backend owns API shape)
- Defining GL account mappings, posting rules, or chart-of-accounts semantics
- Changing backend data model, enforcement, or audit event emission

# 4. Preconditions & Dependencies

## Backend data availability (required)
Backend must persist and serve (read-only) the following for Journal Entries and their posted lines:

### Journal Entry fields (minimum)
- `journalEntryId` (UUIDv7)
- `status` (backend enum; UI treats as authoritative)
- `postedTimestamp` (datetime; present when posted)
- `sourceEventId` (UUIDv7; expected for posted)
- `sourceEventType` (string; expected for posted)
- `mappingVersionId` (UUIDv7; expected for posted)
- `ruleVersionId` (UUIDv7; expected for posted)
- `originalJournalEntryId` (UUIDv7; nullable)
- `reversalJournalEntryId` (UUIDv7; nullable; if backend uses this direction)
- `sourceEventSnapshot` (JSON; expected for posted; may be redacted per backend policy)
- Optional audit fields: `createdAt`, `createdBy`, `updatedAt`, `updatedBy`

### Ledger line fields (minimum)
- `ledgerLineId` (UUIDv7) **or** `ledgerEntryId` (UUIDv7) (see “Naming” below)
- `journalEntryId` (UUIDv7)
- `glAccountId` and/or `glAccountCode` (backend-provided)
- `debitAmount`, `creditAmount` (decimal)
- `currencyUomId` (string)
- Optional: `postedTimestamp`, dimensions (dept/location/class/etc.) as provided

## Backend endpoints/services (required)
This story requires Accounting-owned read endpoints. Exact service names may differ, but the frontend must integrate to these capabilities:

- Journal Entry list/search (paged)
- Journal Entry detail by `journalEntryId`
- Posted lines list by `journalEntryId`
- Posted line detail by line id
- Mapping version detail by `mappingVersionId` (optional; if not supported, UI shows ID only)
- Rule version detail by `ruleVersionId` (optional; if not supported, UI shows ID only)

## Permissions (required)
Per Accounting domain permission gating model (**Decision AD-013**), screens must be protected by explicit permissions. For this story:

- View audit/traceability screens: **`accounting:events:view`**
- View raw source snapshot JSON (if backend provides an unredacted/raw view): **`accounting:events:view-payload`**

If the backend only provides a redacted/curated snapshot, `accounting:events:view` is sufficient to view it.

## Naming dependency (required)
Backend must confirm whether posted lines are exposed as `LedgerEntry` or `LedgerLine` in API responses. UI must not invent semantics; it should render whichever identifier and label the backend provides.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- All identifiers in this workflow are UUIDv7 (**Decision AD-006**). UI must validate UUID format client-side:
  - Search inputs: `journalEntryId`, `sourceEventId`, `mappingVersionId`, `ruleVersionId`, `ledgerLineId/ledgerEntryId`
  - Route params: `journalEntryId`, `ledgerLineId/ledgerEntryId`
- If invalid UUID:
  - Block submit (search) with inline error: `Invalid ID format`
  - For invalid route param: show “Invalid URL” / Not Found state and do not call backend

## Enable/disable rules
- This story is read-only:
  - No edit/delete/post/reverse actions are rendered for any status.
- Reversal navigation:
  - If `originalJournalEntryId` present: show “Reversal of {originalJournalEntryId}” and enable link
  - If `reversalJournalEntryId` present: show “Reversed by {reversalJournalEntryId}” and enable link
- Mapping/rule version navigation:
  - Enabled only if backend supports detail endpoints and returns 200
  - If 404 or capability absent: show ID only; disable link with explanation

## Visibility rules
- Always display traceability block for any JE:
  - `sourceEventId`, `sourceEventType`, `mappingVersionId`, `ruleVersionId`
- If any traceability field is missing/null:
  - Display as “Missing”
  - Show non-blocking warning banner: “Traceability data missing (unexpected for posted entries).”
  - Rationale: auditability expectation; UI must not invent values

## Error messaging expectations
- 401/403: show “Access denied” without revealing whether the ID exists (**Decision AD-013**)
- 404: show “Not found”
- 409: treat as unexpected for read-only; show “Conflict: record changed; please reload” (and offer reload)
- 5xx/timeouts: show retry affordance; preserve user inputs/filters

## Payload visibility policy
- Default: show curated/redacted snapshot/summary only (**Decision AD-009**)
- Raw JSON display:
  - Only if user has `accounting:events:view-payload`
  - Must be rendered safely (no HTML injection), must not be cached in local storage, and must not be logged

# 11. Alternate / Error Flows

## Validation failures
- Invalid UUID in search fields → inline error; no service call
- Invalid UUID in route param → invalid URL/not found state; no service call

## Concurrency conflicts
- If backend returns 409 on detail fetch (rare):
  - UI shows “Record changed; reload” and provides reload action
  - No merge behavior required (read-only)

## Unauthorized access
- 401/403 from any load call:
  - Show access denied message
  - Do not render partial sensitive content (especially snapshot)
  - Provide link back to Accounting home

## Empty states
- Search returns 0 results → “No journal entries found” + “Clear filters”
- JE exists but has 0 ledger lines → show “No ledger lines available” and allow user to copy JE ID for support/audit follow-up

## Missing linked resources
- Mapping/rule version detail 404:
  - Show IDs
  - Disable link with explanation
- Snapshot restricted:
  - Show “Restricted” placeholder or `payloadSummary` only

# 12. Acceptance Criteria

## Scenario 1: Search journal entries by source event id
**Given** I have `accounting:events:view` permission  
**And** I am on the Audit/Traceability Search screen  
**When** I enter a valid `sourceEventId` and submit the search  
**Then** the system displays a paged list of matching Journal Entries  
**And** each result shows `journalEntryId`, `status`, and `postedTimestamp` when available.

## Scenario 2: Prevent invalid ID input
**Given** I am on the Audit/Traceability Search screen  
**When** I enter an invalid UUID value into `journalEntryId`  
**And** I submit the search  
**Then** the UI blocks the request  
**And** shows an inline validation error indicating the ID format is invalid.

## Scenario 3: View JE explainability chain (including ledger lines)
**Given** I have `accounting:events:view` permission  
**And** I navigate to `/accounting/audit/journal-entry/{journalEntryId}` with a valid UUIDv7  
**When** the page loads successfully  
**Then** I can see `sourceEventId`, `sourceEventType`, `mappingVersionId`, and `ruleVersionId`  
**And** I can view the source snapshot as a read-only summary (`payloadSummary` or redacted snapshot)  
**And** I can view the list of ledger lines associated to the Journal Entry  
**And** I can open a ledger line to see its details.

## Scenario 4: Reversal traceability navigation
**Given** I have opened a Journal Entry detail page  
**And** the Journal Entry has `originalJournalEntryId` or `reversalJournalEntryId` populated  
**When** I click the displayed reversal link  
**Then** I am navigated to the linked Journal Entry detail page  
**And** the system loads and displays that Journal Entry’s traceability and ledger lines.

## Scenario 5: Missing mapping/rule version details
**Given** I am on a Journal Entry detail page  
**And** the backend does not provide a retrievable detail for `mappingVersionId` (404 or capability absent)  
**When** the page renders  
**Then** the UI still displays the `mappingVersionId` value  
**And** disables the drilldown link with an explanation “Mapping version details unavailable.”

## Scenario 6: Unauthorized access
**Given** I do not have `accounting:events:view` permission  
**When** I navigate to a Journal Entry detail URL with a valid UUIDv7  
**Then** the system shows an access denied state  
**And** does not display journal entry fields, ledger lines, or any snapshot content.

## Scenario 7: Raw snapshot visibility is permission-gated
**Given** I have `accounting:events:view` permission  
**And** I do not have `accounting:events:view-payload` permission  
**When** I open a Journal Entry detail page  
**Then** I do not see raw JSON payload content  
**And** I see only a curated/redacted summary or a “Restricted” placeholder.
