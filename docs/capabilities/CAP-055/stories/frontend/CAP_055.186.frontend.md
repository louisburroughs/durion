## 2. Story Intent

### As a / I want / So that
**As an** Accounting Admin or System Administrator,  
**I want** an Accounting Ingestion “Suspense/Quarantine Queue” UI to view rejected/quarantined accounting events, see actionable failure details and identifiers, and trigger an async retry,  
**so that** posting/ingestion failures can be resolved and re-run safely and idempotently with complete attempt/job traceability and posting references.

### In-scope
- Moqui screen flow to:
  - List ingestion records with filtering/sorting (default to problem statuses)
  - View ingestion record detail including identifiers, status, idempotency outcome, error details, and posting references
  - Trigger **async retry** for a single ingestion record with required justification
  - View retry job status and outcome (including updated ingestion record state)
- Strict permission gating:
  - view list/detail
  - view raw payload JSON (separate permission)
  - retry (separate permission)
- UI behavior for idempotency/conflict outcomes and authorization failures
- Display of backend-authoritative enums:
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`

### Out-of-scope
- Editing/correcting posting rules, GL mappings, chart of accounts, or tax policies in the UI
- Building/operating the ingestion pipeline, event broker consumer, or posting engine
- Bulk retry / batch operations (single-record retry only)
- Purge/retention job UI or configuration
- Any “suspense account” GL behavior (this is operational visibility only; no implied accounting treatment)

## 3. Actors & Stakeholders
- **Accounting Admin / Accounting Ops:** primary user; investigates failures, confirms external correction, triggers retry.
- **System Administrator:** investigates technical symptoms; triggers retry; broader access.
- **Auditor/Compliance reviewer:** reads records for traceability (view-only; no retry permission).
- **Accounting Ingestion/Posting Backend:** system of record for ingestion record status, idempotency outcomes, errors, and posting references.

## 4. Preconditions & Dependencies
- User is authenticated in the Moqui/Quasar frontend.
- Backend provides Accounting ingestion monitoring endpoints (authoritative):
  - `GET  /accounting/ingestion/list`
  - `GET  /accounting/ingestion/detail?ingestionId=...`
  - `POST /accounting/ingestion/retry` (async) → returns `jobId`
  - `GET  /accounting/ingestion/retryStatus?jobId=...` (or equivalent job status endpoint)
- Backend returns structured error responses `{ errorCode, message, details? }` and uses HTTP status codes (403, 404, 409, 422/400, 5xx).
- Permission tokens exist and are enforced server-side (UI must also gate entry points/actions):
  - View ingestion monitoring: `accounting:events:view`
  - View raw payload JSON: `accounting:events:view-payload`
  - Retry ingestion: `accounting:events:retry`
- Identifiers are UUIDv7 and must be validated client-side for UUID-only fields (Decision AD-006).
- Payload visibility policy applies (Decision AD-009): default to `payloadSummary`; raw JSON only with permission and must not be logged/cached.

### Navigation context

- From list row → detail screen
- From detail → back to list retaining query parameters (filters/sort/page)

### User workflows (happy + alternate paths)

#### Happy path: investigate quarantined record and retry successfully
1. User opens Event Ingestion list; default filter shows `processingStatus in (QUARANTINED, REJECTED)`
2. User opens a record
3. User reviews:
   - `processingStatus`, `idempotencyOutcome`
   - error code/message
   - identifiers (`eventId`, domain key like `invoiceId`/`paymentId`/`refundId` if present)
   - posting references (if any)
   - `payloadSummary` (and raw payload only if permitted)
4. User enters retry justification (>= 10 chars) and clicks **Retry**
5. UI shows job started (`jobId`) and polls status
6. On completion, UI refreshes ingestion detail; status becomes `PROCESSED` and `journalEntryId` appears if posting succeeded

#### Alternate path: retry results in still quarantined/rejected
- Job completes but ingestion remains `QUARANTINED` or `REJECTED`; UI shows updated error details and keeps Retry available (subject to backend eligibility).

#### Alternate path: duplicate conflict
- Record shows `idempotencyOutcome = DUPLICATE_CONFLICT` and `processingStatus = QUARANTINED`; UI displays a conflict banner and does not infer resolution. Retry may be allowed if backend supports; UI follows backend response.

#### Alternate path: unauthorized
- User without retry permission can view list/detail but cannot see Retry action; if attempted via direct call, backend 403 is shown without leaking additional info.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUID validation (Decision AD-006):
  - For filters/route params that are UUIDv7 (`ingestionId`, `eventId`, `invoiceId`, `paymentId`, `refundId`), block invalid UUID input with inline error and do not call backend.
- Retry justification (Decision AD-013):
  - Required; minimum length 10 characters; show inline validation error if not met.
- Date range validation:
  - `receivedAtThru >= receivedAtFrom` (inclusive); block invalid ranges client-side.

### Enable/disable rules
- Entry points:
  - Hide Accounting → Integrations → Event Ingestion menu item unless user has `accounting:events:view`.
- Retry button:
  - Visible only with `accounting:events:retry`.
  - Disabled while retry request is in-flight or while a retry job is in non-terminal state for the same ingestion record.
  - If backend returns 409 for “not retry-eligible”, disable and show backend message after refresh.

### Visibility rules
- Always visible (with view permission):
  - `processingStatus`, `idempotencyOutcome`, `receivedAt`, `eventType`, identifiers, error code/message, posting references.
- Payload:
  - Default show `payloadSummary` only.
  - Raw payload JSON:
    - Only visible with `accounting:events:view-payload`
    - Must be rendered safely (no HTML interpretation), and must not be persisted in client storage.

### Error messaging expectations
Map backend outcomes to user-visible messages (do not invent meanings beyond backend fields):
- `403`: “Access denied.”
- `404`: “Record not found.”
- `409`: “Retry not allowed for this record (already processed or not eligible).”
- `422/400`: “Retry request invalid: <backend message>” (include field-level details if provided)
- `5xx/timeout`: “System error while retrying; you can try again. If it persists, contact support with ingestionId and jobId (if any).”

## 10. State Model & Transitions

### Allowed states (backend-authoritative)
**Ingestion record**
- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`

**Retry job**
- Backend-owned; UI supports at minimum: `QUEUED` → `PROCESSING` → terminal (`READY/COMPLETED` or `FAILED`)

### Role-based transitions
- With `accounting:events:retry`, user may request retry for eligible records.
- Auditors (no retry permission) are view-only.

### UI behavior per state
- `PROCESSED`:
  - Show posting references (journalEntryId primary) if present
  - Retry action may be hidden/disabled; backend is final authority (handle 409)
- `REJECTED`:
  - Show error details; Retry available if permitted
- `QUARANTINED`:
  - Show quarantine/conflict banner; show error details and idempotency outcome; Retry available if permitted

## 11. Alternate / Error Flows

### Validation failures
- Invalid UUID in route (`/accounting/ingestion/{ingestionId}`):
  - Show “Invalid ID format” and do not call backend.
- Missing/short justification:
  - Inline error; do not call backend.

### Concurrency conflicts
- If two admins retry same ingestion record:
  - Backend may accept one and reject the other (409) or serialize; UI must:
    - show backend message
    - refresh detail after any retry completion/409

### Unauthorized access
- Without `accounting:events:view`:
  - No menu entry; direct navigation shows access denied (403 handling).
- Without `accounting:events:view-payload`:
  - Do not request raw payload; show “Restricted” placeholder.
- Without `accounting:events:retry`:
  - Hide retry panel entirely.

### Empty states
- List returns no records:
  - Show “No ingestion records found for current filters.” with “Clear filters”.
- Detail missing (404):
  - Show not found state with link back to list.

## 12. Acceptance Criteria

### Scenario 1: Default queue shows quarantined/rejected records
**Given** I am authenticated and have permission `accounting:events:view`  
**When** I open the Event Ingestion list screen  
**Then** the list loads using `receivedAt` as the date basis  
**And** the default filter includes `processingStatus` in `QUARANTINED, REJECTED`  
**And** each row shows `ingestionId`, `eventId`, `eventType`, `processingStatus`, `idempotencyOutcome`, and `receivedAt`.

### Scenario 2: Detail shows identifiers, errors, and posting references
**Given** an ingestion record exists  
**When** I open the ingestion record detail screen by `ingestionId`  
**Then** I can view `processingStatus`, `idempotencyOutcome`, `errorCode/errorMessage` (if present)  
**And** I can view `journalEntryId` (if present) as the primary posting reference and `ledgerTransactionId` as secondary (if present)  
**And** I can copy `ingestionId` and `eventId`.

### Scenario 3: Payload visibility is permission-gated
**Given** I have `accounting:events:view` but do not have `accounting:events:view-payload`  
**When** I view an ingestion record detail  
**Then** I can see `payloadSummary` if provided  
**And** I cannot see raw payload JSON and the UI does not fetch or render it.

### Scenario 4: Authorized retry starts async job and refreshes detail on completion
**Given** I have permission `accounting:events:retry`  
**And** an ingestion record is in `REJECTED` or `QUARANTINED`  
**When** I enter a justification of at least 10 characters and click Retry  
**Then** the UI calls `POST /accounting/ingestion/retry` with `ingestionId` and `justification`  
**And** the UI displays the returned `jobId` and polls retry status until terminal  
**And** when the job is terminal, the UI refreshes the ingestion record detail from the backend.

### Scenario 5: Retry request validation errors are shown inline
**Given** I have permission `accounting:events:retry`  
**When** I click Retry with an empty or too-short justification  
**Then** the UI shows an inline validation error and does not call the backend.

### Scenario 6: Backend denies retry (409) without duplicating postings
**Given** I have permission `accounting:events:retry`  
**And** an ingestion record is not retry-eligible (e.g., already processed)  
**When** I attempt to retry it  
**Then** the backend responds with `409 Conflict`  
**And** the UI shows a “Retry not allowed” message  
**And** the UI refreshes the ingestion record detail  
**And** the UI does not claim a new posting was created unless the refreshed detail shows new posting references.

### Scenario 7: Unauthorized user cannot retry
**Given** I do not have permission `accounting:events:retry`  
**When** I view an ingestion record detail  
**Then** I do not see the Retry panel  
**And** if I attempt the retry endpoint directly and receive `403 Forbidden`, the UI shows “Access denied” without leaking additional record information.
