## Story Intent
**As an** accountant (preparer) and a controller (approver), **I want** an Angular workflow to pick a bank account, import and correct a statement, match bank transactions to ledger lines, explain timing differences, post adjustments, submit and approve, and see bank-reconciliation readiness on the period-close page, **so that** the backend workflow of §4 is usable end to end with no client-side arithmetic and no policy inferred in the UI (§4.8, §5.9; DOMAIN_NOTES "policy inference creeps into UI").

## Scope
### In scope (all under `src/app/features/accounting/`)
- `pages/bank-accounts/` — list from `GET /v1/accounting/bank-accounts`; profile edit (`PUT …/{glAccountId}/profile`); "Start reconciliation" chooser with the four options of §4.1.
- `pages/bank-import/` — wizard: upload → mapping and sign-convention preview → row corrections → commit (§4.3, §4.4).

- `pages/period-close/period-close-page.component.{ts,html,css,spec.ts}` — readiness panel per period row and the exception dialog (§5.9); `services/period-close.service.ts`: `classifyPeriodActionError` learns `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (count of `unreconciledGlAccountIds` `fieldErrors`) and `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`, `closePeriod` gains the optional exception body, new `getCloseReadiness` / `getBankReconciliationPolicy` wrappers; `models/period-close.models.ts`: `PeriodActionFailure` gains the two kinds and a readiness model.

## Functional behaviour
EXISTING: `pages/period-close/` lists periods, closes by month and reopens with a justification in a native `dialog[appModalDialog]`; `PeriodCloseService` wraps `AccountingPeriodsService` (`listAccountingPeriods`, `closeAccountingPeriod`, `reopenAccountingPeriod`); `classifyPeriodActionError` maps `PERIOD_HAS_DRAFT_ENTRIES` (counting `fieldErrors[draftJournalEntryIds]`), `PERIOD_ALREADY_CLOSED`, `PERIOD_ALREADY_OPEN`, `PERIOD_NOT_FOUND` and 400 / 403 / 404; `canClose` / `canReopen` gate on `ACCOUNTING_SECTION.periodClose` / `periodReopen` with the unknown-`perm_bits` fallback; `refreshing` keeps rows visible with writes disabled during a re-read; `@durion-sdk/accounting` 0.73.0-alpha exposes `BankReconciliationService` (unused); `permission-catalog.ts` lists `accounting:reconciliation:adjust|view` and `accounting:period:*`.

PROPOSED:
1. **Bank accounts** (§4.1): rows show account code and name (never a raw UUID, ADR-0064), bank name and mask, currency, `coverageFrontier`, `reconciledFrontier`, unexplained-transaction and open-item counts. "Start reconciliation" offers (a) a COMMITTED statement with no active or `FINALIZED` reconciliation → `POST /reconciliations {glAccountId, requestId, statementId}`; (b) import a statement (wizard); (c) enter a statement by hand → `POST /bank-statements`; (d) interim reconciliation to a date → `POST /reconciliations` with `windowStartDate = reconciledFrontier + 1`, `windowEndDate`, keyed `openingBalance` / `closingBalance`.
2. **Import wizard** (§4.3, §4.4): step 1 file + header (`statement{startDate, endDate, openingBalance, closingBalance, statementRef}`, `formatCode = CSV`, `requestId` UUIDv7, optional `gapAcknowledgement`) → `POST /bank-imports`; `UPLOADED` with `mappingRequired` → step 2 mapping (`PUT /{importId}/mapping`, `saveAsAccountDefault`), where `signConvention` (`SIGNED_AMOUNT`, `SIGNED_AMOUNT_INVERTED`, `DEBIT_CREDIT_COLUMNS`) is chosen and the first five rows are shown with the resulting sign and the running total `opening + Σ` against `closing` — every figure from the response; step 3 rows grid (`GET /{importId}/rows?status=`, paginated by `rowNumber`) with correct (`PUT /{importId}/rows/{rowId}` `correctedValues`) or skip (`skip: true, reason`), rejection codes translated (`DATE_UNPARSEABLE`, `AMOUNT_UNPARSEABLE`, `AMOUNT_ZERO`, `AMOUNT_AND_DEBIT_CREDIT_BOTH`, `REQUIRED_COLUMN_MISSING`, `DATE_OUTSIDE_STATEMENT`), per-row or bulk `POSSIBLE_DUPLICATE` decisions; step 4 commit (`POST /{importId}/commit {startReconciliation, duplicateDecisions[]}`) then navigate to the workspace; discard (`POST /{importId}/discard {reason}`) from any step.
3. **Workspace** (§4.6, §4.7): left column unexplained bank transactions, right column unexplained ledger lines, both from the review model; selecting a bank row loads `GET /{id}/candidates?bankTransactionId=` ranked with score and reason codes (`EXACT_AMOUNT`, `WITHIN_TOLERANCE`, `DATE_IN_WINDOW`, `DATE_OUT_OF_WINDOW`, `REFERENCE_MATCH`, `DESCRIPTION_SIMILAR`) — precedent `pages/payables/vendor-invoices-exceptions/`; "Auto-match" → `POST /{id}/auto-match`, proposals listed with Accept / Accept all / Reject (`POST /{id}/matches/{matchId}/accept|reject`); "Match selected" → `POST /{id}/matches {bankTransactionIds[], glLineIds[], justification?, requestId}`, a 422 `MATCH_REQUIRES_REVIEW` opens a justification prompt listing the `fieldErrors[justification]` reasons; unmatch with reason; register an outstanding item (`itemKind` ∈ `DEPOSIT_IN_TRANSIT`, `OUTSTANDING_CHECK`, `OTHER_LEDGER_TIMING`, `BANK_ERROR_PENDING`, justification when required) and release; adjustment dialog (types from `GET /adjustment-types`; `amount`, `description`, `bankTransactionId`, `transactionDate` proposed as the first day of the earliest OPEN period after the bank date when that period is CLOSED, `overrideJustification` only for holders of `accounting:period:override`); duplicate review (`DISTINCT` / `DUPLICATE` with justification); exclude / restore; reverse adjustment.
4. **Review panel** (§4.8): renders every block from `GET /{id}/review` — header, each E3 term with its drill-down, `openingDifference` with the "an earlier window is wrong or stale" copy, unresolved lists, posted adjustments, evidence, `canSubmit` / `canApprove` with reasons (`NOT_BALANCED`, `UNEXPLAINED_BANK`, `UNEXPLAINED_LEDGER`, `OPENING_DIFFERENCE`, `PROPOSALS_PENDING`, `SELF_APPROVAL`), `ledgerChangedSinceApproval`; the stored trail from `GET /{id}/audit`. No client arithmetic.
5. **Lifecycle controls** (§4.9): submit (`adjust`); return, approve (`finalize`), cancel, supersede (`approve`), each with the justification prompt §4.9 requires; every mutation sends the current `version` and re-reads on 409 `OPTIMISTIC_LOCK`.
6. **Period-close readiness** (§5.9): each period row expands to `GET /periods/{periodCode}/close-readiness` — accounts with frontier dates, check badges by severity, links into the workspace; under `REQUIRED` the close button is disabled with the blocking reasons; under `REQUIRED_WITH_EXCEPTION` it opens the exception dialog (justification ≥ 10) only when the user holds both `accounting:period:close` and `accounting:period:override`; `closePeriod(periodCode, exception?)`; the policy comes from `GET /periods/bank-reconciliation-policy`.

## Business rules and invariants
- ADR-0031 §1: `state.set('error')` before `errorKey.set(...)` on every page and wizard step; ADR-0033 `onCleanup` on every effect subscription; ADR-0063 sequence-guarded reads (one counter per writer) and owed settlements drained by the current read, including its failure branch.
- ADR-0041: HTTP only through the regenerated `@durion-sdk/accounting` services injected into feature services; never `HttpClient`.
- ADR-0040 §6a: control and handler gate independently on the exact code — `adjust` for import, match, outstanding, adjust, submit; `approve` for approve, return, cancel, supersede, exclude, restore, reverse; `close` + `override` for the exception; a read permission never enables a write; unknown `perm_bits` falls back as `canClose` does today (§6.2).
- ADR-0064: account code and name beside ids; `COMMON.NOT_AVAILABLE` fallback; actionability gates on a per-source `'OK'` read status.
- ADR-0038: bare `YYYY-MM-DD` dates parsed with `parseDateLocal`; `today` is reactive.
- ADR-0065: statement descriptions and counterparty names render as text through the template, never `[innerHTML]`; no tenant data in browser storage (the saved mapping is server-side via `saveAsAccountDefault`).
- ADR-0029 §8: native `dialog[appModalDialog]` for every prompt; focus returned after each action; live regions for outcomes; a keyboard equivalent for row selection.
- ADR-0030: all copy via `| translate`; no `translate.instant()` in a `computed()` or effect; ADR-0032 typed fixtures; ADR-0034 `@serverGenerated` fields omitted from payloads.
- Domain: the client never decides matchability, sign, balance or readiness — every gate comes from the response (`canSubmit`, `canApprove`, `ready`, `mappingRequired`) (§4.8).

## State model
Pages: `idle → loading → ready | error` (ADR-0031). Wizard step follows the import `status`: `UPLOADED` → mapping, `VALIDATED` → rows and commit, `COMMITTED` / `DISCARDED` → read-only (§3.8). Workspace controls follow the reconciliation status: `IN_PROGRESS` editable; `SUBMITTED` approver actions only; `FINALIZED` / `INVALIDATED` supersede only; `SUPERSEDED` / `CANCELLED` read-only (§3.8).

## Alternate and error flows
- 422 `STATEMENT_NOT_CONTIGUOUS` with `fieldErrors[openingBalance]`: show the expected value; offer "correct the header" or "acknowledge with justification" (§4.2, pending D17).
- `IMPORT_NOT_COMMITTABLE`: rows named in `fieldErrors` are highlighted; the `activityTotal` message is shown verbatim; there is no override (E1).
- 409 `OPTIMISTIC_LOCK`, or `RECONCILIATION_NOT_BALANCED` after a concurrent posting: re-read the review; rows stay visible with writes disabled (`refreshing` pattern).
- 403 on a write names the write permission, not the view permission (existing period-close test precedent).
- Self-approval: the submitter sees approve disabled with reason `SELF_APPROVAL` from the review model; the server 403 is still classified (pending D3).
- Readiness read fails: the row shows a readiness-unavailable state; the close button stays enabled only under `ADVISORY` (gate on read status `'OK'`, ADR-0064).
- Returned-payment principal: a "request payment reversal" affordance instead of an adjustment; its target is not defined by the spec (pending D8).

## Acceptance criteria
1. **Given** a CSV whose headers differ from the defaults **When** uploaded **Then** the wizard lands on the mapping step with the raw columns and `mappingRequired`, and mapping re-parses to `VALIDATED`; `state` moves before any `errorKey` (§4.3, ADR-0031).
2. **Given** `DEBIT_CREDIT_COLUMNS` is chosen **Then** the five-row preview shows the response's signs and running total; the component performs no addition (§4.4, §8.4).
3. **Given** 3 of 240 rows are `REJECTED` **When** corrected in the row editor **Then** `rawValues` stay visible beside `correctedValues` and commit becomes available (§4.4).
4. **Given** a bank row is selected **Then** candidates render with score and reason codes; matching 1 bank : 2 ledger prompts for a justification and the accepted match appears in the evidence block (§4.6, M5).
5. **Given** the review model **Then** every E3 term (`statementClosingBalance`, outstanding ledger and bank sums, `adjustedBankBalance`, `glEndingBalance`, late adjustments, `adjustedBookBalance`, `difference`, `openingDifference`) renders from the response with drill-downs; a non-zero `openingDifference` fixture shows the earlier-window message (§4.8, §3.7).
6. **Given** a user with `adjust` only **Then** approve, return, cancel, supersede, exclude and reverse controls are disabled and their handlers refuse; **Given** `approve` only **Then** match and submit are disabled — asserted at control and method level, plus the unknown-`perm_bits` case (ADR-0040 §6a, §6.2).
7. **Given** a period row under `REQUIRED_WITH_EXCEPTION` with BLOCKING checks **When** expanded **Then** badges list the codes per account with frontier dates; the close button opens the exception dialog only for a user holding both `close` and `override`; a `close`-only user sees it disabled with the reasons (§5.9, §5.2).
8. **Given** a 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with two `unreconciledGlAccountIds` entries **Then** `classifyPeriodActionError` returns the count and the page reports it without re-reading; `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` names the override permission (§5.9).
9. **Given** the six bundles **Then** `npm run i18n:check` passes with every new key present and `qps-ploc` regenerated by `npm run i18n:pseudo:generate` (ADR-0030).
10. **Given** the new routes **Then** `npm run a11y:smoke` reports no serious violation and every prompt is a native `dialog[appModalDialog]` (ADR-0029 §8).
