## Story Intent
**As an** accountant (preparer) and a controller (approver), **I want** an Angular workflow to pick a bank account, import and correct a statement (acknowledging a gap when the statement does not continue the last one), match bank transactions to ledger lines, explain timing differences, post typed and linked adjustments — including a residual settlement, a gap bridge and a transfer — submit and approve, and see bank-reconciliation readiness on the period-close page, **so that** the backend workflow of §4 is usable end to end with no client-side arithmetic and no policy inferred in the UI (§4.8, §5.9; DOMAIN_NOTES "policy inference creeps into UI").

## Functional behaviour
EXISTING: `pages/period-close/` lists periods, closes by month and reopens with a justification in a native `dialog[appModalDialog]`; `PeriodCloseService` wraps `AccountingPeriodsService` (`listAccountingPeriods`, `closeAccountingPeriod`, `reopenAccountingPeriod`); `classifyPeriodActionError` maps `PERIOD_HAS_DRAFT_ENTRIES` (counting `fieldErrors[draftJournalEntryIds]`), `PERIOD_ALREADY_CLOSED`, `PERIOD_ALREADY_OPEN`, `PERIOD_NOT_FOUND` and 400 / 403 / 404; `canClose` / `canReopen` gate on `ACCOUNTING_SECTION.periodClose` / `periodReopen` with the unknown-`perm_bits` fallback; `refreshing` keeps rows visible with writes disabled during a re-read; `@durion-sdk/accounting` 0.73.0-alpha exposes `BankReconciliationService` (unused); `permission-catalog.ts` lists `accounting:reconciliation:adjust|view` and `accounting:period:*`.

PROPOSED:
1. **Bank accounts** (§4.1): rows show account code and name (never a raw UUID, ADR-0064), bank name and mask, currency, `reconciliationBaselineDate` (or `COMMON.NOT_AVAILABLE` before the first statement), `coverageFrontier`, `reconciledFrontier`, unexplained-transaction and open-item counts (from the baseline on, as served). "Start reconciliation" offers (a) a COMMITTED statement with no active or `FINALIZED` reconciliation → `POST /reconciliations {glAccountId, requestId, statementId}`; (b) import a statement (wizard); (c) enter a statement by hand → `POST /bank-statements` (with `gapAcknowledgement` when required); (d) interim reconciliation to a date → in phase 1 a manual-entry statement from `reconciledFrontier + 1` to the chosen date, the transactions and closing balance keyed from online banking, through the same `POST /bank-statements` form (§4.1 d, §5.7 b); a 422 `STATEMENT_TRANSACTION_OUT_OF_WINDOW` highlights the rows named in `fieldErrors[transactions[n]]`. Profile edit accepts only `USD`; 422 `CURRENCY_NOT_SUPPORTED` is classified (D18).
2. **Import wizard** (§4.2–§4.4): step 1 file + header (`statement{startDate, endDate, openingBalance, closingBalance, statementRef}`, `formatCode = CSV`, `requestId` UUIDv7, `gapAcknowledgement`) → `POST /bank-imports`; the acknowledgement field is offered only on a 422 `STATEMENT_NOT_CONTIGUOUS` (always the case for the account's first statement) with copy that acknowledging moves the account's reconciliation baseline to the statement's start (§3.1, D17); a 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE` removes the acknowledgement and says the statement continues the previous one (§4.2); `UPLOADED` with `mappingRequired` → step 2 mapping (`PUT /{importId}/mapping`, `saveAsAccountDefault`), where `signConvention` (`SIGNED_AMOUNT`, `SIGNED_AMOUNT_INVERTED`, `DEBIT_CREDIT_COLUMNS`) is chosen and the first five rows are shown with the resulting sign and the running total `opening + Σ` against `closing` — every figure from the response; step 3 rows grid (`GET /{importId}/rows?status=`, paginated by `rowNumber`) with correct (`PUT /{importId}/rows/{rowId}` `correctedValues`) or skip (`skip: true, reason`), rejection codes translated (`DATE_UNPARSEABLE`, `AMOUNT_UNPARSEABLE`, `AMOUNT_ZERO`, `AMOUNT_AND_DEBIT_CREDIT_BOTH`, `REQUIRED_COLUMN_MISSING`, `DATE_OUTSIDE_STATEMENT`), per-row or bulk `POSSIBLE_DUPLICATE` decisions; step 4 commit (`POST /{importId}/commit {startReconciliation, duplicateDecisions[]}`) then navigate to the workspace; discard (`POST /{importId}/discard {reason}`) from any step. **Replace a committed statement** (§4.9 path 3), offered in step 1 and on the manual-statement form under `accounting:reconciliation:adjust`: a picker lists the account's `COMMITTED` statements (`GET /bank-statements?glAccountId=`) and sets `supersedesStatementId`; `supersessionJustification` (≥ 10) is required; when the chosen statement's reconciliation links (`GET /bank-statements/{statementId}`) show a `FINALIZED` reconciliation, the control warns that the approval will be invalidated and a new approval is needed before the period can close; the result is shown from the response, with no client rule about eligibility.
3. **Workspace** (§4.6, §4.7): left column unexplained bank transactions (in phase 2, late arrivals first, D10), right column unexplained ledger lines, both from the review model; selecting a bank row loads `GET /{id}/candidates?bankTransactionId=` ranked with score and reason codes (`EXACT_AMOUNT`, `WITHIN_TOLERANCE`, `DATE_IN_WINDOW`, `DATE_OUT_OF_WINDOW`, `REFERENCE_MATCH`, `DESCRIPTION_SIMILAR`) — precedent `pages/payables/vendor-invoices-exceptions/`; "Auto-match" → `POST /{id}/auto-match`, proposals listed with Accept / Accept all / Reject (`POST /{id}/matches/{matchId}/accept|reject`, D12); "Match selected" → `POST /{id}/matches {bankTransactionIds[], glLineIds[], justification?, requestId}`, a 422 `MATCH_REQUIRES_REVIEW` opens a justification prompt listing the `fieldErrors[justification]` reasons; unmatch with reason; outstanding items: register (`itemKind` ∈ `DEPOSIT_IN_TRANSIT`, `OUTSTANDING_CHECK`, `OTHER_LEDGER_TIMING`, `BANK_ERROR_PENDING`, justification when required), release, **reaffirm** an aged `OTHER_LEDGER_TIMING` item listed as awaiting reaffirmation (`POST …/{itemId}/reaffirm {justification}`), **clear in gap** an earlier item in a reconciliation of an acknowledged statement (`POST …/{itemId}/clear-in-gap {justification}`); duplicate review (`DISTINCT` / `DUPLICATE` with justification), the served near-duplicate candidates (§4.5) offered as candidate originals; exclude / restore; reverse adjustment; for returned-payment principal no link (D8, §4.7): the row shows the bank transaction's reference and check number, and the preparer explains the debit with an `OTHER` adjustment linked to it, recording the original receipt's payment reference in the justification.
4. **Adjustment dialog** (§3.5, §4.2, §4.6, §4.7): types from `GET /adjustment-types` (`BANK_FEE`, `NSF_FEE`, `INTEREST_EARNED`, `OTHER`, `TRANSFER`); `amount` (omitted for a residual settlement or a gap bridge — the server computes it, §3.5), `description`, `requestId`, `transactionDate` proposed as the first day of the earliest OPEN period after the explaining date when that period is CLOSED (D7), `overrideJustification` only for holders of `accounting:period:override`. `OTHER` requires a justification (≥ 10) and exactly one link: a bank transaction (`bankTransactionId`); **settle residual** on an `ACCEPTED` match of the evidence list whose served `toleranceUsed ≠ 0` (`settlesMatchId`; the dialog shows the match's served signed `residual`, the amount the server will post, §3.4, §4.6); or **bridge the gap** when the review flags `OPENING_DIFFERENCE` on a statement carrying a gap acknowledgement (`bridgesStatementId`; the dialog shows the served `openingDifference`). The client performs no arithmetic and sends no `amount` for either. `TRANSFER` requires a `counterGlAccountId` picked from the other bank accounts of `GET /bank-accounts` and a positive (money in from that account) or negative (money out to it) amount; it is not subject to the `OTHER` threshold (D9, §3.5). Typed adjustments may link a bank transaction. The UI never compares an amount with the `OTHER` threshold: a 403 `RECONCILIATION_ADJUSTMENT_APPROVAL_REQUIRED` is classified and names the approve permission (§4.7).
5. **Review panel** (§4.8): renders every block from `GET /{id}/review` — header (incl. `baselineDate` and, when this statement set it, the gap acknowledgement text), each E3 term with its drill-down (`sumLateAdjustments` with the owning reconciliation), a separate **Diagnostics** block with `openingDifference`, its terms and the `OPENING_DIFFERENCE` flag with the likely cause (earlier window invalidated, or gap not yet bridged) — shown as information, never as a blocker — unresolved lists, posted adjustments, evidence (incl. each match's `bankTotal`, `ledgerTotal`, `toleranceUsed`, signed `residual` and `replacesMatchId`, last reaffirmation, "adjustments to clearing" with link, justification, poster and age), `canSubmit` / `canApprove` with reasons (`NOT_BALANCED`, `UNEXPLAINED_BANK`, `UNEXPLAINED_LEDGER`, `SELF_APPROVAL`; `PROPOSALS_PENDING` shown separately), `ledgerChangedSinceApproval`; the stored trail from `GET /{id}/audit`. No client arithmetic.
6. **Lifecycle controls** (§4.9): submit (`adjust`); return, approve (`finalize`), cancel, supersede (`approve`), each with the justification prompt §4.9 requires; every mutation sends the current `version` and re-reads on 409 `OPTIMISTIC_LOCK`; a 422 `RECONCILIATION_HAS_UNEXPLAINED_ITEMS` highlights the ids named in `fieldErrors` and shows both counts.
7. **Period-close readiness** (§5.3, §5.9): each period row expands to `GET /periods/{periodCode}/close-readiness` — accounts with `baselineDate` (the baseline applying at the period end) and frontier dates, check badges by severity, links into the workspace, and the tenant-wide top-level `checks[]` (e.g. `CLEARING_BALANCE_AGING` WARNING with both balances and the listed adjustments) in its own row; under `REQUIRED` the close button is disabled with the blocking reasons; under `REQUIRED_WITH_EXCEPTION` it opens the exception dialog (justification ≥ 10) only when the user holds both `accounting:period:close` and `accounting:period:override` (D4); `closePeriod(periodCode, exception?)`; the policy comes from `GET /periods/bank-reconciliation-policy`.

## Business rules and invariants
- ADR-0031 §1: `state.set('error')` before `errorKey.set(...)` on every page and wizard step; ADR-0033 `onCleanup` on every effect subscription; ADR-0063 sequence-guarded reads (one counter per writer) and owed settlements drained by the current read, including its failure branch.
- ADR-0041: HTTP only through the regenerated `@durion-sdk/accounting` services injected into feature services; never `HttpClient`.
- ADR-0040 §6a: control and handler gate independently on the exact code — `adjust` for import, match, outstanding register/release/reaffirm, adjust (incl. `OTHER`, residual, bridge, `TRANSFER`), submit; `approve` for approve, return, cancel, supersede, exclude, restore, reverse, clear in gap; `close` + `override` for the exception; a read permission never enables a write; unknown `perm_bits` falls back as `canClose` does today (§6.2).
- ADR-0064: account code and name beside ids; `COMMON.NOT_AVAILABLE` fallback; actionability gates on a per-source `'OK'` read status.
- ADR-0038: bare `YYYY-MM-DD` dates (incl. `reconciliationBaselineDate`, `baselineDate`) parsed with `parseDateLocal`; `today` is reactive.
- ADR-0065: statement descriptions, counterparty names, justifications and gap acknowledgements render as text through the template, never `[innerHTML]`; no tenant data in browser storage (the saved mapping is server-side via `saveAsAccountDefault`).
- ADR-0029 §8: native `dialog[appModalDialog]` for every prompt; focus returned after each action; live regions for outcomes; a keyboard equivalent for row selection.
- ADR-0030: all copy via `| translate`; no `translate.instant()` in a `computed()` or effect; ADR-0032 typed fixtures; ADR-0034 `@serverGenerated` fields omitted from payloads.
- Domain: the client never decides matchability, sign, balance, eligibility of a link, the `OTHER` threshold or readiness — every gate comes from the response (`canSubmit`, `canApprove`, `ready`, `mappingRequired`, the served amounts) (§4.8); link actions are offered from served fields (`toleranceUsed`, the `OPENING_DIFFERENCE` flag, the gap acknowledgement) and the server's refusal stays authoritative; `openingDifference` never disables submit or approve (D2).

## State model
Pages: `idle → loading → ready | error` (ADR-0031). Wizard step follows the import `status`: `UPLOADED` → mapping, `VALIDATED` → rows and commit, `COMMITTED` / `DISCARDED` → read-only (§3.8). Workspace controls follow the reconciliation status: `IN_PROGRESS` editable; `SUBMITTED` approver actions only; `FINALIZED` / `INVALIDATED` supersede only; `SUPERSEDED` / `CANCELLED` read-only (§3.8). Outstanding items show `OPEN`, `CLEARED`, `CLEARED_IN_GAP`, `VOIDED`, `RELEASED` with `closedOn` (§3.6).

## Alternate and error flows
- 422 `STATEMENT_NOT_CONTIGUOUS` with `fieldErrors[openingBalance]`: show the expected value; offer "correct the header" or "acknowledge with justification", stating that acknowledging moves the account baseline (§4.2, D17); for the account's first statement only the acknowledgement is offered.
- `IMPORT_NOT_COMMITTABLE`: rows named in `fieldErrors` are highlighted; the `activityTotal` message is shown verbatim; there is no override (E1).
- 409 `OPTIMISTIC_LOCK`, or `RECONCILIATION_NOT_BALANCED` after a concurrent posting: re-read the review; rows stay visible with writes disabled (`refreshing` pattern).
- 403 on a write names the write permission, not the view permission (existing period-close test precedent); `RECONCILIATION_ADJUSTMENT_APPROVAL_REQUIRED` names `approve`.
- Self-approval: the submitter sees approve disabled with reason `SELF_APPROVAL` from the review model; the server 403 is still classified (D3).
- `OPENING_DIFFERENCE` flagged on a statement without a gap acknowledgement: the likely-cause copy points at the invalidated predecessor; no bridge action is offered (§4.2, §4.8).
- Readiness read fails: the row shows a readiness-unavailable state; the close button stays enabled only under `ADVISORY` (gate on read status `'OK'`, ADR-0064).
- Returned-payment principal: no link and no returned-payment adjustment type; the reference and check number are shown and the linked `OTHER` escape is used (D8, §4.7).
- Replace a committed statement: 422 `STATEMENT_SUPERSESSION_NOT_ELIGIBLE` re-reads the statement list (the chosen one may meanwhile be superseded); 409 `RECONCILIATION_WINDOW_ALREADY_RECONCILED` links to the `IN_PROGRESS` or `SUBMITTED` reconciliation to finish or cancel first (§4.9 path 3).

## Acceptance criteria
1. **Given** a CSV whose headers differ from the defaults **When** uploaded **Then** the wizard lands on the mapping step with the raw columns and `mappingRequired`, and mapping re-parses to `VALIDATED`; `state` moves before any `errorKey` (§4.3, ADR-0031).
2. **Given** `DEBIT_CREDIT_COLUMNS` is chosen **Then** the five-row preview shows the response's signs and running total; the component performs no addition (§4.4, §8.4).
3. **Given** 3 of 240 rows are `REJECTED` **When** corrected in the row editor **Then** `rawValues` stay visible beside `correctedValues` and commit becomes available (§4.4).
4. **Given** an account's first statement uploaded without an acknowledgement **When** the 422 `STATEMENT_NOT_CONTIGUOUS` arrives **Then** the acknowledgement prompt (≥ 10 characters) is shown with the baseline copy; after commit the bank-accounts row shows `reconciliationBaselineDate` = the statement's start (§3.1, §4.2).
5. **Given** a bank row is selected **Then** candidates render with score and reason codes; matching 1 bank : 2 ledger prompts for a justification and the accepted match appears in the evidence block (§4.6, M5).
6. **Given** the review model **Then** every E3 term (`statementClosingBalance`, outstanding ledger and bank sums, `adjustedBankBalance`, `glEndingBalance`, `sumLateAdjustments`, `adjustedBookBalance`, `difference`) renders from the response with drill-downs; **Given** a non-zero `openingDifference` with `OPENING_DIFFERENCE` **Then** it renders only in the Diagnostics block with its terms and cause, and submit stays enabled when `canSubmit = true` (§4.8, §3.7, D2).
7. **Given** an `OTHER` adjustment dialog **Then** submit is disabled until exactly one link and a justification are given; "bridge the gap" and "settle residual" show the served `openingDifference` / `residual` and send no `amount` (asserted on the request); "settle residual" is offered only on `ACCEPTED` matches whose served `toleranceUsed ≠ 0`; a 422 `ADJUSTMENT_LINK_NOT_ELIGIBLE` re-reads the review; **Given** `TRANSFER` **Then** the counter picker lists the other bank accounts and excludes the reconciled one, and `GL_ACCOUNT_NOT_ACTIVE` / `ACCOUNT_NOT_RECONCILABLE` are classified (§3.4, §3.5, §4.2, §4.6, D9).
8. **Given** a user with `adjust` only **Then** approve, return, cancel, supersede, exclude, restore, reverse and clear-in-gap controls are disabled and their handlers refuse, while reaffirm and `OTHER` stay enabled; **Given** `approve` only **Then** match, reaffirm and submit are disabled — asserted at control and method level, plus the unknown-`perm_bits` case (ADR-0040 §6a, §6.2).
9. **Given** a period row under `REQUIRED_WITH_EXCEPTION` with BLOCKING checks **When** expanded **Then** badges list the codes per account with `baselineDate` and frontier dates, a tenant-wide `CLEARING_BALANCE_AGING` renders as a WARNING outside the account rows, and the close button opens the exception dialog only for a user holding both `close` and `override`; a `close`-only user sees it disabled with the reasons (§5.3, §5.9, §5.2).
10. **Given** a 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with two `unreconciledGlAccountIds` entries **Then** `classifyPeriodActionError` returns the count and the page reports it without re-reading; `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` names the override permission (§5.9).
11. **Given** the six bundles **Then** `npm run i18n:check` passes with every new key present and `qps-ploc` regenerated by `npm run i18n:pseudo:generate` (ADR-0030); **Given** the new routes **Then** `npm run a11y:smoke` reports no serious violation and every prompt is a native `dialog[appModalDialog]` (ADR-0029 §8).
