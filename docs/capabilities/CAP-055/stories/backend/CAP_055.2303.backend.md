## Story Intent
**As a** preparer (holder of `accounting:reconciliation:adjust`) **I want** to start a reconciliation from a committed statement or as an interim window, see the live equation E3 on one review screen, match bank transactions to posted ledger lines (1:1, 1:N, N:1) from deterministic ranked candidates, register non-posting outstanding items for timing differences, post typed adjustments idempotently on the right date and reverse them explicitly **so that** a window with genuine timing differences finalizes with zero journal entries, every judgement is recorded with its reasons, and no balance is ever computed from a stale snapshot.

## Functional behaviour
1. EXISTING kept — `GET /adjustment-types` (served enum `BANK_FEE, NSF_FEE, INTEREST_EARNED, OTHER`; `TRANSFER` pending D9), `GET` list, `GET /{id}`, `POST /{id}/finalize` (balance-only gate, unchanged permission — S5 changes it), `GET /{id}/report`, `GET /{id}/audit` (derived — S5 stores it); the debit/credit rule of adjustments (positive → Dr reconciled cash / Cr counter; negative → Dr counter / Cr reconciled cash; counter via `GLMappingResolver.resolveGLAccount("BANK_RECONCILIATION", type.name(), transactionDate)`; `BankAdjustmentType.permits(signum)`; **no new mapping**, §3.5); `MATCH_AMOUNT_MISMATCH` ±0.01 (M1); `RECONCILIATION_LINE_INELIGIBLE` for a ledger line in an active match. EXISTING replaced — `POST /{id}/match` → `POST /{id}/matches`; `POST /{id}/unmatch` → `POST /{id}/matches/{matchId}/unmatch` (§6.1); the `@EmitEvent` ids `ACCOUNTING_RECONCILIATION_MATCH` / `_UNMATCH` are kept on the new paths.
2. PROPOSED — create: from a COMMITTED statement (`statementId`, window and balances copied; `RECONCILIATION_WINDOW_ALREADY_RECONCILED` if an `IN_PROGRESS`/`SUBMITTED` reconciliation exists for it — S1 partial unique — or a `FINALIZED` one without a successor — service rule, §6.4 as amended; the correction path is supersede, S5) or interim (`windowStartDate` = `reconciledFrontier + 1` unless the account has no chain, `windowEndDate`, keyed `openingBalance`/`closingBalance`, provenance `MANUAL_ENTRY`, `statementId` null; E2-style contiguity against the previous window). `accountingPeriodCode` is attribution only, never a constraint on the window (§5.7). Non-posting operations are allowed whatever the period state (§5.1).
3. PROPOSED — E3 on every read and mutation, with the F2 sign conventions (bank `signedAmount` positive = cash in; ledger `signedAmount` = debit − credit): `adjustedBankBalance = statementClosingBalance + Σ OPEN ledger-side items − Σ OPEN bank-side items`; `adjustedBookBalance = glEndingBalance(live, POSTED, transactionDate ≤ statementEndDate 23:59:59.999999 via getAccountBalanceAsOf) + Σ this reconciliation's adjustments with transactionDate > statementEndDate`; `difference = adjustedBankBalance − adjustedBookBalance`; `glOpeningBalance` as-of `statementStartDate − 1`; `sumUnexplainedBank` = Σ `UNMATCHED` + `POSSIBLE_DUPLICATE` rows on the account dated ≤ `statementEndDate` (including carried-in ones); `sumUnexplainedLedger` = Σ POSTED lines on the account dated ≤ `statementEndDate` in no active match and no `OPEN` item; `openingDifference` per §3.7. `Σ matched` stays out (C5).
4. PROPOSED — candidates for a `bankTransactionId` (or the mirror for a `glLineId`): POSTED lines on the account, in no active match and no `OPEN` item, dated within `[transactionDate − W, transactionDate + W]`, scored `EXACT_AMOUNT` +60, `WITHIN_TOLERANCE` +40, `DATE_IN_WINDOW` +20 × (1 − d/W), `REFERENCE_MATCH` +20 (`checkNumber` or `reference` equals a JE/line description token), `DESCRIPTION_SIMILAR` up to +10 (Jaccard over `normalizedDescription` tokens ≥ 0.5); `windowDays` widens explicitly and marks `DATE_OUT_OF_WINDOW`. Deterministic, no model.
5. PROPOSED — `auto-match`: for every unexplained bank transaction whose top candidate scores ≥ 90 and beats the second by ≥ 20, create a `ONE_TO_ONE` match `origin = RULE`, `state = PROPOSED`; ties propose nothing and are reported as `ambiguousCount`. The system never creates an `ACCEPTED` match (M6, pending D12).
6. PROPOSED — human match `POST /{id}/matches` `{bankTransactionIds[], glLineIds[], justification?, requestId}`: `matchKind` from cardinality (`ONE_TO_ONE`, `ONE_TO_MANY` = 1 bank : N ledger, `MANY_TO_ONE` = N bank : 1 ledger; N:M → `MATCH_CARDINALITY_NOT_ALLOWED`); M1 (else `MATCH_AMOUNT_MISMATCH`); M3/M4 eligibility (else `RECONCILIATION_LINE_INELIGIBLE`; a `PENDING` row is never matchable, D19); M5 reasons → `MATCH_REQUIRES_REVIEW` with `fieldErrors[justification]` listing them until a justification (≥ 10, pending D15) is supplied; created `ACCEPTED` (`origin = USER`), members `active = true`, bank rows `MATCHED`; any `OPEN` ledger-side outstanding item whose line is now matched → `CLEARED` (`clearedInReconciliationId`, `clearedByMatchId`, `clearedAt`) in the same transaction (§5.4). `accept` / `reject` act on `PROPOSED`; `unmatch` `{reason}` on `ACCEPTED` → `UNMATCHED`, members `active = false`, bank rows `UNMATCHED`, audit `RECONCILIATION_UNMATCH` (G3). Only while the reconciliation is `IN_PROGRESS` (or `SUBMITTED`, S5); `FINALIZED` → `RECONCILIATION_ALREADY_FINALIZED`.
7. PROPOSED — outstanding items: `LEDGER` side (`DEPOSIT_IN_TRANSIT` requires `signedAmount > 0`, `OUTSTANDING_CHECK` `< 0`, `OTHER_LEDGER_TIMING`) on a POSTED line on the account dated ≤ window end, in no active match and no `OPEN` item; `BANK` side `BANK_ERROR_PENDING` on a bank transaction; violations → `OUTSTANDING_ITEM_NOT_ELIGIBLE`; justification required for `OTHER_LEDGER_TIMING`, `BANK_ERROR_PENDING` and any item older than `aging-warning-days`; `signedAmount`/`itemDate` copied from the source; `release` `{reason}` → `RELEASED` only while the registering reconciliation is not `FINALIZED`. An `OPEN` item is carried into every later reconciliation's E3 automatically (O2). Nothing posts (O3, C2).
8. PROPOSED — adjustments `POST /{id}/adjustments` `{type, amount, description, requestId, bankTransactionId?, transactionDate?, overrideJustification?}`: date rule (pending D7) — default the explaining bank transaction's date when its period is OPEN and not hard-locked, else the request `transactionDate` (must be in an OPEN period); a CLOSED date → `PERIOD_CLOSED` unless `overrideJustification` and the caller holds `accounting:period:override` (gate order hard lock > closed > override; `PERIOD_HARD_LOCKED` never overridable); `sourceEventId = nameUUIDFromBytes("BANK_RECONCILIATION_ADJUSTMENT:" + adjustmentId)`, `IdempotencyService` key `BANK_RECONCILIATION_ADJUSTMENT:<adjustmentId>` registered with the `journalEntryId`; replay of the same `requestId` → 200 `replayed: true`, one JE (G9); `transactionDate` and `postedPeriodCode` stored, `status = POSTED`; when `bankTransactionId` is given, the JE's cash line is matched to it as an `ADJUSTMENT` match (`ACCEPTED`, `origin = USER`) in the same transaction; an adjustment dated after `statementEndDate` enters `sumLateAdjustments`.
9. PROPOSED — reverse `POST /{id}/adjustments/{adjustmentId}/reverse` `{reason, reversalDate?, overrideJustification?}` (`accounting:reconciliation:approve`, §6.1): `JournalEntryService.reverseJournalEntry` (period gate on the reversal date; `JE_NOT_POSTED` / `JE_ALREADY_REVERSED` 409 EXISTING; `ADJUSTMENT_ALREADY_REVERSED` 409); the `ADJUSTMENT` match → `UNMATCHED`, the bank transaction → `UNMATCHED`; adjustment `status = REVERSED`, `reversalJournalEntryId`, `reversedAt/By`, `reversalReason`. On a `FINALIZED` owner this story answers `RECONCILIATION_ALREADY_FINALIZED`; S5 replaces that with `INVALIDATED` (§4.9 path 2, §5.5).
10. PROPOSED — `GET /{id}/review` returns the §4.8 blocks in one call, no client arithmetic: header (account code and name, window, provenance, status, preparer, period code and its state, `version`); every E3 term with drill-down lists and ages; unresolved (unexplained bank with top candidate and score, unexplained ledger with top bank candidate, `POSSIBLE_DUPLICATE` rows, `PROPOSED` matches, `BROKEN` matches — empty until S5); posted adjustments with `journalEntryId`, `entryNumber`, date, period, override flag, reversal state (drafted adjustments are not stored); evidence (matches with members/kind/score/reasons/justification/actor, items, exclusions, statement header and file hash); readiness `canSubmit`/`canApprove` with reasons `NOT_BALANCED`, `UNEXPLAINED_BANK`, `UNEXPLAINED_LEDGER`, `OPENING_DIFFERENCE`, `PROPOSALS_PENDING` (`SELF_APPROVAL` arrives with S5). `GET /{id}/report` adds the E3 terms, matched/outstanding/unexplained splits, adjustments including the `OTHER`-to-clearing list, aging.

## Business rules and invariants
- **E3** as in behaviour 3 (§3.7); the tolerance ±0.01 compares at 2 dp; amounts at 4 dp (§8.1).
- **M1** Σ bank − Σ ledger within ±0.01, a larger residual is an adjustment, not a match; **M2** exactly one side may have more than one member; **M3** every ledger member POSTED, on the account, dated ≤ `statementEndDate`; **M4** every bank member `UNMATCHED` or reviewed-distinct, `settlementState = POSTED`, dated inside the window or carried in; **M5** justification when `matchKind ≠ ONE_TO_ONE`, `toleranceUsed ≠ 0`, any date outside the window, or a member was a `POSSIBLE_DUPLICATE`; **M6** a `RULE` match is never `ACCEPTED` by the system; **M7** matches are never deleted (§3.4).
- **O1** a ledger line is in at most one `OPEN` item and never simultaneously in an active match (S1 partial uniques + service check); **O2** an `OPEN` item contributes to every later reconciliation on the account; **O3** registering an item posts nothing — `FLOAT_ADJUSTMENT` stays banned (§3.6, C2).
- A match and an outstanding item change no balance; an adjustment is the only artefact that posts (§3.9). `Σ matched` is excluded from the identity (C5).
- Adjustment date: the period governing an adjustment is the one containing the JE's `transactionDate`, not the window's (§5, C3, pending D7); every posting still goes through `AccountingPeriodGate` (§5.9).
- Idempotency: every command carries a UUIDv7 `requestId`; same payload → `replayed: true`, different → `IDEMPOTENCY_CONFLICT` (§6.3, AD-010).
- Justification minimum 10 characters (pending D15); actor from `SecurityContextHelper` (ADR-0018).

## State model
- `ReconciliationMatch` (§3.4, §3.8): `PROPOSED → ACCEPTED | REJECTED`; `ACCEPTED → UNMATCHED` (human, reason). `→ BROKEN` and sealing at `FINALIZED` are S5.
- `OutstandingItem` (§3.6): `OPEN → CLEARED` (later match, same transaction) | `RELEASED` (human undo, registering reconciliation not `FINALIZED`). `→ VOIDED` is S5.
- `ReconciliationAdjustment` (§3.8): `POSTED → REVERSED` through `reverseJournalEntry`; the `ADJUSTMENT` match `→ UNMATCHED` and the bank transaction `→ UNMATCHED` in the same transaction.
- `BankTransaction`: `UNMATCHED ↔ MATCHED` (match accepted / unmatched).
- `Reconciliation`: created `IN_PROGRESS`; `IN_PROGRESS → FINALIZED` stays the EXISTING transition; `SUBMITTED`, `CANCELLED`, `INVALIDATED`, `SUPERSEDED` — S5.

## Alternate and error flows
- Bank credit 1,250.00 on 09-12 against ledger debits 1,000.00 (09-11) and 250.00 (09-12) matched 1:2 → `ONE_TO_MANY`, justification required, then `ACCEPTED`, all three `MATCHED` (§4.6).
- Bank 99.99 vs ledger 100.00 → `toleranceUsed = 0.01`, justification required; bank 99.50 → `MATCH_AMOUNT_MISMATCH` (§4.6).
- Ledger line dated 10-02 against a window ending 09-30 → `MATCH_REQUIRES_REVIEW` with `DATE_OUT_OF_WINDOW`; with justification allowed and flagged (§4.6, M3).
- Ledger line already in an active match in another reconciliation → 409 `RECONCILIATION_LINE_INELIGIBLE`; `PENDING` bank row → same (D19).
- Outstanding item on a matched line, or `OUTSTANDING_CHECK` on a positive line → `OUTSTANDING_ITEM_NOT_ELIGIBLE` (§8.3).
- Adjustment for a bank date in a CLOSED period without override → `PERIOD_CLOSED` when the request date is closed, success when it is open; hard-locked bank date with `overrideJustification` → `PERIOD_HARD_LOCKED` (§8.3).
- Same adjustment `requestId` twice → one JE, second response `replayed: true`; same `requestId` with a different amount → `IDEMPOTENCY_CONFLICT`.
- Reverse twice → `ADJUSTMENT_ALREADY_REVERSED`; reverse on a `FINALIZED` owner → `RECONCILIATION_ALREADY_FINALIZED` until S5.
- Previous window `INVALIDATED` (S5) or its statement missing → `openingDifference ≠ 0`, reported on the review screen, never "fixed" here (§3.7).
- A JE dated inside the window posted after creation → the next read shows a new unexplained ledger line and a moved `difference` (fixes G4).

## Acceptance criteria
1. **Given** no outstanding items **When** the review is read **Then** `glEndingBalance` equals `getAccountBalanceAsOf(statementEndDate 23:59:59.999999)`; a JE dated `statementEndDate` 23:30 is inside, one dated the next day 00:00 is outside (E3, §8.1).
2. **Given** a deposit in transit +500 and an outstanding check −200 registered **When** the review is read **Then** `adjustedBankBalance = statementClosingBalance + 300` and `difference = 0` when the ledger holds both lines [M] — mutate the sign of the bank-side term (E3, §8.1).
3. **Given** a bank fee for a CLOSED month posted in the open month with `bankTransactionId` **When** both windows are read **Then** it is added exactly once to the closed window's `adjustedBookBalance` as a late adjustment and is not double-counted in the next window [M] (§8.1, C3, pending D7).
4. **Given** Dr cash 100 posted then reversed **When** `getAccountBalanceAsOf` is read **Then** it returns 0 — pinned before any E3 test is trusted; if it returns −100 the query or its documentation is corrected first (G15, §8.1).
5. **Given** a 1:1 exact match **When** created **Then** `ACCEPTED` without justification; **Given** 1:N or N:1 **Then** `MATCH_REQUIRES_REVIEW` until justified; **Given** N:M **Then** `MATCH_CARDINALITY_NOT_ALLOWED` [M] (§8.3, M2, M5).
6. **Given** the candidate fixture (amounts, dates, references) **When** candidates are ranked **Then** the documented scores and reason codes are returned in a deterministic order; a tie proposes nothing under `auto-match` (§4.6, §8.3).
7. **Given** any fixture **When** `auto-match` runs **Then** no match with `state = ACCEPTED` and `origin = RULE` exists [M] (M6, §8.3, pending D12).
8. **Given** an `ACCEPTED` match **When** unmatched with a reason **Then** the header remains with `state = UNMATCHED`, an `AccountingAuditLog` row `RECONCILIATION_UNMATCH` carries actor and reason, and the ledger line can be matched again (M7, U4, §8.3).
9. **Given** the same adjustment `requestId` twice **When** posted **Then** one JE exists, the second answer is `replayed: true`, and `findBySourceEvent(nameUUIDFromBytes("BANK_RECONCILIATION_ADJUSTMENT:" + adjustmentId))` finds it [M] — mutate to a random id and the replay test fails (§3.5, §8.3, G9).
10. **Given** an `OPEN` deposit-in-transit item **When** its ledger line is matched in a later reconciliation **Then** the item is `CLEARED` in the same transaction with `clearedByMatchId`; **Given** its JE is reversed **Then** it is `VOIDED` (S5 hook — asserted there) (§5.4, §8.3).
11. **Given** an adjustment with `bankTransactionId` **When** posted **Then** an `ADJUSTMENT` match links the JE's cash line and the bank row is `MATCHED`; **When** reversed **Then** the match is `UNMATCHED` and the bank row `UNMATCHED` (§3.5, §4.7, §8.3).
