## Story Intent
**As a** preparer (holder of `accounting:reconciliation:adjust`) **I want** bank statements and their transactions to enter accounting through one provider-neutral contract — normalized, fingerprinted, upserted by source id, flagged as possible duplicates instead of dropped — to enter a statement by hand when no file exists, and to commit a statement that does not continue the previous one (the account's first, a date gap or a bank change) only with a justified gap acknowledgement that moves the account's reconciliation baseline **so that** every bank line is retained as evidence exactly as the bank delivered it, no duplicate is ever silently discarded, years of pre-baseline ledger history never block a reconciliation, and the reconciliation core never learns a file format or a provider.

## Functional behaviour
1. EXISTING kept — the F2 `/v1/accounting/reconciliations` endpoints stay as S1 left them; `POST /import` still writes through the S1 persistence (its retirement is S3, D14).
2. PROPOSED — contract: `BankTransactionsObservedV1` carries `sourceKind` (`FILE_IMPORT`/`MANUAL_ENTRY`/`BANK_FEED`), `connectorCode` (label only, never behavioural), `feedConnectionId`, `feedAccountId` (UUID — the connector's feed-account aggregate and the envelope `aggregateId`; null for files and manual entry, whose aggregate is the `importId` / `statementId`), `feedAccountRef` (the provider's account reference, payload only, null for files), `currency`, `observedAt`, `cursorRef` (opaque), optional `statement{statementRef, startDate, endDate, openingBalance, closingBalance}`, `transactions[]` per §2.2 (`signedAmount` positive = money into the account; external ids `String` per ADR-0027). Envelope per ADR-0044 §3 with required `tenantId`. No class in the package references a provider.
3. PROPOSED — `accept` runs in one transaction: (a) resolve the GL account from `ctx.glAccountId` (files/manual; feeds resolve through `bank_account_profile` in phase 2), require `reconcilable` and subtype `BANK_CASH` (D5) else `ACCOUNT_NOT_RECONCILABLE`; (b) a currency the batch carries equals the profile currency — `USD` while no profile exists — else `CURRENCY_NOT_SUPPORTED` (D18, §3.1); (c) if a `statement` block is present: `startDate ≤ endDate`, `endDate` not in the future, U1 (`STATEMENT_ALREADY_IMPORTED`), U2 (`STATEMENT_PERIOD_OVERLAP` with `fieldErrors[statementId]`), E2 against the previous COMMITTED statement — `openingBalance` = its `closingBalance` and `startDate` = its `endDate + 1`; `gapAcknowledgement` checked in order (§4.2): a present value is first validated as a justification (blank → 400 `VALIDATION_ERROR`, 1–9 characters → 400 `JUSTIFICATION_REQUIRED`, D15); absent on a statement that does not continue (the account's first COMMITTED statement, a date gap, or an opening balance that differs from the previous closing balance) → `STATEMENT_NOT_CONTIGUOUS` (with `fieldErrors[openingBalance] = "expected <value>"` when a previous statement exists); present on a statement that does continue → `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE` (never ignored, never accepted — the baseline does not move, D17); for a manual statement every transaction dated inside the header window, else `STATEMENT_TRANSACTION_OUT_OF_WINDOW` with `fieldErrors[transactions[n]]` (§4.3); (d) for each transaction: normalize, then source-id layer — same `(glAccountId, sourceKind, sourceRef, sourceTransactionId)` → update the retained fields, `feedChange = MODIFIED`, advance `lastObservedAt`, never a second row (U3); else fingerprint layer — a collision with an existing row on the account (never an `EXCLUDED` or `REMOVED_BY_SOURCE` one, §4.5) or another row of the batch → `POSSIBLE_DUPLICATE` with `duplicateOfBankTransactionId` pointing at the earlier row (R1), else `UNMATCHED`; `settlementState` stored as delivered (`PENDING` visible, never matchable — D19, enforced in S4); (e) E1: `openingBalance + Σ signedAmount = closingBalance` within ±0.01 else `STATEMENT_ACTIVITY_MISMATCH`; (f) persist the `bank_statement` as `COMMITTED` with `activityTotal` and, when acknowledged, `gapAcknowledgement`, `gapAcknowledgedBy` (the committing actor) and `gapAcknowledgedAt`; link every row by `statementId`; (g) baseline (behaviour 4); (h) set `arrivedAfterApproval = true` on any row dated inside a `FINALIZED` reconciliation window on the account (D10) — reachable only by phase-2 feed batches: a phase-1 file or manual row lies inside its own statement window and windows never overlap (U2, §5.5); (i) return counts (`bankTransactionCount`, `possibleDuplicateCount`, `modifiedCount`).
4. PROPOSED — reconciliation baseline (§3.1, §4.2 step 1, D2, D17): the intake creates the account's `bank_account_profile` row in the commit transaction when it is absent — `bank_name` and `account_mask` null, `currency = USD`, `default_column_mapping` = the import's mapping when `saveAsAccountDefault` was set (S3) else null, `statement_cycle_hint` and the feed columns null (§3.1). When the committed statement carries a `gapAcknowledgement`, the intake sets `reconciliation_baseline_date` to the `startDate` of the latest-starting COMMITTED statement on the account that carries a `gapAcknowledgement` (the partial index on `bank_statement` serves the lookup). The account's first statement always carries one, so every reconciled account has a baseline. When a statement is superseded (§4.9 path 3, driven by S5), the intake recomputes the value from the remaining COMMITTED statements; the value is written, and audited, only when it changes. Every change writes one `AccountingAuditLog` row — `entityType = BANK_ACCOUNT_PROFILE`, operation `BANK_ACCOUNT_BASELINE_SET`, `oldValue` / `newValue` the previous and new date, `justification` the gap acknowledgement, actor the committing user — in the same transaction as the commit. Nobody edits the baseline directly: no endpoint or permission moves it, and `PUT …/profile` neither accepts nor changes it.
5. PROPOSED — normalization (§4.5): sign already in the core convention (adapters/connectors invert, §2.2); amount scaled to 4 dp exactly as delivered (R3); `transactionDate` = the bank's posting date, `authorizedDate` kept separately; `normalizedDescription` = upper-cased, whitespace-collapsed, punctuation-stripped copy used **only** for the fingerprint and (S4) candidate scoring; `description`/`originalDescription` verbatim; provenance (`sourceKind`, `sourceRef`, `connectorCode`, `sourceTransactionId`, `sourceRowNumber`, `firstObservedAt`) always retained; nothing inferred. Fingerprint = SHA-256 of `glAccountId | transactionDate | signedAmount(4 dp) | normalizedDescription | reference-or-checkNumber` (§3.2).
6. PROPOSED — manual entry: `POST /v1/accounting/bank-statements` builds a `BankTransactionsObservedV1` with `sourceKind = MANUAL_ENTRY`, `sourceRef = null`, `sourceTransactionId = null`, `sourceRowNumber` = list position, converting `debit/credit` to `signedAmount` (credit = cash in), passes `gapAcknowledgement` in the `IntakeContext`, and calls the port; this is also the phase-1 interim reconciliation to a date (§4.1 d, §5.7 b) — the preparer keys the transactions and closing balance from online banking and E1/E2, the baseline rule and a first statement's acknowledgement apply as to any statement. Replay with the same `requestId` and payload → 201 body with `replayed: true`; different payload → 409 `IDEMPOTENCY_CONFLICT`.
7. PROPOSED — duplicate review: `decision = DISTINCT` → `UNMATCHED`; `DUPLICATE` → `EXCLUDED` with `duplicateOfBankTransactionId` (defaults to the flagged original) and `exclusionReason`, justification required; only a `POSSIBLE_DUPLICATE` row is reviewable (else `RECONCILIATION_LINE_INELIGIBLE`); bulk review is a list of ids in the same body shape.
8. PROPOSED — exclude: `UNMATCHED` → `EXCLUDED` with justification (only while unmatched); restore: `EXCLUDED` → `UNMATCHED` with justification, refused when a `FINALIZED` reconciliation on the account covers the row's `transactionDate` (§3.8); both `RECONCILIATION_LINE_INELIGIBLE` otherwise. `EXCLUDED` rows leave every sum (R2).
9. PROPOSED — lists: bank transactions filtered by `glAccountId` (required), `status`, `from`, `to`, `sourceKind`, `unexplainedOnly` (= `UNMATCHED` + `POSSIBLE_DUPLICATE`), paginated with stable sort `transactionDate, bankTransactionId`, each row with its match / outstanding-item / exclusion links (null until S4); statements by `glAccountId`, `from`, `to`, each with its gap acknowledgement when present.
10. PROPOSED — bank accounts: every active GL account with `reconcilable = true` and `accountSubtype = BANK_CASH` (D5) with its profile (bank name, mask, currency), `reconciliationBaselineDate` (§3.1; null before the first acknowledged statement), `coverageFrontier` (latest COMMITTED statement `endDate`), `reconciledFrontier` (latest `FINALIZED` reconciliation `statementEndDate` in the contiguous chain), `unexplainedBankTransactionCount` and `openOutstandingItemCount` counted from the baseline on (§4.1; items 0 until S4), feed link state (`NONE` until phase 2); display code and name beside every id (ADR-0064). `PUT …/profile` creates or updates the thin profile (D21); `currency` other than `USD` → 422 `CURRENCY_NOT_SUPPORTED` (D18, §3.1); it never touches `reconciliationBaselineDate`.

## Business rules and invariants
- **E1** `openingBalance + activityTotal = closingBalance` (±0.01) or the commit is refused (§3.1). **E2** contiguity with the previous COMMITTED statement unless acknowledged; the account's first statement always needs an acknowledgement (§3.1, §4.2, D17).
- **U1** one COMMITTED statement per `(glAccountId, startDate, endDate)`; **U2** COMMITTED windows never overlap — service check plus the S1 exclusion constraint (§3.1, §6.5).
- **U3** same source, same id → upsert (§3.2). **R1** a fingerprint collision enters as `POSSIBLE_DUPLICATE`, never a silent drop. **R2** `EXCLUDED`/`REMOVED_BY_SOURCE` rows leave every sum. **R3** amounts stored exactly as delivered after sign normalization (§3.2).
- **Baseline** (§3.1, D2): the first day from which the account's bank transactions and ledger lines must be explained; set only by the intake in the statement-commit transaction, recomputed on supersede, one audit row per change, never set through an endpoint.
- A bank transaction is evidence, never a journal entry (§3.9); `connectorCode` is never used for behaviour in the core; `sourceKind` is the only thing the core branches on (§2.2).
- A `POSSIBLE_DUPLICATE` row counts as unexplained until reviewed (§4.5, E4, D2 — enforced at submit/approve in S5).
- **Only a real discontinuity moves the baseline** (§3.1): an acknowledgement on a contiguous statement is refused, so no preparer can drop history from the unexplained counts at will.
- Justification minimum 10 characters for `gapAcknowledgement`, duplicate review, exclude, restore (§4 preamble, D15); one condition, one code — a short acknowledgement is `JUSTIFICATION_REQUIRED`, never `STATEMENT_NOT_CONTIGUOUS` (ADR-0017 §2).
- Actor strings from `SecurityContextHelper` (ADR-0018); tenant only from `X-Tenant-Id` (§6, ADR-0062).

## State model
`BankTransaction` (§3.8) — transitions delivered here: `POSSIBLE_DUPLICATE → UNMATCHED` (review `DISTINCT`) · `POSSIBLE_DUPLICATE → EXCLUDED` (review `DUPLICATE`, `duplicateOf`) · `UNMATCHED → EXCLUDED` (exclude, justified, only while unmatched) · `EXCLUDED → UNMATCHED` (restore, justified, no `FINALIZED` reconciliation covered it). Entry states: `UNMATCHED` or `POSSIBLE_DUPLICATE` at intake. `UNMATCHED ↔ MATCHED` is S4; `→ REMOVED_BY_SOURCE` is phase 2. `BankStatement`: created `COMMITTED`; `→ SUPERSEDED` by a corrected re-import (§4.9 path 3, S5). Account baseline: none → the first acknowledged statement's `startDate` → a later acknowledged statement's `startDate`; recomputed when a statement is superseded; never moved by an endpoint or by an acknowledgement on a contiguous statement (§3.1).

## Alternate and error flows
- Previous statement closed 12,345.67 on 08-31; new header opening 12,300.00 from 09-01 → 422 `STATEMENT_NOT_CONTIGUOUS`, `fieldErrors[openingBalance] = "expected 12345.67"`; with `gapAcknowledgement` the statement commits, the baseline moves to 09-01 with one `BANK_ACCOUNT_BASELINE_SET` row, and the mismatch surfaces at review as the `openingDifference` diagnostic that a gap bridge may settle (S4) (§4.2).
- An account's first statement without `gapAcknowledgement` → 422 `STATEMENT_NOT_CONTIGUOUS` (§4.10 "or no previous statement exists", §8.2); with it → committed, baseline = its `startDate`, profile row created if absent.
- A contiguous statement → baseline unchanged, no audit row; the same with a valid acknowledgement → 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`, baseline unchanged; with a 5-character one → 400 `JUSTIFICATION_REQUIRED` (§4.2, §8.2).
- A manual statement with a transaction dated after its header end → 422 `STATEMENT_TRANSACTION_OUT_OF_WINDOW` with `fieldErrors[transactions[n]]` (§4.3, §8.2).
- Header 09-15..10-14 against a COMMITTED 09-01..09-30 → 422 `STATEMENT_PERIOD_OVERLAP` naming the `statementId`; two commits racing → the S1 exclusion constraint refuses the loser, mapped to the same code (§8.2 [M]).
- Same account and window from a second source → 409 `STATEMENT_ALREADY_IMPORTED`; a corrected re-import is an explicit supersede (§4.9), not a retry.
- Two identical $5.00 fees in one batch → both `POSSIBLE_DUPLICATE`; review `DISTINCT` on both → both `UNMATCHED`; neither is ever dropped (§8.2).
- Currency differs from the profile, or from `USD` while no profile exists → 422 `CURRENCY_NOT_SUPPORTED`; `PUT …/profile` with `CAD` → the same code (D18, §3.1, §8.2).
- Duplicate review on an `UNMATCHED` row, exclude on a `MATCHED` row, restore inside a `FINALIZED` window → 409 `RECONCILIATION_LINE_INELIGIBLE`.
- Blank justification or acknowledgement → 400 `VALIDATION_ERROR`; any of them shorter than 10 characters → 400 `JUSTIFICATION_REQUIRED` (§4.10, D15).
- Batch with zero transactions, null `change`, zero `signedAmount` or blank `description` → the record's compact constructor rejects it before the port is reached (§6.5).

## Acceptance criteria
1. **Given** a manual statement whose rows sum from opening to 9,985.00 while the header says closing 10,000.00 **When** posted **Then** 422 `STATEMENT_ACTIVITY_MISMATCH`, nothing persisted (E1, §4.4 example, §8.2 "manual entry passes the same E1/E2/U1/U2 checks").
2. **Given** a statement 09-01..09-30 committed **When** a second with the same account and window is posted **Then** 409 `STATEMENT_ALREADY_IMPORTED`; **When** 09-15..10-14 is posted **Then** 422 `STATEMENT_PERIOD_OVERLAP` (U1, U2, §4.5).
3. **Given** a batch with `sourceTransactionId = "T1"` delivered twice, the second with a changed description **When** accepted **Then** one `bank_transaction` exists with `feedChange = MODIFIED`, `lastObservedAt` advanced, `description` updated, `originalDescription` retained (U3, §8.2).
4. **Given** a batch containing two rows with identical date, amount, normalized description and reference **When** accepted **Then** both are stored, the second as `POSSIBLE_DUPLICATE` with `duplicateOfBankTransactionId` = the first (R1, §4.5).
5. **Given** a `POSSIBLE_DUPLICATE` row **When** reviewed `DUPLICATE` with a justification **Then** it is `EXCLUDED`, `duplicateOfBankTransactionId` set, an `AccountingAuditLog` row exists with the actor and justification, and the row is absent from `unexplainedOnly` lists (R2, §4.5).
6. **Given** a `MATCHED` row **When** excluded **Then** 409 `RECONCILIATION_LINE_INELIGIBLE`; **Given** an `EXCLUDED` row dated inside a `FINALIZED` reconciliation window **When** restored **Then** 409 `RECONCILIATION_LINE_INELIGIBLE` (§3.8).
7. **Given** a CSV amount `1,234.5` normalized upstream to `1234.5` **When** stored **Then** `signed_amount = 1234.5000` and the fingerprint uses `1234.5000` (R3, §8.1 rounding).
8. **Given** a `FINALIZED` reconciliation of 09-01..09-30 **When** a manual statement 10-01..10-31 carries a transaction dated 09-28 **Then** 422 `STATEMENT_TRANSACTION_OUT_OF_WINDOW`; **When** a header 09-20..10-31 is posted **Then** 422 `STATEMENT_PERIOD_OVERLAP`; no phase-1 row is ever flagged `arrivedAfterApproval` — D10 tests belong to the phase-2 connector stories (§5.5, §8.4).
9. **Given** the seeded chart after S1 **When** `GET /bank-accounts` is called **Then** `1000 Cash` is listed with `coverageFrontier` = its latest COMMITTED `endDate` and `reconciliationBaselineDate` = its latest acknowledged statement's `startDate`, and `1090 Undeposited Funds` is absent (§4.1, D5).
10. **Given** a caller without the permission **When** any endpoint above is called **Then** 403 with no hint of existence; **Given** a second tenant **Then** it sees none of the first tenant's statements or transactions (§8.4).
11. **Given** an account with no profile and no statement **When** its first statement is committed with a `gapAcknowledgement` **Then** a profile row exists, `reconciliation_baseline_date` = the statement's `startDate`, and exactly one `BANK_ACCOUNT_BASELINE_SET` row (`entityType = BANK_ACCOUNT_PROFILE`, no previous date in `oldValue`, `newValue` the date, `justification` the acknowledgement, actor the committer) is written in the commit transaction; **When** the same first statement has no acknowledgement **Then** 422 `STATEMENT_NOT_CONTIGUOUS`; the created profile has null bank name and mask and `currency = USD`, and a file or request declaring `EUR` on an account without a profile → 422 `CURRENCY_NOT_SUPPORTED` (§3.1, §8.2).
12. **Given** a baseline of 09-01 **When** a contiguous 10-01..10-31 statement is committed **Then** the baseline is unchanged and no audit row is written; **When** it carries a valid acknowledgement **Then** 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE` [M] — accept it and the baseline moves; with a 5-character one **Then** 400 `JUSTIFICATION_REQUIRED`; **When** an acknowledged 12-01..12-31 statement follows a gap **Then** the baseline moves to 12-01 with one audit row; **When** the recompute S5 calls runs after a supersession **Then** the baseline is recomputed from the remaining COMMITTED statements, with one audit row only if the value changes; **When** `PUT …/profile` is called **Then** the stored baseline is unchanged (§3.1 "no endpoint or permission moves it", §8.2).

## Decisions applied
| Dn | Decision (2026-09-28) | Effect on this story |
| --- | --- | --- |
| D2 | Matching-complete approval gate, amended: a per-account reconciliation baseline, set by the first statement and by each gap acknowledgement, bounds what must be explained; unreviewed `POSSIBLE_DUPLICATE` rows count as unexplained. | The intake stores the acknowledgement, sets and recomputes `reconciliation_baseline_date`, creates the profile if absent, audits `BANK_ACCOUNT_BASELINE_SET`; `GET /bank-accounts` returns `reconciliationBaselineDate` and counts from the baseline on. |
| D3 | New `accounting:reconciliation:approve`; preparer ≠ approver enforced by default. | `exclude`/`restore` guarded by `approve`; this story registers the constant and `permissions.yaml` row only (S5 completes). |
| D5 | Bank accounts are `reconcilable` GL accounts of subtype `BANK_CASH`. | Intake account check and `GET /bank-accounts` filter on `BANK_CASH`; 1090 is excluded. |
| D6 | The tenant is the entity boundary. | No entity dimension on statements or transactions. |
| D10 | A bank transaction arriving inside a `FINALIZED` window is flagged, never invalidates; only phase-2 feeds can deliver one. | The intake sets `arrivedAfterApproval` for feed batches; phase-1 paths refuse such rows (`STATEMENT_TRANSACTION_OUT_OF_WINDOW`, `STATEMENT_PERIOD_OVERLAP`). |
| D15 | Justification minimum is 10 characters. | `gapAcknowledgement`, duplicate review, exclude and restore require ≥ 10. |
| D17 | Gaps are allowed with a `gapAcknowledgement`; overlaps are always refused. | First statement, date gap or bank change need the acknowledgement (else `STATEMENT_NOT_CONTIGUOUS`); on a contiguous statement it is refused (`STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`); overlap always `STATEMENT_PERIOD_OVERLAP`; only an acknowledged statement moves the baseline. |
| D18 | A currency different from the profile is refused; a profile's currency is `USD`, including the one the intake creates. | `CURRENCY_NOT_SUPPORTED` at intake (against `USD` without a profile) and on `PUT …/profile`. |
| D19 | Pending feed transactions are visible, never matchable. | Stored with `settlementState = PENDING`; matchability refused in S4. |
| D21 | Thin `bank_account_profile`. | `PUT …/profile` upserts bank name, mask, currency, mapping, cycle hint; no account numbers. |
