## Story Intent
**As a** preparer (holder of `accounting:reconciliation:adjust`) **I want** bank statements and their transactions to enter accounting through one provider-neutral contract — normalized, fingerprinted, upserted by source id, flagged as possible duplicates instead of dropped — and to enter a statement by hand when no file exists **so that** every bank line is retained as evidence exactly as the bank delivered it, no duplicate is ever silently discarded, and the reconciliation core never learns a file format or a provider.

## Functional behaviour
1. EXISTING kept — the F2 `/v1/accounting/reconciliations` endpoints stay as S1 left them; `POST /import` still writes through the S1 persistence (its retirement is S3, pending D14).
2. PROPOSED — contract: `BankTransactionsObservedV1` carries `sourceKind` (`FILE_IMPORT`/`MANUAL_ENTRY`/`BANK_FEED`), `connectorCode` (label only, never behavioural), `feedConnectionId`, `feedAccountRef` (the `importId` string for files), `currency`, `observedAt`, `cursorRef` (opaque), optional `statement{statementRef, startDate, endDate, openingBalance, closingBalance}`, `transactions[]` per §2.2 (`signedAmount` positive = money into the account; external ids `String` per ADR-0027). Envelope per ADR-0044 §3 with required `tenantId`. No class in the package references a provider.
3. PROPOSED — `accept` runs in one transaction: (a) resolve the GL account from `ctx.glAccountId` (files/manual; feeds resolve through `bank_account_profile` in phase 2), require `reconcilable` (and subtype `BANK_CASH`, pending D5) else `ACCOUNT_NOT_RECONCILABLE`; (b) `currency` equals the profile currency else `CURRENCY_NOT_SUPPORTED` (pending D18); (c) if a `statement` block is present: `startDate ≤ endDate`, `endDate` not in the future, U1 (`STATEMENT_ALREADY_IMPORTED`), U2 (`STATEMENT_PERIOD_OVERLAP` with `fieldErrors[statementId]`), E2 against the previous COMMITTED statement — `openingBalance` = its `closingBalance` and `startDate` = its `endDate + 1` — else `STATEMENT_NOT_CONTIGUOUS` with `fieldErrors[openingBalance] = "expected <value>"` unless `gapAcknowledgement` (justification ≥ 10, pending D15/D17) is supplied; (d) for each transaction: normalize, then source-id layer — same `(glAccountId, sourceKind, sourceRef, sourceTransactionId)` → update the retained fields, `feedChange = MODIFIED`, advance `lastObservedAt`, never a second row (U3); else fingerprint layer — a collision with an existing row on the account or another row of the batch → `POSSIBLE_DUPLICATE` with `duplicateOfBankTransactionId` pointing at the earlier row (R1), else `UNMATCHED`; `settlementState` stored as delivered (`PENDING` visible, never matchable — D19, enforced in S4); (e) E1: `openingBalance + Σ signedAmount = closingBalance` within ±0.01 else `STATEMENT_ACTIVITY_MISMATCH`; (f) persist the `bank_statement` as `COMMITTED` with `activityTotal`, link every row by `statementId`; (g) set `arrivedAfterApproval = true` on any row dated inside a `FINALIZED` reconciliation window on the account (pending D10); (h) return counts (`bankTransactionCount`, `possibleDuplicateCount`, `modifiedCount`).
4. PROPOSED — normalization (§4.5): sign already in the core convention (adapters/connectors invert, §2.2); amount scaled to 4 dp exactly as delivered (R3); `transactionDate` = the bank's posting date, `authorizedDate` kept separately; `normalizedDescription` = upper-cased, whitespace-collapsed, punctuation-stripped copy used **only** for the fingerprint and (S4) candidate scoring; `description`/`originalDescription` verbatim; provenance (`sourceKind`, `sourceRef`, `connectorCode`, `sourceTransactionId`, `sourceRowNumber`, `firstObservedAt`) always retained; nothing inferred. Fingerprint = SHA-256 of `glAccountId | transactionDate | signedAmount(4 dp) | normalizedDescription | reference-or-checkNumber` (§3.2).
5. PROPOSED — manual entry: `POST /v1/accounting/bank-statements` builds a `BankTransactionsObservedV1` with `sourceKind = MANUAL_ENTRY`, `sourceRef = null`, `sourceTransactionId = null`, `sourceRowNumber` = list position, converting `debit/credit` to `signedAmount` (credit = cash in), and calls the port. Replay with the same `requestId` and payload → 201 body with `replayed: true`; different payload → 409 `IDEMPOTENCY_CONFLICT`.
6. PROPOSED — duplicate review: `decision = DISTINCT` → `UNMATCHED`; `DUPLICATE` → `EXCLUDED` with `duplicateOfBankTransactionId` (defaults to the flagged original) and `exclusionReason`, justification required; only a `POSSIBLE_DUPLICATE` row is reviewable (else `RECONCILIATION_LINE_INELIGIBLE`); bulk review is a list of ids in the same body shape.
7. PROPOSED — exclude: `UNMATCHED` → `EXCLUDED` with justification (only while unmatched); restore: `EXCLUDED` → `UNMATCHED` with justification, refused when a `FINALIZED` reconciliation on the account covers the row's `transactionDate` (§3.8); both `RECONCILIATION_LINE_INELIGIBLE` otherwise. `EXCLUDED` rows leave every sum (R2).
8. PROPOSED — lists: bank transactions filtered by `glAccountId` (required), `status`, `from`, `to`, `sourceKind`, `unexplainedOnly` (= `UNMATCHED` + `POSSIBLE_DUPLICATE`), paginated with stable sort `transactionDate, bankTransactionId`, each row with its match / outstanding-item / exclusion links (null until S4); statements by `glAccountId`, `from`, `to`.
9. PROPOSED — bank accounts: every active GL account with `reconcilable = true` and `accountSubtype = BANK_CASH` (pending D5) with its profile (bank name, mask, currency), `coverageFrontier` (latest COMMITTED statement `endDate`), `reconciledFrontier` (latest `FINALIZED` reconciliation `statementEndDate` in the contiguous chain), `unexplainedBankTransactionCount`, `openOutstandingItemCount` (0 until S4), feed link state (`NONE` until phase 2); display code and name beside every id (ADR-0064). `PUT …/profile` upserts the thin profile (pending D21).

## Business rules and invariants
- **E1** `openingBalance + activityTotal = closingBalance` (±0.01) or the commit is refused (§3.1). **E2** contiguity with the previous COMMITTED statement unless acknowledged (§3.1, D17).
- **U1** one COMMITTED statement per `(glAccountId, startDate, endDate)`; **U2** COMMITTED windows never overlap — service check plus the S1 exclusion constraint (§3.1, §6.5).
- **U3** same source, same id → upsert (§3.2). **R1** a fingerprint collision enters as `POSSIBLE_DUPLICATE`, never a silent drop. **R2** `EXCLUDED`/`REMOVED_BY_SOURCE` rows leave every sum. **R3** amounts stored exactly as delivered after sign normalization (§3.2).
- A bank transaction is evidence, never a journal entry (§3.9); `connectorCode` is never used for behaviour in the core; `sourceKind` is the only thing the core branches on (§2.2).
- A `POSSIBLE_DUPLICATE` row counts as unexplained until reviewed (§4.5, E4 — enforced at submit/approve in S5).
- Justification minimum 10 characters for `gapAcknowledgement`, duplicate review, exclude, restore (§4 preamble, pending D15).
- Actor strings from `SecurityContextHelper` (ADR-0018); tenant only from `X-Tenant-Id` (§6, ADR-0062).

## State model
`BankTransaction` (§3.8) — transitions delivered here: `POSSIBLE_DUPLICATE → UNMATCHED` (review `DISTINCT`) · `POSSIBLE_DUPLICATE → EXCLUDED` (review `DUPLICATE`, `duplicateOf`) · `UNMATCHED → EXCLUDED` (exclude, justified, only while unmatched) · `EXCLUDED → UNMATCHED` (restore, justified, no `FINALIZED` reconciliation covered it). Entry states: `UNMATCHED` or `POSSIBLE_DUPLICATE` at intake. `UNMATCHED ↔ MATCHED` is S4; `→ REMOVED_BY_SOURCE` is phase 2. `BankStatement`: created `COMMITTED`; `→ SUPERSEDED` (corrected re-import) is S3/S4 (§4.9 path 3).

## Alternate and error flows
- Previous statement closed 12,345.67 on 08-31; new header opening 12,300.00 from 09-01 → 422 `STATEMENT_NOT_CONTIGUOUS`, `fieldErrors[openingBalance] = "expected 12345.67"`; with `gapAcknowledgement` the statement commits and the mismatch surfaces as `openingDifference` at review (S4) (§4.2).
- Header 09-15..10-14 against a COMMITTED 09-01..09-30 → 422 `STATEMENT_PERIOD_OVERLAP` naming the `statementId`; two commits racing → the S1 exclusion constraint refuses the loser, mapped to the same code (§8.2 [M]).
- Same account and window from a second source → 409 `STATEMENT_ALREADY_IMPORTED`; a corrected re-import is an explicit supersede (§4.9), not a retry.
- Two identical $5.00 fees in one batch → both `POSSIBLE_DUPLICATE`; review `DISTINCT` on both → both `UNMATCHED`; neither is ever dropped (§8.2).
- Currency differs from the profile → 422 `CURRENCY_NOT_SUPPORTED`; no profile → the account currency defaults per the seed (USD-only platform, D18).
- Duplicate review on an `UNMATCHED` row, exclude on a `MATCHED` row, restore inside a `FINALIZED` window → 409 `RECONCILIATION_LINE_INELIGIBLE`.
- Blank justification → 400 `VALIDATION_ERROR`; shorter than 10 → `JUSTIFICATION_REQUIRED` (EXISTING catalogued code; status per `ERROR_CODES.md`, minimum aligned to 10 in S9, pending D15).
- Batch with zero transactions, null `change`, zero `signedAmount` or blank `description` → the record's compact constructor rejects it before the port is reached (§6.5).

## Acceptance criteria
1. **Given** a manual statement whose rows sum from opening to 9,985.00 while the header says closing 10,000.00 **When** posted **Then** 422 `STATEMENT_ACTIVITY_MISMATCH`, nothing persisted (E1, §4.4 example, §8.2 "manual entry passes the same E1/E2/U1/U2 checks").
2. **Given** a statement 09-01..09-30 committed **When** a second with the same account and window is posted **Then** 409 `STATEMENT_ALREADY_IMPORTED`; **When** 09-15..10-14 is posted **Then** 422 `STATEMENT_PERIOD_OVERLAP` (U1, U2, §4.5).
3. **Given** a batch with `sourceTransactionId = "T1"` delivered twice, the second with a changed description **When** accepted **Then** one `bank_transaction` exists with `feedChange = MODIFIED`, `lastObservedAt` advanced, `description` updated, `originalDescription` retained (U3, §8.2).
4. **Given** a batch containing two rows with identical date, amount, normalized description and reference **When** accepted **Then** both are stored, the second as `POSSIBLE_DUPLICATE` with `duplicateOfBankTransactionId` = the first (R1, §4.5).
5. **Given** a `POSSIBLE_DUPLICATE` row **When** reviewed `DUPLICATE` with a justification **Then** it is `EXCLUDED`, `duplicateOfBankTransactionId` set, an `AccountingAuditLog` row exists with the actor and justification, and the row is absent from `unexplainedOnly` lists (R2, §4.5).
6. **Given** a `MATCHED` row **When** excluded **Then** 409 `RECONCILIATION_LINE_INELIGIBLE`; **Given** an `EXCLUDED` row dated inside a `FINALIZED` reconciliation window **When** restored **Then** 409 `RECONCILIATION_LINE_INELIGIBLE` (§3.8).
7. **Given** a CSV amount `1,234.5` normalized upstream to `1234.5` **When** stored **Then** `signed_amount = 1234.5000` and the fingerprint uses `1234.5000` (R3, §8.1 rounding).
8. **Given** a row dated inside a `FINALIZED` reconciliation window **When** accepted **Then** `arrivedAfterApproval = true`, status `UNMATCHED`, and the reconciliation's status is unchanged (§5.5, pending D10).
9. **Given** the seeded chart after S1 **When** `GET /bank-accounts` is called **Then** `1000 Cash` is listed with `coverageFrontier` = its latest COMMITTED `endDate` and `1090 Undeposited Funds` is absent (§4.1, pending D5).
10. **Given** a caller without the permission **When** any endpoint above is called **Then** 403 with no hint of existence; **Given** a second tenant **Then** it sees none of the first tenant's statements or transactions (§8.4).
