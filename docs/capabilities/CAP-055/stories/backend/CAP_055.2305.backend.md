## Story Intent
**As a** controller closing an accounting period, **I want** a bank-reconciliation readiness read model, a configurable close policy and an audited exception path wired into `closePeriod`, **so that** a period never closes on a misleading cash balance and every deviation from the policy is explicit and traceable (§5.2, §5.8).

## Scope
### In scope
- `BankReconciliationCloseReadinessService.evaluate(period)` under `internal/bankrec/readmodel`, producing the §5.3 checks per in-scope bank account.
- `GET /v1/accounting/periods/{periodCode}/close-readiness` (`accounting:period:view`; `@EmitEvent ACCOUNTING_PERIOD_CLOSE_READINESS`, fastRead).
- Policy configuration: `accounting_configuration` keys `BANK_REC_CLOSE_POLICY`, `BANK_REC_CLOSE_SCOPE`, `BANK_REC_CLOSE_COVERAGE_LAG_DAYS`; `GET|PUT /v1/accounting/periods/bank-reconciliation-policy` on `AccountingConfigurationService` beside `HARD_LOCK_DATE`; audit `BANK_REC_CLOSE_POLICY_SET`.
- `AccountingPeriodServiceImpl.closePeriod(periodCode, PeriodCloseRequest)` (interface `AccountingPeriodService` too); optional close body `{bankReconciliationException: {justification}}`; response fields `bankReconciliationReady`, `bankReconciliationException`.
- 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (a `PeriodCloseBlockedException` subtype), 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`, audit `PERIOD_CLOSE_BANKREC_EXCEPTION`, readiness summary in the `PERIOD_CLOSE` audit row.
- Property `pos.accounting.bankrec.outstanding.aging-warning-days` (default 90) read by `OUTSTANDING_ITEMS_AGING` (§3.6, §5.3).
### Out of scope (and where it lives)
- Reconciliation states, the invalidation hook and facts — S5. Statements, transactions, `arrivedAfterApproval` — S2. Outstanding items and unexplained counts — S4. Import statuses — S3.
- The readiness panel, exception dialog and `classifyPeriodActionError` — S7. `accounting.period.closed/reopened` facts — pending D16. The "reconciled after close" stamp on the reconciliation report — S4's report; here only the `RECONCILED_AFTER_CLOSE` INFO check. Documentation — S9.

## Functional behaviour
EXISTING (verified in `AccountingPeriodServiceImpl.closePeriod` and `AccountingPeriodController`): `POST /v1/accounting/periods/{periodCode}/close`, no body, `accounting:period:close`, `@EmitEvent ACCOUNTING_PERIOD_CLOSE`; CLOSED → 409 `PERIOD_ALREADY_CLOSED`; DRAFT entries inside → `PeriodCloseBlockedException` → 422 `PERIOD_HAS_DRAFT_ENTRIES` with `fieldErrors[draftJournalEntryIds]`; month not started → 404 `PERIOD_NOT_FOUND`; audit `PERIOD_CLOSE`; `GET|PUT /hard-lock` on `AccountingConfigurationService` (`HARD_LOCK_DATE`, `accounting:period:hard_lock`); `AccountingPeriodGate` order hard lock > closed > override. Close consults only DRAFT entries (G6).

PROPOSED:
1. **Readiness read model** (§5.3): for each in-scope account — `reconcilable` and `accountSubtype = BANK_CASH` under `BANK_CASH_SUBTYPE` (pending D5), every reconcilable account under `ALL_RECONCILABLE` — compute `coverageFrontier` (latest COMMITTED statement or interim window `endDate`) and `reconciledFrontier` (latest `FINALIZED` reconciliation `statementEndDate` in the contiguous chain from the account's first statement, §4.1), then evaluate the check table against `periodEndDate − BANK_REC_CLOSE_COVERAGE_LAG_DAYS`. Read-only: every posting still goes through `AccountingPeriodGate` (§5.9 last row).
2. **Policy** (§5.2): `ADVISORY` — every severity reported, `ready` reflects only `DRAFT_JOURNAL_ENTRIES`, close never blocked, an exception body ignored; `REQUIRED_WITH_EXCEPTION` — BLOCKING checks block unless a valid exception is granted; `REQUIRED` — blocked, an exception refused with 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (`fieldErrors[bankReconciliationException]` says it is not permitted by policy).
3. **Close command** (§5.9): after the DRAFT check, `evaluate(period)` inside the close transaction with the period row locked (EXISTING `FOR UPDATE` path) and each covering reconciliation row locked (§6.3); under `REQUIRED*` with BLOCKING checks and no valid exception → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with `fieldErrors[] = {field: "unreconciledGlAccountIds", value: <glAccountId>, message: "<accountCode>: <check codes>"}` (the `PERIOD_HAS_DRAFT_ENTRIES` shape); with a valid exception → close proceeds, audit `PERIOD_CLOSE_BANKREC_EXCEPTION` on `ACCOUNTING_PERIOD` with the justification and the readiness snapshot in `oldValue`, response `bankReconciliationException = true`; the `PERIOD_CLOSE` row's `newValue` gains the readiness summary.
4. **Exception validity** (§5.2, I5): the closer holds both `accounting:period:close` and `accounting:period:override`; justification ≥ 10 characters (pending D15); otherwise 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` and nothing closes.
5. **Reopen** unchanged (`PERIOD_REOPEN`, §5.6); a re-close re-runs readiness and `RECONCILIATION_INVALIDATED` blocks until the successor is `FINALIZED`.

Check table (§5.3):

| Code | Severity under `REQUIRED*` | Check | References in the response |
| --- | --- | --- | --- |
| `DRAFT_JOURNAL_ENTRIES` | BLOCKING (EXISTING) | DRAFT entries dated inside the period | `draftJournalEntryIds` |
| `STATEMENT_COVERAGE` | BLOCKING | `coverageFrontier ≥ periodEndDate − lag` | account, `coverageFrontier` |
| `RECONCILIATION_APPROVED` | BLOCKING | `reconciledFrontier ≥ periodEndDate − lag`, contiguous chain | account, `reconciledFrontier`, `reconciliationId` |
| `RECONCILIATION_IN_FLIGHT` | BLOCKING | `IN_PROGRESS` / `SUBMITTED` with `statementEndDate ≤ periodEndDate` | ids |
| `RECONCILIATION_INVALIDATED` | BLOCKING | `INVALIDATED` window intersecting the period without a `FINALIZED` successor | ids, `invalidationReason` |
| `BALANCE_AGREEMENT` | BLOCKING | live `glBalanceAsOf(statementEndDate)` = `approvedGlEndingBalance` of the covering reconciliation | account, both values |
| `UNEXPLAINED_BANK_TRANSACTIONS` | BLOCKING | `UNMATCHED` / `POSSIBLE_DUPLICATE` dated ≤ `periodEndDate` (late arrivals included, D10) | count, Σ, first 50 ids |
| `UNEXPLAINED_LEDGER_LINES` | BLOCKING | POSTED lines ≤ `periodEndDate`, unmatched, not in an `OPEN` outstanding item | count, Σ, ids |
| `UNPOSTED_ADJUSTMENTS` | BLOCKING | adjustment rows with a null or non-POSTED JE (defensive) | ids |
| `COVERAGE_LAG_APPLIED` | WARNING | lag > 0 and `reconciledFrontier < periodEndDate` — the frontier passed only because of the lag | account, `reconciledFrontier`, `lagDays` |
| `INCOMPLETE_IMPORTS` | WARNING | `UPLOADED` / `VALIDATED` imports with rows ≤ `periodEndDate` | `importIds` |
| `OUTSTANDING_ITEMS_AGING` | WARNING | `OPEN` items older than `aging-warning-days` | ids, ages |
| `LATE_BANK_TRANSACTIONS` | WARNING | `arrivedAfterApproval = true` inside the period, unresolved | ids |
| `RECONCILED_AFTER_CLOSE` | INFO | covering reconciliation approved after `closedAt` | ids |

Response: `{periodCode, periodStatus, policy, ready, blockingCount, warningCount, accounts[]: {glAccountId, accountCode, accountName, coverageFrontier, reconciledFrontier, checks[]: {code, severity, detail, references{}}}}`; `OPEN` outstanding items are listed with their sum so the closer sees the book-to-bank bridge (I2).

## Business rules and invariants
- **I1** under `REQUIRED*` a period closes only if every in-scope account has a `FINALIZED` reconciliation reaching `periodEndDate − lag` whose `approvedGlEndingBalance` equals the live as-of balance at close time (§5.8).
- **I2** no unexplained bank transaction or ledger line ≤ `periodEndDate` on an in-scope account; `OPEN` outstanding items are the explained differences and never block (§5.4).
- **I3** close re-reads the live balance under the period row lock; the reconciliation row lock serializes against a concurrent approval (§5.8, §6.3).
- **I4** unchanged here — enforced by the EXISTING gate and S5's hook.
- **I5** an exception is never silent: two authorities, a justification, an audit row with the readiness snapshot, and `bankReconciliationException = true` in the response.
- Statement windows are never assumed to align with periods; `accountingPeriodCode` is attribution only; readiness looks only at the frontier (§5.7).
- Aging is a WARNING, never a block (§5.4); under `ADVISORY` only DRAFT entries block (§5.3).
- ADR-0017: 403 for who the caller is (`PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`), 422 for the refusal, one condition one code.

## Data requirements
- No new table. `accounting_configuration` rows `BANK_REC_CLOSE_POLICY` (`ADVISORY` | `REQUIRED_WITH_EXCEPTION` | `REQUIRED`), `BANK_REC_CLOSE_SCOPE` (`BANK_CASH_SUBTYPE` | `ALL_RECONCILABLE`), `BANK_REC_CLOSE_COVERAGE_LAG_DAYS` (integer ≥ 0), tenant-scoped like `HARD_LOCK_DATE` (ADR-0062 §9); defaults when a row is absent: `REQUIRED_WITH_EXCEPTION`, `BANK_CASH_SUBTYPE`, `0` (pending D4, D5).
- Reads only: `bank_statement`, `bank_reconciliation` (INDEX `(tenant_id, gl_account_id, statement_end_date, status)`), `bank_transaction` (`(tenant_id, gl_account_id, transaction_date, status)`), `bank_reconciliation_outstanding_item`, `bank_reconciliation_adjustment`, `bank_import`, the as-of balance of `journal_entry_line` — all delivered by S1–S5; no Flyway change unless a §6.4 index is missing.
- The seed fix `1000 Cash reconcilable = TRUE` (S1, G7) is what places the seeded bank account in scope.

## State model
No new aggregate state; the period stays `OPEN` / `CLOSED` (§5 preamble). Readiness is a derived, non-persisted read model; `ready` is true iff no BLOCKING check remains under the effective policy.

## Alternate and error flows
- `REQUIRED` + exception body → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE`; the exception is refused (§5.2).
- `REQUIRED_WITH_EXCEPTION` + exception body from a caller without `override` → 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`; period stays `OPEN`; no exception audit row.
- `ADVISORY` + BLOCKING checks → closes; `bankReconciliationReady = false`; the readiness summary lands in the `PERIOD_CLOSE` audit `newValue`.
- Coverage lag (e.g. 31 on a mid-month cycle) → the `STATEMENT_COVERAGE` / `RECONCILIATION_APPROVED` thresholds move back by the lag, the straddling window no longer blocks, and `COVERAGE_LAG_APPLIED` WARNING reports the shortfall (§5.2, §5.3, §5.7 option c).
- Period reopened, a JE posted inside a `FINALIZED` window (S5 invalidates) → re-close blocked by `RECONCILIATION_INVALIDATED` until the superseding reconciliation is `FINALIZED` (§5.6).
- Approval landing after `closedAt` → `RECONCILED_AFTER_CLOSE` INFO on the next readiness read (§5.1, §8.4).
- Policy PUT with an unknown enum value or a negative lag → 400 `VALIDATION_ERROR`.

## Acceptance criteria
1. **Given** policy `REQUIRED_WITH_EXCEPTION`, account 1000 with a `FINALIZED` reconciliation reaching the period end and no unexplained items **When** readiness is read **Then** `ready = true`, `blockingCount = 0`, `reconciledFrontier ≥ periodEndDate` (§5.3, I1).
2. **Given** the same policy and an `IN_PROGRESS` reconciliation ending inside the period **When** close is called without a body **Then** 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with one `fieldErrors` entry `unreconciledGlAccountIds` = 1000's id and a message naming `RECONCILIATION_IN_FLIGHT` (§5.9).
3. **Given** AC 2 **When** a caller holding `close` and `override` closes with a `bankReconciliationException.justification` ≥ 10 characters **Then** `CLOSED`; audit `PERIOD_CLOSE_BANKREC_EXCEPTION` holds the justification and the readiness snapshot in `oldValue`; response `bankReconciliationException = true` (§5.2, I5).
4. **Given** AC 2 and a caller without `override` **When** closing with an exception **Then** 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` and the period stays `OPEN` (§5.2).
5. **Given** policy `REQUIRED` **When** closing with an exception **Then** 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (§5.2).
6. **Given** policy `ADVISORY` and BLOCKING checks **When** closing **Then** `CLOSED`, `bankReconciliationReady = false`, and readiness still lists every check (§5.3).
7. **Given** a covering `FINALIZED` reconciliation whose `approvedGlEndingBalance` differs from the live as-of balance **Then** `BALANCE_AGREEMENT` is BLOCKING even if S5's invalidation did not fire (§5.3, I1).
8. **Given** an `OPEN` deposit in transit and an outstanding check **When** readiness is read **Then** neither appears under `UNEXPLAINED_LEDGER_LINES`; both are listed with their sum; an item older than 90 days adds only `OUTSTANDING_ITEMS_AGING` WARNING (§5.4, I2).
9. **Given** a bank transaction with `arrivedAfterApproval = true` inside the period **Then** `LATE_BANK_TRANSACTIONS` WARNING and `UNEXPLAINED_BANK_TRANSACTIONS` BLOCKING; resolving it in the next window clears both (§5.5, §8.4, pending D10).
10. **Given** the period was reopened and a posting invalidated the covering reconciliation **When** re-closing **Then** blocked by `RECONCILIATION_INVALIDATED` until a superseding reconciliation is `FINALIZED`; the invalidated one stays readable (§5.6).
11. **Given** `BANK_REC_CLOSE_SCOPE = BANK_CASH_SUBTYPE` **Then** 1090 Undeposited Funds, 1200 AR and 2000 AP never appear in `accounts[]` (pending D5).
12. **Given** the policy is changed through PUT by a `hard_lock` holder **Then** audit `BANK_REC_CLOSE_POLICY_SET` is written and the next readiness read uses the new policy; a `view`-only caller can read but not change it (§5.9).
