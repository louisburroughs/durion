## Story Intent
**As a** controller closing an accounting period, **I want** a bank-reconciliation readiness read model bounded by each account's reconciliation baseline, a tenant-wide warning when the 2360 clearing account is not cleared back to zero, a configurable close policy that also carries the tenant's self-approval switch and `OTHER` approval threshold, and an audited exception path wired into `closePeriod`, **so that** a period never closes on a misleading cash balance and every deviation from the policy is explicit and traceable (§5.2, §5.8).

## Functional behaviour
EXISTING (verified in `AccountingPeriodServiceImpl.closePeriod` and `AccountingPeriodController`): `POST /v1/accounting/periods/{periodCode}/close`, no body, `accounting:period:close`, `@EmitEvent ACCOUNTING_PERIOD_CLOSE`; CLOSED → 409 `PERIOD_ALREADY_CLOSED`; DRAFT entries inside → `PeriodCloseBlockedException` → 422 `PERIOD_HAS_DRAFT_ENTRIES` with `fieldErrors[draftJournalEntryIds]`; month not started → 404 `PERIOD_NOT_FOUND`; audit `PERIOD_CLOSE`; `GET|PUT /hard-lock` on `AccountingConfigurationService` (`HARD_LOCK_DATE`, `accounting:period:hard_lock`); `AccountingPeriodGate` order hard lock > closed > override. Close consults only DRAFT entries (G6).

PROPOSED:
1. **Readiness read model** (§5.3): for each in-scope account — `reconcilable` and `accountSubtype = BANK_CASH` under `BANK_CASH_SUBTYPE` (D5), every reconcilable account under `ALL_RECONCILABLE` — compute `coverageFrontier` (latest COMMITTED statement or interim window `endDate`) and `reconciledFrontier` (latest `FINALIZED` reconciliation `statementEndDate` in the contiguous chain from the baseline that applies at `periodEndDate`, §3.1, §4.1), then evaluate the check table against `periodEndDate − BANK_REC_CLOSE_COVERAGE_LAG_DAYS`. The `UNEXPLAINED_*` checks run from that baseline to `periodEndDate` and are not evaluated while the account has no baseline (`STATEMENT_COVERAGE` reports it). Each account reports `baselineDate` — the baseline that applies at `periodEndDate`, the one those checks used (null when none); the current baseline stays `reconciliationBaselineDate` on the bank-accounts read (§4.1). `BALANCE_AGREEMENT` reads the live balance counting entries `POSTED` or `REVERSED` at their own dates (§3.7). Tenant-wide checks are evaluated once per period. Read-only: every posting still goes through `AccountingPeriodGate` (§5.9 last row).
2. **Policy** (§5.2): `ADVISORY` — every severity reported, `ready` reflects only `DRAFT_JOURNAL_ENTRIES`, close never blocked, an exception body ignored; `REQUIRED_WITH_EXCEPTION` — BLOCKING checks block unless a valid exception is granted; `REQUIRED` — blocked, an exception refused with 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (`fieldErrors[bankReconciliationException]` says it is not permitted by policy). The same endpoint carries the reconciliation settings of D2 and D3: `BANK_REC_ALLOW_SELF_APPROVAL` (boolean, default false; read by S5) and `BANK_REC_OTHER_APPROVAL_THRESHOLD` (a non-negative amount or unset; no row = unset; no default amount ships — Finance sets it; read by S4). **Policy body** (§5.2): `PUT` replaces all five settings at once, mirroring the hard-lock endpoint — `closePolicy` (`BANK_REC_CLOSE_POLICY`), `closeScope` (`BANK_REC_CLOSE_SCOPE`), `closeCoverageLagDays` (`BANK_REC_CLOSE_COVERAGE_LAG_DAYS`, integer ≥ 0), `allowSelfApproval` (`BANK_REC_ALLOW_SELF_APPROVAL`), `otherApprovalThreshold` (`BANK_REC_OTHER_APPROVAL_THRESHOLD`, amount ≥ 0 or `null` = unset), `justification` (≥ 10, D15); all six required. A missing field, an unknown enum value, a negative number or a blank justification → 400 `VALIDATION_ERROR`; a 1–9 character justification → 400 `JUSTIFICATION_REQUIRED`. Each setting whose value changes writes one `AccountingAuditLog` row — `entityType = ACCOUNTING_CONFIGURATION`, `entityId` = that key's configuration row, operation `BANK_REC_POLICY_SET`, `oldValue` / `newValue`, the request's justification — as `HARD_LOCK_SET` does; an unchanged setting writes nothing. `GET` returns the five effective values (defaults when a key has no row) with `updatedAt` / `updatedBy` of the latest change.
3. **Close command** (§5.9): after the DRAFT check, `evaluate(period)` inside the close transaction with the period row locked (EXISTING `FOR UPDATE` path) and each covering reconciliation row locked (§6.3); under `REQUIRED*` with BLOCKING checks and no valid exception → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with `fieldErrors[] = {field: "unreconciledGlAccountIds", value: <glAccountId>, message: "<accountCode>: <check codes>"}` (the `PERIOD_HAS_DRAFT_ENTRIES` shape); with a valid exception → close proceeds, audit `PERIOD_CLOSE_BANKREC_EXCEPTION` on `ACCOUNTING_PERIOD` with the justification and the readiness snapshot in `oldValue`, response `bankReconciliationException = true`; the `PERIOD_CLOSE` row's `newValue` gains the readiness summary.
4. **Exception validity** (§5.2, I5, D4): the closer holds both `accounting:period:close` and `accounting:period:override`; justification ≥ 10 characters (D15); otherwise 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` and nothing closes.
5. **Reopen** unchanged (`PERIOD_REOPEN`, §5.6); a re-close re-runs readiness and `RECONCILIATION_INVALIDATED` blocks until the successor is `FINALIZED`.

Check table (§5.3):

| Code | Severity under `REQUIRED*` | Check | References in the response |
| --- | --- | --- | --- |
| `DRAFT_JOURNAL_ENTRIES` | BLOCKING (EXISTING) | DRAFT entries dated inside the period | `draftJournalEntryIds` |
| `STATEMENT_COVERAGE` | BLOCKING | `coverageFrontier ≥ periodEndDate − lag` | account, `coverageFrontier` |
| `RECONCILIATION_APPROVED` | BLOCKING | `reconciledFrontier ≥ periodEndDate − lag`, contiguous chain from the baseline that applies at `periodEndDate` | account, `reconciledFrontier`, `reconciliationId` |
| `RECONCILIATION_IN_FLIGHT` | BLOCKING | `IN_PROGRESS` / `SUBMITTED` with `statementEndDate ≤ periodEndDate` | ids |
| `RECONCILIATION_INVALIDATED` | BLOCKING | `INVALIDATED` window intersecting the period without a `FINALIZED` successor | ids, `invalidationReason` |
| `BALANCE_AGREEMENT` | BLOCKING | live `glBalanceAsOf(statementEndDate)` = `approvedGlEndingBalance` of the covering reconciliation | account, both values |
| `UNEXPLAINED_BANK_TRANSACTIONS` | BLOCKING | `UNMATCHED` / `POSSIBLE_DUPLICATE` dated from the applying baseline to `periodEndDate`, in no `OPEN` bank-side item (late arrivals included, D10); not evaluated without a baseline | count, Σ, first 50 ids |

| `UNPOSTED_ADJUSTMENTS` | BLOCKING | adjustment rows with a null or non-POSTED JE (defensive) | ids |

| `CLEARING_BALANCE_AGING` (NEW, tenant-wide, top-level `checks[]`) | WARNING | for each clearing account — each distinct counter account a POSTED `OTHER` adjustment's JE posted to (`2360` in the seed), read from the JEs, never from the mapping — the as-of balance is outside ±0.01 both at `periodEndDate` and at `periodEndDate − clearing.aging-warning-days`; not evaluated when no `OTHER` adjustment was ever posted; account-level by design | per account: both balances; POSTED, unreversed `OTHER` adjustments dated on/before the earlier date (first 50) |
| `LATE_BANK_TRANSACTIONS` | WARNING | `arrivedAfterApproval = true` inside the period, unresolved (phase 2 only — no phase-1 path produces such a row, §5.5) | ids |

Response: `{periodCode, periodStatus, policy, ready, blockingCount, warningCount, checks[], accounts[]: {glAccountId, accountCode, accountName, baselineDate, coverageFrontier, reconciledFrontier, checks[]: {code, severity, detail, references{}}}}`; `OPEN` outstanding items are listed with their sum so the closer sees the book-to-bank bridge (I2). With E4 in force (D2) the approval gate and these checks are complementary: `UNEXPLAINED_*` block close only for what arrived or changed after approval, or for dates past the last approved window (§5.3).

## Business rules and invariants
- **I1** under `REQUIRED*` a period closes only if every in-scope account has a `FINALIZED` reconciliation reaching `periodEndDate − lag` whose `approvedGlEndingBalance` equals the live as-of balance at close time (§5.8).
- **I2** no unexplained bank transaction or ledger line dated from the account's baseline to `periodEndDate` on an in-scope account; `OPEN` outstanding items are the explained differences and never block; what lies before the baseline was bridged at the acknowledged statement and is visible in the clearing account and its aging (§5.4, §5.8).
- **I3** close re-reads the live balance under the period row lock; the reconciliation row lock serializes against a concurrent approval (§5.8, §6.3).
- **I4** unchanged here — enforced by the EXISTING gate and S5's hook.
- **I5** an exception is never silent: two authorities, a justification, an audit row with the readiness snapshot, and `bankReconciliationException = true` in the response.
- Statement windows are never assumed to align with periods; `accountingPeriodCode` is attribution only; readiness looks only at the frontier (§5.7).
- Aging is a WARNING, never a block (§5.4) — except that an aged `OTHER_LEDGER_TIMING` item not reaffirmed in the covering reconciliation counts under `UNEXPLAINED_LEDGER_LINES` (§3.6). `CLEARING_BALANCE_AGING` never blocks under any policy. Under `ADVISORY` only DRAFT entries block (§5.3).
- ADR-0017: 403 for who the caller is (`PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`), 422 for the refusal, one condition one code.

## Data requirements
- No new table. `accounting_configuration` rows, tenant-scoped like `HARD_LOCK_DATE` (ADR-0062 §9): `BANK_REC_CLOSE_POLICY` (`ADVISORY` | `REQUIRED_WITH_EXCEPTION` | `REQUIRED`), `BANK_REC_CLOSE_SCOPE` (`BANK_CASH_SUBTYPE` | `ALL_RECONCILABLE`), `BANK_REC_CLOSE_COVERAGE_LAG_DAYS` (integer ≥ 0), `BANK_REC_ALLOW_SELF_APPROVAL` (boolean), `BANK_REC_OTHER_APPROVAL_THRESHOLD` (non-negative amount; no row = unset); defaults when a row is absent: `REQUIRED_WITH_EXCEPTION`, `BANK_CASH_SUBTYPE`, `0`, `false`, unset (D2, D3, D4, D5).
- Reads only: the acknowledged `bank_statement` rows (baseline that applies at `periodEndDate`), `bank_statement`, `bank_reconciliation` (INDEX `(tenant_id, gl_account_id, statement_end_date, status)`), `bank_transaction` (`(tenant_id, gl_account_id, transaction_date, status)`), `bank_reconciliation_outstanding_item`, `bank_reconciliation_adjustment` (incl. `bridges_statement_id`), `bank_import`, the as-of balances of `journal_entry_line` (entries `POSTED` or `REVERSED`, §3.7) for each bank account and for each counter account the POSTED `OTHER` adjustments' JEs hit — all delivered by S1–S5; no Flyway change unless a §6.4 index is missing.
- The seed fix `1000 Cash reconcilable = TRUE` (S1, G7) is what places the seeded bank account in scope.

## State model
No new aggregate state; the period stays `OPEN` / `CLOSED` (§5 preamble). Readiness is a derived, non-persisted read model; `ready` is true iff no BLOCKING check remains under the effective policy (WARNING and INFO checks, per account or tenant-wide, never affect it).

## Alternate and error flows
- `REQUIRED` + exception body → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE`; the exception is refused (§5.2).
- `REQUIRED_WITH_EXCEPTION` + exception body from a caller without `override` → 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED`; period stays `OPEN`; no exception audit row.
- `ADVISORY` + BLOCKING checks → closes; `bankReconciliationReady = false`; the readiness summary lands in the `PERIOD_CLOSE` audit `newValue`.
- Coverage lag (e.g. 31 on a mid-month cycle) → the `STATEMENT_COVERAGE` / `RECONCILIATION_APPROVED` thresholds move back by the lag, the straddling window no longer blocks, and `COVERAGE_LAG_APPLIED` WARNING reports the shortfall (§5.2, §5.3, §5.7 option c).
- Account without any statement (no baseline) → only `STATEMENT_COVERAGE` reports it; the `UNEXPLAINED_*` checks are not evaluated (§5.3, §8.4).
- Period reopened, a JE posted inside a `FINALIZED` window (S5 invalidates) → re-close blocked by `RECONCILIATION_INVALIDATED` until the superseding reconciliation is `FINALIZED` (§5.6).
- Approval landing after `closedAt` → `RECONCILED_AFTER_CLOSE` INFO on the next readiness read (§5.1, §8.4).
- 2360 reclassified to zero by a JE before period end, or non-zero only at period end → no `CLEARING_BALANCE_AGING` (§8.4).
- Policy PUT with a missing field, an unknown enum value, a negative lag or threshold, or a blank justification → 400 `VALIDATION_ERROR`; a 1–9 character justification → 400 `JUSTIFICATION_REQUIRED` (§5.2).
- No `OTHER` adjustment ever posted → `CLEARING_BALANCE_AGING` not evaluated; the `BANK_RECONCILIATION` / `OTHER` mapping unconfigured or changed at `periodEndDate` → the check still reads the accounts the JEs posted to (§5.3).
- `LATE_BANK_TRANSACTIONS` is implemented but no phase-1 path produces its input; its tests belong to the phase-2 connector stories (§5.5, D10).

## Acceptance criteria
1. **Given** policy `REQUIRED_WITH_EXCEPTION`, account 1000 with a `FINALIZED` reconciliation reaching the period end and no unexplained items **When** readiness is read **Then** `ready = true`, `blockingCount = 0`, `reconciledFrontier ≥ periodEndDate`, and the account's `baselineDate` is reported (§5.3, I1).
2. **Given** the same policy and an `IN_PROGRESS` reconciliation ending inside the period **When** close is called without a body **Then** 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with one `fieldErrors` entry `unreconciledGlAccountIds` = 1000's id and a message naming `RECONCILIATION_IN_FLIGHT` (§5.9).
3. **Given** AC 2 **When** a caller holding `close` and `override` closes with a `bankReconciliationException.justification` ≥ 10 characters **Then** `CLOSED`; audit `PERIOD_CLOSE_BANKREC_EXCEPTION` holds the justification and the readiness snapshot in `oldValue`; response `bankReconciliationException = true` (§5.2, I5, D4).
4. **Given** AC 2 and a caller without `override` **When** closing with an exception **Then** 403 `PERIOD_CLOSE_EXCEPTION_NOT_PERMITTED` and the period stays `OPEN` (§5.2).
5. **Given** policy `REQUIRED` **When** closing with an exception **Then** 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` (§5.2).
6. **Given** policy `ADVISORY` and BLOCKING checks **When** closing **Then** `CLOSED`, `bankReconciliationReady = false`, and readiness still lists every check (§5.3).
7. **Given** a covering `FINALIZED` reconciliation whose `approvedGlEndingBalance` differs from the live as-of balance **Then** `BALANCE_AGREEMENT` is BLOCKING even if S5's invalidation did not fire (§5.3, I1).
8. **Given** an `OPEN` deposit in transit and an outstanding check **When** readiness is read **Then** neither appears under `UNEXPLAINED_LEDGER_LINES`; both are listed with their sum; an item older than 90 days adds only `OUTSTANDING_ITEMS_AGING` WARNING; **Given** an `OPEN` `OTHER_LEDGER_TIMING` item older than 90 days not reaffirmed in the covering reconciliation **Then** it counts under `UNEXPLAINED_LEDGER_LINES` (§5.4, §3.6, I2).
9. **Given** an account whose baseline moved to 2026-10-01 **When** readiness for 2026-08 is read **Then** it reports `baselineDate` = the August baseline while `GET /bank-accounts` shows `reconciliationBaselineDate = 2026-10-01` (§5.3, §8.4).
10. **Given** an account whose baseline is 2026-09-01 with unmatched POSTED lines dated in August **When** readiness for 2026-09 is read **Then** `UNEXPLAINED_LEDGER_LINES` does not report them [M] — drop the lower bound and they appear; **Given** an account without any statement **Then** only `STATEMENT_COVERAGE` reports it; **Given** an unreviewed `POSSIBLE_DUPLICATE` dated after the baseline **Then** `UNEXPLAINED_BANK_TRANSACTIONS` is BLOCKING (§5.3, §8.4). **Given** a JE on the account dated inside 2026-09 and reversed inside 2026-09, its original line having matched a bank row **Then** neither line of the reversal pair appears under `UNEXPLAINED_LEDGER_LINES` while the bank row appears under `UNEXPLAINED_BANK_TRANSACTIONS` — the same answer approval gives (§3.7, §5.3).
11. **Given** a bridge or `OTHER` adjustment leaves 2360 at −45.67 both at `periodEndDate` and at `periodEndDate − 90` **When** readiness is read **Then** the top-level `checks[]` holds `CLEARING_BALANCE_AGING` WARNING listing the adjustment [M] — compare only the period-end balance and a fresh adjustment then warns; it never blocks under any policy; with no `OTHER` adjustment ever posted it is not evaluated, and changing the `OTHER` mapping does not hide the aged 2360 balance (§4.7, §5.3, §8.4, D2).
12. **Given** the period was reopened and a posting invalidated the covering reconciliation **When** re-closing **Then** blocked by `RECONCILIATION_INVALIDATED` until a superseding reconciliation is `FINALIZED`; the invalidated one stays readable (§5.6).
13. **Given** `BANK_REC_CLOSE_SCOPE = BANK_CASH_SUBTYPE` **Then** 1090 Undeposited Funds, 1200 AR and 2000 AP never appear in `accounts[]` (D5).
14. **Given** a PUT by a `hard_lock` holder that changes only `closeCoverageLagDays` **Then** exactly one `BANK_REC_POLICY_SET` row (`ACCOUNTING_CONFIGURATION`) with the old and new lag and the justification [M]; a missing field → 400; `otherApprovalThreshold: null` clears the setting (no row) and the next `OTHER` needs `approve`; the next readiness read uses the new policy; a `view`-only caller can read but not change it (§5.2, §5.9, §6.4, §8.4).
