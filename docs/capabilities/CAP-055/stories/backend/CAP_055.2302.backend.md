## Issue Body

Part of the manual bank reconciliation specification — durion `domains/accounting/SPEC-manual-bank-reconciliation.md` (§7.1 story S3; PR louisburroughs/durion — https://github.com/louisburroughs/durion/pull/519). Capability CAP:055 (louisburroughs/durion#55). Domain: accounting.

## Story Intent
**As a** preparer (holder of `accounting:reconciliation:adjust`) **I want** to upload a bank statement file, see it parsed under my column mapping and sign convention, correct or skip bad rows, confirm that `opening + Σ = closing` before anything is committed, and commit it as a statement through the same intake as a manual entry **so that** a whole file is never rejected for one bad row, a whole-file duplicate is refused at the door, the raw file is retained as audited evidence, and the reconciliation core stays unaware that a CSV ever existed.

## Scope

## Functional behaviour
1. EXISTING kept — `GET /adjustment-types`, `GET`, `GET /{id}`, `match`, `unmatch`, `adjustments`, `finalize`, `report`, `audit` on `/reconciliations` are untouched. EXISTING retired — `POST /reconciliations/import` (D14; pre-production policy, no shim). The F2 parser behaviours are carried into the new parser: header row auto-detected, ISO and US dates, `$`, thousands separators, parentheses negatives, quoted fields with embedded commas and escaped quotes, raw or base64 text.
2. PROPOSED — upload `POST /bank-imports`: multipart `file` + `meta` JSON, or JSON with base64 `content`; body carries `glAccountId`, `requestId` (UUIDv7), `formatCode`, `fileName`, the statement header (`startDate`, `endDate`, `openingBalance`, `closingBalance`, `statementRef?`), optional `columnMapping`, `signConvention`, `dateFormat`, `decimalFormat`, `encoding`, `delimiter`, `gapAcknowledgement`. Steps: account reconcilable and `BANK_CASH` (`ACCOUNT_NOT_RECONCILABLE`, D5); currency against the profile, or `USD` while none exists (`CURRENCY_NOT_SUPPORTED`, D18, §3.1); store bytes in `bank_import_file`, hash SHA-256; same `fileSha256` already COMMITTED for the account → 409 `IMPORT_FILE_ALREADY_COMMITTED` naming the earlier `importId` and `statementId`; header pre-checks against COMMITTED statements so the preparer learns before mapping rows: `STATEMENT_PERIOD_OVERLAP`, then the `gapAcknowledgement` checks in the §4.2 order — a present value blank → 400 `VALIDATION_ERROR`, 1–9 characters → 400 `JUSTIFICATION_REQUIRED` (D15); absent on a statement that does not continue (always the account's first) → 422 `STATEMENT_NOT_CONTIGUOUS`; present on one that does continue → 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE` (D17); the result is shown in the preview; parse with the account's saved mapping (or the request's, or the defaults `date, description, amount, reference`); if the header row cannot be mapped → status `UPLOADED`, `mappingRequired = true`, preview shows raw columns; else `VALIDATED` with the preview summary. Response 201 `BankImportResponse` (counts, header, mapping, status, outcome ids, `version`). Replay with the same `requestId` → the original import with `replayed: true`; a different payload → 409 `IDEMPOTENCY_CONFLICT`.
3. PROPOSED — parse (every parse recomputes all counts, §3.3): each file row becomes a `BankImportRow` with `rawValues` (never rewritten), parsed `date` / `signedAmount` / `description` / `reference` / `checkNumber` / `sourceTransactionId`, `fingerprint` (the §3.2 formula, computed against the account's existing transactions and the other rows of the file) and `rowStatus`: `REJECTED` with `rejectionCode` ∈ {`DATE_UNPARSEABLE`, `AMOUNT_UNPARSEABLE`, `AMOUNT_ZERO`, `AMOUNT_AND_DEBIT_CREDIT_BOTH`, `REQUIRED_COLUMN_MISSING`, `DATE_OUTSIDE_STATEMENT`} and `rejectionDetail`; `OUT_OF_WINDOW` when the date falls outside the header window (§4.5); `POSSIBLE_DUPLICATE` on a fingerprint collision; else `PARSED`. Sign conventions: `SIGNED_AMOUNT` (default, positive = cash in), `SIGNED_AMOUNT_INVERTED`, `DEBIT_CREDIT_COLUMNS` (credit = cash in, debit = cash out) — normalized to the core convention at parse time (§2.2 "the adapter normalizes formats"). The preview returns the first five rows with their resulting sign and the running total against the header so `opening + Σ = closing` is visible before commit (§4.4).
4. PROPOSED — `PUT /{importId}/mapping` re-parses every row with the new `columnMapping` / `signConvention` / options and re-enters `VALIDATED`; `saveAsAccountDefault = true` stores the mapping on `bank_account_profile.default_column_mapping` — on an account without a profile the intake creates it at commit with that mapping (§3.1). `PUT /{importId}/rows/{rowId}` with `correctedValues` → `CORRECTED` (`correctedBy/At`); with `skip = true` and `reason` → `SKIPPED`; a `POSSIBLE_DUPLICATE` row is confirmed distinct (→ `PARSED`) or skipped as a duplicate; an `OUT_OF_WINDOW` row is skipped or the header is widened (which re-runs the overlap check).
5. PROPOSED — `POST /{importId}/commit` `{startReconciliation?, duplicateDecisions?: [{rowNumber, decision}]}`: preconditions — no `REJECTED` rows; no `OUT_OF_WINDOW` rows unless `SKIPPED`; `POSSIBLE_DUPLICATE` rows either decided here or committed as `POSSIBLE_DUPLICATE` bank transactions for later review (§4.4); E1 holds (`fieldErrors[activityTotal] = "opening + activity = <x>, closing = <y>"`); otherwise 422 `IMPORT_NOT_COMMITTABLE` with `fieldErrors` `rows[<rowNumber>]` and/or `activityTotal`. The `gapAcknowledgement` checks run again against the then-previous COMMITTED statement (it can change after upload, §4.2) and answer their own codes (`STATEMENT_NOT_CONTIGUOUS`, `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`). On success, in one transaction: build `BankTransactionsObservedV1` from the non-skipped rows (`sourceRowNumber = rowNumber`, `sourceTransactionId` when the file carries one, `settlementState = POSTED`, `change = ADDED`), call `BankTransactionIntake.accept` with the upload's `gapAcknowledgement` (the intake stores it on the statement and, for an acknowledged statement, sets the baseline and writes `BANK_ACCOUNT_BASELINE_SET`, §3.1), mark rows `COMMITTED` with their `bankTransactionId`, set `statementId`, status `COMMITTED`, `committedAt/By`, audit `BANK_IMPORT_COMMIT`. Response 200 `{statementId, bankTransactionCount, possibleDuplicateCount, reconciliationId?}`; a second commit answers 200 with the same result (idempotent on the import).
6. PROPOSED — `POST /{importId}/discard` `{reason}` → `DISCARDED` (terminal) from `UPLOADED` / `VALIDATED`; the raw file stays until `retention_until`. A mutation of a `COMMITTED` import → 409 `IMPORT_ALREADY_COMMITTED`; of a `DISCARDED` import → 409 `IMPORT_DISCARDED` (§4.4, §4.10).
7. PROPOSED — retention job: nightly, per active tenant, hard-deletes `bank_import_file.file_bytes` where `retention_until < today`, keeps the `bank_import` row and the `bank_import_row` rows (accounting records, §6.4). Download: returns the stored bytes with `contentType`/`fileName`, only to `accounting:reconciliation:approve`, always audited.
8. PROPOSED — `splitAt` (§4.4, §5.7): the upload or mapping body may carry `splitAt[]` dates inside the header window plus a keyed `closingBalance` for every segment but the last (the file carries only the final closing balance); commit creates one statement per segment through the intake, each segment's opening balance being the previous segment's keyed closing balance, so E1 and E2 hold per segment and the earlier segment can be reconciled as its own window. When a manual-entry interim statement already covers the first part (§5.7 b), the bank's file is instead imported with the header window after the interim and the interim's closing balance as opening balance; its earlier rows are `OUT_OF_WINDOW` and skipped with a reason, and E1 on the header then proves the interim was complete.

## Business rules and invariants
- The whole file is never rejected for one bad row (G8, §4.4); `rawValues` are never rewritten (§3.3); corrections and skips are attributed and reasoned.
- Nothing here is accounting truth until `commit` (§3.3); `COMMITTED` and `DISCARDED` are terminal (§3.8).
- Whole-file duplicate: `fileSha256` unique per account among COMMITTED imports (§3.3, S1 partial unique) → `IMPORT_FILE_ALREADY_COMMITTED`.
- E1 is enforced at commit by the intake and pre-checked here; there is no override — "the file or the header is wrong" (§4.4). E2 (incl. the first-statement acknowledgement), U1, U2, U3, R1–R3 and the baseline write are the intake's (S2); the adapter never bypasses the port (§2.1 "may depend on `internal/bankrec/intake` (the port only)").
- A re-import of an already COMMITTED window without `supersedesStatementId` is refused (`STATEMENT_ALREADY_IMPORTED`); a corrected re-import names the statement it supersedes (§4.9 path 3, S5).
- `formatCode` is never visible to the core (§3.3); the core never imports a format library (§2.1 walls).
- Justification minimum 10 characters for `gapAcknowledgement` and for `reason` on skip/discard (D15); an acknowledgement is accepted only on a statement that does not continue the previous one (§3.1). `@Version` on `bank_import` → 409 `OPTIMISTIC_LOCK` (§6.3).

## State model
`BankImport` (§3.8): `UPLOADED → VALIDATED` (parse with a mapping; re-entered on every mapping change or row correction) · `VALIDATED → COMMITTED` (no `REJECTED` rows, E1 holds, no un-skipped `OUT_OF_WINDOW` rows, no unresolved header conflicts) · `UPLOADED | VALIDATED → DISCARDED` (reason). `COMMITTED`, `DISCARDED` terminal.
`BankImportRow` (§3.8): `REJECTED → CORRECTED` (edit) or `→ SKIPPED` (reason) · `POSSIBLE_DUPLICATE → PARSED` (confirm distinct) or `→ SKIPPED` (confirm duplicate) · `OUT_OF_WINDOW → SKIPPED` or back to `PARSED` when the header is widened without overlap · every non-skipped row `→ COMMITTED` at commit.

## Alternate and error flows
- Unreadable file (wrong encoding, zero rows, binary) → 422 `STATEMENT_IMPORT_FAILED` with a message naming the cause; nothing persisted beyond the audit row (§4.3).
- Header names differ from the defaults → `UPLOADED`, `mappingRequired = true`; `PUT /mapping` → `VALIDATED` (§4.3).
- The account's first file uploaded without `gapAcknowledgement` → 422 `STATEMENT_NOT_CONTIGUOUS` at the header pre-check; with it the import proceeds and the commit moves the baseline to the statement's `startDate` (§4.2, §3.1, §8.2).
- A contiguous file uploaded with a valid acknowledgement → 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`; with a 5-character one → 400 `JUSTIFICATION_REQUIRED`; a previous statement committed between upload and commit that makes the header contiguous (or not) → the commit re-check answers accordingly (§4.2, §8.2).
- A file declaring `EUR` on an account without a profile → 422 `CURRENCY_NOT_SUPPORTED` (§3.1, §8.2).
- 240 rows, 3 bad dates → 237 `PARSED`, 3 `REJECTED` with line numbers; commit → 422 `IMPORT_NOT_COMMITTABLE` `fieldErrors[rows[n]]` until corrected (§4.4, §8.2).
- Header closing 10,000.00, rows sum to 9,985.00 → 422 `IMPORT_NOT_COMMITTABLE` `fieldErrors[activityTotal] = "opening + activity = 9985.00, closing = 10000.00"`; no override (§4.4).
- Re-download of September including the last three days of August already committed → those rows `OUT_OF_WINDOW` and must be skipped; widening the header to 08-29 → `STATEMENT_PERIOD_OVERLAP` (§4.5).
- Same file uploaded again after commit → 409 `IMPORT_FILE_ALREADY_COMMITTED` with the earlier ids (§4.3); same window from a different file → 409 `STATEMENT_ALREADY_IMPORTED` at commit (§8.2).
- Commit of a `DISCARDED` import → 409 `IMPORT_DISCARDED`; mapping change on a `COMMITTED` one → 409 `IMPORT_ALREADY_COMMITTED`; second commit of a `COMMITTED` import → 200, same result.
- Wrong sign convention → the preview running total does not tie to the header; the preparer switches convention and every row re-parses (§8.2).
- Download after the retention purge → 404; the metadata row remains and carries `retentionUntil` (§6.1).

## Acceptance criteria
1. **Given** a CSV whose header names differ from the defaults **When** uploaded **Then** the import is `UPLOADED` with `mappingRequired = true` and the preview shows raw columns; **When** `PUT /mapping` supplies a mapping **Then** it is `VALIDATED` (§4.3).
2. **Given** 240 rows of which 3 fail date parsing **When** previewed **Then** 237 `PARSED`, 3 `REJECTED` with `DATE_UNPARSEABLE` and line numbers; **When** the 3 are corrected and totals tie **Then** commit succeeds and 240 `bank_transaction` rows exist with `sourceRowNumber` 1..240 and `rawValues` unchanged (§4.4, §8.2).
3. **Given** the header says closing 10,000.00 and the rows sum from opening to 9,985.00 **When** committed **Then** 422 `IMPORT_NOT_COMMITTABLE` with `fieldErrors[activityTotal]` and nothing committed (E1, §4.4).
4. **Given** a `DEBIT_CREDIT_COLUMNS` file and a `SIGNED_AMOUNT_INVERTED` file **When** parsed under their conventions **Then** every stored `signedAmount` follows the core convention (positive = cash in) and the preview running total ties to the header only under the right convention (§4.4, §8.2).
5. **Given** a file already COMMITTED for the account **When** the same bytes are uploaded again **Then** 409 `IMPORT_FILE_ALREADY_COMMITTED` naming the earlier `importId` and `statementId` (§4.3, §8.2).
6. **Given** a committed import **When** `POST /commit` is called again **Then** 200 with the identical result; **Given** a `DISCARDED` import **When** committed **Then** 409 `IMPORT_DISCARDED` (§4.4).
7. **Given** two identical $5.00 rows in one file **When** previewed **Then** both are `POSSIBLE_DUPLICATE`; **When** committed with `duplicateDecisions` `DISTINCT` for both **Then** both are `UNMATCHED` bank transactions (§4.5, §8.2).
8. **Given** an import older than `file-retention-days` **When** the retention job runs **Then** `bank_import_file.file_bytes` is deleted, the `bank_import` and `bank_import_row` rows remain, and the job touches only the current tenant's rows per iteration (§6.4, ADR-0062 §8, D13).
9. **Given** a class in `internal/bankfeed/file/` that imports `internal/bankrec/repository/` or `internal/bankrec/service/` **When** ArchUnit runs **Then** the build fails; **Given** `org.apache.commons.csv` (if used) imported from `..bankrec..` **Then** the build fails (§2.1, §8.4 [M]).
10. **Given** `POST /v1/accounting/reconciliations/import` **When** called after this story **Then** 404 (route removed) and `ACCOUNTING_RECONCILIATION_IMPORT` is no longer registered; the regenerated SDK has no `importReconciliation` (D14).
11. **Given** an account with no COMMITTED statement **When** its first file is uploaded without `gapAcknowledgement` **Then** 422 `STATEMENT_NOT_CONTIGUOUS`; **Given** a contiguous file **When** uploaded with a valid acknowledgement **Then** 422 `STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`, with a 5-character one 400 `JUSTIFICATION_REQUIRED`; **When** uploaded and committed with one **Then** in the commit transaction the statement carries the acknowledgement, `reconciliation_baseline_date` equals its `startDate` and one `BANK_ACCOUNT_BASELINE_SET` row exists; a commit failing E1 leaves neither (§3.1, §4.2, §4.4 "commit is one transaction", §8.2).

## Decisions applied
| Dn | Decision (2026-09-28) | Effect on this story |
| --- | --- | --- |
| D1 | The file-import adapter lives inside `pos-accounting` behind the contract; provider connectors are separate modules in phase 2. | `internal/bankfeed/file/` runs in-process through `BankTransactionIntake`, no Kafka hop. |
| D5 | Bank accounts are `reconcilable` GL accounts of subtype `BANK_CASH`. | `reconcilable` + `BANK_CASH` checked at upload. |
| D13 | Raw files stay in accounting, encrypted at rest by the database, retention configurable (default 7 years). | `bank_import_file`, `file-retention-days` default 2,555, audited download, per-tenant purge job; no application cipher. |
| D14 | `POST /v1/accounting/reconciliations/import` is retired, no composite shim. | Route, event id, DTO, service method and tests removed; the SDK loses `importReconciliation`. |
| D15 | Justification minimum is 10 characters. | `gapAcknowledgement` and skip/discard reasons require ≥ 10. |
| D17 | Gaps are allowed with a `gapAcknowledgement`; overlaps are always refused. | `gapAcknowledgement` required on a non-contiguous upload (always the account's first), refused on a contiguous one (`STATEMENT_GAP_ACKNOWLEDGEMENT_NOT_APPLICABLE`), checked at upload and commit, passed to the intake, which moves the baseline (S2). |
| D18 | A currency different from the profile is refused; `USD` is the only ledger currency. | `CURRENCY_NOT_SUPPORTED` at upload, against `USD` while the account has no profile. |
