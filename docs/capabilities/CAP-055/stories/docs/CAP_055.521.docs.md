## Functional behaviour
EXISTING documentation state (§1.4): README lists `FLOAT_ADJUSTMENT` (G1); `ERROR_CODES.md` mis-describes `RECONCILIATION_NOT_BALANCED` and `STATEMENT_IMPORT_FAILED` and omits three thrown codes (G10); `PERMISSION_TAXONOMY.md` §11 lists six keys the code does not use (G11); story #187 and its wireframe contradict the backend (G12); `accounting-questions.md` assumes a bank-account entity and a `jel.reconciled` column that do not exist (G13); justification length differs between guides (G14); `BACKEND_API_REFERENCE.generated.md` predates periods and reconciliation; `DOMAIN_NOTES.md` l.730 lists reconciliation as a known gap.

PROPOSED process:
1. Each S1–S7 PR carries the rows marked for it; the PR body names the row numbers touched. S9 is not one PR: it is the standing checklist plus a final sweep PR that closes any row still open after S7.
2. After every merged controller, DTO, `@Operation` / `@Schema`, `@PreAuthorize`, `permissions.yaml` or `openapi.yaml` change: `gh workflow run api-artifacts-sync.yml --repo louisburroughs/durion-positivity-backend --ref <branch> -f modules="pos-accounting pos-domain-events"`; merge the PR it opens in each repo.
3. After every `.business-rules/` or domain `index.md` change: regenerate the catalog, `--check` before push, log entry.
4. The final sweep verifies that every EXISTING / NEW code of §4.10, every `@EmitEvent` id of §3.10, every permission of §6.2, every endpoint of §6.1 and every configuration key and property (`BANK_REC_CLOSE_POLICY`, `BANK_REC_CLOSE_SCOPE`, `BANK_REC_CLOSE_COVERAGE_LAG_DAYS`, `pos.accounting.bankrec.match.date-window-days`, `pos.accounting.bankrec.outstanding.aging-warning-days`, `pos.accounting.bankrec.import.file-retention-days`; configuration key `BANK_REC_ALLOW_SELF_APPROVAL`) appears in the README and the guides exactly as the code spells it.

## Business rules and invariants
- Documentation states code truth, not intent: an entry is written only after the behaviour is merged; every rule the spec marks "(pending Dn)" stays marked in the guides until the owner rules (§9 preamble, §7.1 gating).
- One condition, one code (ADR-0017 §2): `ERROR_CODES.md` entries mirror §4.10 verbatim, status included.
- Permission names are `domain:resource:action` snake_case (CLAUDE.md); the taxonomy lists only registered keys.
- Generated artifacts — `openapi.yaml`, SDKs, tarballs, `BACKEND_API_REFERENCE.generated.md`, `knowledge-catalog/` — are never hand-edited.
- `workorder` is one word wherever it appears; no `organizationId` (CLAUDE.md); Markdown per `.claude/instructions/markdown.md`.

## State model
None. A checklist row is open until its named story merges and the row's document matches the code.

## Alternate and error flows
- A story merges without its rows → the sweep PR adds them and links the story; the row stays open in the checklist until then.
- `API Artifacts Sync` fails the frontend tests against the regenerated SDK → fix in the frontend PR the workflow opened; never patch a tarball by hand.
- Catalog `--check` fails → curate the source (frontmatter, `.business-rules/` guide, domain `index.md`) and rerun; never edit entries.
- An owner ruling on D2–D5 arrives mid-stream → row 8 (`AD-016…`) and row 4's "Open Questions" move in the same PR that applies the ruling to code.
- A documented code, key or id disagrees with the merged code → the document is wrong by definition (§1.4 pattern); fix the document, never add a shim.
