## Business rules and invariants
- Documentation states code truth, not intent: a behaviour entry is written only after the behaviour is merged. Decisions are different: D1–D22 were ratified on 2026-09-28 (§9), so the guides state them as decided — never as "pending" or "recommended" — and the decision rows land without waiting for code.
- The D2 entry and the plan annotation supersede exactly one sentence of ruling (1) of 2026-07-20; they must not restate the rest of the ruling as superseded (§1.5 C1, §9 D2).
- One condition, one code (ADR-0017 §2): `ERROR_CODES.md` entries mirror §4.10 verbatim, status included.
- Permission names are `domain:resource:action` snake_case (CLAUDE.md); the taxonomy lists only registered keys.
- Generated artifacts — `openapi.yaml`, SDKs, tarballs, `BACKEND_API_REFERENCE.generated.md`, `knowledge-catalog/` — are never hand-edited.
- `workorder` is one word wherever it appears; no `organizationId` (CLAUDE.md); Markdown per `.claude/instructions/markdown.md`.

## State model
None. A checklist row is open until its named story merges and the row's document matches the code; the decision rows (8, 14, row 4's resolved questions) are open until their PR merges.

## Alternate and error flows
- A story merges without its rows → the sweep PR adds them and links the story; the row stays open in the checklist until then.
- `API Artifacts Sync` fails the frontend tests against the regenerated SDK → fix in the frontend PR the workflow opened; never patch a tarball by hand.
- Catalog `--check` fails → curate the source (frontmatter, `.business-rules/` guide, domain `index.md`) and rerun; never edit entries.
- A decision is reopened by the platform owner → only the sections that cite it reopen (§9 preamble); rows 4, 8 and 14 and every guide entry citing that Dn are updated in the same PR that applies the new ruling to code.
- A documented code, key or id disagrees with the merged code → the document is wrong by definition (§1.4 pattern); fix the document, never add a shim.
