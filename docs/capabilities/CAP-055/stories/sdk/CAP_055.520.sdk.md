## Story Intent
**As the** platform owner, **I want** an SDK-driven integration suite that walks the full manual bank reconciliation flow through the gateway as two users, plus an accelerated-year simulator that reconciles every bank account monthly before each period close, **so that** the E1–E4 identities, the reconciliation baseline, separation of duties, invalidation and close readiness are proven against a running stack, not only in module tests (§8.4).

## Scope
### In scope
- The suite for the §8.4 "SDK integration" bullet: ledger activity → import (the account's first statement, acknowledged, setting the baseline) → auto-match → outstanding item → bank fee → submit → approve as a second user → balance assertion → readiness → close → reverse a matched JE → `INVALIDATED` and readiness block.
- The accelerated-year simulator: for each in-scope bank account, twelve monthly statements generated from the account's own ledger activity plus injected fees, interest and timing items; a reconciliation approved before each period close; the chain invariant asserted.
- Test principals: a preparer (`accounting:reconciliation:adjust`, `accounting:reconciliation:view`, `accounting:period:view`) and an approver / controller (`accounting:reconciliation:approve`, `accounting:period:close`, `accounting:period:override`) in one tenant (§6.2, D3), plus a principal of a second tenant for the isolation check.
### Out of scope (and where it lives)
- Backend and frontend behaviour (S1–S7); Vitest component tests (S7); module ITs on Testcontainers (S1–S6), which own the §8.2–§8.4 scenarios for the `OTHER` link rule, residual settlement, gap bridge, threshold, reaffirmation, gap clearance, readiness lower bound and clearing-account aging; phase-2 feed simulation (§7); documentation (S9).

## Functional behaviour
EXISTING: the SDK exposes F2's `importReconciliation`, `matchReconciliation`, `unmatchReconciliation`, `addReconciliationAdjustment`, `finalizeReconciliation`, `getReconciliationReport`, `getReconciliationAudit`; `listAccountingPeriods`, `closeAccountingPeriod`, `reopenAccountingPeriod`; `getGLAccountBalance` (`GET /v1/accounting/gl-accounts/{glAccountId}/balance` — the current balance over `POSTED` entries of any date, no as-of parameter, `asOfDate` = the request instant: `GLAccountServiceImpl.java` l.329-346, `JournalEntryLineRepository.java` l.45-52, so it is never the reference for a reconciliation assertion, §3.7); the settlement and AP-payment operations that create cash lines on `1000 Cash` (§1.2). No reconciliation suite exists (§1.1 "Tests").

PROPOSED — suite steps (each names the §6.1 operation and the assertion):
1. Seed check: `GET /v1/accounting/bank-accounts` lists `1000 Cash` (S1 seed fix, G7) with null `coverageFrontier` / `reconciledFrontier` and no `reconciliationBaselineDate` on a fresh tenant (no statement committed yet, §3.1).
2. Ledger activity on the bank account inside the statement month through the existing flows (§1.2): a processor settlement payout (debit to cash) and an AP payment (credit to cash); the reference balance for every later assertion is the reconciliation's own as-of balance at `statementEndDate`, served live as the review's `glEndingBalance` (§3.7) — not `getGLAccountBalance`, which has no as-of date (G15 is pinned by S4's module test, §3.7, §8.1).
3. Generate the month's statement: rows for the two movements plus a bank-fee row the ledger lacks; `closingBalance` satisfying E1. `POST /v1/accounting/bank-imports` (`requestId` UUIDv7) without `gapAcknowledgement` → 422 `STATEMENT_NOT_CONTIGUOUS` (the account's first statement, §8.2); again with a `gapAcknowledgement` (≥ 10 characters) → `VALIDATED`; `POST /{importId}/commit {startReconciliation: true}` → `statementId`, `reconciliationId`; `GET /bank-accounts` → `reconciliationBaselineDate` = the statement's `startDate` (§3.1, D17).
4. `POST /reconciliations/{id}/auto-match` → the two exact rows are `PROPOSED`, never `ACCEPTED` (M6, D12); accept them.
5. Post a deposit JE dated in the month with no bank row; `POST /{id}/outstanding-items {glLineId, itemKind: DEPOSIT_IN_TRANSIT}` → `OPEN`; no JE is created (O3).
6. `POST /{id}/adjustments {type: BANK_FEE, amount < 0, description, bankTransactionId, requestId}` → 201 with `journalEntryId`; the fee row becomes `MATCHED` through the `ADJUSTMENT` match; the same `requestId` again → 200 `replayed: true`, one JE (G9).
7. `GET /{id}/review` → `difference = 0`, `baselineDate` = the statement's `startDate`, `countUnexplainedBank = 0`, `countUnexplainedLedger = 0`, `openingDifference` reported under Diagnostics (§3.7), `canSubmit = true`; `POST /{id}/submit` as the preparer → `SUBMITTED`.
8. `POST /{id}/finalize` as the preparer → 403 `RECONCILIATION_SELF_APPROVAL` (D3); as the approver → `FINALIZED`; assert `approvedGlEndingBalance` equals the review's live `glEndingBalance` and `ledgerChangedSinceApproval = false` (§4.8).
9. `GET /periods/{periodCode}/close-readiness` → `ready = true`; `POST /periods/{periodCode}/close` → `CLOSED`, `bankReconciliationReady = true`, `bankReconciliationException = false`.
10. Reverse the settlement JE (the existing reverse operation, with a reason) → the reversal succeeds (D11); `GET /reconciliations/{id}` → `INVALIDATED`, `invalidationReason = LEDGER_LINE_REVERSED`, `invalidatedByJournalEntryId` set; reopen the period; readiness → `RECONCILIATION_INVALIDATED` BLOCKING; close → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with the account in `unreconciledGlAccountIds`.
11. `POST /{id}/supersede` as the approver → new `IN_PROGRESS` with `supersedesReconciliationId` and the same `baselineDate`; `GET /{id}/audit` on the old record lists the submit, approve and invalidate rows.

Simulator (§8.4): for months 1..12 of a tenant year, per in-scope bank account: (a) create cash activity through the existing flows; (b) inject a bank fee, an interest credit and one timing item — a deposit dated on the last day whose bank row falls in the next month; (c) build the statement from the ledger rows plus the bank-only rows — month 1 with a `gapAcknowledgement` (it sets the baseline), months 2–12 with `openingBalance` = previous `closingBalance`, `startDate` = previous `endDate + 1` and no acknowledgement (E2; the baseline stays put) — and `closingBalance = opening + Σ rows` (E1); (d) import, auto-match, accept, register the timing item, post the fee and interest adjustments linked to their bank rows, submit and approve as two users; (e) run readiness and close the period; (f) assert the chain invariant. Month n+1's statement carries the timing item's bank row so the item clears (§5.4).

## Business rules and invariants
- **E1** every generated statement: `openingBalance + Σ rows = closingBalance` (±0.01) (§3.1). **E2** contiguity month to month; only the first statement carries a `gapAcknowledgement` (§3.1, D17).
- **E3 / E4** at every approval: `adjustedBankBalance = adjustedBookBalance`, `|difference| ≤ 0.01`, zero unexplained bank transactions and ledger lines from the baseline (§3.7, D2); `openingDifference` is reported, never gated.
- **Chain invariant** (§8.4): across the twelve approved reconciliations the `adjustedBankBalance` chain is continuous — each approved `adjustedBankBalance` equals its `adjustedBookBalance`, and each window's `openingDifference` is within ±0.01 against its predecessor (§3.7: within the tolerance it reads as continuous).
- **Baseline** (§3.1): set once by month 1's acknowledged statement; `reconciliationBaselineDate` never moves during the simulated year.
- **M6** `auto-match` never yields `ACCEPTED` (D12). **O2** the timing item registered in month n appears in month n+1's opening and closing terms until `CLEARED`; **O3** registering it posts nothing.
- **I1 / I5** every close on the happy path reports `bankReconciliationReady = true`; the exception path is exercised only in the negative scenario and leaves `PERIOD_CLOSE_BANKREC_EXCEPTION` in the audit (§5.8).
- **G15** is decided in §3.7 (reconciliation balances count `POSTED` and `REVERSED` entries at their own dates) and pinned by S4's module test (§8.1), not by this suite.
- Separation of duties (D3): preparer and approver are distinct principals; the suite never shares a token between them.

## Data requirements
None owned by the SDK repo. The suite runs against a Compose or alpha stack with `pos-accounting` at S6 or later: seeded `BANK_RECONCILIATION` mappings (`BANK_FEE` → 6030, `INTEREST_EARNED` → 4920, EXISTING seed, §1.1), `1000 Cash reconcilable = TRUE` (S1), `BANK_REC_CLOSE_POLICY` at its default `REQUIRED_WITH_EXCEPTION` (D4), `BANK_REC_ALLOW_SELF_APPROVAL` at its default false (D3). The suite provisions its own tenant fixture (ADR-0062) and never reads another tenant's rows.

## State model
Asserted per reconciliation in the main suite: `IN_PROGRESS → SUBMITTED → FINALIZED → INVALIDATED`, then a successor `IN_PROGRESS`; in the simulator `IN_PROGRESS → SUBMITTED → FINALIZED` twelve times. Period: `OPEN → CLOSED` (then `OPEN` → blocked re-close in the negative branch). Outstanding item: `OPEN → CLEARED` across months (§3.6). Account baseline: none → month 1's `startDate`, then unchanged.

## Alternate and error flows
- Approval racing a posting inside the window (§8.4): a variant fires a JE posting while `finalize` is in flight; the outcome is `RECONCILIATION_NOT_BALANCED` or `INVALIDATED`, never a stale `FINALIZED` (I3).
- Late bank transaction (D10): not exercised — phase 1 has no path that stores a row inside a `FINALIZED` window (a file or manual row must lie inside its own window, windows never overlap, and a correction is a statement supersession), so D10 tests belong to the phase-2 connector stories (§5.5, §8.4). The suite asserts the phase-1 refusal instead (AC 7): an import whose header reaches into month n's approved window → 422 `STATEMENT_PERIOD_OVERLAP`.
- Coverage lag: with `BANK_REC_CLOSE_COVERAGE_LAG_DAYS = 31` set through the policy PUT by the controller, a mid-month statement no longer blocks close (§5.2, §5.7).
- A stack without S6 (readiness 404) → the close steps are skipped with an explicit reason, never a silent pass.

## Acceptance criteria
1. **Given** steps 1–9 **When** run as preparer then approver **Then** every assertion in the contract table holds and `approvedGlEndingBalance` equals the review's live `glEndingBalance` — the reconciliation's as-of balance at `statementEndDate` — with `ledgerChangedSinceApproval = false` (§8.4, §3.7, E3).
2. **Given** the account's first statement **When** imported without then with a `gapAcknowledgement` **Then** 422 `STATEMENT_NOT_CONTIGUOUS`, then commit, and `reconciliationBaselineDate` equals the statement's `startDate` (§3.1, §8.2).
3. **Given** step 8 as the preparer **Then** 403 `RECONCILIATION_SELF_APPROVAL` (§4.9, D3).
4. **Given** the same adjustment `requestId` twice **Then** exactly one JE exists and the second answer is `replayed: true` (§6.3, G9).
5. **Given** step 10 **Then** the reconciliation is `INVALIDATED` with the reversing `journalEntryId`, and re-close is blocked by `RECONCILIATION_INVALIDATED` until the superseding reconciliation is `FINALIZED` (§5.5, §5.6).
6. **Given** the twelve-month simulation **Then** every month closes with `bankReconciliationReady = true`, the timing item registered in month n is `CLEARED` in month n+1, the baseline never moves after month 1, every `openingDifference` is within ±0.01, and the `adjustedBankBalance` chain is continuous across the year (§8.4, O2, §3.7).
7. **Given** no phase-1 path **Then** no row of the suite or the simulator ever carries `arrivedAfterApproval = true`, and an import overlapping an approved window answers 422 `STATEMENT_PERIOD_OVERLAP` (§5.5, §8.4, D10).
8. **Given** a second tenant's principal **When** it lists statements, transactions, reconciliations and imports **Then** it sees none of the suite's rows (§8.4 "Security").

## Audit and observability
The suite reads `GET /reconciliations/{id}/audit` and asserts the stored operations `RECONCILIATION_SUBMIT`, `RECONCILIATION_APPROVE`, `RECONCILIATION_INVALIDATE`, and in the exception branch that the close response reports `bankReconciliationException = true` (§4.9, §5.9). It emits nothing itself.

## Tests
- This story is tests. One spec per §8.4 bullet it owns — accounting flow, reversal and invalidation, late transaction, concurrency, simulator — each idempotent per tenant fixture and tagged so CI runs the simulator nightly rather than per PR.
- Suite-level guards **[M]**: run with the approver token replaced by the preparer's → AC 3 must fail; run with an `auto-match` that accepts → the `PROPOSED` assertion of step 4 must fail.
- Contract coupling: the suite compiles against the regenerated SDK; a missing operation is a build failure — the intended signal that `API Artifacts Sync` was not run.

## Dependencies
- Blocked by: S6 (readiness, close body) and S7 (the UI the suite mirrors), both merged so the regenerated SDK carries every operation; `API Artifacts Sync`; two provisioned principals with the roles of §6.2 (CONTROLLER holds `approve`; the accountant role holds `adjust`).
- Blocks: nothing in phase 1; the simulator is the regression bed for phase 2 (§7.6 step 3: approved reconciliations are untouched by feed backfill).
- Platform: `API Artifacts Sync`; ADRs 0013 (UUIDv7 `requestId`), 0017 (codes asserted), 0018, 0044, 0047 (reversal path), 0049, 0062 (tenant fixture).

## Decisions applied
| Dn | Decision (2026-09-28) | Effect on this story |
| --- | --- | --- |
| D2 | Matching-complete approval from the account baseline; `openingDifference` is a never-blocking diagnostic. | Zero unexplained counts asserted before submit; pre-baseline lines excluded; chain invariant uses `\|openingDifference\| ≤ 0.01`. |
| D3 | Preparer ≠ approver enforced by default. | Two principals; self-approval refused with the default switch. |
| D4 | Close policy default `REQUIRED_WITH_EXCEPTION`. | The stack runs at the default; the exception branch uses `close` + `override`. |
| D5 | Readiness scope is the `BANK_CASH` subtype. | `1000 Cash` is the in-scope account. |
| D7 | Adjustments take the explaining date when its period is OPEN. | Fees and interest are dated in the statement month while it is OPEN; the simulator never posts into a CLOSED month. |
| D10 | Late bank arrivals are flagged and resolved in the next window; only phase-2 feeds produce them. | Not tested at SDK level in phase 1; only the phase-1 overlap refusal is asserted. |
| D11 | Reversing a line in an approved reconciliation is allowed and invalidates it. | Step 10. |
| D12 | Auto-matching proposes only. | Step 4 asserts `PROPOSED`. |
| D14 | The F2 import endpoint is retired. | `importReconciliation` absent after regeneration. |
| D17 | Gaps need an acknowledgement, which moves the baseline. | The first statement carries one; the generator is contiguous afterwards. |
