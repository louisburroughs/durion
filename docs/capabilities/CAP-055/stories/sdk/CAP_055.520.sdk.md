## Story Intent
**As the** platform owner, **I want** an SDK-driven integration suite that walks the full manual bank reconciliation flow through the gateway as two users, plus an accelerated-year simulator that reconciles every bank account monthly before each period close, **so that** the E1–E4 identities, separation of duties, invalidation and close readiness are proven against a running stack, not only in module tests (§8.4).

## Scope
### In scope
- The suite for the §8.4 "SDK integration" bullet: ledger activity → import → auto-match → outstanding item → bank fee → submit → approve as a second user → balance assertion → readiness → close → reverse a matched JE → `INVALIDATED` and readiness block.
- The accelerated-year simulator: for each in-scope bank account, twelve monthly statements generated from the account's own ledger activity plus injected fees, interest and timing items; a reconciliation approved before each period close; the chain invariant asserted.
- Test principals: a preparer (`accounting:reconciliation:adjust`, `accounting:reconciliation:view`, `accounting:period:view`) and an approver / controller (`accounting:reconciliation:approve`, `accounting:period:close`, `accounting:period:override`) in one tenant (§6.2, D3), plus a principal of a second tenant for the isolation check.
### Out of scope (and where it lives)
- Backend and frontend behaviour (S1–S7); Vitest component tests (S7); module ITs on Testcontainers (S1–S6); phase-2 feed simulation (§7); documentation (S9).

## Functional behaviour
EXISTING: the SDK exposes F2's `importReconciliation`, `matchReconciliation`, `unmatchReconciliation`, `addReconciliationAdjustment`, `finalizeReconciliation`, `getReconciliationReport`, `getReconciliationAudit`; `listAccountingPeriods`, `closeAccountingPeriod`, `reopenAccountingPeriod`; `getGLAccountBalance` (`GET /v1/accounting/gl-accounts/{glAccountId}/balance`); the settlement and AP-payment operations that create cash lines on `1000 Cash` (§1.2). No reconciliation suite exists (§1.1 "Tests").

PROPOSED — suite steps (each names the §6.1 operation and the assertion):
1. Seed check: `GET /v1/accounting/bank-accounts` lists `1000 Cash` (S1 seed fix, G7) with null `coverageFrontier` / `reconciledFrontier` on a fresh tenant.
2. Ledger activity on the bank account through the existing flows (§1.2): a processor settlement payout (debit to cash) and an AP payment (credit to cash); record the as-of balance with `getGLAccountBalance`.
3. Generate the month's statement: rows for the two movements plus a bank-fee row the ledger lacks; `closingBalance` satisfying E1. `POST /v1/accounting/bank-imports` (`requestId` UUIDv7) → `VALIDATED`; `POST /{importId}/commit {startReconciliation: true}` → `statementId`, `reconciliationId`.
4. `POST /reconciliations/{id}/auto-match` → the two exact rows are `PROPOSED`, never `ACCEPTED` (M6, pending D12); accept them.
5. Post a deposit JE dated in the month with no bank row; `POST /{id}/outstanding-items {glLineId, itemKind: DEPOSIT_IN_TRANSIT}` → `OPEN`; no JE is created (O3).
6. `POST /{id}/adjustments {type: BANK_FEE, amount < 0, description, bankTransactionId, requestId}` → 201 with `journalEntryId`; the fee row becomes `MATCHED` through the `ADJUSTMENT` match; the same `requestId` again → 200 `replayed: true`, one JE (G9).
7. `GET /{id}/review` → `difference = 0`, `countUnexplainedBank = 0`, `countUnexplainedLedger = 0`, `canSubmit = true`; `POST /{id}/submit` as the preparer → `SUBMITTED`.
8. `POST /{id}/finalize` as the preparer → 403 `RECONCILIATION_SELF_APPROVAL` (pending D3); as the approver → `FINALIZED`; assert `approvedGlEndingBalance` = `getGLAccountBalance` as-of `statementEndDate`.
9. `GET /periods/{periodCode}/close-readiness` → `ready = true`; `POST /periods/{periodCode}/close` → `CLOSED`, `bankReconciliationReady = true`, `bankReconciliationException = false`.
10. Reverse the settlement JE (the existing reverse operation, with a reason) → the reversal succeeds (pending D11); `GET /reconciliations/{id}` → `INVALIDATED`, `invalidationReason = LEDGER_LINE_REVERSED`, `invalidatedByJournalEntryId` set; reopen the period; readiness → `RECONCILIATION_INVALIDATED` BLOCKING; close → 422 `PERIOD_BANK_RECONCILIATION_INCOMPLETE` with the account in `unreconciledGlAccountIds`.
11. `POST /{id}/supersede` as the approver → new `IN_PROGRESS` with `supersedesReconciliationId`; `GET /{id}/audit` on the old record lists the submit, approve and invalidate rows.

Simulator (§8.4): for months 1..12 of a tenant year, per in-scope bank account: (a) create cash activity through the existing flows; (b) inject a bank fee, an interest credit and one timing item — a deposit dated on the last day whose bank row falls in the next month; (c) build the statement from the ledger rows plus the bank-only rows with `openingBalance` = previous `closingBalance`, `startDate` = previous `endDate + 1` (E2) and `closingBalance = opening + Σ rows` (E1); (d) import, auto-match, accept, register the timing item, post the fee and interest adjustments, submit and approve as two users; (e) run readiness and close the period; (f) assert the chain invariant. Month n+1's statement carries the timing item's bank row so the item clears (§5.4).

## Business rules and invariants
- **E1** every generated statement: `openingBalance + Σ rows = closingBalance` (±0.01) (§3.1). **E2** contiguity month to month (§3.1, pending D17).
- **E3 / E4** at every approval: `adjustedBankBalance = adjustedBookBalance`, `|difference| ≤ 0.01`, zero unexplained counts, `openingDifference = 0` (§3.7, pending D2).
- **Chain invariant** (§8.4): across the twelve approved reconciliations the `adjustedBankBalance` sequence is continuous — each approved `adjustedBankBalance` equals its `adjustedBookBalance`, and each window's `openingDifference` is 0 against its predecessor.
- **M6** `auto-match` never yields `ACCEPTED` (pending D12). **O2** the timing item registered in month n appears in month n+1's E3 until `CLEARED`; **O3** registering it posts nothing.
- **I1 / I5** every close on the happy path reports `bankReconciliationReady = true`; the exception path is exercised only in the negative scenario and leaves `PERIOD_CLOSE_BANKREC_EXCEPTION` in the audit (§5.8).
- **G15 probe** before the live balance is trusted: post a debit of 100 to cash, reverse it, assert `getGLAccountBalance` as-of returns 0; a −100 result fails the suite with a message naming G15 and is reported upstream, never worked around (§8.1).
- Separation of duties (pending D3): preparer and approver are distinct principals; the suite never shares a token between them.

## Data requirements
None owned by the SDK repo. The suite runs against a Compose or alpha stack with `pos-accounting` at S6 or later: seeded `BANK_RECONCILIATION` mappings (`BANK_FEE` → 6030, `INTEREST_EARNED` → 4920, EXISTING seed, §1.1), `1000 Cash reconcilable = TRUE` (S1), `BANK_REC_CLOSE_POLICY` at its default `REQUIRED_WITH_EXCEPTION` (pending D4). The suite provisions its own tenant fixture (ADR-0062) and never reads another tenant's rows.

## State model
Asserted per reconciliation in the main suite: `IN_PROGRESS → SUBMITTED → FINALIZED → INVALIDATED`, then a successor `IN_PROGRESS`; in the simulator `IN_PROGRESS → SUBMITTED → FINALIZED` twelve times. Period: `OPEN → CLOSED` (then `OPEN` → blocked re-close in the negative branch). Outstanding item: `OPEN → CLEARED` across months (§3.6).

## Alternate and error flows
- Approval racing a posting inside the window (§8.4): a variant fires a JE posting while `finalize` is in flight; the outcome is `RECONCILIATION_NOT_BALANCED` or `INVALIDATED`, never a stale `FINALIZED` (I3).
- Late bank transaction: month n+1's file contains a row dated in month n after n's approval → `arrivedAfterApproval = true`, no invalidation, readiness `LATE_BANK_TRANSACTIONS`; matching it in month n+1 clears the warning (§5.5, pending D10).
- Coverage lag: with `BANK_REC_CLOSE_COVERAGE_LAG_DAYS = 31` set through the policy PUT by the controller, a mid-month statement no longer blocks close (§5.2, §5.7).
- A stack without S6 (readiness 404) → the close steps are skipped with an explicit reason, never a silent pass.

## Acceptance criteria
1. **Given** steps 1–9 **When** run as preparer then approver **Then** every assertion in the contract table holds and `approvedGlEndingBalance` equals `getGLAccountBalance` as-of `statementEndDate` (§8.4, E3).
2. **Given** step 8 as the preparer **Then** 403 `RECONCILIATION_SELF_APPROVAL` (§4.9, pending D3).
3. **Given** the same adjustment `requestId` twice **Then** exactly one JE exists and the second answer is `replayed: true` (§6.3, G9).
4. **Given** step 10 **Then** the reconciliation is `INVALIDATED` with the reversing `journalEntryId`, and re-close is blocked by `RECONCILIATION_INVALIDATED` until the superseding reconciliation is `FINALIZED` (§5.5, §5.6).
5. **Given** the twelve-month simulation **Then** every month closes with `bankReconciliationReady = true`, the timing item registered in month n is `CLEARED` in month n+1, and the `adjustedBankBalance` chain is continuous across the year (§8.4, O2).
6. **Given** the G15 probe **Then** the as-of balance after a post-and-reverse pair is 0, else the suite fails naming G15 (§8.1).
7. **Given** a second tenant's principal **When** it lists statements, transactions, reconciliations and imports **Then** it sees none of the suite's rows (§8.4 "Security").

## Audit and observability
The suite reads `GET /reconciliations/{id}/audit` and asserts the stored operations `RECONCILIATION_SUBMIT`, `RECONCILIATION_APPROVE`, `RECONCILIATION_INVALIDATE`, and in the exception branch that the close response reports `bankReconciliationException = true` (§4.9, §5.9). It emits nothing itself.

## Tests
- This story is tests. One spec per §8.4 bullet — accounting flow, reversal and invalidation, late transaction, concurrency, simulator — each idempotent per tenant fixture and tagged so CI runs the simulator nightly rather than per PR.
- Suite-level guards **[M]**: run with the approver token replaced by the preparer's → AC 2 must fail; run with an `auto-match` that accepts → the `PROPOSED` assertion of step 4 must fail.
- Contract coupling: the suite compiles against the regenerated SDK; a missing operation is a build failure — the intended signal that `API Artifacts Sync` was not run.

## Dependencies
- Blocked by: S6 (readiness, close body) and S7 (the UI the suite mirrors), both merged so the regenerated SDK carries every operation; `API Artifacts Sync`; two provisioned principals with the roles of §6.2 (CONTROLLER holds `approve`; the accountant role holds `adjust`).
- Blocks: nothing in phase 1; the simulator is the regression bed for phase 2 (§7.6 step 3: approved reconciliations are untouched by feed backfill).
- Platform: `API Artifacts Sync`; ADRs 0013 (UUIDv7 `requestId`), 0017 (codes asserted), 0018, 0044, 0047 (reversal path), 0049, 0062 (tenant fixture).
