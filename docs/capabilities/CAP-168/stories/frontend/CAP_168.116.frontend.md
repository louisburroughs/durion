## Issue Body

## Title
[FRONTEND] [STORY] StorePrice: Set Location Store Price Override within Guardrails

## Primary Persona
Store Manager

## Business Value
Enable Store Managers to respond to local market pricing while enforcing centrally-defined pricing guardrails and approval workflow, ensuring pricing is compliant, auditable, and safe.

---

# 2. Story Intent

## As a / I want / So that
**As a** Store Manager  
**I want** to create or update a location-specific store price override for a product  
**So that** I can compete locally while the system enforces guardrails and routes approvals when required.

## In-scope
- Moqui/Vue/Quasar frontend screens to:
  - Search/select a product and location context
  - View base price and any existing override
  - Propose an override price
  - Submit override and display backend outcome (auto-activated vs pending approval vs rejected/invalid)
  - View current override status and approval details (read-only)
  - View audit/status history for overrides (read-only)
- Frontend handling of guardrail/approval outcomes returned by backend services:
  - `ACTIVE` vs `PENDING_APPROVAL` vs validation failure
- Authorization-aware UI behavior (hide/disable actions when user lacks permission)

## Out-of-scope
- Defining guardrail policy values and formulas (backend-owned; UI must not compute)
- Approver-side approval/rejection UI (unless already present elsewhere)
- Workexec consumption/reporting implementation (downstream systems)
- Bulk override upload/import

---

# 3. Actors & Stakeholders
- **Store Manager (Primary)**: Creates/updates override for their authorized location(s).
- **Pricing System (Backend, System Actor)**: Computes base price, enforces guardrails, determines approval requirement, persists override and audit history.
- **Approver (Secondary)**: Approves/rejects pending overrides (handled outside this story unless an existing screen exists).
- **Regional Pricing Manager / Pricing Desk (Stakeholders)**: Operational owners of approvals and guardrail enforcement.
- **Reporting/Analytics (Stakeholder)**: Consumes override state and audit trail (out of scope beyond visibility).

# 4. Preconditions & Dependencies
1. User is authenticated in the Moqui app.
2. User has permission to manage store price overrides:
   - Primary permission: `pricing:override:manage`
   - Optional view permission (if implemented): `pricing:override:view` (UI should tolerate absence and rely on 403 handling).
3. User is scoped to one or more locations; override actions must be limited to authorized locations.
4. Backend endpoints/services exist under `/pricing/v1/...` (DECISION-PRICING-002) to:
   - Retrieve pricing context for `(locationId, productId)` including base/effective price and any existing override
   - Submit an override proposal and return resulting status (`ACTIVE` or `PENDING_APPROVAL`) or validation errors
   - Retrieve override audit/history (or include it in the context payload)
5. Money values are returned by backend using canonical money shape `{ amount: "<decimal-string>", currencyUomId: "USD" }` (DECISION-PRICING-001). UI must not recompute totals/extended amounts.
6. Sensitive fields (e.g., cost) may be redacted/omitted unless explicitly authorized; UI must not assume cost is present (DECISION-PRICING-014).

# 6. Functional Behavior

## Triggers
- Enter list screen:
  - Initialize `locationId` from user default location if available; otherwise require selection.
  - Do not load override list until `locationId` is selected (to avoid unauthorized leakage).
- Select location:
  - Enables product search and (optionally) loads existing overrides list for that location.
- Select product or navigate directly to detail with params:
  - Load pricing context for `(locationId, productId)`.
- Submit override:
  - Validate client-side input format only; call backend; then refresh context and history.

## UI actions
- **Select Location**
  - Dropdown/search constrained to authorized locations (source of authorized locations is outside Pricing; UI must rely on existing location-scoping mechanism and handle 403 defensively).
- **Select Product**
  - Product lookup via Inventory product search (DECISION-PRICING-017).
  - Display at minimum SKU and name; store `productId` as opaque ID.
- **View Pricing Context**
  - Display backend-provided:
    - `basePrice` (money, read-only)
    - `effectivePrice` (money, read-only)
    - `cost` (money, read-only) only if present and permitted
    - existing override summary (if any): `overridePrice`, `status`, timestamps, actors (if provided)
- **Enter Override Price**
  - Monetary input; currency shown from context `currencyUomId` (or from `basePrice.currencyUomId`).
- **Submit**
  - Disabled until required inputs present and parseable.
  - Confirmation step (modal/drawer) shows base vs proposed override using backend values and user input; UI may show derived deltas only if backend provides them (do not compute).
  - On confirm, call submit service.
- **Post-submit**
  - On success: show toast/banner and refresh context + history.
  - On validation error: show field/global errors; preserve input.
  - On 403/404/409/5xx: show appropriate error state; do not assume persistence.

## State changes (frontend-visible)
- Override status is backend-authoritative. UI must treat returned status as truth and re-load context after submit.
- UI must not infer status from dates or local logic.

## Service interactions
- Load pricing context service on selection/navigation.
- Submit override service.
- Load audit/history service (or use embedded history from context).

# 7. Business Rules (Translated to UI Behavior)

> Guardrail evaluation, approval thresholds, and any pricing math are backend-owned. UI is a consumer and must not re-implement pricing calculations (Pricing domain invariant).

## Validation (client-side: format only)
- `locationId` and `productId` required and must be non-empty strings (treat as opaque IDs; do not parse).
- `overridePrice.amount`:
  - Required for submit
  - Must parse as decimal-string and be `> 0`
  - Allow up to 4 fractional digits in input (UI ergonomics); backend is authoritative for rounding/acceptance (DECISION-PRICING-001).
- `currencyUomId`:
  - Not user-editable; derived from context/base price (DECISION-PRICING-004 single-currency per scope; applied here as “override does not change currency”).

## Enable/disable rules
- Submit disabled when:
  - missing `locationId` or `productId`
  - `overridePrice` missing or not parseable or `<= 0`
  - context load is in error state that indicates pricing cannot be evaluated (e.g., missing policy/base data) — fail closed.
- Editing disabled when:
  - user lacks `pricing:override:manage`
  - current override status is `PENDING_APPROVAL` (to avoid ambiguous “replace pending” behavior unless backend explicitly supports it)
  - current override status is `REJECTED` (record is read-only; user may submit a new proposal only if backend supports creating a new override version—see Open Questions)

## Visibility rules
- Approval panel visible when:
  - status is `PENDING_APPROVAL` or `REJECTED`, OR
  - backend returns `approvalRequest` object.
- Cost/margin visible only when backend includes cost and user is authorized (DECISION-PRICING-014).
- Any internal policy metadata returned by backend must be treated as sensitive; render only safe, user-facing fields.

## Error messaging expectations
- Validation errors from backend displayed as:
  - Field error on override price when applicable
  - Global banner for policy/base-data/system errors
- Messages must be actionable and backend-provided; UI must not invent policy thresholds.

**Decision rationale references**
- Money shape and rounding backend-owned: DECISION-PRICING-001.
- Sensitive field redaction: DECISION-PRICING-014.
- Single-currency behavior: DECISION-PRICING-004 (applied as “override does not change currency”).

# 9. Service Contracts (Frontend Perspective)

> All Pricing endpoints must be under `/pricing/v1/...` (DECISION-PRICING-002). Exact endpoint names for store price overrides are not provided in the domain rules; this story defines required frontend expectations and leaves exact paths as an integration dependency.

## Load/view calls

1. **Load pricing context for override**
   - **Request (conceptual):** `GET /pricing/v1/location-price-overrides/context?locationId=...&productId=...`
   - **Response (minimum required):**
     - `basePrice` (money)
     - `effectivePrice` (money)
     - `override` (optional)
     - `approvalRequest` (optional)
     - `cost` (optional/redacted)
   - **Error handling:**
     - `403 FORBIDDEN`: show unauthorized state; do not display sensitive fields.
     - `404 NOT_FOUND`: show “Product not found” (or “Override not found” if product exists but context cannot be built; backend should disambiguate via errorCode).
     - `409 CONFLICT` or `422 UNPROCESSABLE_ENTITY`: show blocking banner for missing policy/base data; disable submit (fail closed).
     - `5xx`: show retry; disable submit.

2. **Load override audit/history**
   - **Request (conceptual):** `GET /pricing/v1/location-price-overrides/{overrideId}/history`
   - **Response:** array of `AuditHistoryEntry` (DECISION-PRICING-015)
   - If history is included in context response, this call is optional.

## Create/update calls

1. **Submit override proposal**
   - **Request (conceptual):** `POST /pricing/v1/location-price-overrides:propose`
   - **Body (minimum):**
     - `locationId`
     - `productId`
     - `overridePrice` (money: `{ amount, currencyUomId }`)
     - Optional concurrency token if backend supports it (e.g., `version` or `etag`) — see Open Questions.
   - **Response (minimum):**
     - `overrideId`
     - `status` (`ACTIVE` or `PENDING_APPROVAL`)
     - `effectivePrice` (money) (post-action effective price as determined by backend)
     - `approvalRequest` (optional)
   - **Error handling:**
     - `400 VALIDATION_ERROR`: map `fieldErrors` to form fields; keep input.
     - `403 FORBIDDEN`: show unauthorized; disable submit.
     - `404 NOT_FOUND`: product/location not found.
     - `409 CONFLICT`: show conflict banner and prompt reload (do not auto-resubmit).
     - `5xx`: show retry; do not assume persistence.

## Submit/transition calls (Moqui implementation expectation)
- List screen uses transitions to navigate to detail with parameters.
- Detail screen form submit transition calls a Moqui service that proxies to Pricing backend (REST) and returns messages in Moqui’s standard message/error structures.
- On success: redirect back to same detail with `locationId`/`productId` and show a success message; then reload context.

## Error handling expectations
- Standardize error mapping:
  - Field errors: `overridePrice.amount`
  - Global errors: policy missing, base price unavailable, service unavailable
- Do not log money values or cost values; log only IDs and error codes (DECISION-PRICING-014).

**Decision rationale references**
- `/pricing/v1` base path: DECISION-PRICING-002.
- Audit entry shape: DECISION-PRICING-015.
- Sensitive field handling: DECISION-PRICING-014.

# 10. State Model & Transitions

## Allowed states (as displayed; backend-authoritative)
- `ACTIVE`
- `PENDING_APPROVAL`
- `REJECTED`
- `INACTIVE` (if backend supports end-dating/deactivation for overrides)

## Role-based transitions (frontend)
- Store Manager (`pricing:override:manage`):
  - Can propose override → backend returns `ACTIVE` or `PENDING_APPROVAL`.
  - Cannot approve/reject in this story.
- Approver (`pricing:override:approve`):
  - Approval/rejection out of scope.

## UI behavior per state
- **No existing override**
  - Show base/effective price.
  - Allow entering override price and submitting.
- **ACTIVE**
  - Show active override summary.
  - Allow proposing a new override price (treated as “replace active”) only if backend supports it; otherwise disable and show message (see Open Questions).
- **PENDING_APPROVAL**
  - Show pending status and approval request summary.
  - Disable editing and submitting new proposals by default (avoid ambiguous replace behavior).
- **REJECTED**
  - Show rejection details.
  - Record itself is read-only.
  - Allow submitting a new proposal only if backend supports creating a new override after rejection; otherwise disable and show message (see Open Questions).
- **INACTIVE**
  - Show inactive status.
  - Allow submitting a new proposal.

# 11. Alternate / Error Flows

## Validation failures (guardrail violations)
- Backend returns validation error(s) indicating guardrail violation.
- UI:
  - Shows errors (field/global as provided).
  - Preserves entered override price.
  - Does not change displayed status unless backend returned an updated context (generally should not).

## Concurrency conflicts
- If backend returns `409 CONFLICT` (e.g., override changed since last load):
  - Show banner: “This override was updated by another user. Reload to see the latest values.”
  - Provide “Reload” action; on reload, refresh context and history.
  - Do not auto-resubmit.

## Unauthorized access
- If user accesses a location they are not authorized for:
  - Show unauthorized state (403).
  - Do not display cost or internal policy details.
  - Provide navigation back to list.

## Empty states
- No override exists:
  - Show “No active override for this product at this location.”
  - Allow submit (if context is otherwise valid).

## Backend dependency failure
- Context load fails (network/5xx):
  - Show retry.
  - Disable submit (fail closed).
