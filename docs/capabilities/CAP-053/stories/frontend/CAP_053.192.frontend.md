## Issue Body

## Title
[FRONTEND] [STORY] Billing/AP: Execute Vendor Payment (Allocate Across Bills) and Track GL Posting Status

## Primary Persona
AP Clerk (or AP Manager) using POS Back Office (Billing/AP area)

## Business Value
Enable AP users to execute a vendor payment, allocate it across one or more open bills with idempotency safety, and see the GL posting status/acknowledgement for auditability and reconciliation.

---

# 2. Story Intent

## As a / I want / So that
**As an** AP Clerk,  
**I want** to initiate a vendor payment and allocate the payment across one or more payable bills,  
**So that** vendor bills are settled correctly and the system can track downstream GL posting completion.

## In-scope
- A Moqui screen flow to:
  - Select a vendor and one or more open bills
  - Enter payment details (amount, currency, paymentRef/idempotency key)
  - Optionally specify explicit allocations by bill
  - Submit payment execution
  - View payment result (gateway transaction id if any, allocations, unapplied remainder)
  - View GL posting status (pending/posted/failed) and acknowledgement reference when available
- UI enforcement of allocation validation rules consistent with Billing domain rules (BILL-DEC-013):
  - `grossAmount > 0`
  - `sum(allocations) ≤ grossAmount`
  - bills must be open/payable (server authoritative)
- Idempotent UX behavior when re-submitting with same `paymentRef` (BILL-DEC-013)
- Read-only detail view of a payment record including allocations and status history
- Observability propagation: W3C Trace Context headers on all Billing/AP calls (BILL-DEC-015)

## Out-of-scope
- Defining accounting posting rules / COA mapping UI (owned by Accounting)
- Implementing payment gateway adapter behavior (backend)
- Retry/backoff controls for GL posting (backend)
- Refunds/chargebacks and payment reversal flows (not specified here)
- Vendor/bill creation flows (assumed existing)
- Any UI that implies “posted” means “paid” beyond backend statuses (GL posting is async and read-only in UI; BILL-DEC-013)

- User is authenticated.
- Authorization is enforced server-side using canonical permissions (BILL-DEC-008):
  - Execute AP payment: `billing:ap:payment:execute`
  - View AP payment detail: `billing:ap:payment:view`
  - View vendor bills: `billing:ap:bill:view`
  - View detailed posting errors (if exposed): `billing:posting-error:detail:view` (BILL-DEC-014)

  - `GET /billing/ap/vendors/{vendorId}/bills?status=OPEN`
  - `POST /billing/ap/payments` (idempotent by `paymentRef`)
  - `GET /billing/ap/payments/{billingPaymentId}`
  - Optional: `GET /billing/ap/payments/by-ref/{paymentRef}`
- GL posting acknowledgement is asynchronous; UI must only display backend-provided GL status fields and must not provide manual “mark posted” controls (BILL-DEC-013).
- Deep links must be resolved via frontend routing; do not embed hardcoded routes in backend payloads (BILL-DEC-016).

# 5. UX Summary (Moqui-Oriented)

## Entry points
- Back Office navigation: **Billing/AP → Vendor Bills → “Make Payment”**
- Alternate entry: **Billing/AP → Payments → New Payment**
- Deep link (frontend route examples; do not embed in backend contracts):
  - New payment: `#/billing/ap/payments/new`
  - Payment detail: `#/billing/ap/payments/view?billingPaymentId=...`

## Screens to create/modify (Moqui)
1. **`billing/ap/payments/NewPayment.xml`** (new)
   - Vendor selection
   - Eligible open bills list for selected vendor
   - Allocation editor (explicit allocations only; see Business Rules)
   - Submit action: execute payment
2. **`billing/ap/payments/PaymentDetail.xml`** (new)
   - Read-only payment summary, allocations, status timeline
   - GL posting status and acknowledgement reference when present
   - “Refresh” action (reload)
3. **`billing/ap/vendors/VendorBills.xml`** (modify or confirm existing)
   - Add “Make Payment” action pre-filtered to selected vendor and optionally pre-selected bills

## Navigation context
- Breadcrumbs: Billing/AP > Payments > New / Payment Detail
- After successful execution (including idempotent replay): route to Payment Detail with `billingPaymentId`

## User workflows (happy + alternate paths)

### Happy path
1. User opens New Payment
2. Select vendor
3. System loads open bills for vendor and displays open balances and due dates
4. User selects one or more bills
5. User enters:
   - `grossAmount`
   - `currencyUomId`
   - `paymentRef` (idempotency key; default generated, editable)
6. User optionally enters explicit allocations per selected bill (or leaves blank to let backend allocate)
7. User submits
8. UI navigates to Payment Detail; status shows gateway result and GL posting status (often pending initially)

### Alternate paths
- **Idempotent resubmit:** User submits again with same `paymentRef` → UI shows existing payment result (no duplicate execution; BILL-DEC-013)
- **Gateway failure:** Payment returns `GATEWAY_FAILED` → UI shows failure status and any sanitized error summary; user can start a new payment with a new `paymentRef`
- **GL posting pending:** Payment returns `GATEWAY_SUCCEEDED` and later transitions to `GL_POST_PENDING`/`GL_POSTED`/`GL_POST_FAILED` on refresh (BILL-DEC-013)

# 6. Functional Behavior

## Triggers
- User clicks **Execute Payment** on New Payment screen.
- User navigates to Payment Detail for an existing payment.
- User clicks **Refresh** on Payment Detail.

## UI actions

### New Payment
- Vendor lookup/select
- Load eligible bills for vendor (`status=OPEN`)
- Select one or more bills (optional if backend allows unapplied payment; see Business Rules)
- Enter:
  - `grossAmount`
  - `currencyUomId`
  - `paymentRef` (idempotency key; default generated)
- Optional: explicit allocations grid:
  - `billId`, `appliedAmount`
- Submit: Execute payment

### Payment Detail
- Display:
  - `billingPaymentId`, `paymentRef`, `vendorId`
  - `status` (AP Vendor Payment Status enum; BILL-DEC-013)
  - `grossAmount`, `currencyUomId`
  - `allocations[]` (billId + appliedAmount)
  - GL posting status (part of `status` enum) and any acknowledgement reference if provided
  - Posting error summary (sanitized) if status is `GL_POST_FAILED` (BILL-DEC-014)
- Refresh: reload payment record

## State changes (frontend-visible)
- On submit: show in-progress state; disable submit to prevent duplicate click
- On response:
  - Success: show returned status (may be `INITIATED`, `GATEWAY_PENDING`, `GATEWAY_SUCCEEDED`, etc.)
  - Failure: show `GATEWAY_FAILED`
- Later transitions are reflected only by reloading Payment Detail; UI does not push transitions.

## Service interactions (Moqui)
- New Payment submit transition calls a Moqui service that proxies to `POST /billing/ap/payments` and passes W3C trace headers (BILL-DEC-015).
- New Payment vendor selection triggers a screen action calling `GET /billing/ap/vendors/{vendorId}/bills?status=OPEN`.
- Payment Detail screen action calls `GET /billing/ap/payments/{billingPaymentId}` (or by-ref when arriving from idempotency conflict and only `paymentRef` is known).

# 7. Business Rules (Translated to UI Behavior)

## Validation (client-side where safe; server authoritative)
- `vendorId` is required.
- `grossAmount` is required and must be > 0 (BILL-DEC-013).
- `currencyUomId` is required (BILL-DEC-013 request includes currency).
- `paymentRef` is required (BILL-DEC-013 idempotency key).
- If explicit allocations are provided:
  - Each `appliedAmount` must be ≥ 0 (BILL-DEC-013).
  - Sum of `appliedAmount` across lines must be ≤ `grossAmount` (BILL-DEC-013).
  - Bills must be open/payable; UI should only allow selecting from the “OPEN” list, but server remains authoritative.
- If no explicit allocations are provided:
  - UI sends `allocations` omitted or empty; backend may allocate or may leave unapplied per its rules (BILL-DEC-013 allows allocations optional).

## Enable/disable rules
- Disable **Execute Payment** until required fields satisfied:
  - vendor selected
  - grossAmount > 0
  - currency selected
  - paymentRef present
  - If explicit allocations mode is enabled: allocation sum ≤ grossAmount and all appliedAmount ≥ 0
- During submit in-flight: disable all inputs and show progress indicator.

## Visibility rules
- Show allocation grid only when user enables “Explicit allocations”.
- Show “Unapplied amount” only if backend returns it (do not compute as authoritative financial truth).
- Show posting error summary only when backend returns a sanitized summary; show detailed diagnostics only if user has `billing:posting-error:detail:view` and backend provides detail (BILL-DEC-014).

## Error messaging expectations
- 422 validation errors: map field-level errors to inputs; show summary at top.
- 409 idempotency conflict:
  - If backend returns an existing `billingPaymentId`, navigate to Payment Detail.
  - If backend returns only `paymentRef`, provide a “Find payment by reference” action (calls by-ref endpoint if available).
- 503 downstream unavailable: show retryable error; preserve form state.

# 9. Service Contracts (Frontend Perspective)

## Load/view calls

1) **List vendor open bills**
- `GET /billing/ap/vendors/{vendorId}/bills?status=OPEN`
- Response: `bills[]` with fields listed in Data Requirements.
- Errors:
  - 401 unauthenticated
  - 403 lacks `billing:ap:bill:view`
  - 404 vendor not found/inaccessible

2) **Get payment detail**
- `GET /billing/ap/payments/{billingPaymentId}`
- Response: payment record with status, amounts, allocations, and (if available) status history and posting acknowledgement.
- Errors:
  - 401 unauthenticated
  - 403 lacks `billing:ap:payment:view`
  - 404 not found/inaccessible

3) **(Optional) Get payment by reference**
- `GET /billing/ap/payments/by-ref/{paymentRef}`
- Used when a 409 idempotency conflict returns only reference.
- Same errors as payment detail.

## Create/update/submit calls

1) **Execute AP vendor payment (idempotent)**
- `POST /billing/ap/payments`
- Request (BILL-DEC-013):
  - `{ vendorId, grossAmount, currencyUomId, paymentRef, allocations[]? }`
  - `allocations[]` optional; if present, each item `{ billId, appliedAmount }`
- Response:
  - `{ billingPaymentId, status, allocations[]?, unappliedAmount?, postingAckRef?, postedAt?, postingErrorSummary? }`
- Errors:
  - 422 validation failures (grossAmount <= 0, allocations invalid, bills not payable/open)
  - 409 conflict:
    - same `paymentRef` with different payload (idempotency conflict), or
    - other deterministic conflicts as defined by backend
  - 503 downstream unavailable (gateway/GL posting pipeline)
- Idempotency behavior (BILL-DEC-013):
  - Same `paymentRef` with identical payload returns the existing payment without re-executing.
  - Same `paymentRef` with different payload returns 409 with deterministic errorCode/reason and should include existing `billingPaymentId` when possible.

## Error handling expectations (frontend)
- 422: show inline errors; keep user inputs.
- 409:
  - If response includes `billingPaymentId`, navigate to Payment Detail and show “This payment reference was already processed.”
  - If response includes only `paymentRef`, provide a “Lookup by reference” action.
- 403: show not authorized; hide execute controls.
- 503: show retry; do not clear form; keep `paymentRef` stable unless user changes it.

# 10. State Model & Transitions

## Allowed states (backend authoritative; BILL-DEC-013)
- `INITIATED`
- `GATEWAY_PENDING`
- `GATEWAY_FAILED`
- `GATEWAY_SUCCEEDED`
- `GL_POST_PENDING`
- `GL_POSTED`
- `GL_POST_FAILED`

## Role-based transitions
- AP Clerk/AP Manager initiates payment creation (requires `billing:ap:payment:execute`).
- All subsequent transitions are system-driven; UI is read-only for state transitions (BILL-DEC-013).

## UI behavior per state
- `INITIATED` / `GATEWAY_PENDING`: show “Processing payment”; allow user to navigate away; Payment Detail shows current status on refresh.
- `GATEWAY_FAILED`: show failure summary if provided; allow starting a new payment (new `paymentRef`).
- `GATEWAY_SUCCEEDED`: show success; GL posting may still be pending.
- `GL_POST_PENDING`: show “GL posting pending”.
- `GL_POSTED`: show acknowledgement reference and timestamp if provided.
- `GL_POST_FAILED`: show sanitized posting error summary and correlationId if provided; do not expose detailed diagnostics unless permitted (BILL-DEC-014).

# 11. Alternate / Error Flows

## Validation failures
- Missing vendor/amount/currency/paymentRef → block submit with client-side validation.
- Explicit allocation sum > grossAmount → block submit and highlight allocation section.
- Negative applied amounts → block submit.

## Concurrency conflicts
- Bill open balance/status changed between load and submit → backend returns 422/409; UI shows “Bill eligibility or balances changed. Reload bills.” and provides Reload action.

## Unauthorized access
- 401: redirect to login.
- 403:
  - On New Payment: show “Not authorized to execute AP payments” and hide submit.
  - On Payment Detail: show “Not authorized to view this payment.”

## Empty states
- No open bills for vendor:
  - Show empty state.
  - User may still execute an unapplied payment (vendor credit) **only if backend accepts allocations omitted and does not require bill selection**; UI must allow submit with zero selected bills when explicit allocations are not enabled.
  - If backend rejects with 422 requiring allocations/bills, UI shows returned validation and instructs user to select bills.
