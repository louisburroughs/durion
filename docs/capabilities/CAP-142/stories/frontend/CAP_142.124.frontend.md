## 1. Story Header

**Title:** [FRONTEND] [STORY] Reporting: Daily Dispatch Board Dashboard (Read-only Board + Exceptions + Partial Availability)

**Primary Persona:** Dispatcher (also applicable: Shop Manager / Dispatch Coordinator)

**Persona Metadata**
- `primary_persona`: `Dispatcher (also applicable: Shop Manager / Dispatch Coordinator)`
- `canonical_persona`: `Dispatcher`
- `persona_family`: `Dispatch`
- `actor_type`: `human`
**Business Value:** Provide an operational, at-a-glance view of a single location’s dispatch day (work orders, assignment context, and exception indicators) so dispatch can proactively manage workload, reduce conflicts, and react quickly to blocking issues—even during partial dependency outages.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Dispatcher  
- **I want** a Daily Dispatch Board dashboard that shows the dispatch day’s work orders and exception indicators, with optional mechanic availability signals  
- **So that** I can dispatch jobs efficiently and avoid preventable scheduling conflicts

### In-scope
- Extend/implement the **existing Moqui workexec dispatch board screen** (`durion-workexec/WorkOrderBoard.xml`) to:
  - Filter by **location** and **date** (default: today)
  - Render a **read-only** board view of work orders for that location/day
  - Surface **server-provided exception indicators** (warning vs blocking)
  - Show “Last updated” and server “As of” timestamps
  - Auto-refresh via polling every **30 seconds** while the screen is active/visible, plus manual refresh
  - Degrade gracefully if **People availability** cannot be loaded (board still renders)
- Frontend integration to:
  - Workexec board data source (Moqui screen actions/services or REST read model if present)
  - Optional People availability endpoint (read-only signal)

### Out-of-scope
- Any dispatch mutations (assigning mechanics/bays, rescheduling, editing work orders/appointments)
- WebSocket/push updates (explicitly v2)
- Multi-location merged board (one location per view only)
- Configuration of bays/mechanic roles/skills
- Time entry / payroll / billing actions
- Creating/updating work orders, estimates, approvals, receiving, picking

- Direct route: the existing Moqui route for `durion-workexec/WorkOrderBoard` (DECISION-INVENTORY-002).

### Screens to create/modify
- **Modify:** `durion-workexec/screen/WorkOrderBoard.xml`
  - Add/confirm parameters:
    - `locationId` (required to load data)

    - Filters (location/date)
    - Board list/grouping

- Filters at top: location selector, date picker.

### User workflows
#### Happy path
1. User opens Dispatch Board.
2. Screen selects default location (last-used if available; otherwise first accessible) and default date (today).

- User changes date: reload board for that day.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `locationId` is required to load board data.
  - If missing, show inline prompt and do not issue board request.
- `viewDate` must be a valid ISO date `YYYY-MM-DD`.

### Enable/disable rules
- While primary board request is in-flight:
  - Disable “Refresh now” to prevent request storms.
  - Allow filter changes, but debounce and cancel/ignore prior in-flight results (implementation detail; must avoid out-of-order overwrites).
- If user lacks permission:
  - Do not attempt polling; show access denied.

### Visibility rules
- Exceptions must be visible without drilling into each work order:
  - Show counts by severity (`WARNING`, `BLOCKING`)
  - Provide a list of exception indicators with stable `code` and human message (DECISION-INVENTORY-009).
- If People availability fails:
  - Show a warning banner: “Mechanic availability is temporarily unavailable; showing work orders only.”

### Error messaging expectations
- Primary board load failure:
  - If no cached data: show error state with retry.
  - If cached data exists: show offline/stale banner and keep cached board visible.
- 401/403:
  - 401: follow app login redirect pattern.
  - 403: show “You don’t have access to Dispatch Board for this location.” Allow switching location if user has others.

**Decision rationale applied:** Permission gating is explicit (`WORKEXEC_DISPATCH_VIEW`) and backend remains authoritative (DECISION-INVENTORY-013).

## 8. Data Requirements

### Entities involved (frontend perspective)
- Workexec work orders: `durion.workexec.DurWorkOrder` (source for board rows)
- Optional shopmgr appointment reference: `durion.shopmgr.DurShopAppointment` via `DurWorkOrder.appointmentId` (DECISION-INVENTORY-010)
- Dispatch board exception indicators: server-provided stable codes (DECISION-INVENTORY-009)
- People availability DTO (read-only signal; People domain SoR)

### Fields (type, required, defaults)

#### Filter inputs
- `locationId`: `id` (opaque string) **required**
- `viewDate`: ISO date string `YYYY-MM-DD` **required**
  - Default: today, bucketed by shop timezone when available; otherwise user timezone with explicit label (DECISION-INVENTORY-016)

#### Board row minimum fields (must be available to render)
- `workOrderId`: `id` (opaque string) **required**
- `statusId`: string enum **required**
- `appointmentId`: `id` (opaque string) optional (DECISION-INVENTORY-010)
- `scheduledStart` / `scheduledEnd` (timestamps) optional but recommended for “overdue” display; if absent, UI must not compute overdue exceptions client-side
- `mechanicId` or `assignedMechanics[]`: `id`(s) optional (DECISION-INVENTORY-005)
- `bayId`: `id` optional
- `exceptionIndicators[]`: array optional (may be empty)

#### ExceptionIndicator minimum fields
- `code`: string **required** (stable enum/code; DECISION-INVENTORY-009)
- `severity`: enum **required** (`WARNING` | `BLOCKING`)
- `message`: string **required**
- `targetType`: enum **required** (`WORK_ORDER` | `MECHANIC` | `BAY` | `APPOINTMENT` | `LOCATION`)
- `targetId`: `id` optional (required when targetType is not LOCATION)
- `asOf`: timestamp optional (if per-indicator; otherwise board-level `asOf`)

#### People availability (if integrated)
- `asOf`: timestamp **required**
- `locationId`: `id` **required**
- `people[]`: array **required**
  - `personId`: `id` **required**
  - `displayName`: string **required** (avoid logging PII; render only)
  - `currentStatus`: enum **required** (People-owned)
  - Optional schedule blocks if `includeSchedule=true`

### Read-only vs editable
- Entire screen is read-only.

### Derived/calculated fields (frontend)
- `isStale = (now - lastSuccessfulFetchAt) > 2 minutes`
- Exception counts grouped by severity
- “Last updated” (client) and “As of” (server) display conversion to user timezone (DECISION-INVENTORY-016)

### Load/view calls

#### B) People availability (secondary; optional)
- `GET /rest/api/v1/people/availability?locationId={locationId}&date={YYYY-MM-DD}&includeSchedule=true`
- Must be called in parallel and must not block board rendering on failure (DECISION-INVENTORY-009).

### Create/update calls
- None.

### Submit/transition calls
- None.

### Error handling expectations
- Standard error envelope when REST is used (DECISION-INVENTORY-011):
  - `{ code, message, correlationId, fieldErrors?, existingResourceId? }`
- 401/403: stop polling; show access messaging.
- 5xx/network:
  - Keep cached board visible if present.
  - Mark stale after 2 minutes since last success.
  - Continue polling with backoff (see Applied Safe Defaults).

## 10. State Model & Transitions

### Allowed states (UI state)
- `loading-initial`
- `loaded-fresh`
- `loaded-stale`
- `error-initial`
- `offline-readonly` (cached data visible)

### Role-based transitions
- View requires capability/permission `WORKEXEC_DISPATCH_VIEW` plus location membership (DECISION-INVENTORY-013).
- If permission is missing, transition to `error-initial` with access denied and stop polling.

### UI behavior per state
- `loading-initial`: show loading indicator; do not show stale banner.
- `loaded-fresh`: show board; show timestamps; polling active.
- `loaded-stale`: show board; show stale banner; polling continues.
- `offline-readonly`: show cached board; disable “Refresh now” only if repeated failures exceed backoff threshold; allow changing filters but warn that data may be stale.
- `error-initial`: show error with retry; no board content.

## 11. Alternate / Error Flows

### Validation failures
- Missing `locationId`: show inline validation; do not request.
- Invalid `viewDate`: block request and show inline message; allow user correction.

### Concurrency / out-of-order responses
- If a slower request returns after a newer request:
  - Ignore older response based on request token or `asOf` comparison (keep newest dataset).
  - Record a debug log entry (no user disruption).

### Unauthorized access
- 401: redirect to login per app convention; preserve intended route.
- 403: show access denied; stop polling; allow location change.

### Empty states
- No work orders: show “No work orders for {viewDate} at {location}.”
- People availability empty: show “No availability data returned for this date.” (board still renders)

### Partial dependency failure (People)
- If People call fails:
  - Render board normally.
  - Show warning banner and hide/disable availability panel.

## 12. Acceptance Criteria

### Scenario 1: Initial load uses canonical screen and renders board
**Given** I am an authenticated user with `WORKEXEC_DISPATCH_VIEW` permission and access to location `LOC-1`  
**When** I open the Dispatch Board screen (`durion-workexec/WorkOrderBoard`)  
**Then** the screen loads and renders the dispatch board for `LOC-1` and today’s dispatch day  
**And** the screen shows a “Last updated” timestamp  
**And** if the server provides an `asOf` timestamp, it is displayed as “As of” in my user timezone with a timezone label

### Scenario 2: Filter by location and date (single-location view)
**Given** I am viewing the Dispatch Board  
**When** I change the location filter to `LOC-2` that I have access to  
**Then** the board reloads and displays only data for `LOC-2`  
**When** I change the date filter to `2026-01-19`  
**Then** the board reloads and displays only data bucketed for `2026-01-19` (shop timezone when available, otherwise user timezone with explicit label)

### Scenario 3: Auto-refresh polling updates data
**Given** I am viewing the Dispatch Board and the screen is visible/active  
**When** 30 seconds have elapsed since the last successful refresh  
**Then** the frontend requests updated board data  
**And** on success the displayed board updates and “Last updated” changes

### Scenario 4: Manual refresh
**Given** I am viewing the Dispatch Board  
**When** I click “Refresh now”  
**Then** the frontend requests updated board data immediately  
**And** the displayed board updates upon success

### Scenario 5: Exceptions are visible and severity-distinguished
**Given** the board payload includes exception indicators with severities `WARNING` and `BLOCKING`  
**When** the Dispatch Board renders  
**Then** I can see exception counts by severity without drilling into individual work orders  
**And** each exception shows a stable `code` and a human-readable message  
**And** items with `BLOCKING` exceptions are visually indicated as blocked

### Scenario 6: People availability failure does not block board
**Given** the board data loads successfully  
**And** the People availability request fails with a network error or 5xx  
**When** the Dispatch Board renders  
**Then** the board still shows work orders and exceptions  
**And** the UI shows a warning that mechanic availability is unavailable  
**And** no blocking error state is shown

### Scenario 7: Stale/offline behavior with cached data
**Given** I have previously loaded the board successfully  
**And** subsequent board refresh requests fail due to network/5xx errors  
**When** more than 2 minutes pass since the last successful fetch  
**Then** the UI indicates the displayed data is stale  
**And** the last successfully loaded board remains visible in read-only mode

### Scenario 8: RBAC enforcement
**Given** I am authenticated but do not have `WORKEXEC_DISPATCH_VIEW` permission for the selected location  
**When** I open the Dispatch Board screen  
**Then** I see an access denied message  
**And** the UI does not continue polling for updates
