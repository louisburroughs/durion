## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Workexec: Display & Edit Work Order Assignment Context (Location/Bay/Mechanic) Pre-Start; Lock After Start; Show Audit Metadata

**Primary Persona:** Service Advisor / Shop Manager (POS user managing a work order)

**Business Value:** Ensures work order execution reflects the correct operational assignment context (location, bay/resource, assigned mechanic(s)) while preventing mid-work drift and preserving traceability for changes and overrides.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor / Shop Manager  
- **I want** to view and update a Work Order’s assignment context (location, bay/resource, mechanic(s)) before work begins  
- **So that** technicians and reporting use the correct operational context, and changes are traceable and concurrency-safe.

### In-scope
- Display assignment context fields on the Work Order edit/detail screen.
- Allow updates **only while the Work Order is pre-start** (per workexec “started” gating).
- Enforce UI gating using server-provided status (and/or `isStarted` if present) and handle server-side enforcement errors.
- Use idempotency for mutation requests (send `Idempotency-Key` and reuse on retry).
- Display **minimum audit metadata** (created/updated + actor if provided) and **status transition history** when available.

### Out-of-scope
- Authoring/editing master data for locations/bays/mechanics (owned by other domains).
- Consuming/processing shopmgr “AssignmentUpdated” events in the frontend (integration mechanics are out of scope for this UI story).
- Time entry / people timekeeping CRUD (people domain).
- Defining permission policy/role inheritance (security domain); this story only consumes capability signals and handles 403.

---

## 3. Actors & Stakeholders

- **Service Advisor / Shop Manager (primary user):** edits assignment context pre-start; may perform manager override after start if permitted.
- **Mechanic (consumer):** expects assignment context to be stable once work has started.
- **Workexec backend:** authoritative for work order status, started gating, concurrency checks, and audit.
- **Shopmgr backend (dependency):** system of record for operational context semantics; workexec may store assignment-like fields on the work order and/or record overrides.
- **Audit/Compliance:** requires traceability for “who changed what and when,” especially for post-start overrides.

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in POS frontend.
- A Work Order exists and is accessible to the user.
- Work Order status is available and aligned to workexec status taxonomy; “started” means `WO_IN_PROGRESS` or later (or equivalent) and should ideally be exposed as `isStarted` to avoid client-side mapping.

### Dependencies (must exist to implement)
- A Work Order detail load contract that returns:
  - `workOrderId` (opaque string id)
  - `statusId` (string)
  - assignment context fields (`locationId`, `bayId` and/or `resourceId`, `mechanicId` and/or `mechanicIds`)
  - audit metadata (`createdDate`, `createdByUserId`, `lastUpdatedDate`, `lastUpdatedByUserId`) if available
  - optional `isStarted` boolean (preferred)
  - optional `version`/`lastUpdatedStamp` token for concurrency (preferred)
- A Work Order update contract for assignment context that:
  - enforces started gating server-side
  - supports idempotency via `Idempotency-Key`
  - returns standard error envelope on failures
- Optional (non-blocking) history endpoint for status transitions:
  - `GET .../transitions` returning append-only transition records

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From Work Order board/list → open a Work Order → Work Order edit/detail.
- Deep link via existing Moqui route to the work order screen (use existing `durion-workexec` screen; do not introduce a new route unless necessary).

### Screens to create/modify
- **Modify:** `durion-workexec/WorkOrderEdit.xml` (canonical per DECISION-INVENTORY-002) to add/standardize an “Assignment Context” section.
- **No new screens required** for v1; use existing screen patterns and transitions.

### Navigation context
- Work Order edit/detail is the parent context.
- Assignment Context is a section within the Work Order screen.

### User workflows (happy + alternate paths)

#### Happy path: pre-start edit
1. User opens Work Order edit screen.
2. User sees current assignment context (location, bay/resource, mechanic(s)).
3. If work is **not started**, user enters edit mode and updates fields using pickers.
4. User saves; UI sends update with `Idempotency-Key`.
5. UI refreshes Work Order and shows updated values and updated metadata.

#### Alternate path: locked after start (no override capability)
1. User opens Work Order that is started (`WO_IN_PROGRESS` or later).
2. Assignment context is read-only.
3. UI shows message: “Assignment context locked after work starts.”

#### Alternate path: manager override after start (if capability present)
1. User opens started Work Order.
2. If user has override capability, UI shows “Override assignment context” action.
3. User enters override reason and updates fields.
4. UI submits override; UI refreshes and shows audit metadata (and any override history if available).

#### Alternate path: concurrency / stale edit
1. User begins editing while pre-start.
2. Another user starts the work order or updates assignment context.
3. Save returns 409 conflict; UI shows conflict message and reloads server state, exiting edit mode.

## 6. Functional Behavior

### Triggers
- Screen load triggers Work Order detail retrieval (including status + assignment context).
- “Save” triggers assignment context update (pre-start) or override (post-start, manager-only).
- “History” section load triggers transition history retrieval (lazy load).

### UI actions
- View assignment context fields.
- Enter edit mode (pre-start) or override mode (post-start with capability).
- Save / Cancel.
- Retry on transient failure without losing local draft (until user cancels).

### State changes
- UI derives:
  - `isStarted` from server `isStarted` if present; otherwise from `statusId` mapping (see State Model).
  - `canEditAssignment` = `!isStarted` AND capability allows edit (if capability signal exists; otherwise show action and rely on 403).
  - `canOverrideAssignment` = `isStarted` AND capability allows override.
- After successful mutation, UI re-fetches Work Order detail to reflect server truth.

### Service interactions
- Load: Work Order detail (Moqui screen action/service call).
- Update (pre-start): Work Order update service for assignment context.
- Override (post-start): Work Order override service (manager-only) if implemented; otherwise UI does not offer override and relies on read-only lock.
- History (optional): Work Order transitions/history service.

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI-level ergonomics; backend authoritative)
- IDs are opaque strings; UI must not enforce UUID format (DECISION-INVENTORY-003).
- Use pickers/search for selecting location/bay/mechanic; avoid free-form ID entry (DECISION-INVENTORY-008).
- Requiredness:
  - Do not enforce required fields client-side unless backend contract marks them required.
  - Allow clearing fields to null/empty; backend may reject with fieldErrors.

### Enable/disable rules
- **Pre-start edit allowed** when work order is not started.
  - Started means `WO_IN_PROGRESS` or later (DECISION-INVENTORY-004).
  - If server provides `isStarted`, use it.
- **Post-start lock**:
  - If started and user lacks override capability: disable edit controls.
  - If started and user has override capability: show override action (manager-only override allowed after start; DECISION-INVENTORY-005).

### Visibility rules
- Assignment Context section always visible.
- Edit action visible when `canEditAssignment`.
- Override action visible when `canOverrideAssignment`.
- History section visible if transition endpoint exists; otherwise show metadata only.

### Error messaging expectations (standard envelope)
- Parse standard error envelope (DECISION-INVENTORY-011):
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`.
- Show:
  - 400 with fieldErrors → inline field messages + banner summary.
  - 403 → “You do not have permission to perform this action.”
  - 409 → “This work order changed since you opened it. Reloading…”
  - Include `correlationId` in the error banner details (copyable) for support.

    ```json
      "version": "2026-01-19T15:01:00Z"
    }
    ```

- **Capabilities (if not already available in session)**
  - `GET /rest/api/v1/user/context` (or equivalent)
  - Must return stable capability flags (DECISION-INVENTORY-013), e.g.:
    ```json
    {
      "capabilities": {
        "WORKEXEC_ASSIGNMENT_EDIT": true,
        "WORKEXEC_ASSIGNMENT_OVERRIDE": false
      }
    }
    ```

### Create/update calls
- **Pre-start update assignment context**
  - `PUT /rest/api/v1/workexec/workorders/{workOrderId}/assignment-context`
  - Headers:
    - `Idempotency-Key: <uuid>` (DECISION-INVENTORY-012)
  - Request body:
    ```json
    {
      "locationId": "LOC-1",
      "bayId": "BAY-2",
      "mechanicId": "MECH-9",
      "version": "2026-01-19T15:01:00Z"
    }
    ```
  - Success: `200 OK` with updated Work Order payload (preferred).

- **Post-start override assignment context (manager-only)**
  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/assignment-context:override`
  - Headers:
    - `Idempotency-Key: <uuid>`
  - Request body:
    ```json
    {
      "locationId": "LOC-1",
      "bayId": "BAY-3",
      "mechanicId": "MECH-9",
      "reason": "Bay reassigned due to lift outage",
      "version": "2026-01-19T15:01:00Z"
    }
    ```
  - Success: `200 OK` with updated Work Order payload.
  - If backend does not yet support override endpoint, UI must not expose override action and must remain read-only post-start.

### Submit/transition calls
- None in this story.

### Error handling expectations
- All non-2xx responses should conform to standard error envelope (DECISION-INVENTORY-011):
  ```json
  {
    "code": "CONFLICT",
    "message": "Work order changed since last load",
    "correlationId": "c-123",
    "fieldErrors": [
      {"field":"mechanicId","message":"Invalid mechanic for location"}
    ]
  }
  ```
- `409 Conflict` for stale version / started gating race.
- `403 Forbidden` for missing capability/permission.
- UI must reuse the same `Idempotency-Key` when retrying the same user-initiated save attempt.

## 11. Alternate / Error Flows

### Validation failures (400)
- Backend returns `fieldErrors[]`:
  - UI highlights fields and shows messages.
  - UI remains in edit/override mode with user inputs preserved.

### Concurrency conflicts (409)
- UI shows conflict banner including `correlationId`.
- UI reloads Work Order detail.
- UI exits edit/override mode and shows server values.

### Unauthorized access (401/403)
- 401: redirect to login/session refresh per app convention.
- 403 on view: show access denied state.
- 403 on edit/override: keep section read-only; show permission message.

### Empty states
- If assignment fields are null:
  - Display “Not assigned” per field.
- If history endpoint is missing or returns empty:
  - Show “No history available” and still show created/updated metadata.

### Partial dependency failure (pickers)
- If a picker lookup fails (e.g., mechanics list unavailable):
  - Do not block viewing the work order.
  - Disable the affected picker and show “Unable to load options; try again” with retry.

## 12. Acceptance Criteria

### Scenario 1: View assignment context on a work order
**Given** I am an authenticated user  
**And** a Work Order exists  
**When** I open the Work Order edit screen  
**Then** I see the assignment context fields (location, bay/resource, mechanic(s))  
**And** if any field is null I see “Not assigned” for that field  

### Scenario 2: Edit assignment context when work has not started
**Given** I am an authenticated user  
**And** the Work Order is not started (`isStarted=false` or status is pre-start)  
**When** I enter edit mode in the Assignment Context section  
**And** I change one or more assignment context fields  
**And** I click Save  
**Then** the frontend sends an update request with an `Idempotency-Key` header  
**And** on success the UI reloads the Work Order and displays the updated values  
**And** the UI displays updated audit metadata (last updated timestamp/actor) if provided  

### Scenario 3: Assignment context is locked after work starts (no override capability)
**Given** I am an authenticated user  
**And** the Work Order is started (`isStarted=true` or status is `WO_IN_PROGRESS` or later)  
**And** I do not have override capability  
**When** I open the Work Order edit screen  
**Then** the Assignment Context section is read-only  
**And** I see messaging that assignment context is locked after work starts  

### Scenario 4: Manager override after start (when capability + endpoint exist)
**Given** I am an authenticated user with override capability  
**And** the Work Order is started  
**When** I choose “Override assignment context”  
**And** I provide an override reason  
**And** I save  
**Then** the frontend sends an override request with an `Idempotency-Key` header  
**And** the UI reloads the Work Order and displays the updated values  
**And** the UI displays updated audit metadata if provided  

### Scenario 5: Save rejected due to status change during edit
**Given** I am editing assignment context for a Work Order that was not started when loaded  
**And** the Work Order becomes started before I click Save  
**When** I click Save  
**Then** the backend responds with a non-2xx error (409 or 400) in the standard error envelope  
**And** the UI shows an error indicating the update cannot be applied after work started  
**And** the UI reloads the Work Order and exits edit mode  

### Scenario 6: Concurrency conflict on stale version token
**Given** I loaded a Work Order with a version token  
**And** another user updates the Work Order before I save  
**When** I save my assignment context changes using the stale version token  
**Then** the backend returns `409 Conflict` with a `correlationId`  
**And** the UI reloads and shows the server’s current assignment context
