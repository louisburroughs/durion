## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] People/HR: View ingested Timekeeping Entries from ShopMgr work sessions (payroll readiness + approval visibility)

### Primary Persona
Payroll Clerk

### Business Value
Payroll Clerks can reliably view finalized work sessions ingested as People-owned `TimekeepingEntry` records (deduplicated by source key) with approval status and audit/source metadata, enabling payroll preparation and compliance review without duplicate rows or ambiguous ingestion provenance.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Payroll Clerk  
- **I want** a People/HR UI to view timekeeping entries ingested from ShopMgr work sessions, including approval status and source identifiers  
- **So that** I can prepare payroll and audit compliance with confidence that sessions are complete, deduplicated, and tracked.

### In-scope
- New People-domain UI screens to:
  - List `TimekeepingEntry` records with paging + filters
  - View a `TimekeepingEntry` detail page with source metadata and approval status
- UI behavior consistent with People domain decisions:
  - Deduplication is a backend invariant; UI must not show duplicates for the same source key (Decision: DECISION-PEOPLE-005)
  - Standard paging and error schema handling (Decisions: DECISION-PEOPLE-021, DECISION-PEOPLE-018)
  - Timezone display rules for timestamps (Decision: DECISION-PEOPLE-015)
  - `tenantId` is treated as sensitive and not displayed by default (Decision: DECISION-PEOPLE-019)
- Read-only visibility for payroll review (no approve/reject actions in this story)

### Out-of-scope
- Implementing ingestion itself (event subscriber, DLQ handling, mapping) — backend concern
- Implementing approve/reject workflows (period-atomic approvals) — separate story (Decision: DECISION-PEOPLE-006)
- Editing/correcting `TimekeepingEntry` records

## 4. Preconditions & Dependencies
- People backend persists `TimekeepingEntry` records ingested from ShopMgr `WorkSessionCompleted` events.
- Ingestion is idempotent/deduplicated by a stable source key (e.g., `workSessionId` / `sourceSessionId`); UI must not attempt dedupe logic beyond rendering server results. (Decision: DECISION-PEOPLE-005)
- People backend exposes REST endpoints under `/rest/api/v1/people` with consistent paging and error schema. (Decision: DECISION-PEOPLE-021, DECISION-PEOPLE-018)
- Authentication is in place; authorization is enforced server-side. UI gates access using named permissions/capability flags when available. (Decision: DECISION-PEOPLE-013)
- Time instants are stored in UTC; UI displays in user profile timezone when available, else location timezone. (Decision: DECISION-PEOPLE-015)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Date range validation: `fromDateTime <= thruDateTime`; block submit and show inline error.
- `approvalStatus` filter must be one of the allowed enum values; UI uses a controlled dropdown (no free-text).
- Detail route requires `timekeepingEntryId`; missing/invalid format results in not-found state (do not attempt partial matching).

### Enable/disable rules
- Menu entry and route access are gated by a named permission (see Service Contracts). (Decision: DECISION-PEOPLE-013)
- Disable “Apply” and paging controls while a request is in-flight to prevent accidental duplicate requests (UI ergonomics).

### Visibility rules
- `approvalStatus` is always visible in list and detail.
- Source identifiers are visible in detail:
  - `sourceSystem`
  - `sourceSessionId` (or `workSessionId`)
- `tenantId` is not displayed by default. (Decision: DECISION-PEOPLE-019)
- Optional fields (e.g., `associatedWorkOrderId`, `locationId`) render as “—” when absent.

### Error messaging expectations (standardized)
- 401/403: access denied message; do not display any data.
- 404: not found state for detail.
- 400: render field-level errors for filters; keep prior results unchanged.
- 409: show conflict banner “Data changed; refresh required” and offer Refresh. (Decision: DECISION-PEOPLE-018)
- 5xx/network: show retryable error banner; preserve last successful results if available.

## 9. Service Contracts (Frontend Perspective)

All endpoints follow People REST conventions under `/rest/api/v1/people` with paging and standard error schema. (Decisions: DECISION-PEOPLE-021, DECISION-PEOPLE-018)

### Load/view calls

1) **List Timekeeping Entries**
- **Method/Path:** `GET /rest/api/v1/people/timekeeping-entries`
- **Query params:**
  - `page` (int, default 0)
  - `pageSize` (int, default 25)
  - `personId` (optional, string/UUID)
  - `approvalStatus` (optional, string enum)
  - `fromDateTime` (optional, ISO-8601 instant or offset datetime)
  - `thruDateTime` (optional, ISO-8601 instant or offset datetime)
  - `locationId` (optional, string/UUID)
  - `workOrderId` (optional, string/UUID) — maps to `associatedWorkOrderId`
  - `includeHistory` (optional, boolean) — not used for timekeeping entries unless backend supports; omit from UI unless present in API docs
- **Response 200 shape:**
  ```json
  {
    "items": [
      {
        "timekeepingEntryId": "…",
        "personId": "…",
        "employeeDisplayName": "…",
        "sessionStartAt": "2026-01-19T16:30:00Z",
        "sessionEndAt": "2026-01-19T18:00:00Z",
        "approvalStatus": "PENDING_APPROVAL",
        "sourceSystem": "shopmgr",
        "sourceSessionId": "…",
        "locationId": "…",
        "associatedWorkOrderId": "…"
      }
    ],
    "page": 0,
    "pageSize": 25,
    "total": 123
  }
  ```

2) **Get Timekeeping Entry Detail**
- **Method/Path:** `GET /rest/api/v1/people/timekeeping-entries/{timekeepingEntryId}`
- **Response 200:** full record; may include additional audit fields and optional approval metadata/history if backend provides it (UI renders if present; does not invent). (Decision: DECISION-PEOPLE-006)

### Create/update calls
- none

### Submit/transition calls
- none

  ```json
  { "errorCode": "VALIDATION_ERROR", "message": "…", "fieldErrors": [{ "field": "fromDateTime", "message": "…" }] }
  ```


## 11. Alternate / Error Flows

### Validation failures
- Invalid date range: block request; show inline error; do not clear existing results.
- Backend 400 with `fieldErrors`: map to corresponding filter fields; keep prior results.

### Concurrency conflicts
- If detail load returns 409 (rare for read): show conflict banner and offer Refresh; do not auto-retry in a loop. (Decision: DECISION-PEOPLE-018)

### Unauthorized access
- Menu entry hidden when user lacks `people:timekeeping.read`.
- Direct URL access:
  - If 401: redirect to login (standard app behavior)
  - If 403: show access denied screen/message with no data

### Empty states
- No results: show empty state with “Clear filters” and “Refresh”.

## 12. Acceptance Criteria

### Scenario 1: View list of ingested timekeeping entries
**Given** I am authenticated as a Payroll Clerk with permission `people:timekeeping.read`  
**When** I navigate to People → Timekeeping → Timekeeping Entries  
**Then** I see a paginated list of Timekeeping Entries  
**And** each row shows employee (display name if provided, else personId), session start time, session end time, approval status, and source session id

### Scenario 2: Filtering by approval status and date range
**Given** I am on the Timekeeping Entries list screen  
**When** I set Approval Status to `PENDING_APPROVAL` and a valid date range and apply filters  
**Then** the list refreshes to show only matching entries  
**And** paging reflects the filtered result set

### Scenario 3: Invalid date range is blocked client-side
**Given** I am on the Timekeeping Entries list screen  
**When** I enter a from-date that is after the thru-date and apply filters  
**Then** the UI prevents the query  
**And** I see an inline validation message indicating the date range is invalid  
**And** any previously loaded results remain visible

### Scenario 4: View entry detail
**Given** I am on the Timekeeping Entries list screen  
**When** I select a Timekeeping Entry  
**Then** I navigate to a detail screen for that entry  
**And** I can see approval status and source metadata including `sourceSystem` and `sourceSessionId`  
**And** I do not see `tenantId` displayed

### Scenario 5: Duplicate ingestion does not appear as duplicates in UI
**Given** the backend has received duplicate deliveries for the same source session id and deduplicated them (idempotent ingestion)  
**When** I view the Timekeeping Entries list  
**Then** I see only one Timekeeping Entry row for that source session id  
**And** there are no duplicate rows representing the same source session

### Scenario 6: Unauthorized user cannot access
**Given** I am authenticated as a user without permission `people:timekeeping.read`  
**When** I attempt to navigate to the Timekeeping Entries list URL directly  
**Then** I see an access denied message  
**And** no timekeeping entry data is displayed

### Scenario 7: Detail not found
**Given** I have a bookmarked Timekeeping Entry detail URL for an entry that does not exist  
**When** I open the URL  
**Then** I see a “not found” state  
**And** I can navigate back to the list screen

### Scenario 8: Timezone display rule is applied
**Given** I am viewing session start/end timestamps in the list or detail  
**When** my user profile timezone is available  
**Then** timestamps are displayed in my user timezone  
**And** when my user profile timezone is not available, timestamps are displayed in the relevant location timezone  
**And** the UI indicates which timezone is being used (label or tooltip)
