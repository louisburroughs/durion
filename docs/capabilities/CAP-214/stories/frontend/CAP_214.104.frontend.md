## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Topology: Sync Locations from durion-hr (Admin UI for LocationRef + SyncLog)  
**Primary Persona:** Inventory Admin / Ops Admin (with inventory topology permissions)  
**Business Value:** Ensures inventory operations are scoped to the authoritative roster of valid shops/mobile sites by providing visibility into synced LocationRefs and auditability of sync runs, and by preventing selection/use of deactivated/pending locations in inventory movement flows.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Inventory Admin (and the System via scheduled/event-driven sync),
- **I want** a frontend interface to view synced locations (LocationRef) and sync audit logs (SyncLog),
- **So that** I can confirm topology is up-to-date, detect drift/failures, and ensure users cannot initiate new stock movements to inactive/pending locations.

### In-scope
- Moqui/Quasar screens to:
  - List/search/view **LocationRef** records synced from `durion-hr` (read model owned by Inventory; HR is upstream SoR)
  - View **SyncLog** entries for runs/events and outcomes (immutable)
  - Provide “Sync now” (manual trigger) via Moqui proxy endpoint
- UI enforcement in inventory-related location pickers (where locations are selected) to block **INACTIVE** and **PENDING** locations from being selectable for **new** stock movements, consistent with backend rules.
- Display of location status/timezone/tags in location selection contexts.
- Permission-gated payload viewing for SyncLog detail.

### Out-of-scope
- Implementing the actual sync ingestion/reconciliation logic (backend responsibility)
- Automatic transfers/reconciliation workflows for any “PendingTransfer” stock (backend/domain policy; not a UI flow in this story)
- Editing HR-owned fields (name/status/timezone/tags) from the frontend (must be read-only)
- Defining/implementing permissions/roles beyond using existing authz checks from backend
- Any inventory ledger mutation UI (ledger is immutable; not part of topology screens)

---

## 3. Actors & Stakeholders
- **Inventory Admin / Ops Admin:** monitors location roster, audits sync runs, investigates failures
- **Warehouse Staff / Service Advisors:** choose locations for stock movements; must be prevented from using inactive/pending locations
- **SRE/Ops:** uses sync logs/correlation IDs to troubleshoot
- **durion-hr system:** authoritative topology source (upstream)

---

## 4. Preconditions & Dependencies

### Preconditions
- Moqui frontend calls **Moqui proxy** endpoints only (no direct Vue → inventory backend). (DECISION-INVENTORY-002)
- Inventory backend exposes the following Moqui-proxied endpoints (plain JSON, deterministic errors): (DECISION-INVENTORY-003, DECISION-INVENTORY-008)
  - `GET /inventory/locations` (LocationRef list)
  - `GET /inventory/locations/{locationId}` (LocationRef detail)
  - `GET /inventory/sync-logs` (SyncLog list)
  - `GET /inventory/sync-logs/{syncLogId}` (SyncLog detail; payload may be permission-gated)
  - `POST /inventory/locations/sync` (manual sync trigger; async)
- Inventory backend enforces movement eligibility and rejects movement attempts to `INACTIVE` or `PENDING` locations with deterministic validation errors (typically 422). UI must proactively block selection and also handle backend rejection. (DECISION-INVENTORY-009)

### Dependencies
- Backend story `durion-positivity-backend#40` (Topology: Sync Locations from durion-hr) implemented or mocked behind Moqui proxy.
- Existing inventory movement flows in this frontend must use a shared location picker component or be updated to use one (see In-scope enforcement). If no movement flows exist yet, implement the shared picker guard and apply it where possible; remaining screens become follow-up tasks.

### Resolution rationale (applied)
- **Permissions** are defined by Inventory domain rules and must be used for UI gating: `inventory:topology:view`, `inventory:topology:payload:view`, `inventory:topology:sync:trigger`. (DECISION-INVENTORY-010)
- **PENDING behavior** is resolved: treat `PENDING` like `INACTIVE` for new movements; allow read-only display. (DECISION-INVENTORY-009)
- **Manual sync trigger** is confirmed and returns `{ "syncRunId": "uuidv7" }`. (DECISION-INVENTORY-008)
- **Service contract shape** is resolved to concrete endpoints above; list endpoints use cursor pagination. (DECISION-INVENTORY-003, DECISION-INVENTORY-008)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Main navigation (permission-gated): **Inventory → Topology → Locations**
- Main navigation (permission-gated): **Inventory → Topology → Sync Logs**

### Screens to create/modify
1. **New Screen:** `apps/pos/inventory/topology/LocationRefList.xml`
   - List + filters + row navigation to detail
2. **New Screen:** `apps/pos/inventory/topology/LocationRefDetail.xml`
   - Read-only detail of a LocationRef + recent SyncLog entries for that `locationId` (or filterable link)
3. **New Screen:** `apps/pos/inventory/topology/SyncLogList.xml`
   - List + filters (date range, outcome, locationId, correlationId if present)
4. **New Screen (recommended for buildability):** `apps/pos/inventory/topology/SyncLogDetail.xml`
   - Read-only detail with safe JSON viewer; payload gated by permission
5. **Modify shared component(s):** Inventory location picker used by movement flows
   - Enforce that only `ACTIVE` locations are selectable for new movements
   - If an inactive/pending location is pre-populated (historical record), display read-only with a “not eligible for new movements” message

### Navigation context
- Location list → Location detail
- Sync log list → Sync log detail
- Cross-links:
  - Location detail → Sync log list filtered by `locationId`
  - Sync log detail → Location detail (if `locationId` present)

### User workflows
- **Happy path (admin visibility):**
  1. Admin opens Locations
  2. Filters by status, searches by name
  3. Opens a location to confirm status/timezone/tags and reviews recent sync outcomes
- **Alternate path (failure investigation):**
  1. Admin opens Sync Logs
  2. Filters to `FAILED` or `INVALID`
  3. Opens a log entry; views error message and (if permitted) payload in safe JSON viewer; copies correlation ID for support
- **Operational path (picker enforcement):**
  1. User opens a “new movement” screen
  2. Location picker shows only `ACTIVE` locations
  3. If a stale/ineligible location is present, UI blocks submit and instructs to select an active location; backend 422 is handled as defense-in-depth

## 6. Functional Behavior

### Triggers
- User navigates to Topology screens
- User searches/filters lists and paginates
- User opens details
- User clicks “Sync now” (manual trigger)

### UI actions
- Cursor pagination controls (Next/Previous) using `nextPageToken` (no total count reliance). (DECISION-INVENTORY-003)
- Filtering:
  - Locations: status (`ACTIVE|INACTIVE|PENDING`), text search (name)
  - Sync logs: outcome, date range, locationId, hrEventId (if present), correlationId (if present)
- Copy-to-clipboard for IDs (`locationId`, `syncLogId`, `hrEventId`, `X-Correlation-Id` when available)
- Safe JSON viewer for `tags` and SyncLog payload (preview in lists; expand in detail). (DECISION-INVENTORY-015)
- “Sync now”:
  - Disabled while in-flight
  - On success, show returned `syncRunId` and provide a “View latest logs” link (pre-filtered by recent time window)

### State changes
- No direct edits to LocationRef or SyncLog in UI.
- Manual sync trigger creates a backend sync run; new SyncLog entries appear asynchronously. (DECISION-INVENTORY-008)

### Service interactions
- All calls go to Moqui proxy endpoints; include/propagate `X-Correlation-Id` header and display it on error UI. (DECISION-INVENTORY-002, DECISION-INVENTORY-012)
- Location picker loads locations via `GET /inventory/locations` with filters to `status=ACTIVE` (or `isActive=true` if provided); UI must treat `PENDING` as ineligible. (DECISION-INVENTORY-009)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Read-only enforcement:
  - LocationRef fields are not editable in this story.
  - SyncLog fields are not editable in this story.
- Filters:
  - Date range: `from <= to`; block search when invalid.
  - Text inputs trimmed; whitespace-only treated as empty.
- Manual sync trigger:
  - No inputs in v1 (single button). If backend later adds inputs, they must be explicit and validated.

### Enable/disable rules
- **Topology navigation and screens**
  - Require `inventory:topology:view` to access list/detail screens; hide nav items when permission data is available; otherwise rely on 403 response handling. (DECISION-INVENTORY-010, DECISION-INVENTORY-012)
- **Sync payload visibility**
  - Payload section/button requires `inventory:topology:payload:view`. If user lacks it:
    - Do not request payload-heavy detail unless needed
    - If detail endpoint returns 403 for payload, show “Payload not permitted” and keep other fields visible. (DECISION-INVENTORY-010)
- **Manual sync trigger**
  - “Sync now” button requires `inventory:topology:sync:trigger`. (DECISION-INVENTORY-010)
- **Movement eligibility**
  - For any “new movement” flow location selection:
    - Only allow `LocationRef.status=ACTIVE` (or `isActive=true` if present and consistent)
    - Treat `PENDING` as ineligible (same as `INACTIVE`) (DECISION-INVENTORY-009)
    - If an ineligible location is prefilled (deep link/historical context), show it read-only and block submit for actions that create new movements.

### Visibility rules
- SyncLog error message shown when `outcome in (FAILED, INVALID, RETRY)` and `errorMessage` present.
- Large JSON fields:
  - List views show a truncated preview only; full view requires explicit expand or detail navigation. (DECISION-INVENTORY-015)

### Error messaging expectations
- 401: follow app convention to login/session refresh. (DECISION-INVENTORY-012)
- 403: “You do not have permission to view this resource.”
- 422 (movement attempt to inactive/pending location): “Location is not eligible for new stock movements. Select an active location.”
- Timeouts: show timeout at 8 seconds with Retry; do not auto-refresh loop. (DECISION-INVENTORY-004)
- Always show correlation ID in “Technical details” when available. (DECISION-INVENTORY-012)

- `status` (enum: `ACTIVE|INACTIVE|PENDING`, required, read-only)

- `effectiveFrom` / `effectiveTo` (datetime, optional, read-only)
- `createdAt`, `updatedAt` (datetime, optional, read-only)
- `deactivatedAt` (datetime, optional, read-only)

- `appliedAt` (datetime, required)
- `outcome` (enum: `OK|INVALID|RETRY|FAILED`, required)
- `errorMessage` (string, optional)
- `payload` (JSON, optional; permission-gated; render safely and never log) (DECISION-INVENTORY-011, DECISION-INVENTORY-015)
- `correlationId` (string, optional; display/copy when present) (DECISION-INVENTORY-012)

### Read-only vs editable by state/role

### Derived/calculated fields
- `displayStatus`: derived from `status` (single source; do not attempt to reconcile `isActive` if also present—prefer `status` for UI eligibility)
- `tagsPreview`: truncated safe string for list display
- `payloadPreview`: truncated safe string for list display

## 9. Service Contracts (Frontend Perspective)

> All calls are to Moqui same-origin proxy endpoints; responses are plain JSON; list endpoints use cursor pagination. (DECISION-INVENTORY-002, DECISION-INVENTORY-003)

### Load/view calls

#### LocationRef list
- **HTTP:** `GET /inventory/locations`
- **Query params (all optional unless noted):**
  - `status` (string enum: `ACTIVE|INACTIVE|PENDING`)
  - `q` (string; free-text search across name and hrLocationId if supported; otherwise name-only)
  - `pageSize` (int)
  - `pageToken` (string cursor)
- **Response (plain JSON):**
  - `{ "items": [LocationRefSummary...], "nextPageToken": "..."? }`

#### LocationRef detail
- **HTTP:** `GET /inventory/locations/{locationId}`
- **Response:** `LocationRef` object (plain JSON)

#### SyncLog list
- **HTTP:** `GET /inventory/sync-logs`
- **Query params (optional):**
  - `locationId` (UUIDv7)
  - `outcome` (enum)
  - `hrEventId` (string)
  - `fromDate` (ISO datetime)
  - `toDate` (ISO datetime)
  - `pageSize` (int)
  - `pageToken` (string)
- **Response:** `{ "items": [SyncLogSummary...], "nextPageToken": "..."? }`

#### SyncLog detail
- **HTTP:** `GET /inventory/sync-logs/{syncLogId}`
- **Response:** `SyncLog` object
- **Payload gating behavior:**
  - If user lacks `inventory:topology:payload:view`, backend may:
    - omit `payload`, or
    - return 403 when requesting detail/payload
  - UI must handle both without breaking the page. (DECISION-INVENTORY-010)

### Create/update calls

#### Manual sync trigger
- **HTTP:** `POST /inventory/locations/sync`
- **Request body:** empty `{}` (v1)
- **Response:** `{ "syncRunId": "uuidv7" }` (DECISION-INVENTORY-008)
- **UI behavior:** disable button while in-flight; do not auto-retry; provide refresh affordance.

### Submit/transition calls
- None for topology entities.

### Error handling expectations (deterministic)
- 400/422: show validation message; map field errors to filters/forms when applicable. (DECISION-INVENTORY-003)
- 401: route to login/session refresh. (DECISION-INVENTORY-012)
- 403: forbidden state; do not leak data. (DECISION-INVENTORY-012)
- 404: not found state with link back to list
- 409: if returned (optimistic lock on triage screens), show “Data changed; refresh” (not expected for read-only topology, but handle generically)
- 5xx/timeout: show retry; include correlation ID if present; do not log payloads/quantities. (DECISION-INVENTORY-011, DECISION-INVENTORY-012)

## 10. State Model & Transitions

### Allowed states (LocationRef.status)
- `ACTIVE`: selectable for new stock movements
- `INACTIVE`: not selectable for new stock movements
- `PENDING`: not selectable for new stock movements; display-only (treated like inactive for eligibility) (DECISION-INVENTORY-009)

### Role-based transitions
- No frontend transitions. Status changes come from HR sync and are reflected in LocationRef read model. (DECISION-INVENTORY-008)

### UI behavior per state
- ACTIVE:
  - Appears in operational pickers
  - Normal display in topology screens
- INACTIVE:
  - Excluded from operational pickers by default
  - Visible in topology screens with “Inactive” badge and deactivated timestamp when available
- PENDING:
  - Excluded from operational pickers by default
  - Visible in topology screens with “Pending” badge and explanatory helper text: “Pending locations are not eligible for new movements until activated.”

## 11. Alternate / Error Flows

### Validation failures
- Date range invalid (`fromDate > toDate`): prevent search; show inline error.
- Manual sync trigger:
  - 403: show forbidden toast/banner; keep user on page
  - 5xx/timeout: show retry; do not auto-retry

### Concurrency conflicts
- Not applicable for read-only lists/details; if 409 occurs unexpectedly, show “This data changed; refresh.”

### Unauthorized access
- If user lacks `inventory:topology:view`:
  - Navigation items hidden when permission data is available
  - Direct URL access returns 403 state with no data rendered (DECISION-INVENTORY-012)

### Empty states
- Locations list empty:
  - Show “No locations synced yet.”
  - If user has `inventory:topology:sync:trigger`, show “Sync now” CTA; otherwise show instruction to contact admin/SRE.
- Sync logs list empty:
  - Show “No sync activity recorded for the selected filters.”

### Payload access denied (partial detail)
- If SyncLog detail loads but payload is omitted or forbidden:
  - Render other fields
  - Render payload section as “Not permitted” with required permission string shown (no payload content)

## 12. Acceptance Criteria

### Scenario 1: View synced locations list (cursor pagination)
**Given** the user has permission `inventory:topology:view`  
**When** they open “Inventory → Topology → Locations”  
**Then** the system displays a cursor-paginated list of LocationRefs including `locationId`, `hrLocationId`, `name`, `status`, and `timezone` (if present)  
**And** the user can filter by `status` including `ACTIVE`, `INACTIVE`, `PENDING`  
**And** pagination uses `nextPageToken` (no reliance on total count).

### Scenario 2: View a location detail and navigate to related sync logs
**Given** at least one LocationRef exists  
**When** the user opens a LocationRef detail page  
**Then** the system shows the LocationRef fields as read-only (including `status`, `timezone`, `tags` rendered safely)  
**And** the page provides a link to “View Sync Logs” pre-filtered by that `locationId`.

### Scenario 3: View sync logs, filter failures, and inspect detail
**Given** the user has permission `inventory:topology:view`  
**And** SyncLog entries exist with outcomes `FAILED` or `INVALID`  
**When** the user opens “Inventory → Topology → Sync Logs” and filters to `FAILED`  
**Then** the list shows matching entries with `syncLogId`, `appliedAt`, `outcome`, and `errorMessage` summary  
**And** the user can open a SyncLog detail page.

### Scenario 4: SyncLog payload visibility is permission-gated
**Given** a SyncLog entry exists with a payload  
**And** the user has `inventory:topology:view` but lacks `inventory:topology:payload:view`  
**When** the user opens the SyncLog detail page  
**Then** the page renders non-payload fields  
**And** the payload section indicates access is not permitted  
**And** no payload content is displayed.

### Scenario 5: Manual “Sync now” trigger (authorized)
**Given** the user has permission `inventory:topology:sync:trigger`  
**When** they click “Sync now”  
**Then** the UI disables the button while the request is in-flight  
**And** on success displays the returned `syncRunId`  
**And** provides a way to navigate to Sync Logs (e.g., link with a recent time filter) without auto-refresh loops.

### Scenario 6: Inactive/Pending locations are not selectable for new stock movements
**Given** a LocationRef exists with status `INACTIVE`  
**And** another LocationRef exists with status `PENDING`  
**When** a user opens any “new stock movement” screen that uses the shared location picker  
**Then** only `ACTIVE` locations are selectable  
**And** `INACTIVE` and `PENDING` locations are hidden or disabled with an explanation “Not eligible for new movements.”

### Scenario 7: Backend rejects movement due to ineligible location (defense in depth)
**Given** the user submits a stock movement referencing an `INACTIVE` or `PENDING` location due to stale UI state  
**When** the backend responds with HTTP 422 and a deterministic error indicating ineligible location  
**Then** the frontend displays “Location is not eligible for new stock movements. Select an active location.”  
**And** the user remains on the form with inputs preserved  
**And** the error UI includes the `X-Correlation-Id` if provided.

### Scenario 8: Permissions enforced for topology screens
**Given** the user lacks permission `inventory:topology:view`  
**When** they navigate directly to the Locations or Sync Logs URL  
**Then** the frontend shows a forbidden state (403)  
**And** no topology data is displayed.
