## Issue Body

## As a / I want / So that
- **As an** Inventory Manager  
- **I want** to configure a site’s default **Staging** and **Quarantine** storage locations  
- **So that** receiving and quality-hold processes can reliably place inventory into the correct initial storage area.

## In-scope
- A frontend configuration UI (Moqui screen + Vue/Quasar components) to:
  - View current site default staging/quarantine storage locations
  - Select/update each default location from eligible storage locations within the site
  - Validate and submit changes
  - Handle null defaults during rollout/migration (show “Not configured” and allow setting)
- Enforce the business rule that staging and quarantine defaults **must be distinct** (DECISION-LOCATION-010)
- Filter picker options to **ACTIVE** storage locations only (DECISION-LOCATION-024)
- Display current configuration and last-updated metadata **if available** from backend (DECISION-LOCATION-020 pattern; otherwise show core fields only)

## Out-of-scope
- Receiving execution behavior (“receiving uses staging by default”) — handled by separate stories
- Permission model design (role taxonomy) — enforced server-side; UI only gates based on `403` and optional permission claims (DECISION-LOCATION-007)
- CRUD for Storage Locations themselves (Inventory domain SoR)
- Cross-site transfers, hierarchy edits, or barcode scanning flows

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated in the frontend.
- The system has:
  - A **Site** (represented as a Location/site record) with a unique `siteId`
  - **Storage Locations** that belong to a site (Inventory domain SoR)

## Dependencies
- Backend capability to:
  - Retrieve a site’s current default location configuration (nullable during rollout) (DECISION-LOCATION-023)
  - List storage locations for a given site with status filtering (ACTIVE) (DECISION-LOCATION-024)
  - Update the site’s default staging/quarantine storage location IDs
- Authorization enforcement exists server-side (frontend must handle 401/403) (DECISION-LOCATION-007)
- Backend enforces:
  - storage location belongs to site
  - staging != quarantine (error code `DEFAULT_LOCATION_ROLE_CONFLICT`) (DECISION-LOCATION-010)

**Decision rationale applied (traceability):**
- **Nullability during rollout** is explicitly allowed (DECISION-LOCATION-023), so UI must support “Not configured”.
- **Eligibility** is ACTIVE-only for pickers (DECISION-LOCATION-024).
- **Distinctness** is mandatory (DECISION-LOCATION-010).

# 7. Business Rules (Translated to UI Behavior)

## Validation
- **Required to save:** both staging and quarantine must be selected (non-null) when submitting an update.
  - Note: existing persisted values may be null during rollout; UI must allow viewing nulls without forcing immediate change (DECISION-LOCATION-023).
- **Distinctness:** staging location ID must not equal quarantine location ID (DECISION-LOCATION-010).
- **Eligibility:** pickers show **ACTIVE** storage locations only (DECISION-LOCATION-024).
- **Belongs-to-site:** frontend only lists storage locations for the current site; still rely on backend validation.

## Enable/disable rules
- Save button enabled only when:
  - user is authorized to manage (either via known permission claim if available, or inferred by allowing edit and handling 403 on save)
  - both fields selected
  - staging != quarantine
  - form is dirty
- During save: disable inputs and show loading state.

## Visibility rules
- Always show current values:
  - If null: show “Not configured” (DECISION-LOCATION-023).
- If user lacks permission:
  - show read-only view of current defaults (if GET allowed)
  - hide/disable Save and show message “You do not have permission to update site defaults.”

## Error messaging expectations
- `DEFAULT_LOCATION_ROLE_CONFLICT`: “Staging and quarantine locations must be different.”
- `401`: prompt re-authentication (standard app behavior)
- `403`: “You do not have permission to update default locations for this site.”
- `404` site not found: “Site not found or you no longer have access.”
- `400/422`: surface field-level errors if backend provides them; otherwise show general error banner.

# 9. Service Contracts (Frontend Perspective)

> Use Location-domain REST convention prefix `/rest/api/v1/location/...` for Moqui-exposed services (DECISION-LOCATION-006). Inventory-owned lookups may live under `/rest/api/v1/inventory/...`. Exact endpoint names must be confirmed in implementation PR, but the frontend must follow these conventions.

## Load/view calls

1. **Get site defaults (Location domain)**
   - `GET /rest/api/v1/location/sites/{siteId}/default-locations`
   - Response (minimum):
     ```json
     {
       "siteId": "…",
       "defaultStagingLocationId": null,
       "defaultQuarantineLocationId": null,
       "updatedAt": "2026-01-01T12:00:00Z",
       "updatedBy": "…",
       "version": 3
     }
     ```
   - `default*` fields may be null (DECISION-LOCATION-023).

2. **Get site context (optional, for header)**
   - `GET /rest/api/v1/location/sites/{siteId}`
   - Response includes `code`, `name` (and optionally timezone).

3. **List eligible storage locations (Inventory domain)**
   - `GET /rest/api/v1/inventory/sites/{siteId}/storage-locations?status=ACTIVE&pageIndex=0&pageSize=50`
   - Response envelope:
     ```json
     { "items": [ { "storageLocationId":"…","name":"…","barcode":null,"status":"ACTIVE" } ], "totalCount": 123 }
     ```
   - Picker must support pagination/search if `totalCount` exceeds page size.

## Create/update calls

- **Update site default locations (Location domain)**
  - `PUT /rest/api/v1/location/sites/{siteId}/default-locations`
  - Request:
    ```json
    {
      "defaultStagingLocationId": "…",
      "defaultQuarantineLocationId": "…",
      "version": 3
    }
    ```
  - Success:
    - `200 OK` with updated config (preferred), or
    - `204 No Content` (UI must re-GET)

## Submit/transition calls
- Moqui `transition` for Save triggers service call; screen should be implementable either as:
  - direct REST calls from Vue client, or
  - Moqui screen transitions invoking services that proxy to backend modules.
- Do not invent additional side effects (no receiving workflow triggers).

## Error handling expectations
- `400/422` with field errors and/or `code`
  - `DEFAULT_LOCATION_ROLE_CONFLICT` → map to both selectors
  - `DEFAULT_LOCATION_NOT_IN_SITE` (example) → map to the offending selector
  - `STORAGE_LOCATION_INACTIVE` (example) → map to selector and instruct to choose ACTIVE
- `403` forbidden
- `404` site not found
- `409 OPTIMISTIC_LOCK_FAILED` if `version` is used (preferred pattern in domain guide)

# 11. Alternate / Error Flows

## Validation failures
- Same staging/quarantine selected:
  - Block Save; show inline message.
- Missing selection:
  - Block Save; show required indicator.

## Concurrency conflicts
- If backend uses optimistic locking and returns `409 Conflict` with `OPTIMISTIC_LOCK_FAILED`:
  - Show message: “This configuration was updated by someone else. Reload and try again.”
  - Provide “Reload” action that re-fetches defaults and resets form.

## Unauthorized access
- `401`: route to login per app standard, then return to same screen.
- `403`:
  - If load succeeded: keep showing read-only values with permission warning.
  - If save attempted: show permission error; do not clear user selections.

## Empty states
- No active storage locations returned:
  - Show empty state: “No active storage locations exist for this site. Create one before configuring defaults.”
  - Provide navigation link to storage locations list (if available).

# 12. Acceptance Criteria

## Scenario 1: View current defaults (including nulls during rollout)
**Given** I am an authenticated user with permission to view site configuration  
**And** Site “WH-1” exists  
**And** the backend returns `defaultStagingLocationId = null` and `defaultQuarantineLocationId = null`  
**When** I navigate to the Site Default Locations screen for “WH-1”  
**Then** I see “Not configured” for both defaults  
**And** I see pickers populated with ACTIVE storage locations for “WH-1”.

## Scenario 2: Update defaults successfully
**Given** I am authenticated as a user authorized to manage site defaults  
**And** Site “WH-1” has ACTIVE storage locations “STAGING-A” and “QUARANTINE-B”  
**When** I set Default Staging Location to “STAGING-A”  
**And** I set Default Quarantine Location to “QUARANTINE-B”  
**And** I click Save  
**Then** the frontend sends `PUT /rest/api/v1/location/sites/{siteId}/default-locations` with both IDs  
**And** staging and quarantine IDs are different  
**And** I see a success confirmation  
**And** reloading the screen shows the saved defaults.

## Scenario 3: Client-side reject duplicate role assignment
**Given** I am authorized to manage site defaults  
**And** “COMMON-AREA” is an ACTIVE storage location in site “WH-1”  
**When** I select “COMMON-AREA” for both staging and quarantine  
**Then** the Save action is disabled (or blocked)  
**And** I see an inline validation message stating the locations must be distinct  
**And** no update request is sent.

## Scenario 4: Server-side reject duplicate role assignment (defense in depth)
**Given** I am authorized to manage site defaults  
**And** I submit an update where staging and quarantine IDs are the same (via any client manipulation)  
**When** the backend responds with `400` and error code `DEFAULT_LOCATION_ROLE_CONFLICT`  
**Then** the frontend shows an inline error on both selectors  
**And** the message states staging and quarantine must be distinct  
**And** the user’s selections remain in the form for correction.

## Scenario 5: Reject unauthorized update
**Given** I am an authenticated user without permission to manage site defaults  
**When** I attempt to Save changes to default staging/quarantine locations  
**Then** the backend responds with `403 Forbidden`  
**And** the frontend displays a permission error  
**And** the configuration remains unchanged in the UI after reload.

## Scenario 6: Picker eligibility filters to ACTIVE only
**Given** I am viewing the Site Default Locations screen for “WH-1”  
**And** “OLD-STAGING” is an INACTIVE storage location in “WH-1”  
**When** the storage location picker options load  
**Then** “OLD-STAGING” is not available for selection  
**And** only ACTIVE storage locations are selectable.

## Scenario 7: Optimistic locking conflict on save
**Given** I am authorized to manage site defaults  
**And** I loaded the screen with `version = 3`  
**And** another user updates the defaults causing the backend version to become `4`  
**When** I click Save with `version = 3`  
**Then** the backend responds with `409` and code `OPTIMISTIC_LOCK_FAILED`  
**And** the UI shows a reload prompt  
**And** when I click Reload, the UI fetches and displays the latest defaults.
