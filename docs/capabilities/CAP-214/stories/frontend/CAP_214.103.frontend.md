## 1. Story Header

### Title
[FRONTEND] [STORY] Topology: Create/Update/Deactivate Storage Locations (Floor/Shelf/Bin/Cage/Yard/MobileTruck/Quarantine) with Site Hierarchy

### Primary Persona
Inventory Manager

**Persona Metadata**
- `primary_persona`: `Inventory Manager`
- `canonical_persona`: `Inventory Control Manager`
- `persona_family`: `Inventory Management`
- `actor_type`: `human`

### Business Value
Enables precise stock tracking and operational picking/putaway by allowing the business to define an auditable, cycle-free storage location hierarchy within each site (`LocationRef`), with barcode uniqueness enforcement, controlled deactivation, and safe handling of JSON metadata fields.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Inventory Manager  
- **I want** to create, edit, and deactivate storage locations (bins) within a site and organize them into a parent/child hierarchy  
- **So that** inventory can be tracked and referenced accurately by `storageLocationId` across operational workflows (e.g., picking/putaway, transfers, adjustments)

### In-scope
- Moqui/Vue/Quasar frontend screens and flows to:
  - List storage locations by site (`locationId`)
  - Create a storage location (optionally as a child of another storage location)
  - Update a storage location (including changing parent, with cycle prevention)
  - Deactivate a storage location
    - If non-empty: require selecting a destination storage location in the same site for transfer (destination-required semantics)
- Frontend validation and error display aligned to backend rules:
  - Barcode is unique within a site
  - Prevent hierarchy cycles (UI prevents obvious cases; backend is authoritative)
  - Storage types are backend-owned enums; UI loads from meta endpoint
  - `storageType` is immutable after creation
- JSON field handling:
  - `tags`, `capacity`, `temperature` treated as opaque JSON; validate JSON syntax only; render safely (escape + truncate + expand/copy)
- Permission-gated access and actions per inventory permission conventions

### Out-of-scope
- Graphical topology map/tree visualization beyond basic hierarchical navigation (optional later)
- Managing inventory quantities themselves, cycle counts, or general transfer workflows outside the deactivation destination requirement
- Reactivation of inactive storage locations (not supported in v1)
- Defining new storage types in the UI (types are consumed from backend enumeration)
- Any direct Vue → inventory backend calls (must use Moqui proxy)

## 7. Business Rules (Translated to UI Behavior)

### Validation
**Create (required):** (DECISION-INVENTORY-007)
- `locationId` (site) required
- `name` required (trim; non-empty)
- `barcode` required (trim; non-empty)
- `storageType` required (must be one of values from `GET /inventory/meta/storage-types`)
- `parentStorageLocationId` optional; if provided must:
  - belong to same `locationId`
  - not equal to self (N/A on create)
  - not create a cycle (backend authoritative)

**Update:**
- `storageType` is immutable after creation; UI must render it read-only/disabled on edit (DECISION-INVENTORY-007)
- `barcode` remains required and trimmed if editable; backend enforces uniqueness per site
- `capacity` and `temperature` are freeform JSON objects; validate JSON syntax only (DECISION-INVENTORY-015)

**Barcode uniqueness within site:**
- UI performs trim + non-empty validation only; backend is authoritative for uniqueness (DECISION-INVENTORY-003, DECISION-INVENTORY-007)

**Cycle prevention:**
- UI must prevent selecting self as parent.
- UI should attempt to prevent obvious cycles if it has enough hierarchy info; otherwise rely on backend deterministic error and show it on parent field (DECISION-INVENTORY-007)

### Enable/disable rules
- If `status=INACTIVE`:
  - Deactivate action hidden/disabled
  - “Operational” actions are not present in this story; however, parent/destination pickers must exclude inactive by default
  - Editing is allowed for non-operational metadata only; UI allows editing fields but must:
    - keep `storageType` read-only
    - keep status read-only
    - handle backend rejections deterministically (DECISION-INVENTORY-007)
- Parent picker:
  - Only shows storage locations within the same `locationId`
  - Excludes inactive by default; provide an explicit toggle “Include inactive parents” for historical organization (optional UI control; default OFF) (DECISION-INVENTORY-007)
- Destination picker (deactivation):
  - Only Active storage locations in same `locationId`
  - Must exclude the source storage location

### Visibility rules
- Destination selector is hidden until backend indicates it is required (via deterministic error on deactivate without destination).
- JSON fields (`tags`, `capacity`, `temperature`) are shown using safe JSON viewer/editor controls; list views show truncated previews only (DECISION-INVENTORY-015).

### Error messaging expectations
- Field-level errors map to fields when possible:
  - `barcode` duplicate → barcode field error “Barcode must be unique within the site.”
  - `parentStorageLocationId` invalid/cycle → parent field error with backend message
- Deactivation:
  - Destination required → inline message “Destination is required to deactivate a non-empty storage location.”
  - Invalid destination → inline message “Destination must be Active and in the same site.”
- All error states show correlation ID in “Technical details” when available (DECISION-INVENTORY-012).

## 9. Service Contracts (Frontend Perspective)

> Integration pattern is fixed: Vue calls Moqui proxy endpoints only (DECISION-INVENTORY-002). Responses are plain JSON (no `{data: ...}` envelope) and errors follow deterministic schema (DECISION-INVENTORY-003). All list endpoints use cursor pagination (`pageSize`, `pageToken`, `nextPageToken`) (DECISION-INVENTORY-003).

### Load/view calls
1. **List sites (LocationRef)**
   - `GET /inventory/locations`
   - Query (optional): `status=ACTIVE` (if supported); otherwise client filters for picker display
   - Response: array of `{ locationId, name, status, ... }`
   - UI rule: sites with `status INACTIVE|PENDING` may be shown but clearly labeled; selection for topology management is allowed (topology is not a “movement flow”), but backend may still restrict—handle 422/403 if returned.

2. **List storage types**
   - `GET /inventory/meta/storage-types`
   - Response: array of strings or objects; UI must support either:
     - `["Floor","Shelf",...]` OR
     - `[{ "storageType": "Floor", "description": "..." }, ...]`
   - UI rule: treat as backend-owned; do not hardcode.

3. **List storage locations by site**
   - `GET /inventory/storage-locations?locationId={locationId}&pageSize={n}&pageToken={token?}&status={...}&storageType={...}&search={...}`
   - Response (plain JSON):
     - `{ items: [StorageLocationSummary...], nextPageToken: "..."? }` OR
     - If backend returns `{ data: ..., nextPageToken: ... }` this would contradict DECISION-INVENTORY-003; treat as a defect and raise.
   - UI must not rely on `totalCount`.

4. **Get storage location detail**
   - `GET /inventory/storage-locations/{storageLocationId}`
   - Response: full `StorageLocation` record, including `locationId`, `status`, and JSON fields.

### Create/update calls
1. **Create storage location**
   - `POST /inventory/storage-locations`
   - Body (plain JSON):
     - `{ locationId, name, barcode, storageType, parentStorageLocationId?, tags?, capacity?, temperature? }`
   - Success: returns created record or at minimum `{ storageLocationId }`
   - Client behavior:
     - Disable submit while in-flight
     - On success navigate to detail

2. **Update storage location**
   - `PUT /inventory/storage-locations/{storageLocationId}`
   - Body: editable fields only; UI must not send `storageType` changes (DECISION-INVENTORY-007)
   - Success: returns updated record or 204; UI then reloads detail

### Submit/transition calls
1. **Deactivate storage location**
   - `POST /inventory/storage-locations/{storageLocationId}/deactivate`
   - Body:
     - `{ destinationStorageLocationId? }` (field name must match backend; if backend expects `destinationLocationId`, map accordingly in Moqui proxy; UI should use `destinationStorageLocationId` in its internal model and let the proxy adapt if needed)
   - Success: returns updated record or `{ status: "INACTIVE" }`
   - Deterministic errors:
     - Destination required when non-empty and no destination provided (DECISION-INVENTORY-007)
     - Invalid destination (different site, inactive, self)

### Error handling expectations
- 400/422 validation: map field errors to form fields when possible; otherwise show banner.
- 401: route to login/session refresh per app convention (DECISION-INVENTORY-012).
- 403: show forbidden state; do not leak data; hide write actions when permission info is available (DECISION-INVENTORY-012).
- 404: show “Not found” and provide link back to list.
- 409: show conflict message (concurrency/optimistic lock) and provide refresh.
- 5xx/timeout:
  - Show timeout at 8 seconds with retry affordance; no auto-retry loops (DECISION-INVENTORY-004).
- Observability:
  - Capture and display `X-Correlation-Id` in error UI “Technical details” (DECISION-INVENTORY-012).
  - Do not log JSON payloads or quantities (not applicable here except payload-like JSON fields; still treat as sensitive-by-default for logs) (DECISION-INVENTORY-011, DECISION-INVENTORY-015).

## 11. Alternate / Error Flows

### Validation failures
- **Duplicate barcode within site**
  - Backend returns deterministic field error; UI highlights barcode field and keeps user input.
- **Cycle detected / invalid parent**
  - Backend rejects; UI shows error on parent field; does not update displayed hierarchy until a successful save + reload.
- **Invalid JSON in capacity/temperature/tags**
  - Client blocks submit with “Invalid JSON” and points to the JSON editor field.

### Concurrency conflicts
- If backend returns 409 conflict (optimistic locking/version mismatch):
  - UI shows banner “This storage location was updated by someone else. Refresh to load the latest version.”
  - Provide “Refresh” action that reloads detail and re-enables editing.

### Unauthorized access
- **401**
  - Redirect to login/session refresh flow; after auth, return to intended route (DECISION-INVENTORY-012).
- **403**
  - If on list/detail: show forbidden state.
  - If on mutation submit: show forbidden banner and keep user input; do not retry automatically.

### Empty states
- **No site selected**
  - Show “Select a site to view storage locations.”
- **No storage locations for selected site**
  - Show empty state with CTA “Create first storage location.”
- **No sites available**
  - Show blocking message “No sites available. Contact an administrator.”

**And** the UI displays the error on the barcode field  
**And** the record is not created.

**Then** the `storageType` field is read-only/disabled

### Scenario 6: Reject hierarchy changes that would create a cycle
**Given** a hierarchy exists in site `L1` where `A` is parent of `B` and `B` is parent of `C`  
**When** I attempt to edit `A` and set its parent to `C`  
**Then** the backend rejects the update with a deterministic cycle error  
**And** the UI displays the error on the parent field  
**And** after refresh, `A` still has no parent (or its prior parent).

### Scenario 7: Deactivate an empty location
**Given** an ACTIVE storage location `Cage-03` exists and is eligible for deactivation without a destination  
**When** I deactivate `Cage-03` and confirm  
**Then** the UI calls `POST /inventory/storage-locations/<id>/deactivate` without a destination  
**And** the UI shows `status=INACTIVE` after success  
**And** the Deactivate action is no longer available.

### Scenario 8: Require destination when deactivating a non-empty location
**Given** an ACTIVE storage location `Bin-12` exists and requires a destination to deactivate  
**When** I deactivate `Bin-12` without selecting a destination  
**Then** the backend returns a deterministic error indicating destination is required  
**And** the UI prompts for a destination storage location in the same site  
**And** `Bin-12` remains `ACTIVE` until a successful deactivation.

### Scenario 9: Deactivate non-empty location with valid transfer destination
**Given** an ACTIVE storage location `Bin-12` exists in site `L1`  
**And** an ACTIVE storage location `Bin-13` exists in the same site `L1`  
**When** I deactivate `Bin-12` and select `Bin-13` as the destination  
**Then** the UI calls `POST /inventory/storage-locations/<Bin-12>/deactivate` with destination `Bin-13`  
**And** the UI reports success  
**And** `Bin-12` becomes `INACTIVE`.

### Scenario 10: 401/403 handling includes correlation ID
**Given** I attempt an action on any topology screen  
**When** the server responds with 401  
**Then** the UI routes me to login/session refresh flow  
**When** the server responds with 403

**And** if `X-Correlation-Id` is present, it is shown in “Technical details”.
