## 2. Story Intent

### As a / I want / So that
**As a** Shop Manager / Dispatcher,  
**I want** to assign (and reassign) a primary technician (and optionally additional technicians if supported) to a work order that is ready to be worked,  
**so that** the right technician can see and execute the work order and the assignment is tracked with an auditable history.

### In-scope
- View current technician assignment for a Work Order.
- Assign a primary technician to a Work Order when allowed by Work Order status and permissions.
- Reassign the primary technician while retaining history (append-only).
- Display assignment history (who/when/reason; prior assignment end time).
- Enforce authorization failures in the UI (no silent failures).
- Reflect assignment in UI behavior (e.g., show assigned technician on Work Order; technician visibility is assumed to be enforced by backend filtering/permissions).

### Out-of-scope
- Defining/implementing technician availability and schedule policy (warn vs block). (People domain SoR; workexec consumes read-only signals only.)
- Implementing notification delivery channels/templates.
- Creating new backend entity/schema; frontend consumes existing Moqui services/entities.
- Any scheduling/bay/appointment authoring (shopmgr SoR).

## 6. Functional Behavior

### Triggers
- User initiates “Assign” or “Reassign” from Work Order detail.

### UI actions
- Load Work Order detail (including status and current `mechanicId`/technician display).
- Load eligible technicians list via picker/search.
- Validate required fields client-side:
  - technician selection required
  - reason optional (unless backend returns field error requiring it)
- Submit assignment mutation with `Idempotency-Key`.
- On success: refresh Work Order detail and assignment history.
- On failure: display error using standard envelope; refresh on 409 to resolve stale state.

### State changes (frontend-observed)
- Work Order may transition to `ASSIGNED` upon successful assignment (consistent with WORKORDER_STATE_MACHINE.md and DECISION-INVENTORY-004 “started gating”).
- Reassignment results in a new active assignment record and closes the previous one (append-only history).

### Service interactions (high-level)
- Fetch Work Order detail (workexec).
- Fetch eligible technicians (People domain or workexec-provided view; read-only).
- Submit assignment (workexec mutation).
- Fetch assignment history (workexec; may be embedded in detail or separate).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Technician selection is required to submit.
- IDs are opaque strings; UI must not enforce formatting beyond non-empty.
- Work Order must be in an allowed status for assignment/reassignment:
  - **Allowed**: `APPROVED`, `ASSIGNED`
  - **Manager-only override allowed** after start is a concept for operational context overrides (DECISION-INVENTORY-005) and does **not** automatically apply to technician assignment; therefore assignment after start is **not allowed** in this story unless backend explicitly supports it.
- Only one active primary technician assignment at a time (represented by `DurWorkOrder.mechanicId`).

### Enable/disable rules
- “Assign/Reassign” action is enabled only when:
  - user has capability/permission to assign (see Visibility rules)
  - Work Order status is `APPROVED` or `ASSIGNED`
- Submit button disabled until technician selected.
- Reason field is optional; if backend returns a field error for `reason`, UI must show it and require correction.

### Visibility rules
- Assignment section visible to users who can view the Work Order.
- Assignment action visible only if capability flag indicates permission (preferred) and/or backend allows:
  - Capability name is implementation-defined; UI must use a stable capability flag from user context when available (DECISION-INVENTORY-013).
- Assignment history is read-only.

### Error messaging expectations
Use standard error envelope (DECISION-INVENTORY-011):
- 403 → “You don’t have permission to assign technicians.”
- 404 → “Work order not found or you no longer have access.”
- 409 (invalid state / stale update) → “This work order changed since you opened it. Refreshing…” then refresh.
- 400 validation → show field-level errors when provided; otherwise show banner with `message` and include `correlationId` in a “Details” affordance.

3. **Technician picker search**
   - REST read (People domain) or workexec-provided view:
     - `GET /rest/api/v1/people/technicians?query={q}&locationId={locationId?}&pageIndex=0&pageSize=20`
   - Must return: `technicianId`, `displayName`

### Create/update calls
**Assign/Reassign primary technician**

  - Inputs:
    - `workOrderId`
    - `technicianId` (maps to `mechanicId`)
    - `reason` (optional)
    - `Idempotency-Key` header (if using REST) or request attribute (if Moqui supports header passthrough)

  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/assign-technician`

### Error handling expectations

- On retry/double-submit, backend must honor `Idempotency-Key` (DECISION-INVENTORY-012); UI must reuse the same key for the same attempt.

## 10. State Model & Transitions

### Allowed states (workexec)
From WORKORDER_STATE_MACHINE.md:
- `DRAFT`, `APPROVED`, `ASSIGNED`, `WORK_IN_PROGRESS`, `AWAITING_PARTS`, `AWAITING_APPROVAL`, `READY_FOR_PICKUP`, `COMPLETED`, `CANCELLED`

### Role-based transitions (relevant to this story)
- Assignment is permitted only before “started”.
- “Started” means `WO_IN_PROGRESS` or later in Moqui taxonomy (DECISION-INVENTORY-004). Mapping to the state machine doc:
  - Treat `WORK_IN_PROGRESS`, `AWAITING_PARTS`, `AWAITING_APPROVAL`, `READY_FOR_PICKUP`, `COMPLETED` as started/post-start.
- Therefore:
  - **Assign** allowed in `APPROVED` (pre-start).
  - **Reassign** allowed in `ASSIGNED` (pre-start).
  - **Not allowed** in any started/post-start status for this story (unless backend explicitly supports manager-only reassignment; not specified by workexec decisions).

### UI behavior per state
- `DRAFT`: assignment controls hidden/disabled.
- `APPROVED`: assignment enabled (if permitted).
- `ASSIGNED`: reassignment enabled (if permitted).
- `WORK_IN_PROGRESS` / `AWAITING_PARTS` / `AWAITING_APPROVAL` / `READY_FOR_PICKUP`: assignment controls disabled with message “Assignment is locked after work has started.”
- `COMPLETED` / `CANCELLED`: assignment controls disabled; history visible.

## 11. Alternate / Error Flows

### Validation failures
- No technician selected → inline error; no request sent.
- Backend returns 400 with `fieldErrors` (e.g., invalid technician) → show inline error on picker.

### Concurrency conflicts
- If another user changes assignment/status while dialog open:
  - Backend returns 409 with `code=CONFLICT` (or similar) and `correlationId`.
  - UI shows conflict banner and refreshes Work Order detail and history; dialog closes by default.

### Unauthorized access
- If capability indicates no permission: hide/disable action.
- If user attempts via direct URL/action and backend returns 403: show forbidden message and keep page read-only.

### Empty states
- No eligible technicians returned:
  - Show “No technicians found for this location/search.”
  - Provide retry and allow clearing filters/search.

## 12. Acceptance Criteria

### Scenario 1: Assign technician to an APPROVED work order
**Given** I am logged in as a Shop Manager/Dispatcher with permission to assign technicians  
**And** a Work Order exists with status `APPROVED`  
**When** I assign Technician A as the primary technician and submit  
**Then** the Work Order displays Technician A as the current assigned technician  
**And** the Work Order status is `ASSIGNED` if the backend transitions status on assignment  
**And** an assignment history entry exists showing `assignedAt` and `assignedBy`

### Scenario 2: Reassign technician preserves history
**Given** I am logged in with permission to assign technicians  
**And** a Work Order exists with status `ASSIGNED`  
**And** Technician A is currently assigned  
**When** I reassign the Work Order to Technician B and submit  
**Then** the Work Order displays Technician B as the current assigned technician  
**And** the assignment history shows Technician A with a populated `unassignedAt`  
**And** the assignment history shows Technician B as the active assignment (no `unassignedAt`)

### Scenario 3: Assignment is blocked after work has started
**Given** I am logged in with permission to assign technicians  
**And** a Work Order exists with status `WORK_IN_PROGRESS` (or `AWAITING_PARTS`, `AWAITING_APPROVAL`, `READY_FOR_PICKUP`)  
**When** I view the Work Order detail  
**Then** the Assign/Reassign action is disabled or hidden  
**And** the UI displays “Assignment is locked after work has started.”  
**And** no assignment mutation request is sent from the UI

### Scenario 4: Unauthorized user cannot assign
**Given** I am logged in without permission to assign technicians  
**And** a Work Order exists with status `APPROVED`  
**When** I view the Work Order detail  
**Then** the Assign/Reassign action is hidden or disabled  
**And** if I attempt the assignment mutation (e.g., via direct request), the backend responds with `403`  
**And** the UI shows a permission error and the assignment remains unchanged after refresh

### Scenario 5: Concurrency conflict on submit
**Given** I am logged in with permission to assign technicians  
**And** a Work Order exists with status `APPROVED`  
**And** another user changes the Work Order status or assignment while I have the assign dialog open  
**When** I submit my assignment  
**Then** the backend responds with `409` conflict  
**And** the UI shows a conflict message including the `correlationId` (if provided)  
**And** the UI refreshes the Work Order detail and history to show the latest assignment/status

### Scenario 6: Idempotent double-submit does not create duplicate history
**Given** I am logged in with permission to assign technicians  
**And** a Work Order exists with status `APPROVED`  
**When** I submit an assignment and the UI retries the same request using the same `Idempotency-Key`  
**Then** the backend returns the same outcome without creating duplicate assignment history entries  
**And** the UI shows the Work Order assigned exactly once after refresh
