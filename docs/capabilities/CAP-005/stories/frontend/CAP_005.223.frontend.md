## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Execution: Record Labor Performed (Work Order Service Item)  
**Primary Persona:** Technician  
**Business Value:** Capture auditable technician labor (time-based or flat-rate) per work order service item to support accurate execution tracking, progress visibility, and downstream job-cost/WIP reporting without posting revenue/AR.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Technician  
- **I want** to record labor performed against a specific work order service line item (either hours or flat-rate completion) with optional notes  
- **So that** work progress is tracked accurately and the system can emit a `LaborRecorded` event for job costing/WIP, while maintaining an auditable, permissioned correction model.

### In Scope
- View work order service items eligible for labor entry.
- Create a new labor entry for a selected service item:
  - time-based hours entry **or**
  - flat-rate completion entry.
- Optional technician notes/results captured with the entry.
- Display existing labor entries for the service item (read-only list).
- Handle validation and backend errors explicitly in UI using the standard error envelope (DECISION-INVENTORY-011).
- Ensure UI reflects item/work order progress updates after save (via refresh).
- Idempotency support for create/submit actions (DECISION-INVENTORY-012).
- Correction-by-superseding flow **only if** backend exposes it (see Open Questions).

### Out of Scope
- Payroll, technician pay rates, or billing calculations.
- Posting revenue/AR or showing accounting postings as a result of labor entry.
- Creating/modifying work order state machine (only reflect/trigger allowed transitions if provided).
- Parts consumption, picking, inventory allocation.
- Configuration of assignment policy, roles, or permissions (UI consumes capability signals; backend enforces).
- Time-entry CRUD (people domain).

---

## 3. Actors & Stakeholders
- **Technician (Primary):** records labor on assigned work orders/items.
- **Service Advisor (Secondary/Stakeholder):** may review or correct labor entries (permission-dependent).
- **Accounting/Reporting Consumers (Downstream Stakeholder):** consumes `LaborRecorded` events; frontend must not display accounting postings as a result of labor entry.
- **System/Audit (Stakeholder):** requires immutable audit trail of entries and corrections.

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated.
- User has permission/capability to record labor entries (capability signal preferred; backend authoritative with 403) (DECISION-INVENTORY-013).
- Work order exists and is in a status that allows labor recording (see State Model & Transitions).

### Dependencies
- Moqui workexec screens exist and are extended rather than replaced (DECISION-INVENTORY-002):
  - `durion-workexec/WorkOrderEdit.xml` (work order detail/edit)
- Backend endpoints/services for:
  - loading a work order + service items + existing labor entries
  - creating a labor entry
  - (optional) superseding/correcting a labor entry
- Backend enforces:
  - assignment policy (assigned vs not assigned)
  - valid work order/item state rules
  - validation for hours and flat-rate completion constraints
  - audit logging and event emission (`LaborRecorded`)
  - idempotency outcomes keyed by `Idempotency-Key` (DECISION-INVENTORY-012)
- Standard error envelope is returned (or normalized by Moqui) (DECISION-INVENTORY-011).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From **Work Order detail** (`WorkOrderEdit.xml`), within an **Execution / Services** section, technician selects a **service line item** and chooses **“Record Labor”**.

### Screens to create/modify
1. **Modify** `durion-workexec/WorkOrderEdit.xml`
   - Add “Record Labor” action per service item.
   - Add “Labor Entries” read-only list per service item (inline panel or expandable section).
2. **Add** a workexec screen for labor entry creation (modal dialog or routed sub-screen under workexec component):
   - Suggested: `durion-workexec/WorkOrderLaborEntryCreate.xml` (screen name may vary; must live in workexec component per DECISION-INVENTORY-002).

### Navigation context
- Required parameters (IDs are opaque strings; no UUID validation) (DECISION-INVENTORY-003):
  - `workOrderId`
  - `workOrderItemSeqId` (or equivalent service line identifier; see Open Questions)
- Return navigation:
  - on success → back to Work Order detail, focused on the same service item (scroll/anchor behavior is UI-only).

### User workflows (happy + alternate)
**Happy path (time-based):**
1. Select service item → Record Labor.
2. Choose “Time-based”.
3. Enter `hours` (decimal) and optional `notes`.
4. Save → success toast/banner.
5. Work order/service item refreshes; new labor entry appears in list.

**Happy path (flat-rate):**
1. Select service item → Record Labor.
2. Choose “Flat-rate completion”.
3. Confirm completion and optional `notes`.
4. Save → success; refresh; entry appears.

**Alternate paths:**
- Not assigned / no capability → action hidden/disabled; backend still enforces with 403.
- Item blocked (`PENDING_APPROVAL`, `CANCELLED`, etc.) → action disabled with explanation.
- Backend validation errors → inline field errors.
- Backend conflict (409) → prompt to refresh and retry; do not duplicate entries (idempotency).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **BR-L1 (Identity attribution):** Labor entry must be attributable to a technician and time.
  - UI MUST NOT accept free-form technician identity.
  - UI SHOULD rely on authenticated session identity; if API requires `technicianId`, it must be sourced from backend-provided user context/capabilities payload (DECISION-INVENTORY-013) and sent as an opaque ID (DECISION-INVENTORY-003).
- **BR-L2 (Labor type):**
  - TIME_BASED requires `hours`.
  - FLAT_RATE requires `confirmComplete=true` and sends `isComplete=true` (or equivalent).
- **BR-L3 (Hours constraints):**
  - UI enforces `hours > 0`.
  - UI does not enforce an upper bound unless backend provides one in payload/metadata; backend remains authoritative.
- **BR-L4 (Audit + immutability):**
  - Existing labor entries are read-only in UI by default.
  - No delete/edit actions unless backend exposes explicit endpoints and capability flags; if supported, corrections must be “supersede” (append-only) and require a note/reason if backend requires it.
- **BR-L5 (Change request blocking):**
  - If the service item is `PENDING_APPROVAL`, labor recording is disabled (Change Request Workflow invariant).

### Enable/disable rules
- Disable or hide “Record Labor” if:
  - backend indicates `canRecordLabor=false` (preferred), OR
  - work order status is not eligible (see State Model), OR
  - item status is not executable (`PENDING_APPROVAL`, `CANCELLED`, `COMPLETED`, etc.), OR
  - capability signal indicates user cannot record labor (DECISION-INVENTORY-013).
- Even if UI enables, backend must enforce and may return 403/400/409.

### Visibility rules
- Labor entry list visible when a service item is selected/expanded.
- Correction actions visible only if backend indicates permission and provides endpoint/capability flag.

### Error messaging expectations (standard envelope)
- Parse standard error envelope fields (DECISION-INVENTORY-011):
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`
- 403: “You don’t have access to record labor on this work order/item.”
- 409: “This work order changed since you opened it. Refresh and try again.”
- 400 validation: show field-level errors (hours, notes length, missing required fields).
- 404: “Work order or service item not found.”
- Always display `correlationId` in an expandable “Details” area for support.

## 9. Service Contracts (Frontend Perspective)

> Moqui may implement these as screen transitions calling services that proxy REST or invoke entity-auto services. Exact paths must be confirmed; below defines required behaviors and error handling.

### Load/view calls
- **Load work order detail** (must include service items and enough fields to gate labor entry):
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}`
  - Response SHOULD include:
    - work order `statusId` and/or `isStarted`
    - service items with `itemId/seqId`, `itemStatusId`, assignment fields, and optionally `canRecordLabor`
- **Load labor entries for a service item** (either embedded or separate):
  - Option A (preferred for UX): included in work order detail under each service item as `laborEntries[]`
  - Option B: `GET /rest/api/v1/workexec/workorders/{workOrderId}/service-items/{itemId}/labor-entries`

### Create/update calls
- **Create labor entry**
  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/service-items/{itemId}/labor-entries`
  - Headers:
    - `Idempotency-Key: <uuid>` (generated client-side per submit attempt; reused on retry) (DECISION-INVENTORY-012)
  - Request body:
    - `laborType`
    - `laborHours` (TIME_BASED)
    - `isComplete=true` (FLAT_RATE)
    - `notes` (optional)
  - Response:
    - 201 or 200 with created labor entry object including `laborEntryId`, timestamps, and any updated item/work order status fields if available.

### Submit/transition calls
- None required beyond create labor entry.
- UI MUST NOT auto-call work order `start` on first labor entry unless backend explicitly requires it and exposes a capability/flag indicating this policy.

### Error handling expectations
- All non-2xx responses should conform to standard error envelope (DECISION-INVENTORY-011) or be normalized by Moqui.
- 409 duplicate/idempotency replay:
  - If backend returns the original success response for the same `Idempotency-Key`, UI treats as success and refreshes.
  - If backend returns 409 with `code=DUPLICATE` and `existingResourceId`, UI shows “Already recorded” and offers to view the existing entry.

## 10. State Model & Transitions

### Work order states (authoritative from `WORKORDER_STATE_MACHINE.md`)
- `DRAFT`
- `APPROVED`
- `ASSIGNED`
- `WORK_IN_PROGRESS`
- `AWAITING_PARTS`
- `AWAITING_APPROVAL`
- `READY_FOR_PICKUP`
- `COMPLETED`
- `CANCELLED`

### Allowed states for recording labor (UI gating)
- **Eligible (started/in-progress):**
  - `WORK_IN_PROGRESS`, `AWAITING_PARTS`, `AWAITING_APPROVAL`
- **Not eligible:**
  - `DRAFT`, `APPROVED`, `ASSIGNED`, `READY_FOR_PICKUP`, `COMPLETED`, `CANCELLED`

**Decision rationale:** Workexec domain decision defines “started” as `WO_IN_PROGRESS` or later (DECISION-INVENTORY-004). Labor recording is execution-time activity and should be gated to started/in-progress states to avoid implicit auto-start policy (auto-start is explicitly deferred in `WORKORDER_STATE_MACHINE.md`). If backend later allows labor in `APPROVED/ASSIGNED`, it must expose `canRecordLabor` or equivalent to override UI gating.

### Role-based transitions
- This story does not introduce new work order transitions.

### UI behavior per state
- If non-eligible: disable Record Labor and show explanation referencing current status.
- If eligible but item is blocked (`PENDING_APPROVAL`): disable and explain approval requirement.

## 11. Alternate / Error Flows

### Validation failures
- TIME_BASED:
  - hours missing → inline error “Hours is required.”
  - hours <= 0 → inline error “Hours must be greater than 0.”
- FLAT_RATE:
  - completion not confirmed → disable Save until confirmed.

### Concurrency conflicts
- If backend responds 409 due to optimistic locking/version mismatch:
  - show message with `correlationId`
  - provide “Refresh Work Order” action that reloads data and reopens the form with preserved inputs where possible
  - do not automatically retry with a new idempotency key; user must re-submit (or reuse same key if the prior attempt may have succeeded but response was lost).

### Unauthorized access
- 403:
  - show message; do not reveal role names
  - if backend provides `code` distinguishing assignment vs permission, tailor message:
    - assignment: “You are not assigned to this work order/item. Please see the Service Advisor.”
    - permission: “You do not have permission to record labor.”

### Empty states
- No service items → show “No service items available for labor entry.”
- No labor entries yet → show “No labor recorded yet.”
