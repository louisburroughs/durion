## Issue Body

## Title
[FRONTEND] [STORY] Execution: Handle Part Substitutions and Returns

## Primary Persona
Technician / Parts Counter Staff

## Business Value
Ensure parts usage on an in-progress Work Order remains inventory-accurate and auditable when a different part is used or unused parts are returned, while properly gating customer-visible price increases through approval when required.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Technician or Parts Counter Staff  
- **I want** to record a part substitution or return against an issued/consumed Work Order part line  
- **So that** inventory quantities reconcile correctly, billing remains accurate, and traceability/audit requirements are satisfied.

## In-scope
- UI entry from Work Order execution to:
  - Return unused quantity for an issued part usage line
  - Substitute an issued part usage line with a different catalog part
- UI validations that prevent invalid adjustments (over-return, invalid quantity, policy blocks)
- UI handling when substitution triggers an approval gate due to price increase (including “price match avoids approval” path when supported by backend)
- Display of substitution/return audit history at least at the Work Order level (read-only)
- Idempotent UI mutation behavior using `Idempotency-Key` for submit actions (DECISION-INVENTORY-012)

## Out-of-scope
- Defining substitution policy rules (backend/policy)
- Implementing inventory availability search/reservation rules beyond what backend exposes
- Implementing Service Advisor approval/rejection UI for substitution price increase (only route/flag visibility; separate story if needed)
- Accounting/COGS ledger posting logic (event emitted by backend)
- SubstituteLink master-data authoring/admin (owned by inventory/product; workexec consumes) (DECISION-INVENTORY-001)

---

# 3. Actors & Stakeholders
- **Technician / Parts Counter (Primary):** initiates substitution or return.
- **Service Advisor:** may need to approve price increase or apply price match (approval UI may be separate).
- **Inventory Manager:** depends on correct reconciliation; reviews audit.
- **Customer:** impacted by substitution price changes (approval required in some cases).
- **Downstream Accounting/Inventory Systems:** consume inventory adjustment effects/events (not implemented here).

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated.
- Work Order exists and is in an execution-eligible status.
  - For this story, execution-eligible means **started** (`WO_IN_PROGRESS` or later) (DECISION-INVENTORY-004).
- Work Order has at least one part usage/line eligible for adjustment (return/substitute).

## Dependencies
- Workexec backend provides:
  - Load Work Order detail including part usage lines and status (Moqui screen/service or REST).
  - Mutation services for:
    - Return unused quantity for a part usage line
    - Substitute a part usage line with another part
  - Server-side enforcement for:
    - Eligibility/policy checks (DECISION-INVENTORY-007)
    - Permission/capability checks (DECISION-INVENTORY-013)
    - Concurrency conflict detection (409) (DECISION-INVENTORY-005 guidance)
    - Standard error envelope (DECISION-INVENTORY-011)
    - Idempotency via `Idempotency-Key` header for create/submit (DECISION-INVENTORY-012)
- Catalog/product search endpoint for substitute selection (DECISION-INVENTORY-008).
- If approval gating is used:
  - Backend returns an authoritative approval-blocked signal (prefer Work Order status `WO_AWAITING_APPROVAL` or equivalent boolean flags) and/or line-level item status (see State Model).

# 6. Functional Behavior

## Triggers
- User invokes `Return` or `Substitute` action on a specific Work Order part usage line.

## UI actions

### Return action
- Open dialog with read-only context:
  - Part display (name/SKU)
  - Issued quantity, consumed quantity, returned quantity (if provided)
- User inputs:
  - `returnQuantity` (required)
  - Optional `reasonCode` (only if backend supports; otherwise omit field)
- On submit:
  - Generate and attach `Idempotency-Key` header (UUID) for this submit attempt; reuse the same key if the user retries the same attempt (DECISION-INVENTORY-012)
  - Call return service
  - On success: close dialog, refresh WorkOrderEdit, show success message

### Substitute action
- Open dialog with read-only context:
  - Original part display (name/SKU)
  - Current quantities (issued/consumed/returned as available)
- User inputs:
  - `substitutePartId` via part picker (search + pagination; no raw ID entry required) (DECISION-INVENTORY-008, DECISION-INVENTORY-003)
  - `substituteQuantity` (required)
  - Optional `reasonCode` (if supported)
  - Optional `priceMatchToOriginal` (only if backend supports and capability allows; see Business Rules)
- On submit:
  - Generate and attach `Idempotency-Key` header (UUID) for this submit attempt; reuse on retry (DECISION-INVENTORY-012)
  - Call substitute service
  - On success: close dialog, refresh WorkOrderEdit, show success message
  - If response indicates approval-blocked: show banner and disable actions per returned state

## State changes (frontend-visible, authoritative from backend)
- Return:
  - Backend updates usage quantities; UI reflects updated values after refresh
- Substitution:
  - Backend updates original usage and creates/updates substitute usage and substitution history; UI reflects after refresh
  - Backend may set Work Order status to an approval-blocked status (e.g., `WO_AWAITING_APPROVAL`) and/or set line item status to `PENDING_APPROVAL` (see State Model)

## Service interactions
- Load: fetch Work Order detail including part usage lines, status, and adjustment history
- Mutations:
  - Return unused part usage
  - Substitute part usage
- Refresh: re-fetch Work Order detail and history after successful mutation or after 409 conflict

# 7. Business Rules (Translated to UI Behavior)

## Validation (client-side guards + backend authoritative enforcement)
- **Identifier handling:** treat all IDs as opaque strings; do not validate UUID/numeric formats (DECISION-INVENTORY-003).
- **Return quantity**
  - Required
  - Must be numeric > 0
  - Must be <= backend-provided “returnable quantity” if provided; otherwise <= `consumedQuantity` as a UI guard
  - Backend remains authoritative; UI must handle backend rejection
- **Substitution**
  - Substitute part selection required (via picker)
  - Quantity required, numeric > 0
  - Backend enforces eligibility/policy and returns a structured error if disallowed (DECISION-INVENTORY-007)
- **Approval gating**
  - Backend is authoritative for whether approval is required and whether the work order/line is blocked
  - UI must reflect approval-blocked signals and prevent further execution-affecting actions when blocked

## Enable/disable rules
- Disable `Return` and `Substitute` row actions when any of the following is true:
  - Work Order is not started (`isStarted=false` preferred; else status < `WO_IN_PROGRESS`) (DECISION-INVENTORY-004)
  - Backend indicates the line is not adjustable (prefer line-level `canReturn` / `canSubstitute` flags if available)
  - Work Order is approval-blocked (status indicates awaiting approval OR boolean `isApprovalBlocked=true` if provided)
- Disable submit buttons while request is in-flight (prevent double-submit)
- Price match controls:
  - Only visible/enabled if backend indicates capability/permission (e.g., `canEnterManualPrice` or `canPriceMatch`) (DECISION-INVENTORY-013)
  - If user lacks capability, UI must not offer price match inputs; backend still enforces

## Visibility rules
- Show “Awaiting approval” banner when backend indicates approval-blocked state
- Show substitution/return history section when backend provides events; otherwise show created/updated metadata only (DECISION-INVENTORY-014)

## Error messaging expectations
- Normalize errors to standard envelope (DECISION-INVENTORY-011):
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`, optional `existingResourceId`
- UI mapping:
  - 400/422: show inline field errors when `fieldErrors` present; otherwise show top-level message
  - 403: “You do not have permission to adjust parts on this work order.”
  - 404: “Work order or part line not found.”
  - 409: “This work order changed since you opened it. Refresh and try again.”
- Always display `correlationId` in an expandable “Details” area for support.

# 11. Alternate / Error Flows

## Validation failures
- Return quantity exceeds returnable/consumed:
  - UI blocks submit with inline error
  - If backend still rejects, show backend message and keep dialog open
- Substitute missing part or invalid quantity:
  - UI blocks submit with inline errors

## Concurrency conflicts (409)
- Show modal/banner: “Work order changed. Refresh to continue.”
- Provide “Refresh” action that reloads WorkOrderEdit data.
- After refresh, keep the dialog open but revalidate quantities against refreshed data; if no longer valid, require user to re-enter.

## Unauthorized access (403)
- Show not-authorized message
- Close dialog or keep open in read-only mode (no submit)

## Empty states
- No eligible part usage lines:
  - Show “No parts available to adjust.”
  - Do not render row actions

## Partial data availability
- If history endpoint/data is unavailable:
  - Show created/updated metadata only (DECISION-INVENTORY-014)
  - Do not block substitution/return flows

# 12. Acceptance Criteria

## Scenario 1: Return unused part (success)
**Given** a Work Order is started (`isStarted=true` or `statusId` is `WO_IN_PROGRESS` or later) and has a part usage line with `consumedQty = 5`  
**When** the user submits a return with `returnQuantity = 2`  
**Then** the UI refresh shows the updated part usage with `consumedQty = 3` (and `returnedQty` increased if provided)  
**And** the Parts Adjustments History shows a `PART_RETURN` event with timestamp and actor (if history is provided).

## Scenario 2: Prevent over-return (client + server)
**Given** a Work Order part usage line has `consumedQty = 3` (or `returnableQty = 3` if provided)  
**When** the user enters `returnQuantity = 4`  
**Then** the UI blocks submission with “Return quantity cannot exceed available consumed quantity.”  
**And** if the request is still sent and backend rejects it, the UI displays the backend error message and no quantities change after refresh.

## Scenario 3: Substitute part (success, no approval required)
**Given** a started Work Order has Part A on a usage line with `consumedQty >= 1`  
**When** the user substitutes Part A with Part B for quantity `1`  
**Then** after refresh the UI shows:
- Part A usage updated to reflect the substitution (as returned by backend)  
- Part B usage created/updated reflecting the substituted quantity  
- A history entry `PART_SUBSTITUTION` linking the original and substitute usage (if history is provided)  
**And** no “Awaiting approval” banner is shown.

## Scenario 4: Substitute part triggers approval gate
**Given** a started Work Order has Part A consumed  
**And** backend policy determines substituting to Part B requires approval (e.g., price increase not price-matched)  
**When** the user submits the substitution  
**Then** the UI refresh shows the substitution applied (per backend)  
**And** the UI shows an “Awaiting approval” banner based on backend status/flag  
**And** Substitute/Return actions are disabled while approval-blocked.

## Scenario 5: Substitution blocked by policy
**Given** a started Work Order  
**When** the user attempts a substitution that backend policy disallows  
**Then** the UI shows a blocking error from the backend (standard envelope)  
**And** after refresh no substitution is present in the part usage list/history.

## Scenario 6: Idempotent submit behavior (double-click / retry)
**Given** the user submits a Return or Substitute action and the UI generated an `Idempotency-Key`  
**When** the user retries the same attempt due to a timeout/network error  
**Then** the UI reuses the same `Idempotency-Key`  
**And** after refresh only one adjustment is reflected (no duplicate return/substitution).

## Scenario 7: Not started work order cannot be adjusted
**Given** a Work Order is not started (`isStarted=false` or status is `WO_CREATED`/`WO_SCHEDULED`)  
**When** the user views the Parts section  
**Then** Substitute/Return actions are not available  
**And** the UI indicates adjustments are only allowed after work has started.
