## 1. Story Header

### Title
[FRONTEND] [STORY] Execution: Start Work Order and Track Status (WIP Reasons + History)

### Primary Persona
Technician (primary), Shop Manager (secondary)

**Persona Metadata**
- `primary_persona`: `Technician (primary), Shop Manager (secondary)`
- `canonical_persona`: `Technician`
- `persona_family`: `Technician`
- `actor_type`: `human`

### Business Value
Provide explicit, auditable work order start and in-progress status reason tracking so the shop can see real-time execution state, prevent starting work when blocked by pending approvals, and retain immutable history for operational analytics.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Technician or Shop Manager  
- **I want** to explicitly start a work order and update its in-progress reason (waiting parts/approval/etc.)  
- **So that** the system accurately reflects execution progress, enforces start eligibility rules, and preserves an immutable status/reason history.

### In Scope
- Work order detail UI shows current status and in-progress reason (when applicable).
- “Start Work” action that calls backend start endpoint and updates UI state.
- “Update In-Progress Reason” action available only while work order is in `WO_IN_PROGRESS` (workexec canonical status taxonomy).
- Read-only, append-only history view of status/reason changes (transition audit list).
- Frontend handling for blocked start (non-startable state, pending blocking change request).
- Explicit mapping of Moqui screen actions to services/transitions and error handling.

### Out of Scope
- Auto-start on first labor entry (explicitly out of scope; follow-on story).
- Creating/approving/declining change requests (only used as a blocking condition display).
- Any new workflow states beyond those enumerated in the authoritative work order status taxonomy.
- Permission model design (frontend respects capability signals and API 401/403; does not invent RBAC rules).

---

## 3. Actors & Stakeholders
- **Technician:** starts work, updates in-progress reason during execution.
- **Shop Manager:** may start work and update reason; monitors progress.
- **Service Advisor:** indirect stakeholder (change requests may block start).
- **Audit/Operations:** relies on immutable history for compliance and analytics.

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in the POS frontend.
- Work order exists and is viewable by the user.
- Workexec backend supports:
  - loading work order details (including `statusId` and optionally `isStarted`)
  - starting a work order (transition to started)
  - updating in-progress reason (execution sub-status/reason)
  - retrieving transition/history events (append-only)

### Dependencies
- **Canonical Moqui screens/routes (DECISION-INVENTORY-002):**
  - Work order detail/edit is implemented under `durion-workexec` (screen: `WorkOrderEdit.xml`)
  - Board/list entry points under `WorkOrderBoard.xml`
- **Work started gating (DECISION-INVENTORY-004):**
  - “Started” means `WO_IN_PROGRESS` or later; pre-start statuses include `WO_CREATED`/`WO_SCHEDULED`
  - Prefer backend-provided boolean `isStarted` to avoid client-side mapping drift
- **Blocking condition (WORKORDER_STATE_MACHINE.md + Change Request workflow):**
  - Start must be rejected if there exists a pending change request requiring advisor review (ChangeRequest status `AWAITING_ADVISOR_REVIEW`)
- **Error envelope (DECISION-INVENTORY-011):**
  - Backend errors are normalized to `{ code, message, correlationId, fieldErrors?, existingResourceId? }`
- **Idempotency (DECISION-INVENTORY-012):**
  - UI must send `Idempotency-Key` for start and reason-change mutations and reuse it on retry for the same attempt
- **Identifier handling (DECISION-INVENTORY-003):**
  - Treat all IDs as opaque strings; no UUID/numeric validation in UI

**Decision rationale applied to remove prior STOP:** The workexec domain guide resolves the earlier conflicts: start gating is status-based with “started = `WO_IN_PROGRESS` or later” (DECISION-INVENTORY-004), and canonical Moqui screens are known (DECISION-INVENTORY-002). Remaining unknowns are limited to exact service names/paths in this repo; the story is still implementable by wiring Moqui screen transitions to existing services and normalizing errors.

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From `durion-workexec/WorkOrderBoard.xml`: open a work order row → navigate to `durion-workexec/WorkOrderEdit.xml` for that work order.
- From global search (if present): open work order → `WorkOrderEdit.xml`.

### Screens to create/modify
1. **Modify** `durion-workexec/WorkOrderEdit.xml`
   - Add/confirm an execution action section:
     - `Start Work` action (conditional)
     - `In-Progress Reason` selector + optional note (conditional)
     - `History` section (embedded) or link to a dedicated history screen
2. **Modify or Create** a history view:
   - Preferred: embedded section within `WorkOrderEdit.xml` (lowest navigation cost)
   - Optional: `durion-workexec/WorkOrderHistory.xml` (if existing patterns prefer separate screens)

### Navigation context
- Work order detail/edit is the canonical place for execution actions.
- After successful start or reason change, remain on the same screen and refresh the work order + history dataset.

### User workflows (happy + alternate paths)

#### Happy path: Start work
1. User opens `WorkOrderEdit` for a work order.
2. UI shows `Start Work` enabled when:
   - backend indicates not started (`isStarted=false`) AND
   - status is start-eligible (pre-start) AND
   - backend does not indicate a blocking pending change request (if signal available)
3. User clicks `Start Work`.
4. UI optionally prompts for a short “start note” (free text) **only if** backend supports storing it in transition history; otherwise no prompt.
5. Backend returns updated work order; UI refreshes:
   - status becomes `WO_IN_PROGRESS`
   - started indicator/time displays if provided
6. History shows a new transition entry.

#### Happy path: Update in-progress reason
1. While status is `WO_IN_PROGRESS` (or backend `isStarted=true` and status indicates in-progress), UI shows reason selector.
2. User selects a reason (e.g., waiting on parts) and saves.
3. Backend persists reason change; UI refreshes and history shows a new entry.

#### Alternate path: Start blocked
- If backend rejects start due to:
  - non-startable status, or
  - pending change request requiring advisor review,
  UI shows the backend message and keeps state unchanged; history remains unchanged after refresh.

## 6. Functional Behavior

### Triggers
- User clicks `Start Work`.
- User updates `In-Progress Reason` while work is in progress.

### UI actions
- **Start Work**
  - Visible when backend indicates the work order is not started (`isStarted=false`) and status is pre-start.
  - Disabled when backend indicates blocked by pending approvals (if a boolean/summary is provided); otherwise enabled and relies on backend enforcement.
  - On click:
    - generate an `Idempotency-Key` for this attempt
    - call start transition service
    - on success: reload work order + history
- **Update In-Progress Reason**
  - Visible only when status is in-progress (`WO_IN_PROGRESS` or later where reason is applicable; see State Model).
  - Allowed values are loaded from backend enum/codelist when available; otherwise use the fixed list in Business Rules.
  - On save:
    - generate/reuse `Idempotency-Key` for this attempt
    - call update reason service
    - on success: reload work order + history
- **View history**
  - Always available read-only.
  - Supports empty state (“No status history yet.”).

### State changes (frontend-observable)
- On successful start:
  - `statusId` transitions to `WO_IN_PROGRESS`
  - `isStarted` becomes `true` (if provided)
  - `workStartedAt` (or equivalent) becomes populated (if provided)
- On reason update:
  - `statusId` remains unchanged
  - `inProgressReasonId` (or equivalent) changes
- History list is append-only.

### Service interactions
- Load work order details (entity/service).
- Start work order (transition service).
- Update in-progress reason (update service).
- Load transitions/history (entity/service).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Start Work**
  - Backend is authoritative.
  - UI gating:
    - If `isStarted=true` → do not show Start action.
    - Else if `statusId` is not pre-start → hide or disable Start with explanation.
  - Backend must reject start if there exists any ChangeRequest with status `AWAITING_ADVISOR_REVIEW` for the work order (WORKORDER_STATE_MACHINE.md + Change Request workflow).
- **Update In-Progress Reason**
  - Only permitted when work is started and in an in-progress status.
  - UI must not allow updates when not started; backend must reject if attempted.

### Enable/disable rules
- Start button:
  - Enabled when:
    - `isStarted == false` (preferred) OR `statusId` is pre-start AND
    - no known blocking pending change request flag is true
  - Disabled otherwise with inline explanation:
    - “Already started.” (when `isStarted=true`)
    - “Not startable in current status: <statusId>.” (when status not pre-start)
    - “Blocked: pending approval required.” (when blocking flag present)
- Reason selector:
  - Enabled only when `statusId == WO_IN_PROGRESS` (strict) **or** when backend explicitly indicates reason is editable (capability/flag if provided).
  - If backend supports multiple in-progress statuses (e.g., `WO_AWAITING_PARTS`), reason selector must be disabled unless backend contract says it is editable in those statuses.

### Visibility rules
- Show `inProgressReason` controls only when editable per above.
- Show `workStartedAt` when present.
- Show history always.

### Error messaging expectations
- Parse and display standard error envelope (DECISION-INVENTORY-011):
  - 400: show `message`; if `fieldErrors[]` present, map to field-level errors
  - 401: follow app standard login/session flow
  - 403: show “You do not have permission to perform this action.”
  - 404: show “Work order not found.”
  - 409: show “Work order was updated by another user. Refresh and try again.” and auto-refresh
  - 5xx/network: show retryable error with `correlationId` if present

## 8. Data Requirements

### Entities involved
- `durion.workexec.DurWorkOrder` (workexec SoR for execution lifecycle)
- Work order transition history entity (append-only), per backend implementation:
  - `WorkOrderStateTransition` (as referenced in WORKORDER_STATE_MACHINE.md), or
  - an equivalent Moqui entity/view exposed by workexec services
- Change request summary (read-only) sufficient to determine “pending advisor review exists”:
  - either a boolean on work order DTO, or
  - a list/count of change requests filtered to `AWAITING_ADVISOR_REVIEW`

### Fields (types, required, defaults)

#### Work Order (read)
- `workOrderId` (type: id/opaque string; required)
- `statusId` (type: id/enum string; required)
- `isStarted` (type: boolean; optional but preferred; derived server-side per DECISION-INVENTORY-004)
- `workStartedAt` (type: datetime; optional)
- `inProgressReasonId` (type: id/enum string; optional; required when reason is editable)
- `hasPendingAdvisorReviewChangeRequest` (type: boolean; optional but preferred; server-derived)

#### Start request (write)
- `workOrderId` (path param)
- `reason` (type: text; optional; only if backend supports storing it)
- Headers:
  - `Idempotency-Key` (required; UUID string generated client-side)

#### Reason update request (write)
- `workOrderId` (path param)
- `inProgressReasonId` (type: id/enum string; required)
- `note` (type: text; optional; only if backend supports storing it in history)
- Headers:
  - `Idempotency-Key` (required)

#### Transition history record (read)
- `transitionId` (type: id; required)
- `workOrderId` (type: id; required)
- `fromStatusId` (type: id/enum string; optional)
- `toStatusId` (type: id/enum string; required)
- `transitionedAt` (type: datetime; required; stored UTC, displayed in user TZ per DECISION-INVENTORY-016)
- `transitionedByUserId` (type: id; required)
- `reason` (type: text; optional)
- `metadata` (type: text/json; optional)

### Read-only vs editable by state/role
- Read-only always:
  - `statusId`, `workStartedAt`, history records
- Editable:
  - Start action: only when not started and pre-start
  - In-progress reason: only when `statusId == WO_IN_PROGRESS` (unless backend indicates otherwise)
- Role gating:
  - UI may hide/disable actions based on capability flags if available (DECISION-INVENTORY-013), but backend remains authoritative (403).

### Derived/calculated fields (frontend)
- `canStart`:
  - prefer `!isStarted && statusId in {WO_CREATED, WO_SCHEDULED}` (pre-start) **or** backend-provided `canStart` if available
- `startDisabledReason` string derived from status/flags
- Display labels for `statusId` and `inProgressReasonId` via i18n keys

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation note: This story is buildable by wiring `WorkOrderEdit.xml` actions to existing workexec services. If REST endpoints exist, they should be used consistently, but the UI must not hardcode conflicting paths without confirming the repo’s actual routes.

### Load/view calls
1. **Load work order**
   - Moqui screen action/service: `find#durion.workexec.DurWorkOrder` by `workOrderId` (or existing workexec service used by `WorkOrderEdit.xml`)
   - Must return at least: `workOrderId`, `statusId`, and preferably `isStarted`, `workStartedAt`, `inProgressReasonId`, `hasPendingAdvisorReviewChangeRequest`
2. **Load transition history**
   - Moqui entity find on `WorkOrderStateTransition` (or equivalent) filtered by `workOrderId`
   - Sort: `transitionedAt` descending (most recent first)
   - Pagination supported (see Safe Defaults)

### Create/update calls
1. **Start work order**
   - Preferred REST-style (from WORKORDER_STATE_MACHINE.md): `POST /api/workorders/{id}/start`
   - Moqui alternative: screen transition calling a workexec service (e.g., `durion.workexec.WorkOrderServices.startWorkOrder`)
   - Request:
     - header `Idempotency-Key` required
     - body includes optional `reason` (if supported)
   - Response:
     - updated work order summary OR 200 with enough data to refresh
2. **Update in-progress reason**
   - Service must:
     - validate work order is in `WO_IN_PROGRESS`
     - append a history entry
   - Request:
     - header `Idempotency-Key` required
     - body includes `inProgressReasonId` and optional `note` (if supported)
   - Response:
     - updated work order summary OR 200 with enough data to refresh

### Submit/transition calls
- Both actions are treated as transitions and must result in an append-only history record.

### Error handling expectations
- All errors normalized to standard envelope (DECISION-INVENTORY-011).
- Duplicate/double-submit behavior:
  - With same `Idempotency-Key`, backend returns the same outcome (DECISION-INVENTORY-012).
- Concurrency:
  - If backend uses version tokens, stale updates return 409; UI refreshes.

## 10. State Model & Transitions

### Allowed states (workexec canonical taxonomy)
Per DECISION-INVENTORY-004:
- Pre-start: `WO_CREATED`, `WO_SCHEDULED`
- Started: `WO_IN_PROGRESS` or later (includes post-start statuses such as `READY_FOR_PICKUP`)

> Note: The WORKORDER_STATE_MACHINE.md document uses a different enum naming (`APPROVED`, `ASSIGNED`, `WORK_IN_PROGRESS`, etc.). For this frontend story in this repo, **workexec canonical status IDs (`WO_*`) are authoritative** (DECISION-INVENTORY-004). If the backend exposes both, it must also expose `isStarted` to avoid client-side mapping.

### Start transition
- Allowed when `statusId ∈ {WO_CREATED, WO_SCHEDULED}` and `isStarted=false`
- Transition result: `statusId = WO_IN_PROGRESS`
- Must be rejected if any pending change request exists with status `AWAITING_ADVISOR_REVIEW`

### In-progress reason (sub-status)
- Editable only when `statusId == WO_IN_PROGRESS`
- Allowed values (initial v1 list; must match backend enum/codelist):
  - `ACTIVE_WORK`
  - `WAITING_PARTS`
  - `WAITING_CUSTOMER_APPROVAL`
  - `WAITING_DIAGNOSIS`
  - `WAITING_EXTERNAL_SERVICE`
  - `PAUSED_BY_SHOP`

### Role-based transitions
- UI gating may use capability flags if available (DECISION-INVENTORY-013), but must not invent roles.
- Backend enforces with 403.

### UI behavior per state
- `WO_CREATED` / `WO_SCHEDULED`:
  - show Start button (enabled unless blocked)
  - hide reason selector
- `WO_IN_PROGRESS`:
  - hide Start button
  - show reason selector enabled
- Any started-but-not-in-progress status (e.g., `READY_FOR_PICKUP`):
  - hide Start button
  - hide/disable reason selector
- All statuses:
  - show history

## 11. Alternate / Error Flows

### Validation failures
- Start attempted when not start-eligible:
  - backend returns 400/409 with message; UI shows message and refreshes
- Reason update attempted when not `WO_IN_PROGRESS`:
  - backend returns 400/409; UI shows message and refreshes
- Invalid reason enum:
  - backend returns 400 with `fieldErrors` for `inProgressReasonId`; UI shows field error

### Concurrency conflicts
- Two users start or update reason:
  - backend returns 409; UI shows conflict message and auto-refreshes work order + history

### Unauthorized access
- 401: redirect/login per app standard
- 403: show permission error; keep screen read-only; do not retry automatically

### Empty states
- No history records:
  - show “No status history recorded yet.”
- Work order not found (404):
  - show not found state and provide navigation back to board/search

## 12. Acceptance Criteria

### Scenario 1: Start work order from WO_CREATED
**Given** a work order exists with `statusId = WO_CREATED`  
**And** there is no ChangeRequest for the work order with `status = AWAITING_ADVISOR_REVIEW`  
**And** I am authenticated  
**When** I open `durion-workexec/WorkOrderEdit` for that work order  
**Then** I see a `Start Work` action enabled  

**When** I click `Start Work`  
**Then** the UI sends the start request with an `Idempotency-Key` header  
**And** on success the UI refreshes and shows `statusId = WO_IN_PROGRESS`  
**And** if `workStartedAt` is returned it is displayed  
**And** the history list includes a new transition entry showing the start transition.

### Scenario 2: Start work order from WO_SCHEDULED
**Given** a work order exists with `statusId = WO_SCHEDULED`  
**And** there is no pending advisor-review change request  
**When** I click `Start Work`  
**Then** the work order transitions to `WO_IN_PROGRESS` and the UI reflects the same outcomes as Scenario 1.

### Scenario 3: Reject start from already-started status
**Given** a work order exists with `statusId = READY_FOR_PICKUP` (or any status where backend indicates `isStarted=true`)  
**When** I open the work order detail screen  
**Then** I do not see `Start Work` (or it is disabled with “Already started.”)  

**When** a start attempt is made (e.g., stale UI)  
**Then** the backend rejection message is shown  
**And** after refresh the work order remains started  
**And** no duplicate start transition appears in history.

### Scenario 4: Block start due to pending change request awaiting advisor review
**Given** a work order exists with `statusId` in a pre-start status  
**And** a ChangeRequest exists for the work order with `status = AWAITING_ADVISOR_REVIEW`  
**When** I click `Start Work`  
**Then** the backend rejects the request  
**And** the UI shows the backend-provided message indicating approval is required  
**And** the work order status remains unchanged after refresh.

### Scenario 5: Change in-progress reason while WO_IN_PROGRESS
**Given** a work order exists with `statusId = WO_IN_PROGRESS` and `inProgressReasonId = ACTIVE_WORK`  
**When** I set the in-progress reason to `WAITING_PARTS` and save  
**Then** the UI sends the update request with an `Idempotency-Key` header  
**And** the UI refreshes and shows `inProgressReasonId = WAITING_PARTS`  
**And** `statusId` remains `WO_IN_PROGRESS`  
**And** the history list includes a new entry reflecting the reason change.

### Scenario 6: Prevent reason change when not WO_IN_PROGRESS
**Given** a work order exists with `statusId = WO_SCHEDULED`  
**When** I view the work order detail screen  
**Then** I cannot edit the in-progress reason  

**When** a reason update is attempted (e.g., stale UI)  
**Then** the UI displays the backend validation error  
**And** after refresh the work order remains unchanged.

### Scenario 7: Idempotent double-submit on Start Work
**Given** a work order exists with `statusId = WO_CREATED` and no blocking change request  
**And** I click `Start Work` twice quickly  
**When** the UI retries the same request using the same `Idempotency-Key`  
**Then** the backend returns the same outcome without creating duplicate transitions  
**And** the history shows only one start transition entry.

### Scenario 8: Concurrency conflict handling
**Given** I have the work order detail open  
**And** another user starts the work order or changes its reason before I submit my action  
**When** I click `Start Work` or update the reason  
**And** the backend returns `409 Conflict` with a `correlationId`  
**Then** the UI displays a conflict message prompting refresh  
**And** the UI reloads the latest work order state and history.
