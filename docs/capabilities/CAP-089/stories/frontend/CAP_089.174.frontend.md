## Business Value
Ensure workorder approval and billing contacts for a commercial account are unambiguous by maintaining CRM-owned relationships with controlled role codes, effective dating, and exactly one primary billing contact per account.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Fleet Account Manager  
- **I want** to associate existing individual (Person) records to an existing commercial account (Organization) with relationship role(s) and effective dates, including managing the account’s primary billing contact  
- **So that** downstream processes (Workexec, Billing) can reliably retrieve approvers and billing contacts from CRM-owned data.

## In-scope
- View a commercial account’s current and historical (inactive) linked individuals by role.
- Create a new relationship between an Organization and a Person with:
  - `roleType` (system-defined; at minimum `APPROVER`, `BILLING`)
  - `effectiveStartDate` (required)
  - `effectiveEndDate` (optional; set by deactivation)
  - `isPrimary` (boolean; only meaningful for `roleType=BILLING`)
- Deactivate an existing relationship (logical end-date; no delete).
- Assign/change the single **primary billing contact** for the commercial account, with automatic demotion of any existing primary billing contact (atomic, backend-enforced). (DECISION-INVENTORY-002)
- Frontend implementation using Moqui screens/forms/transitions and Moqui services that wrap CRM domain services.

## Out-of-scope
- Creating or editing Person/Organization master data (names, addresses, etc.).
- Customer deduplication, merge, “golden record” logic.
- Defining/creating new role types (roles are system-defined).
- Workexec UI or behavior (consumer only).
- Permission model design beyond enforcing 401/403 responses and hiding actions when unauthorized.

# 3. Actors & Stakeholders

## Actors
- **Fleet Account Manager (primary):** manages account contacts/approvers/billing contacts.
- **Service Advisor (secondary/read-only):** may view contacts for operational context.

## Stakeholders
- **Billing Department:** depends on accurate billing contact designation.
- **Workexec domain:** consumes approvers/billing contacts read model (no writes).
- **CRM service owner:** system of record for PartyRelationship/contact roles. (DECISION-INVENTORY-002)

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated in the POS frontend.
- User has authorization to manage relationships for the selected commercial account (backend enforces; UI must handle 403 deterministically). (DECISION-INVENTORY-007)
- The commercial account exists as a Party of subtype Organization/Account.
- Individuals (Person parties) to be linked already exist in CRM.

## Dependencies
- CRM domain services exist in Moqui (preferred) or are reachable via Moqui REST facade.
- Controlled vocabulary for relationship roles includes at minimum: `APPROVER`, `BILLING` (backend-owned list; UI must not invent new codes).
- Canonical identifier in routes and service contracts is `partyId` (no `customerId` as primary). (DECISION-INVENTORY-001)
- Backend enforces:
  - uniqueness/primary policy for billing contact (auto-demotion) (DECISION-INVENTORY-002)
  - overlap/duplicate constraints (if applicable) and returns 409 with a stable errorCode.

**Decision rationale for dependency resolutions**
- Use `partyId` everywhere to avoid split identifiers and drift. (DECISION-INVENTORY-001)
- Primary billing contact must be unique and auto-demoted atomically to prevent race conditions and ambiguity. (DECISION-INVENTORY-002)

# 5. UX Summary (Moqui-Oriented)

## Entry points
- From Commercial Account profile screen: section/tab “Contacts & Roles” (or existing equivalent).

## Screens to create/modify
1. **Screen:** `apps/crm/CommercialAccount/Contacts.xml` (new or extend existing account detail screen)
   - Purpose: view/manage individuals linked to the account with roles and effective dates.
2. **Subscreen/Dialog:** `apps/crm/CommercialAccount/Contacts/AddRelationship.xml`
   - Purpose: create a new Organization↔Person relationship with a selected role and effective start date.
3. **Subscreen/Dialog:** `apps/crm/CommercialAccount/Contacts/DeactivateRelationship.xml`
   - Purpose: confirm and end-date a relationship.
4. **Optional inline action:** “Set Primary Billing Contact” on list rows (no separate screen unless needed).

## Navigation context
- Route parameter: `partyId` (the commercial account Party ID).
  - UI route example: `/crm/commercial-accounts/:partyId/contacts`
- Screen loads relationships for this account on entry and after any mutation.

## User workflows (happy + alternate)

### Happy path: create relationship (APPROVER or BILLING)
1. User opens Commercial Account → Contacts & Roles.
2. User clicks “Add Individual”.
3. User searches/selects an existing Person (selection returns `personPartyId`).
4. User selects `roleType` (`APPROVER` or `BILLING`).
5. User selects `effectiveStartDate`.
6. If `roleType=BILLING`, user may check “Set as primary billing contact”.
7. User saves → list refreshes; new relationship appears as Active.

### Happy path: set/change primary billing contact
1. User finds an active `BILLING` relationship row.
2. User clicks “Set as Primary Billing Contact”.
3. UI submits; on success list refresh shows exactly one primary billing contact (backend auto-demotes prior primary). (DECISION-INVENTORY-002)

### Happy path: deactivate relationship
1. User clicks “Deactivate” on an active relationship row.
2. UI prompts for `effectiveEndDate` (default today; editable).
3. User confirms → relationship becomes Inactive (end-dated) and no longer appears in Active-only view.

### Alternate: view inactive/historical relationships
- User changes filter to `INACTIVE` or `ALL` to view end-dated relationships.

# 6. Functional Behavior

## Triggers
- Screen load: entering Contacts & Roles for a commercial account (`partyId`).
- User actions: create relationship, set primary billing contact, deactivate relationship, change filters.

## UI actions
- **List display** (relationships) shows:

  - `roleType`
  - `effectiveStartDate`
  - `effectiveEndDate` (blank if active)
  - `isPrimary` indicator (only for `roleType=BILLING`)

  - Status filter: `ACTIVE` (default), `INACTIVE`, `ALL`
- **Row actions (conditional)**
  - “Set Primary Billing Contact” visible only when:
    - `roleType == BILLING`
    - relationship is ACTIVE
    - `isPrimary != true`
  - “Deactivate” visible only when relationship is ACTIVE
- **Create action**
  - “Add Individual” opens create dialog.

## State changes (frontend)
- Maintain loading/error states for:
  - list fetch
  - create submit
  - set-primary submit
  - deactivate submit
- After any successful mutation:
  - re-fetch the list using current filters to reflect backend-atomic changes (especially primary demotion). (DECISION-INVENTORY-002)

## Service interactions
- On screen load and after mutations: call Moqui service `crm.CommercialAccountContact.list` (wrapper) which calls CRM read model.
- On create: call Moqui service `crm.CommercialAccountContact.create`.
- On set primary: call Moqui service `crm.CommercialAccountContact.setPrimaryBilling`.
- On deactivate: call Moqui service `crm.CommercialAccountContact.deactivate`.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Create relationship requires:
  - `accountPartyId` (from route param `partyId`)
  - `personPartyId` (selected)
  - `roleType` (must be one of backend-allowed role codes; UI restricts selection)
  - `effectiveStartDate` (required; valid date)
  - `isPrimary` allowed only when `roleType=BILLING`
- Deactivation requires:
  - `effectiveEndDate` (required; valid date)
  - UI must prevent `effectiveEndDate` earlier than `effectiveStartDate` when `effectiveStartDate` is available in the row data (client-side validation); backend remains authoritative.

## Enable/disable rules
- Disable “Save” until required fields are present and valid.
- Disable mutation actions while request is in-flight.
- Disable “Set Primary Billing Contact” if row is already primary or inactive.

## Visibility rules
- Primary billing indicator and “Set Primary Billing Contact” action only apply to `roleType=BILLING`. (DECISION-INVENTORY-002)
- Inactive relationships show `effectiveEndDate` and have no mutation actions.

## Error messaging expectations
- `400 FIELD_INVALID` (or equivalent): show field-level errors when `fieldErrors` provided; otherwise show form-level summary.
- `403 FORBIDDEN`: show “Access denied” and disable mutation controls; do not show partial mutation UI.
- `404 NOT_FOUND`: show “Record not found. Refresh and try again.”
- `409` conflicts:
  - `DUPLICATE_OR_OVERLAP` (name may vary): show “This person already has an overlapping relationship for that role.”
  - `PRIMARY_CONFLICT` (if returned): show “Primary billing contact changed. Refreshing…” then refresh list.
- `500+`: show generic error and include correlation id if provided in response headers/body.

**Decision rationale**
- Primary billing uniqueness and auto-demotion are CRM invariants; UI must treat primary as a server-controlled outcome and always refresh after changes. (DECISION-INVENTORY-002)

# 8. Data Requirements

## Entities involved (conceptual; CRM-owned)
- `PartyRelationship` (relationship record; CRM SoR)
- `Party` (Organization/Person; read-only for this story)

## Fields (type, required, defaults)

### Relationship DTO (frontend contract)
- `partyRelationshipId` (UUID, read-only, required)
- `accountPartyId` (UUID, read-only, required) — equals route `partyId`
- `personPartyId` (UUID, read-only, required)
- `personDisplayName` (string, read-only, required)
- `roleType` (string enum, read-only after create, required; at minimum `APPROVER`, `BILLING`)
- `isPrimary` (boolean, read-only after create; meaningful only when `roleType=BILLING`; default false when absent)
- `effectiveStartDate` (date, read-only after create, required)
- `effectiveEndDate` (date, read-only; nullable)
- Optional audit (read-only if provided):
  - `createdAt` (datetime)
  - `createdByUserId` (string/UUID)
  - `updatedAt` (datetime)
  - `updatedByUserId` (string/UUID)

### Derived/calculated fields (frontend)
- `status` for display/filtering:
  - Prefer backend-provided `status` if present.
  - Otherwise derive:
    - `ACTIVE` when `effectiveEndDate` is null
    - `INACTIVE` when `effectiveEndDate` is non-null
  - UI must not implement “future end date means active” logic unless backend provides explicit status (avoid policy guessing).

## Read-only vs editable by state/role
- ACTIVE relationship:
  - editable via actions: set primary billing (affects `isPrimary`), deactivate (sets `effectiveEndDate`)
  - not editable in this story: `accountPartyId`, `personPartyId`, `roleType`, `effectiveStartDate`
- INACTIVE relationship:
  - all fields read-only (no reactivation in scope)

# 9. Service Contracts (Frontend Perspective)

All browser calls go to Moqui endpoints/services; Moqui is responsible for enforcing RBAC and calling CRM domain services.

## Load/view calls

### List account contacts/roles
- **Moqui service (screen action):** `crm.CommercialAccountContact.list`
- **Inputs**
  - `accountPartyId` (UUID, required) — from route `partyId`
  - `roles` (list<string>, optional)

  - `pageIndex` (int, optional; default 0)

- **Outputs**

## Create/update calls

### Create relationship
- **Moqui service:** `crm.CommercialAccountContact.create`
- **Inputs**
  - `accountPartyId` (UUID, required)
  - `personPartyId` (UUID, required)
  - `roleType` (string, required)
  - `effectiveStartDate` (date, required)

### Deactivate relationship
- **Moqui service:** `crm.CommercialAccountContact.deactivate`
- **Inputs**
  - `partyRelationshipId` (UUID, required)
  - `effectiveEndDate` (date, required)
- **Outputs**
  - success flag or updated DTO

## Error handling expectations
- Moqui services return a consistent error payload:
  - `errorCode` (string)
  - `message` (string)
  - optional `fieldErrors` (map<string,string>)
- UI maps:
  - `fieldErrors` to inline field messages

**Decision rationale for contract resolution**
- The original story’s mutation endpoints were unspecified; Moqui facade services localize integration changes and align with “services enforce RBAC/redaction” guidance. This is a safe technical structuring choice and does not invent business policy. (Aligned with DECISION-INVENTORY-007 patterns)

# 10. State Model & Transitions

## Allowed states (relationship validity)
- **ACTIVE:** `effectiveEndDate` is null (or backend `status=ACTIVE`)
- **INACTIVE:** `effectiveEndDate` is set (or backend `status=INACTIVE`)

## Role-based transitions
- Fleet Account Manager:
  - ACTIVE → INACTIVE via Deactivate
  - ACTIVE `BILLING` relationship → becomes primary via Set Primary Billing (primary swap across relationships is backend-controlled). (DECISION-INVENTORY-002)

## UI behavior per state
- ACTIVE:
  - show Deactivate
  - show Set Primary Billing Contact (if `roleType=BILLING` and not primary)
- INACTIVE:
  - hide Deactivate and Set Primary actions
  - display `effectiveEndDate` in the row

---

# 11. Alternate / Error Flows

## Validation failures
- Missing required fields: prevent submit; show inline required indicators.
- Backend 400: show returned validation message(s); keep dialog open.

## Concurrency conflicts
- If backend responds 409 on create or set-primary:
  - show conflict message
  - re-fetch list to reflect current server state
  - for create: keep dialog open with inputs preserved
  - for set-primary: keep user on list; after refresh, reflect current primary

## Unauthorized access
- 401: redirect to login (standard app behavior).
- 403:
  - If list call returns 403: show access denied screen state (no data).
  - If list call succeeds but mutation returns 403: show access denied toast/banner and disable mutation controls for the session on that screen.

## Empty states
- No ACTIVE contacts: show empty state with “Add Individual”.
- No results for selected filters: show “No contacts match filters” with reset filters action.

# 12. Acceptance Criteria

## Scenario 1: View active approvers and billing contacts (default)
**Given** I am authenticated as a Fleet Account Manager  
**And** a commercial account exists with linked contacts of roles `APPROVER` and `BILLING`  
**When** I open the commercial account’s “Contacts & Roles” screen  
**Then** the UI calls `crm.CommercialAccountContact.list` with `status=ACTIVE` by default  
**And** I can see each contact’s role, `effectiveStartDate`, and whether they are the primary billing contact (only for `BILLING`)  

## Scenario 2: Create an APPROVER relationship
**Given** I am on a commercial account’s “Contacts & Roles” screen  
**And** an individual Person exists in CRM  
**When** I add the individual with `roleType=APPROVER` and an `effectiveStartDate`  
**And** I save  
**Then** the UI calls `crm.CommercialAccountContact.create` with the selected `personPartyId` and `accountPartyId`  
**And** on success the contacts list refreshes and shows the new `APPROVER` relationship as ACTIVE  

## Scenario 3: Create a BILLING relationship and set as primary
**Given** I am on a commercial account’s “Contacts & Roles” screen  
**When** I add an individual with `roleType=BILLING` and select “Set as primary billing contact”  
**And** I save  
**Then** the backend enforces that exactly one `BILLING` relationship is primary after the operation (auto-demoting any prior primary)  
**And** after the list refresh, exactly one relationship is shown as primary billing contact  

## Scenario 4: Change primary billing contact (atomic demotion)
**Given** I am viewing active `BILLING` relationships for a commercial account  
**And** there is an existing primary billing contact  
**When** I click “Set as Primary Billing Contact” on a different active `BILLING` relationship  
**Then** the UI calls `crm.CommercialAccountContact.setPrimaryBilling`  
**And** after refresh, the selected relationship is primary and the previously primary relationship is not primary  
**And** no duplicate primary indicators are shown  

## Scenario 5: Deactivate a relationship
**Given** I am viewing an ACTIVE relationship row  
**When** I deactivate the relationship and provide an `effectiveEndDate`  
**Then** the UI calls `crm.CommercialAccountContact.deactivate` with that `partyRelationshipId`  
**And** after refresh, the relationship no longer appears in the ACTIVE filter view  
**And** it appears in the INACTIVE or ALL filter view with `effectiveEndDate` displayed  

## Scenario 6: Prevent overlapping relationship (conflict)
**Given** there is already a relationship for the same person and role with an overlapping effective date range  
**When** I attempt to create another overlapping relationship  
**Then** the backend returns 409 with an errorCode indicating overlap/duplicate  
**And** the UI shows a conflict error message  
**And** the relationship is not created  
**And** my entered values remain in the form for correction  

## Scenario 7: Unauthorized attempt
**Given** I am authenticated but not authorized to manage contacts for the commercial account  
**When** I attempt to create, deactivate, or set primary billing contact  
**Then** the backend returns 403 `FORBIDDEN`  
**And** the UI shows an authorization error  
**And** no changes are applied
