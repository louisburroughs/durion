## Issue Body

## Title
[FRONTEND] [STORY] Party: Create Individual Person Record

## Primary Persona
Customer Service Representative (CSR)

## Business Value
Enable CSRs to create an individual person (Party/Person) with contact information so the person can later be associated to commercial accounts, vehicles, and work orders (e.g., for notifications/approvals).

---

# 2. Story Intent

## As a / I want / So that
- **As a** CSR  
- **I want** to create an individual person record with contact information (phones/emails) and a preferred contact method  
- **So that** the person can be referenced by downstream workflows (account association, vehicle association, work order notifications/approvals).

## In-scope
- A Moqui/Quasar/Vue screen flow to create a **Person** (CRM Party subtype Person) with:
  - required name fields (`firstName`, `lastName`)
  - required `preferredContactMethod` enum
  - optional multiple emails and phones (zero-to-many contact points)
  - primary selection rules per contact kind (EMAIL vs PHONE)
- Client-side validations aligned with CRM domain rules where defined (required fields, email format, phone normalization constraints)
- Submission to backend and handling success/error outcomes
- UX states: initial, submitting, success, and validation/error display

## Out-of-scope
- Role tags (billing contact, driver, approver) including any placeholder UI/schema (DECISION-INVENTORY-002)
- Customer deduplication, merge, or “golden record” workflows (duplicates explicitly allowed; merge is separate privileged flow per DECISION-INVENTORY-014)
- Associating person to commercial accounts, vehicles, or work orders (only create the person record here)
- Editing an existing person record

---

# 3. Actors & Stakeholders

- **Primary Actor:** CSR (interactive user)
- **System of Record:** CRM (Party/Person master data, ContactPoint) (DECISION-INVENTORY-001)
- **Downstream Consumers (read-only/reference):** Workexec, Billing (consume party identity/snapshot; no writes from this UI) (Domain Boundaries)
- **Supporting Systems:** Moqui backend services handling Person and ContactPoint persistence and validation

## Preconditions
- CSR is authenticated in the frontend.
- CSR is authorized to create person records (permission key to be confirmed; backend must enforce) (DECISION-INVENTORY-007).
- Moqui backend endpoints/services for “Create Individual Person” are reachable.

## Dependencies
- Backend contract for create-person service (request/response DTO, validation error shape, permission key) is required to implement without guessing. This story assumes a dedicated service exists but does not assume its exact name. (risk:incomplete-requirements)
- Controlled vocabulary for `preferredContactMethod` is available from backend or shared constants:
  - `EMAIL | PHONE_CALL | SMS | NONE` (as provided in story input; must be validated server-side).
- Contact point invariants:
  - At most one primary per party per kind (`EMAIL`, `PHONE`) (DECISION-INVENTORY-003).
  - Contact point kind is immutable after creation (not directly applicable to create, but informs UI model and payload) (DECISION-INVENTORY-003).
  - Phone normalization/validation: accept flexible input; normalize; validate 10–15 digits; extension is separate (DECISION-INVENTORY-003).

# 6. Functional Behavior

## Triggers
- Screen load:
  - Initialize form model with empty values.
  - Initialize contact point lists as empty arrays.
- User actions:
  - Add/remove contact point rows.
  - Set primary flags.
  - Submit.

## UI actions
- **Add Email**
  - Appends an email row with:
    - `kind = EMAIL` (fixed for email rows)
    - `emailAddress` (string)
    - `isPrimary` (boolean; default false)
- **Add Phone**
  - Appends a phone row with:
    - `kind = PHONE` (fixed for phone rows)
    - `phoneNumber` (string)
    - `extension` (string, optional)
    - `phoneLabel` (optional enum/label if backend supports; otherwise omit from payload)
    - `isPrimary` (boolean; default false)
- **Remove row**
  - Removes row from local model only.
- **Set Primary**
  - When a row is set to primary:
    - For EMAIL: unset `isPrimary` on all other email rows.
    - For PHONE: unset `isPrimary` on all other phone rows.
  - If user attempts to set a second primary via direct toggle, UI resolves by auto-demoting the previous primary (mirrors backend invariant) (DECISION-INVENTORY-003).

## State changes (frontend view-model)
- `editing` → `submitting` on Create
- `submitting` → `success` on 201/200 success response
- `submitting` → `error` on non-success response
- `error` → `editing` on user edits or retry

## Service interactions
- On submit, call backend create service with:
  - Person fields
  - Contact points list (emails + phones)
  - Primary flags per kind
- On success:
  - Store returned canonical identifier as `partyId` (DECISION-INVENTORY-001)
  - Navigate to person detail route if available; else show success panel

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Person fields:
  - `firstName`: required; trimmed; must not be empty after trim.
  - `lastName`: required; trimmed; must not be empty after trim.
  - `preferredContactMethod`: required; must be one of `EMAIL | PHONE_CALL | SMS | NONE`.
- Email contact points:
  - `emailAddress` required per email row; must match standard email format.
- Phone contact points (DECISION-INVENTORY-003):
  - Accept flexible input (spaces, dashes, parentheses).
  - Normalize by stripping non-digits for validation/payload `normalizedDigits`.
  - Valid if normalized digits length is 10–15.
  - `extension` is separate optional field; must be digits-only if provided.
- Primary constraints (DECISION-INVENTORY-003):
  - At most one primary email and at most one primary phone.
  - Zero primaries is allowed.
- Identifier rule (DECISION-INVENTORY-001):
  - UI routes and success messaging must use `partyId` as the canonical identifier; do not introduce `customerId` as a primary key.

## Enable/disable rules
- Disable **Create** button while `submitting`.
- Disable add/remove row actions while `submitting`.
- Disable editing inputs while `submitting`.

## Visibility rules
- Show email and phone sections even if empty; show empty-state guidance.
- Show success panel only after successful response.

## Error messaging expectations
- 400 validation:
  - Show banner: “Please correct the highlighted fields.”
  - Map `fieldErrors` to specific inputs; for repeatable rows, map by index if backend provides indices, otherwise show row-level error.
- 403 forbidden:
  - Show banner: “Access denied. You don’t have permission to create a person record.”
- 409 conflict:
  - If backend returns `PARTY_MERGED` for any referenced partyId (unlikely on create), show message and provide link to `mergedToPartyId` (DECISION-INVENTORY-014). (Defensive handling; no UI flow depends on it.)
- 5xx:
  - Show generic non-PII error; preserve inputs for retry.

## Load/view calls

## Create/update calls

### Create Individual Person (Party subtype Person) + ContactPoints
- **Action:** Create Party(Person) and associated ContactPoints in a single transaction (all-or-nothing).
- **Method:** `POST`
- **Moqui endpoint (placeholder pattern):** `/rest/api/v1/crm/parties/person` (exact path TBD)
- **Request body (DTO):**
  ```json
  {
    "firstName": "Jane",
    "lastName": "Doe",
    "preferredContactMethod": "EMAIL",
    "contactPoints": [
      {"kind":"EMAIL","emailAddress":"jane@example.com","isPrimary":true},
      {"kind":"PHONE","phoneNumber":"(555) 123-4567","normalizedDigits":"5551234567","extension":null,"isPrimary":false}
    ]
  }
  ```
- **Success:**
  - `201 Created` (or `200 OK` if backend uses 200; UI must accept either as success)
  - Response includes:
    - `partyId` (UUID) — canonical identifier (DECISION-INVENTORY-001)
    - Optional echo fields for display (e.g., displayName)
  ```json
  { "partyId": "aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa" }
  ```
- **Error cases:**
  - `400 Bad Request` for validation errors with payload:
    ```json
    {
      "errorCode": "FIELD_INVALID",
      "message": "Validation failed",
      "fieldErrors": {
        "firstName": "Required",
        "contactPoints[0].emailAddress": "Invalid email format"
      }
    }
    ```
  - `403 Forbidden`:
    ```json
    { "errorCode": "FORBIDDEN", "message": "Missing permission" }
    ```
  - `409 Conflict` (reserved for future duplicate-check flows; not used in this story unless backend already does it):
    ```json
    { "errorCode": "CONFLICT", "message": "..." }
    ```
  - `5xx` generic error; response must not leak PII.

# 12. Acceptance Criteria

## Scenario 1: Minimal person create succeeds
**Given** I am an authenticated CSR with permission to create person records  
**And** I am on the Create Person screen  
**When** I enter `firstName` and `lastName`  
**And** I select `preferredContactMethod = NONE`  
**And** I click Create  
**Then** the system submits a create request  
**And** I receive a success response (201 or 200) with a `partyId`  
**And** the UI shows confirmation including the new `partyId`

## Scenario 2: Create with multiple emails and phones and primary enforcement
**Given** I am an authenticated CSR with permission to create person records  
**When** I enter a valid name and select `preferredContactMethod = EMAIL`  
**And** I add 2 email rows with valid email values  
**And** I mark the second email as primary  
**And** I add 2 phone rows with values that normalize to 10–15 digits  
**And** I mark the first phone as primary  
**And** I click Create  
**Then** the UI ensures only one primary email and one primary phone are set in the payload  
**And** the request includes 4 contact points  
**And** the create succeeds and returns a `partyId`  
**And** the UI indicates success

## Scenario 3: Missing last name is blocked client-side
**Given** I am on the Create Person screen  
**When** I enter `firstName` but leave `lastName` empty  
**And** I select a preferred contact method  
**And** I click Create  
**Then** the UI shows a required-field validation error for `lastName`  
**And** no create request is submitted

## Scenario 4: Invalid email is rejected and nothing is created
**Given** I am on the Create Person screen  
**When** I enter valid `firstName`, `lastName`, and preferred contact method  
**And** I add an email row with value `not-an-email`  
**And** I click Create  
**Then** the UI shows an email format error (client-side or from backend 400)  
**And** the UI remains in editing/error state with user input preserved  
**And** the UI does not show a created `partyId`

## Scenario 5: Phone normalization and validation blocks invalid phone
**Given** I am on the Create Person screen  
**When** I add a phone row with value `12-34`  
**Then** the UI indicates the phone number is invalid because it does not normalize to 10–15 digits  
**And** the Create action is blocked until corrected

## Scenario 6: Not authorized to create
**Given** I am authenticated but do not have permission to create person records  
**When** I attempt to create a person  
**Then** the backend returns 403 (or access is blocked before submit per app convention)  
**And** the UI shows an authorization error message  
**And** no success confirmation is shown
