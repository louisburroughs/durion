## Issue Body

## 1. Story Header

**Title**  
[FRONTEND] [STORY] Appointment: Reschedule Appointment (Backend-Owned Notifications + Conflict Handling)

**Primary Persona**  
Scheduler (Service Advisor / Dispatcher)

**Business Value**  
Keep shop operations coordinated by allowing authorized users to reschedule appointments while preserving estimate/work order links, preventing/handling conflicts correctly, recording an auditable reason trail, and surfacing downstream notification outcomes without letting notification delivery failures block a successful reschedule.

---

## 2. Story Intent

**As a** Scheduler  
**I want** to reschedule an existing appointment (date/time) with a required reason and conditional notes  
**So that** schedule changes are coordinated across shop operations with correct conflict enforcement, facility policy enforcement, idempotent submission, and an auditable trail.

### In-scope
- UI workflow to reschedule an existing appointment:
  - Select new start/end date/time (facility timezone)
  - Select reason (backend-owned enum) and enter notes where required
  - Submit reschedule and render conflicts returned on submit (hard/soft), including suggested alternative time slots when provided
  - Override SOFT conflicts only when permitted and with required override reason (HARD conflicts are never overridable)
  - Handle reschedule policy enforcement (minimum notice, reschedule count limit) via backend responses; collect approvalReason only when backend indicates it is required and user has permission
- Display resulting update status:
  - New scheduled time
  - Notification outcome summary (if provided by backend; reschedule success is not negated by notification issues)
- Facility-scoped permission gating and error feedback
- Audit visibility (who/why/when) in appointment context when backend provides audit endpoint

### Out-of-scope
- Creating appointments
- Editing estimate/work order links (immutable)
- Recurring/series reschedules
- Implementing conflict detection logic on the frontend (frontend only renders backend results)
- UI toggles to control notification delivery (backend-owned in initial contract)
- Building notification delivery UI (templates, channels, retries)

---

## 3. Actors & Stakeholders
- **Scheduler**: initiates reschedule
- **Shop Manager / Dispatcher**: may perform SOFT conflict override and/or approve reschedule exceptions depending on permission
- **Customer**: may receive reschedule notifications (backend-owned policy)
- **Assigned Mechanic**: may be notified (backend-owned policy)
- **Shop Management (shopmgmt) backend**: SoR for appointment schedule/assignment policy enforcement, conflicts, audit
- **Work Execution service**: consumes reschedule effects indirectly (not called by frontend)
- **Notification service**: delivery mechanism (not called by frontend)
- **Audit service/log**: records immutable audit entries (read-only UI consumption)

---

## 4. Preconditions & Dependencies

### Preconditions
- Appointment exists and is in a reschedulable state (backend-enforced; UI must handle denials).
- User is authenticated and authorized for the appointment’s facility (facility scoping is deny-by-default server-side).
- User has `RESCHEDULE_APPOINTMENT` permission (server-side enforced; UI may hide entry points if permissions/allowedActions are provided in payload).

### Dependencies
- Backend services for:
  - Loading appointment reschedule context (current schedule, status, facilityTimeZoneId, rescheduleCount, allowedActions/permissions hints if available)
  - Submitting reschedule (returns success or 409 conflicts payload; idempotent via clientRequestId)
  - Optional: audit list endpoint for appointment (permission-gated, redacted)
- Near-real-time assignment updates are not required for this reschedule flow (covered by separate assignment visibility story); however, Appointment Detail should reflect updated schedule after reschedule.

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From Appointment Detail screen: “Reschedule” action (visible/enabled only when allowed by backend-provided allowedActions/permissions if present; otherwise visible but may error on submit with 403/422).
- From Appointment list/board: “Reschedule” action navigates to Appointment Detail then opens reschedule screen.

### Screens to create/modify (Moqui)
- **Modify**: `apps/pos/screen/shopmgmt/AppointmentDetail.xml`
  - Add “Reschedule” action linking to reschedule screen with `appointmentId`
  - After reschedule success, refresh appointment header schedule fields and show result banner including notificationOutcomeSummary if present
  - Optional: add “Audit” panel/section that calls audit endpoint when user has AUDIT_VIEW (or backend indicates allowed)
- **Create**: `apps/pos/screen/shopmgmt/AppointmentReschedule.xml`
  - Dedicated screen (can be modal-style via Moqui transitions, but must have a routable path)
  - Contains a form for new start/end date/time, reason, notes (conditional), and conditional override/approval fields driven by backend responses
- **Optional**: `component://apps/pos/screen/shopmgmt/widget/AppointmentRescheduleForm.xml` as reusable form widget

### Navigation context
- Route parameters:
  - required: `appointmentId`
- Facility context:
  - Reads may omit facilityId (backend derives from appointmentId and enforces access)
  - Writes MUST include facilityId explicitly in request body (DECISION-SHOPMGMT-012)
- Post-success navigation:
  - Redirect back to Appointment Detail (`appointmentId`) with a success banner and updated schedule visible

### User workflows (happy + alternate)
**Happy path**
1. Scheduler opens Appointment Detail → clicks “Reschedule”.
2. Reschedule screen loads appointment reschedule context (current schedule, facilityTimeZoneId, rescheduleCount, allowed reasons).
3. Scheduler selects new start/end date/time and a reason; enters notes only if required (e.g., reason OTHER).
4. Scheduler submits.
5. Backend returns success; UI navigates back to Appointment Detail and shows updated schedule and any notificationOutcomeSummary.

**Alternate paths**
- Submit returns conflicts:
  - HARD conflicts: show blocking list; no override option; user must pick a different time (DECISION-SHOPMGMT-002).
  - SOFT conflicts: if user has OVERRIDE_SCHEDULING_CONFLICT, allow entering overrideReason and resubmitting; otherwise show blocking message and require escalation (DECISION-SHOPMGMT-007).
  - If suggestedAlternatives are provided, render them as selectable time slots (time-only suggestions; treat as hints) (DECISION-SHOPMGMT-011).
- Policy enforcement:
  - Reschedule count >= 2: backend may require APPROVE_RESCHEDULE permission and approvalReason; UI prompts only when backend indicates required (DECISION-SHOPMGMT-004).
  - Minimum notice / operating hours: backend returns policy failure or HARD conflict; UI renders message and blocks submit (DECISION-SHOPMGMT-008).
- Idempotent retry:
  - If submit times out, user can retry; UI reuses same clientRequestId and expects backend to return original success response (DECISION-SHOPMGMT-014).

## 6. Functional Behavior

### Triggers
- User clicks “Reschedule” from appointment context.
- User edits proposed start/end date/time, reason, notes.
- User clicks “Submit reschedule”.
- User clicks “Retry” after timeout/network error (must reuse clientRequestId).

### UI actions (deterministic)
- Load reschedule context:
  - Call load service with `appointmentId`
  - Render current schedule and facility timezone indicator (facilityTimeZoneId)
  - Render rescheduleCount if provided (informational)
  - Render allowed reasons list if provided; otherwise render a backend-provided enum list endpoint or treat as required field with server validation (see Service Contracts)
- Collect inputs:
  - `newScheduledStartDateTime` (required, ISO-8601 with offset)
  - `newScheduledEndDateTime` (required, ISO-8601 with offset)
  - `rescheduleReason` (required; backend-owned enum)
  - `rescheduleReasonNotes` (required when reason=OTHER; optional otherwise unless backend requires for a specific error/override)
  - `overrideSoftConflicts` (boolean; only set true when resubmitting after SOFT conflicts and user chooses to override)
  - `overrideReason` (required when overrideSoftConflicts=true)
  - `approvalReason` (required only when backend indicates approval required and user has APPROVE_RESCHEDULE)
  - `expectedAppointmentVersion` (optional if backend supports optimistic concurrency for appointment reschedule; if provided by load, include on submit)
  - `clientRequestId` (required for submit; generated once per user submit attempt and reused for retries)
  - `facilityId` (required for submit; obtained from load response)
- Submit reschedule:
  - Call submit service with payload above
  - On success:
    - Navigate back to Appointment Detail
    - Show success banner including new schedule and notificationOutcomeSummary if present
  - On 409 conflicts:
    - Render conflicts grouped by severity
    - If any HARD conflicts: block resubmission with override; allow user to change time or select suggested alternative
    - If only SOFT conflicts:
      - If user has OVERRIDE_SCHEDULING_CONFLICT: show overrideReason input and “Override and submit” action
      - Else: block submit and show “Manager override required” message
  - On 422 policy/eligibility errors:
    - Render banner with backend message; if code indicates approval required, show approvalReason input only if user has APPROVE_RESCHEDULE and backend indicates it can proceed with approvalReason
  - On 403:
    - Show access denied and return to Appointment Detail
  - On 409 version mismatch (if used for appointment reschedule):
    - Prompt reload; on reload, keep user-entered proposed values in form state

### State changes (frontend perspective)
`idle → loading → editing → submitting → (success → redirect) | (conflicts) | (policyError) | (error)`

### Service interactions (frontend perspective)
- `shopmgmt.Appointment.get#RescheduleContext(appointmentId)`
- `shopmgmt.Appointment.reschedule#Submit(payload)`
- Optional: `shopmgmt.AppointmentAudit.list(appointmentId)` for Appointment Detail audit panel (permission-gated)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Required fields before submit:
  - new start/end date/time
  - rescheduleReason
  - facilityId (from load response; required for writes)
  - clientRequestId
- Conditional required fields:
  - rescheduleReasonNotes required when rescheduleReason = OTHER (DECISION-SHOPMGMT-004/013 guidance on reason handling; OTHER requires notes per domain notes)
  - overrideReason required when overriding SOFT conflicts (DECISION-SHOPMGMT-007)
  - approvalReason required when backend indicates reschedule approval is required due to reschedule count policy and user has APPROVE_RESCHEDULE (DECISION-SHOPMGMT-004)
- Date/time semantics:
  - UI must display and collect times in facility timezone; backend returns facilityTimeZoneId and timestamps with offset (DECISION-SHOPMGMT-015)
  - UI must not infer operating hours; if backend blocks due to hours, show returned conflict/policy message (DECISION-SHOPMGMT-008)

### Enable/disable rules
- Submit enabled when required fields present; conflict pre-check is NOT required (conflicts returned on submit) (DECISION-SHOPMGMT-011)
- Override controls:
  - Never show override option for HARD conflicts (HARD not overridable) (DECISION-SHOPMGMT-002)
  - Show override option for SOFT conflicts only when user has OVERRIDE_SCHEDULING_CONFLICT (permission hint may come from backend; otherwise attempt submit and handle 403/422)
- Approval controls:
  - Show approvalReason input only when backend indicates RESCHEDULE_APPROVAL_REQUIRED (or equivalent code) and user has APPROVE_RESCHEDULE

### Visibility rules
- Show suggested alternatives section only when backend provides suggestedAlternatives[]
- Show notification outcome section only when backend provides notificationOutcomeSummary
- Audit panel visible only when user has AUDIT_VIEW (or backend indicates allowed) and endpoint exists

### Error messaging expectations
- 400 (syntactic/field validation): inline field errors using fieldErrors[]
- 422 (policy/eligibility): banner with stable errorCode and safe message; do not guess policy thresholds client-side (DECISION-SHOPMGMT-011)
- 409 (conflicts): render conflicts list; for version mismatch, show reload prompt
- 403: access denied banner (do not leak cross-facility existence)
- 404: “Appointment not found” and navigate back to list/detail safely

## 8. Data Requirements

### Entities involved (frontend read/write)
- **Appointment** (read)
- **RescheduleContext** (read model; may be Appointment + metadata)
- **Conflict** (read model returned on 409)
- **AuditEntry** (read model; optional)
- **NotificationOutcomeSummary** (read model; optional)

### Fields (contract-level expectations)

**RescheduleContext (read)**
- `appointmentId` (string/ID, required)
- `facilityId` (string/ID, required) — required for subsequent write
- `facilityTimeZoneId` (IANA string, required) (DECISION-SHOPMGMT-015)
- `scheduledStartDateTime` (ISO-8601 with offset, required)
- `scheduledEndDateTime` (ISO-8601 with offset, required)
- `status` (string enum, required; treat as opaque)
- `rescheduleCount` (integer, optional but recommended for UX)
- `allowedActions[]` (array of strings, optional; used for gating)
- `allowedRescheduleReasons[]` (array of strings, optional; backend-owned enum values)
- `version` (integer/string, optional; if provided, used for optimistic concurrency on reschedule)

**Reschedule submit (write)**
- `appointmentId` (required)
- `facilityId` (required) (DECISION-SHOPMGMT-012)
- `newScheduledStartDateTime` (required, ISO-8601 with offset)
- `newScheduledEndDateTime` (required, ISO-8601 with offset)
- `rescheduleReason` (required, backend-owned enum string)
- `rescheduleReasonNotes` (string, required when reason=OTHER; max length not specified by domain—treat as backend-validated)
- `overrideSoftConflicts` (boolean, optional; only for SOFT conflicts)
- `overrideReason` (string, required when overrideSoftConflicts=true)
- `approvalReason` (string, required only when backend indicates approval required; max length not specified by domain—treat as backend-validated)
- `expectedVersion` (optional; include if provided by load)
- `clientRequestId` (required; idempotency key) (DECISION-SHOPMGMT-014)

**Conflict response (read; 409)**
- `errorCode` = `SCHEDULING_CONFLICT` (or backend equivalent)
- `conflicts[]` each:
  - `code` (string, required)
  - `severity` (`HARD|SOFT`, required)
  - `message` (string, safe-to-display, required)
  - `overridable` (boolean, required; must be false for HARD)
- `suggestedAlternatives[]` (optional):
  - `startDateTime` (ISO-8601 with offset)
  - `endDateTime` (ISO-8601 with offset)

**Success response (read)**
- `appointmentId` (required)
- `scheduledStartDateTime` / `scheduledEndDateTime` (required)
- `version` (optional)
- `notificationOutcomeSummary` (optional object; render as informational) (DECISION-SHOPMGMT-016)

**AuditEntry (read; optional)**
- `actorId` (string)
- `action` (string)
- `occurredAt` (ISO-8601)
- `reasonCode` (string, optional)
- `identifiers` (object, optional; appointmentId, etc.)
- No customer PII; no free-text notes unless explicitly authorized (DECISION-SHOPMGMT-017)

### Read-only vs editable
- Read-only:
  - estimateId/workOrderId link (immutable)
  - current scheduled times (display)
- Editable:
  - new scheduled times
  - reason + notes (conditional)
  - overrideReason (conditional)
  - approvalReason (conditional)

### Derived/calculated fields
- None computed client-side for policy thresholds (minimum notice, operating hours). UI may display backend-provided indicators/messages only.

> Names follow DECISION-SHOPMGMT-011 guidance (stable, resource-oriented). Exact Moqui service names may differ; backend must provide final names, but UI implementation can proceed with these placeholders and a single mapping layer.

### Load/view calls
1. **Get reschedule context**

   - Response: `RescheduleContext` (includes facilityId + facilityTimeZoneId)

2. **Optional: Audit list (Appointment Detail)**

   - Request: `{ appointmentId, pageIndex?, pageSize? }`
   - Response: `{ entries[], pageIndex, pageSize, totalCount? }`

### Create/update calls
- none

### Submit/transition calls
1. **Submit reschedule**
   - Service: `shopmgmt.Appointment.reschedule#Submit`
   - Request: Reschedule submit payload (includes facilityId + clientRequestId)
   - Success Response: updated appointment schedule + optional notificationOutcomeSummary
   - Conflict Response: HTTP 409 with conflicts payload (HARD/SOFT + suggestedAlternatives) (DECISION-SHOPMGMT-011)
   - Policy Response: HTTP 422 with machine-readable errorCode (e.g., `RESCHEDULE_APPROVAL_REQUIRED`, `OUTSIDE_OPERATING_HOURS`, etc.) (DECISION-SHOPMGMT-011)

### Error handling expectations
- **400 VALIDATION_ERROR**: fieldErrors[]; map to inline errors
- **403 FORBIDDEN**: show access denied; do not leak cross-facility details (DECISION-SHOPMGMT-012)
- **404 NOT_FOUND**: show not found; navigate safely
- **409 SCHEDULING_CONFLICT**: render conflicts; allow SOFT override path only
- **409 VERSION_MISMATCH** (if used): prompt reload; show currentVersion if provided
- **422 POLICY_ERROR**: show banner; if approval required and user can approve, prompt for approvalReason and resubmit
- **5xx / network**: show retry; preserve form state; reuse clientRequestId on retry

**Request headers**
- UI must send `X-Request-Id` correlation header on all calls (DECISION-SHOPMGMT-011)
- UI must not log free-text notes/reasons client-side (PII/sensitive operational notes guidance)

## 10. State Model & Transitions

### Allowed states (relevant to reschedule)
- Appointment status is backend-owned; UI treats as opaque and relies on backend allowedActions/denials (DECISION-SHOPMGMT-013).
- Recommended canonical statuses may include: SCHEDULED, CONFIRMED, IN_PROGRESS, AWAITING_PARTS, READY, COMPLETED, CANCELLED, NO_SHOW; UI must not hardcode logic beyond display labels.

### Role-based transitions (frontend gating)
- `RESCHEDULE_APPOINTMENT`: can attempt reschedule when backend allows
- `OVERRIDE_SCHEDULING_CONFLICT`: can override SOFT conflicts with overrideReason (DECISION-SHOPMGMT-007)
- `APPROVE_RESCHEDULE`: can provide approvalReason when backend requires approval due to reschedule count policy (DECISION-SHOPMGMT-004)
- `AUDIT_VIEW`: can view audit entries (DECISION-SHOPMGMT-017)

### UI behavior per state
- If backend indicates reschedule not allowed (via allowedActions absence or 422/403), hide/disable Reschedule entry point where possible and show explanatory banner on attempt.
- If appointment is terminal (e.g., COMPLETED/CANCELLED), backend should deny; UI shows “Not reschedulable” message.

## 11. Alternate / Error Flows

1. **Client-side validation failure**
   - Missing start/end, missing reason → inline errors; prevent submit.
   - Reason OTHER with empty notes → inline error; prevent submit.

2. **HARD conflicts returned on submit (409)**
   - Render conflicts as blocking.
   - Do not render override controls.
   - If suggestedAlternatives present, allow user to select one to populate start/end and resubmit.

3. **SOFT conflicts returned on submit (409)**
   - Render conflicts as warnings.
   - If user has OVERRIDE_SCHEDULING_CONFLICT: show overrideReason input and “Override and submit”.
   - If not: block submit and instruct escalation.

4. **Reschedule approval required (422)**
   - If user lacks APPROVE_RESCHEDULE: show blocking banner “Approval required”.
   - If user has APPROVE_RESCHEDULE: show approvalReason input; require non-empty; resubmit.

5. **Operating hours / closure (409 HARD conflict or 422 policy)**
   - Render message from backend; block submit; user must choose another time.

6. **Timeout / retry**
   - If submit request times out, UI shows retry option.
   - Retry must reuse the same clientRequestId to avoid duplicates (DECISION-SHOPMGMT-014).

7. **Concurrency/version mismatch (optional 409)**
   - Prompt reload of reschedule context; preserve user-entered proposed values in the form for re-application.

8. **Unauthorized / cross-facility**
   - 403/404: show generic access/not found message; do not reveal existence.

## 12. Acceptance Criteria (Gherkin)

### Scenario 1: Reschedule succeeds with no conflicts
Given a Scheduler has `RESCHEDULE_APPOINTMENT` permission for the appointment’s facility  
And an appointment exists and backend allows reschedule  
When the Scheduler enters a new start and end date/time in the facility timezone  
And selects a reschedule reason that is not OTHER  
And submits the reschedule request with a clientRequestId  
Then the UI navigates back to Appointment Detail  
And displays the updated scheduled start/end date/time  
And the estimate/work order link remains unchanged and read-only.

### Scenario 2: Reason OTHER requires notes
Given a Scheduler is rescheduling an eligible appointment  
When the Scheduler selects reschedule reason OTHER  
And leaves rescheduleReasonNotes empty  
Then the UI prevents submission and shows a field-level error for notes  
When the Scheduler enters notes and submits  
Then the request is sent to the backend.

### Scenario 3: HARD conflicts block reschedule and cannot be overridden
Given a Scheduler has `RESCHEDULE_APPOINTMENT` permission  
And the backend returns a 409 SCHEDULING_CONFLICT with at least one conflict where severity is HARD and overridable is false  
When the UI receives the response  
Then the UI displays the HARD conflicts as blocking errors  
And does not display an override action  
And does not submit an override attempt.

### Scenario 4: SOFT conflicts can be overridden with permission and reason
Given a user has `RESCHEDULE_APPOINTMENT` and `OVERRIDE_SCHEDULING_CONFLICT` permissions  
And the backend returns a 409 SCHEDULING_CONFLICT with only SOFT conflicts  
When the user enters a non-empty overrideReason  
And resubmits with overrideSoftConflicts=true  
Then the reschedule succeeds  
And the UI indicates that a conflict override was applied (based on backend response or audit entry availability).

### Scenario 5: Reschedule approval required after exceeding reschedule limit
Given an appointment has rescheduleCount of 2 or more  
And the backend returns a 422 errorCode RESCHEDULE_APPROVAL_REQUIRED on submit  
When a user without `APPROVE_RESCHEDULE` views the error  
Then the UI shows a blocking banner indicating approval is required  
And does not allow submission to proceed  
When a user with `APPROVE_RESCHEDULE` provides a non-empty approvalReason and resubmits  
Then the reschedule succeeds.

### Scenario 6: Idempotent retry does not create duplicate reschedules
Given a Scheduler submits a reschedule with a clientRequestId  
And the network times out before the UI receives a response  
When the Scheduler retries the submit using the same clientRequestId  
Then the backend returns the original success response  
And the UI shows a single reschedule outcome (no duplicate changes).

### Scenario 7: Notification outcome is informational and does not negate success
Given a Scheduler reschedules an appointment successfully  
And the backend response includes notificationOutcomeSummary with a non-success result (e.g., QUEUED or FAILED)  
When the UI displays the result  
Then the UI shows the reschedule as successful  
And displays the notificationOutcomeSummary as informational follow-up.
