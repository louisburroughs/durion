## Issue Body

## 1. Story Header

### Title
[FRONTEND] Appointment: Show Assignment (Bay/Mobile + Mechanic) with Near-Real-Time Updates

### Primary Persona
Service Advisor

### Business Value
Service Advisors can quickly confirm where work will be performed (bay vs mobile) and who is assigned (mechanic), improving customer expectation setting and reducing operational confusion.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to view the current appointment assignment (bay or mobile unit, mechanic, and notes)  
- **So that** I can set accurate expectations with the customer and coordinate internally.

### In-scope
- Read-only display of assignment details on Appointment Detail view.
- Optional compact assignment summary in list contexts **only if** an Appointment List screen already exists in the frontend IA.
- Near-real-time refresh behavior:
  - Preferred: SSE subscription for assignment updates (facility-scoped stream; filter by appointmentId).
  - Fallback: polling every 30 seconds while Appointment Detail is visible.
  - Manual refresh action.
- Role-based access control for viewing assignments and (optional) editing assignment notes.
- Degraded-mode display when mechanic identity fields are missing or People/HR is unavailable (must not block assignment display).
- Optimistic concurrency handling for notes edits (if enabled) using `expectedVersion` and 409 handling.

### Out-of-scope
- Creating/updating appointments, scheduling, rescheduling, conflict detection/override flows.
- Assignment decision logic (how bays/mobile/mechanics are chosen).
- Automated customer notifications controls/toggles (backend-owned).
- Reverse geocoding mobile GPS coordinates.
- Mechanic HR profile management.

---

## 3. Actors & Stakeholders

### Primary
- **Service Advisor**: views assignment to communicate with customer.

### Secondary
- **Shop Manager / Dispatcher**: may have additional visibility and may edit assignment notes if permitted.
- **Mechanic**: stakeholder of assignment, not primary UI user here.
- **Customer**: impacted indirectly.

### Systems
- **shopmgmt backend**: system of record for appointment assignment data and assignment notes policy/audit.
- **People/HR backend**: system of record for mechanic identity; shopmgmt may expose a minimal derived view (mechanicId + optional displayName/photoUrl).
- **Audit subsystem**: captures scheduling/assignment changes and notes edits (backend-owned; UI displays redacted audit entries only when authorized).

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in POS frontend.
- User is authorized to view the Appointment Detail for the appointment’s facility (facility scoping enforced server-side).
- Appointment exists and is accessible within facility scope.

### Dependencies
- shopmgmt provides a read model `AssignmentView` for an appointment (Decision: DECISION-SHOPMGMT-AGENT_GUIDE “AssignmentView is first-class read model”).
- Near-real-time updates mechanism:
  - Preferred: Server-Sent Events (SSE) delivering full `AssignmentView` updates (Decision: DECISION-SHOPMGMT-006).
  - Fallback: polling every 30 seconds while Appointment Detail is visible (Decision: DECISION-SHOPMGMT-006).
- Optional: shopmgmt service to update assignment notes with optimistic concurrency and required edit reason (Decisions: DECISION-SHOPMGMT-005, DECISION-SHOPMGMT-017).
- Correlation header: frontend sends `X-Request-Id` on service calls (Decision: DECISION-SHOPMGMT-011).

**Decision rationale applied**
- Real-time mechanism and topic naming are defined by shopmgmt decisions:
  - SSE is preferred; polling fallback is required (DECISION-SHOPMGMT-006).
  - Facility-scoped topic naming: `shopmgmt.assignment.facility.<facilityId>`; client filters by appointmentId (DECISION-SHOPMGMT-006).
  - Events deliver full `AssignmentView` (DECISION-SHOPMGMT-006).
- Facility scoping for writes requires explicit `facilityId` (DECISION-SHOPMGMT-012). This story is read-first; notes edit (if enabled) must include facilityId.

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Appointment Detail screen (primary).
- Appointment List screen (secondary, only if it exists): show a compact assignment summary per row.

### Screens to create/modify (Moqui)
- **Modify**: `apps/pos/screen/appointment/AppointmentDetail.xml` (or the repo’s equivalent Appointment Detail screen)
  - Add an “Assignment” section driven by a screen action that loads `AssignmentView`.
  - Add client-side subscription lifecycle (start on screen render; stop on screen leave).
- **Optional Modify**: `apps/pos/screen/appointment/AppointmentList.xml` (or equivalent)
  - Add a compact assignment summary field/column using `AssignmentView` if already available in list payload; otherwise do not add new list-level calls in this story.

### Navigation context
- Required parameter: `appointmentId`.
- Facility context:
  - For reads, facilityId may be omitted if backend derives it from appointmentId while enforcing authorization (DECISION-SHOPMGMT-012).
  - For SSE subscription, facilityId is required to subscribe to the facility stream (DECISION-SHOPMGMT-006).
  - FacilityId source for UI: from appointment detail payload (preferred) or existing facility context in the POS session; do not guess.

### User workflows (happy + alternate paths)

#### Happy path: assignment exists (BAY or MOBILE_UNIT)
1. User opens Appointment Detail.
2. UI loads `AssignmentView` for `appointmentId`.
3. UI renders:
   - Assignment type: BAY / MOBILE_UNIT
   - Bay/mobile identifiers (and optional locationName)
   - Mechanic identity (displayName/photoUrl if present; otherwise mechanicId fallback)
   - Assignment notes (read-only unless user has edit permission)
   - Timestamps: assignedAt, lastUpdatedAt (if provided)
4. UI subscribes to SSE for the facility stream and filters events by appointmentId.
5. When an `AssignmentUpdated` event arrives with a newer `version`, UI updates the assignment section and shows a non-blocking “Assignment updated” banner.

#### Alternate path: UNASSIGNED
- UI shows “No resources assigned yet” and any available timestamps/status.

#### Alternate path: mechanic identity degraded
- If `AssignmentView.mechanic.displayName` is missing but `mechanicId` exists:
  - Show “Mechanic ID: <id>” and do not block rendering.
- UI must not require People/HR calls to render assignment (DECISION-SHOPMGMT-009).

#### Alternate path: SSE unavailable
- If SSE connection fails or browser lacks EventSource:
  - Fall back to polling `AssignmentView` every 30 seconds while Appointment Detail is visible (DECISION-SHOPMGMT-006).
  - Continue to support manual refresh.

## 6. Functional Behavior

### Triggers
- Enter Appointment Detail screen.
- User clicks “Refresh assignment”.
- SSE event received for the facility stream.
- Polling interval fires while Appointment Detail is visible.
- (Optional) user with permission edits notes and saves.

### UI actions
- Load and display assignment section.
- Start SSE subscription:
  - Endpoint: **TBD exact path**; must accept `facilityId` as query param (DECISION-SHOPMGMT-006).
  - Subscribe once per facility context; filter by appointmentId client-side.
- On update:
  - If event payload includes full `AssignmentView`, replace local model.
  - Ignore out-of-order updates using `version` (preferred) or `lastUpdatedAt` (fallback) (DECISION-SHOPMGMT-006).
- Show a non-blocking banner/toast when assignment changes while viewing:
  - Message may be generic (“Assignment updated”) because backend does not guarantee a diff (shopmgmt explicitly does not own UI diffing).
- Provide manual refresh control.

### State changes (frontend)
- View model states:
  - `idle` → `loading` → `loaded`
  - `loaded` → `refreshing` → `loaded`
  - `error` (with retry)
- Track:
  - `currentAssignmentVersion` (number) when present; else `currentLastUpdatedAt` (datetime).

### Service interactions
- shopmgmt:
  - Load `AssignmentView` by appointmentId.
  - Optional: update assignment notes (requires permission, expectedVersion, notesEditReason).
- People/HR:
  - No required calls for this story; mechanic identity may be embedded in `AssignmentView` when authorized (DECISION-SHOPMGMT-009). If the frontend already has a People lookup utility, it may be used as a progressive enhancement but must not be required.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Display-only path: no user input validation.
- Notes edit path (only if enabled):
  - `assignmentNotes` max length: 500 characters (DECISION-SHOPMGMT-005).
  - `notesEditReason` required, non-empty, max 200 characters (DECISION-SHOPMGMT-017).
  - Client-side validation mirrors server rules; server remains authoritative.

### Enable/disable rules
- Assignment section is shown only if backend authorizes the user to view it; UI may additionally hide the section when the user lacks a known permission flag (if permissions are available client-side).
- Notes editing controls:
  - Visible/enabled only when user has `EDIT_ASSIGNMENT_NOTES`.
  - Save disabled until notesEditReason is provided and notes length <= 500.

### Visibility rules
- Appointment status gating:
  - UI must not hardcode status enums for authorization decisions; backend is authoritative (DECISION-SHOPMGMT-013).
  - If appointment payload includes `allowedActions` or a boolean like `canViewAssignment`, use it to decide whether to render the section.
  - Cancelled appointment assignment visibility is permission-gated server-side (DECISION-SHOPMGMT-013). UI should handle 403/404 without leaking details.

### Error messaging expectations
- 401/403:
  - “You don’t have permission to view assignments for this facility/appointment.”
- 404:
  - “Appointment not found or not accessible.”
- 503/network:
  - If previously loaded data exists: “Assignment data is temporarily unavailable. Showing last known data.” + retry.
  - Else: show error state + retry.
- People/HR unavailable (only if a People call is attempted as enhancement):
  - Show mechanicId fallback and a non-blocking warning “Mechanic details unavailable.”

### Notes sensitivity
- Assignment notes are potentially sensitive; frontend must not log note content or notesEditReason in client logs/telemetry (DECISION-SHOPMGMT-005).

## 8. Data Requirements

### Entities / View Models (frontend-facing)
- `AssignmentView` (shopmgmt read model; contract shape per domain guide).
- `AssignmentUpdated` SSE event payload (full `AssignmentView`).

### Fields (type, required, defaults)

#### AssignmentView (required shape for UI)
- `appointmentId` (string/UUID, required)
- `facilityId` (string/UUID, required in payload or derivable; required for SSE subscribe)
- `assignmentType` (enum string: `BAY` | `MOBILE_UNIT` | `UNASSIGNED`, required) (DECISION-SHOPMGMT-003)
- `bay` (object|null)
  - `bayId` (string/UUID, required if assignmentType=BAY)
  - `bayNameOrNumber` (string, required if assignmentType=BAY)
  - `locationName` (string, optional)
- `mobileUnit` (object|null)
  - `mobileUnitId` (string/UUID, required if assignmentType=MOBILE_UNIT)
  - `mobileUnitName` (string, optional)
  - `lastKnownLat` (number, optional)
  - `lastKnownLon` (number, optional)
  - `lastUpdatedAt` (datetime, optional)
- `mechanic` (object|null)
  - `mechanicId` (string/UUID, optional)
  - `displayName` (string, optional)
  - `photoUrl` (string, optional)
- `assignmentNotes` (string, optional; max 500)
- `assignedAt` (datetime, optional)
- `lastUpdatedAt` (datetime, optional)
- `version` (number, preferred; used for ordering/ignore out-of-order updates) (DECISION-SHOPMGMT-006)
- `assignmentStatus` (string enum, optional; treat as opaque string for display)

#### Read-only vs editable (by role)
- Service Advisor: all fields read-only.
- Shop Manager/Dispatcher:
  - `assignmentNotes` editable only with `EDIT_ASSIGNMENT_NOTES` (DECISION-SHOPMGMT-005).

#### Derived/calculated fields (frontend)
- `displayAssignmentSummary` (string):
  - `Bay <bayNameOrNumber> — <mechanicDisplayOrIdOrUnassigned>`
  - `Mobile — <mechanicDisplayOrIdOrUnassigned>`
  - `Unassigned`
- `isStaleUpdateIgnored` (boolean): true when an SSE event has `version` <= current version (or lastUpdatedAt <= current lastUpdatedAt).

## 9. Service Contracts (Frontend Perspective)

> Moqui service names/paths must be confirmed in the repo; this story defines required operations, request/response shapes, and error handling. Exact service names remain an Open Question.

### Load/view calls

1) **Load AssignmentView**
- Operation: `shopmgmt.assignment.get#AssignmentView` (**TBD exact name**)
- Inputs:
  - `appointmentId` (required)
- Output: `AssignmentView`
- Errors:
  - 401/403 unauthorized
  - 404 not found / not accessible (must not leak cross-facility existence)
  - 503 service unavailable

2) **SSE stream subscribe (facility-scoped)**
- Endpoint: **TBD exact path**, produces `text/event-stream`
- Inputs:
  - `facilityId` (required) (DECISION-SHOPMGMT-006)
- Events:
  - Event type: `AssignmentUpdated` (or `ASSIGNMENT_UPDATED`; backend-defined)
  - Payload: full `AssignmentView` (DECISION-SHOPMGMT-006)
- Client behavior:
  - Filter by `appointmentId`
  - Ignore out-of-order by `version` (preferred) or `lastUpdatedAt`

### Create/update calls (optional; only if enabled in this story)

3) **Update assignment notes**
- Operation: `shopmgmt.assignment.updateNotes` (**TBD exact name**)
- Inputs (request body):
  - `facilityId` (required for writes) (DECISION-SHOPMGMT-012)
  - `appointmentId` (required) or `assignmentId` (if contract uses assignmentId; **TBD**)
  - `assignmentNotes` (string, nullable; max 500) (DECISION-SHOPMGMT-005)
  - `notesEditReason` (string, required; max 200) (DECISION-SHOPMGMT-017)
  - `expectedVersion` (number, required) (DECISION-SHOPMGMT-005)
  - `clientRequestId` (string/UUID, optional; recommended if backend supports idempotency for this operation—**TBD**)
- Output:
  - Updated `AssignmentView` (preferred) or `{ assignmentId, version, lastUpdatedAt }` plus a follow-up reload.
- Errors:
  - 400 syntactic validation (missing required fields)
  - 422 policy/validation (e.g., notes too long) (DECISION-SHOPMGMT-011)
  - 403 permission denied
  - 409 `VERSION_MISMATCH` with `currentVersion` (DECISION-SHOPMGMT-005)

### Submit/transition calls
- None.

### Error handling expectations
- 409 on notes save:
  - Show “This assignment changed while you were editing. Reloaded latest notes.” and reload `AssignmentView`.
- SSE errors:
  - Close stream and fall back to polling; show non-blocking “Live updates unavailable; refreshing periodically.”

## 10. State Model & Transitions

### Allowed states
- Assignment type (exclusive): `BAY` | `MOBILE_UNIT` | `UNASSIGNED` (DECISION-SHOPMGMT-003).
- Assignment status (optional field): treat as backend-owned enum string; display only.

### Role-based transitions
- None for assignment type/status in this story.
- Notes edit is a write action gated by `EDIT_ASSIGNMENT_NOTES` and optimistic concurrency (DECISION-SHOPMGMT-005).

### UI behavior per state
- `assignmentType=BAY`: show bay details; hide mobile unit details.
- `assignmentType=MOBILE_UNIT`: show mobile unit details; hide bay details.
- `assignmentType=UNASSIGNED`: show empty state; hide bay/mobile details.
- If `mechanic` missing: show “Mechanic: Unassigned”.
- If `assignmentStatus` present: show as read-only label.

## 11. Alternate / Error Flows

### Validation failures (notes edit only)
- Notes length > 500:
  - Prevent submit; inline error “Max 500 characters.”
- Missing notesEditReason:
  - Prevent submit; inline error “Reason is required.”
- Server returns 422:
  - Map to inline field error using `errorCode`/`fieldErrors` if provided.

### Concurrency conflicts
- Notes save returns 409 `VERSION_MISMATCH`:
  - Reload `AssignmentView`.
  - Show message and allow user to re-apply changes manually.

### Unauthorized access
- If assignment load returns 403:
  - Render a permission message in the assignment section area.
  - Do not retry automatically; allow manual retry.

### Empty states
- No assignment exists / assignmentType=UNASSIGNED:
  - “No resources assigned yet.”
- Mechanic unassigned but bay/mobile assigned:
  - “Mechanic: Unassigned.”
- Bay/mobile missing but mechanic assigned (should not happen; tolerate):
  - Show “Location: Unassigned” and mechanic info.

### Service outage / degraded data
- shopmgmt unreachable:
  - If cached in-memory data exists: keep showing it with warning and allow refresh.
  - Else: show error state + retry.
- SSE fails:
  - Switch to polling; show non-blocking warning.
- People/HR unreachable (only if enhancement call attempted):
  - Show mechanicId fallback; do not block.

## 12. Acceptance Criteria

### Scenario 1: View assignment on appointment detail (assigned bay + mechanic)
**Given** I am authenticated as a Service Advisor authorized to view assignments for Facility A  
**And** an appointment in Facility A exists with `assignmentType=BAY` and `bay.bayNameOrNumber` populated  
**And** the assignment includes a mechanic with either `displayName` or `mechanicId`  
**When** I open the Appointment Detail screen for that appointment  
**Then** I see the assigned bay identifier  
**And** I see the assigned mechanic displayName if provided, otherwise I see “Mechanic ID: <id>”  
**And** I see assignment notes if present  
**And** the assignment section is read-only.

### Scenario 2: Unassigned appointment shows empty state
**Given** I am authenticated and authorized to view assignments  
**And** an appointment exists with `assignmentType=UNASSIGNED`  
**When** I open Appointment Detail  
**Then** I see “No resources assigned yet”  
**And** I do not see bay or mobile unit details  
**And** no edit controls are shown.

### Scenario 3: Near-real-time updates reflect changes while viewing (SSE)
**Given** I am viewing an appointment’s assignment section  
**And** the UI is subscribed to the facility SSE stream  
**And** the backend emits an `AssignmentUpdated` event containing a full `AssignmentView` for the same `appointmentId` with a higher `version`  
**When** the event is received  
**Then** the assignment section updates to show the latest assignment  
**And** I see a visible banner/toast indicating the assignment was updated  
**And** if an event is received with `version` less than or equal to the current version, it is ignored and does not overwrite the UI.

### Scenario 4: SSE failure falls back to polling
**Given** I am viewing an appointment’s assignment section  
**And** the SSE connection fails or is not supported  
**When** the UI detects the failure  
**Then** the UI switches to polling the assignment view every 30 seconds while the screen remains visible  
**And** the UI shows a non-blocking message that live updates are unavailable  
**And** when the assignment changes on the backend, the UI reflects the change within 30 seconds.

### Scenario 5: Permission denied prevents viewing assignments
**Given** I am authenticated but not authorized to view assignments for the appointment’s facility  
**When** I open Appointment Detail  
**Then** the assignment load returns 403 (or 404 if backend masks existence)  
**And** I do not see assignment details  
**And** I see a message indicating I lack permission or the appointment is not accessible.

### Scenario 6: Notes editable only for authorized roles (optional, if enabled)
**Given** I am authenticated as a user with `EDIT_ASSIGNMENT_NOTES`  
**And** the assignment view includes `version=3`  
**When** I enter assignment notes with 500 characters or fewer  
**And** I enter a non-empty notesEditReason (<= 200 chars)  
**And** I save with `expectedVersion=3`  
**Then** the notes are updated and the UI displays the new notes  
**And** if the backend responds with 409 `VERSION_MISMATCH` and `currentVersion=4`, the UI reloads the assignment and informs me it changed while editing  
**And** a user without `EDIT_ASSIGNMENT_NOTES` does not see note edit controls.

## 13. Audit & Observability

### User-visible audit data
- Display `assignedAt` and `lastUpdatedAt` from `AssignmentView` when provided.
- Do not display audit history by default in this story.

### Status history
- Out of scope unless an audit endpoint is already available and wired elsewhere.

### Traceability expectations
- Frontend sends `X-Request-Id` on shopmgmt calls and SSE subscribe request (where applicable) (DECISION-SHOPMGMT-011).
- Frontend must not log:
  - `assignmentNotes`
  - `notesEditReason`
- Frontend may log (non-PII):
  - SSE connect/disconnect events
  - polling fallback activation
  - error codes (without free-text notes)

## 14. Non-Functional UI Requirements

- **Performance**:
  - Assignment section loads asynchronously and must not block the rest of Appointment Detail rendering.
  - SSE updates should apply within 5 seconds of backend emission under normal conditions (DECISION-SHOPMGMT-006).
- **Accessibility**:
  - Update banners/toasts and error messages must be announced via an ARIA live region.
  - All interactive controls (refresh, edit/save/cancel) must be keyboard accessible.
- **Responsiveness**:
  - Must render correctly on tablet POS layouts.
- **i18n/timezone**:
  - Display timestamps using the facility timezone when `facilityTimeZoneId` is available in the appointment context (DECISION-SHOPMGMT-015).
  - If facilityTimeZoneId is not available on the screen, display timestamps using the timestamp’s offset as provided (do not convert to browser timezone without an explicit facility timezone).
- **Security**:
  - No cross-facility caching of assignment data.
  - Handle 403/404 without leaking existence across facilities (DECISION-SHOPMGMT-012).
