## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Apply Payment to Invoice (Single Payment → One or More Invoices)

### Primary Persona
Accounting Clerk (human user) operating within the Accounting domain UI

### Business Value
Ensure cleared payments are applied to invoices accurately and atomically, keeping invoice balances/statuses correct, producing auditable application records, and handling overpayments via explicit customer credit—reducing AR reconciliation errors and audit risk.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Accounting Clerk  
- **I want** to apply an available (cleared) payment to one or more eligible invoices with strong validation, atomic submission, and deterministic outcomes  
- **So that** invoice balances/statuses update correctly, any remainder becomes customer credit per policy, and the action is fully auditable and safe to retry without double-applying.

### In-scope
- A dedicated frontend workflow to:
  - Load an Accounting payment read model by `paymentId` and show apply eligibility (`status`, `unappliedAmount`, `currencyUomId`, `customerId`)
  - Load eligible invoices for the payment’s `customerId` and `currencyUomId`
  - Allocate amounts across one or more invoices (no auto-allocation policy; explicit allocations required)
  - Validate constraints before submit (and surface backend validation per invoice)
  - Submit the application as a single atomic command with an idempotency key (`applicationRequestId`, UUIDv7)
  - Display results from the apply response immediately (created applications, updated balances/statuses, created customer credit if any)
  - Provide navigation to view payment detail and created application records (read-only)

### Out-of-scope
- Payment authorization/capture/clearing lifecycle (owned by Payment domain)
- Creating/editing invoices (Billing/Work Execution domains)
- Reversing/unapplying a payment application (explicitly separate story; no “Reverse” action here)
- GL posting details, chart of accounts, posting rule configuration
- Multi-currency conversions (currency must match; no FX)
- “Apply by policy” / auto-allocation when allocations omitted (not supported)

---

## 3. Actors & Stakeholders
- **Primary user:** Accounting Clerk
- **Secondary stakeholders:** Finance leadership, Auditors/Compliance (read-only)
- **System interactions:** Moqui backend services for Accounting domain (`/accounting/ar/*`, `/accounting/payments/*`), plus invoice read access (via eligible invoice list endpoint)

## 4. Preconditions & Dependencies

### Preconditions
- A payment has been ingested into Accounting as a payment read model and is apply-eligible:
  - `status = AVAILABLE`
  - `unappliedAmount > 0`
- Payment has a known `currencyUomId`.
- User is authenticated.
- User has permission to view payments (`accounting:payment:view`).
- To submit apply: user has `accounting:ar:apply-payment`. (Decision AD-013)

### Dependencies
- Backend endpoints exist and conform to Accounting domain contracts (Decisions AD-010, AD-002, AD-003):
  - `GET  /accounting/ar/payment?paymentId=...`
  - `GET  /accounting/ar/eligibleInvoices?customerId=...&currencyUomId=...`
  - `POST /accounting/ar/apply` with `applicationRequestId` + allocations
- Backend enforces:
  - Atomic application (all-or-nothing)
  - Eligibility constraints (payment status, invoice eligibility, currency match)
  - Idempotency by `applicationRequestId` (UUIDv7)
  - Overpayment remainder becomes `CustomerCredit` and sets `unappliedAmount` to `0` (Decision AD-003)
  - Accounting period enforcement (may reject apply if period closed; Decision AD-012)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Accounting navigation: **Accounting → Receivables → Payments → (select payment) → Apply to Invoices**
- Deep link route supported (UUIDv7 validated client-side):
  - `/accounting/receivables/payment/apply?paymentId=<uuidv7>`

### Screens to create/modify
1. **New Screen:** `apps/accounting/screen/receivables/PaymentApply.xml`
   - Purpose: Apply one payment across one or more invoices
2. **Modify/Ensure Existing (if present):** `apps/accounting/screen/receivables/PaymentDetail.xml`
   - Add action/link “Apply to Invoices” (visible only when payment is apply-eligible and user has submit permission; otherwise view-only link may still open apply screen but submit disabled)

### Navigation context
- Breadcrumb: Accounting / Receivables / Payments / Apply
- Back navigation:
  - If entered from Payment Detail: back returns to that payment detail
  - If entered via deep link: back returns to Payments list

### User workflows (happy + alternate paths)

#### Happy path: apply payment across invoices
1. User opens Apply screen with `paymentId`.
2. UI loads payment via `GET /accounting/ar/payment`.
3. If payment has `customerId`, UI loads eligible invoices via `GET /accounting/ar/eligibleInvoices`.
4. User selects one or more invoices and enters `amountToApply` per invoice.
5. UI validates amounts and enables Submit.
6. On Submit, UI generates `applicationRequestId` (UUIDv7) and calls `POST /accounting/ar/apply`.
7. UI displays results from response:
   - Created `PaymentApplication` records
   - Updated payment `unappliedAmount` and status (backend-authoritative)
   - Updated invoice balances/statuses (backend-authoritative)
   - If remainder exists: created `CustomerCredit` shown and payment `unappliedAmount` shown as `0` (Decision AD-003)

#### Alternate path: apply full remaining amount to a single invoice
- Provide a convenience action per invoice row: “Apply remaining to this invoice”
  - Sets `amountToApply = min(payment.unappliedAmount - appliedTotalExcludingThisRow, invoice.balanceDue)`
  - Does not submit; user still must click Submit.

#### View-only path (no submit permission)
- User without `accounting:ar:apply-payment` can open the screen:
  - Payment and eligible invoices load
  - Allocation inputs are disabled (or enabled but Submit disabled; prefer disabled to reduce confusion)
  - UI shows “You do not have permission to apply payments.”

#### Missing customer on payment (ops triage dependency)
- If payment `customerId` is null:
  - UI cannot load eligible invoices; show “Customer not assigned to this payment.”
  - Provide navigation link to Payment Detail where customer assignment may exist (separate workflow; not implemented here).

## 6. Functional Behavior

### Triggers
- Screen load with `paymentId`
- User actions: select invoice(s), enter allocation amounts, submit application, reload after conflict

### UI actions
- **On init**
  - Validate `paymentId` is UUIDv7; if invalid, show inline error and do not call backend.
  - Call `GET /accounting/ar/payment?paymentId=...`
- **After payment load**
  - If `customerId` and `currencyUomId` present: call `GET /accounting/ar/eligibleInvoices?customerId=...&currencyUomId=...`
  - If missing `customerId`: show blocking message (no invoice list)
- **Allocation editing**
  - Maintain client-side allocation model keyed by `invoiceId`
  - Compute `appliedTotal` and `remainingAfterApply` for display only
- **Submit**
  - Only enabled when user has `accounting:ar:apply-payment` and validations pass
  - Generate `applicationRequestId` UUIDv7 once per submit attempt and persist it in screen state until success/failure is resolved
  - Call `POST /accounting/ar/apply`
  - Disable Submit while request in flight; prevent double-submit
- **Post-success**
  - Display response summary and per-invoice results
  - Provide links:
    - Payment Detail (same `paymentId`)
    - Each affected Invoice (if invoice detail route exists; otherwise show invoiceId copy)
    - Customer Credit detail (if credit created and route exists; otherwise show creditId copy)
- **Post-error**
  - Map errors to:
    - Banner (general)
    - Field errors (allocation inputs)
    - Row errors (invoice-specific) when backend returns per-invoice details

### State changes (frontend view state)
- `screenState`: `LOADING_PAYMENT` → `LOADING_INVOICES` → `READY` → `SUBMITTING` → `SUCCESS` | `ERROR`
- On `409 CONFLICT`: transition to `ERROR` with “Reload required” action; on reload, clear allocations and re-fetch payment + invoices.

### Service interactions (authoritative)
- View:
  - `GET /accounting/ar/payment?paymentId=...`
  - `GET /accounting/ar/eligibleInvoices?customerId=...&currencyUomId=...`
- Command:
  - `POST /accounting/ar/apply` (atomic + idempotent; Decision AD-010)

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side, before submit)
Applies to allocations array `[{invoiceId, amountToApply}]`:

- At least one allocation row is required.
- For each allocation:
  - `invoiceId` required and must be UUIDv7
  - `amountToApply` required
  - `amountToApply > 0`
  - `amountToApply` must be a decimal with currency scale (no floating point; UI uses decimal input)
  - `amountToApply <= invoice.balanceDue` (based on loaded eligible invoice list)
- Across all allocations:
  - `sum(amountToApply) <= payment.unappliedAmount` (based on loaded payment)
- Eligibility constraints (UI gating; backend authoritative):
  - Payment must be `status = AVAILABLE` and `unappliedAmount > 0` (Decision AD-002)
  - Currency must match; UI ensures invoices are loaded by `currencyUomId` and blocks submit if payment currency missing
  - Invoices must be eligible; UI relies on eligible invoice list endpoint and does not attempt to infer additional invoice status enums (Decision AD-002)

### Enable/disable rules
- Submit button is visible only when user has `accounting:ar:apply-payment`; otherwise hidden.
- Allocation inputs are enabled only when:
  - user has `accounting:ar:apply-payment`
  - payment is apply-eligible (`AVAILABLE` and `unappliedAmount > 0`)
  - eligible invoices are loaded
- Submit disabled when:
  - any client-side validation fails
  - request in flight
  - eligible invoices list is empty

### Visibility rules
- Overpayment messaging (Decision AD-003):
  - If `payment.unappliedAmount - sum(amountToApply) > 0`, show: “Any remaining amount will be converted to Customer Credit on submit.”
  - After success, if credit created, show credit reference and amount; show payment `unappliedAmount = 0` as returned.

### Error messaging expectations (backend-authoritative codes)
- UI must display backend `errorCode` and safe `message` in a banner.
- For validation errors with `details`:
  - If `details` contains keys matching `invoiceId` values, show row-level error on that invoice row.
  - If `details` contains field keys (e.g., `applicationRequestId`, `allocations`), show inline field errors.
- Do not invent new meanings for enums/statuses; display as returned with minimal mapping.

## 8. Data Requirements

### Entities involved (frontend-facing)
- `ReceivablePayment` (Accounting read model; apply eligibility and balances)
- `Invoice` (read-only list of eligible invoices for allocation)
- `PaymentApplication` (created records returned by apply)
- `CustomerCredit` (created when overpayment remainder exists; Decision AD-003)

### Fields (minimum required by UI)

#### Payment (from `GET /accounting/ar/payment`)
- `paymentId` (UUIDv7; required)
- `status` (string enum; required; must support `AVAILABLE`)
- `customerId` (UUIDv7; nullable; required for invoice lookup)
- `currencyUomId` (string; required)
- `totalAmount` (decimal; required)
- `unappliedAmount` (decimal; required)
- Optional display:
  - `paymentRef` (string; optional)
  - `receivedAt` / `clearedAt` (datetime; optional; backend-provided)

#### Eligible Invoice row (from `GET /accounting/ar/eligibleInvoices`)
- `invoiceId` (UUIDv7; required)
- `invoiceNumber` (string; optional; display if provided)
- `balanceDue` (decimal; required)
- Optional display:
  - `invoiceDate` (date/datetime; optional)
  - `dueDate` (date; optional)
  - `status` (string; optional; display only; do not hardcode logic beyond eligibility list)

#### Allocation input (client-side)
- `invoiceId` (UUIDv7; required)
- `amountToApply` (decimal; required)

#### Apply response (from `POST /accounting/ar/apply`)
- `applicationRequestId` (UUIDv7; echoed; required)
- `payment` (updated payment summary; required):
  - `paymentId`, `status`, `unappliedAmount`, `currencyUomId`
- `applications[]` (required):
  - `paymentApplicationId` (UUIDv7; required)
  - `paymentId` (UUIDv7; required)
  - `invoiceId` (UUIDv7; required)
  - `appliedAmount` (decimal; required)
  - `applicationTimestamp` (datetime; required)
- `invoices[]` (updated invoice summaries; required for immediate UI display):
  - `invoiceId` (UUIDv7)
  - `balanceDue` (decimal)
  - `status` (string; backend-authoritative)
- `customerCredit` (optional; present when created):
  - `creditId` (UUIDv7; required)
  - `amount` (decimal; required)
  - `currencyUomId` (string; required)

### Read-only vs editable
- Payment fields: read-only
- Invoice fields: read-only
- Allocation `amountToApply`: editable only for selected invoice rows and only when user has submit permission and payment is eligible

### Derived/calculated fields (frontend-only; informational)
- `appliedTotal = sum(amountToApply)`
- `remainingAfterApply = payment.unappliedAmount - appliedTotal`
- These are display-only; backend remains authoritative.

## 9. Service Contracts (Frontend Perspective)

> UI must use the canonical Accounting endpoint families and must not invent schemas. (Decisions AD-010, AD-002, AD-003)

### Load/view calls

1) **Load payment for AR apply**
- **Request:** `GET /accounting/ar/payment?paymentId=<uuidv7>`
- **Response (min):** Payment fields listed in Data Requirements
- **Auth:** requires `accounting:payment:view`
- **Errors:**
  - `400` invalid UUID → show “Invalid payment ID.”
  - `403` → show access denied (do not reveal existence)
  - `404` → show “Payment not found.”
  - `5xx/timeout` → show retry action; preserve `paymentId`

2) **Load eligible invoices**
- **Request:** `GET /accounting/ar/eligibleInvoices?customerId=<uuidv7>&currencyUomId=<string>`
- **Response:** list of eligible invoices (only those eligible; UI does not filter eligibility client-side)
- **Auth:** requires invoice view permission(s) as enforced by backend; UI assumes at least `accounting:payment:view` is sufficient to render list if backend returns it
- **Errors:**
  - `400` invalid UUID → inline error
  - `403` → access denied
  - `5xx/timeout` → retry action; preserve filters

### Submit/transition calls

3) **Apply payment (atomic, idempotent)**
- **Request:** `POST /accounting/ar/apply`
- **Body:**
  - `applicationRequestId` (UUIDv7; required; generated client-side; Decision AD-010)
  - `paymentId` (UUIDv7; required)
  - `allocations` (array; required; at least 1):
    - `{ "invoiceId": "<uuidv7>", "amountToApply": "<decimal>" }`
- **Response (success):** apply response fields listed in Data Requirements
- **Auth:** requires `accounting:ar:apply-payment`
- **Errors:**
  - `400/422` validation → show banner + inline/row errors using `{errorCode, message, details}`
  - `409` conflict (stale balances / state changed) → show “Reload required” and provide reload action; clear allocations after reload
  - `403` → access denied
  - `5xx/timeout` → show retry option; on retry, reuse the same `applicationRequestId` for that attempt if the user clicks “Retry same request”

### Error handling expectations
- Canonical error shape (Decision AD-013):
  - `{ errorCode, message, details? }`
- Mapping rules:
  - `details` keys matching invoiceId → row-level error
  - `details` keys matching field names → inline field error
- Do not log raw response bodies that may contain sensitive data; log only identifiers and errorCode.

## 10. State Model & Transitions

### Allowed states (backend-authoritative; UI uses for gating)
- Payment apply eligibility:
  - `AVAILABLE` is required to apply
  - Other statuses may exist; UI treats any non-`AVAILABLE` as not apply-eligible
- Invoices:
  - UI does not hardcode invoice status enums for eligibility; it relies on eligible invoice list endpoint (Decision AD-002)

### Role-based transitions
- With `accounting:ar:apply-payment`:
  - Can submit apply command
- Without `accounting:ar:apply-payment`:
  - View-only; cannot submit or edit allocations

### UI behavior per state
- Payment `status != AVAILABLE` or `unappliedAmount <= 0`:
  - Show payment summary and a message “Payment is not available to apply.”
  - Hide/disable allocation inputs and submit
- Payment `customerId` is null:
  - Show message “Customer not assigned; cannot load eligible invoices.”
  - No allocations allowed
- After successful apply:
  - Show immutable result summary (applications created, updated balances, credit created if any)

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Amount exceeds invoice `balanceDue`:
  - Inline error on that row; submit disabled
- Applied total exceeds payment `unappliedAmount`:
  - Banner error; submit disabled
- No allocations:
  - Submit disabled; show helper text “Select at least one invoice and enter an amount.”

### Backend validation failures
- Invoice becomes ineligible between load and submit:
  - Backend returns validation error; UI shows row error and offers “Reload invoices”
- Currency mismatch (should be prevented by eligible list, but still possible):
  - Show backend error; offer reload

### Concurrency conflicts
- `409 CONFLICT` on apply:
  - Show “Data changed since you started. Reload required.”
  - “Reload” re-fetches payment + eligible invoices and clears allocations

### Unauthorized access
- `403` on load:
  - Show access denied without revealing whether payment exists
- `403` on submit:
  - Show access denied; keep allocations in UI but disable submit

### Empty states
- Eligible invoices list empty:
  - Show “No eligible invoices found for this customer and currency.”
  - Submit disabled
  - Provide navigation link back to Payments list and/or Payment Detail

## 12. Acceptance Criteria

### Scenario 1: Load apply screen with available payment and eligible invoices
**Given** I am authenticated and have `accounting:payment:view`  
**When** I open `/accounting/receivables/payment/apply?paymentId=<uuidv7>` for a payment with `status=AVAILABLE` and `unappliedAmount>0` and a non-null `customerId`  
**Then** the UI loads payment via `GET /accounting/ar/payment` and displays `unappliedAmount` and `currencyUomId`  
**And** the UI loads eligible invoices via `GET /accounting/ar/eligibleInvoices` for that `customerId` and `currencyUomId`  
**And** the invoice list contains only invoices with `balanceDue>0` as returned by the backend.

### Scenario 2: View-only user cannot apply
**Given** I am authenticated and have `accounting:payment:view` but do not have `accounting:ar:apply-payment`  
**When** I open the apply screen for an available payment  
**Then** I can view payment and eligible invoices  
**And** allocation inputs and Submit are disabled or hidden  
**And** the UI indicates I lack permission to apply payments.

### Scenario 3: Apply full payment to one invoice successfully (idempotent submit)
**Given** I have `accounting:ar:apply-payment`  
**And** the payment has `unappliedAmount = 100.00`  
**And** an eligible invoice has `balanceDue = 100.00`  
**When** I allocate `amountToApply = 100.00` to that invoice and click Submit  
**Then** the UI sends `POST /accounting/ar/apply` with a generated UUIDv7 `applicationRequestId` and the allocation  
**And** on success the UI displays created `PaymentApplication` record(s) and updated invoice/payment summaries from the response  
**And** the payment `unappliedAmount` is `0.00` in the displayed updated payment summary.

### Scenario 4: Apply payment across multiple invoices atomically
**Given** I have `accounting:ar:apply-payment`  
**And** the payment has `unappliedAmount = 120.00`  
**And** two eligible invoices have `balanceDue = 70.00` and `80.00`  
**When** I allocate `70.00` to the first invoice and `50.00` to the second and submit  
**Then** the UI shows success with two `PaymentApplication` records  
**And** the UI shows updated invoice balances/statuses for both invoices from the response  
**And** the payment `unappliedAmount` is `0.00` in the response.

### Scenario 5: Overpayment creates customer credit and unapplied becomes zero
**Given** I have `accounting:ar:apply-payment`  
**And** the payment has `unappliedAmount = 200.00`  
**And** an eligible invoice has `balanceDue = 150.00`  
**When** I allocate `150.00` and submit  
**Then** the UI shows success  
**And** the response includes `customerCredit` with `amount = 50.00` and matching `currencyUomId`  
**And** the displayed updated payment summary shows `unappliedAmount = 0.00`.

### Scenario 6: Client-side validation prevents submitting invalid totals
**Given** I am editing allocations  
**When** the sum of `amountToApply` exceeds the payment’s `unappliedAmount`  
**Then** Submit is disabled  
**And** the UI displays a banner error indicating the applied total exceeds the remaining unapplied amount.

### Scenario 7: Backend returns per-invoice validation error and UI highlights row
**Given** I have selected multiple invoices  
**When** I submit and the backend returns `{ errorCode, message, details }` with a key matching an `invoiceId` in my allocations  
**Then** the UI displays the banner error  
**And** the invoice row matching that `invoiceId` shows the row-level error message  
**And** the UI does not display a success confirmation.

### Scenario 8: Concurrency conflict requires reload
**Given** I have prepared allocations based on loaded balances  
**When** I submit and the backend responds with HTTP `409`  
**Then** the UI shows “Reload required”  
**And** when I click Reload, the UI re-fetches payment and eligible invoices and clears allocations.

### Scenario 9: Invalid UUID blocks backend calls
**Given** I open the apply screen with `paymentId=not-a-uuid`  
**When** the screen initializes  
**Then** the UI shows an inline validation error for `paymentId`  
**And** the UI does not call `GET /accounting/ar/payment`.
