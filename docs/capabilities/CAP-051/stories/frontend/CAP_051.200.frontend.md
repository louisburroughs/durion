## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] GL: Post Journal Entry with Period Controls and Atomicity

### Primary Persona
GL Accountant / Controller (back-office user responsible for posting journal entries)

### Business Value
Enable controlled, auditable posting of journal entries to the ledger with strict accounting period enforcement and atomic commit semantics, preventing financial corruption and ensuring traceability from source events to posted entries.

---

## 2. Story Intent

### As a / I want / So that
- **As a** GL Accountant / Controller  
- **I want** to review a draft journal entry and post it to the ledger only when the accounting period is eligible  
- **So that** ledger balances and trial balance aggregates remain consistent, and the originating source event is linked to a permanent journal entry posting reference.

### In-scope
- A Moqui screen flow to **view a Journal Entry** and **initiate posting**
- UI display of **period eligibility** for the JE posting date (Open/Closed) as returned by backend
- Posting action that calls a backend “post” service and handles:
  - atomic success
  - period-closed rejection (**Decision AD-012**)
  - validation failures (unbalanced, invalid account, etc.)
  - concurrency conflicts
- Display of post results: posted timestamp/status, JE reference, and source event linkage (read-only)

### Out-of-scope
- Creating/editing journal entries and journal entry lines
- Defining accounting periods, opening/closing periods
- Defining GL accounts, posting rule sets, or mappings
- Any GL account balance drilldown UI (only confirm that posting updates are reflected via returned status/data)
- Implementing backend atomicity/period logic (frontend consumes it)
- Any “override closed period” workflow (explicitly disallowed by policy; see Business Rules)

---

## 3. Actors & Stakeholders
- **GL Accountant / Controller (primary user):** initiates posting, needs clear blocking reasons and audit evidence.
- **Auditor (secondary stakeholder):** expects immutable traceability and viewable status history.
- **Upstream Source System / Module (stakeholder):** needs a durable posting reference for reconciliation (journalEntryId primary reference).
- **System Admin (stakeholder):** expects permission enforcement and safe error messaging.

---

## 4. Preconditions & Dependencies

### Preconditions
- A `JournalEntry` exists in a **postable pre-post state** (backend authoritative; UI must not invent additional states).
- User is authenticated in the frontend.

### Dependencies (must exist or be stubbed)
- Backend endpoints/services to:
  - Load a journal entry by ID (including lines, totals, postingDate, status)
  - Provide accounting period eligibility for the JE posting date (either embedded in JE response or via a period-status endpoint)
  - Post a journal entry (atomic operation; blocked in closed periods) (**Decision AD-012**)
- Authorization contract defining what permission is required to post (see Open Questions; cannot be inferred from Accounting domain guide which does not define a GL posting permission token)

## 6. Functional Behavior

### Triggers
- Screen load with `journalEntryId`
- User clicks **Post Journal Entry**
- User confirms posting in dialog

### UI actions
- **On load:**
  - Call JE detail service with `journalEntryId`
  - Render header/lines/totals/status
  - Render period status/eligibility if returned; otherwise show “Period status will be validated on post”
- **Post button enabled only when all are true:**
  - User has permission to post (see Open Questions; UI must gate by explicit permission token or backend-provided capability flag)
  - JE is not already Posted (backend status)
  - Backend indicates posting is allowed (preferred: `canPost=true` or equivalent); if not available, UI uses minimal gating (not Posted) and relies on backend for final validation
  - If period status is available and indicates Closed, Post is disabled and a reason is shown (**Decision AD-012**)
- **On Post confirm:**
  - Call post service with `journalEntryId`
  - Include optimistic locking token if provided by JE load (e.g., `lastUpdatedStamp` or `version`) to support 409 conflict behavior

### State changes (frontend-visible)
- JE status transitions to Posted on success
- UI becomes read-only for posting action (post button hidden/disabled)
- If backend returns posting references (e.g., ledgerTransactionId), display them; `journalEntryId` remains the canonical reference (**Decision AD-011**)
- If backend returns source linkage (e.g., eventId/sourceDocId), display as read-only reference; UI does not mutate source event state

### Service interactions (Moqui)
- Use Moqui screen actions (`service-call`) to:
  - load JE data
  - post JE
- Use transitions for:
  - refresh after post (re-load detail)
  - error routing (remain on same screen with messages)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UI must treat backend as authoritative for:
  - balanced check
  - period eligibility and enforcement (**Decision AD-012**)
  - account validity/locked status
  - atomic posting eligibility
- UI must not implement any “redirect to next open period” or “override closed period” behavior. Closed period blocks posting. (**Decision AD-012**)

### Enable/disable rules
- Disable Post action when JE status indicates already posted.
- Disable Post action when backend indicates period is Closed (if period status is available).
- Disable Post action while a post request is in flight (prevent double-submit).
- If backend returns a `canPost`/`postEligibility` flag and reason codes, UI must use them to enable/disable and display reasons (backend-owned enums; do not invent).

### Visibility rules
- If JE status is Posted:
  - Show posted timestamp (if returned)
  - Show posting user (if returned)
  - Show immutable banner: “Posted entries cannot be modified; corrections require a reversing entry.” (informational only; reversal is out of scope)

### Error messaging expectations
- Backend error codes should be surfaced with user-friendly messages, while retaining a technical code for support (e.g., “Posting blocked: accounting period is closed (errorCode=PERIOD_CLOSED)”).
- Do not display raw stack traces or sensitive payloads.

**Decision rationale used in this story**
- **AD-012 Accounting Period Enforcement:** “All postings and applications are blocked in closed periods.” Therefore the UI must block and must not offer redirect/override flows.
- **AD-011 Posting Reference Canonical Identifier:** Journal entry is the canonical posting reference; ledger IDs are secondary display-only.

## 9. Service Contracts (Frontend Perspective)

> The accounting domain guide provides canonical endpoint families for exports/payments/refunds/ingestion/apply-payment, but does not define GL journal entry posting endpoints. Therefore, JE posting endpoints must be confirmed with backend/Moqui services. This story defines required shapes and error handling; exact paths remain an Open Question.

### Load/view calls
1. **Get Journal Entry Detail**
   - Input: `journalEntryId` (UUIDv7)
   - Output:
     - JE header + lines
     - optional `periodStatus` for `postingDate` (preferred)
     - optional `canPost` boolean and `postBlockReasons[]` (preferred)
   - Errors:
     - 404 → show “Journal Entry not found”
     - 401/403 → show access denied without revealing existence details beyond generic messaging

2. **Get Accounting Period Status** (only if not embedded in JE detail)
   - Input: `postingDate` (date) and any required scoping identifiers (e.g., organization/business unit) if backend requires
   - Output: period status (Open/Closed) and optional period id/date range
   - Errors:
     - If unavailable, show warning “Period status unavailable; posting will be validated on submit.”

### Submit/transition calls
3. **Post Journal Entry (atomic)**
   - Input:
     - `journalEntryId` (UUIDv7)
     - optional optimistic lock token: `lastUpdatedStamp`/`version` (recommended)
   - Output on success:
     - updated JE status = Posted
     - `postedAt`, `postedByUserId` (if provided)
     - posting references (journalEntryId; optional ledgerTransactionId) (**Decision AD-011**)
     - optional source linkage echo (read-only)
   - Error handling expectations:
     - 400/422 validation errors:
       - unbalanced
       - invalid/disabled account
       - missing lines
     - 409 conflict:
       - already posted
       - version mismatch / stale data
     - 403 forbidden:
       - missing post permission
     - Closed period rejection:
       - errorCode indicates period closed; UI must show blocking message (**Decision AD-012**)
     - 5xx/timeout:
       - show generic failure; allow retry; do not assume partial posting (atomicity expectation)

### Error schema expectations
Use canonical error shape when provided:
```json
{ "errorCode": "PERIOD_CLOSED", "message": "Accounting period is closed", "details": { } }
```
- UI must display `message` and include `errorCode` in a “Technical details” expandable section.

## 10. State Model & Transitions

> Exact statuses are backend-defined; UI must be tolerant to backend-provided values and rely on explicit eligibility flags when available.

### Allowed states (minimum)
- Pre-post (e.g., Draft/Ready/Approved) — backend-defined
- Posted — terminal/immutable for this story

### Role-based transitions
- User with posting permission can transition:
  - pre-post → Posted (only if period is open and validations pass) (**Decision AD-012**)
- Users without permission:
  - cannot invoke post; UI hides/disables action and backend enforces with 403

### UI behavior per state
- **Pre-post:** show Post action (if permitted) and show period status if available.
- **Posted:** hide/disable Post; show posted metadata; show immutable info banner.

## 11. Alternate / Error Flows

### Validation failures
- Backend returns validation errors:
  - UI displays error summary
  - Keeps user on detail screen
  - Post remains available only if user can correct upstream (note: no edits in this story); provide “Refresh” action

### Closed period
- Backend rejects with period-closed error:
  - UI shows blocking banner: “Posting blocked: accounting period is closed.”
  - Post button remains disabled if period status is known Closed
  - No override/redirect options are shown (**Decision AD-012**)

### Concurrency conflicts
- If backend returns 409:
  - UI shows “This journal entry changed since you opened it.”
  - Provide action: Refresh (re-load JE detail)
  - After refresh, reflect new status and disable posting if posted

### Unauthorized access
- If load fails with 403:
  - show access denied state, no JE data rendered

### Empty states
- JE has zero lines:
  - show “No lines available”
  - Post disabled
  - If user attempts post (e.g., via direct call), show backend validation error safely

## 12. Acceptance Criteria

### Scenario 1: Successful posting to an open period
**Given** I have permission to post journal entries  
**And** a journal entry exists in a pre-post status with debits equal credits  
**And** the journal entry posting date is within an Open accounting period  
**When** I open the Journal Entry detail screen  
**And** I click “Post Journal Entry” and confirm  
**Then** the system posts the journal entry successfully  
**And** the UI refreshes to show status “Posted” with posted timestamp/user (if provided)  
**And** the UI disables further posting actions for that entry  
**And** the UI displays the journal entry as the canonical posting reference and displays any secondary ledger reference if provided.

### Scenario 2: Attempted posting to a closed period is blocked (no override)
**Given** I have permission to post journal entries  
**And** a balanced journal entry exists in a pre-post status  
**And** the posting date is within a Closed accounting period  
**When** I attempt to post the journal entry  
**Then** the UI shows a blocking error indicating the period is closed (including backend `errorCode`)  
**And** the journal entry remains in the pre-post status in the UI after refresh  
**And** the UI does not offer redirect or override options.

### Scenario 3: Attempted posting of an unbalanced entry is rejected
**Given** I have permission to post journal entries  
**And** a journal entry exists where total debits do not equal total credits  
**When** I attempt to post the journal entry  
**Then** the UI shows a validation error including backend `errorCode`  
**And** the journal entry status does not change to Posted.

### Scenario 4: Backend transaction failure results in no partial posting (atomicity)
**Given** I have permission to post journal entries  
**And** a balanced journal entry exists in an Open period  
**When** I attempt to post the journal entry  
**And** the backend responds with an internal error or timeout  
**Then** the UI shows a non-success error message and does not show Posted status  
**And** when I refresh the journal entry detail, it is still not Posted.

### Scenario 5: Concurrency conflict (already posted)
**Given** I have permission to post journal entries  
**And** I am viewing a pre-post journal entry  
**And** the journal entry is posted by another user/session  
**When** I attempt to post it  
**Then** the UI shows a conflict message and prompts me to refresh  
**And** after refresh, the UI shows status Posted and disables posting.

### Scenario 6: Unauthorized user cannot post
**Given** I do not have permission to post journal entries  
**When** I open the journal entry detail screen  
**Then** the Post action is not available (hidden or disabled)  
**And** if I attempt to invoke posting via direct action, the UI shows an access denied error.
