## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting Policy: Configure Accrual vs Cash Basis per Business Unit (AR scope)

### Primary Persona
Finance Manager / Accountant (with accounting admin privileges)

### Business Value
Enable correct GL posting behavior and reporting consistency by configuring and auditing whether a business unit operates on accrual or cash basis for AR/revenue-cycle postings.

---

## 2. Story Intent

### As a / I want / So that
**As a** Finance Manager / Accountant,  
**I want** to view and change the accounting basis (Accrual or Cash) for a business unit with an effective fiscal-period boundary,  
**so that** journal entry posting behavior is consistent, permission-controlled, and auditable.

### In-scope
- A Moqui UI to:
  - View current accounting basis for a business unit
  - View basis history (effective-dated)
  - Propose a new basis change with an effective-from date/time aligned to fiscal period start
  - Save the change (server-side validated)
- Permission-gated access and UI affordances (read vs edit)
- User-visible audit/trace fields for changes (who/when/old/new/effectiveFrom)

### Out-of-scope
- Defining debit/credit mappings, GL accounts, posting rule configuration UI
- Journal entry creation/posting UI
- AP behavior
- Retroactive re-posting and “catch-up conversion” workflows
- Any changes to Billing/Payment domain behavior; this story is Accounting policy UI only

---

## 3. Actors & Stakeholders
- **Finance Manager / Accountant (interactive user):** configures basis and reviews history
- **Auditor (interactive user):** reviews basis change history/audit records (read-only)
- **Accounting Service (system):** validates and persists basis policy and audit trail
- **Downstream posting/reporting (system):** consumes the configured basis for posting/reporting behavior; not configured here

---

## 4. Preconditions & Dependencies
- Business units exist and are selectable in the UI.
- Backend provides Accounting-owned services/endpoints to:
  - Read current basis for a business unit
  - Read basis policy history (effective-dated)
  - Create a new basis policy change with validation:
    - allowed values: `ACCRUAL` or `CASH`
    - effective date must align to fiscal period start boundary (backend authoritative)
    - permission-controlled

**Dependency note (resolved):** The frontend must not implement fiscal boundary logic beyond basic required-field validation; it relies on backend validation errors for boundary enforcement (Accounting period enforcement is backend-owned; see AD-012).

## 9. Service Contracts (Frontend Perspective)

> This story introduces new Accounting policy endpoints; backend contract must be implemented to match these shapes. UI must not invent additional fields beyond what backend returns.

### Load/view calls
1. **GET `/accounting/policy/basis/detail?businessUnitId=...`**
   - **Inputs (query):**
     - `businessUnitId` (required)
   - **Outputs (JSON):**
     - `businessUnitId`
     - `current`: `{ basis, effectiveFrom? }`
     - `history`: `[{ policyId, basis, effectiveFrom, createdAt, createdByUserId }]`
     - Optional: `serverTime` (timestamp) for consistent “now” comparisons
   - **Errors:**
     - `401` unauthenticated
     - `403` forbidden (do not leak existence)
     - `404` not found (safe message)
     - `5xx` server error

### Create/update calls
2. **POST `/accounting/policy/basis/change`**
   - **Inputs (JSON body):**
     - `businessUnitId` (required)
     - `basis` (required; `ACCRUAL|CASH`)
     - `effectiveFrom` (required; timestamp)
     - `changeRequestId` (optional; UUIDv7) — if backend supports idempotency/audit correlation for this command
     - `justification` (optional; string)
   - **Outputs (JSON):**
     - `policyId`
     - `current`: `{ basis, effectiveFrom }` (as-of now, after change if effective)
     - `history` (optional; may return updated list) OR `changedRecord` (recommended)
   - **Errors (canonical shape):**
     - `400/422` validation errors:
       ```json
       { "errorCode": "ACCOUNTING_VALIDATION_FAILED", "message": "Validation failed", "details": { "effectiveFrom": "NOT_PERIOD_START" } }
       ```
     - `403` forbidden
     - `409` conflict (overlapping effective-dated record / concurrent update)
     - `423` locked period (or `409` with `errorCode` indicating period lock) (AD-012)
     - `5xx` server error

### Submit/transition calls
- None beyond the change command.

### Error handling expectations
- Map `details` keys to fields when keys match:
  - `basis`, `effectiveFrom`
- For `409`:
  - show conflict banner and reload detail endpoint
- For locked period error (`ACCOUNTING_PERIOD_CLOSED` or similar):
  - show blocking message: “Accounting period is closed; basis change cannot take effect on the selected date.”

## 11. Alternate / Error Flows

### Validation failures
- Missing required fields → block submit client-side.
- Backend rejects:
  - invalid `basis` → inline error on basis
  - invalid `effectiveFrom` boundary → inline error on effectiveFrom
  - invalid timestamp format → inline error on effectiveFrom

### Concurrency conflicts
- On `409`:
  - show banner: “Accounting basis policy changed since you loaded this page. Reloading…”
  - reload detail endpoint
  - keep dialog open but require user to re-confirm and re-submit (do not auto-resubmit)

### Unauthorized access
- On load `403`:
  - show access denied page/section without indicating whether BU exists.
- On change `403`:
  - show “You do not have permission to change accounting basis.”
  - close dialog and refresh permissions/state (or keep open but disable submit; implementation choice must be consistent across app)

### Empty states
- No history:
  - show “No basis history available for this business unit.”
- No business units available:
  - show “No business units available.” with guidance to contact admin.

## 12. Acceptance Criteria

### Scenario 1: View current basis and history
**Given** I am an authenticated user with permission to view accounting basis policy  
**And** I am on the Accounting Basis screen with a selected business unit  
**When** the screen loads  
**Then** I see the current accounting basis for the business unit  
**And** I see a list of effective-dated basis policy history entries or an empty-state message if none exist.

### Scenario 2: Authorized user changes basis with valid effective date
**Given** I have permission to change accounting basis policy  
**And** a business unit currently has basis `ACCRUAL`  
**When** I submit a change to basis `CASH` with an effectiveFrom that the backend accepts as a fiscal period start  
**Then** the system saves the new basis policy record  
**And** the UI shows a success confirmation including the new basis and effectiveFrom  
**And** the UI refreshes and shows the new record in history  
**And** the new record displays audit fields (createdAt/createdBy) if provided by backend.

### Scenario 3: Unauthorized user cannot change basis
**Given** I do not have permission to change accounting basis policy  
**When** I view the Accounting Basis screen  
**Then** I do not see an enabled “Change Basis” action  
**And** if I attempt to submit a change, the backend returns 403 and the UI displays an authorization error without leaking record existence.

### Scenario 4: Effective date not aligned to fiscal period boundary is rejected
**Given** I have permission to change accounting basis policy  
**When** I submit a basis change with an effectiveFrom that is not at a fiscal period start boundary  
**Then** the backend rejects the request with a validation error containing `errorCode` and `details.effectiveFrom`  
**And** the UI displays an inline error on the effectiveFrom field  
**And** after refresh, the current basis and history remain unchanged.

### Scenario 5: Conflict due to concurrent change
**Given** I have permission to change accounting basis policy  
**And** another admin changes the basis policy for the same business unit while my dialog is open  
**When** I submit my change  
**Then** the backend returns a 409 conflict  
**And** the UI informs me of the conflict  
**And** the UI reloads current basis and history  
**And** my change is not applied unless I re-submit after reviewing the updated state.

### Scenario 6: Closed/locked period prevents change
**Given** I have permission to change accounting basis policy  
**When** I submit a basis change with an effectiveFrom that falls in a closed accounting period  
**Then** the backend rejects the request with an error code indicating the period is closed  
**And** the UI shows a blocking error message  
**And** no change is reflected in current basis or history after refresh.
