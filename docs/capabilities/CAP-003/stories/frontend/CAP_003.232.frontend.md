## Issue Body

## 1. Story Header

**Title:** [FRONTEND] Approval: Reflect Approval Invalidation After Estimate Financial Revision (Work Order → Pending Re-Approval)

**Primary Persona:** Service Advisor (primary). Secondary: Technician (read-only awareness).

**Business Value:** Prevents scope/price drift by ensuring any financially-relevant estimate revision forces re-approval before execution/promotion, with a clear audit trail visible in the POS UI.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** the POS UI to clearly indicate when a previously customer-approved work order has been invalidated due to an estimate financial revision and is now awaiting re-approval  
- **So that** I can re-seek customer approval and the system prevents continuing under an outdated approval.

### In Scope
- Frontend screens/components to:
  - Display Work Order approval-related status including **Pending Re-Approval** (as a backend-provided status signal).
  - Display the reason/context for invalidation (old vs new totals, estimate version change, timestamp, and event/audit linkage if provided).
  - Block/disable UI actions that require a currently valid approval when status is Pending Re-Approval.
  - Provide navigation to re-approval capture flow (existing estimate approval flow) when re-approval is required.
  - Show audit/transition history entries related to the invalidation.

### Out of Scope
- Implementing backend event publishing/subscription or backend state machine logic.
- Defining pricing rounding rules or recalculation logic.
- Creating a new approval capture method UX (signature/email/etc.) beyond linking to existing flows.
- Introducing new workflow states beyond those already defined by backend/workexec.

---

## 3. Actors & Stakeholders
- **Service Advisor:** needs to see invalidation and re-approve.
- **Technician:** must see that approval is no longer valid (informational); execution restrictions are enforced by backend, but UI must not present misleading “approved” indicators.
- **System (Workexec backend):** transitions Work Order to a re-approval-required status after an estimate financial revision is processed.
- **Auditor/Manager:** needs traceability via transition history/audit entries.

---

## 4. Preconditions & Dependencies

### Preconditions
- A Work Order exists and references an Estimate (`workOrder.estimateId`).
- The Work Order had previously been customer-approved and then was invalidated by backend due to an estimate financial revision.
- Backend exposes Work Order current status and transition/audit history via API.

### Dependencies (Blocking if absent/unknown)
- Backend must provide a stable, frontend-consumable status signal for “re-approval required”. Prefer a boolean `approvalValid` + `approvalState` or `requiresReapproval` in addition to `statusId` to avoid enum drift (see Decision Rationale below).
- Backend must provide an API to load:
  - Work Order details including current status and estimate reference.
  - Transition/audit entries that include invalidation details (old/new totals in minor units, old/new estimate version, eventId/correlationId, actorId) **or** enough metadata to show “details unavailable” safely.
- Existing frontend routes/screens for:
  - Work Order detail view (`durion-workexec/WorkOrderEdit.xml`).
  - Estimate detail/edit view (`durion-workexec/EstimateEdit.xml`) to initiate re-approval.

**Decision Rationale (resolving prior ambiguity):**
- **Status naming alignment:** Workexec guidance (DECISION-INVENTORY-004) requires status-based gating and recommends exposing derived booleans like `isStarted` to avoid client-side mapping tables. Apply the same pattern here: UI should not hardcode “CustomerApproved” vs “APPROVED” mapping; it should rely on backend-provided explicit approval validity flags when available, and fall back to a dedicated status value if that is what exists today.
- **IDs are opaque:** All identifiers are treated as opaque strings (DECISION-INVENTORY-003); UI must not validate UUID/numeric formats.

## 6. Functional Behavior

### Triggers
- Backend changes Work Order to a “re-approval required” condition after an estimate financial revision is processed.
- Frontend detects this on load and on refresh.

### UI actions
- On Work Order Edit load:
  - Load Work Order details (including `statusId` and/or `requiresReapproval`/`approvalState`).
  - Load transition history (either embedded or via a separate call) to find the latest “re-approval required” transition record.
- If re-approval is required:
  - Show blocking banner/callout: “Customer approval invalidated — re-approval required.”
  - Provide actions:
    - “Open revised estimate” (navigate to `EstimateEdit` with `estimateId`)
- Gate actions:
  - Disable/hide actions that require valid approval (see Business Rules).

### State changes (frontend-local)
- UI reflects backend status; no client-side state machine decisions.
- Local UI state: loading, error, empty history, unauthorized.

### Service interactions
- Read: Work Order by id; transitions/history by workOrderId.
- No mutation calls in scope.

## 7. Business Rules (Translated to UI Behavior)

> UI must not invent policy; it must reflect backend-provided status/flags and enforce only presentation-level gating. Backend remains authoritative.

### Validation / gating (UI-level)
When the Work Order requires re-approval (determined by `requiresReapproval==true` OR `statusId` equals the backend-defined re-approval status):
- UI MUST:
  - Indicate approval is not current (do not show “Approved” badges).
  - Disable/hide any UI actions that would proceed as if approval is valid.
  - If disabled, show an inline reason: “Blocked: customer re-approval required due to estimate revision.”

**Deterministic gating list (frontend responsibilities):**
- Gate any of the following actions **if they exist on `WorkOrderEdit` today**:
  - Start work / transition to in-progress
  - Transition to ready-for-pickup / completed / invoiced
  - Any “promote”/“continue workflow” action that assumes approval validity
- If the screen does not expose these actions, no new actions are added by this story; only the banner + navigation is required.

### Visibility rules
- Invalidation callout is shown when:
  - `requiresReapproval==true`, OR
  - `statusId` equals the re-approval-required status.
- Invalidation details (old/new totals, versions) are shown only when present in transition metadata; otherwise show “Details unavailable”.

### Error messaging expectations
- If history cannot be loaded:
  - Show fallback: “Approval requires re-approval due to estimate revision. Details unavailable.”
  - Do not block navigation to estimate re-approval due to missing audit detail.

**Decision Rationale (resolving prior ambiguity):**
- **Backend authoritative eligibility:** UI must not decide whether a change is “financially relevant”; it only reflects the backend’s invalidation signal (consistent with DECISION-INVENTORY-007 principle: backend authoritative eligibility).
- **Standard error envelope:** Errors should be normalized to the standard envelope with `correlationId` (DECISION-INVENTORY-011) for supportability.

### Read-only vs editable by state/role
- All fields in this story are read-only.

### Derived/calculated fields
- “Approval invalidated at”: derived from latest transition where `toStatusId` equals re-approval-required status (or `metadata.eventType` if provided).
- “Changed amount”: derived from `metadata.newTotalMinor - metadata.oldTotalMinor` when both exist.
- Currency display: use existing currency context from estimate/work order if available; otherwise display minor-unit values only if a formatter exists that does not assume currency.

## 12. Acceptance Criteria

### Scenario 1: Work Order displays re-approval required status and banner
**Given** a Work Order loads with `requiresReapproval = true` **or** `statusId` equals the backend-defined re-approval-required status  
**When** the user opens `durion-workexec/WorkOrderEdit` for that work order  
**Then** the UI displays a clear indicator that customer approval is invalidated and re-approval is required  
**And** the UI does not display the Work Order as “Approved/Customer Approved”.

### Scenario 2: Invalidation details shown from transition history
**Given** a Work Order requires re-approval  
**And** the transitions/history response includes a latest transition whose `toStatusId` indicates re-approval required  
**And** that transition includes `transitionedAt`, `reason`, and `metadata.oldTotalMinor` and `metadata.newTotalMinor`  
**When** the user views the Work Order detail (or History section)  
**Then** the UI shows the invalidation timestamp and reason  
**And** the UI shows old vs new totals when available  
**And** the UI shows estimate version change when available (`metadata.oldVersion`/`metadata.newVersion`).

### Scenario 3: Missing transition metadata degrades gracefully
**Given** a Work Order requires re-approval  
**And** the transitions/history call returns an empty list **or** returns records without `metadata`  
**When** the user opens the Work Order detail screen  
**Then** the UI still shows the “re-approval required” banner  
**And** the UI shows “Details unavailable” (or equivalent) without breaking the page.

### Scenario 4: Actions requiring valid approval are blocked in UI
**Given** a Work Order requires re-approval  
**When** the user views the Work Order detail screen  
**Then** any existing action buttons that would proceed as if approval is valid (start/advance/complete/invoice/promote) are disabled or hidden  
**And** if disabled, they include an explanation: “Blocked: customer re-approval required due to estimate revision.”

### Scenario 5: Unauthorized to view audit history
**Given** a Work Order requires re-approval  
**And** the transitions/history call returns `403 Forbidden`  
**When** the user opens the Work Order detail screen  
**Then** the UI shows the re-approval-required banner based on Work Order status/flags  
**And** the UI does not show restricted audit details  
**And** the UI remains usable.

### Scenario 6: Work Order no longer requires re-approval after refresh
**Given** a Work Order previously required re-approval  
**And** after re-approval the backend no longer indicates re-approval required (e.g., `requiresReapproval=false` and status reflects approved)  
**When** the user refreshes the Work Order detail screen  
**Then** the re-approval-required banner is no longer shown  
**And** the History still contains the prior invalidation transition record (if history is accessible).

### Scenario 7: Estimate navigation is available when estimateId exists
**Given** a Work Order requires re-approval  
**And** `estimateId` is present on the work order  
**When** the user clicks “Open revised estimate”  
**Then** the UI navigates to `durion-workexec/EstimateEdit` with that `estimateId`.
