## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Approval: Capture In-Person Customer Approval (Estimate)

### Primary Persona
Service Advisor

### Business Value
Provide a fast, auditable in-POS flow to record a customer’s in-person approval on an estimate so authorized work can proceed, with a clear timestamped trail and correct enforcement of estimate state rules.

---

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** to capture a customer’s in-person approval on an estimate directly in the POS,  
**so that** the estimate is transitioned to an approved state with an immutable approval record and downstream work order creation can proceed.

### In-scope
- Viewing an estimate and its current approval configuration (method) as context for capture.
- Capturing **in-person** approval using the configured method (at minimum `CLICK_CONFIRM`).
- Handling invalid state, authorization failures, and concurrency conflicts during approval.
- Showing updated estimate status and relevant audit metadata post-approval.
- Using Moqui screen transitions/actions consistent with existing `durion-workexec` estimate screens.

### Out-of-scope
- Electronic signature flows (email/SMS) and delivery of notifications.
- Signature capture UX (drawing pad).
- Full decline workflow and decline reason capture (separate story).
- Work order creation from estimate (separate story).
- Approval configuration management UI (separate story).
- Persisting “approval notes” from the frontend unless/ until backend supports it (see Business Rules + Service Contracts).

---

## 3. Actors & Stakeholders
- **Service Advisor (Primary)**: initiates capture and confirms approval.
- **Customer (External)**: provides consent in person (not a system user).
- **Technician/Mechanic (Stakeholder)**: relies on estimate being approved to begin work order execution.
- **Billing/Audit (Stakeholder)**: requires traceable approval record.

---

## 4. Preconditions & Dependencies
- User is authenticated in the POS frontend.
- User has permission to view the estimate and approve it (enforced server-side; UI may optionally gate via capability signal if available).
- Estimate exists and is in an approval-eligible state:
  - Must be `DRAFT` per backend `approveEstimate()` contract in `CUSTOMER_APPROVAL_WORKFLOW.md`.
- Backend endpoints exist and are reachable:
  - `GET /api/estimates/{id}`
  - `POST /api/estimates/{id}/approve?approvedBy={userId}`
  - Optional/context: `GET /api/approval-configurations/applicable?locationId={locationId}&customerId={customerId}`
- Dependency: identity of logged-in user (`userId`) must be available to frontend (from session/user context).
- Dependency: Moqui estimate screen exists in `durion-workexec` (canonical screen artifact: `EstimateEdit.xml` per DECISION-INVENTORY-002).

### Screens to create/modify
- **Modify**: `durion-workexec/EstimateEdit.xml`
  - Add an “Approval” screenlet/section that:
    - Displays current estimate status.
    - Displays effective approval method (if available).
    - Provides “Capture In-Person Approval” action when eligible.
    - Displays approval metadata when approved.
  - Add a confirmation dialog/modal (Moqui screenlet/dialog pattern) invoked from the action.

### Navigation context
- Canonical navigation uses Moqui component routing to `EstimateEdit` (per DECISION-INVENTORY-002). The story does not introduce a new SPA route; it extends the existing Moqui screen.
- After successful approval: remain on the same estimate screen; refresh the estimate header/section to show updated status and audit fields.

### User workflows (happy + alternate paths)

**Happy path**
1. Service Advisor opens estimate in `EstimateEdit`.
2. UI shows status `DRAFT` and an enabled “Capture In-Person Approval” action.

## 6. Functional Behavior

### Triggers
- User clicks “Capture In-Person Approval” on `EstimateEdit`.
- User confirms in modal/dialog.

### UI actions
- On screen load:
  - Load estimate (existing screen behavior) and compute `canApprove`.
  - If approval method is not present on estimate payload and the applicable-config endpoint is available, load effective approval configuration for display (read-only).
- On click “Capture In-Person Approval”:
  - If `canApprove` is false, do nothing besides showing the reason (no dialog).
  - If `canApprove` is true, open confirmation dialog.
- On confirm:
  - Disable confirm button and show loading state.
  - Submit approval request with `approvedBy=<loggedInUserId>`.
  - On success: refresh estimate data (either from response body if returned, or via re-GET) and update UI.

### State changes (frontend-visible)
- Estimate status changes from `DRAFT` → `APPROVED` in UI.
- Approval metadata becomes visible when present (`approvedAt`, `approvedBy`).

### Service interactions
- Load estimate: `GET /api/estimates/{id}` on screen load and after successful approval.
- Approve estimate: `POST /api/estimates/{id}/approve?approvedBy={userId}` on confirm.
- Optional config context: `GET /api/approval-configurations/applicable?locationId={locationId}&customerId={customerId}` for display-only context.

### Decision rationale applied (resolutions)
- **Estimate vs Work Order ambiguity resolved**: This story implements **Estimate approval only**, because the authoritative backend workflow and endpoints are for `Estimate` (`/api/estimates/{id}/approve`) per `CUSTOMER_APPROVAL_WORKFLOW.md`. Work order creation/approval is explicitly out-of-scope here.
- **Moqui screen routing resolved**: Use existing `durion-workexec/EstimateEdit.xml` as the canonical screen per DECISION-INVENTORY-002; do not invent new routes.
- **Approval notes resolved**: Not implemented in this story because the backend approval endpoint is query-param based and does not define a notes payload; adding notes would be a contract change (not a safe default).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Approval may only be attempted when estimate status is `DRAFT`.
  - UI must disable/hide the approval action when status != `DRAFT`.
  - Backend remains authoritative; UI must handle backend rejection even if UI thought it was eligible.

### Enable/disable rules
- “Capture In-Person Approval” enabled only if:
  - Estimate loaded successfully
  - `estimate.status == DRAFT`
  - Not currently submitting
  - (Optional) capability signal indicates approval allowed; otherwise rely on backend 403

### Visibility rules
- Show approval metadata panel when:
  - `estimate.status == APPROVED` OR `approvedAt`/`approvedBy` fields exist.
- Show approval method label when available:
  - Prefer method/config included on estimate payload.
  - Else show method from applicable configuration call.
  - If neither available, show “Approval method: Unknown” (display-only; does not block approval).

### Error messaging expectations (aligned to standard envelope where available)
- Invalid state (400): “This estimate cannot be approved in its current state.”
- Conflict (409): “This estimate was updated by someone else. Refresh to continue.”
- Forbidden (403): “You don’t have permission to approve estimates.”
- Not found (404): “Estimate not found.”
- Server error (5xx): “Approval failed due to a server error. Try again.”

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
1. `GET /api/estimates/{id}`
   - **200 OK**: Estimate JSON including at least `id`, `status`, `shopId`, `customerId`.
   - **401/403**: unauthorized/forbidden.
   - **404**: not found.

2. (Optional, display-only) `GET /api/approval-configurations/applicable?locationId={shopId}&customerId={customerId}`
   - **200 OK**: ApprovalConfiguration JSON.
   - If endpoint returns 404 or empty: UI must treat as “Unknown method” and continue (approval still allowed if estimate is `DRAFT`).

### Submit/transition calls
1. `POST /api/estimates/{id}/approve?approvedBy={userId}`
   - **Expected success**: **200 OK** with updated Estimate JSON (preferred). If backend returns minimal ack, UI must re-GET estimate.
   - **400 Bad Request**: invalid state (not `DRAFT`) or validation failure.
   - **409 Conflict**: concurrent modification or already approved (backend-specific; UI treats as conflict and refreshes).
   - **403 Forbidden**: user not permitted.

### Error handling expectations
- If backend provides a standard error envelope (code/message/correlationId), UI should:
  - Display `message` to user (or mapped friendly message).
  - Surface `correlationId` in an expandable “Details” area for support.
- If backend does not provide envelope, map by HTTP status code.

- `DRAFT`
- `APPROVED`
- `DECLINED`
- `EXPIRED`

### Allowed transitions in this story
- `DRAFT` → `APPROVED` via in-person approval capture.

### Role-based transitions
- Service Advisor can perform approval subject to backend RBAC.
- Other roles: read-only unless backend authorizes.

### UI behavior per state
- `DRAFT`: show approval action enabled.
- `APPROVED`: hide/disable approval action; show approval metadata.
- `DECLINED`/`EXPIRED`: hide/disable approval action; show status only.

## 11. Alternate / Error Flows

### Validation failures
- Estimate changes state between load and submit:
  - Backend returns 400/409.
  - UI shows error, reloads estimate, and closes dialog (or keeps it open but disables confirm and shows updated status).

### Concurrency conflicts
- On 409:
  - Show conflict message and a “Refresh” action.
  - Refresh triggers `GET /api/estimates/{id}` and updates screen.

### Unauthorized access
- 401:
  - Follow project login redirect pattern; preserve return URL to the estimate screen.
- 403:
  - Show permission error; keep user on estimate screen; do not retry automatically.

### Empty states
- 404 on load:
  - Show “Estimate not found” with navigation back to estimate list (if available) or previous screen.

## 12. Acceptance Criteria

### Scenario 1: Approve a Draft estimate in person (click confirm)
**Given** I am logged in as a Service Advisor  
**And** an Estimate exists with status `DRAFT`  
**When** I open the Estimate edit/detail screen (`durion-workexec/EstimateEdit`)  
**And** I click “Capture In-Person Approval”  
**And** I confirm the approval in the confirmation dialog  
**Then** the frontend calls `POST /api/estimates/{id}/approve?approvedBy={myUserId}`  
**And** the UI refreshes the estimate (from response or via `GET /api/estimates/{id}`)  
**And** the Estimate status displayed updates to `APPROVED`  
**And** the approval action is no longer available on the screen

### Scenario 2: Prevent approval when estimate is not Draft
**Given** I am viewing an Estimate with status `APPROVED`  
**When** the Estimate screen renders  
**Then** the “Capture In-Person Approval” action is disabled or hidden  
**And** the approval metadata (approvedAt/approvedBy) is visible if provided by the API

### Scenario 3: Backend rejects approval due to invalid state
**Given** I am viewing an Estimate with status `DECLINED`  
**When** I attempt to approve it (via stale UI or direct action)  
**Then** the backend responds with an error (400 or 409)  
**And** the frontend displays “This estimate cannot be approved in its current state.”  
**And** the displayed status remains `DECLINED` after refresh

### Scenario 4: Concurrency conflict during approval
**Given** an Estimate is `DRAFT` when I load it  
**And** another user approves or modifies it before I confirm  
**When** I confirm in-person approval  
**Then** the backend responds `409 Conflict`  
**And** the frontend informs me the estimate was updated elsewhere  
**And** provides a “Refresh” action that reloads the estimate detail  
**And** after refresh, the UI reflects the server status

### Scenario 5: Unauthorized approval attempt
**Given** I am logged in without permission to approve estimates  
**And** I view a `DRAFT` estimate  
**When** I attempt to confirm approval  
**Then** the backend responds `403 Forbidden`  
**And** the frontend displays “You don’t have permission to approve estimates.”  
**And** the estimate remains `DRAFT` in the UI after refresh
