## 1. Story Header

### Title
[FRONTEND] [STORY] Invoicing: Support Authorized Invoice Adjustments (Draft invoices)

### Primary Persona
Back Office Manager

**Persona Metadata**

### Business Value
Enable authorized corrections and goodwill adjustments on **Draft** invoices while preserving **accounting correctness, auditability, and traceability**, preventing negative invoice totals and ensuring downstream accounting events are produced.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Back Office Manager  
- **I want** to adjust a **Draft** invoice (edit invoice line items and/or apply an invoice-level discount) with required reason capture  
- **So that** invoice totals/taxes are recalculated correctly, the change is fully audited, and the accounting system can emit the appropriate event (`InvoiceAdjusted` or `CreditMemoIssued`).

### In-scope
- Frontend UI to initiate and submit an adjustment for an invoice that is currently `Draft`
- Capturing **reason code** and **justification** when required by configuration
- Displaying before/after totals impact prior to submit (where supported by backend)
- Handling backend rejections: unauthorized, not-draft, negative-total-requires-credit-memo, missing reason code/justification, concurrency conflict
- Displaying adjustment audit history relevant to adjustments (at least the latest adjustment outcome; ideally the list)

### Out-of-scope
- Creating/issuing a **Credit Memo** (separate story; this story only blocks and guides when credit memo is required)
- Defining tax policy, GL account mappings, revenue/tax/AR posting semantics
- Editing **Issued** invoices
- Admin management of Reason Codes and configuration flags (assumed existing)

---

## 3. Actors & Stakeholders
- **Back Office Manager**: performs authorized adjustments and provides reason/justification
- **Accounting domain services**: system of record for invoice financial state; recalculates totals; writes audit event; emits `InvoiceAdjusted` / `CreditMemoIssued`
- **Auditor/Compliance**: consumes immutable audit trail (who/when/what/why)
- **Support/Operations**: needs actionable error feedback and trace identifiers

---

## 4. Preconditions & Dependencies
- Invoice exists and is retrievable in the frontend by `invoiceId` (UUIDv7)
- Invoice is in **status = `Draft`** at time of submit (must be revalidated server-side)
- User is authenticated
- User has permission to adjust invoices (permission token is backend-authoritative; see Open Questions)
- Reason codes exist for invoice adjustments, and backend can validate “active” status
- Backend endpoints/services exist for:
  - Loading invoice details (including status, line items, totals, currency, and concurrency token)
  - Submitting an adjustment command (atomic update + recalculation + audit + event emission)
  - Loading audit events/history for the invoice (recommended)

### Screens to create/modify

   - Submit / Cancel transitions

### Navigation context
- InvoiceDetail → InvoiceAdjust (pass `invoiceId`)
- On success: return to InvoiceDetail (same `invoiceId`) and show confirmation plus updated totals and audit entry visible.

### User workflows (happy + alternate paths)

**Happy path**
1. Manager opens Draft invoice detail
2. Clicks “Adjust Invoice”
3. UI loads invoice + reason codes + (optional) existing adjustment audit history
4. Manager edits allowed fields (line items and/or invoice-level discount)
5. Manager selects reason code; enters justification if required
6. Manager submits
7. Backend recalculates totals, persists changes, writes audit event, emits `InvoiceAdjusted` (or `CreditMemoIssued` if backend chooses that path)
8. UI returns to invoice detail with updated totals and new audit entry

**Alternate paths**
- Not authorized: action hidden; direct navigation shows “Not Authorized” and does not render editable controls
- Invoice becomes non-draft before submit: submit fails with conflict; UI prompts reload and disables submit until refreshed
- Backend rejects due to negative total: UI shows “Credit memo required” banner; keeps edits intact; no local commit
- Missing reason/justification: inline validation; backend errors mapped to fields without losing edits
- Backend indicates preview not available: UI does not attempt client-side tax math; shows “Totals will be recalculated on submit”

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Draft-only adjustment**: If invoice status != `Draft`, adjustment UI must be read-only and show: “Invoice is not Draft and cannot be adjusted.”
- **Authorization**: If user lacks permission, block access and show unauthorized (do not leak invoice existence on 403/404).
- **Reason capture**:
  - UI must treat “reason required” and “justification required” as backend-authoritative flags (do not infer policy).
  - If required, enforce selection of a reason code and non-empty justification before enabling submit.
- **Negative totals disallowed** (Accounting invariant): If backend rejects with a “requires credit memo” error, show a blocking banner and keep edits intact. UI must not attempt to create a credit memo in this story.
- **Calculations are backend-authoritative**: UI must not compute taxes/fees; it may display a backend-provided preview if available.

### Enable/disable rules
- Disable “Submit Adjustment” while:
  - invoice not loaded
  - invoice status not `Draft`
  - required reason/justification missing
  - request in-flight
- Disable editing while submit is in-flight

### Visibility rules
- “Adjust Invoice” action visible only when:
  - invoice status == `Draft`
  - user authorized (permission token enforced by backend; UI hides action when permission absent)
- Show “Adjusted” indicator if `isAdjusted == true` OR audit history contains at least one adjustment event
- Show audit history section when available; otherwise show empty state

### Error messaging expectations
- Unauthorized (403) → “You do not have permission to adjust invoices.”
- Not Draft / conflict (409) → “Invoice is no longer Draft. Reload to see latest status.”
- Optimistic lock conflict (409) → “Invoice changed since you opened it. Reload required.”
- Negative total requires credit memo → “This change would make the invoice total negative. Create a credit memo instead.”
- Invalid/missing reason code / justification → inline errors + backend `errorCode` surfaced in a details panel for support

## 8. Data Requirements

### Entities involved (frontend perspective)
- `Invoice`
- `InvoiceItem`
- `InvoiceAuditEvent` (or equivalent audit view)
- `ReasonCode` (or equivalent reason list)

### Fields (types, required, defaults)

**Invoice (read)**
- `invoiceId` (UUIDv7, string) required
- `status` (string/enum) required; must include `Draft`
- `currencyUomId` (string) required
- `isAdjusted` (boolean) optional; default false if present
- Totals (decimal strings; currency scale per backend):
  - `subtotal` required
  - `taxTotal` required (may be 0)
  - `feeTotal` optional (may be 0 or absent)
  - `grandTotal` required
- Concurrency token (one of):
  - `lastUpdatedStamp` (timestamp string) OR
  - `version` (number/string)
  Required if backend enforces optimistic locking.

**InvoiceItem (read + edit where allowed)**
- `invoiceItemId` (UUIDv7/string) required
- `productId`/`itemType` (string) read-only (if present)
- `description` (string) editable only if backend allows (default: read-only)
- `quantity` (decimal string) editable only if backend allows (default: editable if present and not explicitly read-only)
- `unitPrice` (decimal string) editable only if backend allows (default: editable if present and not explicitly read-only)
- `lineDiscount` (decimal string or structured) editable only if backend allows (default: editable if present and not explicitly read-only)
- Tax fields (`taxCode`, taxability flags) are treated as read-only unless backend explicitly marks editable (Accounting rule: tax policy is authoritative elsewhere).

**Invoice-level discount (edit)**
- `invoiceDiscount` (shape backend-defined) editable only if backend supports; UI must not invent percent vs amount behavior.

**Adjustment command (write)**
- `invoiceId` required
- `reasonCode` conditionally required
- `justification` conditionally required
- `concurrencyToken` (e.g., `lastUpdatedStamp` or `version`) if required
- `changes` payload: only include fields the backend contract accepts (see Service Contracts)

**Audit event (read)**
- `auditEventId` (UUIDv7/string) required
- `eventType` (string) required (filterable)
- `createdByUserId` (string) required
- `createdAt` (timestamp) required
- `reasonCode` (string) optional
- `justification` (string) optional; may be permission-gated (see Business Rules)
- `beforeTotals` / `afterTotals` (structured totals) optional but strongly preferred
- `changeSummary` (string) optional

### Read-only vs editable by state/role
- If invoice status != `Draft`: all fields read-only; submit disabled.
- Only authorized users can edit and submit.
- Audit events are always read-only.

### Derived/calculated fields
- Totals are backend-calculated and must be displayed as authoritative.
- “Adjusted” indicator may be derived from `isAdjusted` or audit history presence.

## 9. Service Contracts (Frontend Perspective)

> Use Moqui screen actions/services consistent with existing frontend integration. Endpoints below are placeholders unless already implemented; UI must not invent schemas.

### Load/view calls
1. **Get Invoice Detail**
   - Request: `invoiceId` (UUIDv7)
   - Response: invoice header, items, status, totals, currency, `isAdjusted` (if present), concurrency token
2. **Get Adjustment Reason Codes**
   - Request: `reasonType=INVOICE_ADJUSTMENT` (or backend-defined)
   - Response: list of active reason codes `{code, label, active}`
3. **Get Invoice Audit Events (adjustments)**
   - Request: `invoiceId`, optional filter `eventType=INVOICE_ADJUSTMENT`
   - Response: list ordered by `createdAt desc`

### Create/update calls
1. **Submit Invoice Adjustment (atomic)**
   - Request (minimum):
     - `invoiceId`
     - `changes` (items and/or invoice-level discount per backend contract)
     - `reasonCode` / `justification` if required
     - concurrency token if required
   - Response:
     - updated invoice (status, totals, `isAdjusted` if present)
     - created audit event summary (preferred)
     - emitted event reference (optional)

### Submit/transition calls
- None beyond “Submit Adjustment”.

### Error handling expectations (map to UI)
- Error schema (canonical): `{ errorCode, message, details? }`
- `403` → unauthorized
- `404` → not found (safe messaging; do not leak existence)
- `409` → conflict (not-draft or optimistic lock)
- `400/422` → validation errors:
  - missing reason/justification
  - negative total requires credit memo
  - invalid line item edits
- UI must display `errorCode` in an expandable “Details” section for support and include trace identifiers when available.

## 11. Alternate / Error Flows

### Validation failures
- Missing reason code when required:
  - inline error on reason selector
  - keep edits intact
- Missing justification when required:
  - inline error on justification field
- Invalid edit (field not allowed / invalid amount):
  - show inline error if backend provides field mapping in `details`
  - otherwise show banner with backend message

### Concurrency conflicts
- Optimistic lock conflict:
  - show banner “Invoice updated by another user; reload required”
  - provide “Reload Invoice” action
  - do not auto-merge changes; user must re-apply edits manually

### Unauthorized access
- Direct navigation without permission:
  - show 403 page/banner
  - do not render editable controls
  - do not fetch sensitive data beyond what backend allows

### Empty states
- No reason codes returned but reason is required:
  - block submission
  - show “No active adjustment reasons configured. Contact administrator.”
- No audit events:
  - show empty state “No adjustments recorded.”

## 12. Acceptance Criteria

### Scenario 1: Authorized user adjusts a Draft invoice successfully
Given an invoice exists with status "Draft"  
And the current user has permission to adjust invoices  
And at least one valid active adjustment reason code exists  
When the user opens "Adjust Invoice" for that invoice  
And edits allowed invoice fields (line items and/or invoice-level discount)  
And selects a reason code  
And provides justification when required by backend configuration  
And submits the adjustment  
Then the system saves the adjustment and returns the updated invoice  
And the displayed totals reflect the backend recalculation (subtotal/tax/fees/grand total)  
And the invoice indicates it has been adjusted (via `isAdjusted=true` or audit history)  
And an adjustment audit entry is visible with actor, timestamp, reason, and before/after totals.

### Scenario 2: Unauthorized user cannot adjust invoices
Given an invoice exists with status "Draft"  
And the current user does not have permission to adjust invoices  
When the user attempts to access the invoice adjustment screen or submit an adjustment  
Then the UI blocks the action  
And a backend 403 Forbidden response (if returned) is handled without leaking invoice existence  
And the UI displays an authorization error message.

### Scenario 3: Invoice is no longer Draft at submit time
Given an invoice exists  
And the user opens the adjustment screen while it is "Draft"  
When the invoice status changes to a non-Draft state before submission  
And the user submits the adjustment  
Then the backend response is handled as a conflict (409 or equivalent)  
And the UI shows "Invoice is no longer Draft and cannot be directly adjusted"  
And the UI provides a reload action  
And no local success confirmation is shown.

### Scenario 4: Adjustment rejected because it would make total negative
Given an invoice exists with status "Draft"  
And the current user has permission to adjust invoices  
When the user submits an adjustment that would result in a grand total less than 0.00  
Then the backend response is handled as a validation error  
And the error code indicating "requires credit memo" is displayed (or mapped to a user-friendly message)  
And the invoice is not updated in the UI  
And the user’s entered changes remain visible for revision.

### Scenario 5: Reason code and justification enforcement
Given an invoice exists with status "Draft"  
And the backend indicates a reason code is required  
And the backend indicates justification text is required  
When the user attempts to submit without selecting a reason code or without justification  
Then the UI prevents submission and highlights the missing fields  
And if submitted anyway, backend validation errors are surfaced inline without losing edits.

### Scenario 6: Multiple adjustments do not corrupt totals (frontend verification)
Given an invoice exists with status "Draft"  
And the current user has permission to adjust invoices  
When the user performs an adjustment successfully  
And then performs a second adjustment successfully  
Then the invoice totals displayed match the backend totals after each adjustment  
And the audit history shows both adjustments in chronological order  
And the UI does not display duplicated or stale totals.
