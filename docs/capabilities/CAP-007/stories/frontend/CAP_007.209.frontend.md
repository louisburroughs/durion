## Title
[FRONTEND] [STORY] Invoicing: Finalize and Issue Invoice

## Primary Persona
Back Office / Accounts Receivable Clerk

**Persona Metadata**
- `primary_persona`: `Back Office / Accounts Receivable Clerk`
- `canonical_persona`: `Accounting Associate`
- `persona_family`: `Accounting Associate`

## Business Value
Convert a reviewed Draft invoice into an official, immutable Issued invoice with auditability and downstream event emission readiness, reducing billing errors and preventing duplicate issuance.

---

# 2. Story Intent

## As a / I want / So that
- **As an** Accounts Receivable Clerk  
- **I want to** issue a Draft invoice after review  
- **So that** it becomes an official Issued invoice (locked/immutable), auditable, and ready for delivery and downstream accounting processing.

## In Scope
- Frontend “Issue Invoice” action from an invoice detail screen.
- Frontend display of invoice totals, line items, delivery preference, and traceability snapshot (read-only review context).
- Frontend rendering of backend-provided `issuancePolicy` and `issuanceBlockers[]` for Draft invoices (pre-issuance gating visibility).
- Frontend orchestration of issuance request to backend (`POST /billing/invoices/{invoiceId}/issue`) including step-up auth token when required.
- Handling validation errors (422 blockers), conflict errors (409 already issued/paid/void), and authorization failures (403).
- Post-issuance UI behavior: lock editing actions, show issued metadata, and show any backend-provided delivery preparation/status fields.
- Artifact list + secure download initiation from invoice context (read-only) when permitted.

## Out of Scope
- Credit/rebill, credit memo creation, refunds/chargebacks.
- Editing invoice lines/totals in this screen/flow (lines/totals are derived from snapshots and not editable here).
- Payment capture/collection flows and receipt delivery/reprint flows (separate stories).
- Accounting postings / AR creation UI (Accounting consumes events asynchronously).
- Designing invoice numbering scheme policy.
- Implementing event bus/outbox mechanics (backend responsibility).
- Implementing Work Order, Estimate, Approval record screens (only link metadata rendering/copy is in scope).

---

# 3. Actors & Stakeholders
- **Accounts Receivable Clerk (primary user):** reviews and issues invoices.
- **Supervisor/Manager (step-up approver, when required):** provides elevation token for overrides when issuance policy requires it.
- **Customer (indirect):** receives invoice via email/print (delivery execution not in scope here).
- **Billing domain / service (SoR):** owns invoice lifecycle state, issuance validations, traceability snapshot, and issuance audit.
- **Accounting domain (downstream consumer):** creates AR and posts based on `InvoiceIssued` event; not directly controlled by frontend.
- **Auditor/Compliance:** requires non-repudiation and issuance audit trail.

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated.
- User has permission `billing:invoice:view` to view invoice detail.
- User has permission `billing:invoice:issue` to issue invoices (action hidden/disabled otherwise).
- Invoice exists and is accessible within tenant boundaries.
- Invoice is in **`DRAFT`** status at time user initiates issuance.

## Dependencies (must exist or be implemented in Moqui backend)
- Invoice detail endpoint:
  - `GET /billing/invoices/{invoiceId}`
  - Must include for Draft invoices: `issuancePolicy` and `issuanceBlockers[]` (BILL-DEC-003).
  - Must include immutable `traceability` snapshot fields (BILL-DEC-004).
  - Should include `allowedActions[]` and/or computed flags for UX (BILL-DEC-008), but backend remains authoritative for security.
- Issue invoice command:
  - `POST /billing/invoices/{invoiceId}/issue`
  - Atomic, idempotent per `invoiceId + invoiceVersion` (BILL-DEC-001, BILL-DEC-003).
  - On success sets: `invoiceNumber`, `issuedAt`, `issuedByUserId` and transitions `DRAFT → ISSUED`.
  - On failure returns:
    - 422 with structured blocker codes matching `issuanceBlockers[]` (BILL-DEC-003)
    - 409 if already `ISSUED/PAID/VOID` (BILL-DEC-001)
- Step-up auth (only when required by policy/blockers):
  - `POST /billing/auth/elevate` returns short-lived `elevationToken` (BILL-DEC-010).
- Artifact retrieval (optional panel, permissioned):
  - `GET /billing/invoices/{invoiceId}/artifacts` (BILL-DEC-005)
  - Secure download via token flow:
    - `POST /billing/artifacts/{artifactRefId}/download-token` → `{downloadToken, expiresAt}`
    - `GET /billing/artifacts/download?token=...`
- Permission model uses canonical permission strings (BILL-DEC-008).
- Observability: propagate W3C Trace Context headers `traceparent` (required) and `tracestate` (optional) on all calls (BILL-DEC-015).

# 5. UX Summary (Moqui-Oriented)

## Entry Points
- From invoice search/list: open invoice detail.
- From Work Order context: navigate to invoice detail via link metadata or by-work-order lookup (if implemented elsewhere).

## Screens to Create/Modify
1. **Create/Modify**: `apps/pos/billing/invoice/InvoiceDetail` (screen name/path must follow repo conventions; do not hardcode in backend payloads per BILL-DEC-016)
   - Data load from `GET /billing/invoices/{invoiceId}`.
   - Render:
     - Invoice header + totals + line items (read-only)
     - Delivery preference summary (read-only)
     - Traceability panel (permissioned by `billing:traceability:view`)
     - Issuance blockers panel (Draft only; derived from `issuanceBlockers[]`)
     - Issuance metadata panel (Issued/Paid/Void)
     - Optional artifacts panel (permissioned by `billing:artifact:list`)
   - Actions:
     - “Issue Invoice” (Draft only; permissioned by `billing:invoice:issue`)
     - “Refresh” (always)
     - Artifact “Download” (permissioned by `billing:artifact:download`)
2. **Create/Modify**: `apps/pos/billing/invoice/IssueInvoiceConfirm` (modal/screenlet)
   - Always shown before issuing (irreversible action confirmation).
   - If issuance requires elevation, includes step-up auth flow to obtain `elevationToken` (BILL-DEC-010).

## Navigation Context
- Invoice detail is addressed by `invoiceId` (UUIDv7).
- Any cross-domain navigation uses backend-provided link metadata `{targetDomain, targetType, targetId}` (BILL-DEC-016):
  - If the frontend router supports the target, render as link.
  - Otherwise render as copy-only identifier.

## User Workflows (happy + alternate paths)

### Happy Path (no elevation required)
1. User opens Draft invoice detail.
2. UI shows `issuanceBlockers[]` (empty) and `allowedActions` includes `ISSUE` (or equivalent).
3. User clicks **Issue Invoice**.
4. Confirmation modal appears; user confirms.
5. UI calls `POST /billing/invoices/{invoiceId}/issue` with no `elevationToken`.
6. UI reloads invoice detail.
7. UI shows `status=ISSUED`, `invoiceNumber`, `issuedAt`, `issuedByUserId`; disables/hides issue action and any edit actions.

### Happy Path (elevation required)
1. User opens Draft invoice detail and sees blockers indicating override/elevation required (backend-defined codes).
2. User clicks **Issue Invoice**.
3. Confirmation modal indicates elevation required; user initiates step-up auth.
4. UI calls `POST /billing/auth/elevate` (credentials captured in secure UI; never logged).
5. UI receives `elevationToken` and submits `POST /billing/invoices/{invoiceId}/issue` with `{elevationToken}`.
6. UI reloads invoice detail and shows Issued state.

### Alternate Paths
- Blocked by missing prerequisites: user sees blockers before attempting issuance; if they attempt anyway, 422 returns same blocker codes; UI renders them.
- Already issued/paid/void: issuance returns 409; UI reloads and shows current state with banner “Already finalized”.
- Unauthorized: issue action hidden/disabled; direct command attempt returns 403; UI shows authorization error.
- Artifact access: list/download only shown when permitted; download uses token flow and opens download in a new tab/window without logging token.

# 6. Functional Behavior

## Triggers
- User clicks “Issue Invoice” on Draft invoice detail screen.

## UI Actions
- On invoice detail load:
  - Call `GET /billing/invoices/{invoiceId}`.
  - Render `issuancePolicy` and `issuanceBlockers[]` when status is `DRAFT`.
  - Render `allowedActions[]` if provided (UX only; not security).
- On “Issue Invoice” click:
  - Open confirmation modal (always).
  - If backend indicates elevation required (via blockers/policy or allowedActions metadata), require step-up auth to obtain `elevationToken`.
  - Disable the Issue button while request is in-flight.
  - Call `POST /billing/invoices/{invoiceId}/issue` with body `{ elevationToken?: string }`.
- On success:
  - Re-fetch invoice detail (do not rely on optimistic updates).
  - Show success notification including `invoiceNumber`.
  - Hide/disable “Issue Invoice” action.
  - Ensure all invoice fields are read-only (status != `DRAFT`).
- On failure:
  - 422: render blockers/errors; keep user on Draft view; do not change local status.
  - 409: refresh invoice detail; show banner “Invoice already finalized” and display current status/metadata.
  - 403: show “Not authorized” banner; keep user on detail screen.
  - 404: route to Not Found / Access Denied screen per app convention.
  - 503/timeout: show retry guidance; re-enable Issue action.

## State Changes (UI-observed)
- `status`: `DRAFT → ISSUED` only (BILL-DEC-001).
- Post-issuance immutability: treat header/lines/totals/traceability as read-only when `status != DRAFT`.

## Service Interactions
- `GET /billing/invoices/{invoiceId}` on entry and after any issuance attempt (success or 409).
- `POST /billing/invoices/{invoiceId}/issue` on confirm.
- `POST /billing/auth/elevate` only when required.
- Optional:
  - `GET /billing/invoices/{invoiceId}/artifacts` to populate artifacts panel.
  - `POST /billing/artifacts/{artifactRefId}/download-token` to initiate download.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Frontend must not implement issuance policy logic; it must render backend-provided policy and blockers (BILL-DEC-003).
- Frontend may perform only UX-level validation:
  - Confirmation checkbox/button required to proceed.
  - If step-up auth is required, ensure `elevationToken` is present before calling issue.
- Backend is authoritative for:
  - Invoice must be `DRAFT` to issue (409 otherwise).
  - Traceability completeness and any conditional requirements (BILL-DEC-003, BILL-DEC-004).
  - Delivery-method consistency requirements.
  - Any tax/fee/totals consistency.

## Enable/Disable Rules
- “Issue Invoice” action is:
  - Visible only if user has `billing:invoice:issue`.
  - Enabled only if:
    - `invoice.status == DRAFT`
    - no in-flight issuance request
    - (optional UX hint) backend `allowedActions[]` includes issue action; if not included, disable and show reason from blockers/messages.
- Traceability panel:
  - Visible only if user has `billing:traceability:view`.
- Artifacts panel:
  - Visible only if user has `billing:artifact:list`.
  - Download action visible only if user has `billing:artifact:download`.

## Visibility Rules
- Draft invoices:
  - Show `issuanceBlockers[]` panel even if empty (empty state: “No blockers detected”).
  - Show `issuancePolicy.policyVersion` (if provided) for audit transparency.
- Issued/Paid/Void invoices:
  - Show issuance metadata: `invoiceNumber`, `issuedAt`, `issuedByUserId`.
  - Hide blockers panel (or show as “Not applicable; invoice finalized”).
- Unknown invoice status enum:
  - Show “Unknown status” banner and disable issuance; provide refresh action.

## Error Messaging Expectations
- 422 issuance blockers:
  - Show summary “Cannot issue invoice” and list each blocker with:
    - `code`
    - `severity` (if provided)
    - `text`
  - If blocker includes a link target metadata, render link; otherwise show copy-only IDs.
- 409 conflict:
  - “Invoice already finalized; refreshed to latest state.”
- 403:
  - “You don’t have permission to issue invoices.”
- 503/timeout:
  - “Issue failed due to a temporary service problem. Try again.” Include `correlationId` if provided.

# 9. Service Contracts (Frontend Perspective)

## Load/view calls
1. **Get invoice detail**
   - `GET /billing/invoices/{invoiceId}`
   - Response must include:
     - invoice header, lines, totals, breakdowns
     - `traceability` snapshot (BILL-DEC-004)
     - for Draft: `issuancePolicy` and `issuanceBlockers[]` (BILL-DEC-003)
     - optional `allowedActions[]` and sanitized `postingErrorSummary` if present (BILL-DEC-014)

2. **List artifacts (optional)**
   - `GET /billing/invoices/{invoiceId}/artifacts`
   - Requires permission `billing:artifact:list`

## Create/update calls
- None (issuance is a command; invoice composition is immutable snapshot-derived in this flow).

## Submit/transition calls
1. **Issue invoice**
   - `POST /billing/invoices/{invoiceId}/issue`
   - Request body: `{ "elevationToken"?: "string" }`
   - Success:
     - 200 with updated invoice snapshot OR minimal success payload; frontend must re-fetch invoice detail either way.
   - Errors:
     - 422 with structured blockers/validation errors (must include blocker codes matching `issuanceBlockers[]`) (BILL-DEC-003)
     - 409 if invoice not in `DRAFT` or already finalized (BILL-DEC-001)
     - 403 if missing `billing:invoice:issue`

2. **Step-up auth (only when required)**
   - `POST /billing/auth/elevate`
   - Response: `{ elevationToken, expiresAt }`
   - Frontend requirements:
     - Do not log credentials or token (BILL-DEC-010)
     - Treat token as short-lived and single-use; clear from memory after use

3. **Artifact download token (optional)**
   - `POST /billing/artifacts/{artifactRefId}/download-token`
   - Response: `{ downloadToken, expiresAt }`
   - Then `GET /billing/artifacts/download?token=...`
   - Frontend must never log token or resulting URL (BILL-DEC-005)

## Error handling expectations
- 422: render blockers list; focus error summary; keep user on same screen.
- 409: refresh invoice detail; show conflict banner; disable issuance.
- 403: show authorization banner; disable issuance.
- 404: show not found/inaccessible.
- 503/timeout: show retry; do not change local state.
- Error payload should support:
  - `errorCode`, `message`, `correlationId`
  - `blockers[]` and/or `fieldErrors[]` (render generically if shape varies; prefer blockers when present).

# 10. State Model & Transitions

## Allowed states
Canonical invoice statuses (BILL-DEC-001):
- `DRAFT`
- `ISSUED`
- `PAID`
- `VOID`
- Optional: `ERROR` (only if backend implements; UI must treat as unknown/finalized for editing purposes unless contract says otherwise)

## Role-based transitions
- User with `billing:invoice:issue`:
  - `DRAFT → ISSUED` via `POST /billing/invoices/{invoiceId}/issue`
- No other transitions in scope.

## UI behavior per state
- `DRAFT`:
  - Show blockers/policy panel.
  - Show Issue action (if permitted).
- `ISSUED`:
  - Hide Issue action.
  - Show issuance metadata.
- `PAID` / `VOID`:
  - Same as `ISSUED` for this screen; show status banner.
- Unknown status:
  - Disable Issue action; show “Unknown status” banner and refresh option.

# 11. Alternate / Error Flows

## Validation failures (422)
- User attempts issuance and backend returns 422 with blockers/field errors.
- UI:
  - Shows “Cannot issue invoice” banner.
  - Renders each blocker with code/text.
  - If blockers indicate missing upstream data (e.g., missing approval), UI provides link/copy actions only; it does not attempt to “fix” within Billing.

## Concurrency conflicts (409)
- Another user issues invoice first.
- UI:
  - Shows conflict banner.
  - Re-fetches invoice detail and displays finalized state.

## Unauthorized access (403)
- User lacks `billing:invoice:issue`.
- UI:
  - Hides or disables Issue action.
  - If user triggers issuance via direct URL/action, show authorization error and do not retry.

## Empty states
- `issuanceBlockers[]` empty:
  - Show “No blockers detected” message (Draft only).
- No artifacts returned or user lacks permission:
  - Show “No artifacts available” or hide panel based on permission.

## Downstream unavailable (503/timeout)
- UI:
  - Shows non-destructive error with retry.
  - Re-enables Issue action after failure.
  - Does not assume issuance succeeded; user may refresh to confirm.

# 12. Acceptance Criteria

## Scenario 1: Draft invoice shows issuance blockers and allows issuing when none exist
**Given** I am authenticated and have `billing:invoice:view` and `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT`  
**When** I open the invoice detail screen  
**Then** the UI loads invoice detail from `GET /billing/invoices/{invoiceId}`  
**And** the UI displays `issuancePolicy` and `issuanceBlockers[]`  
**And** if `issuanceBlockers[]` is empty, the “Issue Invoice” action is enabled.

## Scenario 2: Issue a valid Draft invoice successfully (no elevation)
**Given** I have `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT` and `issuanceBlockers[]` is empty  
**When** I click “Issue Invoice” and confirm  
**Then** the UI calls `POST /billing/invoices/{invoiceId}/issue`  
**And** on success the UI re-fetches invoice detail  
**And** the invoice detail shows `status = ISSUED`  
**And** `invoiceNumber`, `issuedAt`, and `issuedByUserId` are displayed  
**And** the “Issue Invoice” action is no longer available.

## Scenario 3: Issuance blocked by backend policy (422 blockers)
**Given** I have `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT`  
**When** I attempt to issue the invoice  
**And** the backend responds 422 with blockers  
**Then** the UI keeps the invoice displayed as `DRAFT`  
**And** the UI displays a “Cannot issue invoice” banner  
**And** the UI lists each blocker code and message returned by the backend.

## Scenario 4: Issuance requires step-up auth (elevation token)
**Given** I have `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT`  
**And** the backend indicates elevation is required to proceed (via policy/blockers/allowedActions)  
**When** I click “Issue Invoice” and complete step-up authentication  
**Then** the UI obtains an `elevationToken` from `POST /billing/auth/elevate`  
**And** the UI calls `POST /billing/invoices/{invoiceId}/issue` including the `elevationToken`  
**And** on success the UI reloads invoice detail and shows `status = ISSUED`.

## Scenario 5: Prevent duplicate issuance (409 conflict)
**Given** I have `billing:invoice:issue`  
**And** an invoice exists with `status = ISSUED`  
**When** I attempt to issue the invoice (via UI action or direct command)  
**Then** the backend responds 409  
**And** the UI refreshes invoice detail  
**And** the UI shows a banner indicating the invoice is already finalized  
**And** no second issuance is performed.

## Scenario 6: Unauthorized user cannot issue invoice (403)
**Given** I am authenticated and have `billing:invoice:view` but not `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT`  
**When** I view the invoice detail  
**Then** I do not see an enabled “Issue Invoice” action  
**When** I attempt to issue the invoice via the command endpoint  
**Then** I receive a 403 response  
**And** the UI shows an authorization error message.

## Scenario 7: Artifact list and secure download are permissioned
**Given** I am authenticated and have `billing:invoice:view`  
**And** an invoice exists  
**When** I have `billing:artifact:list`  
**Then** the UI can load artifacts from `GET /billing/invoices/{invoiceId}/artifacts` and display them  
**When** I also have `billing:artifact:download` and click “Download” on an artifact  
**Then** the UI requests a download token via `POST /billing/artifacts/{artifactRefId}/download-token`  
**And** the UI initiates download via `GET /billing/artifacts/download?token=...`  
**And** the UI does not log or display the token.

## Scenario 8: Transient backend failure during issuance (503/timeout)
**Given** I have `billing:invoice:issue`  
**And** an invoice exists with `status = DRAFT`  
**When** I attempt to issue the invoice and the backend returns 503 or times out  
**Then** the UI shows a non-destructive error message with retry guidance  
**And** the UI re-enables the “Issue Invoice” action after the failure  
**And** the UI does not change the invoice status optimistically.
