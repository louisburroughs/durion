## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Invoicing (Draft): Trigger Backend Tax/Fee/Total Calculation, Display Snapshot + Variance, and Block Issuance UI When Calculation Fails

### Primary Persona
Service Advisor (primary UI user) and Accountant (review/audit user) viewing a Draft invoice in POS.

### Business Value
Draft invoices show accurate, backend-authoritative totals and explainable variance before issuance, with an auditable calculation snapshot and clear UI blocking when tax basis data is incomplete—reducing disputes and preventing non-compliant issuance attempts.

---

## 2. Story Intent

### As a / I want / So that
- **As a Service Advisor**, I want draft invoice totals to recalculate when I change line items, **so that** I can confidently present accurate totals to the customer.
- **As an Accountant**, I want calculation snapshots and variance indicators visible, **so that** totals are auditable and reviewable before issuance.
- **As the System**, I want to prevent issuance UI actions when calculation is incomplete/failed, **so that** invoices cannot be issued from the UI without valid tax basis.

### In-scope
- Frontend UI behavior on **Draft invoice detail** to:
  - Trigger backend totals calculation on draft invoice create (when lines exist) and on line changes (after commit).
  - Display backend-returned totals: subtotal, tax, fees, rounding adjustment, grand total.
  - Display per-line tax amounts returned by backend.
  - Display calculation status and actionable validation errors (missing tax basis).
  - Display calculation snapshot reference (ID/timestamp) when returned.
  - Display variance vs estimate snapshot when returned by backend (amount, reason code, approval indicators if present).
  - UI-level gating: disable/hide any “Issue invoice” control on this screen when calculation is not successful.
- Moqui screen/form wiring (screens, transitions, forms/services) for the above.

### Out-of-scope
- Performing tax/fee calculations client-side.
- Defining tax/fee rules (owned by Tax Configuration Service).
- Issuing/finalizing invoices (owned by Billing domain) beyond UI gating on this screen.
- Variance approval workflow actions (only display backend-provided status/fields).
- Credit memo creation/issuance.
- GL posting, chart of accounts, posting rules, journal entry screens.

## 4. Preconditions & Dependencies

### Preconditions
- A Draft `Invoice` exists and is viewable in the POS UI.
- Invoice has zero or more `InvoiceItem` lines.

### Dependencies
- Backend provides:
  - Invoice detail read model including current totals and calculation status.
  - A command/service to calculate totals for a draft invoice and return updated totals + snapshot reference + variance (or structured validation errors).
- Backend enforces (authoritative):
  - Tax basis completeness requirements and error codes.
  - Rounding policy: HALF_UP, currency scale; round per line then sum.
  - Immutability once invoice is issued (no recalculation/editing).
  - Variance creation and any “requires approval” semantics (if applicable).

### Frontend tech dependencies
- Vue 3 + TypeScript + Quasar.
- Moqui screen framework conventions (screen paths, transitions, forms/services).

- Invoice creation flow that lands on Draft Invoice Detail.

### Screens to create/modify

  - Add a “Variance vs Estimate” panel when backend returns estimate snapshot linkage and variance data.

**Happy path**
1. User opens Draft invoice detail.
2. User adds/edits/removes an invoice line and saves/commits the change.
3. UI marks totals as “needs recalculation” and triggers recalculation (debounced).
4. UI shows in-progress state; on success, totals and per-line tax amounts update.
5. If variance exists, UI displays variance amount and reason code; snapshot reference is shown.

**Alternate paths**
- Missing tax basis: UI shows calculation failed state with actionable missing-field errors; user fixes fields and retries.
- Tax service unavailable: UI shows retriable banner; user retries later.
- Concurrency/optimistic lock: UI prompts reload and retry.
- Issued invoice: UI is read-only; no recalculation controls.

## 6. Functional Behavior

### Triggers
- **T1**: Draft invoice detail loads and invoice has ≥ 1 line item AND backend indicates totals are not current (status/flag) → UI may prompt/auto-trigger recalculation.
- **T2**: Invoice line is added/modified/removed and the change is committed (saved) on a Draft invoice → trigger recalculation (debounced).
- **T3**: User clicks “Recalculate totals” → trigger recalculation immediately.

### UI actions
- Show calculation status indicator based on backend-provided invoice calculation status/state (do not invent new states).
- Provide a manual “Recalculate totals” action when invoice is Draft and editable.
- Disable/hide any “Issue invoice” control on this screen when:
  - backend indicates calculation failed, or
  - backend indicates totals are not calculated/current, or
  - invoice is not Draft/editable.

### State changes (frontend perspective)
- On successful calculation response:
  - Update totals and per-line tax amounts from response.
  - Display snapshot reference fields if present.
  - Display variance section if variance returned.
- On failed calculation response:
  - Display failure state and errors.
  - Keep invoice editable (Draft) so user can correct tax basis fields and retry.

### Service interactions (Moqui)
- Invoice detail screen uses Moqui transitions to call backend services:
  - `transition name="loadInvoice"` → loads invoice detail context.
  - `transition name="updateInvoiceLines"` → persists line edits; returns updated invoice context and indicates totals need recalculation.
  - `transition name="recalculateTotals"` → triggers backend calculation; returns updated invoice context or structured errors.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- If backend returns missing mandatory tax basis fields, UI must:
  - Show summary: “Cannot calculate totals: missing tax basis information.”
  - Show field-level errors and line-level pointers when provided (by `invoiceItemId` or row index).
  - Keep issuance UI actions disabled/hidden on this screen until calculation succeeds.

Mandatory tax basis fields to surface when missing (backend authoritative list may include more; UI must render what backend returns):
- Invoice-level: `jurisdiction`, `pointOfSaleLocationId`
- Line-level: `taxCode`, `productType`

### Enable/disable rules
- Recalculate action enabled only when invoice is Draft/editable (backend state indicates editable).
- If invoice is Issued (or otherwise non-editable), hide/disable recalculation controls and render totals read-only.

### Visibility rules
- Show “Variance vs Estimate” only when backend returns estimate snapshot linkage and variance data (or explicit “no variance” indicator).
- Show calculation snapshot metadata only when backend returns snapshot reference fields.

### Error messaging expectations
- Validation (422): actionable, field/row-specific where possible.
- Service unavailable (503/502): non-destructive banner + retry action.
- Conflict (409): “Invoice updated elsewhere. Reload to see latest.”

## 8. Data Requirements

### Entities involved (read via backend; not authored client-side)
- `Invoice`
- `InvoiceItem`
- `CalculationSnapshot` (reference/metadata)
- `EstimateSnapshot` (reference for variance comparison)
- `Variance`

### Fields (type, required, defaults)

**Invoice (read model)**
- `invoiceId` (UUIDv7, required, read-only)
- `status` (string/enum, required, read-only; backend authoritative)
- `currencyUomId` (string, required for formatting; read-only)
- Totals (Decimal, read-only):
  - `subtotal`
  - `totalTax`
  - `totalFees`
  - `roundingAdjustment` (display even when 0.00)
  - `grandTotal`
- Calculation metadata (read-only; may be null):
  - `calculationSnapshotId` (UUIDv7)
  - `calculatedAt` (timestamp)
  - `calculationStatus` or equivalent (backend field; drives UI indicator)
- Estimate linkage (read-only; optional):
  - `estimateSnapshotId` (UUIDv7)
- Tax basis fields (editability depends on existing invoice UI contracts; UI must respect backend editability):
  - `jurisdiction` (string)
  - `pointOfSaleLocationId` (UUIDv7)

**InvoiceItem (read model)**
- `invoiceItemId` (UUIDv7, required, read-only)
- `productId` (UUIDv7/string, required, read-only or editable per existing UI)
- Tax basis fields (required for successful calculation; editability per backend):
  - `taxCode` (string)
  - `productType` (string/enum)
- Amount fields (Decimal):
  - `lineTotal` (read-only display from backend)
  - `taxAmount` (read-only; returned after calculation)

**Variance (read model; optional)**
- `varianceAmount` (Decimal, read-only)
- `varianceReasonCode` (string/enum, read-only; treat as backend enum)
- `detectedAt` (timestamp, read-only)
- Optional approval fields (read-only if present):
  - `requiresApproval` (boolean) OR `approvalStatus` (string) OR `approvedBy`/`approvedAt` (backend-provided; do not infer)

### Read-only vs editable by state/role
- Draft/editable invoice: line edits allowed per existing invoice UI; recalculation allowed.
- Issued/non-editable invoice: all fields read-only; recalculation hidden/disabled.

### Derived/calculated fields (UI-only)
- `needsRecalculation` (boolean): derived from backend calculation status/state and/or after successful line update transition.
- “Totals stale” indicator: shown when backend indicates totals not current.

## 9. Service Contracts (Frontend Perspective)

> This story must use backend-authoritative contracts. If the repo already has invoice services, wire to those; otherwise implement Moqui facade services that call the backend.

### Load/view calls
- **SVC1: Load Invoice Detail**
  - Input: `invoiceId` (UUIDv7)
  - Output: invoice header + items + totals + calculation status + optional snapshot ref + optional variance
  - Errors:
    - 403: access denied (do not reveal existence)
    - 404: not found (safe message)

### Create/update calls
- **SVC2: Update Invoice Items (Draft)**
  - Input: `invoiceId` + line mutations (add/update/remove) + optimistic lock token if used by backend
  - Output: updated invoice/items; backend indicates totals need recalculation (status/flag)
  - Errors:
    - 422: validation
    - 409: conflict/stale update

### Submit/transition calls
- **SVC3: Calculate Invoice Totals (Draft)**
  - Input: `invoiceId` (UUIDv7)
  - Output on success:
    - updated invoice totals
    - per-line `taxAmount` values
    - snapshot reference (`calculationSnapshotId`, `calculatedAt`) if available
    - variance records/fields if applicable
  - Output on failure:
    - structured error `{ errorCode, message, details? }`
    - `details` may include:
      - invoice-level missing fields
      - per-line missing fields keyed by `invoiceItemId`
  - Error handling expectations:
    - 422: missing tax basis / validation failures
    - 409: invoice not in Draft/editable state or optimistic lock conflict
    - 502/503: upstream tax service unavailable
    - 5xx: unexpected failure

### Error handling expectations (UI mapping)
- 422: show summary + inline/row errors; keep user on invoice detail.
- 409: show reload prompt; provide “Reload invoice” action; clear stale local edits if needed.
- 502/503: show retry banner; do not auto-retry.
- 403/404: show safe access/not-found screens without leaking existence.

## 10. State Model & Transitions

### Allowed states (UI-rendered)
UI must render based on backend-provided invoice state/calculation status. Minimum expected UI categories:
- Draft/editable + totals current
- Draft/editable + totals need recalculation
- Draft/editable + calculation failed
- Issued/non-editable

### Role-based transitions (frontend gating)
- Users who can edit draft invoices can trigger recalculation; backend remains authoritative for authorization.
- Issued/non-editable invoices: no edit or recalculation actions.

### UI behavior per state
- **Draft + needs recalculation**: show “Needs recalculation” indicator; allow manual recalc; auto-trigger after line commit (debounced).
- **Draft + calculated**: show totals normally; show snapshot ref; show variance if present.
- **Draft + calculation failed**: show blocking error panel; highlight missing fields; allow retry after fixes.
- **Issued/non-editable**: read-only; show totals and snapshot ref if present; hide recalc.

## 11. Alternate / Error Flows

### Validation failures (missing tax basis)
1. User triggers recalculation.
2. Backend returns 422 with `errorCode` and `details` listing missing fields (invoice-level and/or per-line).
3. UI:
   - Shows error summary and inline/row errors.
   - Keeps totals marked stale/not calculated.
   - Keeps issuance UI actions disabled/hidden on this screen.

### Concurrency conflicts (409)
- On update or calculate returning 409:
  - UI shows conflict message and “Reload invoice”.
  - After reload, user can reapply edits and retry recalculation.

### Unauthorized access (403)
- On load: show access denied.
- On calculate/update: show access denied; keep screen stable; do not reveal additional record details.

### Empty states
- Draft invoice with zero lines:
  - Totals panel shows “No line items” and does not auto-trigger calculation.
  - Manual recalc disabled until at least one line exists.

## 12. Acceptance Criteria

### Scenario 1: Calculate totals for a standard taxable invoice
**Given** a Draft invoice exists with one line item and required tax basis fields present  
**When** the user commits a line change and recalculation is triggered  
**Then** the UI calls the Calculate Invoice Totals service for that invoice  
**And** the UI renders totals exactly as returned by backend including `roundingAdjustment` (even if 0.00)  
**And** the UI shows the invoice as “calculated/current” based on backend status.

### Scenario 2: Mixed-tax invoice displays correct aggregated totals and per-line taxes
**Given** a Draft invoice exists with two line items where backend returns different `taxAmount` values per line  
**When** totals are recalculated successfully  
**Then** the UI displays invoice-level totals from backend  
**And** the UI displays per-line `taxAmount` from backend for each line  
**And** the UI does not treat any client-side recomputation as authoritative.

### Scenario 3: Variance is surfaced when estimate snapshot differs
**Given** a Draft invoice is linked to an `estimateSnapshotId`  
**And** recalculation returns variance data including `varianceAmount` and `varianceReasonCode`  
**When** the invoice detail is rendered after calculation  
**Then** the UI displays a “Variance vs Estimate” section  
**And** it shows `varianceAmount`, `varianceReasonCode`, and `detectedAt` as returned by backend  
**And** if backend returns approval-related fields (e.g., `requiresApproval` or `approvedAt`), the UI displays them read-only without inference.

### Scenario 4: Missing tax basis blocks calculation and issuance UI on this screen
**Given** a Draft invoice exists where backend will report missing tax basis (e.g., a line missing `taxCode`)  
**When** totals calculation is triggered  
**Then** the UI displays an error summary “Cannot calculate totals: missing tax basis information.”  
**And** the UI highlights the missing field(s) using backend `details`  
**And** the UI disables/hides any “Issue invoice” action on this screen until calculation succeeds.

### Scenario 5: Tax service unavailable shows retriable error
**Given** a Draft invoice exists with complete tax basis fields  
**When** totals calculation returns 502 or 503  
**Then** the UI shows a non-destructive banner indicating calculation could not be completed  
**And** the UI provides a “Retry calculation” action  
**And** the UI keeps totals marked as not current and keeps issuance UI actions disabled/hidden on this screen.

### Scenario 6: Issued/non-editable invoice is immutable in UI
**Given** an invoice is non-editable (e.g., Issued)  
**When** the invoice detail screen is opened  
**Then** the UI does not show invoice-line editing controls  
**And** the UI does not show “Recalculate totals” controls  
**And** the UI displays totals and snapshot reference fields (if present) as read-only.
