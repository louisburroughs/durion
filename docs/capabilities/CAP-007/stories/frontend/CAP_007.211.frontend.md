## Issue Body

## 1. Story Header

### Title
[FRONTEND] Invoicing: Display Traceability Snapshot + Artifacts and Enforce Issuance Blockers (Policy-Driven)

### Primary Persona
Billing Specialist (authorized POS user) / Billing Administrator

### Business Value
Ensure every invoice is defensible and auditable by (a) surfacing immutable traceability references (work order, estimate/version, approvals/artifacts) captured on the invoice and (b) preventing issuance when backend policy indicates traceability is incomplete—reducing disputes, compliance risk, and issuance rework.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Billing Specialist  
- **I want** the invoice UI to show the invoice’s immutable traceability snapshot (including links/IDs and approval artifacts) and to enforce issuance gating using backend-provided blockers  
- **So that** I can verify the invoice is tied to approved scope and executed work before issuing and collecting payment.

### In-scope
- Add a **Traceability** section to invoice detail screens (Draft + Issued) showing immutable traceability snapshot fields from Billing (BILL-DEC-004).
- Render **issuancePolicy** and **issuanceBlockers[]** (when status is `DRAFT`) and use them to gate the Issue action (BILL-DEC-003).
- List and securely download approval artifacts from invoice context using Billing artifact contracts (BILL-DEC-005).
- Permission-gate traceability panel and artifact actions using canonical permission strings (BILL-DEC-008).
- Handle error/empty states deterministically without guessing policy requirements.

### Out-of-scope
- Generating or mutating the traceability snapshot (backend responsibility; snapshot is immutable) (BILL-DEC-004).
- Editing work orders, estimates, approvals, or artifacts in the Billing UI.
- Customer-facing invoice document formatting/configuration (PDF/email content) beyond displaying traceability in internal UI.
- Accounting/GL posting logic (may display sanitized posting summaries if present, but no posting workflows).

## 3. Actors & Stakeholders
- **Billing Specialist (primary user):** Reviews traceability and issues invoice.
- **Billing Administrator (privileged user):** Can access artifacts and resolve exceptions; may have broader permissions.
- **Auditor (stakeholder):** Requires immutable lineage and access logs for artifacts.
- **System (Moqui UI + Billing services):** Loads invoice, renders blockers/policy, performs issuance command, retrieves artifacts.
- **Upstream systems (stakeholder dependencies):**
  - Work Execution owns Work Order/Estimate/Approval records; Billing stores references only (SoR boundary).
  - Artifact storage service holds artifact content; Billing mediates access via secure download contract.

- User is authenticated.
- Authorization is enforced server-side; UI uses canonical permission strings for visibility/enablement (BILL-DEC-008).
- Billing backend provides:
  - `GET /billing/invoices/{invoiceId}` including `traceability` and, for `DRAFT`, `issuancePolicy` + `issuanceBlockers[]` (BILL-DEC-003, BILL-DEC-004).
  - `POST /billing/invoices/{invoiceId}/issue` which enforces policy and returns structured 422 blockers and 409 conflicts (BILL-DEC-001, BILL-DEC-003).
  - `GET /billing/invoices/{invoiceId}/artifacts` and secure download flow via token or signed URL when authorized (BILL-DEC-005).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From invoice list: open Invoice Detail.
- From Work Order context (if present): open invoice by work order → then Invoice Detail.

### Screens to create/modify
- **Modify**: Invoice detail screen (Draft + Issued views) to add a **Traceability** panel and **Artifacts** sub-panel.
- **Modify**: Issue action area/modal on invoice detail to:
  - show blockers (from invoice detail)
  - require elevation token input only when backend indicates it is required for issuance (BILL-DEC-010)
- **Optional**: Artifact download flow may be implemented as:
  - direct download action (token request then download), or
  - a small dialog showing artifact metadata + “Download” action.

> Screen paths must follow repo conventions; do not embed hardcoded routes in data. Use link metadata resolution (BILL-DEC-016).

### Navigation context
Invoice Detail includes:
- invoice summary (existing)
- **Traceability** panel (new)
- **Artifacts** list (new; loads asynchronously)
- Issue action area (existing/updated), gated by status and blockers

### User workflows (happy + alternate)

**Happy path: view traceability + issue**
1. User opens a `DRAFT` invoice.
2. UI shows Traceability snapshot fields (read-only) and any deep-linkable references.
3. UI shows issuance blockers (if any). If none, Issue action is enabled.
4. User clicks “Issue Invoice”.
5. UI calls issue endpoint; on success refreshes invoice detail and shows `ISSUED` state with issuance metadata.

**Alternate: blockers present**
- Invoice detail shows `issuanceBlockers[]` with codes/messages.

**Alternate: artifacts unavailable**
- Artifact list call fails (403/503/etc.). UI shows a non-blocking error state for artifacts list.
- Issuance remains governed by `issuanceBlockers[]` and/or issuance attempt response; UI must not infer completeness from artifact list availability.

## 6. Functional Behavior

### Triggers
- Invoice Detail screen loads or refreshes.
- User expands Traceability panel.
- User opens Artifacts sub-panel (or it auto-loads after invoice detail).
- User clicks “Download” on an artifact.
- User clicks “Issue Invoice”.

### UI actions
- Load invoice detail by `invoiceId` (or by `workOrderId` then navigate to invoiceId).
- Render traceability snapshot fields and any link metadata targets.
- Render issuance policy summary (if provided) and blockers list (for `DRAFT`).
- Load artifact list asynchronously.
- Download artifact via secure token flow (preferred) or signed URL flow (if returned and authorized).
- Issue invoice; if elevation required, obtain elevation token first and include in request (BILL-DEC-010).

### State changes
- Invoice status changes only via backend:
  - `DRAFT` → `ISSUED` on successful issuance.
- Traceability snapshot is immutable and never edited client-side (BILL-DEC-004).

### Service interactions
- Invoice detail: `GET /billing/invoices/{invoiceId}`
- Invoice by work order (optional entry): `GET /billing/invoices/by-work-order/{workOrderId}`
- Artifact list: `GET /billing/invoices/{invoiceId}/artifacts`
- Artifact download:
  - Preferred: `POST /billing/artifacts/{artifactRefId}/download-token` then `GET /billing/artifacts/download?token=...` (BILL-DEC-005)
  - Optional: signed URL returned only when explicitly requested and authorized; never log it (BILL-DEC-005)
- Issue invoice: `POST /billing/invoices/{invoiceId}/issue`
- Elevation (only when required by backend policy for the action): `POST /billing/auth/elevate` → `elevationToken` (BILL-DEC-010)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Traceability snapshot fields are **display-only** and must never be editable:
  - `traceability.sourceWorkOrderId` (required)
  - `traceability.sourceBillableScopeSnapshotId` (required)
  - `traceability.sourceSchemaVersion` (required)
  - `traceability.sourceEstimateId` (optional)
  - `traceability.sourceEstimateVersionId` (optional; preferred when present)
  - `traceability.sourceApprovalIds[]` (optional; may be required by policy)
  - `traceability.artifactRefs[]` (optional references)
  (BILL-DEC-004)
- Issuance gating:
  - UI must use backend-provided `issuanceBlockers[]` to disable issuance in `DRAFT` (BILL-DEC-003).
  - UI must not guess which traceability identifiers are required; policy is tenant/account configurable and expressed via blockers (BILL-DEC-003).
  - Issuance attempt must handle:
    - 422 with blocker codes/messages
    - 409 for state conflicts (already issued/paid/void)
    - 403 for permission denial
- Artifact access:
  - UI must not attempt to construct storage URLs; only use Billing secure download contract (BILL-DEC-005).
  - UI must never log signed URLs, download tokens, or artifact content (BILL-DEC-005, BILL-DEC-015).

### Enable/disable rules
- Traceability panel visibility:
  - Visible only if user has `billing:traceability:view`.
  - If user lacks permission, show a panel-level “Insufficient permissions” placeholder (do not leak IDs).
- Artifact list and download:
  - List requires `billing:artifact:list`.
  - Download requires `billing:artifact:download`.
  - If list permission missing, hide artifacts sub-panel entirely or show “Not authorized” (no calls).
- “Issue Invoice” action:
  - Visible/enabled only when:
    - `invoice.status == DRAFT`
    - user has `billing:invoice:issue`
    - `issuanceBlockers[]` is empty (or `allowedActions[]` includes ISSUE if present)
  - If blockers indicate elevation required, UI must require elevation token before calling issue (BILL-DEC-010).

### Visibility rules
- Link rendering:
  - If backend provides link metadata `{targetDomain, targetType, targetId}`, UI renders as a navigable link only if:
    - a route exists for that target in the frontend router, and
    - user is authorized for the destination.
  - Otherwise render as copy-only identifier (BILL-DEC-016).

### Error messaging expectations
- Blockers:
  - Display blocker `code` and `text/message` from backend; do not rephrase into policy guesses.
  - Provide a “Copy details” action that copies blocker codes + correlationId (no PII).
- Artifact errors:
  - 403: “You are not authorized to view/download artifacts.”
  - 404: “Artifact not found or no longer available.”
  - 503/timeout: “Artifacts service unavailable. Retry.”
- Issuance errors:
  - 422: show blockers list; keep invoice in `DRAFT`.
  - 409: show “Invoice state changed. Refreshing…” then reload.

- All traceability fields: read-only always (BILL-DEC-004).
- Artifact metadata: read-only.

This derived field must not override backend enforcement.

## 9. Service Contracts (Frontend Perspective)

> Moqui service names are implementation details; the following HTTP semantics and payload shapes are normative per Billing domain guide.

### Load/view calls
1) **Get Invoice Detail**
- `GET /billing/invoices/{invoiceId}`
- Success: returns invoice detail including `traceability`; for `DRAFT` includes `issuancePolicy` + `issuanceBlockers[]`.
- Errors:
  - 403 → show access denied screen
  - 404 → show not found screen
  - 503/timeouts → show retryable error; do not clear cached view state

2) **Get Invoice by Work Order (optional entry path)**
- `GET /billing/invoices/by-work-order/{workOrderId}`
- Success: returns invoice summary or full invoice; UI navigates to invoice detail by `invoiceId`.
- Errors:
  - 404 → show “No invoice found for this work order”
  - 403 → access denied

3) **List Artifacts for Invoice Context**
- `GET /billing/invoices/{invoiceId}/artifacts`
- Success: returns `artifacts[]` metadata.
- Errors:
  - 403 → show “Not authorized to view artifacts” and do not show download actions
  - 404 → show “No artifacts found” (only if endpoint uses 404 for none; otherwise treat empty list as none)
  - 503/timeouts → show retry UI; do not claim “no artifacts exist”

### Submit/transition calls
4) **Issue Invoice**
- `POST /billing/invoices/{invoiceId}/issue`
- Request: `{ "elevationToken": "string?" }`
  - Include `elevationToken` only when UI has obtained it and backend indicates it is required.
- Success: returns updated invoice (recommended) or 200/204; UI must refresh invoice detail.
- Errors:
  - 422 → structured blockers/validation errors; render list; remain in `DRAFT`
  - 409 → conflict (already issued/paid/void or version mismatch); force refresh
  - 403 → show “Not authorized to issue invoices”
  - 503 → show retryable error; prevent double-submit via UI busy state

5) **Elevation Token (step-up auth)**
- `POST /billing/auth/elevate`
- Request: manager credentials per auth system (UI must not log/store raw credentials) (BILL-DEC-010)
- Response: `{ elevationToken, expiresAt }`
- Errors:
  - 401/403 → show “Elevation failed” without revealing details

### Error handling expectations
- All calls should propagate W3C trace headers (`traceparent`, `tracestate`) when supported (BILL-DEC-015).
- UI should display `correlationId` from error responses when present.
- Never log: artifact signed URLs/tokens, credentials, PII (BILL-DEC-005, BILL-DEC-015).

## 10. State Model & Transitions

### Allowed states
InvoiceStatus (BILL-DEC-001):
- `DRAFT`
- `ISSUED`
- `PAID`
- `VOID`
- Optional: `ERROR` (only if backend returns it; UI must treat unknown enums as unknown state and prompt refresh/support)

### Role-based transitions
- `DRAFT` → `ISSUED`
  - Requires permission `billing:invoice:issue` (BILL-DEC-008)
  - Requires backend issuance policy satisfied; blockers must be empty (BILL-DEC-003)
  - May require elevation token depending on policy/blockers (BILL-DEC-010)

### UI behavior per state
- **DRAFT**
  - Show Traceability panel (if permitted)
  - Show issuance blockers list (if any)
  - Enable Issue action only when permitted and blockers empty
- **ISSUED/PAID/VOID**
  - Show Traceability panel (if permitted)
  - Hide Issue action
  - Artifacts remain viewable/downloadable if permitted
- **Unknown/ERROR**
  - Show read-only invoice with warning “Unknown invoice state”; disable issuance; provide refresh

## 11. Alternate / Error Flows

### Validation failures (issuance)
- Backend returns 422 with blocker codes (e.g., `MISSING_APPROVAL`, `MISSING_ESTIMATE_VERSION`) (BILL-DEC-003).
- UI displays blockers and keeps invoice in `DRAFT`.
- If elevation is required and missing/expired, backend returns 422/403; UI prompts to re-auth and retry.

### Concurrency conflicts
- Backend returns 409 on issuance due to state change.
- UI refreshes invoice detail and updates available actions accordingly.

### Unauthorized access
- Missing `billing:traceability:view`:
  - Do not call artifact endpoints from traceability panel.
  - Show “Insufficient permissions” placeholder for traceability.
- Missing `billing:artifact:list` or `billing:artifact:download`:
  - Hide list or disable download actions accordingly.
- Missing `billing:invoice:issue`:
  - Hide/disable Issue action; backend still enforces.

### Empty states
- Optional traceability fields absent:
  - Show “Not provided” for estimate/version and approvals.
- Artifact list empty:
  - Show “No artifacts available for this invoice.”
- Artifact list fails:
  - Show retryable error; do not infer traceability completeness.

## 12. Acceptance Criteria

### Scenario 1: Traceability panel shows immutable snapshot fields
**Given** I am authenticated  
**And** I have permission `billing:traceability:view`  
**And** an invoice exists with a `traceability` snapshot  
**When** I open the Invoice Detail screen  
**Then** I see `traceability.sourceWorkOrderId`, `traceability.sourceBillableScopeSnapshotId`, and `traceability.sourceSchemaVersion` as read-only values  
**And** I see `traceability.sourceEstimateId` and `traceability.sourceEstimateVersionId` if present  
**And** I see `traceability.sourceApprovalIds[]` if present  
**And** there are no editable inputs for any traceability fields.

### Scenario 2: Draft invoice shows issuance blockers and disables Issue action
**Given** I have permission `billing:invoice:issue`  
**And** an invoice is in `DRAFT`  
**And** the invoice detail response includes `issuanceBlockers[]` with at least one `severity=ERROR` item  
**When** I view the invoice detail  
**Then** the Issue action is disabled  
**And** I see the blockers list with backend-provided `code` and `text`.

### Scenario 3: Issuance attempt returns 422 blockers and UI renders them
**Given** I have permission `billing:invoice:issue`  
**And** an invoice is in `DRAFT`  
**When** I click “Issue Invoice”  
**And** the backend responds with HTTP 422 containing structured blockers  
**Then** the invoice remains in `DRAFT`  
**And** the UI displays the blocker codes/messages returned by the backend  
**And** the UI displays the backend `correlationId` if provided.

### Scenario 4: Successful issuance refreshes state and preserves traceability visibility
**Given** I have permission `billing:invoice:issue`  
**And** an invoice is in `DRAFT`  
**And** `issuanceBlockers[]` is empty  
**When** I issue the invoice  
**Then** the UI calls `POST /billing/invoices/{invoiceId}/issue`  
**And** on success the UI refreshes invoice detail  
**And** the invoice status is `ISSUED`  
**And** the Traceability panel still shows the same snapshot identifiers read-only  
**And** the Issue action is no longer available.

### Scenario 5: Artifact list is permission-gated and does not leak data
**Given** an invoice exists  
**And** I do not have permission `billing:artifact:list`  
**When** I open the invoice detail  
**Then** the UI does not call `GET /billing/invoices/{invoiceId}/artifacts`  
**And** I do not see artifact metadata or download actions.

### Scenario 6: Artifact download uses secure token flow and never logs secrets
**Given** I have permissions `billing:artifact:list` and `billing:artifact:download`  
**And** the artifact list returns an item with `artifactRefId`  
**When** I click “Download”  
**Then** the UI requests a download token via `POST /billing/artifacts/{artifactRefId}/download-token` (or uses an explicitly returned signed URL when authorized)  
**And** the UI initiates the download  
**And** the UI does not log or persist the token/signed URL.

### Scenario 7: Artifact list transient failure is retryable and does not imply absence
**Given** I have permission `billing:artifact:list`  
**When** `GET /billing/invoices/{invoiceId}/artifacts` fails with HTTP 503  
**Then** the UI shows a retryable error state for artifacts  
**And** the UI does not display “No artifacts exist”  
**And** issuance gating remains based on `issuanceBlockers[]` and/or issuance attempt response.

### Scenario 8: Concurrency conflict on issuance forces refresh
**Given** I have an invoice detail open for an invoice in `DRAFT`  
**And** another user issues the invoice  
**When** I attempt to issue the invoice  
**Then** the backend responds with HTTP 409  
**And** the UI refreshes invoice detail  
**And** I see the invoice in `ISSUED` state with Issue action removed.
