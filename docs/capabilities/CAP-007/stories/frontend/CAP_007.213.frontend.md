## Issue Body

## Title
[FRONTEND] Invoicing: Generate Draft Invoice from Invoice-Ready Completed Work Order

## Primary Persona
Accounts Receivable (AR) Clerk (Back Office)

**Persona Metadata**
- `primary_persona`: `Accounts Receivable (AR) Clerk (Back Office)`
- `canonical_persona`: `Accounting Associate`
- `persona_family`: `Accounting Associate`
- `actor_type`: `human`

## Business Value
Create an auditable, deterministic Draft Invoice from an invoice-ready Work Order without manual re-entry, ensuring all billable items and traceability links are captured consistently for downstream issuance and payment.

---

# 2. Story Intent

## As a / I want / So that
- **As an** AR Clerk  
- **I want** to generate a **DRAFT** invoice from a single **Completed** Work Order that is **invoiceReady=true**  
- **So that** I can review billing-calculated totals and traceability before issuing the invoice.

## In-scope
- User-initiated UI action “Create Invoice” from a Work Order context (Completed + invoiceReady)
- Frontend integration to Billing draft creation command (idempotent by `workOrderId`) (BILL-DEC-002)
- Display of resulting invoice detail (header, line items, totals, traceability snapshot, issuance blockers/policy when DRAFT) (BILL-DEC-003, BILL-DEC-004)
- Deterministic handling of backend errors (409/422/403/404/503) with correlationId display for support (BILL-DEC-014, BILL-DEC-015)
- Deep-link handling using backend link metadata (no hardcoded routes) (BILL-DEC-016)

## Out-of-scope
- Issuing/finalizing invoices (DRAFT → ISSUED) (separate story)
- Taking payments, refunds, chargebacks
- Editing invoice header/line items/totals (immutable snapshot-derived composition) (BILL-DEC-002)
- Credit notes / rebill / invoice corrections
- BillingRules management UI
- Tax rule configuration, payment terms configuration

# 3. Actors & Stakeholders
- **Primary Actor:** AR Clerk
- **Secondary Actors:** Service Advisor (view-only stakeholder), Accounting (downstream consumer), Support/Finance Admin (error detail viewers)
- **System Actors:**

  - Work Execution service (Work Order completion + `invoiceReady` + BillableScopeSnapshot generation; Billing consumes upstream snapshot)  
  - CRM (customer account master data; Billing validates completeness server-side)

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated in the POS/backoffice UI.
- User has permission `billing:invoice:create-draft` (BILL-DEC-008).
- A Work Order exists and is viewable by the user.
- Work Order is **Completed** and `invoiceReady=true` (authoritative from Work Execution; Billing enforces as well) (BILL-DEC-002).

## Dependencies
- Billing draft creation endpoint exists and is idempotent by `workOrderId` (BILL-DEC-002):
  - `POST /billing/invoices/draft` with `{ workOrderId }`
  - Returns an invoice snapshot (preferred) or at minimum `{invoiceId}`; UI must support either.
  - 409 conflict with deterministic `reasonCode` when not invoice-ready or invoice already in non-draft terminal state.
  - 422 with structured missing fields when billing data incomplete.
  - 503 when upstream dependencies unavailable.
- Billing invoice detail endpoint exists:
  - `GET /billing/invoices/{invoiceId}` includes line items, totals, traceability snapshot, and for DRAFT includes `issuancePolicy` + `issuanceBlockers[]` (BILL-DEC-003, BILL-DEC-004).
- Work Order detail screen provides `workOrderId`, completion status, and `invoiceReady` boolean.

# 5. UX Summary (Moqui-Oriented)

## Entry points
- Work Order detail screen (Back Office) for a **Completed** Work Order.

## Screens to create/modify
1. **Modify:** Work Order detail screen (existing in repo)
   - Add a **Create Invoice** action.
   - Action is user-initiated only (no auto-create) (BILL-DEC-002).
2. **Create/Modify:** Billing Invoice Detail screen
   - Render invoice header, totals, line items, traceability snapshot.
   - Render issuance readiness panel for DRAFT using `issuancePolicy` + `issuanceBlockers[]` (read-only in this story) (BILL-DEC-003).

> Moqui routing note (BILL-DEC-016): any cross-domain navigation (to Work Order, Customer Account, Estimate, Approvals) must be driven by backend-provided link metadata `{targetDomain,targetType,targetId}` when present; do not hardcode URLs in data.

## Navigation context
- From Work Order Detail → Create Invoice → navigate to Invoice Detail for returned `invoiceId`.
- Invoice Detail includes a “Back to Work Order” navigation using invoice’s `workOrderId` (or link metadata if provided).

## User workflows (happy + alternate paths)

### Happy path
1. AR Clerk opens a Completed Work Order with `invoiceReady=true`.
2. Clicks **Create Invoice**.
3. UI disables the action and shows in-flight progress.
4. On success, UI navigates to Invoice Detail and renders the invoice snapshot.

### Alternate path: idempotent existing DRAFT
1. AR Clerk clicks **Create Invoice** for a Work Order that already has a DRAFT invoice.
2. Backend returns success with the existing invoice (or invoiceId).
3. UI navigates to Invoice Detail and shows a non-blocking message: “Draft invoice already exists; opened existing draft.”

### Alternate path: invoice already ISSUED/PAID/VOID (409)
- UI stays on Work Order screen and shows backend-provided message.
- If backend includes a link metadata to the existing invoice, UI may offer “Open existing invoice” (link metadata resolved by router); otherwise show invoice identifier if provided.

### Alternate path: missing billing data (422)
- UI stays on Work Order screen and shows a “Cannot create invoice” panel listing `missingFields[]`.
- If CRM route exists and link metadata is provided, offer navigation; otherwise provide copy-only field names.

### Alternate path: service unavailable (503)
- UI stays on Work Order screen, preserves state, and offers retry.

# 6. Functional Behavior

## Triggers
- User clicks “Create Invoice” on Work Order detail.

## UI actions
- Validate `workOrderId` exists in context before calling backend.
- Disable the Create Invoice control while request is in-flight (prevents accidental double-submit; backend remains authoritative).
- Call `POST /billing/invoices/draft` with `{workOrderId}`.
- On success:
  - If response includes full invoice snapshot: route to Invoice Detail and render immediately; optionally refresh via `GET /billing/invoices/{invoiceId}` to ensure latest.
  - If response includes only `invoiceId`: route to Invoice Detail and load via `GET /billing/invoices/{invoiceId}`.
- On handled failure:
  - Show error banner/panel and remain on Work Order screen.

## State changes (frontend-visible)
- Work Order screen:
  - Create Invoice button: enabled → disabled (in-flight) → enabled (on failure) or remains enabled (after success, user navigates away).
- Invoice Detail screen:
  - Renders invoice status and immutable fields; no edit affordances in this story.

## Service interactions
- Billing:
  - Create draft invoice (idempotent) (BILL-DEC-002)
  - Load invoice detail (BILL-DEC-003, BILL-DEC-004)
- WorkExec:
  - Work Order detail already loaded; UI uses `invoiceReady` to enable/disable action, but backend is authoritative.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- UI must not call create-draft without a `workOrderId`.
- UI must treat invoice composition as immutable for this flow:
  - No editing of line items, totals, traceability snapshot (BILL-DEC-002, BILL-DEC-004).

## Enable/disable rules
- **Create Invoice** action:
  - **Visible** when user has `billing:invoice:create-draft` and Work Order is viewable.
  - **Enabled** only when Work Order indicates `invoiceReady=true` and Work Order is Completed.
  - If Work Order readiness fields are unavailable (not loaded / missing), keep action **disabled** with helper text “Invoice readiness unavailable; refresh” (UI ergonomics only; backend still enforces) (BILL-DEC-002).

## Visibility rules
- Invoice Detail must display:
  - `status` using canonical enum values from backend: `DRAFT`, `ISSUED`, `PAID`, `VOID` (optional `ERROR` only if backend returns it) (BILL-DEC-001).
  - Traceability snapshot fields (read-only) (BILL-DEC-004):
    - `traceability.sourceWorkOrderId`
    - `traceability.sourceBillableScopeSnapshotId`
    - `traceability.sourceSchemaVersion`
    - `traceability.sourceEstimateId` (optional)
    - `traceability.sourceEstimateVersionId` (optional, preferred when present)
    - `traceability.sourceApprovalIds[]` (optional)
  - For DRAFT invoices: `issuancePolicy` and `issuanceBlockers[]` panel (read-only in this story) (BILL-DEC-003).

## Error messaging expectations
- Use backend `message` as primary text; show stable codes when provided.
- 409: show banner with backend message; if `reasonCode` present, include it in a collapsible “Details” section for support.
- 422: show “Cannot create invoice” panel and list `missingFields[]` exactly as returned.
- 403: show “Not authorized to create draft invoices.”
- 503: show “Service unavailable; try again.” and provide retry.
- Include `correlationId` (if provided) in an expandable “Support details” section; do not show stack traces (BILL-DEC-014).

# 9. Service Contracts (Frontend Perspective)

## Load/view calls
- Work Order detail (existing): must provide `workOrderId`, completion status, and `invoiceReady` boolean.
- Invoice detail:
  - `GET /billing/invoices/{invoiceId}`
  - Must include traceability snapshot and totals; for DRAFT must include `issuancePolicy` and `issuanceBlockers[]` (BILL-DEC-003, BILL-DEC-004).

## Create/update calls
- Create Draft Invoice from Work Order (idempotent) (BILL-DEC-002)
  - `POST /billing/invoices/draft`
  - Request: `{ "workOrderId": "uuidv7" }`
  - Response: preferred full invoice snapshot; minimum `{ "invoiceId": "uuidv7" }`
  - Success semantics:
    - 200 OK when returning existing DRAFT (idempotent)
    - 201 Created or 200 OK when newly created (backend choice; UI must accept either)

## Submit/transition calls
- None in this story.

## Error handling expectations
- 409 Conflict:
  - Response includes `{errorCode, message, reasonCode}` (reasonCode deterministic) (BILL-DEC-002)
  - UI shows message and remains on Work Order screen.
- 422 Unprocessable Entity:
  - Response includes `{errorCode, message, missingFields[]}` for billing data completeness issues.
  - UI lists missing fields.
- 403 Forbidden:
  - UI shows not authorized; do not retry automatically.
- 404 Not Found:
  - If Work Order or invoice not accessible, show “Not found or you don’t have access.”
- 503 Service Unavailable:
  - UI offers retry; preserve state.
- Observability:
  - If response includes `correlationId`, display in support details.
  - Propagate W3C Trace Context headers (`traceparent`, optional `tracestate`) on requests (BILL-DEC-015).

# 10. State Model & Transitions

## Allowed states (InvoiceStatus) (BILL-DEC-001)
- `DRAFT`
- `ISSUED`
- `PAID`
- `VOID`
- Optional: `ERROR` (only if backend returns it; UI must not invent it)

## Role-based transitions
- This story implements only the creation of a DRAFT invoice:
  - Requires permission `billing:invoice:create-draft` (BILL-DEC-008).
- No issuance/void/payment transitions are implemented here.

## UI behavior per state
- `DRAFT`: show “Draft” status; show issuance readiness panel (`issuancePolicy` + `issuanceBlockers[]`) read-only.
- `ISSUED`/`PAID`/`VOID`: show status; do not show “Create Invoice” from Work Order if invoice already exists in these states (backend enforces via 409; UI may also hide/disable if it can detect).
- Unknown status enum: show “Unknown status; refresh or contact support” and include `invoiceId` in support details.

# 11. Alternate / Error Flows

## Validation failures (422)
- Backend returns missing billing data:
  - UI shows missing fields list exactly as returned.
  - UI provides guidance: “Update customer billing profile and retry.”
  - If backend provides link metadata to customer account, render navigation; otherwise copy-only.

## Concurrency conflicts / idempotency
- Double click / network retry:
  - UI in-flight guard prevents local duplicates.
  - Backend idempotency ensures same DRAFT returned for same `workOrderId` (BILL-DEC-002).
- Two users:
  - If one creates DRAFT first, the other receives existing DRAFT and is routed to it.

## Unauthorized access (401/403)
- If permission missing:
  - Do not render Create Invoice action when permission is known from session.
  - If backend returns 403 anyway, show error and keep action hidden on subsequent renders.

## Empty states
- Invoice detail loads with `items[]` empty:
  - Render invoice header/totals if present.
  - Show anomaly panel: “No invoice items found; contact support” with `invoiceId` and `workOrderId`.
  - Do not allow editing to “fix” items in UI.

# 12. Acceptance Criteria

## Scenario 1: Successful Draft Invoice Creation
**Given** I am authenticated and have permission `billing:invoice:create-draft`  
**And** I am viewing a Work Order in a Completed state with `invoiceReady=true`  
**When** I click “Create Invoice”  
**Then** the UI sends `POST /billing/invoices/draft` with `{workOrderId}`  
**And** the UI navigates to Invoice Detail for the returned `invoiceId`  
**And** the Invoice Detail displays `status=DRAFT`, `workOrderId`, and `customerAccountId`  
**And** the Invoice Detail displays at least one line item or shows the “No invoice items found” anomaly panel  
**And** the Invoice Detail displays backend totals including `subtotal`, `taxTotal`, and `grandTotal`.

## Scenario 2: Idempotent Return When Draft Already Exists
**Given** I have permission `billing:invoice:create-draft`  
**And** a DRAFT invoice already exists for the Work Order  
**When** I click “Create Invoice”  
**Then** the UI receives a success response containing the existing `invoiceId`  
**And** the UI navigates to Invoice Detail for that `invoiceId`  
**And** the UI shows a non-blocking message indicating an existing draft was opened.

## Scenario 3: Block When Work Order Not Invoice-Ready (409)
**Given** I have permission `billing:invoice:create-draft`  
**And** I am viewing a Work Order with `invoiceReady=false`  
**When** I attempt to create an invoice  
**Then** the UI does not navigate away from the Work Order screen  
**And** the UI shows an error banner based on the 409 response message  
**And** the UI includes the backend `reasonCode` in support details when provided.

## Scenario 4: Block When Invoice Already Exists in Non-Draft State (409)
**Given** I have permission `billing:invoice:create-draft`  
**And** the Work Order already has an invoice in status `ISSUED` or `PAID` or `VOID`  
**When** I click “Create Invoice”  
**Then** the UI receives a 409 Conflict  
**And** the UI shows an error indicating a new draft cannot be created for this Work Order  
**And** the UI does not create or navigate to a new invoice.

## Scenario 5: Missing Customer Billing Data (422)
**Given** I have permission `billing:invoice:create-draft`  
**And** I am viewing a Completed Work Order with `invoiceReady=true`  
**And** required billing data is missing  
**When** I click “Create Invoice”  
**Then** the UI receives a 422 response containing `missingFields[]`  
**And** the UI displays “Cannot create invoice”  
**And** the UI lists each missing field returned by the API.

## Scenario 6: Service Unavailable (503)
**Given** I have permission `billing:invoice:create-draft`  
**And** I am viewing a Completed Work Order with `invoiceReady=true`  
**When** I click “Create Invoice” and the backend returns 503  
**Then** the UI remains on the Work Order screen  
**And** the UI displays a retry option  
**And** the UI preserves the Work Order context and does not lose page state.

## Scenario 7: Permission Denied (403)
**Given** I am authenticated but do not have permission `billing:invoice:create-draft`  
**When** I view a Work Order detail screen  
**Then** the UI does not show the “Create Invoice” action  
**And** if I still trigger the action and receive 403, the UI shows “Not authorized to create draft invoices.”
