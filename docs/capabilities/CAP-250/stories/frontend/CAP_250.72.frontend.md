## Issue Body

## Title
[FRONTEND] Payment Reversal: Void Authorization or Refund Captured Payment (with approvals, reasons, and async refund status)

## Primary Persona
Store Manager

**Persona Metadata**
- `primary_persona`: `Store Manager`
- `canonical_persona`: `Location Manager`
- `persona_family`: `Location Management`
- `actor_type`: `human`

## Business Value
Enable safe, permissioned correction of payment mistakes (void auths / refund captured payments), with complete auditability and accurate invoice/payment status updates to prevent financial discrepancies and support reconciliation.

---

# 2. Story Intent

## As a / I want / So that
As a **Store Manager**, I want to **void authorized payments** or **refund captured/settled payments** (including partial refunds where allowed), so that payment corrections are handled safely with proper approvals, reasons, and traceable outcomes.

## In-scope
- UI to initiate **Void** on eligible payments in **AUTHORIZED** state.
- UI to initiate **Refund** on eligible payments in **CAPTURED/SETTLED** state (full and partial per policy).
- Capture **reason code** (+ notes for OTHER and for certain tiers), and show required **approvals** if the amount requires it.
- Display and update **payment reversal status** and **invoice status** (including refund pending lifecycle).
- Display reversal history (void/refund records) with audit metadata (actor, approver, timestamps, reason, notes).
- Handle common error cases and provide actionable messages.

## Out-of-scope
- Implementing payment gateway logic, webhooks, or backend reconciliation.
- Defining or changing tax/accounting posting behavior (frontend only reflects backend status).
- Creating new business policy beyond what backend already decided (e.g., settlement timing rules beyond exposed eligibility).
- Receipt generation/reprint UX unless explicitly returned by backend contract.

# 3. Actors & Stakeholders
- **Store Manager (primary)**: initiates void/refund, provides reason/notes, may need additional approvals.
- **District Manager / Finance Approver (secondary)**: provides approval for high-value reversals (if workflow requires separate approval step).
- **Cashier (secondary)**: may execute cash refund operational steps (display-only unless backend requires).
- **Billing/Payment services (system)**: evaluate eligibility, enforce policy, execute reversal, emit events.
- **Accounting (downstream)**: receives reversal events; frontend may show “synced/pending” if exposed.

# 4. Preconditions & Dependencies

## Preconditions
- User is authenticated.
- User can access the invoice/payment context (tenant/account boundary enforced).
- A payment exists and is linked to an invoice.

## Dependencies (must exist server-side)
- Backend endpoints/services to:
  - Load invoice + payments + reversal history.
  - Determine eligibility and required action (void vs refund) and any approval requirement.
  - Create void/refund request with idempotency and return a status.
  - Expose async refund lifecycle (REQUESTED/PENDING/COMPLETED/FAILED).
- Permission model exposed to frontend (at least via 401/403; ideally via explicit permission flags in response).
- Step-up authentication endpoint for approvals that require elevation token (BILL-DEC-010 pattern):
  - `POST /billing/auth/elevate` → `{ elevationToken, expiresAt }`

# 5. UX Summary (Moqui-Oriented)

## Entry points
- From **Invoice Detail** screen: “Payments” section listing payments with actions.
- Optional: From a **Payment Detail** view (reachable by clicking a payment row).

## Screens to create/modify (Moqui)
1. **Modify** existing Invoice screen (assumed): `InvoiceDetail`
   - Add Payments panel with actions: **Void Authorization**, **Refund Payment**
   - Add Reversal History subpanel (void/refund records)
2. **Create** modal/dialog screen(s) or embedded forms:
   - `VoidPaymentDialog` (form + confirm)
   - `RefundPaymentDialog` (form + confirm + amount input if partial)
3. **Create** step-up auth dialog (reusable):
   - `ElevationDialog` (manager/supervisor re-auth to obtain `elevationToken`) (BILL-DEC-010)
4. **Optional**: `PaymentReversalDetail` screen to view a specific reversal record and status history (only if backend exposes a stable reversalId lookup).

## Navigation context
- Do not hardcode routes in domain payloads (BILL-DEC-016). Screen transitions should accept `invoiceId` and (optionally) `paymentId`.
- Dialogs return to Invoice Detail and refresh data on completion.

## User workflows (happy + alternate)

### Happy path: Void an authorized payment
1. Manager opens Invoice Detail → Payments.
2. Selects an **AUTHORIZED** payment row with `eligibleActions` including `VOID` → clicks “Void Authorization”.
3. Dialog shows payment summary (amount, tender type, createdAt) and any backend-provided policy messages.
4. Manager selects reason code and enters notes if required.
5. If backend indicates elevation required, manager completes ElevationDialog to obtain `elevationToken`.
6. Submit → success message; payment/reversal status updates; invoice refreshes.

### Happy path: Refund a captured/settled payment (full)
1. Manager selects **CAPTURED/SETTLED** payment with `eligibleActions` including `REFUND` → “Refund Payment”.
2. Dialog shows refundable remaining amount and currency; defaults refund amount to full refundable remaining (editable only if partial refunds allowed).
3. Manager selects reason code and enters notes if required.
4. If elevation required, manager completes ElevationDialog.
5. Submit → refund created; UI shows returned status (COMPLETED or PENDING) and refreshes invoice/payments.

### Alternate path: Partial refund (when allowed)
- Refund dialog enables amount input when backend indicates partial refunds are allowed for this payment/invoice/account policy.
- Manager enters amount within allowed bounds; submit.

### Alternate path: Approval/elevation required
- If backend indicates `requiresElevation=true` (or equivalent), UI blocks submission until `elevationToken` is provided.
- If backend indicates `overrideRequiresSecondApprover=true`, UI must support capturing a second elevation token (see Open Questions; cannot be finalized without contract).

### Alternate path: Async refund pending
- UI shows “Refund pending” status on reversal record and provides manual refresh; optional polling only if backend provides recommended polling metadata (do not invent).

# 6. Functional Behavior

## Triggers
- User clicks “Void Authorization” or “Refund Payment” on a payment row.

## UI actions

### Payments list (Invoice Detail)
- Render a list/table of payments linked to the invoice.
- Each payment row displays (as provided by backend; do not infer):
  - `paymentId`
  - `status` (gateway/payment status enum string)
  - `amount` + `currencyUomId`
  - `tenderType` (masked/label only; never PAN)
  - `createdAt`
  - `refundableRemaining` (if provided)
  - `eligibleActions[]` (preferred) and/or `canVoid`, `canRefund` flags
- Action buttons:
  - **Void Authorization** visible/enabled only when `eligibleActions` contains `VOID` and user has permission.
  - **Refund Payment** visible/enabled only when `eligibleActions` contains `REFUND` and user has permission.

### Void dialog
- Inputs:
  - `reasonCode` (from backend discovery endpoint; do not hardcode) (BILL-DEC-007 pattern)
  - `notes` (required if backend indicates notes required OR reasonCode == `OTHER` when `OTHER` exists)
- Optional inputs:
  - `elevationToken` (not user-entered; obtained via ElevationDialog)
- Submit:
  - Calls backend void endpoint with idempotency key (if required) and optional elevation token.
- On success:
  - Close dialog
  - Refresh invoice detail (single source of truth)
  - Show toast/banner with reversal reference id and status

### Refund dialog
- Inputs:
  - `refundAmount` (decimal string)
  - `reasonCode` (from backend discovery endpoint)
  - `notes` (required if backend indicates notes required OR reasonCode == `OTHER`)
- Enablement:
  - Amount field editable only if backend indicates partial refunds allowed; otherwise read-only set to full refundable remaining.
- Submit:
  - Calls backend refund endpoint with amount, reason, notes, idempotency key (if required), and optional elevation token(s).
- On success:
  - Close dialog
  - Refresh invoice detail
  - If refund status is async, show “Pending” banner and show reversal record status.

## State changes (frontend-visible)
- Payment row and reversal history reflect backend-returned statuses only.
- Invoice status is backend-driven; UI must not invent new invoice statuses beyond canonical Billing InvoiceStatus (BILL-DEC-001). If backend exposes a separate “refund lifecycle” status, display it as a separate field (e.g., `refundStatus`) rather than overloading invoice status.

## Service interactions
- Initial load:
  - Fetch invoice detail including payments and reversal history (or fetch payments/reversals via separate endpoints).
- Action submit:
  - POST void/refund command.
  - On success, re-fetch invoice detail.
- Refresh:
  - Manual refresh action re-fetches invoice detail.
  - Optional polling for pending refunds only if backend provides a polling hint (interval/nextCheckAt) in response.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Reason code is required for void and refund.
- Notes requirement:
  - If backend provides `notesRequired=true` for selected reason code, enforce required.
  - If backend does not provide per-reason metadata, enforce notes required when reason code equals `OTHER` (only if `OTHER` is present in returned reason codes list).
- Refund amount:
  - Must be a valid decimal in invoice currency.
  - Must be > 0.
  - If `refundableRemaining` is provided, client validates `refundAmount <= refundableRemaining` to reduce round-trips; backend remains authoritative.
- Elevation:
  - If backend indicates elevation required, UI must require an `elevationToken` before enabling submit (BILL-DEC-010).

## Enable/disable rules
- Void disabled when:
  - `eligibleActions` does not include `VOID`, OR
  - user lacks required permission, OR
  - backend indicates ineligible (time window, already voided, etc.)
- Refund disabled when:
  - `eligibleActions` does not include `REFUND`, OR
  - user lacks required permission, OR
  - `refundableRemaining` is 0 (if provided), OR
  - backend indicates ineligible (policy, max refunds, etc.)
- Submit buttons disabled while request in-flight; prevent double-submit.

## Visibility rules
- Show actions based on backend eligibility (`eligibleActions[]`) rather than inferring from payment status alone.
- Show approval/elevation prompts only when backend indicates required; do not hardcode thresholds (SAFE_DEFAULTS denylist).

## Error messaging expectations
- 401/403: “You don’t have permission to void/refund payments.”
- 409: “Payment state changed or request conflicts with current state. Refresh and try again.”
- 422: Show field-level errors (amount/reason/notes) and/or policy blockers using backend-provided structured errors.
- 503: “Payment service unavailable; try again later.”
- Sanitization: never display or log sensitive gateway diagnostics; show correlationId when provided (BILL-DEC-014 pattern).

# 8. Data Requirements

## Entities involved (frontend view models)
- Invoice (Billing SoR):
  - `invoiceId`, `invoiceNumber?`, `status` (BILL-DEC-001), totals, `balanceDue`
- Payment (Billing-orchestrated payment record):
  - `paymentId`, `invoiceId`, `amount`, `currencyUomId`, `status`, `tenderTypeLabel`, `createdAt`
  - `refundableRemaining?`
  - `eligibleActions[]` (preferred)
- Reversal record (void/refund):
  - `reversalId`, `type` (VOID|REFUND), `paymentId`, `amount?`, `status`, `reasonCode`, `notes?`
  - `createdAt`, `createdByUserId`
  - `approvedByUserId?`, `approvedAt?`
  - `failureCode?`, `failureMessageSafe?`, `correlationId?`

## Fields (type, required, defaults)

### Void request
- `paymentId` (UUID/string, required)
- `reasonCode` (string, required; from discovery endpoint category `VOID` or `PAYMENT_VOID`)
- `notes` (string, required iff policy says required)
- `elevationToken` (string, required iff policy says required)
- `idempotencyKey` (string, required iff backend requires)

### Refund request
- `paymentId` (UUID/string, required)
- `amount` (decimal string, required)
- `currencyUomId` (string, required if backend requires; otherwise inferred from payment/invoice display only)
- `reasonCode` (string, required; from discovery endpoint category `REFUND` or `PAYMENT_REFUND`)
- `notes` (string, required iff policy says required)
- `elevationToken` (string, required iff policy says required)
- `secondApproverElevationToken` (string, required iff policy says required) **(contract needed)**
- `idempotencyKey` (string, required iff backend requires)

## Read-only vs editable
- Invoice/payment/reversal fields are read-only.
- Only dialog fields (reasonCode, notes, amount) are editable.
- Elevation token is never directly editable; obtained via ElevationDialog.

## Derived/calculated fields
- `refundableRemaining` display: prefer backend-provided.
- Currency formatting: use `currencyUomId` from invoice/payment; do not assume USD.

# 9. Service Contracts (Frontend Perspective)

> Billing domain guide provides normative contracts for invoices, receipts, AP, billing rules. Payment reversal endpoints are not defined in the provided Billing guide; therefore, this story cannot finalize without explicit backend contract. The frontend must not invent endpoint paths, enums, or approval policy fields.

## Load/view calls
- `GET /billing/invoices/{invoiceId}`
  - Must include payments and reversal history OR provide link metadata to fetch them.
  - Must include `allowedActions[]`/eligibility metadata per payment (preferred) to avoid UI guessing (pattern consistent with BILL-DEC-003, BILL-DEC-011).

## Create/update calls (required; contract TBD)
- Void authorization command (idempotent):
  - `POST /billing/payments/{paymentId}/void` (example only; **must be confirmed**)
  - Request: `{ reasonCode, notes?, elevationToken?, idempotencyKey? }`
  - Response: reversal record + updated payment snapshot OR `{reversalId}` for refresh
- Refund command (idempotent):
  - `POST /billing/payments/{paymentId}/refund`
  - Request: `{ amount, reasonCode, notes?, elevationToken?, secondApproverElevationToken?, idempotencyKey? }`
  - Response: reversal record with async status + updated payment snapshot OR `{reversalId}` for refresh

## Submit/transition calls
- Step-up auth (normative pattern from BILL-DEC-010):
  - `POST /billing/auth/elevate` → `{ elevationToken, expiresAt }`

## Error handling expectations
- 422 validation failures with structured errors:
  - `fieldErrors[]` and/or `blockers[]` with stable codes
- 409 conflicts:
  - stale state, duplicate idempotency key with different payload, already reversed, etc.
- 403 forbidden:
  - missing permission or missing elevation
- 503 downstream unavailable:
  - gateway unavailable; show retry guidance
- Observability:
  - propagate W3C Trace Context headers (BILL-DEC-015)
  - display `correlationId` when provided; never log tokens or sensitive payment instrument data

# 10. State Model & Transitions

## Allowed states (as surfaced to UI)

### Invoice (Billing canonical) (BILL-DEC-001)
- `DRAFT`, `ISSUED`, `PAID`, `VOID` (optional `ERROR` only if implemented)
UI must treat unknown values as “Unknown status” and prompt refresh/support.

### Payment / Reversal (contract TBD)
- Payment status examples: `AUTHORIZED`, `CAPTURED`, `SETTLED`, etc. (**backend authoritative**)
- Reversal status examples: `REQUESTED`, `PENDING`, `COMPLETED`, `FAILED` (**backend authoritative**)

## Role-based transitions
- Store Manager can initiate void/refund only with appropriate permissions (canonical permission strings for payment reversal are **not provided** in Billing guide; must be clarified).
- Elevation required for certain reversals uses `billing:auth:elevate` (BILL-DEC-010), plus the specific action permission.

## UI behavior per state
- If reversal status is `PENDING`: show banner “Refund pending” and show last updated time; allow manual refresh.
- If `FAILED`: show safe failure message and correlationId; do not show raw gateway errors.

# 11. Alternate / Error Flows

## Validation failures
- Missing reason/notes/amount → inline errors; prevent submit.
- Amount exceeds refundable remaining → show backend message and keep dialog open.

## Concurrency conflicts
- Payment state changes while dialog open → backend returns 409; UI shows “Payment state changed; refresh.”

## Unauthorized access
- 403 on action: show message; action buttons disabled for that session context.

## Empty states
- No payments: show “No payments found for this invoice.”
- No reversal history: show “No voids/refunds recorded.”

## Async refund pending too long
- If backend provides `pendingSince` or `nextCheckAt`, display it.
- Provide manual refresh; do not invent automated retries beyond optional polling with backend hint.

# 12. Acceptance Criteria (Gherkin)

## Scenario 1: Void an authorized payment successfully
Given I am a Store Manager with permission to void payments  
And an invoice has a payment eligible for void as indicated by the backend  
When I open the Void Authorization dialog and select a void reason  
And I provide notes if required by the backend for that reason  
And I submit the void request  
Then the system shows a success confirmation  
And the payment and invoice are refreshed from the backend  
And the void record appears in reversal history with my user identity, reason, and timestamp

## Scenario 2: Void requires notes when reason is OTHER
Given I am initiating a void for an eligible payment  
And the backend provides a reason code OTHER  
When I select void reason OTHER  
And I do not enter notes  
Then the UI prevents submission and displays a required-field error for notes

## Scenario 3: Refund a captured payment and receive pending status
Given I am a Store Manager with permission to refund payments  
And an invoice has a payment eligible for refund as indicated by the backend  
When I submit a refund for the full refundable amount with a valid refund reason  
Then the UI displays the refund record status returned by the backend  
And if the status is PENDING, the UI indicates the refund is pending and provides a refresh action  
And reversal history shows the refund with status PENDING

## Scenario 4: Partial refund amount validation
Given a payment has refundable remaining amount of 50.00 in the invoice currency  
And the backend indicates partial refunds are allowed  
When I enter a refund amount of 60.00 and submit  
Then the UI displays an actionable validation error from the backend  
And the dialog remains open for correction

## Scenario 5: Permission denied
Given I lack permission to refund payments  
When I attempt to open or submit a refund for a payment  
Then the UI shows an authorization error  
And the refund action is disabled or blocked

## Scenario 6: Elevation required for refund
Given I have permission to refund payments  
And the backend indicates elevation is required to refund a specific payment  
When I attempt to submit the refund without an elevation token  
Then the UI blocks submission and prompts for manager elevation  
When I complete elevation and receive an elevation token  
And I submit the refund with the elevation token  
Then the refund request is submitted and the UI refreshes invoice/payment data

## Scenario 7: Payment state changed (conflict)
Given I opened a refund/void dialog for a payment  
And the payment state changes before I submit  
When I submit the request  
Then the UI shows a conflict error instructing me to refresh  
And the UI provides a refresh action to reload the latest invoice/payment state

# 16. Open Questions

1. **Backend contract (blocking):** What are the canonical endpoints and schemas for payment reversal within Billing?
   - Void authorization command endpoint, request/response, idempotency mechanism
   - Refund command endpoint, request/response, idempotency mechanism
   - Reversal status query (by invoice, by payment, by reversalId) and whether reversal history is embedded in invoice detail
2. **Permissions (blocking):** What are the canonical permission strings for:
   - initiating void authorization
   - initiating refund
   - viewing reversal history
   (Billing guide defines invoice/receipt/AP permissions but not payment reversal permissions.)
3. **Approval semantics (blocking):** How does the backend represent approval requirements for reversals?
   - Is elevation token always sufficient, or is a second approver token required (`overrideRequiresSecondApprover`)?
   - If second approver is required, what is the request shape (two tokens in one call vs separate approve step)?
4. **Policy discovery (blocking):** What discovery endpoint provides reversal reason codes and per-reason metadata (notes required, categories)?
   - Confirm `GET /billing/meta/reason-codes?category=...` categories for VOID and REFUND.
5. **Async refund polling (non-blocking if manual refresh is acceptable):** Does backend provide `nextCheckAt`/recommended polling interval for pending refunds, or should UI be manual refresh only?
6. **Multi-payment refunds (blocking):** For invoices with multiple payments, can a single refund request target multiple payments, or must refunds be per paymentId?
