## Issue Body

## Title
[FRONTEND] Payment: Initiate Card Authorization and Capture (Checkout)

## Primary Persona
Cashier

## Business Value
Enable cashiers to take compliant card payments against an invoice at checkout (sale/capture and auth→capture), generate a receipt, and ensure billing/audit traceability for accounting reconciliation—without exposing or storing cardholder data.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Cashier  
- **I want** to initiate a card payment for an invoice (sale/capture or auth then capture)  
- **So that** the invoice can be paid at checkout, a receipt is produced, and the transaction is auditable without storing card data.

## In-scope
- From an invoice checkout context, start a card payment
- Support **SALE_CAPTURE** default and **AUTH_ONLY → CAPTURE** flow (same-session)
- Display payment status/progress and final outcome
- Persist and show only **token/transaction references** (no PAN/CVV)
- Trigger receipt generation and allow immediate receipt viewing/printing entrypoint
- Record/show audit-friendly metadata visible to user (who/when/terminal) where exposed by backend
- Handle error responses and “unknown outcome” states safely (frontend UX + inquiry hooks)

## Out-of-scope
- Multi-gateway selection/failover UI
- Refunds/chargebacks UI
- Back-office “manual capture later” workflows
- Invoice regeneration/voiding flows
- Receipt reprint authorization flow details (separate story)
- Implementing printer formatting (receipt content is backend-provided)

---

# 3. Actors & Stakeholders
- **Cashier**: initiates and completes payment at POS
- **Customer**: presents card and may request receipt delivery (print/email) per policy
- **Manager/Supervisor** (optional): step-up approval via elevation token when required by policy
- **Billing (backend SoR)**: orchestrates payments against invoices; generates receipts; enforces policy and audit (Billing domain)
- **Payment Gateway adapter**: executes authorization/capture via Billing orchestration (integrated; not frontend-owned)
- **Accounting (downstream)**: consumes Billing events; not directly handled by frontend

---

# 4. Preconditions & Dependencies
- User is authenticated in POS.
- User has permission to initiate invoice payments (exact canonical permission string for AR card payment is **not defined in provided Billing rules**; see Open Questions).
- Invoice exists in Billing and is payable:
  - `balanceDue > 0`
  - invoice `status` is not `VOID`
  - if invoice `status` is `PAID`, then `balanceDue` must be 0 and payment entrypoint must be disabled
- POS terminal/location context is available to send to backend if required (e.g., `terminalId`, `locationId`).
- Backend provides endpoints for:
  - initiating card payment (sale/capture or auth-only)
  - capturing an existing authorization (same-session)
  - payment status inquiry for unknown outcomes
  - receipt retrieval after successful capture
- Observability: frontend propagates W3C Trace Context headers (`traceparent`, optional `tracestate`) per BILL-DEC-015.
- Security: frontend must never log/store sensitive payment data; only masked metadata and references.

# 5. UX Summary (Moqui-Oriented)

## Entry points
- From **Invoice Detail / Checkout** screen: action “Pay by Card”
- From an “Outstanding Balance” panel (if present): “Pay by Card”

## Screens to create/modify
1. **Modify**: Invoice checkout/detail screen (existing)
   - Add “Pay by Card” action (permission-gated)
   - Add a “Payments” panel section showing latest payment attempts (read-only)
2. **Create**: Card payment flow screen (new)
   - Handles initiation, progress, inquiry, and outcome display
3. **Modify**: Receipt view screen (existing) or create minimal receipt viewer
   - Wire to receipt retrieval by `invoiceId` (preferred) or `receiptId` returned by payment response

> Per BILL-DEC-016, do not hardcode routes in backend payloads; use link metadata if provided.

## Navigation context
- Entry requires `invoiceId` (from invoice screen context).
- Return to Invoice Detail on completion or user exit.
- Do not place tokens, signed URLs, or elevation tokens in URL parameters.

## User workflows (happy + alternate)

### Happy path A: SALE_CAPTURE (default)
1. Cashier clicks “Pay by Card”
2. Payment screen loads invoice summary and current `balanceDue`
3. Cashier confirms amount (default = full `balanceDue`) and submits
4. UI shows processing; disables duplicate submission
5. On success:
   - UI shows “Payment captured”
   - UI shows receipt action (View/Print) once receipt is available
   - UI refreshes invoice and shows updated `balanceDue` (likely 0) and/or `status=PAID`

### Happy path B: AUTH_ONLY then CAPTURE (same session)
1. Cashier selects “Authorize only” (only if allowed by backend capabilities + permission)
2. UI initiates authorization; shows “Authorized”
3. Cashier clicks “Capture” to complete payment
4. On capture success, UI shows receipt action and refreshes invoice

### Alternate path: Unknown outcome / timeout
1. Cashier submits payment; request times out or returns “pending/unknown”
2. UI enters “Confirming status” and performs status inquiry loop
3. UI resolves to success/failure and updates invoice/receipt accordingly
4. UI never encourages blind retry while outcome is unknown

### Alternate path: Policy requires supervisor step-up
- If backend indicates step-up required (policy/permission), UI prompts for supervisor elevation (token-based) and retries the action with `elevationToken` (BILL-DEC-010 pattern).

# 6. Functional Behavior

## Triggers
- Click “Pay by Card” from invoice screen
- Click “Process Card” on payment screen
- Click “Capture” for an authorized intent
- Automatic inquiry/polling when outcome is pending/unknown
- Receipt retrieval after capture success

## UI actions
- Load context:
  - Fetch invoice detail/summary (must include `invoiceId`, `status`, `balanceDue`, `currencyUomId`)
  - Optionally fetch existing payments/intents for this invoice to prevent duplicate attempts and show history
- Start payment:
  - Flow type defaults to `SALE_CAPTURE`
  - “Authorize only” option is shown only when backend indicates allowed + user has permission
  - Amount defaults to full `balanceDue`; editability depends on partial payment policy (see Open Questions)
  - Submit includes an idempotency key (client-generated UUID) per attempt
- Capture:
  - Enabled only when intent is `AUTHORIZED` and backend indicates capture is allowed
  - Submit includes a new idempotency key for capture command
- Inquiry:
  - If initiation/capture returns timeout/unknown, call inquiry endpoint using intent id and/or idempotency key
  - Continue until definitive status or until inquiry attempts exhausted (see Applied Safe Defaults)

## State changes (frontend view state)
- Local UI state machine (frontend-only):
  - `idle` → `submitting` → (`succeeded` | `failed` | `unknown`)
  - Auth-only branch: `authorized` → `capturing` → (`succeeded` | `failed` | `unknown`)
- While `submitting/capturing/unknown`:
  - Disable primary submit buttons to prevent duplicate charges
  - Allow “Return to invoice” but warn that payment status is still being confirmed (do not lose the ability to resume inquiry)

## Service interactions
- Invoice load: `GET /billing/invoices/{invoiceId}` (Billing SoR)
- Payment initiation: **endpoint not defined in provided Billing rules** (see Open Questions)
- Capture: **endpoint not defined in provided Billing rules** (see Open Questions)
- Inquiry: **endpoint not defined in provided Billing rules** (see Open Questions)
- Receipt retrieval:
  - Preferred: `GET /billing/receipts/by-invoice/{invoiceId}` (BILL-DEC-011)
  - Delivery actions (optional in this story; see scope below): `POST /billing/receipts/{receiptId}/deliver` with `channel=PRINT|EMAIL`

# 7. Business Rules (Translated to UI Behavior)

## Validation
- `invoiceId` is required to enter the payment flow.
- Invoice must be payable:
  - `balanceDue > 0`
  - `status != VOID`
- Amount:
  - Default = `invoice.balanceDue`
  - If partial payments are not allowed by policy, amount is read-only and must equal `balanceDue`
  - If partial payments are allowed, amount must be `> 0` and `<= balanceDue` (BILL-DEC-012 supports partial payments unless disabled by policy; exact policy signal is not defined here—see Open Questions)
- Sensitive data handling:
  - No PAN/CVV/track data may be stored in component state, localStorage, sessionStorage, logs, URLs, or analytics
  - Only masked metadata (brand, last4) and gateway references may be displayed if provided

## Enable/disable rules
- “Pay by Card” entrypoint:
  - Disabled/hidden if user lacks payment permission (permission string TBD)
  - Disabled if `balanceDue == 0` or `status in {PAID, VOID}`
- Flow selector:
  - Default `SALE_CAPTURE`
  - “Authorize only” visible only if backend indicates allowed and user has permission (permission string TBD)
- “Capture” button:
  - Enabled only when intent status is `AUTHORIZED` and backend indicates capture is allowed
- Retry:
  - Enabled only when backend returns a definitive failure that guarantees no capture occurred (must be explicit in response; otherwise treat as unsafe)

## Visibility rules
- Show receipt actions only when receipt exists and backend policy allows the action:
  - Receipt view requires `billing:receipt:view`
  - Deliver requires `billing:receipt:deliver`
  - Reprint requires `billing:receipt:reprint` (reprint itself is out-of-scope here; view/deliver immediate receipt is in-scope if permitted)
- Show correlationId in a collapsible “Details” section for support (BILL-DEC-014/015 style), never showing sensitive gateway payloads.

## Error messaging expectations
- 422 validation: show actionable message (e.g., invoice not payable, missing required fields) using backend-provided field/blocker codes where available
- 409 conflict: show “Invoice already paid / payment already processed / state changed” and refresh invoice
- 403 forbidden: show “You don’t have permission to take card payments” and return to invoice
- 503 unavailable: show “Payment service unavailable; try again” and preserve form state
- Gateway decline: show “Card declined” with non-sensitive reason code/text if provided; do not show raw gateway messages if they may contain sensitive details
- Unknown outcome: show “Confirming payment status…” and run inquiry; do not suggest retry until resolved

# 8. Data Requirements

## Entities involved
Billing-owned (SoR):
- **Invoice**: `invoiceId`, `status` (InvoiceStatus: `DRAFT|ISSUED|PAID|VOID` per BILL-DEC-001), `balanceDue`, `currencyUomId`, `customerAccountId`
- **Receipt**: `receiptId`, `deliveryStatus` (`PENDING|SENT|FAILED|BOUNCED` per BILL-DEC-011), `deliverySuppressed` (bool), `allowedActions[]`, `reprintPolicy` (if returned)

Payment orchestration (Billing-owned conceptually, but contract not provided here):
- **BillingPayment / PaymentIntent**: identifiers, status, amounts, timestamps, gateway reference (masked), idempotency key, correlationId

## Fields (type, required, defaults)
- `invoiceId` (UUIDv7/string, required)
- `amount` (decimal, required; default = invoice `balanceDue`)
- `currencyUomId` (string, required; default from invoice)
- `flowType` (enum, required; default `SALE_CAPTURE`; allowed values depend on backend)
- `idempotencyKey` (string, required; UUID generated client-side per command; must not include PII)
- `elevationToken` (string, optional; only when backend requires step-up per policy; TTL-limited and never persisted) (BILL-DEC-010 pattern)

## Read-only vs editable by state/role
- Amount:
  - Read-only unless backend explicitly indicates partial payments are allowed for this invoice/payment method
- Flow type:
  - Read-only/hidden unless backend indicates allowed and user has permission
- Gateway/card metadata:
  - Always read-only and masked

## Derived/calculated fields
- “Remaining balance” is derived from refreshed invoice `balanceDue` after payment outcome; do not compute totals client-side beyond display.

# 9. Service Contracts (Frontend Perspective)

> Moqui screen actions should call Moqui services that proxy to backend REST endpoints. Billing domain provides canonical endpoints for receipts; payment endpoints are not defined in the provided Billing rules and must be confirmed.

## Load/view calls
- `GET /billing/invoices/{invoiceId}` → invoice detail/summary
- `GET /billing/receipts/by-invoice/{invoiceId}` → receipts for invoice (may be empty immediately after capture; poll/refresh)
- (Optional) `GET <payment>/by-invoice/{invoiceId}` → list payment attempts/intents (endpoint TBD)

## Create/update calls (TBD - requires clarification)
- `POST <payment>/invoices/{invoiceId}/card/initiate`
  - Request: `{ invoiceId, amount, currencyUomId, flowType, idempotencyKey, terminalId?, locationId?, elevationToken? }`
  - Response: `{ billingPaymentId/paymentIntentId, status, maskedCardMeta?, gatewayRef?, correlationId, receiptId? }`
- `POST <payment>/{paymentIntentId}/capture`
  - Request: `{ idempotencyKey, amount? (only if partial capture supported), elevationToken? }`
  - Response: updated payment intent + receipt pointer if available
- `POST <payment>/{paymentIntentId}/inquire` (or `GET ...`)
  - Response: definitive status or `PENDING`, plus safe-to-retry indicator if provided

## Submit/transition calls
- Receipt delivery (in-scope only for immediate post-payment receipt delivery):
  - `POST /billing/receipts/{receiptId}/deliver` with `{ channel: PRINT|EMAIL }` (BILL-DEC-011)
  - UI must honor `allowedActions[]` and policy output; do not hardcode reprint/delivery windows (BILL-DEC-011)

## Error handling expectations
- All endpoints return stable error shape:
  - `errorCode`, `message`, `correlationId`
  - For 422: `fieldErrors[]` and/or `missingFields[]`
  - For payment policy gating: structured codes indicating step-up required (exact codes TBD)
- Frontend must:
  - Display user-safe messages
  - Provide correlationId for support
  - Never log sensitive payloads, tokens, or signed URLs (BILL-DEC-005, BILL-DEC-015)

# 10. State Model & Transitions

## Allowed states
Invoice (canonical, Billing SoR) (BILL-DEC-001):
- `DRAFT`, `ISSUED`, `PAID`, `VOID` (optional `ERROR` only if implemented)

Payment intent/status (TBD - requires clarification; do not invent backend enums)
- Frontend must treat backend payment status as authoritative and render unknown statuses as “Unknown status; refresh or contact support”.

## Role-based transitions
- Cashier:
  - Can initiate card payment only with appropriate payment permission (string TBD)
  - Can view receipt with `billing:receipt:view`
  - Can deliver receipt with `billing:receipt:deliver` (if enabled)
- Supervisor/Manager:
  - Step-up auth via elevation token using `billing:auth:elevate` when required (BILL-DEC-010)
  - Any additional override permission for payments is TBD (not in BILL-DEC-008 table)

## UI behavior per state
- Invoice `PAID` or `balanceDue==0`: payment entrypoint disabled; show “No payment due”
- Payment `PENDING/PROCESSING`: show progress; disable submit
- Payment `AUTHORIZED`: show “Capture” if allowed
- Payment `CAPTURED/SUCCEEDED`: show success; fetch receipt; refresh invoice
- Payment `FAILED/DECLINED`: show failure; allow safe retry only if backend indicates no capture occurred
- Payment `UNKNOWN`: run inquiry loop; do not allow retry until resolved

# 11. Alternate / Error Flows

## Validation failures
- Missing `invoiceId`: show error and route back to invoice list/detail safely
- Invoice not payable: show “No payment needed” and disable actions

## Concurrency conflicts
- If invoice is paid on another terminal while payment screen is open:
  - Invoice refresh shows `balanceDue==0` or `status==PAID`
  - UI stops payment actions and returns to invoice with message “Invoice already paid”

## Unauthorized access
- If user lacks payment permission:
  - Hide entrypoint
  - If deep-linked, show 403 and provide “Back to invoice”

## Empty states
- No receipts found after capture:
  - Show “Receipt generating…” and allow refresh/poll receipt endpoint
- No payment history available:
  - Show “No card payment attempts yet” (informational)

## Downstream/gateway timeouts
- On timeout/unknown:
  - Transition to `UNKNOWN`
  - Perform inquiry attempts
  - If still unresolved after attempts, show “Unable to confirm payment status. Check invoice balance and payment history before retrying.” and return to invoice

# 12. Acceptance Criteria

### Scenario 1: Start SALE_CAPTURE card payment and succeed
**Given** a cashier with permission to take card payments is viewing an invoice with `balanceDue > 0` and `status != VOID`  
**When** the cashier selects “Pay by Card” and submits payment with flow type `SALE_CAPTURE` for the default amount (full balance due)  
**Then** the UI shows a processing state and prevents duplicate submission  
**And** on success the UI shows captured amount, masked card details (brand/last4 only if provided), and a receipt action (View/Print)  
**And** the UI refreshes the invoice and shows updated `balanceDue` and/or `status=PAID` consistent with backend.

### Scenario 2: AUTH_ONLY then CAPTURE in the same session (when allowed)
**Given** a cashier is viewing an eligible invoice and the backend indicates `AUTH_ONLY` is allowed and the user is permitted to select it  
**When** the cashier selects flow type `AUTH_ONLY` and submits  
**Then** the UI shows the payment as authorized and enables “Capture”  
**When** the cashier clicks “Capture”  
**Then** the UI completes capture, shows receipt access, and refreshes the invoice balance/status.

### Scenario 3: Card declined (non-success)
**Given** a cashier initiates a card payment  
**When** the backend returns a declined/failed outcome  
**Then** the UI displays “Card declined” (and only non-sensitive reason text/code if provided)  
**And** the UI does not mark the invoice as paid and does not reduce `balanceDue` without an invoice refresh confirming it.

### Scenario 4: Timeout/unknown outcome triggers inquiry instead of blind retry
**Given** a cashier submits a card payment  
**When** the initiation or capture request times out or returns an unknown/pending outcome  
**Then** the UI enters “Confirming status” state and calls the payment status inquiry endpoint  
**And** the UI does not enable “Retry” while the outcome is unknown  
**And** once a definitive status is received, the UI reflects that outcome and refreshes the invoice.

### Scenario 5: Prevent storing card data
**Given** the cashier completes any payment attempt  
**When** the UI stores state, logs errors, or navigates between screens  
**Then** no PAN, CVV, track data, or raw gateway payload is stored in browser storage, logs, or URLs  
**And** only token/transaction references and masked card metadata may be displayed.

### Scenario 6: Receipt retrieval and delivery actions are policy/permission gated
**Given** a payment capture succeeds for an invoice  
**When** the UI loads receipts via `GET /billing/receipts/by-invoice/{invoiceId}`  
**Then** the UI displays receipt records and delivery status  
**And** the UI only shows “Print”/“Email” actions when `allowedActions[]` includes the action and the user has `billing:receipt:deliver`  
**And** the UI does not hardcode reprint/delivery windows or limits (BILL-DEC-011).

# 15. Applied Safe Defaults
- **SD-UX-EMPTY-STATE**: Provide standard empty-state messaging for “no receipts yet” / “no payment attempts yet” because it’s UI ergonomics and does not affect domain policy. (Sections: UX Summary, Alternate / Error Flows)
- **SD-ERR-HTTP-MAP**: Map 422/409/403/503 to validation/conflict/forbidden/unavailable UI messages because these are standard HTTP semantics implied by the domain contracts. (Sections: Business Rules, Alternate / Error Flows, Acceptance Criteria)
- **SD-OBS-CORRELATION-ID**: Surface backend `correlationId` in a collapsible details panel and propagate W3C trace headers because this is observability boilerplate and does not change business policy. (Sections: Service Contracts, Audit & Observability)
- **SD-UX-POLL-BOUNDS**: Bound inquiry polling to a small fixed number of attempts with increasing delay (e.g., 6 attempts over ~60–90s) because it is a UI safety/ergonomics choice and does not define payment policy; backend remains authoritative. (Sections: Functional Behavior, Alternate / Error Flows)
