## Issue Body

## 1. Story Header

**Title:** [FRONTEND] Payment: Print/Email Receipt and Store Reference (Post-Capture + Reprint)

**Primary Persona:** Cashier (secondary: Supervisor/Manager, Customer Service)

**Persona Metadata**
- `primary_persona`: `Cashier (secondary: Supervisor/Manager, Customer Service)`
- `canonical_persona`: `Customer Support Associate`
- `persona_family`: `Customer Support Associate`
- `actor_type`: `human`
**Business Value:** Provide customers immediate proof of payment (printed or emailed), ensure auditable linkage between payment/invoice/receipt, and support controlled reprints without financial or privacy risk.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Cashier  
- **I want** the POS to load the receipt generated for a successful payment and allow printing and optional emailing (or “No Receipt” delivery suppression)  
- **So that** customers receive proof of payment and the business retains a traceable receipt reference for audit and controlled reprint.

### In-scope
- Showing receipt actions immediately after successful capture:
  - fetch receipt(s) for the invoice (receipt is generated on successful capture by Billing)
  - print receipt (backend-provided printer-ready content)
  - optionally email receipt (backend delivery request)
  - allow “No Receipt” (suppress delivery but keep receipt record)
- Storing/displaying the **receipt reference** on the payment/invoice UI
- Reprint flow with:
  - permission gating
  - policy-driven reason code and step-up auth (elevation token) when required
  - “REPRINT/DUPLICATE” indication as provided by backend content/policy (frontend must not invent watermarking rules)
- Display receipt delivery status/history and reprint policy output (remaining reprints, window, allowed actions)

### Out-of-scope
- Implementing backend receipt generation, storage, retention, retry policies, or template rendering
- Defining/altering financial settlement, reconciliation, or accounting posting
- Creating/updating CRM contact data (manual email entry must not be persisted to CRM)
- Designing printer drivers; only invoking existing POS print mechanism
- Implementing payment capture itself (assumed already completed before this story begins)

---

## 3. Actors & Stakeholders

- **Cashier:** prints/email receipts; performs reprints when allowed
- **Supervisor/Manager:** performs step-up auth and approves policy-required actions (reprint, overrides) subject to permissions
- **Customer Service:** may reprint with permission and reason code
- **Customer:** receives printed/email receipt
- **Billing (backend SoR):** receipt retrieval, delivery/reprint policy evaluation, delivery/reprint commands, audit trail
- **CRM (integrated):** provides suggested email contact when customer account exists (read-only suggestion)
- **POS Printer subsystem:** prints receipt payload

## 4. Preconditions & Dependencies

### Preconditions
- A **payment capture succeeded** for an **invoice** (invoice exists and is identifiable via `invoiceId`; invoice may be `ISSUED` or `PAID` depending on upstream flow).
- User is authenticated in POS and has required permissions for actions they attempt.

### Dependencies (must exist/confirmed)
- Billing endpoints (normative):
  - `GET /billing/receipts/by-invoice/{invoiceId}`
  - `POST /billing/receipts/{receiptId}/deliver` with `channel=PRINT|EMAIL`
  - `POST /billing/receipts/{receiptId}/reprint`
  - Policy outputs included in receipt payload: `allowedActions[]`, `reprintPolicy` (and any reason-code/elevation requirements) (BILL-DEC-011)
- Step-up auth endpoint (normative):
  - `POST /billing/auth/elevate` → `{ elevationToken }` (BILL-DEC-010)
- Reason codes discovery (normative):
  - `GET /billing/meta/reason-codes?category=REPRINT|...` (BILL-DEC-007, BILL-DEC-011)
- Frontend has access to:
  - current terminal/printer configuration identifier (e.g., `terminalId`, `printerId` if applicable to printer integration)
  - current user identity and permission checks (canonical permissions; BILL-DEC-008)
- Printer integration available in frontend runtime to send a print job using backend-provided printer-ready content (BILL-DEC-011).

## 5. UX Summary (Moqui-Oriented)

### Entry points
1. **Post-payment success panel** (immediately after capture confirmation; invoice context available)
2. **Invoice detail screen** (paid/issued invoice → receipt section)
3. **Receipt detail screen** (from invoice detail; optional direct navigation if receiptId known)

### Screens to create/modify (Moqui)
1. **Modify existing**: Payment success view/screen (where capture success is shown)
   - Add “Receipt” action group: **Print**, **Email**, **No Receipt**, **View Details**, **Reprint** (only when allowed by policy + permissions)
2. **Create/Modify**: `ReceiptDetail` screen
   - Shows receipt identifiers, invoice linkage, delivery history/statuses, reprint policy output, and actions
3. **Modify existing**: Invoice detail screen
   - Add receipt summary panel with link to `ReceiptDetail`

> Note: Per BILL-DEC-016, do not hardcode routes in data. Navigation uses frontend routing; backend returns only IDs and link metadata where applicable.

### Navigation context
- Payment success → Receipt actions inline; “View Details” navigates to `ReceiptDetail` (receiptId)
- Invoice detail → Receipt summary → Receipt detail
- Receipt detail → actions (deliver/reprint) and history

### User workflows (happy + alternate paths)

**Happy path (print):**
- Payment captured → UI loads receipts by invoiceId → cashier clicks Print → UI calls `deliver(channel=PRINT)` → backend returns printer-ready content (or a print job descriptor) → frontend sends to printer → UI refreshes receipt to show updated delivery status.

**Happy path (email):**
- Payment captured → UI loads receipts → cashier clicks Email → UI suggests CRM email (if available in invoice/customer context) or allows manual entry → UI calls `deliver(channel=EMAIL)` with email → UI refreshes receipt to show `deliveryStatus` (`PENDING`/`SENT`).

**Alternate paths:**
- Printer error in frontend print subsystem → show actionable error; allow retry; delivery attempt should still be recorded via backend deliver response (do not invent separate “record print outcome” unless backend requires it).
- Email delivery `FAILED`/`BOUNCED` → allow retry only if backend `allowedActions[]` includes retry; otherwise instruct user to correct email in CRM or enter a new email and retry (BILL-DEC-011).
- Reprint requires reason code and/or elevation token → prompt for reason code and step-up auth; then call reprint.

## 6. Functional Behavior

### Triggers
- **On payment success panel mount** (invoiceId known): call `GET /billing/receipts/by-invoice/{invoiceId}`.
- **On invoice detail load**: call `GET /billing/receipts/by-invoice/{invoiceId}` (lazy-load allowed; must not block invoice rendering).
- **On Print click**: call `POST /billing/receipts/{receiptId}/deliver` with `channel=PRINT` (and any required payload per contract), then print returned content.
- **On Email click**: call `POST /billing/receipts/{receiptId}/deliver` with `channel=EMAIL` and `emailAddress`.
- **On No Receipt click**: call `POST /billing/receipts/{receiptId}/deliver` with a suppression flag if supported by contract; otherwise call a dedicated suppression action if present. If neither exists, this story is blocked (see Open Questions). (BILL-DEC-011 requires delivery suppression without suppressing receipt generation.)
- **On Reprint click**: call `POST /billing/receipts/{receiptId}/reprint` with required reason code and optional `elevationToken` if policy requires.

### UI actions (explicit)
- Buttons (rendered only when permitted by both permissions and backend `allowedActions[]`):
  - `Print Receipt`
  - `Email Receipt`
  - `No Receipt` (delivery suppressed)
  - `Reprint Receipt`
  - `View Receipt Details`
- Email entry modal:
  - Prefill from customer/account context if available (read-only suggestion)
  - Validate email format before submit
  - Must display a non-persistence notice: “Email will be used only to send this receipt and will not be saved.” (copy may be adjusted by product/legal; behavior is required)

### State changes (frontend-visible)
- Receipt record already exists post-capture (BILL-DEC-011). UI reflects:
  - `deliveryStatus` transitions: `PENDING` → `SENT` or `FAILED`/`BOUNCED`
  - `deliverySuppressed=true` when “No Receipt” selected
  - Reprint policy fields and history updates after reprint
- UI must refresh receipt detail after each deliver/reprint command to reflect authoritative state.

### Service interactions (frontend perspective)
- Read:
  - `GET /billing/receipts/by-invoice/{invoiceId}`
  - `GET /billing/meta/reason-codes?category=REPRINT` (only when reprint flow requires reason codes)
- Commands:
  - `POST /billing/receipts/{receiptId}/deliver` (PRINT/EMAIL)
  - `POST /billing/receipts/{receiptId}/reprint`
  - `POST /billing/auth/elevate` (only when policy requires elevation)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Email address**
  - Required only when `channel=EMAIL`
  - Client-side: basic syntax validation (e.g., `something@domain.tld`)
  - Server-side: treat 422 field errors as authoritative; display returned message
- **Reprint policy**
  - UI must not hardcode reprint windows/limits.
  - Backend provides `reprintPolicy` and `allowedActions[]`; UI enforces by disabling/hiding actions and by handling 403/409/422 responses.
- **Step-up auth (elevation token)**
  - If backend indicates `requiresElevation=true` (or equivalent) for reprint/delivery action, UI must prompt for manager/supervisor step-up auth and submit `elevationToken` with the command (BILL-DEC-010).
  - UI must never store or log raw manager credentials; only handle the returned token in-memory.

### Enable/disable rules
- Disable action buttons while request is in-flight.
- Disable/hide actions when:
  - user lacks required permission (BILL-DEC-008)
  - backend `allowedActions[]` does not include the action
- If receipt `deliverySuppressed=true`, hide “Email Receipt” and “Print Receipt” unless backend explicitly allows “deliver anyway” (do not invent).

### Visibility rules
- Always show:
  - `receiptId`, `invoiceId`, `invoiceNumber` (if present), `generatedAt`, `deliveryStatus`, `deliverySuppressed`
- Show reprint policy panel only when backend provides `reprintPolicy`.
- Show delivery history/statuses when present; otherwise show empty state.

### Error messaging expectations
- 403: “You do not have permission to perform this action.”
- 409: “This receipt can’t be updated due to its current state. Refresh and try again.” (include correlationId if provided)
- 422: show structured validation errors (email invalid, reason code missing, elevation required)
- 503: “Billing service unavailable. Try again.”

## 8. Data Requirements

### Entities involved (frontend view models; backend SoR = Billing)
- `Receipt` (Billing SoR)
- `ReceiptDeliveryStatus` (enum; Billing SoR)
- `ReprintPolicy` (policy DTO; Billing SoR)
- `AllowedActions[]` (policy output; Billing SoR)

### Fields (type, required, defaults)

**Receipt (read-only in UI; authoritative from Billing):**
- `receiptId` (UUIDv7/string, required)
- `invoiceId` (UUIDv7/string, required)
- `deliveryStatus` (enum: `PENDING|SENT|FAILED|BOUNCED`, required) (BILL-DEC-011)
- `deliverySuppressed` (boolean, required) (BILL-DEC-011)
- `generatedAt` (datetime, required)
- `allowedActions[]` (string[], optional but expected for action gating) (BILL-DEC-011)
- `reprintPolicy` (object, optional; includes fields such as `remainingReprints`, `windowEndsAt`, `requiresReasonCode`, `requiresElevation`) (BILL-DEC-011)
- `balanceDue` (decimal, optional; if present, UI must display remaining balance for partial payments) (BILL-DEC-012)
- `paymentSummary` (optional; if present, includes `amountPaid`, `paymentType` = `PAID_IN_FULL|PARTIAL_PAYMENT`) (BILL-DEC-012)

**Deliver request payload (editable input):**
- `channel` (enum: `PRINT|EMAIL`, required)
- `emailAddress` (string, required for EMAIL only)
- `elevationToken` (string, optional; required when policy requires elevation)
- `reasonCode` (string, optional; required when policy requires reason code for reprint/delivery actions)

**Reprint request payload (editable input):**
- `elevationToken` (string, optional; required when policy requires elevation)
- `reasonCode` (string, optional; required when policy requires reason code)

> Decision rationale: reason codes and elevation are policy-driven and must be enforced server-side; UI only prompts when policy indicates required (BILL-DEC-011, BILL-DEC-010).

### Read-only vs editable by state/role
- Receipt fields are read-only.
- Editable inputs are only the deliver/reprint command inputs (email, reasonCode, elevationToken).
- Permissions (canonical):
  - View receipts: `billing:receipt:view`
  - Deliver receipts: `billing:receipt:deliver`
  - Reprint receipts: `billing:receipt:reprint`
  - Elevation: `billing:auth:elevate` (BILL-DEC-008)

### Derived/calculated fields (display only)
- Display “Partial payment” vs “Paid in full” based on backend-provided `paymentType` or by comparing `balanceDue>0` when provided (do not compute if fields absent).
- Display timestamps in store/local timezone.

## 9. Service Contracts (Frontend Perspective)

> Concrete Moqui service names may vary; HTTP semantics and field shapes below are normative per Billing domain guide.

### Load/view calls
1. **Load receipts by invoice**
   - `GET /billing/receipts/by-invoice/{invoiceId}`
   - Response: list of receipts or a single receipt (implementation may return array; UI must handle both by normalizing to an array)
   - Must include: `receiptId`, `deliveryStatus`, `deliverySuppressed`, and policy outputs (`allowedActions[]`, `reprintPolicy`) when applicable.

2. **Load reason codes (when required)**
   - `GET /billing/meta/reason-codes?category=REPRINT`
   - Response: list of `{code, label, description?}`

### Create/update calls
3. **Deliver receipt**
   - `POST /billing/receipts/{receiptId}/deliver`
   - Request:
     - `channel=PRINT|EMAIL`
     - `emailAddress` required for EMAIL
     - `elevationToken` when required by policy
   - Response: updated receipt (preferred) or delivery result DTO; UI must refresh receipt state after success.

### Submit/transition calls
4. **Reprint receipt**
   - `POST /billing/receipts/{receiptId}/reprint`
   - Request: `reasonCode` and/or `elevationToken` when required by policy
   - Response: printer-ready content (or a print job descriptor) plus updated policy/status; UI must print returned content and then refresh receipt.

5. **Step-up auth**
   - `POST /billing/auth/elevate`
   - Request: manager credentials (implementation-specific; UI must treat as sensitive)
   - Response: `{ elevationToken }` short-lived, single-use recommended (BILL-DEC-010)

### Error handling expectations
- 401/403: show permission error; do not retry automatically
- 409: show conflict (e.g., action no longer allowed, stale policy window)
- 422: show validation errors (missing email, invalid email, missing reason code, elevation required)
- 404: receipt not found/inaccessible → show “Receipt not available” and offer refresh
- 503: show “Service unavailable, try again” with retry button

## 10. State Model & Transitions

### Receipt lifecycle (as displayed)
- Receipt exists after successful capture (BILL-DEC-011).
- Delivery status enum (canonical): `PENDING`, `SENT`, `FAILED`, `BOUNCED` (BILL-DEC-011).
- Delivery suppression:
  - `deliverySuppressed=true` means “No Receipt” selected; receipt still exists for audit and later reprint (BILL-DEC-011).

### Allowed transitions (UI-driven)
- Deliver:
  - `deliver(PRINT)` updates delivery history/status (backend authoritative)
  - `deliver(EMAIL)` updates delivery history/status (backend authoritative)
- Reprint:
  - `reprint()` allowed only when backend policy allows; may require reason code and/or elevation token

### Role-based transitions (UI gating)
- Cashier:
  - deliver print/email if has `billing:receipt:deliver` and backend allows
  - reprint only if has `billing:receipt:reprint` and backend allows
- Supervisor/Manager:
  - may perform step-up auth (`billing:auth:elevate`) to satisfy policy requirements for reprint/delivery
- Customer service:
  - reprint with permission and reason code when required

## 11. Alternate / Error Flows

1. **Printer unavailable (frontend subsystem failure)**
- If backend deliver returns printable content but local print fails:
  - Show actionable error and allow retry print without re-submitting deliver if content is still available in-memory for that attempt.
  - If content is not retained, user retries by invoking deliver/reprint again (backend should be idempotent or policy-safe; UI must still prevent double-click in-flight).

2. **Email invalid**
- Client-side blocks obvious invalid format.
- Server-side 422 shows field-level error; allow correction and resubmit.
- Manual email must not be persisted to CRM.

3. **Email delivery failure**
- If receipt shows `FAILED` or `BOUNCED`:
  - Show status and backend-provided user-safe message if present.
  - Allow retry only if backend `allowedActions[]` includes retry/deliver action; otherwise instruct user to correct email and retry.

4. **Unauthorized**
- 403 on deliver/reprint/elevate:
  - Show “Not authorized” and include correlationId if provided.
  - Do not reveal policy internals beyond what backend already returned.

5. **Concurrency / double-submit**
- Disable buttons while request in-flight.
- If backend returns “already delivered/reprinted” semantics, treat as success and refresh receipt.

6. **Empty states**
- `GET receipts by invoice` returns empty:
  - Show “No receipt found for this invoice.” with a Refresh action.
  - Do not auto-create receipts in frontend; receipt generation is backend responsibility (BILL-DEC-011).

## 12. Acceptance Criteria

### Scenario 1: Receipt details available after successful capture
Given a cashier completes a payment capture successfully for an invoice with an `invoiceId`  
When the payment success screen loads  
Then the UI requests receipts via `GET /billing/receipts/by-invoice/{invoiceId}`  
And the UI displays the `receiptId` and `deliveryStatus` for the receipt returned  
And the UI displays receipt actions only if the user has the required permissions and the receipt `allowedActions[]` includes them.

### Scenario 2: Print receipt successfully
Given a receipt exists for the invoice  
And the user has permission `billing:receipt:deliver`  
And the receipt `allowedActions[]` includes `DELIVER_PRINT` (or equivalent print action)  
When the cashier clicks "Print Receipt"  
Then the UI calls `POST /billing/receipts/{receiptId}/deliver` with `channel=PRINT`  
And the UI prints the backend-provided printer-ready content  
And the UI refreshes receipt data and shows updated delivery status/history.

### Scenario 3: Printer error offers retry without double-submit
Given a receipt exists for the invoice  
And the cashier initiates "Print Receipt"  
When the local printer subsystem returns an error  
Then the UI shows an actionable printer error message  
And the UI allows the cashier to retry printing  
And the UI prevents duplicate in-flight deliver requests for the same click action.

### Scenario 4: Email receipt with manual email entry (not stored in CRM)
Given a receipt exists for the invoice  
And the user has permission `billing:receipt:deliver`  
And the receipt `allowedActions[]` includes `DELIVER_EMAIL` (or equivalent email action)  
When the cashier clicks "Email Receipt"  
Then the UI prompts for an email address and validates basic syntax  
When the cashier submits a valid email  
Then the UI calls `POST /billing/receipts/{receiptId}/deliver` with `channel=EMAIL` and `emailAddress`  
And the UI refreshes receipt data and displays `deliveryStatus` as `PENDING` or `SENT`  
And the UI does not create or update any CRM contact record.

### Scenario 5: Customer selects “No Receipt” (delivery suppressed)
Given a receipt exists for the invoice  
And the receipt `allowedActions[]` includes `SUPPRESS_DELIVERY` (or equivalent)  
When the cashier selects "No Receipt"  
Then the UI submits the backend command to suppress delivery for that receipt  
And the UI shows `deliverySuppressed=true` after refresh  
And the UI does not initiate print or email delivery.

### Scenario 6: Reprint allowed with reason code and elevation when required
Given a receipt exists for the invoice  
And the user has permission `billing:receipt:reprint`  
And the receipt `allowedActions[]` includes `REPRINT`  
When the cashier clicks "Reprint Receipt"  
And the receipt `reprintPolicy.requiresReasonCode=true`  
Then the UI requires selecting a reason code from `GET /billing/meta/reason-codes?category=REPRINT` before submitting  
And when the receipt `reprintPolicy.requiresElevation=true`  
Then the UI requires obtaining an `elevationToken` via `POST /billing/auth/elevate` and includes it in the reprint request  
And the UI prints the backend-provided reprint content and refreshes receipt state.

### Scenario 7: Reprint denied due to permissions
Given a receipt exists  
And the user lacks permission `billing:receipt:reprint`  
When the user attempts to reprint  
Then the UI does not call the reprint endpoint  
And the UI displays an authorization error.

### Scenario 8: Email delivery failure status and retry gating
Given a receipt exists and its `deliveryStatus` is `FAILED` or `BOUNCED`  
When the cashier views receipt details  
Then the UI displays the failure status  
And the UI shows a retry action only if `allowedActions[]` includes a retry/deliver action  
And if retry is not allowed, the UI instructs the user to correct the email and try again later.

## 13. Audit & Observability

### User-visible audit data
- `receiptId`
- `deliveryStatus` and `deliverySuppressed`
- Reprint policy output (e.g., remaining reprints/window) when provided
- Any backend-provided delivery/reprint history entries (timestamps and channels) if included in receipt payload

### Status history
- Show chronological list of delivery attempts and reprints when backend provides it; otherwise show current status only.

### Traceability expectations
- Propagate W3C Trace Context headers (`traceparent`, `tracestate` optional) on all Billing calls (BILL-DEC-015).
- UI logs (client-side) must include non-PII identifiers only: `invoiceId`, `receiptId`, correlationId.
- Never log: email addresses, elevation tokens, signed URLs/tokens, payment instrument secrets (BILL-DEC-015, BILL-DEC-010).

---

## 14. Non-Functional UI Requirements

- **Performance:** Receipt load must not block payment success rendering; show loading state; allow user to proceed while receipt loads.
- **Accessibility:** All actions keyboard-navigable; dialogs have focus trapping; status updates announced via ARIA live region.
- **Responsiveness:** Works on standard POS tablet/desktop resolutions; receipt actions usable in narrow layouts.
- **i18n/timezone/currency:** Display timestamps in store/local timezone. If amounts/balance are shown, use currency from backend-provided data; do not hardcode currency symbols.

## 15. Applied Safe Defaults

- **SD-UX-EMPTY-STATE:** Provide explicit empty/loading states for receipt not yet available; qualifies as UI ergonomics. Impacted sections: UX Summary, Alternate/Error Flows.
- **SD-UX-INFLIGHT-GUARD:** Disable action buttons during in-flight requests to prevent double-submit; qualifies as UI ergonomics. Impacted sections: Functional Behavior, Alternate/Error Flows.
- **SD-ERR-STD-MAPPING:** Map 401/403/404/409/422/503 to standard user messages and retry affordances; qualifies as standard error-handling mapping. Impacted sections: Service Contracts, Alternate/Error Flows.
- **SD-OBS-CORRELATION:** Propagate W3C trace context and include correlationId in user-facing error UI when provided, without PII; qualifies as observability boilerplate. Impacted sections: Audit & Observability.
