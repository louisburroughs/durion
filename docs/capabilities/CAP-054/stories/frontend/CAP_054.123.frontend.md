## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Work Order: Display Operational Context (Location/Bay/Assigned Mechanics) with Manager Override + Audit (Status-Gated)

### Primary Persona
Mechanic (primary), Shop Manager / Service Advisor (secondary for privileged overrides)

**Persona Metadata**
- `primary_persona`: `Mechanic (primary), Shop Manager / Service Advisor (secondary for privileged overrides)`
- `canonical_persona`: `Technician`
- `persona_family`: `Technician`
- `actor_type`: `human`

### Business Value
Mechanics can immediately see where to work (location/bay) and who they’re working with (assigned mechanics), reducing misrouting and improving shop-floor coordination; managers retain controlled ability to correct dispatch context with traceable audit, including after work has started.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Mechanic  
- **I want** the work order view to display operational context (location/bay/assigned mechanics/schedule/resources/constraints)  
- **So that** I know where to work and who/what is assigned while executing the work order.

### In-Scope
- Add an **Operational Context** section to the existing Work Order edit/view screen.
- Fetch and render operational context from **Shopmgr (system of record)** (DECISION-INVENTORY-005).
- Determine “work started” from Workexec work order status using the workexec taxonomy (DECISION-INVENTORY-004).
- Provide a **manager-only override** action that:
  - is available **both pre-start and post-start** (manager-only), and
  - is **audited** and **concurrency-safe** (DECISION-INVENTORY-005, DECISION-INVENTORY-014).
- Display user-visible audit metadata (created/updated + override result metadata when available) (DECISION-INVENTORY-014).
- Handle partial/missing context and upstream unavailability gracefully (DECISION-INVENTORY-009).

### Out-of-Scope
- Authoring/maintaining operational context as a standalone CRUD record in workexec UI (Shopmgr remains SoR).
- Defining RBAC policies/role inheritance (security domain defines; workexec consumes capability signals and enforces via 403 handling) (DECISION-INVENTORY-013).
- Implementing event-stream consumption in the frontend (no inbox/event UI here).
- Implementing work order lifecycle transitions (start/complete/etc.) beyond reading status for gating.

## 3. Actors & Stakeholders
- **Mechanic**: Views work order; needs operational context for execution.
- **Shop Manager**: Performs operational context overrides when needed; requires audit.
- **Service Advisor**: May perform overrides if granted the same capability (capability-driven; do not hardcode role names) (DECISION-INVENTORY-013).
- **Shopmgr (Shop Management)**: System of record for operational context and appointment scheduling (DECISION-INVENTORY-010).
- **Workexec backend**: System of record for work order execution status and the override action/audit trail (DECISION-INVENTORY-004, DECISION-INVENTORY-005).
- **Audit/Compliance**: Requires traceability for overrides and post-start changes (DECISION-INVENTORY-014).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From `WorkOrderBoard.xml` → open a work order → `WorkOrderEdit.xml` (DECISION-INVENTORY-002).
- Direct navigation/deep link to `WorkOrderEdit` with `workOrderId`.

### Screens to create/modify
- **Modify**: `durion-workexec/WorkOrderEdit.xml`
  - Add an “Operational Context” section.
  - Add an “Override Operational Context” action (visible only when capability allows).

### Navigation context
- Operational context is displayed within the Work Order screen and loads asynchronously.
- Provide a manual “Refresh context” action within the section.

### User workflows (happy + alternate paths)

#### Happy path: Mechanic views operational context
1. Mechanic opens Work Order (`WorkOrderEdit.xml`).
2. UI loads Work Order (existing) and reads `statusId` (and `isStarted` if provided).
3. UI loads operational context and renders fields.
4. UI shows “Work started” indicator when started (status-based) (DECISION-INVENTORY-004).

#### Manager flow: override (pre-start)
1. Manager opens Work Order in `WO_CREATED`/`WO_SCHEDULED` (or other pre-start status).
2. UI shows “Override operational context” action (capability-gated).
3. Manager edits allowed override fields + enters required reason.
4. UI submits override with `Idempotency-Key` header (DECISION-INVENTORY-012).
5. UI refreshes operational context and displays updated metadata.

#### Manager flow: override (post-start)
1. Manager opens Work Order in `WO_IN_PROGRESS` or later.
2. UI still allows override (manager-only) and shows a warning that the work has started and override will be audited (DECISION-INVENTORY-005).
3. Submit + refresh as above.

#### Alternate path: partial context or upstream failure
- If operational context is missing optional fields, show “Not set”/empty list states.
- If Shopmgr is unavailable, show an inline error and allow retry; do not block the rest of the Work Order screen (DECISION-INVENTORY-009).

## 7. Business Rules (Translated to UI Behavior)

### Validation
Override submission must enforce client-side validation before calling backend:
- `reason` is required; trim whitespace; must be non-empty.
- At least one override field must be provided in `overrides` object.
- IDs are opaque strings; do not validate UUID format (DECISION-INVENTORY-003).
- If schedule fields are present:
  - Accept ISO-8601 timestamps; do not enforce timezone beyond parsing.
  - If both start and end provided, client may validate `end >= start` (UI ergonomics only); backend remains authoritative.

### Enable/disable rules
- Operational Context section is visible whenever the work order is viewable.
- Override action:
  - Visible/enabled only when capability indicates permission (preferred) OR shown but disabled with tooltip if capability unknown.
  - Backend 403 must be handled even if UI shows the action (DECISION-INVENTORY-013).
- Terminal work orders:
  - If status is terminal (`WO_COMPLETED`, `WO_CANCELLED`, `WO_INVOICED` if present), disable override action and show “Work order is closed; operational context cannot be overridden.”

### Visibility rules
- Show “Work started” indicator when started (DECISION-INVENTORY-004):
  - Started means `WO_IN_PROGRESS` or later.
  - Prefer backend-provided `isStarted`; if absent, use status mapping in State Model section.
- Show “Data source: Shop Management (Shopmgr)” label in the section (DECISION-INVENTORY-005).

### Error messaging expectations
- Load failure (5xx/timeout): “Operational context is temporarily unavailable. You can still view the work order.”
- 403 on override: “You do not have permission to override operational context.”
- 409 on override: “Operational context changed since you loaded this page. Refresh and try again.”
- 400 on override: show field-level errors when provided; otherwise show generic “Please correct the highlighted fields.”
- 404: “Operational context not found for this work order.”

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation may use screen actions calling services; regardless of implementation, the following behaviors must be met.

### Load/view calls

1. **Load Work Order (existing)**
   - Must return `statusId` and `workOrderId`.
   - Preferred: also return `isStarted` boolean (DECISION-INVENTORY-004).

2. **Load Operational Context (Shopmgr SoR)**
   - Required behavior: fetch operational context by workOrderId.
   - Suggested REST shape (align to existing patterns in repo; path may differ):
     - `GET /rest/api/v1/shopmgr/workorders/{workOrderId}/operational-context`
   - Success: `200 OK` with Operational Context DTO.
   - Errors:
     - `404` if no context exists
     - `403` if user cannot view
     - `5xx`/timeout for upstream failure

### Create/update calls
- None (no direct CRUD).

### Submit/transition calls

1. **Override Operational Context (Workexec)**
   - Required behavior: manager-only override, audited, concurrency-safe (DECISION-INVENTORY-005).
   - Suggested REST shape:
     - `POST /rest/api/v1/workexec/workorders/{workOrderId}/operational-context:override`
   - Headers:
     - `Idempotency-Key: <uuid>` (required for submit; reuse on retry) (DECISION-INVENTORY-012)
   - Request body:
     ```json
     {
       "overrides": {
         "bayId": "BAY-2",
         "scheduledStartAt": "2026-01-21T16:00:00Z",
         "scheduledEndAt": "2026-01-21T18:00:00Z"
       },
       "reason": "Reassigned bay due to lift maintenance",
       "version": "N"
     }
     ```
     Notes:
     - Do **not** send `actorId` from the client unless the existing backend contract explicitly requires it; backend should derive actor from auth context to avoid spoofing (DECISION-INVENTORY-005 rationale: “avoid accepting client-supplied actor IDs”).
   - Success:
     - Prefer `200 OK` returning updated Operational Context DTO (or at least updated `version` + metadata).
     - If backend returns acknowledgment only, UI must follow with a GET refresh.
   - Errors:
     - `400` validation errors (standard envelope)
     - `403` forbidden
     - `409` conflict on stale version (when versioning is supported)
     - `5xx` unexpected

### Error handling expectations
- Errors should conform to standard envelope (DECISION-INVENTORY-011):
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`
- UI must:
  - show `message` to user when safe,
  - log `correlationId` for support,
  - map `fieldErrors` to form fields.

## 10. State Model & Transitions

### Allowed states (workexec)
Use workexec status taxonomy for “started” gating (DECISION-INVENTORY-004). For this story, treat statuses as:

- Pre-start: `WO_CREATED`, `WO_SCHEDULED`
- Started (in-progress-or-later): `WO_IN_PROGRESS` and later statuses including `READY_FOR_PICKUP` and beyond (DECISION-INVENTORY-004)

> Note: The repository also contains a separate state machine doc with different names (e.g., `APPROVED`, `ASSIGNED`, `WORK_IN_PROGRESS`). For this frontend story, the gating rule is: **started = `WO_IN_PROGRESS` or later**; prefer backend-provided `isStarted` to avoid mismatches across taxonomies (DECISION-INVENTORY-004).

### Role-based transitions
- Not implemented here; only read status and gate override action.

### UI behavior per state
- Pre-start (`WO_CREATED`, `WO_SCHEDULED`):
  - Show operational context.
  - If user has override capability, allow override.
- Started (`WO_IN_PROGRESS` or later):
  - Show “Work started” indicator.
  - If user has override capability, allow override but show warning “This change will be audited.”
- Terminal (`WO_COMPLETED`, `WO_CANCELLED`, `WO_INVOICED` if present):
  - Disable override action.

## 11. Alternate / Error Flows

### Validation failures (override)
- Missing reason:
  - Prevent submit; show inline error on reason field.
- No override fields set:
  - Prevent submit; show form-level error “Select at least one change to submit.”
- Invalid timestamp ordering (if both provided):
  - Show inline error; allow submit only after correction.

### Concurrency conflicts
- If backend returns `409 Conflict`:
  - Show conflict banner with “Refresh context” action.
  - Keep user-entered reason/fields in the modal so they can re-submit after refresh.

### Unauthorized access
- If operational context load returns `403`:
  - Show “Not authorized to view operational context” and do not display details.
- If override returns `403`:
  - Show permission error; keep modal open for user to copy reason if needed.

### Empty states
- `assignedMechanics` empty:
  - Display “No mechanics assigned”.
- Optional fields missing:
  - Display “Not set”.

### Upstream unavailable
- If operational context load fails (timeout/5xx):
  - Show inline error + retry.
  - Do not block the rest of the Work Order screen.

## 12. Acceptance Criteria

### Scenario 1: Display operational context (happy path)
**Given** a work order exists and the operational context endpoint returns location, bay, schedule, assigned mechanics, and metadata  
**When** a Mechanic opens `WorkOrderEdit` for that work order  
**Then** the Operational Context section displays all returned fields  
**And** the section labels the data source as Shop Management (Shopmgr)  
**And** the UI displays `lastUpdatedAt` and `lastUpdatedBy` when present.

### Scenario 2: Display partial context (graceful degradation)
**Given** the operational context endpoint returns location and an empty `assignedMechanics` list and omits bay/schedule/resources/constraints  
**When** a Mechanic opens the work order  
**Then** the UI displays location  
**And** the UI displays “No mechanics assigned”  
**And** the UI displays “Not set” for missing optional fields  
**And** the rest of the Work Order screen remains usable.

### Scenario 3: Context unavailable does not block work order
**Given** the operational context request fails with a 5xx or network timeout  
**When** a user opens the work order  
**Then** the Operational Context section shows an inline error message and a retry action  
**And** the Work Order details outside the section are still visible and usable.

### Scenario 4: Manager override allowed pre-start (capability-gated)
**Given** the current user has the operational-context override capability  
**And** the work order is not started  
**When** the user submits an override with a non-empty reason and at least one override field  
**Then** the UI sends the override request with an `Idempotency-Key` header  
**And** on success, the UI refreshes operational context  
**And** the updated values and metadata are displayed.

### Scenario 5: Manager override allowed after start (audited)
**Given** the current user has the operational-context override capability  
**And** the work order is started (`isStarted=true` or status is `WO_IN_PROGRESS` or later)  
**When** the user opens the override modal  
**Then** the UI displays a warning that work has started and the override will be audited  
**When** the user submits a valid override  
**Then** the UI processes it the same as pre-start and refreshes the context on success.

### Scenario 6: Override rejected due to permission
**Given** the current user does not have the operational-context override capability (or backend denies)  
**When** the user attempts to submit an override  
**Then** the UI displays an authorization error message  
**And** the displayed operational context remains unchanged.

### Scenario 7: Override rejected due to version conflict
**Given** a manager loads operational context version `N`  
**And** the operational context changes to version `N+1` before the manager submits  
**When** the manager submits an override using version `N`  
**Then** the UI receives `409 Conflict`  
**And** the UI prompts the user to refresh  
**And** after refresh, the UI displays version `N+1` (when version is provided by the backend).

### Scenario 8: IDs treated as opaque strings
**Given** the operational context contains non-UUID identifiers (e.g., `BAY-2`, `WO-123`)  
**When** the UI renders the Operational Context section  
**Then** the UI displays these IDs/labels without client-side UUID validation errors.
