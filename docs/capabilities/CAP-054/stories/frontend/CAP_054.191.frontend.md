## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting Periods: Create / Close / Reopen with Posting Locks (per Business Unit)

### Primary Persona
Finance / Accounting Manager (with period management permissions)

### Business Value
Enforce deterministic posting controls by accounting period per business unit, protect financial reporting integrity, and provide auditable exception handling for reopening closed periods.

---

## 2. Story Intent

### As a / I want / So that
**As a** Finance / Accounting Manager,  
**I want** to create, close, and (with elevated permission) reopen accounting periods per business unit,  
**so that** postings are blocked in closed periods unless explicitly reopened with an audit reason.

### In-scope
- Frontend screens to:
  - list/filter accounting periods by business unit and date range
  - create accounting periods with non-overlap validation feedback
  - close an open period
  - reopen a closed period with mandatory reason and elevated permission gate
  - view audit/history for period actions (create/close/reopen)
- Frontend handling of “posting blocked because period closed” errors (surface deterministic error message/code to user).

### Out-of-scope
- Implementing backend posting enforcement logic itself (frontend only consumes and displays errors).
- Defining GL accounts, posting rules, or journal entry behavior.
- Designing business unit master data (frontend only selects an existing business unit reference).
- Reporting UI beyond the period/audit views.
- Any “reversal” or retroactive posting workflows beyond reopen (separate stories).

---

## 3. Actors & Stakeholders

### Actors
- **Accounting Manager**: can create and close periods.
- **Privileged Accounting Manager / Controller**: can reopen periods (requires special permission).
- **Auditor / Finance Reviewer**: reads period history/audit events.
- **System (Moqui app)**: enforces permissions and displays backend validation errors.

### Stakeholders
- Finance/Accounting leadership (controls and auditability)
- Operations (impacts ability to post transactions)
- Engineering (screen/service wiring, permission gating)
- Compliance/audit (exception logging for reopen)

## 4. Preconditions & Dependencies

### Preconditions
- User authentication is available in Moqui.
- Permission concepts exist and are checkable in UI.
- A Business Unit concept exists and is selectable (entity + id + display name).

### Dependencies (backend/API)
This story assumes Accounting-domain backend support exists (or will exist) for Accounting Period enforcement (**Decision AD-012**). Frontend depends on the following endpoint families being available (names are required for buildability; request/response fields remain backend-authoritative):

- `GET  /accounting/periods/list`
- `GET  /accounting/periods/detail?accountingPeriodId=...`
- `POST /accounting/periods/create`
- `POST /accounting/periods/close`
- `POST /accounting/periods/reopen`

Audit/history may be:
- embedded in `/accounting/periods/detail`, or
- provided via `GET /accounting/periods/history?accountingPeriodId=...`

**Decision rationale:** The Accounting domain guide defines period enforcement as authoritative and mandatory (**AD-012**) and requires explicit permission gating (**AD-013**). The exact `/accounting/periods/*` endpoints are not enumerated in the guide, but are consistent with the normative `/accounting/*` namespace pattern and required to make the frontend implementable without inventing cross-domain routes.

Additional dependency:
- Business Unit selector data source (likely Organization/Party) must be available via an existing shared service; this story will consume it read-only.

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side, then server-side authoritative)
**Create Period**
- `businessUnitId`: required
- `startDate`: required
- `endDate`: required
- `startDate <= endDate` (client-side validation)
- Non-overlap with existing periods for the business unit (server-side validation; UI must render conflict clearly)

**Close Period**
- Allowed only if current status is OPEN (UI hides/disabled if not)

**Reopen Period**
- Allowed only if current status is CLOSED
- Requires elevated permission (UI hides action if lacking permission) (**Decision AD-013**)
- **Reason is mandatory** and must be **>= 10 characters** (client-side + server-side)  
  **Decision rationale:** Accounting domain mandates justification for sensitive mutations with minimum length >= 10 chars for human-initiated actions (customer assignment, ingestion retry). Reopen is an exception action with audit requirements; applying the same minimum is consistent with the domain’s audit posture and does not define accounting policy beyond audit hygiene.

**Posting blocked because period closed**
- Backend is authoritative for period enforcement (**Decision AD-012**). UI must not infer open/closed eligibility for a transaction date beyond displaying the backend error.

### Enable/disable rules
- Disable submit while service call in flight.
- Disable Close/Reopen buttons while action in flight to prevent double submits.
- In detail view, actions must re-check current status from latest loaded data (avoid stale UI).
- If backend returns 409 indicating state already changed, UI must force reload before allowing another attempt.

### Visibility rules (permissions)
Because **Decision AD-013** requires explicit permission mapping and the guide does not define period-specific tokens, this story defines required permissions for Accounting Period management:

- View periods (list/detail): `accounting:periods:view`
- Create/close periods: `accounting:periods:manage`
- Reopen periods: `accounting:periods:reopen`
- View period audit/history: `accounting:periods:audit:view` (or included in `accounting:periods:view` if backend does not separate)

**Decision rationale:** The accounting guide provides normative permission patterns but not period-specific strings. Defining explicit tokens is necessary to ship screens securely-by-default and aligns with AD-013’s “do not ship screens without explicit permission mapping”.

### Error messaging expectations
- Overlap conflict: show message “Date range overlaps an existing period for this business unit.” Include conflicting period identifiers/date range if returned.
- Period closed posting error: show deterministic message and preserve backend error code (e.g., `ERR_ACCOUNTING_PERIOD_CLOSED`).
- Unauthorized: show “You do not have permission to perform this action.” Preserve HTTP 403.
- Concurrency conflict (optimistic locking or stale update): show “This period was changed by another user. Reload and try again.”

## 8. Data Requirements

### Entities involved (frontend perspective)
- `AccountingPeriod`
- `BusinessUnit` (or equivalent entity representing business unit)
- `User` (for display of closedBy/reopenedBy if returned)
- `AccountingPeriodAuditEvent` (or generic audit log entity)

### Fields (type, required, defaults)

#### AccountingPeriod (minimum required for UI)
- `accountingPeriodId` (UUIDv7) — required, read-only
- `businessUnitId` (UUIDv7) — required, editable on create only
- `businessUnitName` (string) — read-only (derived via join)
- `startDate` (date) — required, editable on create only
- `endDate` (date) — required, editable on create only
- `status` (enum: `OPEN`, `CLOSED`) — read-only except via transitions
- `createdAt` (datetime) — read-only
- `createdByUserId` (UUIDv7/string) — read-only
- `closedAt` (datetime, nullable) — read-only
- `closedByUserId` (UUIDv7/string, nullable) — read-only
- `reopenedAt` (datetime, nullable) — read-only
- `reopenedByUserId` (UUIDv7/string, nullable) — read-only
- `updatedAt` (datetime) — read-only
- `updatedByUserId` (UUIDv7/string) — read-only
- `version` or `lastUpdatedStamp` (optimistic lock token, if used) — read-only but must be submitted back on close/reopen if required by backend

**Decision rationale:** UUIDv7 is the identifier strategy for accounting identifiers (**Decision AD-006**). If backend uses non-UUID for user ids, UI treats as opaque strings and does not validate as UUID.

#### AccountingPeriodAuditEvent (for display)
- `eventId` (UUIDv7) — read-only
- `accountingPeriodId` (UUIDv7) — read-only
- `action` (enum/string: `CREATED`, `CLOSED`, `REOPENED`) — read-only
- `actorUserId` (string/UUIDv7) — read-only
- `occurredAt` (datetime) — read-only
- `reason` (text, nullable except required for REOPENED) — read-only

### Read-only vs editable by state/role
- Only create form fields are editable (businessUnitId, startDate, endDate).
- Close/Reopen are transitions only (no direct edit of status).
- Reason is editable only within the reopen action dialog and is stored as part of the audit event (and/or transition record) per backend.

### Derived/calculated fields
- Display label “Period: YYYY-MM-DD to YYYY-MM-DD”
- Status badge from `status`
- “Locked for posting” derived as `status == CLOSED`

## 9. Service Contracts (Frontend Perspective)

> Request/response schemas are backend-authoritative; UI must not invent fields. The contracts below define required endpoints, required inputs, and minimum outputs needed for UI behavior.

### Load/view calls

1) **List periods**
- `GET /accounting/periods/list`
- Query params:
  - `businessUnitId` (required)
  - `status` (optional: `OPEN|CLOSED`)
  - `fromDate` (optional, inclusive)
  - `toDate` (optional, inclusive)
  - `pageIndex`, `pageSize`, `orderBy` (recommended)
- Response:
  - `data[]` of period summaries including: `accountingPeriodId`, `startDate`, `endDate`, `status`, `businessUnitName`
  - pagination metadata (if supported)

2) **Get period detail**
- `GET /accounting/periods/detail?accountingPeriodId=...`
- Response:
  - full `AccountingPeriod`
  - optionally `history[]` (audit events)

3) **Get period history** (if not embedded)
- `GET /accounting/periods/history?accountingPeriodId=...`
- Response:
  - `history[]` ordered by `occurredAt` desc

### Create/update calls

4) **Create period**
- `POST /accounting/periods/create`
- Body:
  - `businessUnitId`, `startDate`, `endDate`
- Response:
  - created `accountingPeriodId` and created record (or at least id)

### Submit/transition calls

5) **Close period**
- `POST /accounting/periods/close`
- Body:
  - `accountingPeriodId`
  - optimistic lock token if required (`lastUpdatedStamp`/`version`)
- Response:
  - updated record (status `CLOSED`, closed metadata)

6) **Reopen period**
- `POST /accounting/periods/reopen`
- Body:
  - `accountingPeriodId`
  - `reason` (>= 10 chars)
  - optimistic lock token if required
- Response:
  - updated record (status `OPEN`, reopened metadata)
  - audit event reference (optional)

### Error handling expectations (mapping)
Use canonical error shape (**Decision AD-013**):

```json
{ "errorCode": "...", "message": "...", "details": { } }
```

- `400/422`: validation errors (missing reason, start>end, missing businessUnitId)
- `403`: permission denied (do not leak record existence)
- `404`: not found (safe messaging)
- `409`: overlap on create OR period already in target state OR optimistic lock conflict
- Posting rejection elsewhere:
  - error code `ERR_ACCOUNTING_PERIOD_CLOSED` (or backend-provided equivalent); UI must display code and user-safe message.

## 10. State Model & Transitions

### Allowed states (AccountingPeriod.status)
- `OPEN`
- `CLOSED`

### Transitions
- `OPEN` → `CLOSED` via **Close Period**
  - Permission: `accounting:periods:manage`
- `CLOSED` → `OPEN` via **Reopen Period**
  - Permission: `accounting:periods:reopen`
  - Requires: reason (>= 10 chars)

### UI behavior per state
- OPEN:
  - Show “Close Period” if permitted
  - Hide “Reopen Period”
  - Indicate posting allowed
- CLOSED:
  - Show “Reopen Period” if permitted
  - Hide “Close Period”
  - Indicate posting locked/blocked for dates in range

## 11. Alternate / Error Flows

### Validation failures
- Create with missing fields → inline field errors + no request (client-side)
- Create with endDate < startDate → inline error + no request
- Create overlap detected server-side → show banner error + keep form values
- Reopen without reason or < 10 chars → inline reason error, no request (client-side)

### Concurrency conflicts
- If close/reopen returns 409 indicating stale version:
  - show message “Period was updated by another user”
  - provide “Reload” action on the detail screen
  - after reload, clear any pending dialog inputs (reason) to avoid applying to changed state

### Unauthorized access
- If user navigates directly to create/detail URL without permission:
  - screen shows access denied and does not render action controls
  - do not attempt to fetch restricted payloads if permission absent (deny by default)

### Empty states
- List with no periods → show empty-state guidance: “No periods found for selected business unit/date range.” with “Clear filters” and (if permitted) “Create Period”.

## 12. Acceptance Criteria

### Scenario 1: List periods for a business unit
**Given** I am authenticated  
**And** I have permission `accounting:periods:view`  
**When** I open the Accounting Periods screen  
**And** I select a business unit  
**Then** the UI requests `GET /accounting/periods/list` with that `businessUnitId`  
**And** I see a list of accounting periods for that business unit  
**And** each row shows start date, end date, and status  

### Scenario 2: Create an accounting period successfully
**Given** I am authenticated  
**And** I have permission `accounting:periods:manage`  
**When** I create a period for business unit “BU-1” with start date “2026-01-01” and end date “2026-01-31”  
**Then** the UI calls `POST /accounting/periods/create` with those values  
**And** the period is created with status “OPEN”  
**And** I am navigated to the period detail screen for the returned `accountingPeriodId`  

### Scenario 3: Reject creating an overlapping accounting period
**Given** an accounting period exists for business unit “BU-1” from “2026-01-01” to “2026-01-31”  
**And** I have permission `accounting:periods:manage`  
**When** I attempt to create another period for “BU-1” from “2026-01-15” to “2026-02-15”  
**Then** the system rejects the request with HTTP 409  
**And** the response includes an `errorCode` and user-safe `message`  
**And** the UI displays an overlap validation message  
**And** the form remains editable with my entered values preserved  

### Scenario 4: Close an open period successfully
**Given** I am authenticated  
**And** I have permission `accounting:periods:manage`  
**And** an accounting period exists with status “OPEN”  
**When** I click “Close Period” and confirm  
**Then** the UI calls `POST /accounting/periods/close` for that `accountingPeriodId`  
**And** the period status becomes “CLOSED”  
**And** the UI displays `closedAt` and `closedByUserId` if provided  
**And** the “Close Period” action is no longer available  

### Scenario 5: Reopen a closed period with reason (authorized)
**Given** I am authenticated  
**And** I have permission `accounting:periods:reopen`  
**And** an accounting period exists with status “CLOSED”  
**When** I click “Reopen Period”  
**And** I enter the reason “Correcting mis-categorized invoice #123”  
**And** I confirm the reopen action  
**Then** the UI calls `POST /accounting/periods/reopen` with the reason  
**And** the period status becomes “OPEN”  
**And** the period history/audit section includes a “REOPENED” entry with my user and reason (if history is provided by backend)  

### Scenario 6: Reopen a closed period without sufficient reason (client validation)
**Given** I am authenticated  
**And** I have permission `accounting:periods:reopen`  
**And** an accounting period exists with status “CLOSED”  
**When** I click “Reopen Period” and submit with an empty reason or a reason shorter than 10 characters  
**Then** the UI prevents submission  
**And** the reason field shows a validation error indicating the minimum length requirement  

### Scenario 7: Reopen denied without permission
**Given** I am authenticated  
**And** I do not have permission `accounting:periods:reopen`  
**And** an accounting period exists with status “CLOSED”  
**When** I view the period detail screen  
**Then** I do not see the “Reopen Period” action  
**And** if I attempt to call reopen via direct request, I receive HTTP 403 and the UI shows a permission error without revealing additional record details  

### Scenario 8: Posting attempt blocked by closed period is shown deterministically
**Given** an accounting period for business unit “BU-1” is “CLOSED” for dates including “2026-01-10”  
**When** I attempt a posting operation elsewhere in the app for business unit “BU-1” with transaction date “2026-01-10”  
**And** the backend responds with error code “ERR_ACCOUNTING_PERIOD_CLOSED”  
**Then** the UI shows an error message indicating posting is blocked due to a closed accounting period  
**And** the UI displays the backend error code “ERR_ACCOUNTING_PERIOD_CLOSED” in a copyable/support-friendly way
