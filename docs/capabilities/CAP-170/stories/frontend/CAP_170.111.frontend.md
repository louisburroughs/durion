- User navigates to a list screen (Runs/Normalized/Unmapped/Exceptions)
- User changes filters and clicks **Search**
- User opens a detail view
- User performs triage update (PATCH) on Unmapped or Exception records

### UI actions

#### Runs list
- Render a filter form:
  - Date range (`from`, `to`) required (default last 7 days; see Applied Safe Defaults)
  - Optional filters if supported by backend contract (e.g., `sourceSystem`, `vendorCode`, `status`, `severity`)
- On Search:
  - Validate date range
  - Call `GET /inventory/availability-feeds/runs` with cursor pagination
- Render list rows with stable identifiers and timestamps; include `correlationId` when present (DECISION-INVENTORY-013)

#### Run detail
- Load `GET /inventory/availability-feeds/runs/{runId}`
- Render run metadata and summary counts (as provided)
- Provide navigation links to Exceptions/Unmapped/Normalized with pre-filled filters (only using filters supported by endpoints; see Open Questions)

- List: `GET /inventory/availability-feeds/normalized` with cursor pagination and date range filters (DECISION-INVENTORY-013)
- Detail: load normalized record detail endpoint (see Open Questions)
- Render normalized fields and raw fields; any JSON-like fields must use safe JSON viewer (DECISION-INVENTORY-015)

#### Unmapped list/detail + update
- List: `GET /inventory/availability-feeds/unmapped` with cursor pagination and date range filters
- Detail: load unmapped record detail endpoint (see Open Questions)
- Update:
  - If user has `inventory:feedops:unmapped:update`, show status update control
  - Allowed statuses in v1: `PENDING_REVIEW`, `IGNORED`, `RESOLVED` (DECISION-INVENTORY-013)

## 7. Business Rules (Translated to UI Behavior)

### Decision-backed rules (normative)
- **BR-INV-013-A (Feed ops ownership & updates):** UI must implement feed ops screens and only allow the documented PATCH updates for unmapped/exceptions. (DECISION-INVENTORY-013)
- **BR-INV-003-A (Cursor pagination):** All list screens must use cursor pagination (`pageSize`, `pageToken`, `nextPageToken`) and must not rely on `totalCount`. (DECISION-INVENTORY-003)
- **BR-INV-015-A (Safe JSON rendering):** Any JSON/payload/details fields must be escaped, truncated in list views, and expanded/copyable on demand; never persisted to localStorage. (DECISION-INVENTORY-015)
- **BR-INV-010-A (Permission gating):**
  - Read access gated by `inventory:feedops:view`
  - Unmapped updates gated by `inventory:feedops:unmapped:update`
  - Exception updates gated by `inventory:feedops:exception:update` (DECISION-INVENTORY-010)
- **BR-INV-012-A (401/403 behavior + correlation):**
  - 401 triggers login/session refresh per app convention
  - 403 shows forbidden state without leaking data
  - Show correlation ID in technical details on errors (DECISION-INVENTORY-012)
- **BR-INV-013-B (Retention/date range):** Default to a bounded date range and tolerate missing older records without error. (DECISION-INVENTORY-013)

### Validation
- Date range filters:
  - `from` and `to` required on Runs/Normalized/Unmapped/Exceptions lists
  - Must enforce `from <= to`; block Search if invalid
- Update forms:
  - Unmapped status must be one of: `PENDING_REVIEW`, `IGNORED`, `RESOLVED` (DECISION-INVENTORY-013)
  - Notes fields (if present) must be trimmed; empty string treated as null
  - If backend provides version/etag, UI must include it on PATCH to avoid lost updates (see Service Contracts)

### Enable/disable rules
- Disable Search and Update buttons while request is in-flight
- Hide update controls if permission is missing; still handle backend 403 if permission discovery is unavailable or stale
- Disable “Save” if no changes were made (prevents no-op PATCH)

### Error messaging expectations (deterministic schema)
- Errors follow deterministic schema and plain JSON responses (DECISION-INVENTORY-003)
- 400/422: show inline validation errors when field mapping is possible; otherwise show banner
- 401: redirect to login/session refresh
- 403: forbidden state; do not render partial sensitive payloads
- 404: show “Not found” with back link to list
- 409: show “This record changed since you loaded it” with reload action; preserve user-entered note in memory until reload completes
- Timeout: at 8 seconds show timeout state with Retry (DECISION-INVENTORY-004 UX target applied to these screens as a general UX pattern)

## 9. Service Contracts (Frontend Perspective)

All endpoints return **plain JSON** (no `{data: ...}` envelope) and deterministic errors (DECISION-INVENTORY-003). All list endpoints use cursor pagination.

### Load/view calls

1) **List Feed Runs**
- `GET /inventory/availability-feeds/runs`
- Query params:
  - `from` (ISO-8601 datetime; required)
  - `to` (ISO-8601 datetime; required)
  - `pageSize` (int; optional)
  - `pageToken` (string; optional)
  - Optional filters (only if backend supports; do not invent): `status`, `severity`, `vendorCode`, `sourceSystem`
- Response:
  - `items` (array of FeedRun)
  - `nextPageToken` (string|null)

2) **Get Feed Run Detail**
- `GET /inventory/availability-feeds/runs/{runId}`
- Response: FeedRun detail (including any counts, correlationId, and metadata)

3) **List Normalized Outputs**
- `GET /inventory/availability-feeds/normalized`
- Query params:
  - `from` (required), `to` (required)
  - `pageSize`, `pageToken`
  - Optional filters (if supported): `productSku`, `vendorCode`, `manufacturerPartNumber`, `locationId` (only if backend defines)
- Response:
  - `items` (array)
  - `nextPageToken`

4) **List Unmapped Parts**
- `GET /inventory/availability-feeds/unmapped`
- Query params:
  - `from` (required), `to` (required)
  - `status` (optional; enum)
  - `pageSize`, `pageToken`
- Response:
  - `items` (array of UnmappedPart)
  - `nextPageToken`

5) **List Feed Exceptions**
- `GET /inventory/availability-feeds/exceptions`
- Query params:
  - `from` (required), `to` (required)
  - `status` (optional)
  - `severity` (optional)
  - `pageSize`, `pageToken`
- Response:
  - `items` (array of FeedException summary)
  - `nextPageToken`

6) **Detail endpoints (must exist; confirm exact paths)**
- `GET /inventory/availability-feeds/unmapped/{unmappedId}`
- `GET /inventory/availability-feeds/exceptions/{exceptionId}`
- `GET /inventory/availability-feeds/normalized/{normalizedId}` (if supported)

### Create/update calls

7) **Update Unmapped Part**
- `PATCH /inventory/availability-feeds/unmapped/{unmappedId}`
- Request body (minimum):
  - `status` (required; one of `PENDING_REVIEW`, `IGNORED`, `RESOLVED`)
  - `note` (optional; string)
  - `version` (optional; if backend uses optimistic locking) OR `If-Match` header (etag)
- Response: updated UnmappedPart

8) **Update Feed Exception**
- `PATCH /inventory/availability-feeds/exceptions/{exceptionId}`
- Request body (minimum; exact fields depend on backend):
  - `status` (optional; if backend supports status updates)
  - `operatorNote` (optional)
  - `version` (optional) OR `If-Match` header (etag)
- Response: updated FeedException

### Submit/transition calls
- None required by Inventory decisions for feed ops UI.  
  - If a manual “trigger ingestion” endpoint exists, it must be specified explicitly and added as a separate in-scope item only after confirmation. (See Open Questions)

### Error handling expectations
- Deterministic error schema (DECISION-INVENTORY-003):
  - Map field-level errors to form fields when keys match
  - Unknown shapes fall back to generic error message + correlation ID
- 401/403 behavior per DECISION-INVENTORY-012
- Do not log raw payloads or large JSON blobs; do not log sensitive quantities if present in normalized outputs (apply same “sensitive-by-default” posture as inventory docs; DECISION-INVENTORY-011)

## 11. Alternate / Error Flows

### Validation failures
- Invalid date range (`from > to`): block Search; show inline error on date inputs
- Missing required date range: block Search; show inline errors

### Concurrency conflicts (409)
- On PATCH returning 409:
  - Show conflict banner: “This record was updated by another user/process.”
  - Provide **Reload** action
  - Preserve user-entered note in memory and re-apply after reload only if user confirms

### Unauthorized access
- User without `inventory:feedops:view` deep-links to any Availability Feeds screen:
  - Render forbidden state (403) or redirect per app convention; must not leak any data (DECISION-INVENTORY-012)
- User without update permission attempts PATCH:
  - UI should hide controls; if attempted via crafted request and backend returns 403, show forbidden message and keep record unchanged

### Empty states
- No runs in date range: “No feed runs found for the selected date range.”
- No exceptions/unmapped: “No items found for current filters.”
- Missing older records due to retention: treat as empty results; do not show error (DECISION-INVENTORY-013)

### Network/timeouts
- Show loading indicator within 100ms; if request exceeds 8 seconds, show timeout state with Retry; do not auto-refresh loops (DECISION-INVENTORY-004 UX target)

## 12. Acceptance Criteria

### Scenario 1: View feed runs with cursor pagination
**Given** I am authenticated and have permission `inventory:feedops:view`  
**When** I open “Inventory → Availability Feeds → Runs”  
**And** I search with a valid date range  
**Then** the UI calls `GET /inventory/availability-feeds/runs` with `from`, `to`, and `pageSize`  
**And** the UI renders the returned items  
**And** when I click “Load more”, the UI uses `nextPageToken` as `pageToken` and appends results  
**And** the UI does not rely on `totalCount`.

### Scenario 2: Date range validation blocks search
**Given** I am on any Availability Feeds list screen  
**When** I set `from` later than `to` and click “Search”  
**Then** I see an inline validation error  
**And** no backend request is made.

### Scenario 3: View exception detail and see correlation ID
**Given** I have permission `inventory:feedops:view`  
**And** an exception exists in the exceptions list  
**When** I open the exception detail  
**Then** the UI loads the exception detail from the backend  
**And** I can see `severity`, `status`, `message`, `details`, and `correlationId`  
**And** any JSON-like `details` content is rendered safely (escaped, truncated with expand/copy).

### Scenario 4: Update unmapped part status (authorized)
**Given** I have permissions `inventory:feedops:view` and `inventory:feedops:unmapped:update`  
**And** an unmapped part exists with status `PENDING_REVIEW`  
**When** I change its status to `RESOLVED` and click “Save”  
**Then** the UI sends `PATCH /inventory/availability-feeds/unmapped/{unmappedId}` with `status=RESOLVED`  
**And** the UI disables the Save button while the request is in-flight  
**And** on success the UI shows the updated status.

### Scenario 5: Update unmapped part status (unauthorized)
**Given** I have permission `inventory:feedops:view` but not `inventory:feedops:unmapped:update`  
**When** I view an unmapped part detail  
**Then** I do not see status update controls  
**And** if I attempt an update and the backend returns 403, the UI shows a forbidden message and does not change the displayed record.

### Scenario 6: Update exception note/status with conflict handling
**Given** I have permissions `inventory:feedops:view` and `inventory:feedops:exception:update`  
**And** I open an exception detail and enter an operator note  
**When** I click “Save”  
**Then** the UI sends `PATCH /inventory/availability-feeds/exceptions/{exceptionId}` with the note (and version/etag if required)  
**And** if the backend returns 409, the UI shows a conflict message and offers Reload  
**And** my entered note remains available to re-apply after reload.

### Scenario 7: 401/403 behavior and technical details
**Given** I am on an Availability Feeds screen  
**When** a request returns 401  
**Then** the UI follows the app’s login/session refresh flow  
**When** a request returns 403  
**Then** the UI shows a forbidden state without rendering partial sensitive data  
**And** if an error response includes `X-Correlation-Id`, the UI shows it in “Technical details”.
