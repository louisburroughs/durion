## 1. Story Header

### Title
[FRONTEND] [STORY] Availability: View On-hand and Available-to-Promise (ATP) by Location for a Product

### Primary Persona

### Business Value
Enables accurate quoting and fulfillment expectation-setting by showing location-level on-hand and ATP for a selected product.

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** to view on-hand and available-to-promise quantities by fulfillment location for a selected product,  
**So that** I can quote realistically and avoid committing inventory that is already reserved.

### In-scope
- A POS UI screen (and embeddable panel) that, given a `productSku` and `locationId` (and optional `storageLocationId`), loads and displays availability (on-hand, allocated, ATP) as returned by Inventory services.
- Deep-linking via URL query params: `productSku`, `locationId`, optional `storageLocationId`, with auto-run once per load. (DECISION-INVENTORY-014)
- Handling of empty results as success-with-zeros (not an error). (DECISION-INVENTORY-004)
- Moqui screen + transitions + service-call integration to the Inventory availability endpoint via Moqui proxy (no direct Vue → inventory backend). (DECISION-INVENTORY-002)
- Standard auth behavior: 401 → login/session refresh; 403 → forbidden state without data leakage; show correlation ID in technical details. (DECISION-INVENTORY-012)

### Out-of-scope
- Editing inventory, making reservations, allocations, transfers, or replenishment actions.
- Computing availability/ATP in the frontend (backend-authoritative only). (DECISION-INVENTORY-004, DECISION-INVENTORY-016)
- Including expected replenishments in ATP (explicitly excluded in v1; only what backend returns is shown).
- Any changes to Product domain master data (names, descriptions, UOM).
- Cross-product search UX beyond selecting a product SKU from existing POS context (quote line/product detail) or entering a SKU string (no catalog browsing requirements in this story).

**Decision rationale (applied):**
- Use `productSku` (not `productId`) and `locationId`/`storageLocationId` per canonical inventory contracts and deep-link conventions. (DECISION-INVENTORY-004, DECISION-INVENTORY-014, DECISION-INVENTORY-001)
- Use Moqui proxy endpoints and plain JSON parsing. (DECISION-INVENTORY-002, DECISION-INVENTORY-003)

## 6. Functional Behavior

### Triggers
- **Auto-run on load**: when `productSku` and `locationId` are present in URL query params; run once per load. (DECISION-INVENTORY-014)
- **User submit**: user clicks Lookup/Refresh.

### UI actions
- **Lookup**: validates inputs and fetches availability.
- **Refresh**: re-fetches availability for current inputs.
- **Change inputs**: editing `productSku` or changing `locationId` clears current results and any `storageLocationId` selection that no longer matches the selected `locationId`. (DECISION-INVENTORY-001)
- **Clear**: resets form and results to idle state.

### State changes (frontend UI state)
- `idle` → `loading` when request starts
- `loading` → `loaded` on 200 response (including “zeros” responses)
- `loading` → `error` on 4xx/5xx or network error
- `loaded` → `loading` on Refresh

### Service interactions (Moqui-side integration)
- Moqui screen transition invokes a Moqui service (or REST call via Moqui tools) to fetch availability via Moqui proxy:
  - Endpoint: `GET /inventory/availability`
  - Inputs: `productSku`, `locationId`, optional `storageLocationId`
  - Output: `AvailabilityView` placed in screen context for rendering
- Frontend must not compute ATP; it renders backend-provided values. (DECISION-INVENTORY-004, DECISION-INVENTORY-016)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `productSku`:
  - Required; trimmed; reject empty/whitespace-only. (STORY_VALIDATION_CHECKLIST, DECISION-INVENTORY-004)
- `locationId`:
  - Required; selected via LocationRef picker (no free-text UUID). (DECISION-INVENTORY-001)
- `storageLocationId`:
  - Optional; selected via StorageLocation picker filtered by `locationId`. (DECISION-INVENTORY-001, DECISION-INVENTORY-007)
  - If a `storageLocationId` is present and user changes `locationId`, UI must clear `storageLocationId` and require re-selection.
- Location eligibility:
  - If the selected `LocationRef.status` is `INACTIVE` or `PENDING`, the Availability query is still allowed (read-only view), but the UI must visually indicate the location is not eligible for new movement flows (informational only). Movement blocking is enforced in movement stories, not here. (DECISION-INVENTORY-009)

### Enable/disable rules
- Disable Lookup/Refresh while `loading`.
- Disable Refresh when required inputs are missing.
- Disable StorageLocation picker until a `locationId` is selected.

### Visibility rules
- Results visible only in `loaded` state.
- Empty-state visible in `loaded` state when backend indicates “no history”/zeros (see Data Requirements).
- Error banner visible in `error` state; include correlation ID when available. (DECISION-INVENTORY-012)

### Error messaging expectations
- 400/422 validation: show field-level errors when provided; otherwise show a generic “Check inputs and try again.”
- 401: route to login/session refresh (no partial rendering). (DECISION-INVENTORY-012)
- 403: show forbidden state; do not show stale results. (DECISION-INVENTORY-012)
- 404: show “Product not found” only if backend uses 404 for unknown SKU; otherwise treat as validation error per backend schema. (DECISION-INVENTORY-003)
- 5xx/network/timeout: show “Unable to load availability right now. Retry.” and keep prior results marked stale if present.

## 8. Data Requirements

### Entities involved (frontend perspective)
- Read-only view model returned by Inventory:
  - `AvailabilityView` (backend-authoritative)
  - `LocationRef` (for picker display)
  - `StorageLocation` (for picker display)

### Fields

**Input (query)**
- `productSku` (string, required)
- `locationId` (UUID string, required)
- `storageLocationId` (UUID string, optional)

**Response (AvailabilityView) — required minimum for UI**
- `productSku` (string, required, read-only)
- `locationId` (UUID string, required, read-only)
- `storageLocationId` (UUID string, optional, read-only)
- Quantities (numbers; read-only; do not log):
  - `onHandQty` (number, required)
  - `allocatedQty` (number, required) — if backend provides; if absent, UI must not infer it
  - `availableToPromiseQty` (number, required)
- Optional metadata (render if present; do not require):
  - `asOfTs` (ISO-8601 timestamp string) for “last updated”
  - `uom` (string) if provided (display only; no conversion)

**Picker data**
- LocationRef list items:
  - `locationId` (UUID string)
  - `name` (string)
  - `status` (`ACTIVE` | `INACTIVE` | `PENDING` | other) (display badge if present)
- StorageLocation list items:
  - `storageLocationId` (UUID string)
  - `locationId` (UUID string)
  - `name` (string)
  - `status` (if present)

### Read-only vs editable
- All availability quantities are read-only.
- Inputs are editable until lookup; results are not editable.

### Derived/calculated fields
- UI-only:
  - `isStale` boolean when showing prior results after an error.
  - `lastSuccessfulFetchTs` timestamp for stale banner.
- No client-side computation of ATP or allocations. (DECISION-INVENTORY-004, DECISION-INVENTORY-016)

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
All calls are to Moqui proxy endpoints (same-origin), returning plain JSON. (DECISION-INVENTORY-002, DECISION-INVENTORY-003)

1. **Availability**
   - `GET /inventory/availability?productSku={productSku}&locationId={locationId}&storageLocationId={storageLocationId?}`
   - 200: plain JSON `AvailabilityView`
   - “No history” is 200 with zeros (not 404). (DECISION-INVENTORY-004)

2. **Location picker**
   - `GET /inventory/locations?pageSize={n}&pageToken={token?}`
   - 200: `{ items: LocationRef[], nextPageToken?: string }` (cursor pagination) (DECISION-INVENTORY-003)

3. **StorageLocation picker**
   - `GET /inventory/storage-locations?locationId={locationId}&pageSize={n}&pageToken={token?}`
   - 200: `{ items: StorageLocation[], nextPageToken?: string }` (cursor pagination) (DECISION-INVENTORY-003, DECISION-INVENTORY-007)

### Create/update calls
- None.

### Submit/transition calls (Moqui)
- Transition: `lookupAvailability`
  - Validates `productSku` and `locationId`
  - Calls `GET /inventory/availability`
  - Stores result in screen context and renders results section

### Error handling expectations
- Deterministic error schema (plain JSON) is parsed; map field errors to form fields when possible. (DECISION-INVENTORY-003)
- 401/403 behavior per convention. (DECISION-INVENTORY-012)
- Include `X-Correlation-Id` header on requests; surface response header/value in error UI technical details. (DECISION-INVENTORY-012)
- Do not log quantities or full payloads in client logs/telemetry. (DECISION-INVENTORY-011)

## 10. State Model & Transitions

### Allowed states
- `idle`: no request yet / cleared
- `loading`: request in-flight
- `loaded`: last request succeeded (including zeros)
- `error`: last request failed

### Role-based transitions
- Viewing is permitted/denied by backend authorization.
- UI gating (if permission info is available in the app shell) may hide the Inventory → Availability menu item for unauthorized users, but backend remains authoritative.

### UI behavior per state
- `idle`: show inputs and guidance; no results.
- `loading`: show spinner within 100ms; disable actions. (DECISION-INVENTORY-004)
- `loaded`: show results; if zeros/no history, show empty-state copy but still render the returned quantities as provided.
- `error`: show error banner; show Retry; if prior results exist, show them with stale banner.

## 11. Alternate / Error Flows

### Validation failures
- Missing/blank `productSku`:
  - Block submit; show inline error; no request sent.
- Missing `locationId`:
  - Block submit; show inline error; no request sent.
- `storageLocationId` selected but not under selected `locationId` (should be prevented by picker):
  - Clear selection on location change; if backend still returns validation error, show field error and prompt re-select. (DECISION-INVENTORY-001)

### Concurrency conflicts
- Not applicable (read-only).
- If multiple requests are in-flight (e.g., rapid refresh), latest response wins; earlier responses ignored.

### Unauthorized access
- 401:
  - Redirect to login/session refresh; do not render partial results. (DECISION-INVENTORY-012)
- 403:
  - Render forbidden state; do not show stale results (avoid data leakage). (DECISION-INVENTORY-012)

### Empty states
- Backend returns success-with-zeros:
  - Show message: “No inventory history for this product at the selected location/bin.”
  - Provide “Change location/bin” and “Retry” actions (Retry re-calls same query). (DECISION-INVENTORY-004)

### Timeout
- If request exceeds 8 seconds:
  - Show timeout message and Retry; do not auto-retry. (DECISION-INVENTORY-004)

## 12. Acceptance Criteria

### Scenario 1: View availability (happy path) for a product at a location
**Given** I am an authenticated Service Advisor  
**And** I open the Availability screen  
**And** I enter `productSku="SKU-123"`  
**And** I select `locationId="<uuid>"` from the Location picker  
**When** I click Lookup  
**Then** the system calls `GET /inventory/availability` with `productSku` and `locationId`  
**And** I see the returned `onHandQty`, `allocatedQty` (if provided), and `availableToPromiseQty` rendered  
**And** the UI does not compute or alter these values.

### Scenario 2: Deep-link auto-run occurs once per load
**Given** I am an authenticated Service Advisor  
**When** I navigate to `/inventory/availability?productSku=SKU-123&locationId=<uuid>`  
**Then** the screen automatically runs the availability lookup once  
**And** it does not re-run repeatedly unless I click Refresh/Lookup.

### Scenario 3: “No inventory history” is success-with-zeros
**Given** I am an authenticated Service Advisor  
**And** I lookup availability for `productSku="SKU-456"` at `locationId="<uuid>"`  
**When** the API responds `200` with quantities all equal to `0` (and/or an explicit “no history” indicator if provided)  
**Then** I see a message indicating no inventory history for the selected scope  
**And** the screen remains in a successful loaded state (not an error state).

### Scenario 4: Missing required inputs are blocked client-side
**Given** I am on the Availability screen  
**When** I click Lookup with `productSku` blank or whitespace-only  
**Then** I see an inline validation message for `productSku`  
**And** no API request is sent.  
**When** I click Lookup without selecting a `locationId`  
**Then** I see an inline validation message for `locationId`  
**And** no API request is sent.

### Scenario 5: StorageLocation picker is filtered by Location and cleared on change
**Given** I selected `locationId="<uuid-A>"` and `storageLocationId="<bin-A>"`  
**When** I change the selected `locationId` to `<uuid-B>`  
**Then** the UI clears `storageLocationId`  
**And** the StorageLocation picker only shows bins for `<uuid-B>`.

### Scenario 6: Unauthorized behaviors (401 vs 403)
**Given** I am not authenticated (session expired)  
**When** I attempt to load availability  
**And** the API responds `401`  
**Then** I am redirected to login/session refresh flow.  
**Given** I am authenticated but not authorized  
**When** I attempt to load availability  
**And** the API responds `403`  
**Then** I see a forbidden state  
**And** no availability quantities are displayed.

### Scenario 7: Timeout and retry
**Given** I am on the Availability screen with valid inputs  
**When** the availability request takes longer than 8 seconds  
**Then** I see a timeout message with a Retry action  
**When** I click Retry and the API succeeds  
**Then** I see the loaded availability results.

### Scenario 8: Sensitive data is not logged
**Given** I perform an availability lookup that returns quantities  
**Then** client logs/telemetry do not include numeric availability quantities from the response (only status/latency/correlation ID as applicable).
