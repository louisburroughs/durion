## 1. Story Header

### Title
[FRONTEND] Availability Feeds (Ops): Monitor Feed Runs + Review/Triage Unmapped Parts + Review Exceptions

### Primary Persona
Integration Operator (Ops user responsible for monitoring integration health and resolving unmapped items)

**Persona Metadata**
- `primary_persona`: `Integration Operator (Ops user responsible for monitoring integration health and resolving unmapped items)`
- `canonical_persona`: `Accounting Associate`
- `persona_family`: `Accounting Associate`
- `actor_type`: `human`

### Business Value
Provide operational visibility into manufacturer availability feed ingestion so the business can (a) confirm freshness/health of availability data and (b) quickly triage unmapped manufacturer part numbers that prevent downstream availability/lead-time estimates for special orders—without digging through logs.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Integration Operator  
- **I want** a UI in the POS frontend to monitor manufacturer availability feed ingestion results and review/triage unmapped manufacturer part numbers and exceptions  
- **So that** availability/lead-time data can be trusted, ingestion failures can be investigated with correlation IDs, and unmapped parts can be routed for mapping maintenance.

### In-scope
- Frontend screens (Moqui screens/forms) to:
  - View recent feed ingestion runs (per manufacturer, as-of time, outcome)
  - View normalized availability records (read-only) for troubleshooting/verification
  - View and triage **unmapped manufacturer parts backlog** (status update supported)
  - View integration exceptions/failed ingestions routed to an exception queue (read-only list + detail; optional status/notes update if permitted)
- Moqui screen + service-call wiring to Inventory-domain proxy endpoints (same-origin) with deterministic error handling and empty states. (DECISION-INVENTORY-002, DECISION-INVENTORY-003, DECISION-INVENTORY-013)
- Permission-gated access to these operational views and actions. (DECISION-INVENTORY-010)

### Out-of-scope
- Implementing the ingestion pipeline itself (backend responsibility).
- Editing/creating Manufacturer Part Map entries (explicitly out-of-scope; handled by separate product-domain tool/story).
- Enforcing min-order rules in cart/ordering.
- Any inventory valuation/costing logic.
- Any client-side computation of availability/ATP (this story is ops monitoring only; normalized/ops records are displayed as returned). (DECISION-INVENTORY-004)

   - `inventory:feedops:view`
   - `inventory:feedops:unmapped:update`

6. Retention: runs and exceptions retained at least 90 days; UI must use date range filters and tolerate missing older records. (DECISION-INVENTORY-013)

## 7. Business Rules (Translated to UI Behavior)

1. **Inventory owns feed ops read models and triage updates**: UI must use inventory feed ops endpoints and must not attempt to interpret/repair ingestion beyond allowed status/notes updates. (DECISION-INVENTORY-013)

2. **Cursor pagination only**: list screens must use `pageSize`, `pageToken`, and `nextPageToken`; UI must not rely on `totalCount`. (DECISION-INVENTORY-003)

3. **Retention-aware UX**: default date range filters (e.g., last 7 days) and clear messaging when older records are missing/archived; do not attempt infinite history. (DECISION-INVENTORY-013)

4. **Unmapped triage statuses**: allowed statuses in v1 are exactly `PENDING_REVIEW`, `IGNORED`, `RESOLVED`. UI must only offer these values and must handle backend rejection deterministically. (DECISION-INVENTORY-013)

5. **Exception queue scope and required fields**: exceptions are inventory-scoped and must display required fields: `severity`, `status`, `message`, `details` (redacted-safe), `correlationId`, timestamps. UI must treat `details` as safe-to-display but still render via safe JSON viewer. (DECISION-INVENTORY-013, DECISION-INVENTORY-015)

6. **Sensitive data & logging**:
   - Do not log raw payload blobs or large JSON details to console/telemetry.
   - Do not persist payload/details to `localStorage`. (DECISION-INVENTORY-011, DECISION-INVENTORY-015)

7. **Safe JSON rendering**: any JSON-like fields (details/payload/metadata) must be escaped, truncated in list views, and expanded on-demand with copy support. (DECISION-INVENTORY-015)

8. **Auth behavior**:
   - 401: follow app convention to redirect to login/session refresh.
   - 403: render forbidden state; do not leak partial data. Show correlation ID if available. (DECISION-INVENTORY-012)

Error messaging expectations:
- Validation errors (400/422): show inline on the relevant filter/input when possible; otherwise banner.
- Unauthorized (403): “You do not have access to Availability Feed Ops.”
- Backend unavailable/timeout: show retry; keep user filters intact; do not auto-refresh loops. (DECISION-INVENTORY-004)

**Decision rationale references (why these are resolved):**
- Endpoints and update capability are explicitly defined by Inventory decisions for feed ops. (DECISION-INVENTORY-013)
- Permissions are explicitly defined by Inventory permission taxonomy. (DECISION-INVENTORY-010)
- Pagination and error schema conventions are explicitly defined. (DECISION-INVENTORY-003)
- Correlation/auth handling is explicitly defined. (DECISION-INVENTORY-012)
- JSON safe rendering and sensitive logging constraints are explicitly defined. (DECISION-INVENTORY-011, DECISION-INVENTORY-015)
- Retention expectation is explicitly defined (>= 90 days) and drives date-range UX. (DECISION-INVENTORY-013)

## 9. Service Contracts (Frontend Perspective)

All calls are via Moqui proxy endpoints and return **plain JSON** (no `{data: ...}` envelope). (DECISION-INVENTORY-002, DECISION-INVENTORY-003)

### Load/view calls

1. **List feed runs**
   - Method/Path: `GET /inventory/availability-feeds/runs`
   - Query params (recommended):
     - `manufacturerId?`
     - `from?` (ISO timestamp/date; backend-defined)
     - `to?`
     - `outcome?`
     - `pageSize?`
     - `pageToken?`
     - `sort?`
   - Response (cursor paging):
     - `{ "items": [FeedRun...], "nextPageToken": "..."? }` (shape may vary; UI must support `nextPageToken` per DECISION-INVENTORY-003)

2. **Run detail**
   - Method/Path: `GET /inventory/availability-feeds/runs/{runId}`
   - Response: FeedRun detail object (may include additional fields; render safely)

3. **List normalized records**
   - Method/Path: `GET /inventory/availability-feeds/normalized`
   - Query params:
     - `manufacturerId?`
     - `manufacturerPartNumber?`
     - `from?`, `to?`
     - `pageSize?`, `pageToken?`, `sort?`
   - Response: cursor-paged list

4. **List unmapped parts**
   - Method/Path: `GET /inventory/availability-feeds/unmapped`
   - Query params:
     - `manufacturerId?`
     - `status?` (one of allowed statuses)
     - `manufacturerPartNumber?` (search)
     - `from?`, `to?` (optional; if supported)
     - `pageSize?`, `pageToken?`, `sort?`
   - Response: cursor-paged list

5. **List exceptions**
   - Method/Path: `GET /inventory/availability-feeds/exceptions`
   - Query params:
     - `severity?`
     - `status?`
     - `correlationId?`
     - `from?`, `to?` (date range strongly recommended)
     - `pageSize?`, `pageToken?`, `sort?`
   - Response: cursor-paged list

6. **Exception detail** (if list does not include `details` or for deep link)
   - Method/Path: `GET /inventory/availability-feeds/exceptions/{exceptionId}`

### Create/update calls

1. **Update unmapped part status**
   - Permission: `inventory:feedops:unmapped:update` (DECISION-INVENTORY-010)
   - Method/Path: `PATCH /inventory/availability-feeds/unmapped/{unmappedId}`
   - Body:
     - `{ "status": "IGNORED" | "RESOLVED" | "PENDING_REVIEW", "note"? : "string", "version"? : ... }`
   - Response: updated UnmappedPart

2. **Update exception status/notes** (optional but supported by decision set)
   - Permission: `inventory:feedops:exception:update` (DECISION-INVENTORY-010)
   - Method/Path: `PATCH /inventory/availability-feeds/exceptions/{exceptionId}`
   - Body: backend-defined; UI sends only fields exposed by backend (typically `status`, `operatorNote`, `version/etag`)
   - Response: updated FeedException

### Submit/transition calls
- None beyond PATCH updates above.

### Error handling expectations (deterministic)
- `400/422`: validation error; map to field(s) when possible; keep filters/inputs.
- `401`: redirect to login/session refresh (app convention). (DECISION-INVENTORY-012)
- `403`: forbidden state; hide update controls; do not leak data. (DECISION-INVENTORY-012)
- `404`: detail not found (archived/purged); show “Not found (may have been archived)” and link back.
- `409`: conflict/optimistic locking; show “This record changed; refresh and try again.” (DECISION-INVENTORY-013)
- `5xx/timeout`: show retry; do not auto-retry mutations; show correlation ID if present. (DECISION-INVENTORY-004, DECISION-INVENTORY-012)

### UI behavior per state
- Runs:
  - `FAILED`: emphasize; show `errorSummary` and link to Exceptions filtered by `correlationId` when present.
  - `PARTIAL_SUCCESS`: show `unmappedCount` and link to Unmapped filtered by `manufacturerId`.
- Unmapped:
  - Default filter `status=PENDING_REVIEW`.
  - Status update requires confirmation and disables controls while in-flight.
- Exceptions:
  - Show severity/status badges; detail view shows safe `details`.
  - If update permitted, show edit controls; otherwise read-only.

## 11. Alternate / Error Flows

1. **Empty state: no runs**
   - Show “No feed runs found for selected filters.” Suggest expanding date range (within retention).

2. **Empty state: no unmapped parts**
   - With default `PENDING_REVIEW`: “No unmapped parts pending review.”

3. **Empty state: no exceptions**
   - “No exceptions found for selected filters.”

4. **Backend unavailable / timeout**
   - Show error banner with retry.
   - Keep last successful list in memory for the current screen session (do not persist to localStorage). (DECISION-INVENTORY-015)

5. **Unauthorized access**
   - Direct URL navigation:
     - On 401: redirect to login/session refresh.
     - On 403: show forbidden state; do not render partial data; do not continue paging calls. (DECISION-INVENTORY-012)

6. **Invalid filter values**
   - Client-side validation blocks submit for malformed UUID/date range.
   - If backend returns 400/422, show message and highlight offending field when possible.

7. **Detail not found (retention/archival)**
   - Show “Not found (may have been archived).” Provide link back to list with preserved filters.

8. **Concurrency conflict on PATCH**
   - If 409 returned, show conflict message and refresh the record (re-fetch detail or list row) before allowing retry. (DECISION-INVENTORY-013)

## 12. Acceptance Criteria

### Scenario 1: View runs list (cursor pagination)
**Given** I am authenticated and have `inventory:feedops:view`  
**When** I open “Inventory → Availability Feeds (Ops) → Runs”  
**Then** the UI calls `GET /inventory/availability-feeds/runs` via Moqui proxy  
**And** I see a list of runs with `runId`, `manufacturerId`, `asOf`, `receivedAt`, `itemCount`, `mappedCount`, `unmappedCount`, and `outcome`  
**And** when I click “Next” (or “Load more”), the UI uses `pageToken` and renders additional results using `nextPageToken` without relying on a total count (DECISION-INVENTORY-003)

### Scenario 2: Filter runs by date range and manufacturer
**Given** I am on the Runs screen  
**When** I set a date range where `from <= to` and enter a manufacturerId  
**Then** the UI validates the inputs and reloads the list using those filters  
**And** if the backend returns an empty list, I see a non-error empty state message

### Scenario 3: Navigate from a partial-success run to unmapped parts
**Given** a run exists with `outcome=PARTIAL_SUCCESS` and `unmappedCount > 0`  
**When** I open that run and click “View unmapped parts”  
**Then** I am taken to the Unmapped Parts screen with `manufacturerId` pre-applied  
**And** the UI loads `GET /inventory/availability-feeds/unmapped` and shows `manufacturerPartNumber`, `firstSeen`, `lastSeen`, `occurrenceCount`, and `status`

### Scenario 4: Triage an unmapped part (status update)
**Given** I have `inventory:feedops:unmapped:update`  
**And** an unmapped part is in `PENDING_REVIEW`  
**When** I change its status to `IGNORED` and confirm  
**Then** the UI calls `PATCH /inventory/availability-feeds/unmapped/{unmappedId}` with the new status  
**And** on success the row updates to `IGNORED`  
**And** on 409 the UI shows a conflict message and refreshes the row before allowing retry (DECISION-INVENTORY-013)

### Scenario 5: View normalized records (schema-tolerant)
**Given** normalized records exist for a manufacturer within a date range  
**When** I open “Normalized” and filter by manufacturerId and date range  
**Then** the UI calls `GET /inventory/availability-feeds/normalized`  
**And** the list renders without crashing even if some optional fields are missing  
**And** any JSON-like fields are rendered safely with truncation and explicit expand/copy (DECISION-INVENTORY-015)

### Scenario 6: View exceptions and open detail
**Given** I have `inventory:feedops:view`  
**When** I open “Exceptions” and select an exception  
**Then** the UI shows `severity`, `status`, `message`, `createdAt`, and `correlationId` (if present)  
**And** the detail view renders `details` safely (escaped, truncated, expandable) (DECISION-INVENTORY-015)

### Scenario 7: Access denied (403)
**Given** I am authenticated but do not have `inventory:feedops:view`  
**When** I navigate directly to any Availability Feeds (Ops) URL  
**Then** the UI shows a forbidden state  
**And** no operational data is displayed  
**And** the UI does not continue paging or retrying list calls after receiving 403 (DECISION-INVENTORY-012)

### Scenario 8: Timeout / backend error handling
**Given** the backend times out or returns 5xx while loading Runs  
**When** I open the Runs screen  
**Then** I see a timeout/error state within 8 seconds with a retry action  
**And** my filters remain intact  
**And** the error UI shows `X-Correlation-Id` when available (DECISION-INVENTORY-004, DECISION-INVENTORY-012)
