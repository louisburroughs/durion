## 1. Story Header

**Title:** [FRONTEND] [STORY] Billing: View Invoice & Issue (Finalize) Invoice from Work Order (Policy-Gated, Audited)  
**Primary Persona:** Service Advisor

**Business Value:** Enables Service Advisors to review Billing-authoritative invoice details for a completed Work Order and, when permitted and unblocked, issue (finalize) the invoice so it becomes immutable and ready for payment—while enforcing backend policy, permissions, and auditability.

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to view the Billing invoice for a completed Work Order and issue the invoice when eligible  
- **So that** the invoice is locked (immutable) and can proceed to payment and downstream accounting processes with traceability and controls

### In-scope
- Invoice detail view (read-only):
  - Header, status, totals, taxes/fees breakdown, line items
  - Traceability snapshot and issuance gating info (`issuancePolicy`, `issuanceBlockers[]`)
  - Allowed actions (from backend) and permission-gated UI controls
- Invoice retrieval by `workOrderId` and by `invoiceId` (context-dependent)
- Draft invoice creation from Work Order (user-initiated, idempotent)
- Invoice issuance (finalization) command:
  - Policy-gated issuance with blockers rendered prior to attempt
  - Step-up auth via **elevation token** only when required by policy/blockers
  - Idempotent issuance handling (409/422/200)
- Display of sanitized posting error summary when present (role-targeted detail gating)

### Out-of-scope
- Editing invoice lines, prices, taxes, fees, traceability (Billing-owned and immutable post-issuance; lines not editable in this flow)
- Taking/processing payments and receipt delivery/reprint (separate stories)
- Voiding invoices (separate story)
- Credit/rebill/corrections (separate stories)
- Implementing Accounting/GL posting logic (Accounting-owned); only display statuses/acknowledgements returned by Billing

## 3. Actors & Stakeholders

- **Service Advisor**: views invoice, creates draft (when none), attempts issuance
- **Shop Manager/Supervisor**: provides step-up approval via elevation token when required
- **Billing (SoR)**: invoice lifecycle, totals, taxes/fees, issuance gating, traceability snapshot, allowed actions
- **Work Execution (integrated)**: Work Order completion + `invoiceReady=true` prerequisite for draft creation
- **Accounting (integrated)**: consumes Billing events; may provide posting acknowledgements surfaced by Billing
- **Audit/Compliance**: requires immutable traceability and auditable issuance/override actions

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in POS frontend.
- User has navigated in a Work Order context with a valid `workOrderId` **or** has a deep link with `invoiceId`.
- For draft creation: Work Order must be Completed and `invoiceReady=true` (enforced server-side; UI must handle 409 reason codes).

### Dependencies
- Billing endpoints (normative contracts):
  - `GET /billing/invoices/by-work-order/{workOrderId}`
  - `GET /billing/invoices/{invoiceId}`
  - `POST /billing/invoices/draft` (idempotent by `workOrderId`)
  - `POST /billing/invoices/{invoiceId}/issue` (idempotent per invoice/version)
- Step-up auth endpoint (normative):
  - `POST /billing/auth/elevate` → `{ elevationToken }` (short-lived, single-use; do not log credentials/token)
- Permission model (canonical strings; server authoritative):
  - View invoice: `billing:invoice:view`
  - Create draft: `billing:invoice:create-draft`
  - Issue invoice: `billing:invoice:issue`
  - Elevate: `billing:auth:elevate`
  - Traceability panel: `billing:traceability:view`
  - Posting error detail: `billing:posting-error:detail:view` (optional UI gating if detail is present)
- Deep-link metadata (no hardcoded routes): Billing may return `{targetDomain,targetType,targetId}` for related records; frontend resolves if route exists.

## 6. Functional Behavior

### Triggers
- Screen load with `invoiceId` or `workOrderId`
- User clicks “Create Draft Invoice”
- User clicks “Issue Invoice”
- User initiates “Manager Approval” (step-up) when required

### UI actions

#### On load
1. Determine identifier:
   - If `invoiceId` present: call `GET /billing/invoices/{invoiceId}`
   - Else call `GET /billing/invoices/by-work-order/{workOrderId}`
2. Render:
   - Invoice header: `invoiceNumber` (if issued), `invoiceId`, `status`, `workOrderId`, `customerAccountId`
   - Totals: `subtotal`, `taxTotal`, `feeTotal`, `discountTotal`, `grandTotal`, `balanceDue`, `currencyUomId`
   - Line items list (read-only)
   - Taxes/fees breakdown lists (read-only)
   - Traceability panel (permission-gated by `billing:traceability:view`)
   - Issuance gating panel:
     - `issuancePolicy` summary (display as provided)
     - `issuanceBlockers[]` list with severity/message (display as provided)
   - Allowed actions panel (derived from backend `allowedActions[]` if present; otherwise derive only from status + permissions, but never for security)

#### Create Draft Invoice (user-initiated)
- Visible/enabled only if:
  - No invoice found (404 by-work-order)
  - User has `billing:invoice:create-draft`
- Action:
  - Call `POST /billing/invoices/draft` with `{workOrderId}`
  - On 200: render returned invoice (or navigate to same screen with `invoiceId`)
  - On 409: show deterministic conflict message (e.g., not invoice-ready, already issued/paid/void) and keep empty state
  - On 422: show missing billing data fields (as provided) and keep empty state

#### Issue Invoice (finalize)
- Visible/enabled only if:
  - User has `billing:invoice:issue`
  - Invoice `status == DRAFT`
  - Backend indicates no blockers preventing issuance (preferred: `issuanceBlockers[]` empty and/or `allowedActions[]` includes issuance)
- Action:
  1. Confirm dialog: “Issuing locks the invoice and assigns an invoice number. This cannot be edited afterward.”
  2. If backend indicates elevation required:
     - Require elevation token acquisition step (see below)
  3. Call `POST /billing/invoices/{invoiceId}/issue` with `{ elevationToken? }`
  4. On success: refresh invoice detail via GET and show updated status/metadata

#### Step-up auth (elevation token)
- Only shown when:
  - Backend indicates issuance requires elevation (via blockers/policy/allowedActions metadata)
  - User has `billing:auth:elevate`
- Flow:
  - Open modal for manager credentials (implementation-specific; do not store)
  - Call `POST /billing/auth/elevate`
  - Store `elevationToken` in memory only (not persisted); TTL assumed short-lived; clear on modal close/submit
  - Use token once in issuance request; clear immediately after request completes

### State changes (frontend)
- `loadingInvoice`, `invoiceLoaded`, `invoiceNotFound`, `creatingDraft`, `issuing`, `elevating`, `errorState`
- No local mutation of invoice financials/lines; always re-fetch after commands.

### Service interactions (Moqui-oriented)
- Use Moqui `service-call`/`rest-call` patterns consistent with repo conventions:
  - REST calls to Billing endpoints above
  - Propagate W3C trace headers (see Audit & Observability)

## 7. Business Rules (Translated to UI Behavior)

### Validation (backend authoritative; UI reflects)
- Draft creation:
  - Only allowed when Work Order is Completed and `invoiceReady=true` (enforced server-side).
  - If not allowed, backend returns 409 with deterministic `reasonCode`; UI displays reason and does not retry automatically.
- Issuance:
  - Only allowed when invoice `status == DRAFT`.
  - Backend provides `issuancePolicy` and `issuanceBlockers[]` in invoice detail for drafts.
  - UI must render blockers and must not guess required traceability identifiers.
  - Issuance attempt returning 422 must display blocker codes/messages and refresh invoice.

### Enable/disable rules
- “Create Draft Invoice”:
  - Enabled only when invoice lookup by work order returns 404 and user has `billing:invoice:create-draft`.
- “Issue Invoice”:
  - Enabled only when:
    - user has `billing:invoice:issue`
    - invoice status is `DRAFT`
    - backend indicates issuance is allowed (no blockers / allowed action present)
- “Manager Approval / Elevate”:
  - Visible only when backend indicates elevation required and user has `billing:auth:elevate`.

### Visibility rules
- Traceability panel visible only with `billing:traceability:view`.
- Artifact links (if present in traceability) must use deep-link metadata; if route not available, show copy-only.
- Posting error details:
  - Always show `postingErrorSummary` if present (sanitized).
  - Only show detailed posting diagnostics if present **and** user has `billing:posting-error:detail:view`.

### Error messaging expectations
- 403: “You don’t have permission to perform this action.”
- 404 (by-work-order): “No invoice exists for this work order yet.”
- 409: “Invoice state changed or action is not allowed: <reason>.” Provide refresh CTA.
- 422: “Invoice can’t be issued yet.” List blockers/missing fields from response.
- 503: “Billing service is temporarily unavailable. Try again.” Preserve correlationId if provided.

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
1. **Get by invoiceId**
   - `GET /billing/invoices/{invoiceId}`
   - Expected: full invoice snapshot including `traceability`, totals, and for drafts `issuancePolicy` + `issuanceBlockers[]`
2. **Get by workOrderId**
   - `GET /billing/invoices/by-work-order/{workOrderId}`
   - 404 if none exists

### Create/update calls
1. **Create draft (idempotent)**
   - `POST /billing/invoices/draft`
   - Request: `{ "workOrderId": "uuidv7" }`
   - Success: returns invoice snapshot (recommended)
   - Errors:
     - 409 `{ errorCode, message, reasonCode }` (not invoice-ready / already issued/paid/void)
     - 422 `{ errorCode, message, missingFields[] }` (billing data incomplete)

### Submit/transition calls
1. **Issue invoice**
   - `POST /billing/invoices/{invoiceId}/issue`
   - Request: `{ "elevationToken": "string?" }`
   - Errors:
     - 422 blockers with structured codes (must match invoice detail blockers)
     - 409 if already issued/paid/void or state conflict

2. **Elevation token**
   - `POST /billing/auth/elevate`
   - Response: `{ elevationToken, expiresAt? }`
   - Frontend requirements:
     - Never log credentials or token
     - Token stored in memory only; cleared after use

### Error handling expectations
- Standard mapping:
  - 401/403: show permission/auth message; disable protected actions
  - 404: show empty state (by-work-order) or not-found (by-invoice)
  - 409: show conflict; force refresh
  - 422: show blockers/missing fields; keep user on screen
  - 503: show temporary outage; allow retry
- Always display `correlationId` when provided (support/debug), but do not display internal stack traces.

## 10. State Model & Transitions

### Allowed states (Billing canonical)
- `DRAFT`
- `ISSUED`
- `PAID`
- `VOID`
- Optional: `ERROR` (only if backend returns it; UI must treat unknown enums as “Unknown state” and prompt refresh/support)

### Role-based transitions (frontend initiation)
- Service Advisor:
  - May create draft (permission `billing:invoice:create-draft`)
  - May issue invoice (permission `billing:invoice:issue`) when backend policy allows
  - May require manager elevation token depending on policy/blockers
- Manager/Supervisor:
  - Provides elevation token via step-up auth (permission `billing:auth:elevate`)

### UI behavior per state
- `DRAFT`:
  - Show issuance gating panel (`issuancePolicy`, `issuanceBlockers[]`)
  - Show “Issue Invoice” enabled only when unblocked and permitted
- `ISSUED` / `PAID` / `VOID`:
  - Invoice immutable; hide/disable “Issue Invoice”
  - Show issuance metadata (`invoiceNumber`, `issuedAt`, `issuedByUserId`)
- `ERROR` (if present):
  - Read-only; show sanitized error summary and correlationId; no issuance unless backend explicitly allows (via allowed actions)

## 11. Alternate / Error Flows

### Validation failures (422)
- Draft creation 422:
  - Display `missingFields[]` and message
  - Provide guidance: “Update customer billing info / required data, then retry.”
- Issuance 422:
  - Display blocker list from response (code/severity/text)
  - Refresh invoice detail to sync blockers

### Concurrency conflicts (409)
- If invoice was issued by another user:
  - Issuance returns 409
  - UI shows “Invoice already issued or state changed” and refreshes invoice detail

### Unauthorized access (401/403)
- If user lacks `billing:invoice:view`:
  - Show access denied screen (no invoice data rendered)
- If user can view but cannot issue/create draft:
  - Hide/disable those actions; show tooltip/message on disabled controls

### Empty states
- By-work-order returns 404:
  - Show “No invoice exists for this work order.”
  - If permitted, show “Create Draft Invoice” (user-initiated)
  - If not permitted, show “Contact a manager or billing admin to create an invoice.”

### Unknown enum/state
- If `status` is not recognized:
  - Show “Unknown invoice status. Refresh or contact support.”
  - Disable issuance actions until refreshed

**And** the “Issue Invoice” action is disabled

**And** `issuanceBlockers[]` is empty  
**And** I have `billing:invoice:issue`

**Then** the UI calls `POST /billing/invoices/{invoiceId}/issue` without an elevation token  
**And** the UI refreshes invoice detail

**Given** I am viewing an invoice with `status = DRAFT`

**When** I complete the manager step-up flow  
**Then** the UI calls `POST /billing/auth/elevate` and receives an `elevationToken`  
**When** I submit issuance  
**Then** the UI calls `POST /billing/invoices/{invoiceId}/issue` with `{ elevationToken }`  
**And** the UI clears the token from memory after the request completes

### Scenario 7: Issuance conflict due to concurrent issuance
**Given** I am viewing a draft invoice that becomes issued by another user  
**When** I attempt to issue it  
**Then** the backend responds 409  
**And** the UI shows a conflict message and refreshes invoice detail to show the current status

### Scenario 8: Posting error summary is sanitized and correlationId shown
**Given** I am viewing an invoice where Billing returns `postingErrorSummary` and `correlationId`  
**When** the invoice view renders  
**Then** I see the sanitized `postingErrorSummary` and the `correlationId`  
**And** I do not see detailed diagnostics unless I have `billing:posting-error:detail:view` and such details are provided
