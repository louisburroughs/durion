## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Workexec: WIP Dashboard for Active Work Orders (Status, Assignment, Drilldown, Near-Real-Time Updates)

### Primary Persona
Counter Associate

### Business Value
Enable counter staff to provide accurate, timely work-in-progress (WIP) updates to customers by showing current work order execution status, assignment context (mechanic/bay/location), and recent status changes with near-real-time refresh.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Counter Associate  
- **I want** a WIP dashboard that shows current execution status for active work orders and allows drilling into a work order’s details/history  
- **So that** I can quickly answer customer “what’s the status?” questions and manage expectations.

### In-scope
- A WIP list view for active work orders with:
  - Canonical work order execution status (workexec status taxonomy)
  - Assignment context (mechanic + bay/location) when available
  - “Last updated” / staleness indicator
  - Drilldown to a work order detail view/panel
- Data refresh via polling, with optional event-driven updates if already available
- Basic filtering (status/mechanic/location) and empty/loading/error states
- Moqui screen implementation (screens/forms/transitions) and Vue/Quasar frontend components integrated via Moqui

### Out-of-scope
- Changing work order state from this UI (no “force start/complete”)
- Implementing new backend event infrastructure (SSE/broker/webhooks) if not already present
- Owning Shop Management scheduling/assignment truth (shopmgr remains SoR for operational context)
- Detailed inventory parts breakdown beyond what backend provides for WIP
- Automatic customer notifications

---

## 3. Actors & Stakeholders
- **Counter Associate (primary)**: consumes WIP list + detail to answer customers
- **Mechanic / Technician**: updates work order status in workexec (not via this UI)
- **Shop Manager / Dispatcher**: owns scheduling/operational context decisions (shopmgr SoR)
- **Workexec (Moqui component)**: authoritative work order execution status + transition history
- **Shopmgr (Moqui component)**: authoritative appointment/scheduling context linked via `appointmentId`
- **Security/Authorization**: provides capability/permission signaling; backend enforces with 403
- **Audit/Support**: relies on correlation IDs and status history for troubleshooting

---

- User is authenticated in the POS frontend.
- Work orders exist with statuses from the workexec taxonomy.
- User has permission to view WIP/dispatch-style data for at least one location.

- Data sources:
  - Work order execution data from `durion.workexec.DurWorkOrder` (workexec SoR).
  - Appointment/scheduling context from `durion.shopmgr.DurShopAppointment` (shopmgr SoR) via `DurWorkOrder.appointmentId` when present.
  - People availability (if shown) is read-only and must not block rendering (people SoR); **not required** for this story.

**Dependencies (implementation)**
- Reuse/extend existing Moqui screen(s) rather than inventing new routes (DECISION-INVENTORY-002).
- IDs are opaque strings; UI must not validate UUID/numeric formats (DECISION-INVENTORY-003).
- Standard error envelope parsing for REST calls where applicable (DECISION-INVENTORY-011).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- All identifiers are treated as opaque strings; UI must not reject non-UUID/non-numeric IDs (DECISION-INVENTORY-003).
- Status filter values must be from the canonical workexec status set listed in Section 10.
- If a user deep-links to a work order they cannot access, show “Not authorized” (403) rather than “not found” unless backend returns 404.

### Enable/disable rules
- Location filter:
  - Enabled only for locations the user is permitted to view.
  - If user has exactly one permitted location, preselect it and hide/disable the selector.
- Refresh:
  - Manual refresh always enabled unless a refresh is already in-flight.
  - Auto-refresh pauses after repeated failures (see Error Flows).

### Visibility rules
- Assignment context:
  - Show mechanic/bay fields if present on the work order; otherwise show “Unassigned”.
  - Appointment-derived scheduling fields (if shown) must be labeled as “Appointment” and only shown when `appointmentId` is present (DECISION-INVENTORY-010).
- PII:
  - Default to showing non-sensitive identifiers (workOrderId, status, vehicle summary if already present in existing screen). Do not introduce new PII fields in this story (see Data Requirements).

### Error messaging expectations
- Network/timeout: “Unable to refresh WIP. Showing last updated data from {timestamp}. Retry.”
- 403: “You do not have access to view work orders for this location.”
- Generic: “Unable to load work-in-progress. Try again.” Include correlationId when available.

## 10. State Model & Transitions

### Allowed states (canonical for workexec UI)
Use the workexec status taxonomy as implemented/documented:

- `DRAFT`
- `APPROVED`
- `ASSIGNED`
- `WORK_IN_PROGRESS`
- `AWAITING_PARTS`
- `AWAITING_APPROVAL`
- `READY_FOR_PICKUP`
- `COMPLETED`
- `CANCELLED`

**Decision rationale:** This is the authoritative workexec state machine representation provided in `WORKORDER_STATE_MACHINE.md` and aligned with workexec domain guidance (DECISION-INVENTORY-004).

### What counts as “Active” for WIP list
Active (default) includes all non-terminal statuses:
- `DRAFT`, `APPROVED`, `ASSIGNED`, `WORK_IN_PROGRESS`, `AWAITING_PARTS`, `AWAITING_APPROVAL`, `READY_FOR_PICKUP`

Terminal (hidden by default; shown only when `includeTerminal=true`):
- `COMPLETED`, `CANCELLED`

**Decision rationale:** WIP is operationally focused on in-flight work; terminal states are noise unless explicitly requested. This is a UI ergonomics choice and does not alter domain policy.

### “Work started” indicator (for display only)
- Consider “started” when status is `WORK_IN_PROGRESS` or later (including `READY_FOR_PICKUP`, `COMPLETED`, `CANCELLED` if cancelled after start), per DECISION-INVENTORY-004.
- Prefer a backend-provided boolean `isStarted` if available; otherwise derive from status mapping above.

### Role-based transitions
- Not applicable (view-only). However, access to the board must be permission-gated (see below).

### Permission gating (view)
- Viewing the WIP/board requires an explicit permission capability such as `WORKEXEC_DISPATCH_VIEW` (DECISION-INVENTORY-013).
- Location membership constraints must also apply (DECISION-INVENTORY-013).

## 11. Alternate / Error Flows

### Validation failures
- Invalid status filter (e.g., unknown statusId) selected via URL/query:
  - Reset to default active statuses
  - Show non-blocking message: “Some filters were reset due to invalid values.”

### Concurrency / live updates
- If polling refresh returns changed status for a row currently visible:
  - Update the row status and updated timestamp
  - If user is on `WorkOrderEdit`, the next navigation back to board reflects latest data
- If transition history is displayed and refresh occurs:
  - Re-render history list; preserve scroll position best-effort

### Unauthorized access
- If board load returns 403:
  - Show full-page authorization error
  - Do not display any cached rows for that location
- If detail load returns 403:
  - Show “Not authorized” and provide navigation back to board

### Empty states
- No active work orders:
  - Show “No work in progress” and last refresh time
  - Keep refresh active

### Dependency failures / refresh failures
- Polling refresh fails:
  - Keep last successful data visible
  - Mark view as stale and show banner with retry
- Repeated failures (e.g., 3 consecutive):
  - Pause auto-refresh for 2 minutes (configurable) and require manual retry to resume

## 12. Acceptance Criteria

### Scenario 1: Load WIP list (happy path)
**Given** the Counter Associate is authenticated and has `WORKEXEC_DISPATCH_VIEW` permission for at least one location  
**When** they open `durion-workexec/WorkOrderBoard`  
**Then** the system displays a list of active work orders (non-terminal statuses) scoped to their permitted location(s)  
**And** each row shows `workOrderId`, `statusId`, and a “Last updated” timestamp  
**And** each row shows mechanic/bay context when present or “Unassigned” when not.

### Scenario 2: Filter by status and location
**Given** the WIP list is displayed  
**When** the user filters to status `AWAITING_PARTS` and selects a permitted location  
**Then** the list refreshes and shows only work orders matching that status and location  
**And** the active filter state remains applied after manual refresh.

### Scenario 3: Drill into work order detail
**Given** the WIP list is displayed  
**When** the user selects a work order row  
**Then** the UI navigates to `durion-workexec/WorkOrderEdit` for that `workOrderId`  
**And** the detail view shows the current `statusId`  
**And** if transition history is available, it shows a list of status transitions with timestamps.

### Scenario 4: Polling refresh updates list
**Given** the WIP dashboard is open  
**And** auto-refresh is enabled  
**When** the polling interval elapses and the backend returns an updated status for a listed work order  
**Then** the row updates to the new `statusId`  
**And** the “Last updated” timestamp updates to the refresh time.

### Scenario 5: Staleness indicator on refresh failure
**Given** the WIP dashboard has loaded successfully at least once  
**When** subsequent refresh attempts fail (network error or 5xx)  
**Then** the UI keeps the last successful list visible  
**And** displays a staleness warning including the last successful refresh time  
**And** provides a “Retry” action that triggers an immediate refresh.

### Scenario 6: Unauthorized access
**Given** the user does not have `WORKEXEC_DISPATCH_VIEW` permission or is not a member of the requested location  
**When** they attempt to open the WIP dashboard for that location  
**Then** the backend returns 403  
**And** the UI shows an authorization error and does not render work order data.

## 14. Non-Functional UI Requirements

- **Performance**: Board initial load should render within 2 seconds on typical shop network for up to 100 active work orders; use pagination if larger.
- **Accessibility**: Table rows and actions keyboard-navigable; status text has sufficient contrast; refresh/stale banner announced via aria-live when it appears.
- **Responsiveness**: Usable on tablet widths; columns may collapse to a summary view on small screens.
- **i18n/timezone**:
  - Display timestamps in the user’s timezone (DECISION-INVENTORY-016).
  - If a “day” filter is added later, bucket by shop timezone when available and label timezone explicitly (DECISION-INVENTORY-016).
- **Security**: Do not introduce new PII fields in list/detail beyond what is already present in existing screens; rely on backend authorization.
