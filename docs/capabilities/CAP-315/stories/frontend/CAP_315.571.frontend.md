## Story Intent

As an Inventory Clerk, I want to load ASN data and receive against expected shipments so that receiving is controlled and accrual-ready for accounting.

## In-scope

- Create ASN from vendor shipment payload.
- Validate ASN against approved PO lines and quantities.
- Create receiving session from ASN/PO context.
- Receive items into staging with deterministic error handling.
- Render receipt summary with references (`asnId`, `poId`, `receipt/session id`) and correlation metadata when available.

## Out-of-scope

- AP invoice creation and payment workflows.
- GL posting UI or reconciliation UI.
- Put-away and pick execution flows.

## API Wiring (Expected)

- `createAsn`
- `getAsn`
- `createReceivingSession`
- `receiveItemsIntoStaging`
- `listPurchaseOrders`
- `getPurchaseOrder`

- `createAsn` / `getAsn` contracts now exist in inventory.
- ASN should be treated as the normal receiving path: `createAsn -> createReceivingSession -> receiveItemsIntoStaging`.
- ASN loading lives inside the existing receiving flow rather than in a separate dedicated subflow.
- Trucks without an ASN are less common but remain a supported fallback case.

## Receiving Architecture Note

- The frontend does not create a separate ASN-only receiving experience.
- The operator enters through the existing receiving screens used by the inventory receiving flow.
- The normal happy path is:
  1. load or create ASN
  2. review ASN-backed expected shipment data
  3. create receiving session from the ASN source document
  4. receive items into staging through the standard receiving-session flow
- Non-ASN trucks remain supported, but they are explicitly a fallback path through the same receiving entry point rather than a parallel primary flow.

## Frontend Contract Addendum

- Canonical inventory operations:
  - `POST /v1/inventory/asns` (`createAsn`)
  - `GET /v1/inventory/asns/{asnId}` (`getAsn`)
  - `POST /v1/inventory/receiving/sessions` (`createReceivingSession`)
  - `POST /v1/inventory/receiving/sessions/{sessionId}/receive` (`receiveItemsIntoStaging`)
- Session bootstrap rules:
  - ASN-backed receiving pre-populates the receiving-session source document as `ASN`.
  - Expected lines, shipment reference, and supplier context are loaded from the ASN before the operator confirms the receiving session.
  - Once the session is created, receiving proceeds exactly like the existing staging receipt flow.
- Fallback path rules:
  - When no ASN exists, the operator still uses the existing receiving entry point.
  - The fallback source document remains a receivable PO or other approved receiving source accepted by `createReceivingSession`.
  - The UI should visually distinguish fallback receiving as an exception path, not the default branch.

## Remaining Implementation Notes

- Reuse the existing receiving detail/session screens rather than adding a dedicated ASN shell.
- Keep ASN-backed receiving as the default CTA and language in the receiving flow.
- Keep non-ASN receiving available as an explicit fallback for exceptional inbound trucks.
