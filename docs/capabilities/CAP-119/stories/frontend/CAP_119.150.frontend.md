## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] People: Assign Person to Location (Effective-Dated) with Primary Flag

### Primary Persona
Manager (people/location administrator)

**Persona Metadata**
- `primary_persona`: `Manager (people/location administrator)`
- `canonical_persona`: `Location Manager`
- `persona_family`: `Location Management`
- `actor_type`: `human`

### Business Value
Ensures accurate, effective-dated employee-to-location eligibility so downstream systems (workexec/shopmgr) can build rosters and enforce staffing eligibility based on a single source of truth.

---

## 2. Story Intent

### As a / I want / So that
**As a** Manager,  
**I want** to assign an employee (Person) to one or more Locations with effective dates and a primary designation,  
**so that** operations can reliably determine where the employee is eligible to work and which location is primary at any point in time.

### In-scope
- Moqui frontend screens to:
  - View a Person’s location assignments (active + historical).
  - Create a new `PersonLocationAssignment` (with effective dates and primary flag).
  - End an assignment via setting `effectiveEndAt` (no hard delete).
- UI validation and clear error handling for:
  - Effective date validity.
  - Primary assignment rule feedback (including automatic demotion behavior as reported by backend).
  - Optimistic concurrency conflicts when the backend provides a concurrency token.
- Audit visibility (read-only) of assignment change metadata where exposed (created/updated by/at; `lastUpdatedStamp`/version).

### Out-of-scope
- Defining/altering permission matrices or authentication behavior.
- Implementing backend event emission, saga retries, or downstream integration logic.
- Location creation/management.
- Person/employee profile creation/updates beyond selecting an existing Person.
- In-place edits of assignment core fields (location, start/end, primary) beyond “end + create new” (see Business Rules).

---

## 3. Actors & Stakeholders
- **Manager (Actor):** Creates/ends assignments for employees.
- **Employee/Technician (Subject):** The Person being assigned.
- **Workexec / Shopmgr (Stakeholders):** Consume assignment data; not directly interacted with via UI in this story.
- **Auditor/HR Admin (Stakeholder):** Needs traceability of changes (audit metadata).

- User has permission to view and/or manage person location assignments (permission strings must be implemented as named permissions; see Service Contracts and Open Questions).
- Person exists and is selectable/viewable in frontend.

  - End assignment (set `effectiveEndAt`, exclusive semantics). (DECISION-PEOPLE-014, DECISION-PEOPLE-023)
  - Standard error schema for 400/409. (DECISION-PEOPLE-018)
  - Optimistic concurrency via `lastUpdatedStamp` when exposed. (DECISION-PEOPLE-017)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From People/Employees list: select a Person → “Location Assignments” section/tab.
- Direct route (deep link): `/people/person/{personId}/locations` (final route must match repo conventions; see Open Questions).

### Screens to create/modify
1. **Person detail screen (People module)**:
   - Add a “Location Assignments” subsection with an embedded list and actions.
2. **Create assignment screen/dialog**:
   - Used only for creating a new assignment record (not editing core fields of an existing assignment).
3. **End assignment confirmation dialog**:
   - Sets `effectiveEndAt` rather than deleting.

### Navigation context
- Breadcrumb: People → Person → Location Assignments
- Back navigation returns to Person detail.

### User workflows (happy + alternate paths)

**Happy path (Create primary assignment)**
1. Manager opens Person → Location Assignments.
2. Clicks “Add Assignment”.
3. Selects Location, sets `primary=true`, sets `effectiveStartAt`, optional `effectiveEndAt` (exclusive).
4. Saves; UI refreshes list, showing new assignment as active/primary.
5. If backend demoted a prior primary, UI reflects updated prior assignment after refresh (no UI-side demotion logic).

**Alternate path (Create non-primary secondary assignment)**
- Same as above but `primary=false`; primary remains unchanged.

**Alternate path (End assignment)**
- Manager selects an active assignment → “End Assignment”.
- Provides end timestamp (default now) and confirms.
- Assignment shows ended/inactive and disappears from “Active only” view.

**Alternate path (View history)**
- Manager toggles “Include history” to view ended/future assignments.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `locationId` required.
- `effectiveStartAt` required, must be valid ISO-8601 timestamp input.
- If `effectiveEndAt` provided: must be **strictly greater than** `effectiveStartAt` (half-open interval; end is exclusive). (DECISION-PEOPLE-014)
- Primary semantics:
  - UI allows selecting `primary=true`.
  - UI must display helper text: “Setting Primary may automatically demote the current primary assignment.” (DECISION-PEOPLE-004)
  - UI must not attempt to demote any other assignment locally; it must refresh after create and render server results. (DECISION-PEOPLE-004)
- Overlap handling:
  - UI must not implement overlap detection as a policy engine.
  - If backend returns 409 for overlap/constraint conflicts, show conflict banner and keep form values for correction. (DECISION-PEOPLE-018)

### Enable/disable rules
- Disable Save while submitting or when required fields missing/invalid.
- Disable “End” action for ended assignments and for assignments not currently active.
- Hide/disable mutation actions when user lacks manage permission; view-only users can still see list if permitted. (DECISION-PEOPLE-013)

### Visibility rules
- Active assignments shown by default; “Include history” toggle reveals ended/future assignments. (DECISION-PEOPLE-021)
- Primary indicator shown in list (e.g., “Primary” column/badge).
- Do not display `tenantId` anywhere in this UI. (DECISION-PEOPLE-019)

### Error messaging expectations
- 400 validation errors: show field-level errors where possible; otherwise show banner with backend `message`. (DECISION-PEOPLE-018)
- 403: show “You do not have permission to manage location assignments.” and disable/hide mutation controls.
- 404 (person not found): show not-found state and navigation back.
- 409 conflict (overlap, concurrency, or other constraint): show conflict banner with recommended next step (“Refresh and try again.”) and provide a Refresh action. (DECISION-PEOPLE-018, DECISION-PEOPLE-017)

## 9. Service Contracts (Frontend Perspective)

> Contracts below follow People REST conventions and must be implemented/exposed by Moqui. If the repo uses different routing/service naming, map these to Moqui screen transitions/services while preserving shapes and semantics. (DECISION-PEOPLE-021)

### Load/view calls
1. **Person summary**
   - `GET /rest/api/v1/people/persons/{personId}`
   - Response includes at least: `personId`, `displayName`, `employmentStatus`, and capability flags if available.

2. **List assignments**
   - `GET /rest/api/v1/people/persons/{personId}/location-assignments?includeHistory=false&page=1&pageSize=25`
   - Response shape (preferred): `{ items: PersonLocationAssignment[], page, pageSize, total }` (DECISION-PEOPLE-021)
   - Default sort: stable and deterministic (backend-defined; UI should not assume). If not provided, UI sorts by `effectiveStartAt desc` for display only.

3. **Locations for picker**
   - `GET /rest/api/v1/people/locations?status=ACTIVE&page=1&pageSize=100` (or a shared Location domain endpoint if that is the platform standard; see Open Questions)
   - Response includes `locationId`, `locationName`.

### Create/update calls
1. **Create assignment**
   - `POST /rest/api/v1/people/persons/{personId}/location-assignments`
   - Body:
     - `locationId` (required)
     - `effectiveStartAt` (required)
     - `effectiveEndAt` (optional)
     - `primary` (required boolean)
     - `role` (optional; may be null)
     - `changeReasonCode` (optional)
   - Success:
     - 201/200 with created assignment payload (including `assignmentId`) and any server-side adjustments (e.g., demoted prior primary reflected on subsequent list reload). (DECISION-PEOPLE-004)

2. **End assignment**
   - Preferred:
     - `POST /rest/api/v1/people/location-assignments/{assignmentId}/end`
     - Body: `effectiveEndAt` (required), `lastUpdatedStamp` (optional/required depending on backend) (DECISION-PEOPLE-017)
   - Acceptable alternative:
     - `PUT /rest/api/v1/people/location-assignments/{assignmentId}` with `effectiveEndAt` set (and `lastUpdatedStamp`)

### Error handling expectations
- 400:
  - `{ errorCode, message, fieldErrors?: [{ field, message, code? }] }` (DECISION-PEOPLE-018)
- 409:
  - `{ errorCode, message, blockingIds?: [], details?: {} }` (DECISION-PEOPLE-018)
  - UI behavior: show conflict banner + Refresh action; do not clear user input.
- 403:
  - Standard forbidden response; UI must not infer existence from differing errors (handle 403/404 consistently in messaging where appropriate). (DECISION-PEOPLE-013)
- Network/timeouts:
  - Show retry UI state; preserve last loaded list on mutation failure.

## 10. State Model & Transitions

### Allowed states (derived from dates; display-only)
- **Scheduled**: `effectiveStartAt` in the future (now < start)
- **Active**: `now >= effectiveStartAt` and (`effectiveEndAt` is null OR `now < effectiveEndAt`) (exclusive end) (DECISION-PEOPLE-014)
- **Ended/Historical**: `effectiveEndAt` is not null and `now >= effectiveEndAt`

### Role-based transitions
- Users with manage permission:
  - Create assignment (scheduled or active depending on start date).
  - End assignment (set end timestamp; must be > start).
- Users without manage permission:
  - No create/end actions.

### UI behavior per state
- Scheduled:
  - Display as upcoming.
  - End action should be disabled by default (ending before it starts is allowed only if backend supports; UI should block by default with validation “End must be after start”).
- Active:
  - End action enabled.
- Ended:
  - Read-only; no actions.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing required fields → inline errors, no submit.
- `effectiveEndAt <= effectiveStartAt` → inline error on end date (exclusive end).
- Invalid timestamp format → inline error.

### Backend validation failures (400)
- Render `fieldErrors` inline when present.
- Render `message` in a banner when field mapping is not provided.

### Concurrency conflicts (409)
- If backend returns 409 due to `lastUpdatedStamp` mismatch:
  - UI shows “This assignment changed since you loaded it. Refresh to see the latest state.”
  - Provide “Refresh” button that reloads assignments and re-evaluates action availability. (DECISION-PEOPLE-017, DECISION-PEOPLE-018)

### Primary demotion side-effect
- After creating a primary assignment, the backend may demote a previous primary.
- UI must always reload the assignment list after create and render the server’s resulting primary flags; it must not attempt to predict which record was demoted. (DECISION-PEOPLE-004)

### Unauthorized access
- If list load returns 403: show “Not authorized” state; do not show assignment data.
- If mutation returns 403: show banner; keep view mode and do not change list.

### Empty states
- No assignments:
  - Show “No location assignments yet” with CTA “Add Assignment” (only if authorized).
- No locations available for picker:
  - Show “No active locations available” and disable Save.

## 12. Acceptance Criteria

### Scenario 1: View a person’s assignments (empty)
**Given** I am a Manager with permission to view location assignments  
**And** a Person exists with no `PersonLocationAssignment` records  
**When** I open the Person’s “Location Assignments” view  
**Then** I see an empty state indicating no assignments exist  
**And** I see an “Add Assignment” action available if I have manage permission

### Scenario 2: Create first primary assignment
**Given** I am a Manager with permission to manage location assignments  
**And** a Person exists with no current assignments  
**When** I create a new assignment with a valid `locationId`, valid `effectiveStartAt`, and `primary=true`  
**Then** the system saves successfully  
**And** the assignment list refreshes showing the new assignment marked as Primary

### Scenario 3: Create secondary (non-primary) assignment
**Given** I am a Manager with permission to manage location assignments  
**And** a Person has an existing active primary assignment  
**When** I create a second assignment to a different location with `primary=false` and valid dates  
**Then** the system saves successfully  
**And** the list shows both assignments  
**And** the original assignment remains marked as Primary

### Scenario 4: Create new primary triggers backend demotion and UI reflects result
**Given** I am a Manager with permission to manage location assignments  
**And** a Person has an existing active primary assignment at Location A  
**When** I create a new assignment at Location B with `primary=true` and a later `effectiveStartAt`  
**Then** the system saves successfully  
**And** after refresh, the list shows the Location B assignment as Primary  
**And** the previously primary assignment is no longer primary as returned by the backend

### Scenario 5: End date uses exclusive semantics (client-side validation)
**Given** I am a Manager with permission to manage location assignments  
**When** I enter an `effectiveEndAt` that is equal to or before `effectiveStartAt`  
**Then** the UI prevents submission  
**And** I see a validation message indicating the end must be after the start

### Scenario 6: End an active assignment
**Given** I am a Manager with permission to manage location assignments  
**And** a Person has an active assignment  
**When** I end the assignment by setting `effectiveEndAt` to now (or a selected timestamp after the start)  
**Then** the system saves successfully  
**And** the assignment is shown as ended/historical and is no longer shown in “Active only” view

### Scenario 7: 409 conflict on end requires refresh
**Given** I am a Manager with permission to manage location assignments  
**And** I am ending an assignment that has been modified by another admin since I loaded it  
**When** I submit the end action  
**Then** the backend responds with 409  
**And** the UI shows a conflict message with a “Refresh” action  
**And** clicking “Refresh” reloads the assignment list and updates the displayed state

### Scenario 8: Permission denied on mutation
**Given** I am authenticated but do not have permission to manage location assignments  
**When** I attempt to create or end an assignment  
**Then** the system denies the action with a 403 response  
**And** the UI displays a permission error message  
**And** no changes are applied
