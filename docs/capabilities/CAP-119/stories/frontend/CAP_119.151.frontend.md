## Issue Body

## 1. Story Header

**Title**  
[FRONTEND] Location: Create/Update Location (pos-location) Including Timezone

**Primary Persona**  
Admin (location administrator)

**Business Value**  
Admins can create and maintain accurate location metadata (including timezone) so downstream systems (staffing, scheduling, timekeeping, work execution) can anchor activity to the correct site context.

---

## 2. Story Intent

**As a** Admin  
**I want** to create and update Locations (code, name, address, timezone, status, optional parent)  
**So that** the organization has an authoritative, up-to-date catalog of sites with correct timezone context.

### In-scope
- Frontend screens and flows to:
  - Create a new Location.
  - View an existing Location.
  - Edit/update an existing Location.
  - Soft-deactivate/reactivate a Location via `status` update (ACTIVE/INACTIVE).
- Client-side validation aligned to known domain rules:
  - `code` immutable after creation. (DECISION-LOCATION-001)
  - `name` uniqueness is case-insensitive + trimmed (validated via backend; UI should surface conflicts). (DECISION-LOCATION-002)
  - `timezone` must be a valid IANA timezone identifier; UI uses backend-provided allowed list with fallback. (DECISION-LOCATION-003)
  - Optional `parentLocationId` must reference an existing Location; UI prevents self-parent selection. (DECISION-LOCATION-021)
- Error handling and feedback for typical backend errors (400/401/403/404/409) including optimistic locking conflicts (409 with `OPTIMISTIC_LOCK_FAILED`).

### Out-of-scope (explicit)
- Enforcing “Inactive locations prevent new staffing assignments” in staffing/scheduling/workorder creation flows (belongs to consuming domains).
- Defining hierarchy cascade behavior (e.g., parent INACTIVE cascades to children).
- Sync/import workflows (SyncLog) and external authoritative system ingestion.
- Managing Bays, Mobile Units, Service Areas, Travel Buffer Policies, site default storage locations (separate stories).

---

## 3. Actors & Stakeholders

- **Admin (primary user):** Creates/updates location records.
- **Location Domain Service (system of record):** Persists and validates Location data; returns errors for constraint violations.
- **Downstream consumers (stakeholders):** People/Scheduling/Workexec systems consuming `locationId`, `status`, and `timezone`.

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated.
- User has permission to manage locations:
  - Read-only access: `location:view`
  - Mutations (create/update/status change): `location:manage` (DECISION-LOCATION-007)

### Dependencies
- Backend endpoints for Location CRUD exist and are reachable from Moqui frontend.
  - Use REST convention prefix `/rest/api/v1/location/...` (DECISION-LOCATION-006). Concrete endpoint list must be confirmed during implementation (see Open Questions).
- Timezone allowed list endpoint exists (preferred) or frontend fallback list is available:
  - Preferred: backend-provided list (DECISION-LOCATION-003)
  - Fallback: static list only when endpoint unavailable (DECISION-LOCATION-003)
- Ability to query Locations for parent selection (list/search endpoint with pagination).

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side where safe; authoritative on server)
- **code** (DECISION-LOCATION-001)
  - Create: required; trim on submit; must be unique (server-enforced).
  - Edit: read-only; UI must not send `code` in update payload unless backend requires echoing unchanged fields (prefer PATCH).
  - Conflict: map backend 409 to code field with message “Code already exists.”

- **name** (DECISION-LOCATION-002)
  - Required; trim on submit.
  - Uniqueness is case-insensitive + trimmed (server-enforced).
  - Conflict: map backend 409 to name field with message “Name already exists.”

- **timezone** (DECISION-LOCATION-003)
  - Required.
  - UI uses backend-provided allowed list endpoint; selection is constrained to list values.
  - Fallback: if timezone list endpoint fails/unavailable, UI may allow a searchable static list (temporary) and still submits selected IANA ID; if neither available, block save with retryable error.

- **status** (DECISION-LOCATION-022, DECISION-LOCATION-019)
  - Allowed values: `ACTIVE`, `INACTIVE`.
  - Create: status defaults to `ACTIVE`; create form does not expose status selection. (DECISION-LOCATION-022)
  - Edit: status change is allowed via explicit actions (Deactivate/Reactivate) for users with `location:manage`. (DECISION-LOCATION-019)

- **parentLocationId** (DECISION-LOCATION-021)
  - Optional.
  - Must reference an existing Location.
  - UI prevents selecting self as parent.
  - Backend prevents cycles; UI does not attempt to enforce max depth.

- **buffers** (from Location invariants)
  - `checkInBufferMinutes` and `cleanupBufferMinutes`: null or non-negative integers only.

- **operatingHours / holidayClosures**
  - Not in scope for this story (separate story). If backend includes these fields in Location payload, detail screen may display them read-only but no editing in this story.

### Enable/disable rules
- Save disabled while submitting.
- Create: Save enabled only when required fields valid.
- Edit: Save enabled only when form dirty and required fields valid.
- Code input disabled in edit mode.

### Visibility rules
- Parent selector visible in create and edit.
- Status selector hidden on create (status defaults to ACTIVE); status actions visible on detail for manage users.

### Error messaging expectations
- 400 validation: show field-level messages when backend provides field mapping; otherwise show banner with backend message.
- 409 conflict: show specific message for code/name duplicates.
- 403: show “You don’t have permission to manage locations.”
- 404 on edit/detail: show not-found screen with link back to list.
- 409 `OPTIMISTIC_LOCK_FAILED`: show reload-required dialog.

## 9. Service Contracts (Frontend Perspective)

> Use REST convention `/rest/api/v1/location/...` (DECISION-LOCATION-006). Exact endpoint paths and payload shapes must be confirmed during implementation and documented in the PR (risk item).

### Load/view calls
- **List Locations**
  - `GET /rest/api/v1/location/locations?status=ACTIVE|INACTIVE|ALL&pageIndex=<n>&pageSize=<n>&q=<optional>`
  - Default UI request omits `status` and relies on server default OR explicitly sends `status=ACTIVE` (UI should send explicitly to ensure deterministic behavior). (DECISION-LOCATION-008)
  - Response envelope expectation (DECISION-LOCATION-013 pattern):
    - `{ items: LocationSummary[], totalCount: number }`

- **Get Location by ID**
  - `GET /rest/api/v1/location/locations/{locationId}`
  - Response: Location with `version` if optimistic locking is supported.

- **List Timezones (allowed list)**
  - `GET /rest/api/v1/location/timezones` (DECISION-LOCATION-003)
  - Response: list of IANA timezone IDs (strings) or objects `{id, label}`; UI supports either.

### Create/update calls
- **Create Location**
  - `POST /rest/api/v1/location/locations`
  - Request (minimum):
    - `code`, `name`, `timezone`
    - Optional: `parentLocationId`, `address` (contract-driven), `checkInBufferMinutes`, `cleanupBufferMinutes`
  - Status on create:
    - UI does not send `status`; backend defaults to `ACTIVE`. (DECISION-LOCATION-022)

- **Update Location**
  - Preferred: `PATCH /rest/api/v1/location/locations/{locationId}`
  - Request includes only editable fields plus `version` (if required by backend):
    - `name`, `timezone`, `parentLocationId`, `address`, `checkInBufferMinutes`, `cleanupBufferMinutes`, `version`
  - UI must not send `code` changes. (DECISION-LOCATION-001)

### Submit/transition calls
- **Deactivate / Reactivate**
  - Option A (preferred): `POST /rest/api/v1/location/locations/{locationId}:deactivate` and `:reactivate`
  - Option B: `PATCH /rest/api/v1/location/locations/{locationId}` with `{ status: "INACTIVE" | "ACTIVE", version }`
  - UI must support whichever is implemented; implementation must pick one and document it in PR.

### Error handling expectations (HTTP + codes)
- 400: validation errors (missing required fields, invalid timezone, negative buffers, cycle attempt).
- 401: not authenticated.
- 403: not authorized (enforce `location:manage` for mutations). (DECISION-LOCATION-007)
- 404: location not found.
- 409: conflicts:
  - duplicate code/name
  - optimistic locking conflict with code `OPTIMISTIC_LOCK_FAILED` (Location invariant)
- Error payload expectation:
  - Stable `code` and optional `field` for mapping; UI must gracefully handle missing `field`.

## 11. Alternate / Error Flows

### Validation failures
- Missing required fields on create (code/name/timezone): prevent submit; show inline errors.
- Invalid timezone:
  - If timezone list loaded: cannot select invalid value.
  - If fallback mode: backend may reject; map `INVALID_TIMEZONE` to timezone field when provided. (DECISION-LOCATION-003)
- Negative buffer minutes: block client-side; if server rejects, map to field.

### Concurrency conflicts
- If backend returns 409 with `OPTIMISTIC_LOCK_FAILED`:
  - Show blocking dialog: “This location was updated by someone else. Reload to continue.”
  - Actions: Reload (discard local changes) / Cancel.

### Unauthorized access
- 403 on list/detail: show authorization error page (view permission missing).
- 403 on create/edit/status change: show “You don’t have permission to manage locations.” and keep user on current screen without persisting changes.

### Empty states
- LocationList with no locations: show empty state + “Create Location”.
- Parent selector when no other locations exist: show “No parent locations available” and allow clearing.

### Timezone list unavailable
- If timezone endpoint fails:
  - Show inline warning “Timezone list unavailable; retry.”
  - Allow fallback static list if available; otherwise disable Save and provide Retry action. (DECISION-LOCATION-003)

**And** I am navigated to the Location detail screen for the new location  
**And** I see a success confirmation

### Scenario 2: Update location fields (success; code immutable)
**Given** I am an authenticated user with `location:manage`  
**And** an existing Location exists  
**When** I open the Location edit screen  
**Then** the `code` field is displayed as read-only  
**When** I change the `name` and `timezone` and submit  
**Then** the updated values are displayed on the Location detail screen

### Scenario 3: Attempt to modify immutable code (prevented)
**Given** I am editing an existing Location  
**Then** I cannot edit the `code` field  
**And** the update request does not include any changed `code` value

### Scenario 4: Duplicate code on create (conflict)
**Given** a Location already exists with `code` = "MAIN-WH"  
**When** I attempt to create a new Location with `code` = "MAIN-WH"  
**Then** the save fails with a conflict response  
**And** I see a field-level error indicating the code already exists  
**And** no new Location is created

### Scenario 5: Duplicate name on create/update (case-insensitive, trimmed)
**Given** a Location already exists with `name` = "Main Shop"  
**When** I attempt to create or update a Location with `name` = "  main shop  "  
**Then** the save fails with a conflict response  
**And** I see a field-level error indicating the name already exists

### Scenario 6: Invalid timezone (validation error)
**Given** I am on the create/edit Location screen  
**When** I submit a Location with an invalid `timezone` value  
**Then** the save fails  
**And** I see an error message on the timezone field (or form banner) indicating the timezone is invalid

### Scenario 7: Deactivate location (ACTIVE → INACTIVE)
**Given** I am an authenticated user with `location:manage`  
**And** an existing Location is `ACTIVE`  
**When** I trigger the “Deactivate” action and confirm  
**Then** the Location detail shows `status` = `INACTIVE`

### Scenario 8: Reactivate location (INACTIVE → ACTIVE)
**Given** I am an authenticated user with `location:manage`  
**And** an existing Location is `INACTIVE`  
**When** I trigger the “Reactivate” action and confirm  
**Then** the Location detail shows `status` = `ACTIVE`

### Scenario 9: Prevent self-parent selection
**Given** I am editing an existing Location with `locationId` = "loc-1"  
**When** I open the parent location selector  
**Then** "loc-1" is not selectable as its own parent  
**And** if I attempt to submit `parentLocationId` = "loc-1" via any means  
**Then** the save fails and I see an error message

### Scenario 10: Optimistic locking conflict (reload required)
**Given** I am editing a Location  
**And** another user updates the same Location after I loaded it  
**When** I submit my changes with a stale `version`  
**Then** the save fails with a conflict response and error code `OPTIMISTIC_LOCK_FAILED`  
**And** I am prompted to reload before continuing

### Scenario 11: Not authorized (forbidden)
**Given** I am authenticated but do not have `location:manage`  
**When** I attempt to open the create/edit Location screen or submit changes or change status  
**Then** I receive a forbidden response  
**And** the UI shows an authorization error message and does not persist changes

### Scenario 12: Timezone list endpoint unavailable (fallback behavior)
**Given** I am on the create/edit Location screen  
**And** the timezone list endpoint returns an error  
**When** the UI cannot load the allowed timezone list  
**Then** I see a retryable error state for timezone selection  
**And** if a static fallback list is available, I can still select a timezone from the fallback list and save  
**And** if no fallback list is available, Save is disabled until the list loads successfully
