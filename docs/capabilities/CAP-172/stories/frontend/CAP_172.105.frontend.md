## Issue Body

## 1. Story Header

### Title
[FRONTEND] Audit UI: Search/Detail + Pricing Evidence Drilldown (Pricing Snapshot + Pricing Rule Trace) with Guardrails, Permissions, and Safe Rendering

### Primary Persona
Compliance Auditor

### Business Value
Provide verifiable, immutable evidence for price/cost changes and “how price was calculated” rule traces so margin disputes and compliance investigations can be resolved with defensible, searchable records—without exposing sensitive payloads beyond least-privilege permissions.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Compliance Auditor  
- **I want** to search immutable audit history for pricing/cost changes and drill from an estimate line’s `snapshotId` into the stored pricing snapshot and rule evaluation trace  
- **So that** I can explain pricing outcomes, validate margin calculations, and resolve disputes with unalterable evidence.

### In-scope
- New/updated **Moqui screens** for:
  - Searching audit records with mandatory date range + indexed filter guardrails
  - Viewing an **audit record detail** by `eventId` (normalized fields; raw payload gated)
  - Viewing a **Pricing Snapshot** by `snapshotId` and its associated **Pricing Rule Trace** (paged/truncated handling)
  - Drill path: **estimate line → snapshot → rule trace** (read-only)
- Permission-gated UI and safe rendering per audit domain rules:
  - Raw payload behind `audit:payload:view`
  - Pricing evidence behind `audit:pricing-snapshot:view` and `audit:pricing-trace:view`
  - Cross-location search behind `audit:scope:cross-location`
  - Proof fields display-only behind `audit:proof:view`
- Standard pagination, sorting, empty states, and deterministic error handling.

### Out-of-scope
- Implementing audit ingestion, retention enforcement, immutability storage controls, or outbox delivery (backend responsibility).
- Defining or changing pricing rule logic/computation behavior (pricing domain responsibility).
- Creating/modifying/deleting audit records, snapshots, traces, or reason codes from the UI.
- Reason-code registry management UI (admin screens) beyond optional read-only lookup for display labels.

## 5. UX Summary (Moqui-Oriented)

### Entry points
1. **Administration / Compliance → Audit Logs**: opens Audit Search/List screen (visible only with `audit:log:view`).
2. **Contextual links** (visible only with `audit:log:view`):
   - From Work Order, Appointment, Mechanic, Movement, Product screens: “View Audit Logs” pre-filtered by the relevant identifier (when available).
3. **Estimate Line → View Pricing Trace**: from estimate line detail and estimate/invoice review contexts, show action when `snapshotId` exists and user has `audit:pricing-snapshot:view` (and `audit:pricing-trace:view` for trace section).

### Screens to create/modify
- **Create:** `apps/pos/audit/AuditSearch.xml`
  - Search form + results list
- **Create:** `apps/pos/audit/AuditDetail.xml`
  - Detail view for a single audit event by `eventId`
- **Create:** `apps/pos/audit/PricingSnapshotDetail.xml`
  - Pricing snapshot detail by `snapshotId` + linked trace viewer
- **Modify (integration):** Workexec estimate line detail + estimate/invoice review screens
  - Add navigation action to `PricingSnapshotDetail` with `snapshotId=<value>`

### Navigation context
- Audit screens are tenant-scoped and location-scoped by default to the user’s current POS location context.
- Cross-location search UI is only visible/enabled when the user has `audit:scope:cross-location`; when used, the UI must require explicit `locationIds[]`.

### User workflows (happy + alternate paths)

**Happy path A — Search audit logs**
1. User opens Audit Search.
2. Selects `fromUtc` and `toUtc` (UTC inputs; UI may display local time but converts to UTC).
3. Provides at least one indexed filter (e.g., `productId` or `sku` or `partNumber` or `eventType` or `actorId` or `aggregateId` or `correlationId` or `reasonCode` or workexec IDs).
4. Submits search; sees paginated results sorted by `occurredAt desc`.
5. Opens a row to view Audit Detail.

**Happy path B — Drill estimate line → snapshot → rule trace**
1. User opens an estimate line that has `snapshotId`.
2. Clicks “View Pricing Trace”.
3. Pricing Snapshot Detail loads snapshot.
4. If snapshot includes `ruleTraceId`, the screen loads trace via trace endpoint; renders steps with safe rendering and pagination/truncation handling.

**Alternate path — Missing snapshotId on estimate line**
- Action is hidden; optionally show a non-blocking message “Pricing evidence not available for this line.”

**Alternate path — Trace too large**
- UI loads first page of steps; user can load more pages if `nextPageToken` is returned, or sees “Trace truncated” if `isTruncated=true`.

## 6. Functional Behavior

### Triggers
- Navigate to Audit Search screen.
- Submit audit search form.
- Navigate to Audit Detail with `eventId`.
- Navigate to Pricing Snapshot Detail with `snapshotId`.
- In Pricing Snapshot Detail: request trace page(s) when `ruleTraceId` exists.

### UI actions
- **Audit Search**
  - User sets date range and filters; clicks Search.
  - User changes page/sort; list refreshes.
  - User clicks a result row; navigates to Audit Detail.
- **Audit Detail**
  - User views normalized fields.
  - If user has `audit:payload:view` and `rawPayload` exists, user can expand/collapse raw payload (escaped text) and copy.
  - If user lacks `audit:payload:view`, raw payload section is hidden entirely (no “locked” preview).
- **Pricing Snapshot Detail**
  - User views snapshot metadata and final price (if present).
  - User views quote context only as returned (escaped text); no UI-side redaction.
  - If `ruleTraceId` exists and user has `audit:pricing-trace:view`, user can view trace steps with optional client-side filtering (applied/rejected/skipped).
  - If trace endpoint indicates pagination/truncation, user can load more pages (if token) or sees truncation notice.

### State changes
- None (read-only). UI state only:
  - current filters, pagination, sort
  - expanded/collapsed raw payload
  - trace step filter and pagination token

### Service interactions (frontend ↔ Moqui)
Moqui screens use transitions that call services (or REST calls via Moqui) mapping to capability endpoints:

- Audit Search → `GET /audit/logs/search`
- Audit Detail → `GET /audit/logs/detail?eventId=...`
- Meta (optional) → `GET /audit/meta/eventTypes`, `GET /audit/meta/reasonCodes`, `GET /audit/meta/locations`
- Pricing Snapshot → `GET /audit/pricing/snapshot?snapshotId=...`
- Pricing Trace → `GET /audit/pricing/trace?ruleTraceId=...` (with pagination token if supported)

## 7. Business Rules (Translated to UI Behavior)

### Validation
**Query guardrails (mirror backend; backend authoritative):**
- Require `fromUtc` and `toUtc` on Audit Search.
- Validate `fromUtc <= toUtc`.
- Enforce max window: `toUtc - fromUtc <= 90 days` (default). If user selects a larger window, block submission with message: “Date range must be 90 days or less.”
- Require at least one indexed filter beyond date range. Qualifying filters (AND semantics with date range):
  - `workOrderId`, `appointmentId`, `mechanicId`, `movementId`
  - `productId`, `sku`, `partNumber`
  - `actorId`
  - `eventType`
  - `aggregateId`
  - `correlationId`
  - `reasonCode`
- If user has cross-location permission and selects multiple locations, require `locationIds[]` non-empty.

**Decision rationale (normative):**
- Mandatory date range + max window + indexed filter requirement are required guardrails (AUD-SEC-005).
- Multi-identifier product search is required (AUD-SEC-007).
- Cross-location requires explicit permission and explicit location filters (AUD-SEC-002/003).

### Enable/disable rules
- Audit navigation/menu item visible only with `audit:log:view`.
- Audit Detail route accessible only with `audit:log:view-detail` (and `audit:log:view` implied/also checked).
- Raw payload expand/copy controls visible only with `audit:payload:view`.
- Pricing Snapshot Detail accessible only with `audit:pricing-snapshot:view`.
- Pricing Trace section visible only with `audit:pricing-trace:view`.
- Cross-location location picker visible/enabled only with `audit:scope:cross-location`.
- Proof fields (`hash`, `prevHash`, `signature`) visible only with `audit:proof:view` and must be labeled “Provided (not verified)” unless backend provides explicit verification status.

### Visibility rules
- If user lacks permission for a screen, show Access Denied state (403) without leaking record existence.
- Deep-link metadata (if present on audit detail) is optional; hide absent links. Links must navigate via frontend route resolution (no URLs stored in audit data).

### Error messaging expectations
- 400 validation errors: show inline field errors (date range, missing filter, max window, missing locationIds for cross-location).
- 401: redirect to login/session restore per POS standard.
- 403: show Access Denied.
- 404: show Not Found for `eventId`/`snapshotId`/`ruleTraceId` without revealing additional info.
- 429: show “Too many requests” with retry-after guidance if provided.
- 5xx/timeouts: show generic retryable error; do not display raw payload or stack traces.

## 8. Data Requirements

### Entities involved (logical; UI consumes)
- `AuditLog` (immutable log entry; system of record is audit domain)
- `PricingSnapshot` (immutable evidence record; stored/served by audit domain)
- `PricingRuleTrace` (immutable evidence record; stored/served by audit domain)

### Fields (type, required, defaults)

**AuditLog (list + detail) — minimum required fields**
- `auditLogId` (UUIDv7, read-only; optional to display)
- `eventId` (UUIDv7, required, read-only; primary detail key)
- `schemaVersion` (string/int, required, read-only)
- `eventType` (string, required, read-only; controlled vocabulary)
- `occurredAt` (datetime UTC, required, read-only)
- `emittedAt` (datetime UTC, optional, read-only)
- `tenantId` (string, read-only; not displayed unless admin/debug)
- `locationId` (UUIDv7/string, required, read-only; displayed)
- `actor` (object, optional but preferred)
  - `actorType` (string, required if actor present)
  - `actorId` (UUIDv7/string, required if actor present)
  - `displayName` (string, optional)
- `aggregateType` (string, required, read-only)
- `aggregateId` (UUIDv7/string, required, read-only)
- `changeSummaryText` (string, optional, read-only)
- `changePatch` (structured diff, optional, read-only; display if present)
- `reasonCode` (string, optional, read-only)
- `reasonNotes` (string, optional, read-only; length-limited; escaped rendering)
- `correlationId` (string, optional, read-only; W3C trace context correlation)
- `sourceSystem` (string, optional, read-only)
- `rawPayload` (string/text, optional, read-only; restricted permission)
- Proof fields (optional; read-only; restricted permission):
  - `hash`, `prevHash`, `signature`

**PricingSnapshot (detail) — minimum required fields**
- `snapshotId` (UUIDv7, required, read-only)
- `timestamp` (datetime UTC, required, read-only)
- `finalPrice` (money, required if returned; read-only)
- `ruleTraceId` (UUIDv7, optional if trace embedded; read-only)
- `quoteContext` (text/JSON string, optional/restricted; escaped rendering)

**PricingRuleTrace (detail) — minimum required fields**
- `ruleTraceId` (UUIDv7, required, read-only)
- `evaluationSteps[]` (array; may be paged)
  - `stepIndex` (int, required; stable index)
  - `ruleId` (string, required)
  - `status` (`APPLIED|REJECTED|SKIPPED`, required)
  - `inputs` (text/JSON string, optional; may be redacted; escaped rendering)
  - `outputs` (text/JSON string, optional; may be redacted; escaped rendering)
- Pagination/truncation indicators (one of the following patterns must be supported by backend; UI supports both):
  - `nextPageToken` (string, optional)
  - `isTruncated` (boolean, optional) + `nextPageToken` (optional)

### Read-only vs editable by state/role
- All fields are read-only for all roles in this story.
- No create/update/delete actions exist in UI.

### Derived/calculated fields
- Display timestamps in user locale/timezone, but always send UTC query parameters (`fromUtc`, `toUtc`) and show UTC values in a “Raw/UTC” view if needed.
- Optional derived display:
  - “Actor display” = `actor.displayName` if present else `actor.actorId` else “System”.

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation may wrap these as services; the frontend contract is the capability endpoints and parameters below.

### Load/view calls

**Audit search**
- `GET /audit/logs/search`
  - Required params:
    - `fromUtc` (ISO-8601 UTC)
    - `toUtc` (ISO-8601 UTC)
  - At least one of (indexed filters; AND semantics with date range):
    - `workOrderId`, `appointmentId`, `mechanicId`, `movementId`
    - `productId`, `sku`, `partNumber`
    - `actorId`
    - `eventType`
    - `aggregateId`
    - `correlationId`
    - `reasonCode`
  - Location scoping:
    - If user lacks `audit:scope:cross-location`: backend implicitly scopes to session location; UI does not send `locationIds[]` unless explicitly supported/required by backend.
    - If user has `audit:scope:cross-location`: UI must send `locationIds[]` (one or more).
  - Pagination/sort (UI-supported; backend must support some form):
    - `pageSize`, `pageIndex` (or cursor token if backend uses it)
    - `sortBy=occurredAt`, `sortOrder=desc` (default)

**Audit detail**
- `GET /audit/logs/detail?eventId=<UUIDv7>`
  - Returns `AuditLog` detail fields.
  - Raw payload included only if caller has `audit:payload:view` (backend enforced).

**Meta endpoints**
- `GET /audit/meta/eventTypes` (tenant-scoped)
- `GET /audit/meta/reasonCodes` (tenant-scoped; optional for display labels)
- `GET /audit/meta/locations` (tenant-scoped; used only when cross-location UI is enabled)

**Pricing evidence**
- `GET /audit/pricing/snapshot?snapshotId=<UUIDv7>`
  - Returns snapshot; should include `ruleTraceId` by default.
  - May embed trace only for small traces (backend decision); UI must handle both.
- `GET /audit/pricing/trace?ruleTraceId=<UUIDv7>&pageToken=<optional>`
  - Returns steps page and pagination/truncation indicators.

### Create/update calls
- none.

### Submit/transition calls
- Moqui screen transitions should map to the above GET endpoints (or internal services that proxy them).
- Export is not implemented in this story unless separately added; do not include export UI actions here.

### Error handling expectations
- 400: backend returns field-level errors for guardrail violations; UI maps to inline errors.
- 401/403/404/429/5xx: map to standard POS states as described in Business Rules.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing `fromUtc`/`toUtc`: block submit; show inline errors.
- `fromUtc > toUtc`: block; show inline error.
- Range > 90 days: block; show inline error.
- Missing indexed filter beyond date range: block; show message listing acceptable filters.
- Cross-location enabled but no `locationIds[]` selected: block; show inline error.

### Concurrency conflicts
- Not applicable (read-only). If backend returns 409/412 due to caching/ETag mismatch, UI retries once without ETag and then shows retryable error.

### Unauthorized access
- 401: redirect to login/session restore.
- 403: show Access Denied; do not reveal whether `eventId`/`snapshotId` exists.

### Empty states
- Search returns 0 results: show “No audit records found” and keep filters intact.
- Snapshot found but trace unavailable (404 on trace or missing `ruleTraceId`):
  - Show snapshot section.
  - Show “Trace unavailable” with reason if provided (generic otherwise).
  - Do not attempt to infer trace from payload.

## 12. Acceptance Criteria

### Scenario 1: Search audit logs with required guardrails
**Given** a user with `audit:log:view` is authenticated  
**When** the user opens the Audit Search screen  
**Then** the screen requires `fromUtc` and `toUtc` inputs  
**And** the screen indicates that at least one additional filter is required beyond the date range  
**And** the screen prevents selecting a date range greater than 90 days

### Scenario 2: Successful audit search by SKU within a valid date range
**Given** a user with `audit:log:view` is on the Audit Search screen  
**And** the user enters `fromUtc` and `toUtc` within 90 days  
**And** the user enters a `sku` filter  
**When** the user submits the search  
**Then** the UI calls `GET /audit/logs/search` with `fromUtc`, `toUtc`, and `sku`  
**And** the UI displays a paginated list of results sorted by `occurredAt` descending by default

### Scenario 3: Prevent unbounded audit searches (date range only)
**Given** a user with `audit:log:view` is on the Audit Search screen  
**When** the user enters only `fromUtc` and `toUtc` and no other indexed filter  
**And** submits the search  
**Then** the UI blocks submission  
**And** displays a message requiring at least one indexed filter (e.g., productId/sku/partNumber/eventType/actorId/aggregateId/correlationId/reasonCode/workOrderId/etc.)

### Scenario 4: Cross-location search requires permission and explicit locations
**Given** a user with `audit:log:view` but without `audit:scope:cross-location` is on the Audit Search screen  
**Then** the UI does not show multi-location selection controls

**Given** a user with `audit:log:view` and `audit:scope:cross-location` is on the Audit Search screen  
**When** the user attempts to search without selecting any `locationIds[]`  
**Then** the UI blocks submission and requires at least one location selection  
**When** the user selects one or more locations and submits  
**Then** the UI calls `GET /audit/logs/search` including `locationIds[]`

### Scenario 5: View audit record detail (normalized fields)
**Given** a user with `audit:log:view-detail` navigates to Audit Detail with a valid `eventId`  
**When** the screen loads  
**Then** the UI calls `GET /audit/logs/detail?eventId=<eventId>`  
**And** displays the returned audit fields as read-only (eventId, eventType, occurredAt, locationId, actor, aggregateType/aggregateId, reasonCode, correlationId if present)

### Scenario 6: Raw payload is permission-gated and safely rendered
**Given** a user without `audit:payload:view` opens Audit Detail for an event that has `rawPayload`  
**Then** the UI does not display the raw payload section

**Given** a user with `audit:payload:view` opens Audit Detail for an event that has `rawPayload`  
**Then** the UI displays raw payload only as escaped text (no HTML execution)  
**And** provides a copy action

### Scenario 7: Drill estimate line → pricing snapshot → rule trace
**Given** a user with `audit:pricing-snapshot:view` is viewing an estimate line that contains `snapshotId`  
**When** the user selects “View Pricing Trace”  
**Then** the UI navigates to Pricing Snapshot Detail with `snapshotId`  
**And** calls `GET /audit/pricing/snapshot?snapshotId=<snapshotId>`  
**And** displays snapshot fields read-only

**Given** the snapshot response includes `ruleTraceId` and the user has `audit:pricing-trace:view`  
**When** the trace section loads  
**Then** the UI calls `GET /audit/pricing/trace?ruleTraceId=<ruleTraceId>`  
**And** displays evaluation steps with `ruleId`, `status`, and `stepIndex`  
**And** supports loading additional pages when `nextPageToken` is returned or shows “Trace truncated” when `isTruncated=true`

### Scenario 8: Not found and forbidden handling does not leak data
**Given** a user navigates to Audit Detail with a non-existent `eventId`  
**When** the backend returns 404  
**Then** the UI shows a Not Found state

**Given** a user without `audit:log:view-detail` navigates to Audit Detail with any `eventId`  
**When** the backend returns 403  
**Then** the UI shows an Access Denied state  
**And** does not indicate whether the event exists
