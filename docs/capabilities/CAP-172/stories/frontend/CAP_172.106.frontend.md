## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Security: Admin UI to Manage Roles & Permissions (RBAC) + RBAC Audit View

### Primary Persona
System Administrator (Admin)

**Persona Metadata**
- `primary_persona`: `System Administrator (Admin)`
- `canonical_persona`: `System Administrator`
- `persona_family`: `System Administration`
- `actor_type`: `human`

### Business Value
Provide a secure, auditable, least-privilege way to configure who can access sensitive capabilities (including product/pricing actions) by managing Roles and Role→Permission grants, with deny-by-default enforcement and traceable audit history.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Admin  
- **I want** a frontend interface to view and manage Roles and Role→Permission grants, and to view security-owned RBAC audit entries  
- **So that** access is explicitly granted (deny-by-default), changes are controlled, and RBAC mutations are auditable.

### In-scope
- Moqui-based admin screens to:
  - List/view **Permissions** (read-only registry; searchable/filterable)
  - List/create/update **Roles** (update limited to non-identifier metadata)
  - Grant/revoke **Permissions** to/from a **Role** (RolePermission management; idempotent)
  - View **security-owned audit history** related to RBAC mutations (read-only, curated fields)
- Frontend route/action gating based on backend authorization outcomes (401/403) and explicit permission keys (see Business Rules).
- Consistent error handling using the canonical error envelope (code/message/correlationId/fieldErrors).

### Out-of-scope
- Defining the product/pricing permission matrix content (which roles should have which permissions).
- Creating/editing permissions in UI (permission registry is code-first and UI read-only).
- Assigning roles to users/principals (PrincipalRole UI deferred in v1).
- Location-scoped RBAC/ABAC overrides (explicitly out-of-scope for v1; tenant-global RBAC only).
- Authentication/IdP integration details (assumed external).

---

## 3. Actors & Stakeholders
- **Admin (Primary):** Configures roles and role-permission grants; reviews RBAC audit.
- **Security Service (System of Record):** Owns Role, Permission registry (read-only), RolePermission grants, and security-owned audit entries.
- **Product/Pricing domain owners (Stakeholders):** Register permission keys in code-first manifests; consume RBAC enforcement in their domains.
- **Compliance/Audit stakeholders:** Require visibility into RBAC changes and correlation IDs for traceability.

## 6. Functional Behavior

### Triggers
- Screen load triggers list-fetch calls (roles, permissions, audit).
- Form submit triggers create/update/grant/revoke calls.
- Manual refresh triggers re-fetch (no automatic polling required for these screens).

### UI actions

**Roles list**
- Search/filter by roleName (client-side filter allowed only after server paging; primary filter should be server-side via `search`)
- Pagination controls
- “Create Role” action (only if authorized)
- Open Role Detail

**Role detail**
- View role metadata (roleId, roleName, description)
- Edit description (only if authorized)
- View granted permissions (paged if needed)
- Grant permission(s) to role:
  - Minimum: single grant action
  - Optional: multi-select grant in one submit if backend supports replace-set or bulk grant; otherwise loop single grants with clear progress and per-item error reporting
- Revoke permission from role (single revoke per action)

**Permissions list**
- Search by permissionKey substring
- Filter by domain prefix (derived from permissionKey or provided by backend)
- Read-only display (no create/edit/delete)

**Security audit view**
- Filter by date range (required)
- Optional filters if supported by backend: eventType, actorId, roleId, permissionKey, outcome
- View curated audit fields; optional “Copy correlationId”

### State changes
- Backend authoritative changes:
  - Role created
  - Role description updated
  - RolePermission grant created (idempotent)
  - RolePermission revoked (idempotent)
- UI state:
  - In-flight request states per action
  - Local form dirty state for description edit

### Service interactions
All calls must handle:
- `400` validation errors (with `fieldErrors[]` when applicable)
- `401` unauthenticated
- `403` forbidden (deny-by-default)
- `404` not found (role/permission missing or cross-tenant access)
- `409` conflict (role name taken; email mismatch not applicable here; other conflicts as defined)
- All error responses include `correlationId` (DECISION-INVENTORY-015)

## 7. Business Rules (Translated to UI Behavior)

### Validation
**Role create**
- `roleName` required
- UI should trim input before submit (presentation only); backend enforces normalization uniqueness:
  - normalized = trim + collapse internal whitespace + lowercase (DECISION-INVENTORY-003)
- On `409 ROLE_NAME_TAKEN`, show message: “Role name already exists.”

**Role update**
- `roleName` is immutable after create (DECISION-INVENTORY-004)
- UI must not present roleName as editable; only `description` editable
- If backend returns `ROLE_NAME_IMMUTABLE` (or equivalent) due to unexpected payload, show non-field error and keep user on page

**Permissions**
- Permission registry is code-first; UI is read-only (DECISION-INVENTORY-006)
- Permission keys are immutable and must match `domain:resource:action` snake_case; UI does not validate beyond basic display/search (DECISION-INVENTORY-002)

**Grant/revoke**
- Grants/revokes must be idempotent (DECISION-INVENTORY-005):
  - Re-granting an already granted permission should succeed as no-op (preferred) or return deterministic conflict; UI must treat either as success for end state “granted”
  - Revoking a non-existent grant should succeed as no-op (preferred) or return deterministic not-found; UI must treat either as end state “not granted”
- No location scope fields are accepted or displayed (DECISION-INVENTORY-008)

### Enable/disable rules
- Disable submit controls while request is in-flight
- Disable “Grant” if no permission selected
- Hide or disable mutation controls based on authorization:
  - If user lacks create/update/grant/revoke permissions, do not show those actions
  - If permissions are unknown at route-render time, render conservatively and rely on backend 403 to finalize UI state (deny-by-default UX)

### Visibility rules
- Route-level access:
  - If initial load returns 401/403, show Access Denied state (do not leak data)
- Audit tab/screen:
  - Visible only if `security:audit_entry:view` is granted; otherwise hide from nav or show “Not authorized” if directly navigated

### Error messaging expectations
- Use canonical error envelope (DECISION-INVENTORY-015):
  - Show banner with `message`
  - Map `fieldErrors[]` to inputs when `field` matches known form fields
  - Always display `correlationId` in an expandable “Details” section for support

## 8. Data Requirements

### Entities involved (conceptual)
- `Role` (security-owned)
- `Permission` (security-owned registry; read-only)
- `RolePermission` (security-owned)
- `AuditEntry` (security-owned for RBAC/provisioning mutations; this story uses RBAC subset)

### Fields (type, required, defaults)

**Role**
- `roleId` (UUID/string; read-only)
- `roleName` (string; required on create; immutable thereafter)
- `description` (string; optional; editable)
- `createdAt` (datetime; read-only; optional if provided)
- `updatedAt` (datetime; read-only; optional if provided)

**Permission**
- `permissionKey` (string; read-only; immutable)
- `description` (string; read-only; optional)
- `serviceName` (string; read-only; optional; if backend provides provenance)
- `deprecated` (boolean; read-only; optional)

**RolePermission**
- `roleId` (UUID/string; read-only)
- `permissionKey` (string; read-only)
- `grantedAt` (datetime; read-only; optional)
- `grantedBy` (string/principalId; read-only; optional)

**AuditEntry (curated view)**
- `auditEntryId` (UUID/string; read-only)
- `timestamp` (datetime; read-only)
- `actorId` (string; read-only; principal identifier)
- `eventType` (string; read-only; RBAC mutation types)
- `outcome` (string; read-only; e.g., SUCCESS|DENY|FAILURE if provided)
- `target` (object; read-only; should include roleId and/or permissionKey when applicable)
- `detailsSummary` (string; read-only; curated summary)
- `correlationId` (string; read-only)
- Raw payload is not displayed in v1 (redaction/gating per DECISION-INVENTORY-013)

### Read-only vs editable by state/role
- Editable only when authorized by permission keys (see Service Contracts / gating)
- Permissions are always read-only
- Audit entries are always read-only

### Derived/calculated fields
- `permissionDomain` derived client-side as substring before first `:` in `permissionKey` for filtering/display when backend does not provide a domain field (UI-only convenience; does not affect authorization)

## 9. Service Contracts (Frontend Perspective)

All endpoints are under `/api/v1/security/*` unless noted. Pagination uses `pageIndex`, `pageSize`, `totalCount` (DECISION-INVENTORY-015).

### Load/view calls

**List roles**
- `GET /api/v1/security/roles?pageIndex=&pageSize=&search=`
- Response:
  - `{ items: Role[], pageIndex, pageSize, totalCount }`

**Get role**
- `GET /api/v1/security/roles/{roleId}`
- Response: `Role`

**List permissions (registry; read-only)**
- `GET /api/v1/security/permissions?pageIndex=&pageSize=&search=&domain=`
  - `domain` filter is optional; if unsupported, frontend uses derived domain filtering client-side after search results are returned (but must still page server-side)
- Response:
  - `{ items: Permission[], pageIndex, pageSize, totalCount }`

**List role permissions (grants)**
- `GET /api/v1/security/roles/{roleId}/permissions?pageIndex=&pageSize=&search=`
- Response:
  - `{ items: RolePermission[], pageIndex, pageSize, totalCount }`

**List security audit entries (RBAC-focused)**
- `GET /api/v1/security/audit-entries?pageIndex=&pageSize=&from=&to=&eventType=&actorId=&roleId=&permissionKey=`
- Response:
  - `{ items: AuditEntry[], pageIndex, pageSize, totalCount }`

### Create/update calls

**Create role**
- `POST /api/v1/security/roles`
- Request: `{ roleName: string, description?: string }`
- Success response: `Role`
- Errors:
  - `409 ROLE_NAME_TAKEN` when normalized name collides (DECISION-INVENTORY-003)

**Update role (description only)**
- `PUT /api/v1/security/roles/{roleId}`
- Request: `{ description?: string }`
- Success response: `Role`
- Errors:
  - `400 ROLE_NAME_IMMUTABLE` (or equivalent) if roleName included/changed (DECISION-INVENTORY-004)

### Submit/transition calls (grant/revoke)

**Grant permission to role (incremental)**
- `POST /api/v1/security/roles/{roleId}/permissions`
- Request: `{ permissionKey: string }`
- Success response: `{ roleId, permissionKey, grantedAt?, correlationId? }` or `RolePermission`
- Idempotency: re-grant is no-op success (preferred) (DECISION-INVENTORY-005)

**Revoke permission from role**
- `DELETE /api/v1/security/roles/{roleId}/permissions/{permissionKey}`
- Success response: `204 No Content` (preferred) or `{ revoked: true }`
- Idempotency: revoke missing grant is no-op success (preferred) (DECISION-INVENTORY-005)

**Optional (if backend supports replace-set semantics)**
- `PUT /api/v1/security/roles/{roleId}/permissions`
- Request: `{ permissionKeys: string[] }`
- Behavior: replace-set “set exactly these permissions” (DECISION-INVENTORY-005)
- If not implemented, UI must not expose “Replace all” bulk action.

### Error handling expectations
All non-2xx responses return canonical envelope (DECISION-INVENTORY-015):
```json
{
  "code": "STRING_CODE",
  "message": "Human readable",
  "correlationId": "uuid-or-string",
  "fieldErrors": [{"field":"roleName","message":"required"}],
  "details": {}
}
```
Frontend mapping:
- `400 VALIDATION_FAILED`: show banner + field errors
- `401 UNAUTHENTICATED`: route to login/session-expired flow
- `403 FORBIDDEN`: show Access Denied; hide/disable mutation controls
- `404 NOT_FOUND`: show not found; offer navigation back to list
- `409 ROLE_NAME_TAKEN`: show roleName field error
- Any other `code`: show banner with `message` and correlationId

## 10. State Model & Transitions

### Allowed states
UI interaction states (not domain states):
- `loading`
- `ready:view`
- `ready:edit-description`
- `submitting:create-role`
- `submitting:update-role`
- `submitting:grant`
- `submitting:revoke`
- `error` (recoverable; user can retry)

### Role-based transitions
Permission keys gate actions (DECISION-INVENTORY-002):
- View roles: `security:role:view`
- View permissions: `security:permission:view`
- Create role: `security:role:create`
- Update role: `security:role:update`
- Delete role: `security:role:delete` (not used unless backend supports and product decides to include; default UI excludes delete)
- Grant/revoke:
  - `security:role_permission:grant`
  - `security:role_permission:revoke`
  - Optional replace-set: `security:role_permission:replace`
- View audit: `security:audit_entry:view`
- Export audit: `security:audit_entry:export` (export UI out-of-scope unless explicitly added)

### UI behavior per state
- `loading`: show skeleton/spinner; do not render stale data
- `ready:view`: show data; show only authorized actions
- `ready:edit-description`: enable description input; show save/cancel
- `submitting:*`: disable relevant controls; show progress; on success refresh affected lists
- `error`: show banner with correlationId; keep user on same screen with retry

## 11. Alternate / Error Flows

### Validation failures
- Create role with empty roleName:
  - Backend returns `400 VALIDATION_FAILED` with `fieldErrors[roleName]`
  - UI highlights roleName and shows message
- Create role with normalized duplicate:
  - Backend returns `409 ROLE_NAME_TAKEN`
  - UI shows roleName field error “Role name already exists”
- Attempt to update roleName (should be impossible in UI):
  - If occurs (e.g., tampered request), backend returns immutable error; UI shows banner and refreshes role

### Concurrency conflicts
- If backend uses optimistic locking and returns `409` on update:
  - UI shows “Role was updated by another user. Reload required.” with Reload action
  - On reload, discard local edits

### Unauthorized access
- User navigates directly to `/admin/security/*` without permissions:
  - If initial API call returns `403`, show Access Denied state and do not render data
- Partial authorization:
  - User can view roles but cannot grant/revoke:
    - Role detail shows granted permissions list read-only; grant/revoke controls hidden/disabled
  - User can view roles but cannot view audit:
    - Audit menu item hidden; direct navigation shows Not Authorized

### Empty states
- No roles exist:
  - Show empty state; show “Create Role” only if `security:role:create`
- No permissions registered / no results:
  - Show “No permissions found” with suggestion to adjust search/filter (do not instruct how to register permissions beyond “Permissions are registered by deployed services.”)
- Role has no granted permissions:
  - Show empty granted list; show grant control only if authorized

## 12. Acceptance Criteria

### Scenario 1: View permissions filtered by domain
**Given** I am authenticated and have `security:permission:view`  
**When** I open the Permissions screen and filter to domain `pricing`  
**Then** I see only permissions whose `permissionKey` begins with `pricing:`  
**And** I cannot create or edit permissions from the UI.

### Scenario 2: Create a new role
**Given** I am authenticated and have `security:role:create`  
**When** I submit a new role with `roleName="Pricing Analyst"` and an optional description  
**Then** the role is created  
**And** the response includes a `roleId`  
**And** I am routed to Role Detail for that `roleId`.

### Scenario 3: Prevent duplicate role names using normalization
**Given** a role exists with `roleName="manager"` in my tenant  
**And** I have `security:role:create`  
**When** I try to create a role with `roleName="  MANAGER  "`  
**Then** the API returns `409` with `code="ROLE_NAME_TAKEN"`  
**And** the UI shows a roleName field error “Role name already exists”  
**And** the UI displays the returned `correlationId`.

### Scenario 4: Update role description only (roleName immutable)
**Given** a role exists  
**And** I have `security:role:update`  
**When** I update the role description and save  
**Then** the role description is updated  
**And** the roleName remains unchanged  
**And** the UI does not allow editing roleName.

### Scenario 5: Grant a permission to a role (idempotent)
**Given** I have `security:role_permission:grant`  
**And** a role exists  
**And** a permission exists with `permissionKey="pricing:price_book:edit"`  
**When** I grant `pricing:price_book:edit` to the role  
**Then** the role’s granted permissions list includes `pricing:price_book:edit` after refresh  
**And** if I repeat the same grant, the end state remains granted and the UI does not show an error (idempotent behavior).

### Scenario 6: Revoke a permission from a role (idempotent)
**Given** I have `security:role_permission:revoke`  
**And** a role has `pricing:price_book:edit` granted  
**When** I revoke `pricing:price_book:edit`  
**Then** the role no longer shows that permission after refresh  
**And** if I repeat the revoke, the end state remains not granted and the UI does not show an error (idempotent behavior).

### Scenario 7: Access denied is deny-by-default
**Given** I am authenticated but do not have `security:role:view`  
**When** I open the Roles screen  
**Then** the UI shows an Access Denied state  
**And** no role data is displayed.

### Scenario 8: View RBAC audit entries (curated fields)
**Given** I have `security:audit_entry:view`  
**When** I open the Security Audit screen and filter by a date range  
**Then** I see audit entries including `timestamp`, `actorId`, `eventType`, `detailsSummary`, and `correlationId`  
**And** I do not see raw/unredacted payload fields.
