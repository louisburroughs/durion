## Business Value
Enable managers to identify attendance vs productive job-time discrepancies by technician/day/location, so they can investigate gaps, overhead, and anomalies using a consistent threshold policy returned by People.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Manager  
- **I want** a report that compares technicians’ total attendance time (clocked time) to total job time (approved productive labor) by day and location  
- **So that** I can quickly find and investigate significant discrepancies.

## In-scope
- A Moqui screen (Vue/Quasar) to run and view the report.
- Filters:
  - `startDate`, `endDate` (local dates)
  - `timezone` (IANA TZ)
  - optional `locationId`
  - optional `technicianIds` (multi-select)
  - `flaggedOnly` (boolean)
- Tabular results at granularity: technician + location + local day.
- Exception flagging is displayed using backend-provided `isFlagged` and `thresholdApplied` (UI must not compute policy).
- Empty/error states and proper handling of upstream failures (People report may fail due to WorkExec dependency).

## Out-of-scope
- Configuring threshold policies (TimekeepingPolicy CRUD).
- Implementing backend report logic or WorkExec integration.
- Row drill-down into underlying time entries, job labor lines, or reconciliation details (future enhancement).
- Export/CSV (unless already a project standard elsewhere; not required here).

---

# 3. Actors & Stakeholders
- **Manager (primary user):** runs report for permitted locations/technicians; investigates flagged rows.
- **Technician (subject):** appears in results; no direct interaction.
- **People domain service (SoR for attendance + threshold policy + report aggregation):** serves report endpoint and enforces authorization.

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Required:
  - `startDate` (YYYY-MM-DD)
  - `endDate` (YYYY-MM-DD)
  - `timezone` (IANA TZ string)
- Validate:
  - `startDate <= endDate`; otherwise block submit with inline error.
- `technicianIds`:
  - Optional list; when present, encode as repeated query params: `technicianId=<id>&technicianId=<id>` (Decision ID: DECISION-PEOPLE-020).
  - Compatibility: backend *may* accept comma-separated, but UI must use repeated params for determinism (Decision ID: DECISION-PEOPLE-020).
- Date range maximum:
  - UI does not enforce a hard maximum unless backend returns a clear range violation error; UI surfaces server message (Decision ID: DECISION-PEOPLE-020).

## Enable/disable rules
- Disable **Run Report** while loading.
- Filters remain editable while results are shown; changing filters does not auto-run until user clicks Run (unless query-param auto-run is an established pattern).

## Visibility rules
- Results section visible after first successful run; prior results remain visible across subsequent runs/errors.
- Display `thresholdApplied` per row (minutes) alongside discrepancy (hours) to aid interpretation.
- Do not display `tenantId` anywhere (Decision ID: DECISION-PEOPLE-019).

## Error messaging expectations
- 400: show “Invalid request” plus field-level errors when provided (Decision ID: DECISION-PEOPLE-018).
- 403: show “Not authorized for selected scope.”
- 404: show “Report not found” (treat as configuration/deployment issue).
- 409: show “Report data changed; refresh and retry” (if applicable; generally unlikely for reports, but handle per standard schema) (Decision ID: DECISION-PEOPLE-018).
- 5xx/503: show “Report unavailable right now. Try again.”
- If backend returns a recognizable upstream dependency code (example: `WORKEXEC_UNAVAILABLE`), show: “Job time system unavailable; report cannot be generated. Try again later.”

# 11. Alternate / Error Flows

## Validation failures (client-side)
- Missing required fields: show inline validation; do not call API.
- `startDate > endDate`: inline error on date range; do not call API.

## Backend validation failures (400)
- Show error banner.
- If `fieldErrors` present, map to fields and show inline messages without clearing user input.

## Concurrency conflicts (409)
- If 409 occurs:
  - Show conflict banner using `message`.
  - Provide a **Retry** action that re-runs the request with current filters.
  - Do not attempt to auto-resolve; do not clear results.

## Unauthorized access (401/403)
- 401: show “Session expired. Please sign in again.” and route to login if app supports it.
- 403: show “Not authorized for selected scope.” Do not silently remove selected filters.

## Empty states
- No rows returned:
  - Show “No discrepancies found for the selected period/scope.”
  - If `flaggedOnly=true`, show “No flagged discrepancies found for the selected period/scope.”

## Upstream dependency failure (WorkExec issues surfaced by People endpoint)
- If errorCode indicates dependency outage (example `WORKEXEC_UNAVAILABLE`):
  - Show “Job time system unavailable; report cannot be generated. Try again later.”
- Otherwise:
  - Generic 5xx/503 message.

# 12. Acceptance Criteria

## Scenario 1: Run report successfully with required filters
**Given** I am an authenticated Manager  
**And** I can access the Attendance vs Job Time Discrepancy report screen  
**When** I enter a valid `startDate`, `endDate`, and `timezone`  
**And** I click Run Report  
**Then** the UI sends a GET request to `/rest/api/v1/people/reports/attendance-jobtime-discrepancy` with those parameters  
**And** I see a results table with one row per technician+location+day showing attendance hours, job hours, discrepancy hours, threshold applied, and flagged status.

## Scenario 2: Technician multi-select is encoded as repeated query params
**Given** I have selected two technicians with IDs `per_1` and `per_2`  
**When** I run the report  
**Then** the request query string includes `technicianId=per_1` and `technicianId=per_2` as repeated parameters (not a JSON array string)  
**And** the UI renders only the rows returned by the server.  

## Scenario 3: Flagged rows are clearly indicated without recomputing policy
**Given** the report response includes a row with `isFlagged=true` and `thresholdApplied=60`  
**When** the results are displayed  
**Then** the UI clearly marks that row as flagged  
**And** the UI displays `thresholdApplied` from the response  
**And** the UI does not compute or override `isFlagged` based on discrepancy math.

## Scenario 4: Filter to flaggedOnly
**Given** I have selected valid dates and timezone  
**When** I set `flaggedOnly=true` and run the report  
**Then** the UI includes `flaggedOnly=true` in the request  
**And** if zero rows are returned, I see an empty-state message indicating no flagged discrepancies for the selected scope.

## Scenario 5: Client-side validation prevents invalid date ranges
**Given** I am on the report screen  
**When** I set `startDate` later than `endDate`  
**And** I click Run Report  
**Then** the UI prevents the request from being sent  
**And** I see an inline error indicating the start date must be on or before the end date.

## Scenario 6: Unauthorized scope shows explicit error
**Given** I am authenticated but not authorized for a selected location or technician scope  
**When** I run the report for that forbidden scope  
**And** the backend responds with 403  
**Then** the UI shows an authorization error message  
**And** the UI does not silently remove or alter my selected filters.

## Scenario 7: Backend unavailable or WorkExec-related failure bubbles to UI and preserves prior results
**Given** I previously ran the report successfully and results are visible  
**When** I run the report again with valid filters  
**And** the backend responds with 503 or an errorCode indicating job-time dependency is unavailable  
**Then** the UI shows a non-technical error message that the report is unavailable  
**And** the previously visible results remain on screen  
**And** I can retry without reloading the page.
