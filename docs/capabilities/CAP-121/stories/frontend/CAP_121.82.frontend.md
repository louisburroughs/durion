## 1. Story Header

### Title
[FRONTEND] Order: Cancel Order (Order-Orchestrated) with Audit + Void/Refund Outcome Rendering (Moqui + Quasar)

### Primary Persona
Store Manager (and Service Advisor where permitted)

**Persona Metadata**
- `primary_persona`: `Store Manager (and Service Advisor where permitted)`
- `canonical_persona`: `Location Manager`
- `persona_family`: `Location Management`
- `actor_type`: `human`

### Business Value
Enable policy-compliant order cancellation from the POS UI with deterministic outcomes (cancelled, refund-required, failed, in-progress), minimal coupling to downstream systems, and complete, immutable audit visibility for operators and support.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Store Manager (and Service Advisor if authorized),
- **I want** to cancel an order from the Order Detail screen,
- **So that** mistaken orders can be cancelled safely, cancellation is blocked when work is irreversible, payment handling is correctly reflected (void vs refund-required), and every attempt is auditable.

### In-scope
- Cancel action surfaced from an Order Detail context in the Moqui/Quasar frontend.
- Cancellation dialog collecting required inputs (`reason`, optional `comments`) with confirmation.
- Frontend calls **one Order-owned cancellation command service** (no direct UI calls to Payment/Workexec).
- UI handling of canonical cancellation-related order statuses:
  - `CANCELLING`, `CANCELLED`, `CANCELLED_REQUIRES_REFUND`, `CANCELLATION_FAILED`
- Display of latest cancellation audit details (at minimum: `cancellationId`, who/when, reason/comments, payment/work outcome statuses; correlation IDs only when permitted).
- Permission/capability gating for “Cancel Order” (`ORDER_CANCEL` enforced server-side; UI gates via backend-provided capability).
- Deterministic error handling for `400/403/409/500` with stable `errorCode`.

### Out-of-scope
- Executing payment void/refund logic (owned by backend/payment domain).
- Executing work rollback/cancel logic (owned by backend/workexec domain).
- Any refund processing UI beyond “manual refund required” guidance.
- Admin-only “retry cancellation” action (explicitly excluded for v1).
- Building a separate operations dashboard for failed cancellations (UI only renders current state and audit/support identifiers).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- **Order Detail screen** (single launch point for cancellation UI).

### Screens to create/modify
- **Modify** Order Detail screen:
  - Add Cancel action gated by backend capability (e.g., `canCancel`) and UI state.
  - Add a “Cancellation” summary section when cancellation data exists or status is cancellation-related.
- **Add** cancellation dialog (screenlet/modal):
  - Required reason picker
  - Optional comments textarea with character counter (max 2000)
  - Confirmation copy indicating:
    - cancellation may be blocked if work is irreversible
    - settled payments result in “refund required” status (no refund UI here)

### Navigation context
- User remains on Order Detail after submit.
- UI refreshes Order Detail after submit (success or error) to reflect authoritative status.

### User workflows (happy + alternate paths)

#### Happy path: cancellable; cancellation completes to CANCELLED
1. User clicks **Cancel Order**
2. Dialog opens; user selects `reason`, optionally enters `comments`
3. User confirms; submit disables and shows in-flight indicator
4. Cancel service returns `200` with `status=CANCELLED` (or UI reload shows it)
5. UI shows cancellation summary including `cancellationId` and outcome statuses

#### Alternate: payment settled → refund required
- Cancel returns `200` with `status=CANCELLED_REQUIRES_REFUND`
- UI shows prominent “Manual refund required” guidance; no refund action provided

#### Alternate: cancellation blocked by work state
- Cancel returns `400` with `errorCode=WORK_NOT_CANCELLABLE` and user-safe message
- UI shows error; order remains not cancelled after refresh

#### Alternate: cancellation in progress (concurrency)
- Cancel returns `409` with `errorCode=CANCELLATION_IN_PROGRESS`
- UI shows warning and refreshes; status renders as `CANCELLING`

#### Alternate: orchestration failure
- Cancel returns `500` (or `200` with status `CANCELLATION_FAILED`, depending on backend pattern) and/or subsequent refresh shows `CANCELLATION_FAILED`
- UI shows “manual intervention required” guidance and displays available support identifiers (permission-gated)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `reason` is required.
- `comments` optional; max length 2000 characters (client-side + server-side).
- If backend returns field errors, map them to the form fields.

### Enable/disable rules
- Cancel action is shown/enabled only when:
  - backend indicates capability (e.g., `canCancel=true`), AND
  - UI is not currently submitting, AND
  - current status is not one of: `CANCELLING`, `CANCELLED`, `CANCELLED_REQUIRES_REFUND` (if status is already cancellation-related, cancel action is disabled/hidden)
- Submit button disabled while request is in-flight.

### Visibility rules
- Cancellation summary section is visible when:
  - order status is one of the canonical cancellation-related statuses, OR
  - latest cancellation record exists (even if status is already terminal)
- “Manual refund required” guidance is shown when:
  - order status is `CANCELLED_REQUIRES_REFUND` (authoritative), and/or
  - latest cancellation record indicates `paymentVoidStatus=REFUND_REQUIRED`
- “Manual intervention required” guidance is shown when:
  - order status is `CANCELLATION_FAILED`

### Error messaging expectations (deterministic mapping)
- `400`:
  - If `fieldErrors` present → show inline field errors
  - Else show `message` (must be user-safe) in dialog/global banner
- `403` (`errorCode=FORBIDDEN` or equivalent): show “You do not have permission to cancel orders.”
- `409` (`errorCode=CANCELLATION_IN_PROGRESS`): show “Cancellation is already in progress. Refreshing status…” and trigger refresh.
- `500`:
  - show “Cancellation failed; manual intervention required.”
  - show `message` only if backend marks it user-safe (otherwise omit and rely on generic text)
  - if support identifiers are present and permitted, display them in the cancellation summary

## 10. State Model & Transitions

### Allowed states (frontend must render)
Cancellation-related canonical states:
- `CANCELLING`
- `CANCELLED`
- `CANCELLED_REQUIRES_REFUND`
- `CANCELLATION_FAILED`

Non-cancellation states may exist; UI must not break on unknown values.

### Role-based transitions
- Initiate cancellation:
  - Requires backend authorization `ORDER_CANCEL`
  - UI gates via backend capability (`canCancel`) and hides/disables otherwise
- No retry transition in v1 UI for `CANCELLATION_FAILED`.

### UI behavior per state
- `CANCELLING`:
  - Cancel action hidden/disabled
  - Show “Cancellation in progress” and refresh affordance
- `CANCELLED`:
  - Cancel action hidden/disabled
  - Show cancellation summary and outcomes
- `CANCELLED_REQUIRES_REFUND`:
  - Cancel action hidden/disabled
  - Show “Manual refund required” guidance and payment outcome
- `CANCELLATION_FAILED`:
  - Cancel action hidden/disabled
  - Show failure guidance; show support identifiers if permitted

## 11. Alternate / Error Flows

### Validation failures
- Missing reason:
  - client-side blocks submit; show inline error
- Comments too long:
  - client-side blocks submit; show inline error and character counter
- Backend `400`:
  - show `message` and any `details`
  - keep dialog open for correction (unless error indicates non-correctable block like `WORK_NOT_CANCELLABLE`, in which case dialog may remain open but submit stays available only if user changes reason/comments; cancellation will still be blocked—UI should not pretend it can fix work state)

### Concurrency conflicts
- Backend `409`:
  - show warning
  - trigger refresh after short delay and/or provide “Refresh” button
  - do not auto-resubmit

### Unauthorized access
- Backend `403`:
  - show permission error
  - ensure cancel action is hidden/disabled after refresh (since `canCancel` should be false)

### Empty states
- No cancellation record:
  - hide cancellation summary section or show “No cancellation activity” empty state
- Unknown status values:
  - render a safe fallback label (e.g., “Status: <raw>”)
  - do not show cancel action unless `canCancel=true`

## 12. Acceptance Criteria

### Scenario 1: Cancel order successfully → CANCELLED
**Given** I am authenticated and have permission `ORDER_CANCEL`  
**And** the Order Detail response indicates `canCancel=true`  
**When** I open the Cancel Order dialog  
**And** I select a valid cancellation reason  
**And** I submit the cancellation  
**Then** the UI disables the submit action while the request is in-flight  
**And** the UI calls the Order-owned cancel service with `orderId`, `reason`, and `comments`  
**And** the UI refreshes Order Detail after the response  
**And** the UI displays order status `CANCELLED`  
**And** the UI displays `cancellationId` and outcome fields `paymentVoidStatus` and `workRollbackStatus` when provided.

### Scenario 2: Cancel order with settled payment → CANCELLED_REQUIRES_REFUND
**Given** I have permission `ORDER_CANCEL` and `canCancel=true`  
**When** I submit cancellation with a valid reason  
**Then** the UI displays order status `CANCELLED_REQUIRES_REFUND`  
**And** the UI displays guidance that a manual refund is required  
**And** the Cancel action is hidden/disabled after refresh.

### Scenario 3: Cancellation blocked by work state
**Given** I have permission `ORDER_CANCEL` and `canCancel=true`  
**When** I submit cancellation  
**And** the backend responds `400` with `errorCode=WORK_NOT_CANCELLABLE`  
**Then** the UI displays the backend `message`  
**And** if `details.workStatus` is present, the UI displays it as part of the error context  
**And** after refresh the order is not in `CANCELLED` or `CANCELLED_REQUIRES_REFUND`.

### Scenario 4: Cancellation already in progress (409)
**Given** I have permission `ORDER_CANCEL`  
**When** I submit cancellation  
**And** the backend responds `409` with `errorCode=CANCELLATION_IN_PROGRESS`  
**Then** the UI displays a conflict warning  
**And** the UI triggers a refresh of Order Detail  
**And** the UI renders status `CANCELLING` if returned by Order Detail.

### Scenario 5: Orchestration failure → CANCELLATION_FAILED
**Given** I have permission `ORDER_CANCEL` and `canCancel=true`  
**When** I submit cancellation  
**And** the backend responds with a failure (`500` and/or subsequent Order Detail shows `CANCELLATION_FAILED`)  
**Then** the UI displays “manual intervention required” guidance  
**And** after refresh the UI renders order status `CANCELLATION_FAILED`  
**And** the UI displays `cancellationId` if available  
**And** correlation IDs are displayed only if present in the response (support/admin view).

### Scenario 6: Permission denied (403)
**Given** I am authenticated but do not have permission `ORDER_CANCEL`  
**When** I view Order Detail  
**Then** the UI does not show an enabled Cancel Order action (because `canCancel=false` or capability absent)  
**And** if I attempt cancellation (e.g., via direct request), the backend returns `403`  
**And** the UI displays a permission error without exposing internal details.

### Scenario 7: Idempotent repeat cancel on already-cancelled order
**Given** an order is already in status `CANCELLED` or `CANCELLED_REQUIRES_REFUND`  
**When** a cancellation request is submitted again  
**Then** the backend responds `200` without creating new side effects  
**And** the UI refreshes and continues to display the existing cancellation summary  
**And** the UI does not show a retry/cancel action.
