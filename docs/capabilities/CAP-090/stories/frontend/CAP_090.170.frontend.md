## 1. Story Header

**Title:** [FRONTEND] [STORY] CRM Contacts: Manage Multiple Contact Points (Email/Phone) with Primary per Kind

**Primary Persona:** CSR (Customer Service Representative)

**Persona Metadata**
- `primary_persona`: `CSR (Customer Service Representative)`
- `canonical_persona`: `Customer Support Associate`
- `persona_family`: `Customer Support Associate`
- `actor_type`: `human`
**Business Value:** Enables reliable customer communication by storing multiple labeled emails/phone numbers and selecting a primary per kind for downstream usage (e.g., approvals and invoice delivery display).

---

## 2. Story Intent

**As a** CSR,  
**I want** to add, edit, remove, and mark primary phone numbers and email addresses for a customer party,  
**So that** I can contact them using the correct method and downstream systems can display the right contact details.

### In-scope
- View a customer’s existing contact points for a **Party** (`partyId`) with:
  - kinds: `EMAIL`, `PHONE`
  - optional label tags: `WORK`, `HOME`, `MOBILE`, `OTHER`
  - primary indicator **per kind** (at most one primary `EMAIL` and one primary `PHONE` per party)
- Add a new contact point (kind + value + optional label + primary flag).
- Edit an existing contact point (value, label, primary flag).
- Remove an existing contact point.
- Enforce “single primary per kind” behavior in UI (and reflect backend enforcement).
- Client-side validation mirroring CRM rules where defined (non-authoritative; backend remains source of truth).

### Out-of-scope
- Customer deduplication/merge, golden record rules, uniqueness policy beyond what backend enforces.
- Customer hierarchy/relationships management.
- Communication consent/preferences (marketing consent, contactability).
- Workorder Execution UI changes (consumer behavior only referenced).
- Bulk import/export of contact points.

---

## 3. Actors & Stakeholders

- **CSR (Primary Actor):** Manages contact points on a customer record.
- **Customer Party (Subject):** Person or organization/account represented by `partyId`.
- **CRM Domain Services (System of Record):** Authoritative validation, persistence, and “single primary per kind” enforcement.
- **Downstream Consumers (e.g., Workexec/Billing):** Read-only consumption of primary contact points via CRM snapshot/read models (not part of this UI story).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From **Customer/Party Detail** screen for a given `partyId`, via a navigation item/tab: **“Contact Points”**.

### Screens to create/modify
1. **Modify existing Party/Customer detail screen** to include a subscreen for contact points.
2. **Create/modify subscreen**: `ContactPoints.xml` (exact path must follow repo conventions; see Open Questions removed—resolved below).

**Moqui-oriented screen behavior requirements**
- Screen accepts `partyId` as a required parameter.
- Screen renders two lists/sections: `EMAIL` and `PHONE`.
- Each list supports actions (if authorized): Add, Edit, Delete, and “Make Primary”.

### Navigation context
- Breadcrumb: Customer Search → Customer Detail → Contact Points.
- Header shows minimal party context (display name + `partyId`), avoiding PII beyond what is already displayed on the customer detail screen.

### User workflows (happy + alternate paths)

**Happy path: Add a new contact point**
1. CSR navigates to Contact Points for `partyId`.
2. CSR selects “Add Email” or “Add Phone”.
3. CSR enters `value`, optional `label`, optional `extension` (phone only), and optionally sets as primary.
4. CSR saves.
5. UI refreshes list(s) from server to reflect canonical state and any primary auto-demotion.

**Alternate path: Change primary**
- CSR uses “Make Primary” on a non-primary contact point.
- UI shows a confirmation note: “Setting this as primary will remove primary from the current primary <kind> contact.”
- On success, UI refreshes and shows only one primary for that kind.

**Alternate path: Edit**
- CSR edits `value`, `label`, `extension` (phone only), and `isPrimary`.
- `kind` is not editable (see Business Rules).

**Alternate path: Delete**
- CSR deletes a contact point after confirmation.
- If the deleted contact point was primary, no auto-promotion is assumed; UI simply reflects server state after refresh.

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side, mirrors CRM decisions where defined; backend authoritative)
**Common**
- `partyId` required (UUID).
- `kind` required; enum: `EMAIL`, `PHONE`.
- `value` required (string).
- `label` optional; enum: `WORK`, `HOME`, `MOBILE`, `OTHER`.
- `isPrimary` boolean; default `false`.

**Email**
- Basic email format validation (must contain `@` and a domain portion).
- Error message: `Invalid email format`.

**Phone** (DECISION-INVENTORY-003)
- Accept flexible input (spaces, dashes, parentheses) but validate after normalization:
  - Normalize to digits-only (strip non-digits) for validation.
  - Valid if normalized digit count is **10–15**.
- Support optional `extension` as a separate field (string); extension is not included in digit-count validation.
- Error message: `Invalid phone number (must be 10–15 digits)`.

### Enable/disable rules
- Save disabled until required fields are present and pass client-side validation.
- While saving, disable inputs and prevent duplicate submits.

### Visibility rules
- Show primary indicator per contact point.
- Group by kind (`EMAIL`, `PHONE`).
- `kind` is shown but not editable on existing contact points.

### Error messaging expectations
- Backend field errors map to inline field messages when possible.
- Non-field errors show a form banner.
- Do not render backend-provided strings as HTML (treat as plain text).

**Decision rationale**
- Contact point kind immutability is required (DECISION-INVENTORY-003): changing kind must be delete + recreate; UI must not offer kind editing.

## 9. Service Contracts (Frontend Perspective)

> Moqui service names/routes are implementation details; the UI requires the following capabilities and payload shapes. Backend must enforce RBAC and redaction policies; UI must handle 403/400/409 deterministically.

### Load/view calls

**`crm.contactPoint.list`** (capability)
- Input:
  - `partyId` (UUID, required)
- Output:
  - `items: ContactPoint[]`
- Ordering:
  - UI sorts by `kind`, then `isPrimary desc`, then `updatedAt desc` (if present) else stable by `contactPointId`.
  - Backend may return any order; UI must not rely on backend ordering.

### Create/update calls

**`crm.contactPoint.create`** (capability)
- Input:
  - `partyId` (UUID, required)
  - `kind` (`EMAIL|PHONE`, required)
  - `value` (string, required)
  - `label` (`WORK|HOME|MOBILE|OTHER`, optional)
  - `extension` (string, optional; phone only)
  - `isPrimary` (boolean, optional; default false)
- Success:
  - Returns created `ContactPoint` DTO (including `contactPointId`)
- Errors:
  - `400` with `errorCode`, `message`, optional `fieldErrors`
  - `403` forbidden
  - `409` conflict for duplicates if enforced by backend (UI must handle if returned)

**`crm.contactPoint.update`** (capability)
- Input:
  - `contactPointId` (UUID, required)
  - `value` (string, required)
  - `label` (optional)
  - `extension` (optional; phone only)
  - `isPrimary` (boolean, optional)
- Constraints:
  - `kind` is not accepted/updated (immutable) (DECISION-INVENTORY-003)
- Success:
  - Returns updated `ContactPoint` DTO
- Side-effect:
  - If `isPrimary=true`, backend atomically demotes prior primary of same kind for the same party (DECISION-INVENTORY-002).

### Delete calls

**`crm.contactPoint.delete`** (capability)
- Input:
  - `contactPointId` (UUID, required)
- Success:
  - `204` or `{ success:true }`
- Notes:
  - If deleting primary: allowed; UI does not assume auto-promotion.

### Error handling expectations
- Standard error payload shape expected:
  - `errorCode` (string)
  - `message` (string)
  - `fieldErrors` (object map fieldName → message) when applicable
- UI must:
  - Preserve user input on validation errors
  - Re-enable controls after any error
  - Avoid logging PII (`value`, phone digits, email) in client logs/telemetry

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Email invalid: block save; inline error on `value`.
- Phone invalid after normalization (10–15 digits): block save; inline error on `value`.
- Missing required fields: save disabled; show required indicators.

### Backend validation failures (400)
- Render `fieldErrors` inline.
- Render `message` as banner if present.
- Do not clear form.

### Duplicate contact point (409)
- Show banner: `This contact point already exists for this customer.`
- Refresh list after dismissal only if backend indicates state may have changed; otherwise keep current list.

### Concurrency conflicts
- If backend returns `409 CONFLICT` for stale update (not guaranteed for ContactPoint): show `This contact point was updated by someone else. Refresh and try again.` and refresh list.

### Unauthorized access (403)
- On load: show access denied screen; do not render any contact point data.
- On mutation: show `Not authorized to modify contact points.` and keep user on screen; refresh list to ensure canonical state.

### Empty states
- If no emails: show `No email addresses on file.`
- If no phones: show `No phone numbers on file.`
- If authorized to manage: show Add action(s) in empty state.

## 12. Acceptance Criteria

### Scenario 1: View contact points
**Given** I am an authenticated user with permission to view contact points for a party  
**And** a party exists with 1 email and 1 phone contact point  
**When** I open the party’s Contact Points screen with that `partyId`  
**Then** I see the email and phone displayed with their labels (if any) and primary indicators  
**And** at most one primary is shown for EMAIL and at most one primary is shown for PHONE

### Scenario 2: Add a non-primary phone contact point
**Given** I am an authorized CSR with manage permission  
**And** I am viewing a party’s Contact Points  
**When** I add a new PHONE contact point with label MOBILE, value "555-123-4567", isPrimary=false  
**Then** the new contact point appears in the PHONE list after save  
**And** the existing primary PHONE contact point (if any) remains primary

### Scenario 3: Add an email as primary when another primary exists (auto-demotion)
**Given** I am an authorized CSR with manage permission  
**And** the party has an existing primary EMAIL contact point "old@ex.com"  
**When** I add a new EMAIL contact point "new@ex.com" with isPrimary=true  
**Then** "new@ex.com" is shown as primary after save  
**And** "old@ex.com" is shown as not primary after save  
**And** there is only one primary EMAIL contact point displayed

### Scenario 4: Make Primary action demotes prior primary
**Given** I am an authorized CSR with manage permission  
**And** the party has two PHONE contact points where Phone A is primary and Phone B is not  
**When** I click “Make Primary” on Phone B and confirm  
**Then** Phone B is shown as primary after save  
**And** Phone A is shown as not primary after save  
**And** there is only one primary PHONE contact point displayed

### Scenario 5: Edit contact point value and label
**Given** I am an authorized CSR with manage permission  
**And** the party has an EMAIL contact point with label WORK and value "a@b.com"  
**When** I edit that contact point to label HOME and value "c@d.com" and save  
**Then** the list shows the updated label and value after save

### Scenario 6: Kind is immutable on edit
**Given** I am an authorized CSR with manage permission  
**And** the party has an EMAIL contact point  
**When** I open the edit form for that contact point  
**Then** I cannot change the contact point kind  
**And** the UI does not send `kind` in the update request payload

### Scenario 7: Client-side invalid phone is blocked (10–15 digits rule)
**Given** I am an authorized CSR with manage permission  
**When** I attempt to add a PHONE contact point with value "12-34"  
**Then** the Save action is blocked  
**And** I see an error message `Invalid phone number (must be 10–15 digits)` on the value field

### Scenario 8: Backend rejects duplicate contact point
**Given** I am an authorized CSR with manage permission  
**And** the party already has an EMAIL contact point with value "a@b.com"  
**When** I attempt to add another EMAIL contact point with value "a@b.com"  
**Then** the save fails with a conflict/validation error  
**And** I see an error message indicating the contact point already exists  
**And** no duplicate is added to the list

### Scenario 9: View-only user cannot mutate
**Given** I am authenticated and can view contact points but do not have manage permission  
**When** I open the Contact Points screen  
**Then** I can view contact points  
**And** I do not see Add/Edit/Delete/Make Primary actions  
**When** a mutation request is attempted and the backend returns 403  
**Then** the UI shows `Not authorized to modify contact points.`  
**And** no changes occur in the list
