## Issue Body

## 1. Story Header

**Title:** [FRONTEND] Pricing: Maintain MSRP per Product with Effective Dates

**Primary Persona:** Pricing Manager

**Business Value:** Maintain auditable, effective-dated MSRP records per product so downstream pricing calculations, reporting, and compliance can reliably reference the correct MSRP for a given date.

---

## 2. Story Intent

### As a / I want / So that
**As a** Pricing Manager  
**I want** to create, update, and view MSRP records for a product with effective start/end timestamps  
**So that** the system has a single authoritative MSRP per product at any point in time, with clear history and validation against overlaps.

### In-scope
- Moqui UI screens to:
  - Search/select a product context for MSRP maintenance (Inventory-owned lookup)
  - List MSRP records for a product (effective-dated timeline)
  - Create a new MSRP record
  - Edit an existing MSRP record (subject to historical immutability + permissions)
  - View an MSRP record (read-only)
  - View audit/history entries for MSRP admin changes (standard pricing admin audit contract)
- Client-side validation + server-side validation surfacing for:
  - Required fields, date/time logic, positive amount, money shape
  - Overlapping effective ranges conflict
  - Product existence validation failures
  - Permission/authorization failures
- Navigation, transitions, and confirmation/error handling patterns consistent with Moqui frontend conventions

### Out-of-scope
- Defining/altering pricing formulas, taxes, rounding policies, discount precedence (Pricing backend-owned)
- Product master data management (Inventory domain)
- Bulk import/export of MSRPs
- Approval workflows for MSRP changes
- Promotion management, price books, location overrides, restriction rules

---

## 3. Actors & Stakeholders
- **Pricing Manager (primary user):** Maintains MSRP records.
- **Auditor (stakeholder):** Reviews change history and effective-dated records.
- **Pricing Engine / Downstream consumers (system):** Consume active MSRP by product/as-of timestamp (UI does not compute).
- **Inventory domain (external dependency):** System of record for products; MSRP references `productId` owned elsewhere.

---

## 4. Preconditions & Dependencies
- User is authenticated.
- User has permissions:
  - View MSRP admin UI: `pricing:msrp:view` (if backend does not support view/manage split, UI must degrade to manage-only gating).
  - Manage MSRP: `pricing:msrp:manage`
  - Manage historical MSRP edits (past-effective): `pricing:msrp:manage:historical` (DECISION-PRICING-018).
- Inventory product lookup exists and is used for product selection (DECISION-PRICING-017):
  - `GET /inventory/v1/products?query=...&page=...&pageSize=...` returning at minimum `{ productId, sku, name }`.
- Pricing API base path is `/pricing/v1/...` (DECISION-PRICING-002).
- Effective dating semantics:
  - MSRP records are effective-dated using timestamps interpreted in **store-local timezone** and evaluated as half-open intervals `[effectiveStartAt, effectiveEndAt)` (DECISION-PRICING-003).
  - UI uses **date-time pickers** and displays the store timezone in the editor (DECISION-PRICING-003).
- Money representation:
  - UI treats MSRP money as backend-owned and displays backend-provided values; money shape is `{ amount: "<decimal-string>", currencyUomId: "USD" }` (DECISION-PRICING-001).
- Audit/history contract for pricing admin entities is available (DECISION-PRICING-015).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Required fields (create):**
  - `productId` (required; selected via Inventory lookup)
  - `msrp` money object:
    - `amount` required; must parse as decimal-string; must be `> 0`
    - `currencyUomId` required
  - `effectiveStartAt` (required timestamp)
  - `effectiveEndAt` (optional timestamp)
- **Date/time logic (store-local semantics; DECISION-PRICING-003):**
  - If `effectiveEndAt` provided, must be strictly after `effectiveStartAt` to avoid zero-length intervals (because `[start,end)`).
- **Overlap prevention:**
  - UI may show existing ranges for context, but backend is authoritative.
  - On backend `409 CONFLICT` overlap error: show banner and keep form open.
- **Historical immutability (DECISION-PRICING-018):**
  - If record is past-effective (i.e., `effectiveEndAt` exists and `effectiveEndAt <= now` in store-local time), editing is disabled unless user has `pricing:msrp:manage:historical`.
  - If user has historical permission, editing is allowed but UI must show a warning “Editing historical MSRP is audited and should be rare.”

### Enable/disable rules
- Permission gating:
  - With `pricing:msrp:view` only: list + detail view allowed; create/edit actions hidden/disabled.
  - With `pricing:msrp:manage`: create/edit allowed except historical restriction.
  - With `pricing:msrp:manage:historical`: historical edits enabled.
  - If backend does not implement `pricing:msrp:view`, UI must gate the entire feature behind `pricing:msrp:manage` and handle 403 defensively.
- ProductId field:
  - Editable only during create via picker; read-only on edit.

### Visibility rules
- Show audit metadata on detail:
  - createdAt/createdBy, updatedAt/updatedBy if provided
- Show derived status chip in list and detail (Active/Upcoming/Expired)
- Show store timezone label near effective date-time fields (DECISION-PRICING-003)

### Error messaging expectations
- Field-level errors for missing/invalid input.
- Banner-level errors for overlap conflicts, product not found, authorization failures, backend unavailable/timeouts.
- UI must not recompute or “fix” money rounding; display backend-returned money values (DECISION-PRICING-001).

## 8. Data Requirements

### Entities involved
- **Pricing domain entity:** `ProductMSRP` (Pricing is system of record)
- **External reference:** Product (Inventory-owned) referenced by `productId`

### Fields (frontend model)
`ProductMSRP`
- `productMsrpId` (UUID/string, read-only, required for edit/view)
- `productId` (UUID/string, required; editable on create only; read-only on edit)
- `msrp` (Money object, required)
  - `amount` (decimal-string, required)
  - `currencyUomId` (string, required)
- `effectiveStartAt` (timestamp, required)
- `effectiveEndAt` (timestamp, optional; null = indefinite)
- `createdAt` (timestamp, read-only)
- `createdBy` (string/userRef, read-only; optional)
- `updatedAt` (timestamp, read-only; optional)
- `updatedBy` (string/userRef, read-only; optional)

Derived (UI-only; not persisted)
- `status`: `ACTIVE | UPCOMING | EXPIRED` (derived using store-local now and half-open interval)
- `isHistorical`: boolean (derived: `effectiveEndAt != null && effectiveEndAt <= now`)

### Read-only vs editable by state/role
- Create (manage permission):
  - Editable: productId (picker), msrp.amount, msrp.currencyUomId, effectiveStartAt, effectiveEndAt
- Edit (manage permission):
  - productId read-only
  - msrp + effective timestamps editable unless historical restriction applies
- Edit (historical record):
  - If no `pricing:msrp:manage:historical`: all fields read-only, Save disabled
  - If has `pricing:msrp:manage:historical`: editable with warning banner
- View:
  - all read-only

## 9. Service Contracts (Frontend Perspective)

> Pricing endpoints MUST use `/pricing/v1/...` (DECISION-PRICING-002). If actual routes differ in the repo, implement an adapter in the frontend API client but do not introduce non-versioned pricing paths.

### Load/view calls
1. **Inventory product search (for picker)**
   - `GET /inventory/v1/products?query=<string>&page=<int>&pageSize=<int>`
   - `200`:
     ```json
     { "items": [{ "productId": "p-1", "sku": "SKU-1", "name": "Product Name" }], "page": 1, "pageSize": 10, "total": 123 }
     ```
2. **List MSRPs by product**
   - `GET /pricing/v1/msrps?productId=<uuid>`
   - `200`:
     ```json
     { "items": [ { "productMsrpId": "...", "productId": "...", "msrp": { "amount": "100.00", "currencyUomId": "USD" }, "effectiveStartAt": "...", "effectiveEndAt": null } ] }
     ```
3. **Get MSRP by id**
   - `GET /pricing/v1/msrps/<productMsrpId>`
   - `200` `ProductMSRP`
   - `404` not found
   - `403` forbidden
4. **Audit/history for MSRP**
   - `GET /pricing/v1/msrps/<productMsrpId>/audit`
   - `200`:
     ```json
     { "items": [ { "changedAt": "2026-01-19T12:01:00Z", "changedBy": "user-1", "action": "UPDATE", "summary": "msrp.amount: 99.99 -> 109.99" } ] }
     ```
   - UI must render safely without assuming optional fields (DECISION-PRICING-015).

### Create/update calls
5. **Create MSRP**
   - `POST /pricing/v1/msrps`
   - Body:
     ```json
     {
       "productId": "uuid",
       "msrp": { "amount": "99.99", "currencyUomId": "USD" },
       "effectiveStartAt": "2026-02-01T00:00:00",
       "effectiveEndAt": "2026-03-01T00:00:00"
     }
     ```
   - Responses:
     - `201` created `ProductMSRP`
     - `400` validation errors:
       ```json
       { "errorCode": "VALIDATION_ERROR", "fieldErrors": { "effectiveStartAt": "required" } }
       ```
     - `404` product not found OR `400` invalid product (backend-defined; UI handles both as “Product not found/invalid”)
     - `409` overlap conflict:
       ```json
       { "errorCode": "CONFLICT", "message": "effective range overlaps existing MSRP" }
       ```
     - `403` forbidden
6. **Update MSRP**
   - `PUT /pricing/v1/msrps/<productMsrpId>`
   - Body (same shape as create minus productId):
     ```json
     {
       "msrp": { "amount": "109.99", "currencyUomId": "USD" },
       "effectiveStartAt": "2026-02-01T00:00:00",
       "effectiveEndAt": null
     }
     ```
   - Responses:
     - `200` updated `ProductMSRP`
     - `400` validation errors
     - `403` forbidden (including historical edit without permission)
     - `404` not found
     - `409` conflict (overlap or optimistic concurrency if backend uses versioning)

### Error handling expectations
- `400`:
  - If `fieldErrors` present: map to inline field errors.
  - Else: show banner with `message`.
- `403`: show “You do not have permission to view/manage MSRPs.” and disable editing.
- `404`: show “Record not found” and provide navigation back to list.
- `409`: show conflict banner; preserve form values; offer “Refresh list” action.
- `5xx`/network: show retry; preserve form values; do not clear selection.

## 10. State Model & Transitions

### Allowed states (UI-derived)
- `UPCOMING`: `now < effectiveStartAt`
- `ACTIVE`: `effectiveStartAt <= now < effectiveEndAt` OR (`effectiveEndAt` null and `effectiveStartAt <= now`)
- `EXPIRED`: `effectiveEndAt != null && effectiveEndAt <= now`

### Role-based transitions
- `pricing:msrp:view`: can view list/detail and audit history.
- `pricing:msrp:manage`: can create and edit non-historical records.
- `pricing:msrp:manage:historical`: can edit historical records (DECISION-PRICING-018).

### UI behavior per state
- UPCOMING: editable with manage permission.
- ACTIVE: editable with manage permission.
- EXPIRED:
  - Default: read-only; show “Historical MSRP is immutable.”
  - If historical permission: editable with warning and audit emphasis.

## 11. Alternate / Error Flows

### Validation failures
- Missing required fields: inline errors; submission blocked client-side; server remains authoritative.
- End <= start: inline error; block submission.

### Concurrency conflicts
- If backend returns `409 CONFLICT` due to version mismatch:
  - Show banner “This MSRP was updated by another user. Reload to continue.”
  - Provide “Reload” action; warn unsaved changes will be lost.

### Unauthorized access
- User without view permission:
  - If screen is accessed: show 403 page/state and no MSRP data rendered.
- User with view but not manage:
  - List/detail visible; create/edit controls hidden/disabled.
  - Direct navigation to edit: render read-only and show permission message; Save disabled.

### Empty states
- No product selected: show instruction “Select a product to view MSRPs.”
- Product selected but no MSRPs: show empty state with CTA “Create MSRP” (only if manage permission).

### Dependency failures
- Inventory product lookup fails:
  - Disable product picker; show error and “Retry”.
- Pricing list/load fails:
  - Show error state with retry; keep selected product context.

## 12. Acceptance Criteria

### Scenario 1: View MSRP list for a product
**Given** I am authenticated  
**And** I have `pricing:msrp:view` permission (or `pricing:msrp:manage` if view/manage split is not supported)  
**When** I navigate to Pricing → MSRP  
**And** I select a product from Inventory search results  
**Then** the UI calls `GET /pricing/v1/msrps?productId=<productId>`  
**And** I see a list of MSRP records including MSRP money, effectiveStartAt, effectiveEndAt (or “No end date”)  
**And** each row shows derived status Active/Upcoming/Expired using store-local time and `[start,end)` semantics.

### Scenario 2: Create a time-bound MSRP successfully
**Given** I have `pricing:msrp:manage` permission  
**And** I am on the MSRP list for product `<productId>`  
**When** I choose Create MSRP  
**And** I enter msrp amount `"99.99"`, currencyUomId `"USD"`, effectiveStartAt `"2026-02-01T00:00:00"`, effectiveEndAt `"2026-03-01T00:00:00"`  
**And** I submit  
**Then** the UI sends `POST /pricing/v1/msrps` with the money object `{amount, currencyUomId}`  
**And** on `201` I see a success confirmation  
**And** the new record appears in the list for `<productId>`.

### Scenario 3: Create an indefinite MSRP successfully
**Given** I have `pricing:msrp:manage` permission  
**And** I am on the MSRP list for product `<productId>`  
**When** I create an MSRP with effectiveEndAt omitted/null  
**Then** the UI displays “No end date” for that record  
**And** the record is considered Active when `effectiveStartAt <= now` (store-local).

### Scenario 4: Prevent invalid effective range in the UI
**Given** I am creating or editing an MSRP  
**When** I set effectiveStartAt to `"2026-03-01T00:00:00"`  
**And** I set effectiveEndAt to `"2026-03-01T00:00:00"`  
**Then** the UI blocks submission  
**And** I see an inline error indicating end must be after start (half-open interval).

### Scenario 5: Show overlap conflict returned by backend
**Given** an MSRP already exists for product `<productId>` overlapping my requested range  
**When** I submit a create or update that overlaps  
**Then** the backend responds `409` with `errorCode="CONFLICT"`  
**And** the UI shows a conflict banner indicating overlapping effective dates  
**And** my entered values remain in the form.

### Scenario 6: Historical immutability enforcement
**Given** an MSRP record has `effectiveEndAt` in the past (store-local)  
**And** I have `pricing:msrp:manage` but not `pricing:msrp:manage:historical`  
**When** I open the MSRP detail screen  
**Then** all fields are read-only and Save is disabled  
**And** the UI explains that historical MSRP is immutable without elevated permission.

### Scenario 7: Historical edit allowed with elevated permission
**Given** an MSRP record has `effectiveEndAt` in the past (store-local)  
**And** I have `pricing:msrp:manage:historical`  
**When** I edit and save the record  
**Then** the update succeeds (200) or returns a deterministic error (400/409/403)  
**And** an audit entry is visible in the audit/history panel for that MSRP.

### Scenario 8: Permission enforcement for manage actions
**Given** I am authenticated  
**But** I only have `pricing:msrp:view` permission  
**When** I navigate to Pricing → MSRP  
**Then** I do not see Create/Edit actions  
**And** if I attempt to access an edit URL directly, I cannot save changes and see a forbidden/insufficient permission message.
