## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Receiving: Receive Items into Staging (Generate Ledger Entries)

### Primary Persona
Receiver (warehouse receiving clerk)

### Business Value
Accurately increases on-hand inventory in the default Staging location at time of receipt, records variances (over/short), and creates immutable inventory ledger entries so downstream put-away and availability workflows can proceed with auditable data.

---

## 2. Story Intent

### As a / I want / So that
**As a** Receiver,  
**I want** to receive items against a Purchase Order (PO) or ASN into the site’s default Staging location by entering actual quantities (and UOM only when explicitly supported),  
**so that** on-hand increases immediately in staging, variances are recorded, and put-away can follow using accurate inventory state.

### In-scope
- Moqui screen flow to:
  - search/select a PO/ASN to receive
  - load expected lines (items, expected qty, expected UOM)
  - enter actual received qty per line
  - review variances (preview only)
  - finalize/confirm receipt (single atomic submit)
- Display outcome:
  - lines marked with received states returned by backend
  - confirmation that items are now “in staging”
  - show receipt session summary including correlation id and variance summary
- Error handling UX for not found, validation failures, conflicts, and transaction failure messaging.

### Out-of-scope
- Receiving items **not** on PO/ASN (“unplanned receipt”)
- Put-away process/UI (moving from staging to final bins)
- Inventory valuation/cost display changes
- Backorder/substitution policies
- Printing labels, barcode receiving scan flows
- Any client-side computation of on-hand/availability (inventory backend remains authoritative)

---

## 3. Actors & Stakeholders
- **Receiver (Primary):** performs receiving and confirms counts.
- **Warehouse Manager (Stakeholder):** expects auditability and inventory accuracy.
- **System (Moqui app):** enforces validation, calls Moqui proxy services, renders states.
- **Downstream Work Execution (Stakeholder/System):** may consume availability/receipt completion signals (frontend only displays results; eventing is backend-owned).

## 6. Functional Behavior

### Triggers
- User submits document search (find)
- User edits actual quantities
- User reviews
- User confirms receipt

### UI actions
- **Find action**
  - Validate `documentType` selected and `documentId` is trimmed non-empty
  - Call Moqui proxy load service
  - Render document header + lines + staging destination
- **Edit action**
  - For each receivable line, allow editing `actualQty`
  - `actualUomId` is displayed; editable only if backend explicitly supports it (otherwise read-only)
- **Review action**
  - Compute client-side variance preview (expected vs actual) for display only
  - Does not persist and does not call backend
- **Confirm action**
  - Submit receipt payload (single atomic backend operation)
  - Disable confirm while in-flight; show spinner within 100ms; timeout at 8s with Retry (no auto-refresh loops). (DECISION-INVENTORY-004 UX target)
  - On success, show result summary and lock the form (read-only)

### State changes (frontend)
- Local UI state:
  - `idle` (no document loaded)
  - `loaded` (document + lines loaded)
  - `reviewing` (variance preview visible)
  - `submitting` (confirm in-flight)
  - `submitted` (success result shown)
- Draft edits are held client-side until confirm; no partial saves.

### Service interactions (frontend to Moqui backend)
- Load expected lines for PO/ASN (Moqui proxy)
- Submit receipt confirmation (Moqui proxy):
  - backend creates immutable ledger entries (append-only)
  - backend updates on-hand in staging
  - backend records variances
  - backend updates receiving line states

Decision rationale applied:
- Ledger is immutable; UI never edits ledger entries. (DECISION-INVENTORY-005)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Find**
  - `documentType` required (PO or ASN)
  - `documentId` required; trimmed; whitespace-only rejected
- **Receive lines**
  - `actualQty` required for each receivable line
  - `actualQty` must be numeric and `>= 0`
  - `actualQty == 0` is allowed (represents full shortage for that line); backend remains authoritative for whether zero is permitted per document rules
- **No UI-side UOM conversion**
  - If `actualUomId` is editable, UI only submits the selected value; it does not convert quantities locally (conversion policy is backend-owned)

### Enable/disable rules
- **Search** enabled when `documentType` selected and `documentId` non-empty
- **Confirm Receipt** enabled only when:
  - document is loaded
  - at least one receivable line exists
  - all receivable lines have valid `actualQty`
  - not `submitting`
- **Review** enabled when lines are valid

### Visibility rules
- Destination Staging location is displayed read-only:
  - show `locationId` (site) and `stagingStorageLocationId` (bin) if both are provided by backend
- Variance preview visible after Review, and/or when any line has `actualQty != expectedQty`
- If no receivable lines returned, show empty-state and disable Review/Confirm

### Error messaging expectations
- Not found / not eligible: “Document not found or not eligible for receiving.”
- Validation: field-level messages (e.g., “Quantity must be 0 or greater.”)
- Permission (403): “You do not have permission to receive inventory.”
- Status conflict (409): “This document changed since you loaded it. Reload to continue.”
- Transaction failure (5xx): “Receipt failed; no inventory was updated. Please retry.”
- Timeout: “Request timed out. Check your connection and retry.”

Decision rationale applied:
- Deterministic error handling and correlation IDs for support. (DECISION-INVENTORY-003, DECISION-INVENTORY-012)

## 8. Data Requirements

### Entities involved (conceptual; frontend reads/writes via services)
- Receiving document header + lines (PO/ASN receiving view model; backend-owned)
- `StorageLocation` (staging destination; read-only display)
- `InventoryLedgerEntry` (created by backend; display summary only)
- Variance records (backend-owned; display summary only)

### Fields (type, required, defaults)

**Document search (UI input)**
- `documentType` (enum: `PO` | `ASN`) — required  
- `documentId` (string) — required, trimmed
- `locationId` (UUIDv7 string) — optional input; if not provided, backend resolves from user context (see Open Questions)

**Document header (loaded)**
- `documentId` (string) — required
- `documentType` (enum) — required
- `status` (string) — required (display)
- `locationId` (UUIDv7 string) — required (site)
- `locationName` (string) — optional (display)

**Staging destination (loaded; read-only)**
- `stagingStorageLocationId` (UUIDv7 string) — required
- `stagingStorageLocationName` (string) — required (display)
- `stagingStorageLocationBarcode` (string) — optional (display)

**Receiving line (loaded)**
- `receivingLineId` (string/UUID) — required
- `productSku` (string) — required (display + submit reference if backend requires)
- `productName` (string) — optional (display; product domain-owned)
- `expectedQty` (decimal) — required
- `expectedUomId` (string) — required
- `state` (string enum) — required (display)
- `isReceivable` (boolean) — required (drives editability); if not provided, UI infers from `state` using backend-provided `receivableStates` list (preferred) (see Open Questions)

**Receiving input (editable; client-side until confirm)**
- `actualQty` (decimal) — required; default = `expectedQty` (UI convenience)
- `actualUomId` (string) — default = `expectedUomId`; editable only if backend indicates `uomEditable=true` per line or per document

**Receipt result (read-only)**
- `receiptCorrelationId` (string) — required (also show `X-Correlation-Id` if provided separately)
- `receivedAt` (datetime UTC string) — required
- `receivedByUserId` (string) — required
- Per line:
  - `state` (string) — required
  - `varianceType` (enum `SHORTAGE|OVERAGE|NONE`) — optional but recommended
  - `varianceQty` (decimal) — optional but recommended
- Optional:
  - `ledgerEntryCount` (int) or `ledgerEntryIds[]` (string[]) — optional

### Read-only vs editable by state/role
- Before confirm: only `actualQty` (and possibly `actualUomId`) editable for receivable lines
- After confirm: all fields read-only
- If user lacks receive permission:
  - UI may allow Find/load if backend allows, but must disable Confirm and show permission messaging when permission data is available or on 403

### Derived/calculated fields (frontend)
- Variance preview only (non-authoritative):
  - `varianceQtyPreview = actualQty - expectedQty`
  - `varianceTypePreview = OVERAGE if >0 else SHORTAGE if <0 else NONE`

## 9. Service Contracts (Frontend Perspective)

Integration constraints:
- UI calls Moqui proxy endpoints only; no direct calls to inventory backend. (DECISION-INVENTORY-002)
- Responses are plain JSON; errors follow deterministic schema. (DECISION-INVENTORY-003)

> Endpoint paths for receiving are not defined in the provided inventory decisions. This story defines **proposed** Moqui proxy routes and payload shapes; backend must align or provide mapping.

### Load/view calls
1. **GET** `/inventory/receiving/document`
   - **Query params:**
     - `documentType` (required; `PO|ASN`)
     - `documentId` (required)
     - `locationId` (optional; if omitted backend resolves from session/user context)
   - **200 Response (plain JSON):**
     - `documentId`, `documentType`, `status`
     - `locationId`, `locationName?`
     - `stagingStorageLocationId`, `stagingStorageLocationName`, `stagingStorageLocationBarcode?`
     - `lines[]` with fields in Data Requirements, including `isReceivable` and optional `uomEditable`
   - **404:** not found / not eligible
   - **403:** forbidden

### Create/update calls
- None (draft edits are client-side until confirm)

### Submit/transition calls
2. **POST** `/inventory/receiving/confirm`
   - **Request body (plain JSON):**
     - `documentId` (required)
     - `documentType` (required)
     - `locationId` (required if backend cannot infer)
     - `stagingStorageLocationId` (required; backend validates it is the default staging for the site)
     - `lines[]` (required; only receivable lines):
       - `receivingLineId` (required)
       - `actualQty` (required)
       - `actualUomId` (optional; only if editable/supported)
   - **Headers:**
     - `X-Correlation-Id` (client-generated UUIDv7 recommended) (DECISION-INVENTORY-012)
     - (Idempotency header TBD; see Open Questions)
   - **200 Response (plain JSON):**
     - `receiptCorrelationId`
     - `receivedAt`, `receivedByUserId`
     - `lines[]` with updated `state` and variance summary fields when available
     - `ledgerEntryCount?` / `ledgerEntryIds?`
   - **422:** validation failure (e.g., inactive/pending location, invalid qty/UOM, staging mismatch)
   - **409:** conflict (document changed/already received)
   - **403:** forbidden

### Error handling expectations
- Deterministic error schema (DECISION-INVENTORY-003):
  - Map field errors to:
    - `documentId`, `documentType`
    - `lines[i].actualQty`, `lines[i].actualUomId`
- 401:
  - follow app convention: redirect to login/session refresh; do not show partial data (DECISION-INVENTORY-012)
- 403:
  - show forbidden state; do not leak document/line data if load is forbidden (DECISION-INVENTORY-012)
- 409:
  - show conflict banner + “Reload document”
- 422:
  - show validation banner; map to fields when possible
- 5xx/timeout:
  - show retry affordance; keep edits; do not auto-retry mutations

## 10. State Model & Transitions

### Allowed states
Receiving document/line state machine is backend-owned. UI must treat states as display strings and rely on backend-provided `isReceivable` (preferred) or a backend-provided list of receivable/terminal states.

Minimum UI expectations:
- Receivable lines: editable
- Non-receivable/terminal lines: read-only and excluded from confirm payload

### Role-based transitions
- Receiver triggers “Confirm Receipt” which transitions receivable lines to backend-determined received states and posts ledger entries.
- UI does not implement approval workflows or multi-step posting.

### UI behavior per state
- If a line is not receivable when loaded:
  - show as read-only
  - show a hint: “Not receivable in current state”
  - exclude from confirm payload
- After successful confirm:
  - lock all inputs
  - show result summary and updated states

## 11. Alternate / Error Flows

### Validation failures
- Missing `documentType` or empty `documentId`:
  - block Find; show inline errors
- Missing/invalid `actualQty`:
  - block Review/Confirm; show inline per line
- Negative qty:
  - inline error; prevent Review/Confirm

### Concurrency conflicts
- On 409 from confirm:
  - show banner “Document changed since loaded”
  - actions:
    - Reload (re-call GET `/inventory/receiving/document`)
    - Cancel (return to FindDocument; keep or discard edits based on user choice)

### Unauthorized access
- 401:
  - redirect to login/session refresh per app convention
- 403 on load:
  - show forbidden state; do not render document/lines
- 403 on confirm:
  - keep edits; show banner; disable confirm

### Empty states
- Document found but no receivable lines:
  - show “Nothing to receive.”
  - disable Review/Confirm
  - allow “Find another document”

### Timeout / network failure
- If request exceeds 8 seconds:
  - show timeout message + Retry
  - do not auto-retry confirm
  - keep edits intact

## 12. Acceptance Criteria

### Scenario 1: Load receivable document and default staging location
**Given** I am logged in as a Receiver  
**And** I have permission to view receiving documents  
**When** I select document type `PO` and enter a valid document id and search  
**Then** the system displays the document status and its expected receiving lines  
**And** the destination is shown as the default Staging storage location (read-only)

### Scenario 2: Receive exact expected quantity (no variance)
**Given** a loaded document line expects quantity `10` in UOM `EACH`  
**And** the line is marked receivable by the backend  
**When** I leave the actual quantity as `10` and confirm receipt  
**Then** the receipt succeeds and a receipt correlation id is shown  
**And** the line is displayed in a received state returned by the backend  
**And** the UI indicates the items are now in Staging  
**And** the variance for that line is `NONE` (or variance quantity is `0`) when provided

### Scenario 3: Short receipt shows variance result
**Given** a loaded document line expects quantity `10` in UOM `EACH`  
**When** I enter an actual quantity of `8` and confirm receipt  
**Then** the receipt succeeds  
**And** the line is displayed in the backend-returned received-short state (or equivalent)  
**And** the result includes a `SHORTAGE` variance of `2` `EACH` for that line when provided

### Scenario 4: Over receipt shows variance result
**Given** a loaded document line expects quantity `10` in UOM `EACH`  
**When** I enter an actual quantity of `12` and confirm receipt  
**Then** the receipt succeeds  
**And** the line is displayed in the backend-returned received-over state (or equivalent)  
**And** the result includes an `OVERAGE` variance of `2` `EACH` for that line when provided

### Scenario 5: Document not found or not eligible
**Given** I am on the Receive into Staging screen  
**When** I search for an identifier that does not match an eligible PO/ASN  
**Then** I see “Document not found or not eligible for receiving.”  
**And** no receiving lines are displayed  
**And** I cannot confirm receipt

### Scenario 6: Client validation prevents confirm on negative quantity
**Given** I have loaded a document with at least one receivable line  
**When** I enter a negative quantity for a line  
**Then** I see an inline validation error on that line  
**And** the Review and Confirm Receipt actions are disabled

### Scenario 7: Backend conflict on confirm (409)
**Given** I have loaded a document and entered actual quantities  
**When** I confirm receipt and the backend responds with HTTP `409`  
**Then** the UI shows a conflict banner  
**And** I can reload the document  
**And** the UI does not show a success result

### Scenario 8: Forbidden confirm (403)
**Given** I have loaded a document and entered actual quantities  
**When** I confirm receipt and the backend responds with HTTP `403`  
**Then** the UI shows a forbidden message  
**And** my entered quantities remain on screen  
**And** Confirm Receipt is disabled until permissions change or I reload

### Scenario 9: Correlation ID is shown on errors
**Given** I attempt to confirm receipt  
**When** the backend responds with an error that includes `X-Correlation-Id`  
**Then** the UI displays the correlation id in a “Technical details” section  
**And** the UI does not log quantities or full payloads to console/telemetry
