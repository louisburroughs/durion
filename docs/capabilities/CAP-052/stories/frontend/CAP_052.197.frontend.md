## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] AR: View AR Invoice Created from `InvoiceIssued` Event (Traceability + Idempotency Indicators)

### Primary Persona
Accounting Clerk / Finance User (AR) and Accounting Support Analyst

### Business Value
Enable finance users to verify that `InvoiceIssued` events resulted in an AR invoice and corresponding journal entry, with clear traceability and idempotency visibility to support reconciliation, auditing, and operational support.

---

## 2. Story Intent

### As a / I want / So that
- **As an** AR/Accounting user  
- **I want** to view an AR invoice record that was created from an `InvoiceIssued` event, including links to the source event ingestion record and resulting journal entry  
- **So that** I can confirm financial recording correctness, diagnose failures/duplicates/quarantine outcomes, and provide audit-ready traceability.

### In-scope
- Moqui UI screens to **search and view** AR invoices created from `InvoiceIssued` events.
- Display of **traceability identifiers**:
  - `sourceInvoiceId` (Billing invoice identifier)
  - `sourceEventId` (`eventId`, UUIDv7)
  - `ingestionId` (Accounting ingestion record identifier, UUIDv7) when available
  - `journalEntryId` (canonical posting reference; primary navigation target) (**Decision AD-011**)
- Display of key header amounts/dates: invoice date, due date, currency, totals, status.
- Read-only view of journal entry summary lines (GL account code + debit/credit + amount) when available via backend service.
- Display of **idempotency and processing indicators** sourced from ingestion record:
  - `processingStatus`: `PROCESSED | REJECTED | QUARANTINED`
  - `idempotencyOutcome`: `NEW | DUPLICATE_IGNORED | DUPLICATE_CONFLICT` (**Decision AD-007**)

### Out-of-scope
- Creating AR invoices from events (backend responsibility).
- Editing AR invoices or journal entries (posted/immutable).
- Defining GL account mappings, payment terms configuration, or posting rules.
- DLQ management beyond read-only visibility already represented by `processingStatus=QUARANTINED`. (**Decision AD-007**)

---

## 3. Actors & Stakeholders
- **Primary user:** Accounting Clerk (AR)
- **Secondary users:** Controller/Auditor (read-only verification), Support Analyst (troubleshooting)
- **Upstream system:** Billing domain emits `InvoiceIssued`
- **Accounting subsystem:** Ingests `InvoiceIssued` and persists `AccountingEventIngestionRecord` for ops visibility (**Decision AD-007**)
- **Downstream/related:** GL posting subsystem / journal entry records (Accounting-owned)

---

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated and has at least `accounting:ar-invoice:view` (see Permissions section below).
- Backend has ingested at least one `InvoiceIssued` event and created:
  - an AR invoice read model record, and
  - an ingestion record (`AccountingEventIngestionRecord`) for the event (even if rejected/quarantined), and
  - optionally a `JournalEntry` posting reference when processed. (**Decision AD-007**, **Decision AD-011**)

### Dependencies (backend contracts required)
This story is buildable only if the backend provides the following endpoints (names are normative for Accounting UI namespace; schemas remain backend-authoritative):

1. **AR invoice list/detail**
   - `GET /accounting/ar/invoices/list`
   - `GET /accounting/ar/invoices/detail?arInvoiceId=...`

2. **Ingestion monitoring list/detail** (for idempotency/processing indicators)
   - `GET /accounting/ingestion/list` (filterable by `eventId` and/or `sourceInvoiceId` via domain keys)
   - `GET /accounting/ingestion/detail?ingestionId=...` (**Decision AD-007**)

3. **Journal entry detail**
   - `GET /accounting/gl/journalEntry/detail?journalEntryId=...` (or equivalent Accounting-owned JE detail endpoint)
   - `journalEntryId` is the canonical navigation reference. (**Decision AD-011**)

### Permission dependencies (explicit; do not ship without mapping) (**Decision AD-013**)
- View AR invoices:
  - `accounting:ar-invoice:view` (new permission token for this UI capability; required)
- View ingestion monitoring:
  - `accounting:events:view` (existing; required to see ingestion indicators and navigate to ingestion detail)
- View journal entries:
  - `accounting:gl:journal-entry:view` (new permission token for JE view; required)
- View raw payload JSON (if shown anywhere):
  - `accounting:events:view-payload` (existing; optional) (**Decision AD-009**)

**Decision rationale:** The Accounting domain guide mandates explicit permission mapping and least privilege; existing tokens cover ingestion/payload, but AR invoice and GL JE view tokens are not defined in the provided rules and must be explicit to avoid shipping unauthenticated screens. (**Decision AD-013**)

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Main navigation: **Accounting → Accounts Receivable → Invoices**
- Deep link entry:
  - From support tooling or other screens using `sourceInvoiceId` and/or `sourceEventId` query params.
  - From ingestion detail screen via `sourceInvoiceId`/`eventId` navigation (if that screen exists).

### Screens to create/modify
1. **`Accounting/AR/InvoiceList`** (create or extend)
   - Search/filter AR invoices with traceability columns
2. **`Accounting/AR/InvoiceDetail`** (create or extend)
   - Read-only detail view with Traceability + Ingestion Status + Posting Reference sections
3. **`Accounting/Integrations/IngestionDetail`** (link target; may already exist per ingestion monitoring stories)
   - If it exists, reuse; otherwise this story only links when available
4. **`Accounting/GL/JournalEntryDetail`** (link target; may already exist)
   - Read-only journal entry view

### Navigation context
- From InvoiceList → InvoiceDetail via `arInvoiceId`
- From InvoiceDetail:
  - → JournalEntryDetail via `journalEntryId` (if present and permitted)
  - → IngestionDetail via `ingestionId` (if present and permitted)
  - If `ingestionId` is not present but `sourceEventId` is present, allow navigation to ingestion list pre-filtered by `eventId` (if supported by list screen).

### User workflows (happy + alternate)
- **Happy path (processed)**
  1. User opens AR Invoice List
  2. Filters by `sourceInvoiceId` or `sourceEventId`
  3. Opens an invoice
  4. Sees traceability identifiers and ingestion indicators: `processingStatus=PROCESSED`, `idempotencyOutcome=NEW`
  5. Opens journal entry and verifies lines
- **Alternate path: duplicate ignored**
  1. User opens invoice detail
  2. Ingestion indicators show `idempotencyOutcome=DUPLICATE_IGNORED`
  3. UI displays a non-blocking banner: “Duplicate event ignored; no new postings created.”
- **Alternate path: quarantined**
  1. User opens invoice detail or ingestion detail
  2. Ingestion indicators show `processingStatus=QUARANTINED` and/or `idempotencyOutcome=DUPLICATE_CONFLICT`
  3. UI displays a warning banner and shows backend-provided `errorCode`/`errorMessage` (no inference)
- **Alternate path: rejected (no AR invoice created)**
  - User searches by `sourceEventId` and sees no AR invoice results; UI suggests checking ingestion monitoring (link to ingestion list filtered by `eventId`).

## 6. Functional Behavior

### Triggers
- Entering InvoiceList loads initial results (paged).
- Submitting search form triggers reload.
- Opening InvoiceDetail triggers load by `arInvoiceId`.
- If InvoiceDetail includes ingestion indicators and backend does not embed them in invoice detail response, the screen triggers a secondary load:
  - ingestion lookup by `sourceEventId` (via ingestion list filter) or by `ingestionId` if provided.
- Clicking journal entry link navigates to JE detail screen.

### UI actions
- List search filters:
  - `sourceInvoiceId` (string)
  - `sourceEventId` (UUIDv7; validated client-side) (**Decision AD-006**)
  - `customerId` (string; optional)
  - invoice date range (`invoiceDateFrom`, `invoiceDateTo`; inclusive)
  - status (backend-provided enum values; UI treats as opaque)
- Detail actions:
  - Copy-to-clipboard: `sourceInvoiceId`, `sourceEventId`, `ingestionId`, `journalEntryId`
  - Navigate to ingestion detail/list (permission-gated)
  - Navigate to journal entry detail (permission-gated)

### State changes
- None to domain records (read-only).
- UI state: loading, loaded, empty, error.

### Service interactions (frontend → backend)
- `GET /accounting/ar/invoices/list`
- `GET /accounting/ar/invoices/detail`
- `GET /accounting/ingestion/list` (optional secondary call for indicators)
- `GET /accounting/ingestion/detail` (when navigating)
- `GET /accounting/gl/journalEntry/detail` (when navigating)

**Decision rationale:** Ingestion monitoring is the authoritative source for idempotency outcomes and processing status; the UI must not infer duplicates/quarantine from invoice presence alone. (**Decision AD-007**)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `sourceEventId` input:
  - Must be valid UUID format (UUIDv7 expected); block invalid input with inline error. (**Decision AD-006**)
- Date range:
  - `invoiceDateTo >= invoiceDateFrom` (inclusive); block invalid range.
- Do not validate/limit `sourceInvoiceId` length unless backend publishes a constraint; treat as free-text with trimming.

### Enable/disable rules
- Journal Entry navigation:
  - Enabled only when `journalEntryId` is present AND user has `accounting:gl:journal-entry:view`.
- Ingestion navigation:
  - Enabled only when user has `accounting:events:view`.
  - If `ingestionId` is present, link to ingestion detail.
  - Else if only `sourceEventId` is present, link to ingestion list filtered by `eventId` (if supported).

### Visibility rules
- Traceability section always visible; missing values show “Not available”.
- Ingestion indicators section:
  - Visible only if user has `accounting:events:view`.
  - If user lacks permission, show a small “Restricted” placeholder without fetching ingestion data.
- Raw payload JSON:
  - Never shown by default; only show if user has `accounting:events:view-payload` and only on ingestion detail screen (not required in this story). (**Decision AD-009**)

### Error messaging expectations
- 401/403:
  - Show “Access denied.” Do not reveal whether a specific ID exists. (**Decision AD-013**)
- 404:
  - Show “Not found or no access.”
- 409:
  - Show “Data changed; reload.” (rare for read-only, but handle if backend uses optimistic locking semantics)
- 5xx/timeout:
  - Show retry action and display a support-friendly correlation hint (see Observability).

## 10. State Model & Transitions

### Allowed states (display-only)
- AR invoice `status` is backend-defined; UI displays as opaque string.
- Ingestion statuses are authoritative and must be displayed exactly:
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (**Decision AD-007**)

### Role-based transitions
- None (read-only).

### UI behavior per state
- If ingestion `processingStatus=PROCESSED`:
  - Show “Processed” indicator; show posting reference(s) when present.
- If `processingStatus=REJECTED`:
  - Show “Rejected” banner; show `errorCode`/`errorMessage`; guide user to ingestion detail (if permitted).
- If `processingStatus=QUARANTINED` or `idempotencyOutcome=DUPLICATE_CONFLICT`:
  - Show “Quarantined / Conflict” banner; show backend error fields; do not imply remediation steps beyond “contact support / retry may be available in ingestion screen if permitted.”

## 11. Alternate / Error Flows

### Validation failures (search)
- Invalid UUID in `sourceEventId`:
  - Block search; show inline “Must be a valid UUID.”
- Invalid date range:
  - Block search; show inline “End date must be on or after start date.”

### Concurrency conflicts
- Invoice removed/permissions changed between list and detail:
  - Detail returns 404/403; show safe message and link back to list.

### Unauthorized access
- User can access list but not detail:
  - Detail returns 403; show access denied and link back.
- User can view invoice but not ingestion indicators:
  - Do not fetch ingestion endpoints; show “Restricted” placeholder.
- User can view invoice but not journal entry:
  - Hide/disable JE link; do not attempt JE fetch.

### Empty states
- No matching invoices:
  - Show empty state with “Clear filters” and suggestion to search by `sourceInvoiceId` or check ingestion monitoring by `sourceEventId`.

### Partial data
- `journalEntryId` missing:
  - Show “Posting reference not available” warning; allow navigation to ingestion detail (if permitted) to see why.
- Ingestion lookup returns no record:
  - Show “Ingestion record not available” (non-blocking); do not infer success/failure.

## 12. Acceptance Criteria

### Scenario 1: Search AR invoices by sourceInvoiceId
**Given** I have `accounting:ar-invoice:view`  
**When** I open the AR Invoice List screen and search by a `sourceInvoiceId`  
**Then** I see a paginated list of AR invoices matching that `sourceInvoiceId`  
**And** each row shows `invoiceDate`, `dueDate`, `totalAmount`, `currencyUomId`, `status`  
**And** selecting a row navigates to AR Invoice Detail for that invoice.

### Scenario 2: Search AR invoices by sourceEventId (UUID validation)
**Given** I have `accounting:ar-invoice:view`  
**When** I enter an invalid `sourceEventId` value in the filter  
**Then** the UI blocks the search and shows an inline validation error  
**When** I enter a valid UUID `sourceEventId` and submit  
**Then** the list reloads using that filter.

### Scenario 3: View AR invoice detail with traceability
**Given** an AR invoice exists that was created from an `InvoiceIssued` event  
**And** I have `accounting:ar-invoice:view`  
**When** I open the AR Invoice Detail screen for that invoice  
**Then** I see `sourceInvoiceId` and `sourceEventId` in a Traceability section  
**And** I see `journalEntryId` when present  
**And** I can copy each identifier to clipboard.

### Scenario 4: Ingestion indicators shown when permitted
**Given** I have `accounting:events:view`  
**And** the backend has an ingestion record for the invoice’s `sourceEventId`  
**When** I view AR Invoice Detail  
**Then** I see `processingStatus` and `idempotencyOutcome` values exactly as returned by backend  
**And** if `processingStatus=QUARANTINED` or `idempotencyOutcome=DUPLICATE_CONFLICT`, the UI shows a warning banner including backend `errorCode` and `errorMessage` (if provided).

### Scenario 5: Ingestion indicators hidden when not permitted
**Given** I have `accounting:ar-invoice:view`  
**And** I do not have `accounting:events:view`  
**When** I view AR Invoice Detail  
**Then** the UI does not display ingestion indicators  
**And** the UI does not call ingestion endpoints  
**And** the UI shows a non-sensitive “Restricted” placeholder in the ingestion section area.

### Scenario 6: Navigate to journal entry when available and permitted
**Given** I have `accounting:gl:journal-entry:view`  
**And** an AR invoice has a non-null `journalEntryId`  
**When** I click the journal entry link from AR Invoice Detail  
**Then** I am navigated to the Journal Entry Detail screen for that `journalEntryId`.

### Scenario 7: Journal entry not available
**Given** an AR invoice has `journalEntryId` null OR the JE endpoint returns 404  
**When** I view AR Invoice Detail  
**Then** the UI shows “Posting reference not available” (non-blocking warning)  
**And** no journal entry navigation action is enabled.

### Scenario 8: Invoice not found or no access
**Given** I navigate to AR Invoice Detail with an `arInvoiceId` that is invalid or not accessible  
**When** the screen loads  
**Then** I see “Not found or no access”  
**And** I can return to AR Invoice List.
