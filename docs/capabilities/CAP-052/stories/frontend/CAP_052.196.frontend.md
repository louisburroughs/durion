## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting AR: Apply Payment to Open Invoice(s)

### Primary Persona
Back Office Accountant (AR Clerk)

### Business Value
Enable accurate, auditable AR cash application by allocating an **AVAILABLE** accounting payment (receipt) across one or more eligible issued/open invoices, creating immutable `PaymentApplication` records with idempotency, and handling overpayment via `CustomerCredit` per policy.

---

## 2. Story Intent

### As a / I want / So that
**As a** Back Office Accountant (AR Clerk),  
**I want** to apply an available customer payment to one or more eligible open invoices (full/partial),  
**so that** AR balances and invoice settlement statuses are correct, overpayments become customer credit, and the action is traceable and idempotent.

### In-scope
- Load an accounting payment read model by `paymentId` and display apply-eligibility (Decision **AD-002**).
- Load eligible invoices for the payment’s `customerId` + `currencyUomId` and allocate amounts per invoice.
- Submit an **atomic** apply command with a frontend-generated UUIDv7 idempotency key `applicationRequestId` (Decisions **AD-010**, **AD-006**).
- Display backend-authoritative results:
  - created `PaymentApplication` records
  - updated invoice balances/statuses
  - updated payment `unappliedAmount`
  - optional `CustomerCredit` created on overpayment (Decision **AD-003**).
- Client-side validations for amounts/UUIDs and robust error mapping (canonical error schema).
- Permission-gated submit and payload visibility (Decision **AD-013**).

### Out-of-scope
- Payment capture/settlement/refunds (Payment domain SoR).
- Invoice issuance/void/cancel (Billing domain SoR).
- Reversal/unapply workflows (explicitly separate story; Decision **E9**).
- Auto-allocation policies (allocations are required; Decision **E7**).
- Multi-currency / FX application.
- Write-offs, disputes, credit reapplication.

---

## 3. Actors & Stakeholders
- **AR Clerk (User):** Performs allocations and reviews results.
- **Accounting Domain (SoR):** Validates and persists `PaymentApplication`; updates invoice/payment balances; creates `CustomerCredit` on overpayment (AD-002/003/010).
- **Billing Domain (Adjacent SoR):** Owns invoice lifecycle; accounting provides financial balance/status view used for eligibility.
- **Payment Domain (Upstream SoR):** Owns payment lifecycle; accounting consumes `PaymentReceived` and exposes `ReceivablePayment` read model.
- **Auditor/Compliance:** Requires immutable records, actor/time, idempotency behavior, and no hidden policy.

---

## 4. Preconditions & Dependencies
1. User is authenticated and authorized:
   - View payment: `accounting:payment:view`
   - Submit apply: `accounting:ar:apply-payment` (Decision **AD-013**, **E1**)
2. Backend endpoints exist and are reachable (Decision **A1/E2**):
   - `GET  /accounting/ar/payment?paymentId=...`
   - `GET  /accounting/ar/eligibleInvoices?customerId=...&currencyUomId=...`
   - `POST /accounting/ar/apply`
3. Payment is apply-eligible per backend:
   - payment status is `AVAILABLE`
   - `unappliedAmount > 0`
   - `customerId` is present (if absent, this workflow is blocked; customer assignment is a separate screen/story per AD-004)
4. Eligible invoices are determined by backend rules (Decision **E3**):
   - issued/open, not voided/cancelled, not paid-in-full, positive balance due
   - currency matches payment currency (no FX)

## 6. Functional Behavior

### Triggers
- On screen load with `paymentId`: load payment then eligible invoices.
- On “Load payment” action: same as above.
- On Submit: validate client-side then call apply command.

### UI actions
- **Payment ID input**
  - Single input `paymentId` (UUIDv7). Client-side UUID validation (Decision **AD-006**).
- **Invoice allocations table**
  - Each row: invoice identifiers + balance due + editable `amountToApply`.
  - Row action: “Apply max” sets `amountToApply = min(invoice.balanceDue, remainingUnappliedPreview)`.
- **Submit**
  - Disabled unless:
    - user has `accounting:ar:apply-payment`
    - payment is eligible (`status=AVAILABLE` and `unappliedAmount > 0`)
    - at least one allocation has `amountToApply > 0`
    - sum allocations `<= payment.unappliedAmount`
    - each allocation `<= invoice.balanceDue`
  - On click:
    - generate `applicationRequestId` UUIDv7
    - send request; disable submit while in-flight
    - on timeout/network error, allow retry using the **same** `applicationRequestId` for that attempt (Decision **AD-010**)

### State changes (frontend-visible)
- After success:
  - Allocation inputs become read-only for the loaded payment (since payment balances changed); user must reload to apply remaining amount if any (but overpayment policy sets to 0 when credit created).
  - Payment summary updates to backend-returned values.
  - Invoice rows update to backend-returned balances/statuses.

### Service interactions
- Read:
  - `/accounting/ar/payment`
  - `/accounting/ar/eligibleInvoices`
- Command:
  - `/accounting/ar/apply` (atomic, idempotent)

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side)
- **UUID format**: block invalid UUIDv7 format for `paymentId`, and for any invoiceId entered/used (Decision **AD-006**).
- **Amounts**:
  - decimal input only; no floating point
  - `amountToApply` must be `> 0` to count as an allocation
  - per-row: `amountToApply <= invoice.balanceDue`
  - total: `sum(amountToApply) <= payment.unappliedAmount`
- **Allocations required**: no submit with empty allocations (Decision **E7**).
- **Currency**: UI does not attempt FX; eligible invoices endpoint is already filtered by currency; if backend returns mixed currency unexpectedly, UI must block submit and show error “Currency mismatch” (Decision **AD-002**).

### Enable/disable rules
- Hide/disable Submit if user lacks `accounting:ar:apply-payment` (Decision **AD-013**).
- Disable all allocation inputs if payment is not eligible (status not `AVAILABLE` or `unappliedAmount <= 0`).
- Disable invoice row input if backend marks invoice ineligible (if such a flag is returned); otherwise rely on eligible list only.

### Visibility rules
- Always show:
  - payment `status`, `currencyUomId`, `unappliedAmount`, `paymentId`, `customerId`
- Show “Preview remaining” = `payment.unappliedAmount - sum(amountToApply)` (client-side preview only; backend is authoritative).
- On success, show:
  - `applicationRequestId` used
  - created `paymentApplicationIds[]` (if returned)
  - `customerCreditId` (if returned) and message “Overpayment converted to customer credit” (Decision **AD-003**)

### Error messaging expectations
- Use canonical error schema `{errorCode, message, details?}`.
- Map HTTP/status to UX:
  - **401/403**: “Access denied.” Do not reveal whether IDs exist (Decision **AD-013**).
  - **404**: “Not found.” (safe messaging)
  - **409**: “Data changed. Reload and try again.” (concurrency)
  - **422/400**: show validation banner + inline row errors when `details` contains invoiceId keys.
- Do not invent new enum meanings; display backend-provided `errorCode` and `message` and optionally a help link/runbook id if provided.

## 8. Data Requirements

### Entities involved (backend-owned; UI treats as contracts)
- `ReceivablePayment` (Accounting payment read model; apply eligibility and `unappliedAmount`)
- `Invoice` (Accounting financial view of invoice balance/status for AR eligibility)
- `PaymentApplication` (immutable application records)
- `CustomerCredit` (created on overpayment; Decision **AD-003**)

### Fields (type, required, defaults)

#### Payment (from `GET /accounting/ar/payment`) — read-only
- `paymentId` (UUIDv7, required)
- `customerId` (UUIDv7, required)
- `currencyUomId` (string, required)
- `status` (enum string, required; includes `AVAILABLE`)
- `totalAmount` (decimal, required)
- `unappliedAmount` (decimal, required)
- `effectiveAt` (datetime, optional for display; application date is backend-controlled per AD-012/E6)

#### Eligible Invoice row (from `GET /accounting/ar/eligibleInvoices`) — read-only + input
- `invoiceId` (UUIDv7, required)
- `invoiceNumber` (string, required for display)
- `invoiceDate` (date/datetime, optional but recommended)
- `balanceDue` (decimal, required)
- `currencyUomId` (string, required)
- `status` (string, optional; UI must not hardcode beyond eligibility list behavior)

#### Allocation input (client-side only until submit)
- `invoiceId` (UUIDv7, required)
- `amountToApply` (decimal, required; >0)

#### Apply response (from `POST /accounting/ar/apply`) — read-only
- `applicationRequestId` (UUIDv7, echoed back; required)
- `paymentApplications[]` (array; required)
  - each includes `paymentApplicationId` (UUIDv7) and `invoiceId`, `appliedAmount`
- `updatedPayment` (object; required)
  - includes `paymentId`, `unappliedAmount`, `status` (if changed)
- `updatedInvoices[]` (array; required)
  - includes `invoiceId`, `balanceDue`, and a settlement indicator (backend-owned)
- `customerCredit` (object, optional)
  - includes `customerCreditId` and `amount` (Decision **AD-003**)

### Read-only vs editable by state/role
- Editable only:
  - `amountToApply` fields, and only when user has submit permission and payment eligible.
- Everything else read-only.

### Derived/calculated fields (frontend)
- `totalToApply` = sum of entered `amountToApply`
- `previewRemaining` = `payment.unappliedAmount - totalToApply`

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
1. **Load payment for application**
   - Method/Path: `GET /accounting/ar/payment?paymentId=<UUIDv7>`
   - Success: returns payment summary and eligibility fields (backend-authoritative)
   - Errors:
     - 403/404 safe messaging
     - 422 invalid UUID (should be prevented client-side)

2. **List eligible invoices**
   - Method/Path: `GET /accounting/ar/eligibleInvoices?customerId=<UUIDv7>&currencyUomId=<string>`
   - Notes:
     - UI must not attempt to compute eligibility; list is authoritative (Decision **E3**).
     - Server-side pagination supported if backend provides it; UI must pass `pageIndex/pageSize/orderBy` when available.

### Submit/command calls
3. **Apply payment (atomic, idempotent)**
   - Method/Path: `POST /accounting/ar/apply`
   - Request body:
     - `applicationRequestId` (UUIDv7; generated by frontend; Decision **AD-010/AD-006**)
     - `paymentId` (UUIDv7)
     - `allocations` (array of `{ invoiceId: UUIDv7, amountToApply: decimal }`; required; Decision **E7**)
   - Response:
     - created applications + updated aggregates (Decision **E8**)
     - optional customer credit (Decision **AD-003**)
   - Idempotency:
     - Re-submit with same `applicationRequestId` must return the same outcome without double-applying (Decision **AD-010**).

### Error handling expectations
- Canonical error schema:
  ```json
  { "errorCode": "...", "message": "...", "details": { "...": "..." } }
  ```
- Per-invoice errors:
  - `details` may map `invoiceId` → error code/message; UI highlights corresponding row.

- Without it: can view payment and eligible invoices (if `accounting:payment:view`), but cannot submit.

### UI behavior per state
- Payment not eligible: show “Not eligible for application” and disable allocations/submit.
- Payment eligible but no invoices: show empty state; submit disabled.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Invalid UUID in paymentId → inline error; “Load” disabled.
- Any allocation invalid → row-level error; submit disabled.
- Total exceeds `unappliedAmount` → summary error; submit disabled.

### Backend validation failures (422/400)
- Backend rejects allocation due to stale balances or eligibility change:
  - show banner with `errorCode/message`
  - if `details` includes invoiceId keys, mark those rows
  - no partial apply is shown; user must reload (atomicity requirement)

### Concurrency conflicts (409)
- Another process applied the payment or invoice balance changed:
  - show “Data changed. Reload and try again.”
  - provide “Reload payment & invoices” action that re-calls both GET endpoints and clears allocations.

### Unauthorized access (403)
- Show access denied; do not reveal record existence.

### Empty states
- Payment has no eligible invoices: show empty state and guidance “No eligible invoices for this customer/currency.”

### Network/timeouts
- If POST times out:
  - UI shows “Request uncertain; you can retry.”
  - Retry uses the same `applicationRequestId` for that attempt to ensure idempotency (Decision **AD-010**).

## 12. Acceptance Criteria

### Scenario 1: Apply payment across multiple invoices (partial across invoices)
Given I have `accounting:payment:view` and `accounting:ar:apply-payment` permissions  
And an accounting payment exists with status `AVAILABLE` and `unappliedAmount` 100.00 USD  
And the backend returns two eligible invoices with `balanceDue` 60.00 and 80.00 USD  
When I enter allocations of 60.00 and 40.00 and submit  
Then the UI sends `POST /accounting/ar/apply` with a UUIDv7 `applicationRequestId` and both allocations  
And the backend response is displayed showing created payment application records for both invoices  
And the UI displays updated invoice balances (0.00 and 40.00) and updated settlement indicators as returned  
And the UI displays the updated payment `unappliedAmount` as returned by the backend

### Scenario 2: Overpayment creates customer credit
Given I have `accounting:ar:apply-payment` permission  
And an accounting payment exists with status `AVAILABLE` and `unappliedAmount` 200.00 USD  
And eligible invoices total 150.00 USD balance due  
When I allocate 150.00 across invoices and submit  
Then the backend response indicates a `CustomerCredit` was created for 50.00  
And the UI displays the `customerCreditId` and amount  
And the UI displays payment `unappliedAmount = 0` per backend response

### Scenario 3: Prevent applying more than invoice balance (client-side)
Given I loaded eligible invoices including one with `balanceDue` 10.00  
When I enter `amountToApply` 11.00 for that invoice  
Then the UI shows a row-level validation error  
And the Submit action remains disabled

### Scenario 4: Backend rejects due to invoice becoming ineligible (atomic failure)
Given I loaded eligible invoices and entered allocations  
And before I submit, one invoice becomes ineligible or its balance due changes  
When I submit  
Then the backend returns a validation error with `errorCode` and optional `details` keyed by `invoiceId`  
And the UI shows an error banner and highlights the affected invoice row(s) when identifiable  
And the UI does not show any “partial success” allocations

### Scenario 5: Idempotent replay on retry
Given I submitted an apply request with `applicationRequestId` X  
And the network times out before I receive a response  
When I retry submission using the same `applicationRequestId` X  
Then the backend returns the same outcome without double-applying  
And the UI displays the returned allocations and updated balances

### Scenario 6: Permission gating
Given I have `accounting:payment:view` but do not have `accounting:ar:apply-payment`  
When I load an eligible payment  
Then I can view payment and eligible invoices  
But the allocation inputs and Submit action are not available (or are disabled)  
And any direct POST attempt results in a safe access denied message
