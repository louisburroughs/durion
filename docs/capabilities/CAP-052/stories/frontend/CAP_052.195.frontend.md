## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] AR: Issue Posted Credit Memo Against Issued Invoice (Traceable, Audited; No Refund Execution)

### Primary Persona
Accounts Receivable (AR) Clerk

**Persona Metadata**
- `primary_persona`: `Accounts Receivable (AR) Clerk`
- `canonical_persona`: `Accounting Associate`
- `persona_family`: `Accounting Associate`
- `actor_type`: `human`

### Business Value
Enable AR to correct issued invoices by issuing an auditable, immutable credit memo that reduces AR appropriately, preserves period controls, and provides traceability for audit/compliance—without crossing into Payment-domain refund execution.

---

## 2. Story Intent

### As a / I want / So that
**As an** AR Clerk,  
**I want** to create and post a Credit Memo that references a specific issued invoice with a required reason code and justification,  
**so that** the customer’s AR balance is reduced appropriately and the action is fully traceable for audit review.

### In-scope
- Frontend screens and flows to:
  - Locate an issued invoice and initiate “Issue Credit Memo”.
  - Enter credit memo details (amount, reason code, justification).
  - Submit to backend to create **and post** the credit memo (no draft-save in this story).
  - View created credit memo details including link back to original invoice and audit metadata.
- UI validation enforcing required fields and basic constraints (non-negative, currency-scale formatting, cannot exceed allowable amount per backend).
- Display backend-calculated results (totals, status, timestamps, reference IDs).
- Error handling for invalid state, validation failures, concurrency, accounting period enforcement, and unauthorized access.

### Out-of-scope
- Executing a **cash refund** or payment transaction (Payment domain; see AD-001 boundary pattern).
- Reversal/voiding of credit memos (separate story).
- Defining GL account mappings, debit/credit lines, tax jurisdiction rules, or period-close accounting policies beyond displaying backend errors (backend-defined).
- Auto-allocation policies (not applicable here).
- Approval workflows (not specified by Accounting domain rules; not introduced via safe defaults).

## 3. Actors & Stakeholders
- **AR Clerk (primary user):** issues posted credit memo.
- **Accounting Manager (stakeholder):** reviews audit trail and outcomes; may enforce policy outside this story.
- **Auditor (stakeholder):** needs immutable traceability (who/when/why/what changed).
- **Billing domain / Invoice system (dependency):** invoice issuance/finalization is Billing-owned; Accounting consumes issued invoices for AR effects.
- **Tax Configuration Service (dependency):** authoritative tax/fee rules used by backend for any reversal calculations.
- **Payment domain (downstream):** may later execute refunds; explicitly out-of-scope.

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in Moqui.
- User has permission to view invoices and issue credit memos (permission token(s) must be configured; see below).
- Target invoice exists and is **issued/open with positive balance due** (eligibility is rule-based; do not hardcode additional statuses beyond backend-provided eligibility).
- Credit memo reason codes are configured and retrievable.

### Dependencies (frontend contracts required)
Backend must provide Accounting-owned endpoints/services for:
- Loading invoice summary/details including `currencyUomId` and `balanceDue` (or equivalent).
- Listing credit memo reason codes.
- Creating/posting a credit memo against an invoice.
- Loading credit memo details after creation.

Security dependencies:
- Moqui artifact authorization for screens and transitions.
- Service authorization enforcing least privilege (deny by default; AD-013).

Observability dependencies:
- W3C Trace Context propagation (`traceparent`, `tracestate`) on all calls (AD-008).

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI-enforced; backend remains source of truth)
- **BR-UI-1 Required reason code:** cannot submit without selecting a reason code; inline error “Reason code is required.”
- **BR-UI-2 Required justification:** justification is required and must be **>= 10 characters** (mirrors mutation-justification standard used in Accounting for sensitive mutations; AD-004 pattern). Inline error “Justification must be at least 10 characters.”
- **BR-UI-3 Credit amount required:** cannot submit with empty amount.
- **BR-UI-4 Positive amount:** `creditAmount > 0.00` (do not allow zero-value credit memos). Inline error “Amount must be greater than 0.00.”
- **BR-UI-5 Currency scale:** enforce decimal input consistent with currency scale (no floating point; decimal only).
- **BR-UI-6 Invoice eligibility:** if invoice is not eligible (not issued/open, voided/cancelled, paid-in-full, or balance due <= 0), hide/disable “Issue Credit Memo”; if navigated directly, show blocking error state.
- **BR-UI-7 No negative totals:** UI must not allow negative credit amount; backend will also enforce that invoice totals cannot become negative and credit memo rules apply (Accounting invariant: negative totals disallowed; credit memos used for reductions).

### Enable/disable rules
- “Issue Credit Memo” action visible only when user has permission to issue credit memos; otherwise hidden (secure-by-default; AD-013).
- “Issue Credit Memo” action enabled only when invoice is eligible per backend-provided fields (e.g., `eligibleForCreditMemo=true` or `balanceDue>0` + `status`).
- Submit disabled while request in-flight; Cancel always available.

### Visibility rules
- Invoice context fields are read-only.
- Credit memo detail is read-only (posted/immutable in this story).
- If backend returns any raw payload-like fields, UI must treat them as restricted and not render unless explicitly permitted (AD-009). (This story does not require payload viewing.)

### Error messaging expectations
- Use backend `errorCode` and `message` (canonical error schema from Accounting guide) to drive user-safe messages.
- For validation errors with `details`, map to field-level errors; for row/record errors, show banner plus inline where possible.

## 9. Service Contracts (Frontend Perspective)

> Backend contract for credit memo issuance endpoints is not defined in the provided Accounting guide (unlike payments/refunds/ingestion/export). This story defines **required** contract shape and error handling expectations; exact route/service names must be confirmed by backend module owners.

### Load/view calls

1) **Get invoice AR context**
- Endpoint (proposed): `GET /accounting/ar/invoice?invoiceId=...`
- Request: `{ invoiceId }`
- Response (minimum required):
  - `invoiceId`, `invoiceStatus`, `currencyUomId`, `balanceDue`, `customerId`, `customerDisplayName` (or equivalent)
  - Optional: `eligibleForCreditMemo`, `ineligibilityReason`
- Errors:
  - `403` (no leakage; show Access Denied)
  - `404` (safe Not Found)
  - Validation error for invalid UUID (UI should block before calling; AD-006)

2) **List credit memo reason codes**
- Endpoint (proposed): `GET /accounting/ar/creditMemoReasonCodes?activeOnly=true`
- Response: list of `{ reasonCode, description, activeFlag }` (treat `reasonCode` as opaque)
- Errors: `403`

3) **Get credit memo detail**
- Endpoint (proposed): `GET /accounting/ar/creditMemos/detail?creditMemoId=...`
- Response: credit memo display fields + linkage to invoice
- Errors:
  - `403`, `404`

### Create/update calls

4) **Issue (create + post) credit memo**
- Endpoint (proposed): `POST /accounting/ar/creditMemos/issue`
- Request:
  - `creditMemoRequestId` (UUIDv7; idempotency key; required)
  - `invoiceId` (UUIDv7; required)
  - `creditAmount` (decimal; required)
  - `reasonCode` (string; required)
  - `justificationNote` (string; required; >= 10 chars)
- Response (minimum required):
  - `creditMemoId` (UUIDv7; required)
  - `status` (string)
  - `postedAt` (timestamp)
  - Optional: updated `balanceDue` for invoice, and any breakdown fields
- Error handling expectations (canonical schema):
  - Validation: `400/422` with `{ errorCode, message, details }`
    - `details` may include `creditAmount`, `reasonCode`, `justificationNote`
  - State/conflict: `409` with `errorCode` such as:
    - `INVALID_INVOICE_STATE`
    - `INVOICE_BALANCE_CHANGED`
    - `ACCOUNTING_PERIOD_CLOSED` (AD-012)
  - Authorization: `401/403`
  - Not found: `404` (invoice not found)
- Idempotency behavior:
  - If the same `creditMemoRequestId` is submitted again, backend must return the same `creditMemoId` (or a deterministic “already processed” response). UI treats as success and navigates to detail.

### Error handling expectations (UI)
- `details` field mapping:
  - If `details` contains field keys, show inline errors.
  - If `details` contains general keys, show banner with backend `message`.
- `409`:
  - Show banner “This invoice changed or is not eligible. Reload and try again.”
  - Provide “Reload invoice” action that re-fetches invoice context and resets any derived preview.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing reason code → inline error; no request sent.
- Missing justification or < 10 chars → inline error; no request sent.
- Invalid amount format or <= 0 → inline error; no request sent.
- Invalid UUID in route → show blocking error state; do not call backend.

### Backend validation failures
- Backend returns `ACCOUNTING_VALIDATION_FAILED` with `details`:
  - Map to inline errors; keep user inputs.
- Backend returns `CREDIT_EXCEEDS_BALANCE_DUE` (example):
  - Show inline error on amount and banner with backend message.

### Concurrency conflicts
- Backend returns `409 INVOICE_BALANCE_CHANGED`:
  - Show banner with “Reload invoice” action.
  - On reload, clear amount input (or keep but revalidate against new balance due) and re-run client-side max checks.

### Accounting period enforcement
- Backend returns `409 ACCOUNTING_PERIOD_CLOSED` (AD-012):
  - Show banner “Cannot post credit memo because the accounting period is closed.”
  - Provide support hint: “Contact Accounting Manager to reopen period or use approved adjustment process.” (No UI action to reopen period.)

### Unauthorized access
- If user lacks permission:
  - Hide action on invoice detail.
  - If direct navigation: show Access Denied; do not reveal invoice existence (consistent 403/404 handling).

### Empty states
- Reason code list empty:
  - Block submission; show message “No credit memo reason codes configured.”
  - Provide link back to invoice.

## 12. Acceptance Criteria

### Scenario 1: Issue full credit memo successfully (posted)
**Given** an invoice `INV-123` is eligible for credit memo issuance and has `balanceDue = 110.00` in currency `USD`  
**And** the user has permission to issue credit memos  
**And** credit memo reason code `RETURNED_GOODS` is available  
**When** the user initiates “Issue Credit Memo” from `INV-123`  
**And** enters credit amount `110.00`  
**And** selects reason code `RETURNED_GOODS`  
**And** enters justification “Customer returned items; restocking approved.”  
**And** submits the form  
**Then** the backend returns a `creditMemoId` and a posted status  
**And** the UI navigates to the Credit Memo Detail screen for that `creditMemoId`  
**And** the detail displays a reference/link to invoice `INV-123`  
**And** the detail displays reason code, justification, `createdBy/createdAt`, and `postedBy/postedAt`.

### Scenario 2: Issue partial credit memo successfully
**Given** invoice `INV-123` is eligible with `balanceDue = 110.00`  
**And** reason code `PRICING_ERROR` is available  
**When** the user issues a credit memo for amount `55.00` with reason `PRICING_ERROR` and a valid justification  
**Then** the Credit Memo Detail shows total amount `55.00` (or backend-returned total)  
**And** the credit memo remains linked to `INV-123`.

### Scenario 3: Block submit when reason code missing
**Given** the user is on the Issue Credit Memo screen for an eligible invoice  
**When** the user enters a valid credit amount and valid justification  
**And** does not select a reason code  
**And** clicks Submit  
**Then** the UI does not call the issue credit memo service  
**And** the UI shows an inline validation error that a reason code is required.

### Scenario 4: Block submit when justification is too short
**Given** the user is on the Issue Credit Memo screen for an eligible invoice  
**When** the user enters a valid credit amount and selects a reason code  
**And** enters justification “Too short”  
**And** clicks Submit  
**Then** the UI does not call the issue credit memo service  
**And** the UI shows an inline validation error that justification must be at least 10 characters.

### Scenario 5: Backend rejects credit exceeding balance due
**Given** invoice `INV-123` is eligible with `balanceDue = 50.00`  
**When** the user submits a credit memo for `60.00` with valid reason and justification  
**Then** the backend responds with a validation error code indicating the credit exceeds the allowable amount  
**And** the UI displays an error banner/message using the backend message  
**And** the amount field is marked invalid  
**And** no navigation to credit memo detail occurs.

### Scenario 6: Invoice not eligible
**Given** invoice `INV-999` is not eligible for credit memo issuance  
**When** the user views the invoice detail screen  
**Then** the “Issue Credit Memo” action is hidden or disabled  
**And** if the user navigates directly to the Issue Credit Memo URL for `INV-999`  
**Then** the UI displays a blocking error indicating the invoice is not eligible (without leaking sensitive details).

### Scenario 7: Idempotent retry after timeout
**Given** the user submits the Issue Credit Memo form and the request times out client-side  
**When** the user retries submission from the same screen state  
**Then** the UI reuses the same `creditMemoRequestId`  
**And** if the backend returns success for the original request, the retry results in navigation to the same `creditMemoId` without creating a duplicate credit memo.
