## 1. Story Header

### Title
[FRONTEND] Users: Provision User and Link to Person

### Primary Persona
Admin (authorized to provision users)

**Persona Metadata**
- `primary_persona`: `Admin (authorized to provision users)`
- `canonical_persona`: `System Administrator`

### Business Value
Enable an employee to authenticate and be correctly attributed across downstream systems (workexec/timekeeping/shopmgr) by provisioning a platform `User` and initiating linkage to an existing `Person` via asynchronous orchestration.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Admin  
- **I want** to provision a new system `User` (IdP identity + optional initial roles) and initiate linking it to an existing `Person`  
- **So that** the employee can log in and is correctly attributed across downstream services.

### In-scope
- A Moqui/Quasar frontend flow to:
  - Search/select an existing `Person` (by email/name fragment via `search` query) to link
  - Capture provisioning identity fields (`idpSubject`, `email`, optional `username`) and `status`
  - Select **zero or more** initial roles (by `roleId`)
  - Submit provisioning request to Security provisioning endpoint (idempotent)
  - Show immediate success (linking is asynchronous)
  - Show link status (`PENDING|LINKED|FAILED`) with a **manual refresh** action (no polling)
  - Display canonical error envelope responses with actionable messaging

### Out-of-scope
- Creating/editing `Person` records (people domain)
- Principal-role assignment UI beyond initial roles at provision time (no ongoing assignment management UI)
- Creating/editing permissions (permission registry is code-first; UI read-only)
- Implementing the event consumer/linking in `pos-people` (backend responsibility)
- Downstream integrations beyond reflecting linkage status in UI

---

## 3. Actors & Stakeholders
- **Admin user**: initiates provisioning
- **Security service (`pos-security-service`)**: SoR for `User`, SoR for roles, hosts provisioning + user detail endpoints
- **People service (`pos-people`)**: SoR for `Person` and `UserPersonLink`, provides person search endpoint, consumes provisioning outbox event
- **Downstream services**: rely on `User`↔`Person` linkage for attribution and staff visibility

## 4. Preconditions & Dependencies
- Admin is authenticated in the frontend.
- Admin has permission `security:user:provision` (gates both screen access and submit in v1).
- A `Person` already exists in `pos-people` with a stable `personId` and canonical primary `email`.
- Backend endpoints exist and are reachable from the Moqui frontend (gateway or direct):
  - People:
    - `GET /api/v1/people/persons?search=...`
  - Security:
    - `GET /api/v1/security/roles`
    - `POST /api/v1/security/users/provision`
    - `GET /api/v1/security/users/{userId}` (for link status)
- Tenant context is derived from trusted auth claims/request context (not user input); RBAC is tenant-scoped (no location-scoped RBAC in v1).
- Canonical error envelope is implemented for Security endpoints:
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`, optional `details`

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Admin navigation: **Users → Provision User**
- Direct route access is permitted only if the current principal is authorized for `security:user:provision` (deny-by-default).

### Screens to create/modify
- Create new Moqui screen:
  - `component://frontend/screen/admin/users/ProvisionUser.xml` (adjust to repo conventions)
- Optional: modify Users admin index screen to add a link/button to provisioning flow.

### Navigation context
- Admin Home → Users → Provision User

### User workflows (happy + alternate paths)

#### Happy path (new user, link pending)
1. Admin opens “Provision User”.
2. Admin searches for an existing Person using a search string (email fragment or name).
3. Admin selects exactly one Person from results; UI displays Person summary and locks selection unless changed.
4. Admin enters:
   - `idpSubject` (required)
   - `email` (required; must match selected Person email case-insensitively)
   - `username` (optional; if omitted backend derives from email local-part)
   - `status` (defaults to `ACTIVE`)
5. Admin optionally selects initial roles (0..n) from Security roles list (by `roleId`).
6. Admin submits.
7. UI shows success with returned `userId`, `personId`, `resolvedExisting`, `eventEnqueued`, `correlationId`, and `linkStatus` (initially expected `PENDING`).
8. Admin may click “Refresh status” to call `GET /api/v1/security/users/{userId}` and update `linkStatus`.

#### Alternate paths
- Person not found: show empty state; cannot submit until a Person is selected.
- User already exists (idempotent resolve): show success; indicate “Existing user resolved” when `resolvedExisting=true`.
- Link status becomes `FAILED`: show operational guidance (see Error Flows) and keep “Refresh status” available.
- Backend returns validation errors: show field-level messages using `fieldErrors[]`.
- Unauthorized: show access denied; do not render form controls or data.

## 6. Functional Behavior

### Triggers
- Screen load:
  - Verify route permission (`security:user:provision`) via existing frontend authz mechanism; if unauthorized, render access denied state.
  - Load roles list from Security (`GET /api/v1/security/roles`) for role selection.
- Person search:
  - On user input, trigger debounced search to People (`GET /api/v1/people/persons?search=...`).
- Submit:
  - On “Provision User”, call Security provisioning endpoint (`POST /api/v1/security/users/provision`).
- Refresh status:
  - On “Refresh status”, call Security user detail (`GET /api/v1/security/users/{userId}`).

### UI actions
- Person search input + results list; selecting a Person:
  - Sets `personId` (read-only)
  - Prefills `email` with selected Person email and locks it to prevent mismatch (still displayed as editable=false)
- Provisioning form:
  - `idpSubject` input (required)
  - `username` input (optional)
  - `status` select (`ACTIVE|DISABLED`, default `ACTIVE`)
  - Roles multi-select (0..n) populated from roles list
- Submit button:
  - Disabled until required fields are present and valid (see Business Rules)
  - Disabled during submission

### State changes (frontend)
- View-state:
  - `idle` → `loadingRoles`
  - `idle` → `searchingPerson` → `personSelected`
  - `personSelected` → `submitting` → `success` | `error`
  - `success` → `refreshingStatus` → `success` (updated status) | `error` (status refresh error)
- After success:
  - Persist the last successful response in screen state for display
  - Do not auto-poll; only update link status on manual refresh

### Service interactions
- People lookup:
  - `GET /api/v1/people/persons?search=<string>`
- Security role list:
  - `GET /api/v1/security/roles?pageIndex=<int>&pageSize=<int>` (pagination supported; UI may request first page with sufficiently large pageSize for admin usability)
- Security provisioning:
  - `POST /api/v1/security/users/provision`
- Security user detail (link status):
  - `GET /api/v1/security/users/{userId}`

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side; backend authoritative)
- Required fields to enable submit:
  - `personId` selected from People search results (not free text)
  - `idpSubject` non-empty
  - `email` present and format-valid **and** equals selected Person email case-insensitively (UI enforces by prefilling + locking)
  - `status` is one of `ACTIVE|DISABLED` (default `ACTIVE`)
- Optional:
  - `username` optional; if omitted backend derives from email local-part
  - `roleIds[]` optional; zero roles allowed
- Permission keys are immutable and validated server-side; UI does not attempt to create/edit permissions.

### Enable/disable rules
- Disable provisioning form until a Person is selected.
- Disable `email` editing after Person selection to prevent `EMAIL_MISMATCH` errors (still display value).
- Disable Submit while submitting or when required fields invalid/missing.
- Disable “Refresh status” until a successful provisioning response provides `userId`.

### Visibility rules
- Show selected Person summary once selected (minimum: displayName, email, personId).
- Show roles selector only after roles list load succeeds; if roles load fails, show an error but still allow provisioning with zero roles (roles optional).
- Show success panel after provisioning:
  - `userId`, `personId`, `status`, `resolvedExisting`, `eventEnqueued`, `correlationId`, `linkStatus`, and timestamps if provided.
- Show link status guidance:
  - `PENDING`: “Linking in progress; refresh later.”
  - `LINKED`: “Linked successfully.”
  - `FAILED`: “Linking failed; see guidance.”

### Error messaging expectations (canonical envelope)
- For Security endpoints, map errors using envelope:
  - `VALIDATION_FAILED` (400): show `fieldErrors[]` inline; show `message` as summary
  - `FORBIDDEN` (403): show access denied
  - `NOT_FOUND` (404): show not found (for user detail refresh)
  - `EMAIL_MISMATCH` (409): show “Email must match selected Person email” (should be prevented by UI)
  - `ROLE_NAME_TAKEN` / role errors not expected in this screen (no role creation)
  - `5xx`: show generic retryable error; include `correlationId` in UI for support
- For People search endpoint errors:
  - If non-2xx, show a non-sensitive error and allow retry; do not block navigation away.

1) **Provision User (Security domain)**
- Permission required: `security:user:provision`
- `POST /api/v1/security/users/provision`
- Request:
```json
{
  "personId":"p1",
  "idpSubject":"idp|abc123",
  "email":"john.doe@example.com",
  "username":"john.doe",
  "status":"ACTIVE",
  "roleIds":["r1","r2"]

```

```json

```

- All non-2xx responses from Security endpoints return:

```json
  "correlationId":"c-123",

```
- Frontend behavior:
  - Always surface `message`
  - Map `fieldErrors[]` to inputs when present
  - Display `correlationId` in error summary for support
  - Treat provisioning as safe-to-retry only when the user explicitly retries; backend idempotency on `idpSubject` prevents duplicates

## 10. State Model & Transitions

### Allowed states (frontend workflow state)
- `DRAFT` (editing; not submitted)
- `LOADING_ROLES`
- `SEARCHING_PERSON`
- `SUBMITTING`
- `PROVISIONED` (success; includes `linkStatus`)
- `ERROR` (submission failed)
- `REFRESHING_STATUS` (transient)

### Role-based transitions
- Only principals with `security:user:provision` can access the screen and execute `DRAFT → SUBMITTING`.
- Deny-by-default: if permission is absent, route is not accessible and submit is blocked.

### UI behavior per state
- `DRAFT`: editable form; submit enabled only when required fields valid.
- `LOADING_ROLES`: allow person search and identity entry; roles selector shows loading/disabled.
- `SUBMITTING`: disable inputs and submit; show progress.
- `PROVISIONED`: show success details; enable “Refresh status” and “Provision another user”.
- `ERROR`: show error summary; keep entered values; allow correction and retry.
- `REFRESHING_STATUS`: disable refresh button; keep success panel visible.

## 11. Alternate / Error Flows

### Validation failures (400 VALIDATION_FAILED)
- Show summary message and inline field errors.
- Keep Person selection and previously entered values.
- Do not clear selected roles.

### Conflict: email mismatch (409 EMAIL_MISMATCH)
- Expected to be prevented by UI (email locked to Person email).
- If received:
  - Show error “Email must match selected Person email”
  - Provide action “Reset from selected Person” to re-apply Person email into the email field (and lock)

### Idempotent resolve (200 with resolvedExisting=true)
- Treat as success.
- Display “Existing user resolved” and show returned `userId`.
- Continue to show link status and allow refresh.

### Link status FAILED
- Display:
  - “Linking failed. The user was provisioned, but linking to Person did not complete.”
  - Show `correlationId` from provisioning response (and from refresh if provided).
  - Provide guidance:
    - “Verify the Person email is correct.”
    - “Retry provisioning with the same IdP subject (safe; idempotent) after correcting upstream data.”
    - “Contact support with correlationId if failure persists.”
- Do not attempt automatic remediation in UI.

### Unauthorized access
- `401`: route to login per app standard.
- `403`: show access denied state; do not render form or search results.

### Empty states
- Person search returns no results:
  - Show “No matching person found.”
  - Guidance: “Create the Person record first in People (if available) or contact HR/admin.”

### Network/server errors
- For 5xx or network failure on provisioning:
  - Show retryable error with correlationId if available (if none, show “No correlationId returned”)
  - Allow user to retry; backend idempotency on `idpSubject` prevents duplicates.

## 12. Acceptance Criteria

### Scenario 1: Successful provisioning with pending link
**Given** I am authenticated as an Admin with permission `security:user:provision`  
**And** a Person exists in People with `personId` and email `john.doe@example.com`  
**When** I search Persons with `search=john.doe`  
**And** I select the Person result  
**And** I enter `idpSubject=idp|abc123` and keep the prefilled email `john.doe@example.com`  
**And** I leave `username` empty  
**And** I submit the Provision User form  
**Then** the frontend sends `POST /api/v1/security/users/provision` with `personId`, `idpSubject`, `email`, `status=ACTIVE`, and no `username` field (or `username=null` per implementation)  
**And** I see a success confirmation including `userId`, `personId`, `correlationId`, `eventEnqueued=true`  
**And** I see `linkStatus=PENDING` with messaging that linking completes asynchronously

### Scenario 2: Idempotent retry resolves existing user
**Given** I am authenticated as an Admin with permission `security:user:provision`  
**And** a Security User already exists for `idpSubject=idp|abc123`  
**When** I submit provisioning again with the same `idpSubject` and the same selected Person/email  
**Then** the frontend displays success  
**And** the response indicates `resolvedExisting=true`  
**And** the displayed `userId` is the existing user’s id

### Scenario 3: Person not found blocks provisioning
**Given** I am authenticated as an Admin with permission `security:user:provision`  
**When** I search Persons with a value that returns zero results  
**Then** I see an empty-state message indicating no matching person was found  
**And** the Provision User submit action remains disabled until a Person is selected

### Scenario 4: Backend validation error is shown with field mapping
**Given** I am authenticated as an Admin with permission `security:user:provision`  
**And** I have selected a Person  
**When** I submit the form with `idpSubject` empty  
**Then** the backend responds with `400` and an error envelope with `code=VALIDATION_FAILED` and `fieldErrors` including `field=idpSubject`  
**And** the frontend displays the error summary and highlights the `idpSubject` field with the returned message  
**And** my Person selection and other entered values remain for correction

### Scenario 5: Email mismatch is prevented (and handled if returned)
**Given** I am authenticated as an Admin with permission `security:user:provision`  
**And** I have selected a Person with email `john.doe@example.com`  
**Then** the email field is prefilled to `john.doe@example.com` and is not editable  
**When** I submit provisioning  
**Then** the request email matches the selected Person email case-insensitively  
**And** if the backend still returns `409 EMAIL_MISMATCH`, the UI shows “Email must match selected Person email” and offers a reset action

### Scenario 6: Link status refresh (manual, no polling)
**Given** I have successfully provisioned a user and see `userId=u1` and `linkStatus=PENDING`  
**When** I click “Refresh status”  
**Then** the frontend calls `GET /api/v1/security/users/u1`  
**And** the UI updates the displayed `linkStatus` to the returned value (`PENDING` or `LINKED` or `FAILED`)  
**And** the UI does not automatically poll for status updates

### Scenario 7: Unauthorized access is denied
**Given** I am authenticated as a user without permission `security:user:provision`  
**When** I navigate to Users → Provision User  
**Then** I receive an access denied experience (403 handling)  
**And** I cannot view the provisioning form or submit provisioning requests
