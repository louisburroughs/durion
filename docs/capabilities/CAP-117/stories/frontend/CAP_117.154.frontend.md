## 1. Story Header

**Title:** Users: Disable User (Soft Offboarding) Without Losing History (Frontend / Moqui)

**Primary Persona:** Admin (People/HR Admin)

**Persona Metadata**
- `primary_persona`: `Admin (People/HR Admin)`
- `canonical_persona`: `System Administrator`
- `persona_family`: `System Administration`
- `actor_type`: `human`
**Business Value:** Immediately revoke a user’s system access while preserving historical labor/timekeeping data for audit, reporting, and payroll continuity; ensure the disable action is deliberate, auditable, and consistent with People-domain lifecycle rules.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Admin  
- **I want** to disable (soft-offboard) a user account from the POS UI  
- **So that** the user cannot authenticate and cannot be selected for future work/schedules, while all historical records remain intact and all forced changes are auditable.

### In-scope
- Moqui screen flow to initiate **Disable User** for a target user/person.
- Confirmation UI (modal) and optional reason capture.
- Use backend-provided capability flags/options to render allowed disable options (UI must not infer policy). (DECISION-PEOPLE-013, DECISION-PEOPLE-024)
- Display resulting `User.status` and `Person`/employment status, effective timestamp, and last status change metadata if provided. (DECISION-PEOPLE-001, DECISION-PEOPLE-024)
- Handle People-standard error schema for 400/409 and standard 403/404/5xx. (DECISION-PEOPLE-018)
- Ensure disabled users are excluded by default from user pickers/lists **owned by this frontend** (with an explicit “include disabled” filter in admin list/search). (DECISION-PEOPLE-001)

### Out-of-scope
- Implementing authentication/session enforcement (Security domain); People provides status and emits downstream propagation. (DECISION-PEOPLE-001, DECISION-PEOPLE-002)
- Implementing saga retry/DLQ operations UI. (DECISION-PEOPLE-002)
- Termination (`TERMINATED`) workflow and irreversible offboarding. (DECISION-PEOPLE-001)
- Any WorkExec/ShopMgmt business logic for timers/schedules; UI only displays backend-reported outcomes if provided. (People boundary)

## 3. Actors & Stakeholders
- **Admin (actor):** Performs disable action.
- **People Service (system of record):** Owns User lifecycle status and offboarding semantics. (DECISION-PEOPLE-001)
- **Security Service (downstream):** Blocks authentication after disable (consumes status/events). (DECISION-PEOPLE-001, DECISION-PEOPLE-002)
- **Work Execution / Shop Management (downstream):** May stop timers/exclude disabled users; eventual consistency via saga. (DECISION-PEOPLE-002)
- **Auditors/Operations (stakeholders):** Need traceability of who disabled whom and why.

## 4. Preconditions & Dependencies
- Admin is authenticated in the frontend.
- Admin has authorization to disable users:
  - UI gating uses named permission **`people:user.disable`** and/or backend capability flag `canDisableUser`. (DECISION-PEOPLE-013)
- Target user exists and is in `ACTIVE` state at time of action. (DECISION-PEOPLE-001)
- Backend endpoints exist under People REST conventions:
  - User detail load endpoint returns status + capability flags/options. (DECISION-PEOPLE-021, DECISION-PEOPLE-024)
  - Disable action endpoint performs atomic local disable and triggers async propagation; returns updated status. (DECISION-PEOPLE-002, DECISION-PEOPLE-024)
- Frontend has a User Detail screen route capable of hosting the action (see UX Summary).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From **Users** list/search: select a user → open User Detail → click **Disable User**
- Direct deep link to user detail by `userId` (admin-only access still enforced)

### Screens to create/modify
1. **Users List/Search Screen** (create or modify)
   - Shows status badge (ACTIVE/DISABLED/TERMINATED).
   - Default filter excludes DISABLED/TERMINATED; provide “Include disabled/terminated” toggle.
2. **User Detail Screen** (create or modify)
   - Shows identity summary and current status.
   - Shows **Disable User** action only when allowed (permission/capability + status ACTIVE).
   - Shows last status change metadata if returned (disabledAt, disabledBy, reason).
3. **Disable User Confirmation Modal**
   - Explicit confirmation step (modal confirm).
   - Optional reason input (free text) and/or reason code picker if backend provides allowed values.
   - Optional disable options rendered only if backend returns `disableOptions[]`.

### Navigation context
- `People → Users → User List → User Detail`
- Post-success: remain on User Detail and refresh data (DECISION-PEOPLE-024)

### User workflows (happy + alternate paths)

**Happy path**
1. Admin opens User Detail for an ACTIVE user.
2. Admin clicks **Disable User**.
3. UI shows confirmation modal with summary of effects:
   - “Access is revoked immediately; historical records remain.”
   - “Downstream cleanup may complete asynchronously.”
4. Admin optionally selects a disable option (if provided) and optionally enters a reason.
5. Admin confirms.
6. UI shows success toast, closes modal, refreshes User Detail; status shows `DISABLED` with effective timestamp.

**Alternate paths**
- User already disabled/terminated: action hidden; status shown.
- Backend returns 409 conflict (already disabled / state changed): UI shows conflict message and refreshes detail.
- Backend returns 403: UI shows access denied and does not change state.

## 6. Functional Behavior

### Triggers
- Admin clicks **Disable User** on User Detail.

### UI actions
- Open modal dialog:
  - Requires explicit confirmation via a modal confirm button (no typed confirmation required by default). (DECISION-PEOPLE-024)
  - Show optional “Reason” input:
    - If backend provides `reasonCodes[]` and indicates required, show picker and require selection.
    - Otherwise allow optional free-text `reasonText` (non-blocking).
  - Show optional disable options:
    - Render only if backend returns `disableOptions[]` (policy-driven).
    - If no options returned, submit a minimal disable request.

- Submit behavior:
  - Disable confirm button and show in-flight indicator.
  - Prevent double-submit.

### State changes (frontend)
- On success:
  - Close modal.
  - Re-fetch user detail and re-render from server state (do not locally “assume” status). (DECISION-PEOPLE-002)
  - Hide disable action; show DISABLED badge and effective timestamp.
- On failure:
  - Keep modal open if failure is 400 field errors; render field errors inline.
  - Close modal only if user cancels; otherwise allow retry after error.

### Service interactions
- Load user detail on screen entry and after successful disable.
- Call disable action endpoint with payload including:
  - `userId` (path param)
  - optional `statusReasonCode` and/or `reasonText` (if supported)
  - optional `disableOption` (one of backend-provided options)
- Do **not** send timecard/session identifiers; identity/session is derived server-side. (DECISION-PEOPLE-022)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Disable action is only available when target `User.status == ACTIVE`. (DECISION-PEOPLE-001)
- Confirmation is required (modal confirm). (DECISION-PEOPLE-024)
- Reason handling:
  - `statusReasonCode` is **optional unless backend indicates required** (capability/field metadata). (DECISION-PEOPLE-024)
  - If backend returns allowed codes, UI must validate selection is one of them.
- UI must not implement policy about ending assignments/stopping timers; it only submits backend-allowed options and displays backend outcomes if provided. (DECISION-PEOPLE-013)

### Enable/disable rules
- **Disable User** button visible/enabled only when:
  - current user has `people:user.disable` **and/or** `canDisableUser=true` from detail payload, AND (DECISION-PEOPLE-013)
  - target user status is `ACTIVE`. (DECISION-PEOPLE-001)

### Visibility rules
- Disabled users:
  - excluded by default from user pickers and operational lists in this frontend.
  - visible in admin list/search when “Include disabled” is enabled.
- `tenantId` must not be displayed by default. (DECISION-PEOPLE-019)

### Error messaging expectations (mapped to DECISION-PEOPLE-018)
- 400: show `message` and map `fieldErrors[]` to fields (reason/options).
- 403: “You don’t have permission to disable users.”
- 404: “User not found or no longer available.”
- 409: show conflict `message` and prompt “Refresh to see latest status”; auto-refresh after acknowledgement.
- 5xx/network: show generic error and allow retry; do not change local state.

## 8. Data Requirements

### Entities involved (frontend view)
- `User` (People SoR for lifecycle status)
- `Person` / `EmployeeProfile` (employment status display; exact field name depends on API shape)
- Optional: `Audit`/status history projection (read-only) if provided by backend

### Fields (types, required, defaults)

**User detail (read-only)**
- `userId` (string/UUID, required)
- `username` (string, required)
- `status` (enum: `ACTIVE` | `DISABLED` | `TERMINATED`, required) (DECISION-PEOPLE-001)
- `statusEffectiveAt` (instant/datetime, required when status != ACTIVE)
- `statusReasonCode` (string, optional)
- `personId` (string/UUID, required) (DECISION-PEOPLE-012)
- `canDisableUser` (boolean, optional but recommended) (DECISION-PEOPLE-013, DECISION-PEOPLE-024)
- `disableOptions[]` (array of option objects/strings, optional) (DECISION-PEOPLE-024)
- `lastUpdatedStamp` (datetime, optional; used if backend requires optimistic concurrency) (DECISION-PEOPLE-017)

**Person/Employment (read-only)**
- `personId` (string/UUID, required)
- `displayName` or `legalName` (string, required for display; prefer `displayName` if provided) (DECISION-PEOPLE-012)
- `employmentStatus` or `status` (enum aligned with user lifecycle, required) (DECISION-PEOPLE-001)

**Disable action inputs (editable in modal)**
- `statusReasonCode` (string, optional unless backend indicates required)
- `reasonText` (string, optional)
- `disableOption` (string/enum, optional; must be one of `disableOptions[]` if provided)

### Read-only vs editable by state/role
- When target user is `DISABLED` or `TERMINATED`, disable action is not available; all fields are read-only in this story scope.
- When current user lacks permission/capability, disable action is not rendered.

### Derived/calculated fields
- “Effective status since” = formatted `statusEffectiveAt` displayed in user timezone if available, else location timezone (see NFR). (DECISION-PEOPLE-015)

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation may wrap these REST calls via screen transitions/services; the frontend contract below is the required behavior and shape.

### Load/view calls
- **GET** `/rest/api/v1/people/users/{userId}`
  - Returns:
    - `user` object (fields above) and linked `person` summary
    - capability fields: `canDisableUser`, `disableOptions[]` (optional but recommended)
  - List conventions not applicable (detail endpoint). (DECISION-PEOPLE-021)

### Create/update calls
- **POST** `/rest/api/v1/people/users/{userId}/disable`
  - Request body (minimum):
    - `statusReasonCode?`
    - `reasonText?`
    - `disableOption?`
    - `lastUpdatedStamp?` (only if backend enforces optimistic concurrency for this resource) (DECISION-PEOPLE-017)
  - Response:
    - Updated `user` status fields (status, statusEffectiveAt, statusReasonCode)
    - Optional `warnings[]` (non-blocking) if backend uses warnings pattern
    - Optional `downstreamStatus` object if backend chooses to expose saga progress (UI must treat as informational only). (DECISION-PEOPLE-002)

### Submit/transition calls
- Moqui screen transition should:
  - call disable endpoint/service
  - on success, redirect/refresh to same User Detail screen (DECISION-PEOPLE-024)

### Error handling expectations (DECISION-PEOPLE-018)
- **400**:
  ```json
  { "errorCode":"...", "message":"...", "fieldErrors":[{"field":"statusReasonCode","message":"..."}] }
  ```
- **409**:
  ```json
  { "errorCode":"...", "message":"...", "blockingIds":["userId"], "details":{...} }
  ```
- UI must surface `message` and map `fieldErrors` to inputs; for 409, prompt refresh and then reload detail.

## 10. State Model & Transitions

### Allowed states (authoritative from People domain)
- `ACTIVE`
- `DISABLED` (reversible; target of this story)
- `TERMINATED` (irreversible; not set by this story) (DECISION-PEOPLE-001)

### Role-based transitions
- `ACTIVE → DISABLED`: allowed when user has permission `people:user.disable` and backend returns `canDisableUser=true` (if provided). (DECISION-PEOPLE-013, DECISION-PEOPLE-024)
- Other transitions are out of scope.

### UI behavior per state
- `ACTIVE`:
  - Show Disable action if authorized.
- `DISABLED`:
  - Hide Disable action.
  - Show status metadata and reason (if present).
  - Show informational note: “Access revoked; downstream cleanup may be in progress.”
- `TERMINATED`:
  - Hide Disable action; show terminated badge; read-only.

## 11. Alternate / Error Flows

### Validation failures (400)
- Missing required reason code (only if backend indicates required and returns 400 otherwise):
  - UI shows inline error on reason field; modal remains open.
- Invalid disable option:
  - UI should prevent selection by only rendering backend-provided options; if server still returns 400, show error and keep modal open.

### Concurrency conflicts (409)
- If another admin disables the user between load and submit:
  - backend returns 409 (or equivalent conflict)
  - UI shows conflict message and reloads detail; disable action disappears.

### Unauthorized access (403)
- If user lacks permission:
  - Disable action not rendered.
  - If attempted via direct call, show access denied; no UI state change.

### Empty states (404 / load failure)
- If user detail returns 404:
  - show not-found state with link back to Users list.
- If network/5xx:
  - show error state with retry; preserve last successful data if available.

## 12. Acceptance Criteria

### Scenario 1: Admin disables an active user successfully
**Given** an Admin with `people:user.disable` permission is viewing an ACTIVE user detail page  
**And** the detail payload indicates the action is allowed (`canDisableUser=true` when provided)  
**When** the Admin clicks “Disable User”, confirms the action, and submits  
**Then** the frontend calls `POST /rest/api/v1/people/users/{userId}/disable` with any selected `disableOption` and optional reason fields  
**And** on success the UI refreshes the user detail  
**And** the UI displays `status = DISABLED` and `statusEffectiveAt` from the backend response  
**And** the “Disable User” action is no longer available for that user.

### Scenario 2: User is already disabled
**Given** an Admin is viewing a user whose status is `DISABLED`  
**When** the page renders  
**Then** the UI does not offer the “Disable User” action  
**And** the UI shows the disabled status and effective timestamp.

### Scenario 3: Permission denied
**Given** a signed-in user without `people:user.disable` attempts to disable an ACTIVE user  
**When** the disable request returns HTTP 403  
**Then** the frontend displays an “Access Denied” error  
**And** no status fields in the UI are changed  
**And** the disable action remains unavailable.

### Scenario 4: User not found
**Given** an Admin navigates to a user detail route for a `userId` that does not exist  
**When** the frontend loads the user detail and receives HTTP 404  
**Then** the UI shows a “User not found” empty state  
**And** provides navigation back to the Users list.

### Scenario 5: Conflict on disable due to concurrent change
**Given** an Admin has the disable confirmation modal open for an ACTIVE user  
**And** another admin disables that user before the first admin submits  
**When** the first admin submits and the backend returns HTTP 409 with an error message  
**Then** the UI shows the conflict message  
**And** the UI refreshes the user detail  
**And** the UI reflects the latest server status (DISABLED) and hides the disable action.

### Scenario 6: Disabled users excluded from operational pickers by default
**Given** an Admin opens a Users list/search screen in this frontend  
**When** the screen loads with default filters  
**Then** users with status `DISABLED` are not shown by default  
**And** when the Admin enables “Include disabled”, disabled users are included and clearly labeled.
