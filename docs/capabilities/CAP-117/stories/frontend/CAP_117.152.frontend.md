## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] People: Create/Update Employee Profile (pos-people)

### Primary Persona
HR Administrator (HR user)

### Business Value
Maintain accurate employee profiles (identity, status, contact info) for operational directory use and downstream consistency in work execution and shop management, with auditability and deterministic duplicate detection feedback.

---

## 2. Story Intent

### As a / I want / So that
**As an** HR Administrator,  
**I want** to create and update employee profiles from the POS frontend,  
**so that** employee identity and employment status are accurate, auditable, and available to downstream systems.

### In-scope
- Moqui/Vue/Quasar frontend screens to:
  - Create a new Employee Profile
  - Edit an existing Employee Profile
  - Render duplicate warnings and conflict errors returned by backend
  - Display audit metadata (created/updated timestamps; actor if available)
- Field-level validation aligned to People domain rules (required fields, date rules, enum constraints)
- Handling of backend responses: 201/200 success, 400 validation, 403 forbidden, 404 not found, 409 conflict, warnings payload
- Optimistic concurrency handling when backend provides `lastUpdatedStamp` (or equivalent) (Decision ID: DECISION-PEOPLE-017)

### Out-of-scope
- Role assignment, user disable/termination workflows, location assignments
- Time entry approval, breaks, scheduling/dispatch
- Implementing downstream consumers (workexec/shopmgr); only ensure data is captured consistently
- Defining backend entities/services beyond calling existing endpoints/contracts

---

## 3. Actors & Stakeholders
- **HR Administrator (primary actor):** creates/updates employee profiles.
- **Store/Operations Managers (stakeholder):** consume accurate employee status/name in rosters (indirect).
- **Downstream systems (stakeholders):** workexec, shopmgr consume employee identity/status.
- **Audit/Compliance (stakeholder):** expects traceability of changes.

---

## 4. Preconditions & Dependencies
- User is authenticated in the POS frontend.
- User is authorized for employee profile operations:
  - Create requires `people.employee.create`
  - Update requires `people.employee.update`
- Backend provides People REST endpoints under `/rest/api/v1/people` conventions (Decision ID: DECISION-PEOPLE-021):
  - Create: `POST /rest/api/v1/people/employees`
  - Update: `PUT /rest/api/v1/people/employees/{employeeId}`
  - Load: `GET /rest/api/v1/people/employees/{employeeId}`
- Backend returns:
  - `409 Conflict` on high-confidence duplicates (Decision ID: DECISION-PEOPLE-008, DECISION-PEOPLE-018)
  - `warnings[]` payload on non-blocking issues (including ambiguous duplicates) (Decision ID: DECISION-PEOPLE-008)
  - Audit fields in response (`createdAt`, `updatedAt`; optionally actor identifiers)
  - Concurrency token when supported (prefer `lastUpdatedStamp`) and returns 409 on mismatch (Decision ID: DECISION-PEOPLE-017)
- `tenantId` is treated as sensitive and must not be displayed by default (Decision ID: DECISION-PEOPLE-019)

## 7. Business Rules (Translated to UI Behavior)

### Validation
Client-side validations (mirror backend; backend remains authoritative):
- Required on create (and required to remain present on update):
  - `legalName` (non-empty)
  - `employeeNumber` (non-empty)
  - `status` (enum; required)
  - `hireDate` (valid date)
- Allowed status values (Decision ID: DECISION-PEOPLE-025 + backend reference):
  - `ACTIVE | ON_LEAVE | SUSPENDED | TERMINATED`
- Date rule:
  - If `terminationDate` provided, must be **>=** `hireDate`
- Email normalization:
  - Trim whitespace; lowercase before submit (safe normalization; aligns with backend expectations)
- Phone normalization:
  - Trim whitespace only; do **not** attempt E.164 formatting client-side unless repo has an established formatter (see Open Questions). Backend remains authoritative for E.164 normalization.

### Enable/disable rules
- Save disabled when:
  - Required fields missing/invalid
  - Request in-flight
- Status default on create:
  - Default to `ACTIVE` (Decision ID: DECISION-PEOPLE-025)
- Terminated edit rules:
  - If loaded employee `status=TERMINATED`, default UI behavior is **read-only** unless backend indicates edit capability (Decision ID: DECISION-PEOPLE-025, DECISION-PEOPLE-013).
  - Implementation: if response includes capability flag(s) (e.g., `canEditTerminated=true` or `editableFields[]`), honor them; otherwise lock editing and show explanation.

### Visibility rules
- Show warning panel if backend returns `warnings[]` (non-blocking).
- Show field-level errors when backend returns 400 with `fieldErrors`.
- Show blocking banner on 409 conflict.
- Show read-only audit fields when available: `createdAt`, `updatedAt` (and createdBy/updatedBy if returned).
- Do not display `tenantId` by default (Decision ID: DECISION-PEOPLE-019).

### Error messaging expectations
- 400: “Please correct highlighted fields.” + per-field messages from backend.
- 409 (duplicate/conflict): show backend `message`; if `fieldErrors` or `details` identify fields, highlight those.
- 409 (concurrency): “This employee was updated by someone else. Reload to continue.” Provide Reload action.
- 403: “You don’t have permission to manage employee profiles.”
- 404: “Employee not found.”

## 9. Service Contracts (Frontend Perspective)

All endpoints below follow People REST conventions (Decision ID: DECISION-PEOPLE-021) and error schema (Decision ID: DECISION-PEOPLE-018).

### Load/view calls
- **Get Employee Profile**
  - `GET /rest/api/v1/people/employees/{employeeId}`
  - Success 200:
    ```json
    {
      "employeeId": "uuid",
      "legalName": "string",
      "preferredName": "string|null",
      "employeeNumber": "string",
      "status": "ACTIVE|ON_LEAVE|SUSPENDED|TERMINATED",
      "hireDate": "YYYY-MM-DD",
      "terminationDate": "YYYY-MM-DD|null",
      "contactInfo": { "...": "..." },
      "createdAt": "instant",
      "updatedAt": "instant",
      "lastUpdatedStamp": "instant",
      "warnings": [],
      "capabilities": { "canEdit": true, "canEditTerminated": false }
    }
    ```
  - Errors:
    - 403 forbidden
    - 404 not found
    - 401 unauthorized (if session expired)

### Create/update calls
- **Create**
  - `POST /rest/api/v1/people/employees`
  - Request body: all modifiable fields excluding `employeeId`, audit fields, and capabilities.
  - Response:
    - 201 created with full profile payload
    - May include `warnings[]` (non-blocking) (Decision ID: DECISION-PEOPLE-008)
  - Errors:
    - 400 validation error:
      ```json
      { "errorCode": "VALIDATION_ERROR", "message": "…", "fieldErrors": { "legalName": "Required" } }
      ```
    - 403 forbidden
    - 409 conflict (duplicate):
      ```json
      { "errorCode": "EMPLOYEE_DUPLICATE", "message": "…", "details": { "fields": ["employeeNumber"] } }
      ```

- **Update**
  - `PUT /rest/api/v1/people/employees/{employeeId}`
  - Request body: modifiable fields + `lastUpdatedStamp` if provided on load (Decision ID: DECISION-PEOPLE-017)
  - Response:
    - 200 ok with full updated profile payload
    - May include `warnings[]`
  - Errors:
    - 400 validation error (with `fieldErrors`)
    - 403 forbidden
    - 404 not found
    - 409 conflict:
      - Duplicate conflict (as above), or
      - Concurrency conflict (stale `lastUpdatedStamp`):
        ```json
        { "errorCode": "CONCURRENCY_CONFLICT", "message": "…", "details": { "expectedLastUpdatedStamp": "…" } }
        ```

### Submit/transition calls
- None (status changes are performed via Update in this story; no separate transition endpoints are assumed).

### Error handling expectations
- Parse and render errors per DECISION-PEOPLE-018:
  - 400: show summary + map `fieldErrors` to inputs; preserve user-entered values.
  - 409: show blocking banner; if `errorCode=CONCURRENCY_CONFLICT`, offer Reload action; otherwise treat as duplicate/conflict and highlight implicated fields when possible.
- If response includes request/correlation ID headers, surface them in an expandable “Details” section for support (observability; see section 13).

## 11. Alternate / Error Flows

### Validation failures (400)
- Backend returns 400 with `fieldErrors`.
- UI maps errors to fields and shows summary banner.
- Form remains editable; save re-enabled after response.

### Duplicate conflicts (409)
- UI shows blocking banner with backend message.
- If backend indicates which field collided (via `fieldErrors`, `details.fields`, or similar), highlight those fields; otherwise highlight `employeeNumber` and `contactInfo.primaryEmail` as likely keys (do not invent match details).

### Concurrency conflicts (409)
- If backend returns 409 with `errorCode=CONCURRENCY_CONFLICT` (or equivalent):
  - UI shows “updated elsewhere” message.
  - Provide actions:
    - **Reload**: re-fetch profile and replace form with latest server state.
    - **Copy my changes** (optional): preserve current form values in a temporary buffer so user can re-apply after reload (UI-only; no auto-merge).
  - Do not auto-resubmit without user confirmation.

### Unauthorized access (403)
- On load or save: show permission error and disable editing; provide navigation away.

### Empty states
- Create screen: empty form with required-field indicators; status defaults to `ACTIVE`.
- Edit screen: while loading, show loading state; if 404, show not-found state.

## 12. Acceptance Criteria

### Scenario 1: Create employee profile successfully (default ACTIVE)
**Given** I am authenticated as a user with permission `people.employee.create`  
**When** I navigate to the Create Employee Profile screen  
**Then** the `status` field defaults to `ACTIVE`  
**When** I enter `legalName`, `employeeNumber`, and `hireDate` with valid values  
**And** I click Save  
**Then** the frontend sends `POST /rest/api/v1/people/employees`  
**And** I see a success confirmation  
**And** the form displays the returned `employeeId` and audit timestamps if provided

### Scenario 2: Update employee profile successfully with optimistic concurrency
**Given** I am authenticated as a user with permission `people.employee.update`  
**And** an employee exists with `employeeId = E123`  
**And** I have loaded the edit screen and received `lastUpdatedStamp = T1`  
**When** I change `preferredName`  
**And** I click Save  
**Then** the frontend sends `PUT /rest/api/v1/people/employees/E123` including `lastUpdatedStamp = T1`  
**And** I see a success confirmation  
**And** the displayed `updatedAt` value refreshes if provided

### Scenario 3: Block create on high-confidence duplicate (409)
**Given** I am authenticated as a user with permission `people.employee.create`  
**And** the backend would detect an existing employee with the same `employeeNumber` or `contactInfo.primaryEmail`  
**When** I attempt to create an employee profile with that same value  
**Then** the save fails with HTTP 409  
**And** I see a blocking duplicate/conflict message from the backend  
**And** no navigation occurs away from the create form

### Scenario 4: Show non-blocking warnings when backend returns warnings
**Given** I am authenticated as a user with permission `people.employee.create`  
**And** the backend returns `warnings[]` for non-blocking issues  
**When** I create an employee profile and the response includes `warnings[]`  
**Then** the employee profile is created successfully  
**And** I see a non-blocking warning panel displaying the warning code(s) and message(s) returned by the backend

### Scenario 5: Client-side validation prevents submit for missing required fields
**Given** I am authenticated as a user with permission `people.employee.create`  
**When** I leave `legalName` empty  
**And** I click Save  
**Then** I see a validation error for `legalName`  
**And** no create request is sent until the field is corrected

### Scenario 6: Date validation for termination date
**Given** I am editing an employee profile  
**When** I set `terminationDate` to a date earlier than `hireDate`  
**Then** I see a validation error indicating termination date must be on or after hire date  
**And** I cannot successfully save until corrected

### Scenario 7: Concurrency conflict prompts reload
**Given** I am authenticated as a user with permission `people.employee.update`  
**And** I loaded employee `E123` with `lastUpdatedStamp = T1`  
**And** another user updates `E123` so the server now has `lastUpdatedStamp = T2`  
**When** I attempt to save my changes with `lastUpdatedStamp = T1`  
**Then** the backend responds with HTTP 409 and a concurrency error code  
**And** the UI prompts me to reload the latest employee profile  
**And** the UI does not silently overwrite the other user’s changes

### Scenario 8: Terminated employee is read-only by default
**Given** I am authenticated as a user with permission `people.employee.update`  
**And** I load an employee profile with `status = TERMINATED`  
**And** the response does not include a capability indicating terminated edits are allowed  
**Then** the form fields are read-only  
**And** the Save action is disabled  
**And** the UI explains that terminated employees are read-only by default

### Scenario 9: Forbidden access
**Given** I am authenticated without `people.employee.create`  
**When** I navigate to the Create Employee Profile screen  
**Then** I see an access denied message  
**And** I cannot submit a create request
