## Issue Body

## Title
[FRONTEND] [STORY] Accounting Event Ingestion Monitoring: Idempotency Outcomes, Quarantine Visibility, and Async Retry

## Primary Persona
Accounting Ops (operational user monitoring and resolving ingestion integrity issues)

## Business Value
Provide operational visibility into accounting event ingestion outcomes (processed/rejected/quarantined), including idempotency outcomes (new/duplicate/conflict), and enable safe, auditable async retries—reducing time-to-diagnose ingestion issues while protecting financial integrity and auditability.

---

# 2. Story Intent

## As a / I want / So that
- **As an** Accounting Ops user (and Auditor in read-only mode)  
- **I want** to search and inspect accounting event ingestion records (including idempotency outcomes and errors) and trigger safe async retries when permitted  
- **So that** duplicate submissions do not create duplicate postings, conflicts are visible and traceable, and ingestion failures can be retried without policy inference or data leakage.

## In-scope
- Moqui screens under Accounting for:
  - List/search ingestion records (`AccountingEventIngestionRecord`) by identifiers and status
  - View ingestion record detail including:
    - `processingStatus` (`PROCESSED|REJECTED|QUARANTINED`)
    - `idempotencyOutcome` (`NEW|DUPLICATE_IGNORED|DUPLICATE_CONFLICT`)
    - error code/message
    - posting references (`journalEntryId` primary; `ledgerTransactionId` secondary if present)
    - curated `payloadSummary` (default) and raw payload JSON only when permitted
  - Trigger **async retry** for eligible ingestion records (backend-owned eligibility), with required justification and job status polling
- Permission-gated UI entry points and actions per Accounting domain rules (**Decision AD-013**)
- Client-side UUIDv7 validation for identifier filters (**Decision AD-006**)
- Standard error handling mapping for 400/401/403/404/409/5xx and safe messaging (no existence leakage)

## Out-of-scope
- Implementing backend ingestion/idempotency, posting, DLQ/quarantine mechanics, or retention policies (backend-owned)
- Any mutation of source events or payloads (immutable)
- Any “conflict resolution workflow/state machine” beyond what backend exposes via ingestion record fields (no separate conflict entity in this story)
- Reversal/compensating posting workflows
- Auto-retry policies or scheduling (UI only triggers manual retry when permitted)

---

# 3. Actors & Stakeholders
- **Accounting Ops**: monitors ingestion, triages quarantined/rejected records, initiates retries with justification.
- **Auditor**: reviews ingestion outcomes and traceability; read-only; cannot retry.
- **SRE/Support**: uses ingestion detail identifiers for incident triage; may have view access depending on org policy.
- **Upstream event producers (Billing/Payment/etc.)**: indirectly impacted; ingestion errors/conflicts indicate producer issues.

- `receivedAtFrom` / `receivedAtTo` (inclusive date-time range; default filter basis is `receivedAt` per **Decision AD-007**)

- Sorting: stable `orderBy` (default `-receivedAt`)

Results table columns (minimum):
- `receivedAt`
- `eventType`
- `processingStatus`
- `idempotencyOutcome`
- `eventId`
- Primary domain key if present (display one of: `invoiceId` / `paymentId` / `refundId`; do not assume all exist)
- `journalEntryId` (if present)
- Action: View (navigates to detail by `ingestionId`)

Row affordances:
- Copy-to-clipboard for `eventId` and `ingestionId`
- Visual indicator for `QUARANTINED` and `DUPLICATE_CONFLICT` (text badge)

### Ingestion Detail
On load:
- Fetch detail by `ingestionId`
- Render sections:
  - Summary: identifiers + statuses + timestamps
  - Errors: `errorCode`, `errorMessage` (if present)
  - Posting references: `journalEntryId` (primary), `ledgerTransactionId` (secondary)
  - Payload:
    - Always show curated `payloadSummary` (if present)
    - Show raw payload JSON only if user has `accounting:events:view-payload` and backend provides it

Actions:
- **Retry ingestion** (button)
  - Visible only if user has `accounting:events:retry`
  - Enabled only when backend indicates retry is allowed by returning an `isRetryEligible=true` flag OR when `processingStatus != PROCESSED` (fallback)  
    - If backend does not provide `isRetryEligible`, UI must still rely on backend enforcement and handle 409/422 gracefully.
  - Requires justification input (>= 10 chars) before submit
  - On submit: call retry endpoint; show returned `jobId`; start polling status; disable button while in-flight

## State changes (frontend-observable)
- Ingestion record status may change after retry:
  - `QUARANTINED|REJECTED` → (after retry) `PROCESSED` or remain `QUARANTINED/REJECTED` with updated error fields
- Idempotency outcomes are backend-owned; UI displays without reinterpretation (**Decision AD-007**)

## Service interactions
- Read:
  - `/accounting/ingestion/list`
  - `/accounting/ingestion/detail`
- Command:
  - `/accounting/ingestion/retry` (async) with justification and identifiers
  - `/accounting/ingestion/retryStatus` (polling)

# 7. Business Rules (Translated to UI Behavior)

## Validation
- UUIDv7 fields (`ingestionId`, `eventId`) must validate as UUID format client-side (**Decision AD-006**):
  - If invalid: block submit and show inline error “Enter a valid UUID”
- Date range validation:
  - `receivedAtFrom <= receivedAtTo` else inline error
- Retry justification:
  - Required, minimum 10 characters (**Decision AD-013**)

## Enable/disable rules
- Entry point visibility:
  - Hide Accounting → Event Ingestion menu item unless user has `accounting:events:view` (deny-by-default)
- Retry button:
  - Hidden without `accounting:events:retry`
  - Disabled while retry request is in-flight or while retry job is `QUEUED/PROCESSING`
- Raw payload section:
  - Hidden unless user has `accounting:events:view-payload`
  - If hidden, UI must not fetch raw payload when possible (prefer backend to omit it unless permitted)

## Visibility rules
- Always show `payloadSummary` if provided (safe default view) (**Decision AD-009**)
- Show prominent banner when:
  - `processingStatus=QUARANTINED` OR `idempotencyOutcome=DUPLICATE_CONFLICT`
  - Banner text must be non-speculative: “This record is quarantined by the backend. Review error details and escalate if needed.”
- Show “Posting not created” when `journalEntryId` is null (do not infer why)

## Error messaging expectations
- 409 Conflict:
  - Show banner: “Conflict: the record state changed or the operation is not allowed. Refresh and try again.”
  - If backend returns `errorCode` indicating duplicate conflict/quarantine, display it verbatim and suggest filtering by `eventId`.
- 403/401:
  - Show access denied without confirming record existence (consistent messaging)
- 404:
  - Show “Record not found” (safe)
- 422/400 validation:
  - Map `details` to inline field errors when keys match known fields; otherwise show generic validation banner

# 9. Service Contracts (Frontend Perspective)

## Load/view calls

### `GET /accounting/ingestion/list`
Request (query params; all optional unless noted):
- `ingestionId` (UUIDv7)
- `eventId` (UUIDv7)
- `eventType` (string)
- `processingStatus` (enum)
- `idempotencyOutcome` (enum)
- `receivedAtFrom` (datetime)
- `receivedAtTo` (datetime)
- `pageIndex` (int, default 0)
- `pageSize` (int, default 25)
- `orderBy` (string, default `-receivedAt`)

Response (shape backend-owned; UI expects):
- `data[]`: ingestion record summaries (subset of fields)
- `pageIndex`, `pageSize`, `totalCount`

### `GET /accounting/ingestion/detail?ingestionId=...`
Request:
- `ingestionId` (UUIDv7, required)

Response:
- Full ingestion record detail including errors, posting refs, payloadSummary, and optionally raw payload (permission-gated)

## Create/update calls
- none (ingestion records are immutable read models)

## Submit/transition calls

### `POST /accounting/ingestion/retry`
Request body (minimum; backend authoritative):
- `ingestionId` (UUIDv7, required)
- `justification` (string, required, min 10 chars) (**Decision AD-013**)

Response:
- `jobId` (UUIDv7/string, required)
- Optional: `acceptedAt`, `estimatedWaitMs`

### `GET /accounting/ingestion/retryStatus?jobId=...`
Request:
- `jobId` (UUIDv7/string, required)

Response (backend-owned):
- `jobId`
- `status` (e.g., `QUEUED|PROCESSING|SUCCEEDED|FAILED`)
- Optional: `message`, `errorCode`
- Optional: `resultIngestionId` (if retry created a new record) or `updatedIngestionId` (if same)

## Error handling expectations
- Canonical error schema (**Decision AD-013**):
  - `{ errorCode, message, details? }`
- UI mappings:
  - 400/422: validation banner + inline mapping from `details`
  - 401: route to login
  - 403: access denied (no existence leakage)
  - 404: not found
  - 409: conflict banner + refresh suggestion
  - 5xx/timeout: retryable banner; preserve filters and current view state
- Payload safety (**Decision AD-009**):
  - Never log raw payloads
  - Render JSON as text (escaped), with truncation/lazy rendering for large payloads

# 10. State Model & Transitions

## Allowed states

### Ingestion `processingStatus` (backend authoritative) (**Decision AD-007**)
- `PROCESSED`
- `REJECTED`
- `QUARANTINED`

UI behavior per state:
- PROCESSED:
  - Show success badge
  - Show posting refs if present
  - Retry generally disabled/hidden (backend may still allow; UI should default to disabled unless `isRetryEligible=true`)
- REJECTED:
  - Show rejected badge
  - Show error code/message
  - Retry available only if permitted and backend allows
- QUARANTINED:
  - Show prominent quarantine banner
  - Show error code/message and idempotency outcome
  - Retry available only if permitted and backend allows

### Ingestion `idempotencyOutcome` (backend authoritative) (**Decision AD-007**)
- `NEW`
- `DUPLICATE_IGNORED`
- `DUPLICATE_CONFLICT`

UI behavior per outcome:
- NEW: normal display
- DUPLICATE_IGNORED: show “Duplicate ignored” informational badge; do not imply re-posting
- DUPLICATE_CONFLICT: show “Duplicate conflict” warning badge; typically paired with `QUARANTINED`

## Role-based transitions
- No UI-managed state transitions for ingestion records
- Retry action is role/permission gated:
  - Allowed only with `accounting:events:retry` (**Decision AD-013**)
  - Auditors are read-only (no retry)

# 11. Alternate / Error Flows

## Validation failures
- Invalid UUID in `eventId`/`ingestionId` filter:
  - Prevent search submit; show inline error
- Invalid date range:
  - Prevent submit; show inline error
- Retry justification too short:
  - Disable submit; show inline error

## Concurrency conflicts
- Retry requested while backend already processing:
  - Backend may return 409; UI shows “Already processing or not eligible” and refreshes detail

## Unauthorized access
- User without `accounting:events:view`:
  - Menu entry hidden
  - Direct URL access returns access denied screen; do not show whether record exists

## Empty states
- List returns 0 results:
  - Show “No ingestion records found” with “Clear filters”
- Detail fetch 404:
  - Show “Record not found” with link back to list

## Large payload rendering
- If `payloadSummary` or raw payload is large:
  - UI collapses by default and renders lazily
  - Provide copy-to-clipboard; avoid full DOM rendering until expanded

# 12. Acceptance Criteria

## Scenario 1: View ingestion list with filters and pagination
**Given** I am an authenticated user with permission `accounting:events:view`  
**When** I open Accounting Event Ingestion list  
**Then** the UI requests `GET /accounting/ingestion/list` with `pageIndex` and `pageSize`  
**And** I can filter by `eventId` and `processingStatus`  
**And** the results show `receivedAt`, `eventType`, `processingStatus`, `idempotencyOutcome`, and `eventId`.

## Scenario 2: Client-side UUID validation blocks invalid searches
**Given** I am on the ingestion list screen  
**When** I enter an invalid UUID into the `eventId` filter and submit  
**Then** the UI blocks the request  
**And** shows an inline error indicating a valid UUID is required.

## Scenario 3: Ingestion detail shows quarantine/conflict indicators
**Given** an ingestion record exists with `processingStatus = QUARANTINED` and `idempotencyOutcome = DUPLICATE_CONFLICT`  
**And** I have permission `accounting:events:view`  
**When** I open the ingestion detail by `ingestionId`  
**Then** the UI displays a quarantine banner  
**And** displays `errorCode` and `errorMessage` if present  
**And** displays `journalEntryId` only if provided (otherwise shows “Posting not created”).

## Scenario 4: Raw payload is permission-gated
**Given** an ingestion record has raw payload available from backend  
**And** I have permission `accounting:events:view` but do not have `accounting:events:view-payload`  
**When** I view ingestion detail  
**Then** I can see `payloadSummary` if provided  
**And** I do not see raw payload JSON  
**And** the UI does not display or log raw payload content.

## Scenario 5: Authorized user can submit async retry with justification
**Given** I have permissions `accounting:events:view` and `accounting:events:retry`  
**And** an ingestion record exists that backend allows to be retried  
**When** I click “Retry ingestion”, enter a justification of at least 10 characters, and confirm  
**Then** the UI calls `POST /accounting/ingestion/retry` with `ingestionId` and `justification`  
**And** the UI displays the returned `jobId`  
**And** the UI polls `GET /accounting/ingestion/retryStatus?jobId=...` until terminal status  
**And** the UI refreshes the ingestion detail after completion.

## Scenario 6: Unauthorized user cannot access ingestion screens
**Given** I am authenticated but lack permission `accounting:events:view`  
**When** I navigate directly to the ingestion list or detail URL  
**Then** I see an access denied experience  
**And** no ingestion record data is displayed.

## Scenario 7: Backend validation errors map to UI errors
**Given** I have retry permission  
**When** I submit retry with an empty or too-short justification  
**Then** the UI shows an inline validation error (client-side)  
**And** if the backend still returns a validation error, the UI shows the backend `errorCode` and maps `details` to the justification field.
