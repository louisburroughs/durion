## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Review `InvoiceAdjusted` / `CreditMemoIssued` Ingestion Records and Navigate to Posting References

### Primary Persona
Accounting Ops Specialist (secondary: Auditor read-only; Accounting Manager oversight)

### Business Value
Provide an operational Moqui UI to triage and trace ingestion outcomes for invoice adjustments and credit memos, enabling finance to confirm processing status, investigate rejections/quarantine/duplicate conflicts, and navigate to authoritative posting references (journal entries) and related invoice context for auditability.

---

## 2. Story Intent

### As a / I want / So that
**As an** Accounting Ops Specialist,  
**I want** to list and view ingestion records for `InvoiceAdjusted` and `CreditMemoIssued` events (including processing status, idempotency outcome, errors, and posting references),  
**so that** I can confirm whether accounting ingestion/posting succeeded, investigate exceptions (rejected/quarantined/duplicate conflict), and trace each event to its related invoice and journal entry for audit support.

### In-scope
- Moqui screens to:
  - List ingestion records filtered to `eventType in (InvoiceAdjusted, CreditMemoIssued)`
  - View ingestion record detail including:
    - envelope identifiers (eventId, eventType, schemaVersion, sourceModule)
    - timestamps (receivedAt required; occurredAt optional)
    - `processingStatus` and `idempotencyOutcome` (backend-owned enums)
    - error code/message and quarantine indicators when applicable
    - posting references with **primary navigation by `journalEntryId`** (Decision **AD-011**)
    - curated `payloadSummary` by default; raw payload only with explicit permission (Decision **AD-009**)
  - Deep links by `ingestionId` and copyable identifiers for support
- Permission gating per Accounting domain model (Decision **AD-013**)
- Standard operational filters and server-side pagination/sorting

### Out-of-scope
- Implementing ingestion consumers/processors, posting rules, or financial calculations (backend responsibility)
- Editing/reposting journal entries (immutability)
- Retrying ingestion records (separate story; not included here)
- Approving variances/adjustments (separate workflow; not included here)
- Any mutation of invoice/credit memo state from this UI

- **Primary user:** Accounting Ops Specialist
- **Secondary users:** Auditor (read-only), Accounting Manager (read-only oversight unless separately permitted)
- **System actors:** Accounting ingestion processor (backend), journal entry subsystem (backend)

## 4. Preconditions & Dependencies
- Backend provides Accounting ingestion read model: `AccountingEventIngestionRecord` with primary key `ingestionId` (UUIDv7) (Decision **AD-007**, **AD-006**).
- Backend exposes endpoints (Decision **AD-007**):
  - `GET /accounting/ingestion/list`
  - `GET /accounting/ingestion/detail?ingestionId=...`
- Backend provides posting references on ingestion records:
  - `journalEntryId` is canonical reference for navigation; `ledgerTransactionId` optional secondary (Decision **AD-011**).
- Backend provides curated `payloadSummary` and (optionally) raw payload gated by permission (Decision **AD-009**).
- Permissions exist and are enforced server-side; UI must gate entry points/actions (Decision **AD-013**):
  - View ingestion monitoring: `accounting:events:view`
  - View raw payload JSON: `accounting:events:view-payload`
- UUIDv7 is used for identifiers; UI validates UUID format client-side for UUID fields (Decision **AD-006**).
- Timestamp filtering defaults to `receivedAt` (Decision **AD-007**).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUIDv7 validation (Decision **AD-006**):
  - Fields validated client-side: `ingestionId`, `eventId`, `invoiceId` (if present), `journalEntryId` (if UUIDv7), `ledgerTransactionId` (if UUIDv7)
  - If invalid UUID format: block submit and show inline error “Must be a valid UUID”.
- Date range validation:
  - `from <= to` (inclusive)
  - If invalid: block submit and show inline error “Start must be on or before end”.

### Enable/disable rules
- Entry point/menu item visible only if user has `accounting:events:view` (Decision **AD-013**).
- “View Raw Payload” section:
  - Hidden unless user has `accounting:events:view-payload` (Decision **AD-009**, **AD-013**).
- “View Journal Entry” link enabled only when `journalEntryId` is present (Decision **AD-011**).
- “View Ledger Transaction” link enabled only when `ledgerTransactionId` is present.

### Visibility rules
- Prominent banner rules:
  - If `processingStatus = QUARANTINED`: show “Quarantined” banner with backend-provided error code/message.
  - If `idempotencyOutcome = DUPLICATE_CONFLICT`: show “Duplicate conflict” banner (do not infer cause; display backend-provided error fields).
- Error panel visible when `processingStatus in (REJECTED, QUARANTINED)` OR `errorCode` present.

### Error messaging expectations
- Display backend `errorCode` and `message` verbatim (user-safe).
- Do not invent meanings for `processingStatus` or `idempotencyOutcome` beyond labels:
  - `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (Decision **AD-007**)
- For 403/404, show safe messaging without confirming record existence (Decision **AD-013**).

## 10. State Model & Transitions

### Allowed states
Backend authoritative (Decision **AD-007**):
- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`

### Role-based transitions
- None (read-only).

### UI behavior per state
- `PROCESSED`:
  - Show posting references section; enable journal entry navigation when `journalEntryId` present.
- `REJECTED`:
  - Show error section; hide posting navigation if no posting refs.
- `QUARANTINED`:
  - Show quarantine banner + error section; hide posting navigation unless backend provides posting refs (do not assume).
- `DUPLICATE_IGNORED`:
  - Show “Duplicate ignored” badge; if duplicate linkage ID present, show it as copyable and linkable (to ingestion detail) when permitted.
- `DUPLICATE_CONFLICT`:
  - Show “Duplicate conflict” banner; emphasize investigation; display backend error fields and any linkage IDs.

## 12. Acceptance Criteria

### Scenario 1: Authorized user can list adjustment/credit memo ingestion records
Given I have permission `accounting:events:view`  
When I navigate to Accounting → Event Ingestion → Adjustments & Credit Memos  
Then the system requests `GET /accounting/ingestion/list` filtered to event types `InvoiceAdjusted` and `CreditMemoIssued`  
And I see a paginated list of ingestion records  
And each row shows `receivedAt`, `eventType`, `processingStatus`, `idempotencyOutcome`, `eventId`, and `ingestionId`

### Scenario 2: Filtering defaults to receivedAt and validates date range
Given I am on the ingestion list screen  
When I set `receivedAtFrom` later than `receivedAtTo` and submit  
Then the UI blocks the request  
And I see an inline validation message indicating the start must be on or before the end

### Scenario 3: UUID validation blocks invalid identifier searches
Given I am on the ingestion list screen  
When I enter an invalid UUID into the `eventId` filter and submit  
Then the UI blocks the request  
And I see an inline validation message “Must be a valid UUID”

### Scenario 4: Detail view shows processed record with journal entry navigation
Given an ingestion record exists with `processingStatus = PROCESSED` and `journalEntryId` populated  
And I have permission `accounting:events:view`  
When I open the ingestion detail screen for its `ingestionId`  
Then I see `ingestionId`, `eventId`, `eventType`, and `receivedAt`  
And I see `processingStatus` and `idempotencyOutcome`  
And I see a “View Journal Entry” link that navigates using `journalEntryId`

### Scenario 5: Detail view shows rejected/quarantined record with error details and no implied posting
Given an ingestion record exists with `processingStatus = REJECTED` or `processingStatus = QUARANTINED`  
And `errorCode` and `errorMessage` are populated  
When I open the ingestion detail screen for its `ingestionId`  
Then I see the error code and error message displayed  
And the UI does not display any posting impact statements beyond the backend-provided fields  
And if `journalEntryId` is not present, no journal entry navigation link is shown

### Scenario 6: Raw payload is permission-gated
Given an ingestion record includes `payloadSummary` and may include raw payload  
When I view the ingestion detail screen without permission `accounting:events:view-payload`  
Then I can see `payloadSummary` (if provided)  
And I cannot see raw payload JSON  
When I view the same screen with permission `accounting:events:view-payload`  
Then I can see the raw payload JSON section (if backend returns it)

### Scenario 7: Unauthorized users cannot access ingestion screens or infer record existence
Given I do not have permission `accounting:events:view`  
When I navigate directly to the ingestion detail URL with an `ingestionId`  
Then I see an access denied message  
And no ingestion record data is displayed
