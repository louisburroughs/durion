## Issue Body

## Title
[FRONTEND] [STORY] Accounting Events: View & Validate Canonical Accounting Event Envelope (Contract UI)

## Primary Persona
- **Domain Architect / Backend Engineer (Accounting)** maintaining the canonical event envelope contract and verifying conformance.

## Business Value
Provide a Moqui-native UI surface to **view** (and optionally **validate**) the Canonical Accounting Event Envelope contract so producers/consumers can align on required fields, data types, and traceability requirements—reducing integration defects and audit gaps.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Domain Architect (Accounting),
- **I want** a frontend screen to view the Canonical Accounting Event Envelope specification (fields, constraints, examples, schema version),
- **So that** cross-module teams can reliably implement and validate event payloads against a single, discoverable contract.

## In-scope
- Moqui screen(s) that present the canonical envelope requirements:
  - Required envelope fields and meaning
  - Expected types/format constraints (UUIDv7, timestamps, enums as opaque)
  - Nested structures (at minimum: `payloadSummary`/payload guidance, traceability identifiers)
  - Traceability context examples (invoiceId, paymentId, refundId, ingestionId, etc.)
  - Schema version string and governance note
  - Correlation & trace header standard (W3C Trace Context) for producers/consumers
- Optional “validate payload” utility UI that accepts a JSON payload and runs validation against the schema **only if** a backend validation service exists and is exposed for this purpose.

## Out-of-scope
- Defining the schema itself (contract definition is a backend/repo artifact)
- Publishing schema to external Git repo or schema registry (governance process)
- Producing or ingesting events from other modules
- Any debit/credit posting mappings, GL account logic, tax policy definition
- Any mutation of ingestion records (retry/reprocess is a separate operational workflow under ingestion monitoring)

# 4. Preconditions & Dependencies

## Preconditions
- Moqui frontend module is running and can render new screens under an Accounting navigation context.
- Authentication/authorization exists for accessing Accounting screens.

## Dependencies (implementation)
1) **Source of truth for contract content**
   - This story will implement the UI to render a contract/spec **provided by backend** (preferred), or a static artifact served by backend.
   - The frontend must not invent schema fields beyond what backend returns.

2) **Permissions**
   - Must be explicitly gated (deny-by-default). See Business Rules section.

3) **Optional validation**
   - Only implement validation UI if backend provides a validation endpoint for the canonical envelope.

## Resolved ambiguity (decision rationale)
- **Identifier format**: All identifiers shown/validated by this UI that are IDs are **UUIDv7** (Decision **AD-006**). This resolves the prior ambiguity about UUIDv4 examples.
- **Correlation standard**: W3C Trace Context headers (`traceparent`, `tracestate`) are the standard (Decision **AD-008**).

# 7. Business Rules (Translated to UI Behavior)

## Authorization & permission gating (Decision AD-013)
- **Deny by default**: if permission is unknown or missing, hide entry points and rely on backend 403.
- Proposed permissions for this story (must be implemented consistently in Moqui artifact authz and UI gating):
  - View contract screen: `accounting:events:view` (reuse existing “events view” permission to avoid introducing a new permission family)
  - Validate payload (if supported): `accounting:events:view` (same as view; still read-only)
  - View raw payload JSON examples (if any “raw” is included): `accounting:events:view-payload` (Decision **AD-009**)

## Validation (client + server)
- Client-side:
  - JSON must parse; otherwise show inline error “Invalid JSON” and do not call backend.
  - For any input fields that accept IDs (if the UI provides “jump to field” or “search by id”), validate UUIDv7 format and block invalid input (Decision **AD-006**).
- Server-side (if validate endpoint exists):
  - Render backend validation errors as a list with:
    - `errorCode` (stable)
    - `jsonPath` (e.g., `$.eventId`)
    - `message` (user-safe)
  - Do not reinterpret backend enums/statuses; display as provided (Decision **AD-007** enum drift warning).

## Content requirements (what must be displayed)
The contract UI must explicitly include:
- **Correlation & trace headers**:
  - `traceparent` required, `tracestate` optional (Decision **AD-008**)
- **Identifier strategy**:
  - IDs are UUIDv7 (Decision **AD-006**)
- **Raw payload visibility policy**:
  - Default to curated summaries; raw JSON display is permission-gated and must not be cached or logged (Decision **AD-009**)
- **Ingestion monitoring linkage guidance**:
  - Canonical posting reference is `journalEntryId`; `ledgerTransactionId` is secondary (Decision **AD-011**)
- **Ingestion status taxonomy** (for producers/consumers to understand outcomes):
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (Decision **AD-007**)

## Enable/disable rules
- Validate button disabled until textarea contains non-empty content.
- Validate section hidden if validate endpoint is not available (determined by config flag or a 404/501 response on capability probe; see Service Contracts).

## Error messaging expectations
- Load failure: show non-technical summary + correlation id if provided.
- Unauthorized: show standard “Not authorized” screen and do not render spec content.
- Not found: show “Contract not available” without implying environment misconfiguration details.

# 9. Service Contracts (Frontend Perspective)

## Load/view calls (required)
### `GET /accounting/event-contracts/canonical-envelope`
**Request**
- none
- Optional: `schemaVersion` (string) to view a specific version **only if backend supports** (see Open Questions)

**Response (minimum)**
```json
{
  "schemaVersion": "1.0.0",
  "publishedAt": "2026-01-01T00:00:00Z",
  "sourceUri": "https://…",
  "fields": [
    { "fieldName": "eventId", "required": true, "type": "string", "format": "uuidv7", "description": "…" }
  ],
  "examples": [
    { "name": "InvoiceIssued", "json": { "eventId": "…", "eventType": "InvoiceIssued" } }
  ]
}
```

**Error handling expectations**
- 401/403: render unauthorized/access denied (no partial content)
- 404: show “Contract not available”
- 5xx/timeout: show load failure with retry; preserve route

## Create/update calls
- none (out-of-scope)

## Submit/transition calls (optional)
### `POST /accounting/event-contracts/canonical-envelope/validate`
**Request**
```json
{
  "payloadJson": "{...}",
  "schemaVersion": "1.0.0"
}
```
- `payloadJson` required (string)
- `schemaVersion` optional (string)

**Response**
```json
{
  "valid": false,
  "errors": [
    { "errorCode": "REQUIRED", "jsonPath": "$.eventId", "message": "eventId is required" }
  ]
}
```

**Error handling expectations**
- 400/422: validation errors; render inline and/or list
- 413: payload too large; show “Payload too large”
- 501/404: treat as “validation not supported”; hide/disable validation UI after detection

## Capability detection (to avoid guessing)
- On first visit, UI may:
  - Attempt to load the validate endpoint only when user opens Validate section; if it returns 404/501, show “Validation not available in this environment” and do not show the form again for the session.
  - This is UI ergonomics only; no business policy inference.

# 12. Acceptance Criteria

### Scenario 1: View canonical envelope contract successfully
**Given** a user with permission `accounting:events:view` navigates to Accounting → Integrations → Event Contracts → Canonical Accounting Event Envelope  
**When** the screen loads  
**Then** the UI displays the contract `schemaVersion`  
**And** the UI displays that identifiers are UUIDv7  
**And** the UI displays that correlation uses `traceparent` (required) and `tracestate` (optional)  
**And** the UI displays ingestion status taxonomy (`processingStatus` and `idempotencyOutcome`) as backend-owned enums  
**And** the UI displays that `journalEntryId` is the canonical posting reference (and `ledgerTransactionId` is secondary) when present.

### Scenario 2: Contract load failure
**Given** a user with permission `accounting:events:view` navigates to the Canonical Envelope screen  
**When** `GET /accounting/event-contracts/canonical-envelope` returns a 5xx or times out  
**Then** the UI shows a load failure message  
**And** provides a retry action  
**And** does not display partial or stale contract data.

### Scenario 3: Unauthorized access
**Given** a user without permission `accounting:events:view` attempts to access the Canonical Envelope screen  
**When** the screen loads  
**Then** the UI renders an access-denied state  
**And** does not reveal the contract field list or examples.

### Scenario 4 (optional): Validate a conforming payload
**Given** the environment supports `POST /accounting/event-contracts/canonical-envelope/validate`  
**And** a user with permission `accounting:events:view` opens the Validate section  
**And** pastes valid JSON  
**When** the user clicks Validate  
**Then** the UI calls the validate endpoint with the pasted JSON  
**And** when the response returns `valid=true`, the UI shows a “valid” result  
**And** no validation errors are displayed.

### Scenario 5 (optional): Validate a non-conforming payload
**Given** the environment supports `POST /accounting/event-contracts/canonical-envelope/validate`  
**And** a user opens the Validate section  
**And** pastes a JSON payload missing a required field  
**When** the user clicks Validate  
**Then** the UI shows an “invalid” result  
**And** displays at least one error containing `errorCode` and `jsonPath` for the missing field.

### Scenario 6: Client-side invalid JSON
**Given** the user opens the Validate section  
**When** the user enters malformed JSON and clicks Validate  
**Then** the UI shows “Invalid JSON”  
**And** does not call the backend validation endpoint.

### Scenario 7 (optional): Validation not supported in environment
**Given** the environment does not expose the validate endpoint (404/501)  
**When** the user opens the Validate section  
**Then** the UI shows “Validation not available in this environment”  
**And** does not repeatedly attempt validation calls on subsequent interactions in the same session.
