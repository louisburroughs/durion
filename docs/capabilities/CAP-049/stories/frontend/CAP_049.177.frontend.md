## 2. Story Intent

**As a** Finance Ops user  
**I want** a UI to list and view refund transactions derived from `RefundIssued` events, including linkage to the original payment (mandatory) and invoice (optional), plus processing status/errors  
**So that** I can audit refund activity, identify exceptions (missing references, quarantined/failed), and support operations without initiating or modifying refunds.

### In-scope
- Moqui screen flow to:
  - List refunds (`RefundTransaction` read model) with server-side pagination/sorting
  - View refund detail with traceability identifiers and linkage fields
  - Surface backend-authoritative refund status and processing/ingestion diagnostics (including `QUARANTINED` and duplicate conflict)
- Filtering/search on identifiers and operational fields:
  - `refundId`, `eventId`, `paymentId`, `invoiceId`, `originalTxnRef`
  - date range (based on `receivedAt` where available; otherwise backend-provided timestamp field)
  - `status`
- Permission-gated visibility of raw payload JSON (default: payload summary only)
- Empty/error states and safe handling of unresolved references

### Out-of-scope
- Initiating/authorizing/voiding refunds (Payment domain responsibility; **Decision AD-001**)
- Any GL posting inference or “reverse cash/revenue” UI behavior (Accounting UI must not infer postings)
- Editing refund financials or reason codes
- Refund reversal workflows

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUIDv7 validation (client-side) for fields:
  - `refundId`, `eventId`, `paymentId`, `invoiceId`
  - If invalid UUID format: block submit and show inline error (**Decision AD-006**)
- Date range validation:
  - `thruDate >= fromDate` (inclusive); block submit with inline error
- Do not validate or interpret `originalTxnRef` beyond basic length trimming; treat as opaque string.

### Enable/disable rules
- “View Refund Detail” enabled only for rows with `refundId`.
- “View Original Payment” link enabled only when `paymentId` is present.
- “View Invoice” link enabled only when `invoiceId` is present.
- “View Raw Payload” section:
  - Visible only if user has `accounting:events:view-payload`
  - Otherwise show “Restricted” placeholder and do not fetch raw payload fields if backend supports separate payload retrieval.

### Visibility rules
- Show status banner based on backend `status`:
  - `FAILED`: error banner + show `errorCode` and safe `errorMessage`
  - `QUARANTINED`: quarantine banner + show `processingStatus/idempotencyOutcome` if provided + error details
  - `PENDING`: info banner “Processing” + show timestamps
  - `COMPLETED`: no banner (normal view)
- Show “Unresolved reference” banner when:
  - `paymentId` is missing (should be rare; backend says paymentId is mandatory—if missing, treat as data integrity issue)
  - OR backend explicitly indicates unresolved linkage (e.g., `unresolvedReference=true` or errorCode indicating missing original transaction)
  - OR user navigates to linked entity and receives 403/404 (show generic “Unable to open linked record” without stating existence)

### Error messaging expectations
- UI must display backend-provided `errorCode` and `message` without inventing new reason mappings.
- If backend returns `errorCode` values, UI shows:
  - A user-safe summary: “Refund could not be processed” (FAILED) / “Refund quarantined” (QUARANTINED)
  - A details block with `errorCode`, `message`, and identifiers for support
- Never display or log raw payload bodies unless permitted; never log them even when permitted (**Decision AD-009**, **AD-008**).

## 11. Alternate / Error Flows

### Validation failures
- Invalid UUID in any UUID field → inline error; search not submitted.
- Invalid date range → inline error; search not submitted.

### Concurrency conflicts
- If detail fetch returns 409 or indicates stale data:
  - UI shows “Data changed; refresh” and provides refresh action.

### Unauthorized access
- If user lacks `accounting:refund:view`:
  - List and detail screens show access denied.
  - Deep-linking to a refundId must not reveal existence (generic message).

### Empty states
- No results:
  - Show empty state with “Clear filters” and guidance to search by refundId/originalTxnRef.
- Refund detail missing:
  - If authorized and 404: show “Refund not found” with entered refundId.

## 12. Acceptance Criteria

### Scenario 1: View refunds list (authorized)
**Given** the user has `accounting:refund:view`  
**When** the user navigates to `Accounting → Refunds`  
**Then** the UI requests `GET /accounting/refunds/list` with default pagination  
**And** the UI displays rows including `refundId`, `status`, `refundAmount`, `currencyUomId`, `paymentId`, and `receivedAt`.

### Scenario 2: Filter refunds by UUID identifiers and date range
**Given** the user is on the refunds list  
**When** the user enters a valid UUIDv7 `refundId` and a valid inclusive date range  
**And** submits the search  
**Then** the UI calls `GET /accounting/refunds/list` with those filters  
**And** the results reflect the applied filters.

### Scenario 3: Client-side validation blocks invalid UUID
**Given** the user is on the refunds list  
**When** the user enters an invalid `refundId` value that is not a UUID  
**Then** the UI shows an inline validation error  
**And** does not call the backend until the value is corrected.

### Scenario 4: View refund detail with traceability identifiers
**Given** the user has `accounting:refund:view`  
**And** a refund exists with `refundId=R1`  
**When** the user opens `/accounting/refunds/detail?refundId=R1`  
**Then** the UI calls `GET /accounting/refunds/detail?refundId=R1`  
**And** displays `refundId`, `status`, `refundAmount`, `currencyUomId`, `paymentId` (mandatory), and `invoiceId` (if present)  
**And** displays a copyable identifiers block including `refundId`, `eventId` (if present), `paymentId`, `invoiceId` (if present), and `originalTxnRef` (if present).

### Scenario 5: Quarantined refund shows quarantine banner and diagnostics
**Given** a refund detail response has `status=QUARANTINED`  
**When** the user views the refund detail  
**Then** the UI shows a quarantine banner  
**And** displays backend-provided `processingStatus`, `idempotencyOutcome`, `errorCode`, and `errorMessage` when present  
**And** does not infer or display GL/posting effects.

### Scenario 6: Payload visibility is permission-gated
**Given** the user has `accounting:refund:view` but does not have `accounting:events:view-payload`  
**When** the user views refund detail  
**Then** the UI shows `payloadSummary` if provided  
**And** the UI does not display raw payload JSON and shows a “Restricted” placeholder for raw payload.

### Scenario 7: Unauthorized access does not leak existence
**Given** the user does not have `accounting:refund:view`  
**When** the user navigates to the refunds list or directly to a refund detail URL  
**Then** the UI shows an access denied message  
**And** does not display refund data  
**And** does not indicate whether the requested `refundId` exists.
