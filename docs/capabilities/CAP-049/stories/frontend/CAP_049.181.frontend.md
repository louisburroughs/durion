## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Accounting: Ingestion Monitoring UI for `InvoiceIssued` (Status, Idempotency Outcome, Posting References, Optional Retry)

**Primary Persona:** Accounting Ops / Finance Admin (operational responsibility for accounting integrations)

**Business Value:** Provide operational visibility into `InvoiceIssued` ingestion outcomes so Accounting can confirm idempotent processing, diagnose failures (schema/mapping/period), and trace resulting postings via canonical references—without backend access.

---

## 2. Story Intent

**As an** Accounting Ops user  
**I want** a Moqui/Quasar UI to list and view `InvoiceIssued` ingestion records (including processing status, idempotency outcome, errors, and posting references) and optionally trigger an async retry when permitted  
**So that** I can ensure invoices post exactly once, quickly resolve ingestion errors, and provide traceability for audit and reconciliation.

### In-scope
- Moqui screens to:
  - List ingestion records filtered to `eventType = InvoiceIssued`
  - Filter by `processingStatus`, `idempotencyOutcome`, `receivedAt` date range, and identifiers (`invoiceId`, `eventId`, `ingestionId`)
  - View ingestion record detail (envelope identifiers, timestamps, idempotency outcome, posting references, error details)
  - Display curated `payloadSummary` by default; show raw payload JSON only with explicit permission
  - Optional: trigger **async** retry for eligible records if backend supports `/accounting/ingestion/retry` (Decision **AD-014**)
- Navigation entry under Accounting → Integrations / Event Ingestion
- Standardized error rendering per canonical `{errorCode, message, details?}` schema (Decision **AD-013**)

### Out-of-scope
- Implementing ingestion/posting logic (backend responsibility)
- Creating/editing Chart of Accounts, Posting Rules, GL mappings
- Changing invoice state or issuing invoices (Billing-owned)
- DLQ management beyond surfacing backend-provided quarantine/DLQ indicators and errors
- Any financial calculation or “balanced” determination computed in UI (Accounting backend is authoritative)

## 7. Business Rules (Translated to UI Behavior)

1. **Backend-authoritative ingestion taxonomy (Decision AD-007)**
   - UI must display `processingStatus` and `idempotencyOutcome` exactly as returned.
   - UI must not create additional statuses; unknown values must render as “Unknown (<value>)”.

2. **Idempotency visibility (Decision AD-007)**
   - UI must display `eventId` and any backend-provided business keys (e.g., `invoiceId`, `invoiceVersion`) as identifiers.
   - If `idempotencyOutcome = DUPLICATE_IGNORED`, UI must display a clear message: “Duplicate ignored; no new postings created.”
   - If `idempotencyOutcome = DUPLICATE_CONFLICT` and/or `processingStatus = QUARANTINED`, UI must display a conflict banner and direct user to error details.

3. **Posting reference display (Decision AD-011)**
   - `journalEntryId` is the canonical posting reference and must be displayed prominently when present.
   - `ledgerTransactionId` is secondary and displayed when present.
   - UI must not infer debit/credit lines or “balanced” unless backend provides explicit fields.

4. **Payload visibility policy (Decision AD-009)**
   - Default: show only `payloadSummary` (curated/redacted).
   - Raw payload JSON is visible only with `accounting:events:view-payload`.
   - UI must render JSON as plain text (no HTML), must not log it, and must avoid caching it beyond normal page lifecycle.

5. **Permission gating (Decision AD-013)**
   - Screen access requires `accounting:events:view`.
   - Retry action requires `accounting:events:retry`.
   - Raw payload requires `accounting:events:view-payload`.
   - Deny-by-default: if permission unknown/unavailable, hide entry points and rely on backend 403.

6. **Retry semantics (Decision AD-014)**
   - Retry is async only; UI must not block waiting for completion.
   - Justification is required (>= 10 chars) for human-initiated retries.

## 10. State Model & Transitions

### Allowed states (backend-authoritative)
- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED` (Decision **AD-007**)
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (Decision **AD-007**)

### Role-based transitions
- **View-only users** (`accounting:events:view`): no transitions
- **Ops retry users** (`accounting:events:retry`): may initiate retry job from:

### UI behavior per state
- `PROCESSED`: show posting references (journal entry primary) if present; hide retry
- `REJECTED`: show error section; show retry if permitted
- `QUARANTINED`: show conflict/quarantine banner + error section; show retry if permitted and backend allows
- `idempotencyOutcome = DUPLICATE_IGNORED`: show “duplicate ignored” banner; do not imply postings were created for this record
- `idempotencyOutcome = DUPLICATE_CONFLICT`: show “duplicate conflict” banner; emphasize quarantine/investigation

## 11. Alternate / Error Flows

1. **Empty list**
   - No results → show empty state with “Clear filters” and keep filter values visible.

2. **Invalid UUID filter input**
   - User enters non-UUIDv7 in `ingestionId/eventId/invoiceId` → block submit and show inline error “Must be a valid UUID” (Decision **AD-006**).

3. **Backend unavailable / timeout**
   - Show non-destructive error and “Retry” action; keep filters and current page.

4. **Unauthorized**
   - If list/detail returns 403, show access denied; do not reveal whether the record exists.

5. **Record not found**
   - Detail returns 404 → show “Ingestion record not found” and provide link back to list.

6. **Retry conflict**
   - Retry returns 409 (status changed or not eligible) → show message and refresh detail.

7. **Large payload summary**
   - If `payloadSummary` is large, UI must render it in a collapsible/virtualized area to avoid lockups; raw payload remains permission-gated.
