## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Work Order Reopen → Completion Posting Reversal Visibility (Ingestion Monitor + Journal Entry Linkage)

### Primary Persona
Accounting Operations user / Accountant (read-only ops visibility)

**Persona Metadata**
- `primary_persona`: `Accounting Operations user / Accountant (read-only ops visibility)`
- `canonical_persona`: `Accounting Associate`
- `persona_family`: `Accounting Associate`
- `actor_type`: `human`

### Business Value
Provide operational visibility and auditability when a Work Order is reopened and completion-related accounting postings are reversed, without introducing unsafe cross-domain mutations. Ensure accounting state is traceable (event → ingestion record → journal entry) and support can diagnose quarantines/duplicates/rejections.

---

## 2. Story Intent

### As a / I want / So that
**As an** Accounting Operations user,  
**I want** to view the accounting ingestion and posting outcomes related to a Work Order reopen and any resulting completion-posting reversal,  
**so that** I can confirm whether accounting processed the reopen/reversal correctly (or see why it did not), and I can navigate to the resulting journal entry for audit and support.

### In-scope
- Accounting UI screens to:
  - Search and view **AccountingEventIngestionRecord** entries related to a `workorderId` and/or `eventId`.
  - View ingestion detail including `processingStatus`, `idempotencyOutcome`, error fields, and posting references.
  - Navigate to the **Journal Entry** referenced by ingestion (`journalEntryId` is canonical; AD-011).
  - Display curated `payloadSummary` by default; optionally show raw payload JSON only with explicit permission (AD-009, AD-013).
- UI handling for quarantined/duplicate conflict/rejected ingestion outcomes (AD-007).
- UUIDv7 validation for identifiers used in filters/search (AD-006).
- W3C trace header propagation on all calls (AD-008).

### Out-of-scope
- Any UI action that **initiates** reversal or changes Work Order state (Work Execution domain owns Work Order lifecycle; Accounting consumes events).
- Defining posting rules, GL mappings, or debit/credit lines.
- Implementing event consumers/producers (backend responsibility).
- Editing posted journal entries (immutable).
- Determining “invoice-ready” or preventing invoicing (Billing/Work Execution domain behavior; Accounting UI only shows accounting ingestion/posting visibility).

  - `GET /accounting/ingestion/list`
  - `GET /accounting/ingestion/detail?ingestionId=...`

  - A route/screen to view `JournalEntry` by `journalEntryId` (if not present, link should be copyable ID only).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Accounting menu: **Accounting → Integrations → Event Ingestion**
- Deep link from support tooling: `/accounting/ingestion/detail?ingestionId=...`
- Optional: from a Work Order detail screen (if exists) provide a link “View Accounting Ingestion” that pre-filters by `workorderId` (read-only link; no cross-domain mutation).

### Screens to create/modify
1. **Screen: Accounting Ingestion List**
   - Path: `apps/accounting/screen/ingestion/IngestionList.xml` (illustrative)
   - Uses `GET /accounting/ingestion/list`
   - Filters include `eventType`, `processingStatus`, `idempotencyOutcome`, `receivedAt` date range, and identifier filters (UUIDv7).
2. **Screen: Accounting Ingestion Detail**
   - Path: `apps/accounting/screen/ingestion/IngestionDetail.xml` (illustrative)
   - Uses `GET /accounting/ingestion/detail?ingestionId=...`
   - Shows identifiers, timestamps, status/outcomes, error fields, posting references, and payload summary (raw payload gated).

### Navigation context
- List route: `/accounting/ingestion`
- Detail route: `/accounting/ingestion/detail?ingestionId=<uuidv7>`
- Breadcrumb: Accounting > Integrations > Event Ingestion > {ingestionId}

### User workflows (happy + alternate)
**Happy path: confirm reversal posting exists**
1. User opens Ingestion List.
2. User filters by `workorderId` (UUIDv7) or `eventId`.
3. User opens the ingestion record.
4. User sees `processingStatus=PROCESSED` and a `journalEntryId`.
5. User clicks the `journalEntryId` link (if journal entry screen exists) or copies it for audit.

**Alternate path: quarantined/duplicate conflict**
1. User opens ingestion detail.
2. UI shows `processingStatus=QUARANTINED` and/or `idempotencyOutcome=DUPLICATE_CONFLICT`.
3. UI displays error code/message and a prominent “Quarantined” banner; no UI inference about postings.

**Alternate path: rejected**
1. User filters by workorderId and sees a record with `processingStatus=REJECTED`.
2. UI shows error code/message; posting references may be absent.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUIDv7 validation (AD-006):
  - Fields treated as UUIDv7: `ingestionId`, `eventId`, `workorderId` (if used as identifier), `journalEntryId` (if UUIDv7), `ledgerTransactionId` (if UUIDv7).
  - UI blocks invalid UUID input with inline error and prevents search submit.
- Date range validation:
  - `receivedAtFrom` and `receivedAtThru` (if both provided): `thru >= from` (inclusive).

### Enable/disable rules
- Entry points and screens:
  - Hide Accounting → Integrations → Event Ingestion menu item unless user has `accounting:events:view` (deny by default; AD-013).
- Payload visibility (AD-009, AD-013):
  - If user lacks `accounting:events:view-payload`, do not fetch raw payload fields when possible; show “Restricted” placeholder.
  - If backend returns payload regardless, UI must not render raw payload unless permission is present.

### Visibility rules
- Always show:
  - `processingStatus`, `idempotencyOutcome`, `receivedAt`, identifiers present.
- Show posting references section even if empty:
  - If no `journalEntryId`, show “No posting reference available for this ingestion record.”

### Error messaging expectations
- UI must treat backend enums as authoritative (AD-007); do not invent meanings beyond:
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`
- Standard HTTP mapping:
  - 401/403: “Access denied.”
  - 404: “Record not found.”
  - 5xx/timeout: “Service unavailable; try again.”

## 10. State Model & Transitions

### Allowed states
This story uses ingestion record statuses (backend-authoritative; AD-007):
- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`

### Role-based transitions
- None (read-only).

### UI behavior per state
- `PROCESSED`:
  - Show success styling; show posting references if present.
- `REJECTED`:
  - Show error styling; show `errorCode/errorMessage`; posting refs may be absent.
- `QUARANTINED`:
  - Show prominent banner “Quarantined”; show `errorCode/errorMessage`; instruct user to follow ops runbook (link placeholder if available).
- `DUPLICATE_IGNORED`:
  - Show note “Duplicate ignored; no new postings created” (wording must not imply more than idempotency outcome).
- `DUPLICATE_CONFLICT`:
  - Show banner “Duplicate conflict; quarantined for review” when paired with `QUARANTINED` (do not infer pairing if backend differs; display both fields as-is).

## 12. Acceptance Criteria

### Scenario 1: View ingestion list filtered by workorderId
Given I have permission `accounting:events:view`  
And I am on the Accounting Event Ingestion list screen  
When I enter a valid UUIDv7 workorderId filter and submit  
Then the UI calls `GET /accounting/ingestion/list` with the filter  
And I see a paginated list of ingestion records matching the filter  
And each row shows ingestionId, eventId, eventType, receivedAt, processingStatus, and idempotencyOutcome

### Scenario 2: Block invalid UUID filter input
Given I have permission `accounting:events:view`  
When I enter an invalid UUID into the eventId (or ingestionId/workorderId) filter field  
Then the UI shows an inline validation error  
And the Search action is disabled until the value is corrected or cleared  
And no backend request is sent

### Scenario 3: View ingestion detail with processed status and journal entry reference
Given I have permission `accounting:events:view`  
And an ingestion record exists with `processingStatus=PROCESSED` and a `journalEntryId`  
When I open the ingestion detail screen for that ingestionId  
Then the UI calls `GET /accounting/ingestion/detail?ingestionId=...`  
And I see processingStatus and idempotencyOutcome displayed  
And I see the journalEntryId displayed as the primary posting reference  
And I can copy the journalEntryId (and navigate to it if a journal entry screen exists)

### Scenario 4: Quarantined ingestion record shows diagnostics
Given I have permission `accounting:events:view`  
And an ingestion record exists with `processingStatus=QUARANTINED`  
When I open the ingestion detail screen  
Then I see a “Quarantined” banner  
And I see errorCode and errorMessage (if provided)  
And the UI does not claim postings were created unless a journalEntryId is present

### Scenario 5: Raw payload is restricted without permission
Given I have permission `accounting:events:view`  
And I do not have permission `accounting:events:view-payload`  
When I open an ingestion detail screen  
Then I can see `payloadSummary` if provided  
And I see a “Restricted” placeholder for raw payload  
And the UI does not render raw JSON payload content

### Scenario 6: Raw payload is visible with permission
Given I have permissions `accounting:events:view` and `accounting:events:view-payload`  
When I open an ingestion detail screen that includes raw payload  
Then I can expand and view the raw payload JSON safely  
And the UI does not cache or log the raw payload content

### Scenario 7: Unauthorized user cannot access ingestion screens
Given I do not have permission `accounting:events:view`  
When I navigate directly to `/accounting/ingestion` or an ingestion detail URL  
Then the backend returns 403  
And the UI shows “Access denied” without revealing whether the record exists
