## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Ingestion Monitoring UI for `InventoryIssued` Events (Status, Idempotency, Quarantine, Posting Traceability)

### Primary Persona
Accounting Operations User (Accountant / Finance Ops) monitoring and troubleshooting automated accounting event ingestion.

### Business Value
Provide an operational UI to observe and troubleshoot ingestion of `InventoryIssued` accounting events so postings are traceable, idempotency outcomes are visible, and rejects/quarantine cases can be investigated without backend access.

---

## 2. Story Intent

### As a / I want / So that
**As an** Accounting Operations user,  
**I want** to list and view ingestion records for `InventoryIssued` events (including processing status, idempotency outcome, errors, and posting references),  
**so that** I can confirm events were processed exactly once, identify quarantined/conflicting duplicates, and provide audit-ready traceability to resulting journal entries.

### In-scope
- Moqui screen set under Accounting to:
  - List ingestion records filtered to `eventType = InventoryIssued`
  - View ingestion record detail including:
    - Envelope identifiers (eventId, schemaVersion, sourceModule)
    - Timestamps (receivedAt, processedAt; occurredAt optional)
    - Backend-owned enums: `processingStatus`, `idempotencyOutcome`
    - Error fields (errorCode, errorMessage)
    - Posting references (journalEntryId primary; ledgerTransactionId secondary if present)
    - Curated `payloadSummary` by default; raw payload JSON only with explicit permission
  - Optional action (backend-supported): Retry ingestion processing as an async job with justification and job status polling

### Out-of-scope
- Implementing ingestion, valuation, inventory quantity changes, or GL posting logic (backend responsibility)
- Defining valuation methods, COGS/WIP rules, or GL mappings
- Editing inventory/workorder data or journal entry lines from the UI
- Any “mark reviewed/acknowledged” workflow unless a backend entity/endpoint exists (not defined here)

## 4. Preconditions & Dependencies
- Backend persists ingestion outcomes in **AccountingEventIngestionRecord** read model (**Decision AD-007**) with primary key `ingestionId` (UUIDv7) (**Decision AD-006**).
- Backend exposes ingestion monitoring endpoints (**Decision AD-007**):
  - `GET /accounting/ingestion/list`
  - `GET /accounting/ingestion/detail?ingestionId=...`
  - `POST /accounting/ingestion/retry` (optional; async) (**Decision AD-014**)
- Backend supports filtering by `eventType` and timestamp basis defaults to `receivedAt` (**Decision AD-007**).
- Permissions are enforced per Accounting domain model (**Decision AD-013**):
  - View ingestion: `accounting:events:view`
  - View raw payload JSON: `accounting:events:view-payload` (**Decision AD-009**)
  - Retry ingestion: `accounting:events:retry` (**Decision AD-014**)
- Identifier formats are UUIDv7; UI must validate UUID format client-side for UUID fields (**Decision AD-006**).
- Posting reference canonical identifier is `journalEntryId` (**Decision AD-011**). If a Journal Entry detail screen exists elsewhere, this story links to it; otherwise show as copyable reference only.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUID validation (client-side) for UUIDv7 fields (**Decision AD-006**):
  - `ingestionId` (route param/query)
  - `eventId` filter
- Date range validation:
  - `receivedAt_thru >= receivedAt_from` (inclusive)
- Retry justification:
  - Required, minimum 10 characters (**Decision AD-013**)

### Enable/disable rules
- Entry point visibility:
  - Hide the menu item unless user has `accounting:events:view` (deny-by-default) (**Decision AD-013**)
- Retry button visibility:
  - Visible only when:
    - user has `accounting:events:retry`, AND
    - record `processingStatus` is `REJECTED` or `QUARANTINED` (never for `PROCESSED`), AND
    - backend indicates retry is supported (either via endpoint availability or a `canRetry` flag if provided)
  - Disabled while request is in-flight
- Raw payload section:
  - Only visible and fetched when user has `accounting:events:view-payload` (**Decision AD-009**)

### Visibility rules
- Quarantine banner:
  - Show when `processingStatus = QUARANTINED` OR `idempotencyOutcome = DUPLICATE_CONFLICT`
- Duplicate banner:
  - Show when `idempotencyOutcome = DUPLICATE_IGNORED`
- Rejected banner:
  - Show when `processingStatus = REJECTED`

### Error messaging expectations
- Use backend-provided `errorCode` and `errorMessage` verbatim (user-safe), without inventing meanings for codes (**Decision AD-007**).
- For HTTP errors:
  - 401/403: “Access denied.”
  - 404: “Ingestion record not found.”
  - 409: “Record changed or conflict detected. Refresh and try again.”
  - 5xx/network: “Unable to load ingestion data. Try again.”

## 10. State Model & Transitions

### Allowed states
**Ingestion processingStatus** (**Decision AD-007**):
- `PROCESSED`
- `REJECTED`
- `QUARANTINED`

**Idempotency outcome** (**Decision AD-007**):
- `NEW`
- `DUPLICATE_IGNORED`
- `DUPLICATE_CONFLICT`

### Role-based transitions
- Retry ingestion:
  - Requires `accounting:events:retry` (**Decision AD-013**)
  - Only from `REJECTED` or `QUARANTINED`
  - Requires justification (>= 10 chars)

### UI behavior per state
- `PROCESSED`:
  - Show success status
  - Show posting references if present
  - Hide retry action
- `REJECTED`:
  - Show error banner with errorCode/errorMessage
  - Show retry action if permitted
- `QUARANTINED`:
  - Show quarantine banner emphasizing conflict/needs attention
  - Show retry action if permitted and backend supports
- `DUPLICATE_IGNORED`:
  - Show “Duplicate ignored” badge; do not imply new posting
- `DUPLICATE_CONFLICT`:
  - Show “Duplicate conflict” badge and quarantine banner; do not infer resolution steps beyond retry if supported

## 11. Alternate / Error Flows

### Validation failures
- Invalid UUID in `eventId` filter:
  - UI shows inline error and disables Search until corrected (**Decision AD-006**).
- Invalid UUID in `ingestionId` deep link:
  - UI shows “Invalid identifier format” and does not call backend.

### Concurrency/conflicts
- Retry submitted twice:
  - UI prevents double-submit while in-flight.
  - If backend returns 409, UI shows conflict message and offers refresh.

### Unauthorized access
- User without `accounting:events:view`:
  - Menu entry hidden.
  - Direct link returns 403 screen/message without revealing record existence (**Decision AD-013**).
- User without `accounting:events:view-payload`:
  - Payload section shows “Restricted” and does not fetch raw payload (**Decision AD-009**).
- User without `accounting:events:retry`:
  - Retry action hidden.

### Empty states
- No records found:
  - Show empty state with “Clear filters” and guidance to widen receivedAt range.

## 12. Acceptance Criteria

### Scenario 1: View InventoryIssued ingestion list (authorized)
**Given** I have permission `accounting:events:view`  
**When** I open `/apps/accounting/ingestion/inventory-issued`  
**Then** the UI calls `GET /accounting/ingestion/list` with `eventType=InventoryIssued`  
**And** I see a paginated list where each row includes `ingestionId`, `eventId`, `receivedAt`, `processingStatus`, and `idempotencyOutcome`

### Scenario 2: Filter by receivedAt date range (inclusive)
**Given** I am on the InventoryIssued ingestion list  
**When** I set `receivedAt_from` to `2026-01-01` and `receivedAt_thru` to `2026-01-31` and search  
**Then** the UI sends those filter parameters to the list endpoint  
**And** only records with `receivedAt` within the inclusive range are shown

### Scenario 3: Client-side UUID validation blocks invalid eventId filter
**Given** I am on the InventoryIssued ingestion list  
**When** I enter `eventId = "not-a-uuid"`  
**Then** I see an inline validation error for the eventId field  
**And** the Search action is disabled until the value is a valid UUIDv7 format

### Scenario 4: View ingestion record detail (processed)
**Given** an ingestion record exists with `ingestionId = <UUIDv7>` and `processingStatus = PROCESSED`  
**When** I open the detail screen for that ingestionId  
**Then** I see `eventId`, `eventType`, `schemaVersion`, `sourceModule`, `receivedAt`, and `processingStatus`  
**And** if `journalEntryId` is present, it is displayed as the primary posting reference

### Scenario 5: Duplicate ignored is clearly indicated
**Given** an ingestion record exists with `idempotencyOutcome = DUPLICATE_IGNORED`  
**When** I view the detail screen  
**Then** I see a “Duplicate ignored” indicator  
**And** the UI does not claim a new posting occurred

### Scenario 6: Quarantined conflict is visible and filterable
**Given** ingestion records exist with `processingStatus = QUARANTINED` and/or `idempotencyOutcome = DUPLICATE_CONFLICT`  
**When** I filter the list by `processingStatus = QUARANTINED`  
**Then** only quarantined records are shown  
**And** opening a quarantined record shows a quarantine banner and any backend-provided `errorCode`/`errorMessage`

### Scenario 7: Raw payload is permission-gated
**Given** I have `accounting:events:view` but do not have `accounting:events:view-payload`  
**When** I view an ingestion record detail  
**Then** I can see `payloadSummary`  
**And** I cannot see raw payload JSON and the UI does not fetch/render it

### Scenario 8: Retry ingestion is permission-gated and requires justification (if supported)
**Given** the backend supports `POST /accounting/ingestion/retry`  
**And** I have permission `accounting:events:retry`  
**And** I am viewing a record with `processingStatus = REJECTED`  
**When** I click “Retry processing”, enter a justification of at least 10 characters, and confirm  
**Then** the UI calls `POST /accounting/ingestion/retry` with `ingestionId` and `justification`  
**And** I see the returned `jobId` and a visible job status area (polling if supported)

### Scenario 9: Unauthorized users cannot access ingestion screens
**Given** I do not have permission `accounting:events:view`  
**When** I navigate directly to `/apps/accounting/ingestion/inventory-issued`  
**Then** I see an access denied message  
**And** the UI does not reveal whether any specific ingestionId exists

### Scenario 10: Backend/service error handling
**Given** the ingestion list endpoint returns a 5xx error  
**When** I load the InventoryIssued ingestion list  
**Then** I see a non-technical error banner indicating the list could not be loaded  
**And** I can retry loading without a full app refresh
