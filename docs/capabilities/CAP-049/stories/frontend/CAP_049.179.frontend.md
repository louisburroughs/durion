## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Payments Ingestion Visibility (PaymentReceived) — Payments List/Detail + Unassigned Work Queue + One-Time Customer Assignment

### Primary Persona
Accounting Ops User (Accountant / Accounting Clerk)

### Business Value
Provide an operational UI to monitor and troubleshoot `PaymentReceived` ingestion results via Accounting’s payment read model and ingestion monitoring read model, and to work “unapplied/unassigned” payments (including one-time customer assignment with justification). This enables timely reconciliation and reduces support burden while preserving auditability, idempotency, and strict permission gating.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Accounting Ops User  
- **I want** a UI to view Accounting’s ingested payments created from `PaymentReceived` events (including linkage to ingestion outcomes for duplicates/rejections/quarantine) and to triage unapplied/unassigned payments  
- **So that** I can reconcile cash receipts, identify ingestion issues (schema/currency/customer mismatches), and maintain traceable accounting records without direct database access.

### In-scope
- New/updated Moqui screens to:
  - List and view Accounting payment read-model records created/updated from `PaymentReceived` (`/accounting/payments/list`, `/accounting/payments/detail`).
  - Provide an “Unapplied & Unassigned Payments” work queue (pre-filtered list view: `status=AVAILABLE` and `customerId is null`).
  - Display source metadata and ingestion traceability identifiers returned by backend (eventId, receivedAt, processingStatus/idempotencyOutcome when available via ingestion record).
  - Display `sourceEventPayload` **only** when user has `accounting:events:view-payload` (Decision AD-009).
  - Allow **one-time** manual association of `customerId` to an ingested payment with mandatory justification (Decision AD-004) via `/accounting/payments/assignCustomer`.
- Operational visibility for failures/duplicates:
  - Link from payment detail to ingestion record detail when `ingestionId` is available.
  - Provide navigation to ingestion monitoring list filtered by `paymentId`/`eventId` when payment record does not exist (e.g., rejected currency mismatch) (Decision AD-007, D5).

### Out-of-scope
- Building the ingestion pipeline itself (message broker consumption).
- Creating/changing posting rules, GL mappings, journal entry logic.
- Applying payments to invoices / AR reduction (separate story; Decision AD-002).
- Editing immutable payment financials (amount/currency/method) after ingestion.
- Refund execution (Payment domain-owned; Accounting is read-only visibility) (Decision AD-001).
- Payment application reversal workflows (separate story).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UUIDv7 validation (Decision AD-006):
  - For inputs `paymentId`, `eventId`, `ingestionId`, `customerId`: block submission if not valid UUID format.
- Date range validation:
  - `from <= thru` (inclusive).
- Assign customer (Decision AD-004):
  - `justification` required, min length 10 characters (client-side enforced; backend authoritative).
  - `customerId` required and must be UUIDv7.
  - Only allowed when `customerId` is currently null (UI must not offer “change customer”).
- Payload handling (Decision AD-009):
  - UI must not log or persist raw payloads in client logs; do not include payload in error telemetry.

### Enable/disable rules
- Hide Payments screens entry points unless user has `accounting:payment:view` (Decision AD-013 deny-by-default).
- Disable/hide “Assign Customer” when:
  - missing permission `accounting:payment:assign-customer`
  - `customerId` already set (one-time assignment)
  - payment status is not eligible (backend should enforce; UI disables if status != `AVAILABLE` when present)
- Disable “View raw payload” toggle/section when missing `accounting:events:view-payload`.

### Visibility rules
- `sourceEventPayload` raw JSON:
  - Visible only with `accounting:events:view-payload`.
  - Otherwise show “Restricted” placeholder and do not render content.
- Ingestion error details:
  - Visible to users with `accounting:events:view` (ingestion screens permission); on payment detail, show only what backend returns in payment detail response unless user also has ingestion view permission and UI fetches ingestion detail.
- On 403/404:
  - Do not reveal whether a specific paymentId exists (Decision AD-013); show safe “Not found or access denied.”

### Error messaging expectations
- Use backend `errorCode` and `message` (canonical error schema) and map to user-safe UI:
  - 401 → prompt re-authentication
  - 403 → “Access denied.”
  - 404 → “Not found or access denied.”
  - 409 → “This record changed. Reload and try again.”
  - 422/400 validation → inline field errors; for assign customer show justification/customerId errors.

## 9. Service Contracts (Frontend Perspective)

> Canonical endpoint families are authoritative per Accounting domain guide. UI must not invent schemas; it must render fields returned and treat enums as backend-owned.

### Load/list calls
- `GET /accounting/payments/list`
  - Query params (as supported by backend; UI sends only non-empty):
    - `paymentId` (UUIDv7)
    - `externalTransactionId`
    - `sourceSystem`
    - `status`
    - `customerId` (UUIDv7) or `customerAssigned` (boolean) if supported
    - `receivedAtFrom`, `receivedAtThru` (inclusive)
    - `currencyUomId`
    - `pageIndex`, `pageSize`, `orderBy`
  - Response:
    - `data[]` payment summaries
    - `pageIndex`, `pageSize`, `totalCount`

### View/detail calls
- `GET /accounting/payments/detail?paymentId=<UUIDv7>`
  - Response: payment detail record including audit fields and (if permitted/available) `payloadSummary` and/or `sourceEventPayload`, plus optional linkage fields (`eventId`, `ingestionId`, `journalEntryId`).

### Ingestion linkage calls (for rejected/duplicate/quarantine visibility)
- `GET /accounting/ingestion/list`
  - Used when payment record is missing or when user navigates from payment to ingestion list.
  - Filters should include:
    - `eventType=PaymentReceived` (if supported)
    - `paymentId` and/or `eventId` when available
    - `receivedAtFrom/Thru`
    - `processingStatus`, `idempotencyOutcome`
- `GET /accounting/ingestion/detail?ingestionId=<UUIDv7>`
  - Used when payment detail includes `ingestionId` and user has ingestion view permission.

### Mutation calls
- `POST /accounting/payments/assignCustomer`
  - Permission: `accounting:payment:assign-customer` (AD-013)
  - Request body:
    - `paymentId` (UUIDv7)
    - `customerId` (UUIDv7)
    - `justification` (string, min 10 chars) (AD-004)
  - Response:
    - updated payment detail (or success + refetch)

### Error handling expectations
- Canonical error schema (from Accounting guide):
  - `{ errorCode, message, details? }`
- UI mapping:
  - `details` keys matching field names (`customerId`, `justification`) render inline errors.
  - 409 conflict: show reload CTA; on reload, clear any unsaved form state for assignment.

## 11. Alternate / Error Flows

### Validation failures
- Invalid UUID input in filters:
  - Block search; show inline “Must be a valid UUID.”
- Invalid date range:
  - Block search; show inline error.

### Concurrency conflicts
- Assign customer returns 409:
  - Show conflict message.
  - Refresh payment detail.
  - If `customerId` is now set, hide assignment form.

### Unauthorized access
- User lacks `accounting:payment:view`:
  - Do not show menu entry; direct navigation shows access denied.
- User lacks `accounting:events:view-payload`:
  - Do not fetch/render raw payload; show “Restricted.”
- User lacks `accounting:payment:assign-customer`:
  - Hide assignment form entirely (preferred) or show disabled with permission tooltip.

### Empty states
- Payments list returns 0:
  - Show “No payments found” + “Clear filters”.
- Queue returns 0:
  - Show “No unassigned available payments.”

### Payment not found / ingestion-only case
- Payment detail 404/403:
  - Show safe “Not found or access denied.”
  - Provide link to ingestion monitoring list (if user has `accounting:events:view`) with prefilled filters if user had entered an `eventId`/externalTransactionId.

## 12. Acceptance Criteria

### Scenario 1: View payments list with filters and pagination
**Given** a user with permission `accounting:payment:view`  
**When** the user opens the Payments List screen  
**Then** the system displays a server-paginated list of payments including `paymentId`, `amount`, `currencyUomId`, `status`, `receivedAt`, `sourceSystem`, and `externalTransactionId` when available  
**And** the user can filter by received date range and source system  
**And** the UI sends `pageIndex`, `pageSize`, and `orderBy` to the backend and renders `totalCount`.

### Scenario 2: View payment detail with restricted payload handling
**Given** a payment exists  
**When** a user with `accounting:payment:view` opens Payment Detail for that `paymentId`  
**Then** the system displays read-only payment fields including audit fields  
**And** if the user lacks `accounting:events:view-payload`, the UI does not render raw `sourceEventPayload` and shows “Restricted”  
**And** if the user has `accounting:events:view-payload`, the UI renders raw payload as read-only JSON without logging it.

### Scenario 3: Unapplied & Unassigned queue shows only eligible items
**Given** payments exist with various statuses and customer assignments  
**When** the user opens the Unapplied & Unassigned Queue  
**Then** the list is pre-filtered to show only payments with `status=AVAILABLE` and `customerId` null  
**And** opening a row navigates to the corresponding Payment Detail.

### Scenario 4: Assign customer once with justification
**Given** a payment exists with `status=AVAILABLE` and `customerId` is null  
**And** the user has permission `accounting:payment:assign-customer`  
**When** the user submits an assignment with a valid UUIDv7 `customerId` and a `justification` of at least 10 characters  
**Then** the UI calls `POST /accounting/payments/assignCustomer`  
**And** the payment detail refreshes showing the new `customerId` and updated audit fields  
**And** the assignment form is no longer available for that payment.

### Scenario 5: Prevent customer reassignment and enforce permissions
**Given** a payment exists with `customerId` already set  
**When** any user opens Payment Detail  
**Then** the UI does not offer a “Change Customer” action  
**And** if a user without `accounting:payment:assign-customer` attempts to call the assign endpoint (e.g., via crafted request)  
**Then** the backend returns 403 and the UI shows “Access denied” without revealing additional record details.

### Scenario 6: Visibility into rejected/quarantined PaymentReceived events via ingestion monitoring
**Given** a `PaymentReceived` event was ingested but resulted in `processingStatus=REJECTED` or `QUARANTINED` and no payment record exists  
**And** the user has permission `accounting:events:view`  
**When** the user navigates to ingestion monitoring and filters by `eventType=PaymentReceived` and `eventId`  
**Then** the UI displays the ingestion record with `processingStatus`, `idempotencyOutcome`, and backend-provided `errorCode/errorMessage`.
