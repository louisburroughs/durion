## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting Event Ingestion Monitoring: Validate Completeness/Integrity (List + Detail + Optional Retry)

### Primary Persona
Accounting Operations Analyst (secondary: System Auditor)

### Business Value
Provide a deterministic, auditable UI to review canonical accounting event ingestion outcomes (including validation errors, idempotency outcomes, and posting references) so upstream teams can quickly correct invalid events and Accounting can prevent corrupted/unsafe data from entering downstream posting.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Accounting Operations Analyst  
- **I want** to search and inspect accounting event ingestion records and see clear processing status, idempotency outcome, and actionable error codes/messages  
- **So that** I can triage rejected/quarantined events, confirm successful processing, and provide precise feedback to upstream producers without guessing accounting policy.

### In-scope
- Moqui frontend screens (Vue/Quasar) to:
  - List/search **AccountingEventIngestionRecord** records
  - View ingestion record detail including:
    - envelope identifiers (eventId, eventType, schemaVersion, sourceModule)
    - timestamps (receivedAt, processedAt; occurredAt optional)
    - `processingStatus` and `idempotencyOutcome`
    - error code/message and quarantine indicators
    - posting references (journalEntryId primary; ledgerTransactionId optional)
    - curated `payloadSummary` and (permission-gated) raw payload JSON
  - Optional: trigger **Retry/Reprocess** for eligible ingestion records (async job), with justification
- UI behaviors for handling:
  - schema validation failures
  - unknown event type (backend returns `REJECTED`; no suspense behavior in this workflow)
  - idempotency duplicates and conflicts (`DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`)
  - quarantine/DLQ representation via `processingStatus = QUARANTINED`
- Permission gating per Accounting domain rules (**Decision AD-013**)

### Out-of-scope
- Defining or implementing validation logic (backend-owned)
- Creating/maintaining canonical schemas
- Editing/remediating event payloads in UI
- Any “move from quarantined to processed” workflow beyond backend-provided retry endpoint
- Any posting/journal entry editing (read-only linking only)

---

## 3. Actors & Stakeholders
- **Primary user:** Accounting Operations Analyst
- **Secondary user:** System Auditor / Compliance reviewer (read-only)
- **System actor:** Accounting Event Ingestion Service (backend)
- **Upstream stakeholders:** Engineering teams producing events (need actionable error feedback)
- **Downstream stakeholders:** Accounting posting/GL monitoring users (need posting references)

## 4. Preconditions & Dependencies
- Backend provides Accounting ingestion monitoring endpoints (**Decision AD-007**):
  - `GET /accounting/ingestion/list`
  - `GET /accounting/ingestion/detail?ingestionId=...`
  - Optional retry: `POST /accounting/ingestion/retry` returning `jobId` (**Decision AD-014**)
  - Retry status endpoint exists (name may vary): `GET /accounting/ingestion/retryStatus?jobId=...` or standard job status endpoint (**Decision AD-014**)
- Backend returns authoritative enums (UI must not invent meanings) (**Decision AD-007**):
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`
- Identifiers are UUIDv7 and must be validated client-side (**Decision AD-006**):
  - `ingestionId`, `eventId`, and any linked IDs returned
- Permission model is enforced in UI and backend (**Decision AD-013**):
  - View: `accounting:events:view`
  - View raw payload: `accounting:events:view-payload`
  - Retry: `accounting:events:retry`
- Correlation/trace propagation uses W3C Trace Context headers (**Decision AD-008**):
  - `traceparent` required; `tracestate` optional

- Deep links:

  - Detail: `/accounting/ingestion/detail?ingestionId=<uuidv7>`

### Screens to create/modify

   - Purpose: searchable list of ingestion records with status, idempotency outcome, timestamps, and key identifiers
2. **Screen: `apps/accounting/ingestion/IngestionDetail.xml`**
   - Purpose: full ingestion record view including payload summary, (optional) raw payload, errors, and posting references

   - Purpose: collect justification and trigger async retry (only if backend supports and user has permission)

### Navigation context
- From list → select row → detail screen
- From detail → optional navigation links:
  - to Journal Entry detail screen (if `journalEntryId` present; route depends on existing accounting posting UI)

- **Happy path (review processed event):**
  1. User opens list, filters `processingStatus=PROCESSED`

- **Alternate (triage rejected):**
  1. Filter `processingStatus=REJECTED`
  2. Open detail; view `errorCode`, `errorMessage`, and `payloadSummary`
  3. Copy `ingestionId`/`eventId` and error code to share with upstream team
- **Alternate (quarantined duplicate conflict):**
  1. Filter `processingStatus=QUARANTINED` or `idempotencyOutcome=DUPLICATE_CONFLICT`
  2. Open detail; see quarantine banner and any duplicate linkage fields returned
  3. If permitted, trigger retry with justification (async) and monitor job status

## 6. Functional Behavior

### Triggers
- List screen load triggers ingestion list fetch
- Filter/sort/pagination changes trigger list refresh
- Detail screen load triggers ingestion detail fetch by `ingestionId`
- Retry submit triggers retry endpoint (async) and then status polling (manual refresh or controlled polling)

### UI actions
- **List**
  - Filters (server-side):
    - `processingStatus` (enum)
    - `idempotencyOutcome` (enum)
    - `eventType` (string)
    - `eventId` (UUIDv7; validated)
    - `receivedAt` date range (inclusive; basis is `receivedAt` per **Decision AD-007**)
  - Sorting:
    - default sort: `receivedAt desc`
  - Pagination:
    - `pageIndex`, `pageSize`
- **Detail**
  - Display:
    - identifiers: `ingestionId`, `eventId`, `eventType`, `schemaVersion`, `sourceModule`
    - timestamps: `receivedAt`, `processedAt` (if present), `occurredAt` (if present)
    - statuses: `processingStatus`, `idempotencyOutcome`
    - posting refs: `journalEntryId` (primary), `ledgerTransactionId` (secondary) (**Decision AD-011**)
    - errors: `errorCode`, `errorMessage`, and any structured `errorDetails` returned
    - payload:
      - always show `payloadSummary` (curated/redacted)
      - show raw payload JSON only if user has `accounting:events:view-payload` (**Decision AD-009**)
  - Actions:
    - copy-to-clipboard for identifiers and error codes/messages
    - refresh detail
    - retry (permission-gated; only when backend indicates eligible or when `processingStatus != PROCESSED`)
- **Retry (optional)**
  - Requires justification (>= 10 chars) (**Decision AD-013**)
  - Calls retry endpoint; displays returned `jobId`
  - Provides “Check status” action (manual refresh) and optional polling with backoff

### State changes (frontend-observable)
- UI does not mutate ingestion record state directly; it reflects backend state.
- After retry, UI expects ingestion record may transition from `QUARANTINED/REJECTED` to `PROCESSED` or remain unchanged; UI must display latest backend values.

### Service interactions
- List: `GET /accounting/ingestion/list`
- Detail: `GET /accounting/ingestion/detail?ingestionId=...`
- Retry (optional): `POST /accounting/ingestion/retry`
- Retry status (optional): `GET /accounting/ingestion/retryStatus?jobId=...` (or standard job status endpoint)

## 7. Business Rules (Translated to UI Behavior)

### Validation (backend-owned; UI presentation rules)
- UI must surface backend outcomes without reinterpretation (**Decision AD-007**):
  - `processingStatus` and `idempotencyOutcome` displayed as backend-provided values
  - `errorCode` and `errorMessage` displayed verbatim (user-safe)
- Unknown event types are **REJECTED** in this workflow; UI must not present “suspense” as a possible state unless backend returns it (it should not per domain rules: unknown event types are `REJECTED`) (**Decision AD-007**).

### Enable/disable rules
- Entry points:
  - Hide Accounting → Integrations → Event Ingestion menu item unless user has `accounting:events:view` (**Decision AD-013**).
- Detail payload:
  - If user lacks `accounting:events:view-payload`, do not fetch raw payload field if backend supports field-level omission; otherwise render “Restricted” placeholder and never log payload (**Decision AD-009**).
- Retry:
  - Show retry button only if user has `accounting:events:retry`.
  - Require justification input (>= 10 chars) before enabling submit (**Decision AD-013**).
  - Disable retry submit while request in-flight; prevent double-submit.

### Visibility rules
- Error section:
  - Visible when `processingStatus` is `REJECTED` or `QUARANTINED`, or when backend returns error fields.
- Quarantine banner:
  - Visible when `processingStatus=QUARANTINED` OR `idempotencyOutcome=DUPLICATE_CONFLICT`.
- Posting references:
  - Show `journalEntryId` link when present; show `ledgerTransactionId` as read-only text when present (**Decision AD-011**).

### Error messaging expectations
- 400/422: show validation banner using `{errorCode, message, details}` (do not invent codes)
- 401/403: show access denied; do not reveal record existence (use generic messaging)
- 404: show not found (generic)
- 409: show conflict banner; if backend returns idempotency outcome, display it
- 5xx/timeout: show retry affordance; preserve filters and scroll position where feasible

## 8. Data Requirements

### Entities involved (frontend-facing)
- **AccountingEventIngestionRecord** (read model; authoritative for this UI) (**Decision AD-007**)

### Fields (type, required, defaults)

**Ingestion record summary (list row)**
- `ingestionId` (UUIDv7, string) — required
- `eventId` (UUIDv7, string) — required
- `eventType` (string) — required
- `schemaVersion` (string) — required
- `sourceModule` (string) — required
- `receivedAt` (datetime ISO-8601) — required
- `processingStatus` (enum) — required: `PROCESSED|REJECTED|QUARANTINED`
- `idempotencyOutcome` (enum) — required: `NEW|DUPLICATE_IGNORED|DUPLICATE_CONFLICT`
- `errorCode` (string, nullable) — optional
- `journalEntryId` (UUIDv7, nullable) — optional

**Ingestion record detail**
- All summary fields plus:
- `processedAt` (datetime, nullable) — optional
- `occurredAt` (datetime, nullable) — optional
- `errorMessage` (string, nullable) — optional
- `errorDetails` (object, nullable) — optional (backend-defined)
- `payloadSummary` (object/string, nullable) — optional but recommended (**Decision AD-009**)
- `rawPayloadJson` (object/string, nullable) — optional; only returned/rendered with permission (**Decision AD-009**)
- `ledgerTransactionId` (UUIDv7, nullable) — optional (**Decision AD-011**)
- `duplicateOfIngestionId` (UUIDv7, nullable) — optional (if backend provides linkage for duplicates/conflicts)

### Read-only vs editable by state/role
- All ingestion record fields are read-only.
- Retry justification is editable input, not persisted in ingestion record; it is part of retry audit trail (**Decision AD-013**).

### Derived/calculated fields (UI-only)
- “Terminal” indicator:
  - `PROCESSED` is terminal for this UI
  - `REJECTED` and `QUARANTINED` are terminal unless retry is executed and backend changes state
- Duration display:
  - if `processedAt` present: `processedAt - receivedAt`

## 9. Service Contracts (Frontend Perspective)

> Frontend must use canonical endpoint families and treat schemas as backend-authoritative. Do not invent fields/enums.

### Load/view calls

1. **List ingestion records**
   - `GET /accounting/ingestion/list`
   - Query params (all optional unless noted):
     - `processingStatus`
     - `idempotencyOutcome`
     - `eventType`
     - `eventId` (UUIDv7; validate client-side)
     - `receivedFrom` (date/datetime; inclusive)
     - `receivedTo` (date/datetime; inclusive)
     - `pageIndex` (required)
     - `pageSize` (required)
     - `orderBy` (default `receivedAt desc`)
   - Response:
     - `items[]` ingestion summaries
     - pagination metadata (backend-defined)

2. **Get ingestion record detail**
   - `GET /accounting/ingestion/detail?ingestionId=<uuidv7>`
   - Response:
     - ingestion detail object including payload summary and (permission-gated) raw payload

### Submit/transition calls

3. **Retry ingestion (optional)**
   - `POST /accounting/ingestion/retry`
   - Request body:
     - `ingestionId` (UUIDv7)
     - `justification` (string, min 10 chars) (**Decision AD-013**)
   - Response:
     - `jobId` (UUIDv7 or string; backend-defined)
   - Follow-up:
     - `GET /accounting/ingestion/retryStatus?jobId=...` (or standard job status endpoint) (**Decision AD-014**)

### Error handling expectations
- Canonical error shape (**Decision A3**):
  ```json
  {
    "errorCode": "ACCOUNTING_VALIDATION_FAILED",
    "message": "Validation failed",
    "details": { "fieldName": "REQUIRED" }
  }
  ```
- UI mapping:
  - If `details` contains field keys, show inline errors where applicable (filters, justification)
  - Otherwise show banner/toast with `message` and a “Details” expandable section

## 10. State Model & Transitions

### Allowed states (backend-owned; displayed)
- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED` (**Decision AD-007**)
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (**Decision AD-007**)

### Role-based transitions
- View-only for most users:
  - `accounting:events:view` can list and view detail (without raw payload)
- Retry transition (optional):
  - Only users with `accounting:events:retry` can initiate retry (**Decision AD-013**)
  - Retry is async job; UI must not assume outcome (**Decision AD-014**)

### UI behavior per state
- `PROCESSED`: show success badge; show posting refs if present; hide retry action by default (can still show if backend allows but recommended hidden)
- `REJECTED`: show error banner; show error fields; show retry if permitted
- `QUARANTINED`: show quarantine banner; emphasize conflict/duplicate; show retry if permitted
- `DUPLICATE_IGNORED`: show informational note “Duplicate ignored; no new postings created” (wording only; do not claim postings unless backend provides posting refs)
- `DUPLICATE_CONFLICT`: show conflict banner and any backend-provided linkage identifiers

## 11. Alternate / Error Flows

### Validation failures (view)
- If record is `REJECTED`:
  - Show error banner with `errorCode` and `errorMessage`
  - Show `payloadSummary`
  - If raw payload not permitted, show “Restricted” placeholder

### Retry failures (optional)
- If retry request returns 400/422:
  - Show inline error on justification if applicable; otherwise show banner with backend message
- If retry request returns 403:
  - Show access denied; do not reveal whether ingestionId exists
- If retry job ends in failure:
  - Show job status as `FAILED` (backend-defined) and show error code/message if provided

### Concurrency / stale data
- If detail refresh shows changed `processingStatus`/`idempotencyOutcome` since last fetch:
  - Show non-blocking “Updated” indicator with timestamp (UI-only)

### Unauthorized access
- If list/detail returns 403:
  - Show “You do not have access to Event Ingestion” and do not render any record data
- If user can view detail but not payload:
  - Render payload section as restricted and do not log payload content (**Decision AD-009**)

### Empty states
- List: show “No ingestion records found” with active filters summary and “Clear filters”
- Detail: if 404, show “Record not found” with safe messaging

## 12. Acceptance Criteria

### Scenario 1: View ingestion list (authorized)
**Given** I am logged in with permission `accounting:events:view`  
**When** I navigate to Accounting → Integrations → Event Ingestion  
**Then** I see a paginated list of ingestion records showing `ingestionId`, `eventId`, `eventType`, `processingStatus`, `idempotencyOutcome`, and `receivedAt`

### Scenario 2: Filter by processingStatus
**Given** I am on the ingestion list  
**When** I filter `processingStatus` to `REJECTED`  
**Then** the list refreshes and only shows records where `processingStatus` is `REJECTED`

### Scenario 3: Filter by eventId with UUID validation
**Given** I am on the ingestion list  
**When** I enter an invalid UUID into the `eventId` filter  
**Then** the UI shows an inline validation error and does not submit the filter request  
**And** when I enter a valid UUIDv7, the UI submits the request

### Scenario 4: View ingestion detail (processed)
**Given** an ingestion record exists with `processingStatus=PROCESSED`  
**When** I open the detail page for its `ingestionId`  
**Then** I see `eventId`, `eventType`, `schemaVersion`, `sourceModule`, `receivedAt`  
**And** I see `processingStatus=PROCESSED` and the `idempotencyOutcome` value returned by the backend

### Scenario 5: View ingestion detail (rejected with error)
**Given** an ingestion record exists with `processingStatus=REJECTED` and `errorCode`/`errorMessage` populated  
**When** I open the detail page  
**Then** I see an error banner showing the backend-provided `errorCode` and `errorMessage`  
**And** I see `payloadSummary` if provided by the backend

### Scenario 6: Quarantined duplicate conflict is clearly indicated
**Given** an ingestion record exists with `processingStatus=QUARANTINED` or `idempotencyOutcome=DUPLICATE_CONFLICT`  
**When** I open the detail page  
**Then** I see a quarantine/conflict banner  
**And** I see any backend-provided duplicate linkage identifiers (if present) without the UI inferring relationships

### Scenario 7: Raw payload is permission-gated
**Given** I can view ingestion detail with `accounting:events:view`  
**And** I do not have `accounting:events:view-payload`  
**When** I open an ingestion detail page  
**Then** I do not see raw payload JSON  
**And** the UI shows a “Restricted” placeholder for raw payload  
**And** the UI still shows `payloadSummary` if provided

### Scenario 8: Retry ingestion requires permission and justification (optional)
**Given** I have `accounting:events:retry`  
**And** an ingestion record exists with `processingStatus=QUARANTINED`  
**When** I click “Retry” and enter a justification shorter than 10 characters  
**Then** the UI prevents submission and shows an inline validation error  
**When** I enter a justification of at least 10 characters and submit  
**Then** the UI calls `POST /accounting/ingestion/retry` and displays the returned `jobId`

### Scenario 9: Unauthorized access does not leak record existence
**Given** I do not have `accounting:events:view`  
**When** I navigate directly to `/accounting/ingestion/detail?ingestionId=<some-id>`  
**Then** I see an access denied message  
**And** the UI does not display whether the record exists
