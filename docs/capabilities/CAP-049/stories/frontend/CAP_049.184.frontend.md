## Issue Body

## 1. Story Header

**Title:** [FRONTEND] [STORY] Accounting: Event Ingestion Monitoring — InventoryAdjusted (List/Detail, Status/Idempotency, Posting Links, Optional Retry)

**Primary Persona:** Accounting Ops User (Finance/Accounting back-office user)

**Business Value:**  
Provide an operational UI to view and diagnose ingestion outcomes for `InventoryAdjusted` events (processing status, idempotency outcome, errors, posting references, traceability identifiers) so inventory correction postings are auditable and supportable without backend log access.

---

## 2. Story Intent

**As a** Accounting Ops User  
**I want** to list and view `InventoryAdjusted` ingestion records with their processing outcomes and posting references  
**So that** I can verify what happened (processed/rejected/quarantined/duplicate), investigate failures, and support reconciliation and audit requests.

### In-scope
- Moqui screen flow to:
  - List ingestion records filtered to `eventType=InventoryAdjusted` using Accounting ingestion read model
  - View ingestion record detail (envelope identifiers, timestamps, status/idempotency, error info)
  - Show curated `payloadSummary` by default; show raw payload JSON only when permitted
  - Navigate to linked accounting artifacts (journal entry primary; ledger transaction secondary if present)
  - Optional: trigger ingestion retry as an async job **if** backend supports `/accounting/ingestion/retry` for this event type
- Permission gating per Accounting domain rules (AD-013, AD-009)

### Out-of-scope
- Implementing ingestion consumers, DLQ/quarantine mechanics, idempotency enforcement, or posting logic (backend-owned)
- Defining inventory valuation, GL debit/credit mappings, or posting rule configuration (accounting policy + backend)
- Editing event payloads (immutable)
- Any inventory operational workflow (owned by Inventory/Work Execution domains)

---

## 3. Actors & Stakeholders

- **Primary Actor:** Accounting Ops User
- **Secondary Stakeholders:**
  - Controller/Auditor (read-only verification)
  - Support Engineer (triage failures; typically read-only unless explicitly granted retry permission)
- **Upstream Producers (informational only):** Operational domains may emit inventory adjustment events; Accounting UI treats them as ingested events (read model)
- **Downstream / Related:** Journal Entry views (Accounting), Ledger views (if present)

## 4. Preconditions & Dependencies

- Backend exposes Accounting ingestion monitoring endpoints (normative, AD-007):
  - `GET  /accounting/ingestion/list`
  - `GET  /accounting/ingestion/detail?ingestionId=...`
  - Optional retry (async, AD-014):
    - `POST /accounting/ingestion/retry` → returns `jobId`
    - `GET  /accounting/ingestion/retryStatus?jobId=...` (or equivalent job status endpoint)
- Ingestion read model is `AccountingEventIngestionRecord` with primary key `ingestionId` (UUIDv7) (AD-006, AD-007).
- Ingestion status taxonomy is backend-authoritative (AD-007):
  - `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED`
  - `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT`
- Permissions are defined and enforced (AD-013):
  - View ingestion: `accounting:events:view`
  - View raw payload: `accounting:events:view-payload`
  - Retry ingestion: `accounting:events:retry`
- Posting reference canonical identifier is `journalEntryId` (AD-011).
- Trace context propagation uses W3C Trace Context headers (`traceparent`, `tracestate`) (AD-008).

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI-level)
- UUID validation (AD-006):
  - Inputs `eventId`, `ingestionId` must be valid UUIDv7 format; block submit/search and show inline error if invalid.
- Date range validation:
  - `receivedTo >= receivedFrom` (inclusive); block list call if invalid.
- Retry justification validation (AD-013):
  - Required, minimum 10 characters; block submit if shorter.

### Enable/disable rules
- Entry points and screens require `accounting:events:view`; otherwise hide menu entry and show unauthorized if deep-linked.
- Raw payload viewer:
  - Hidden unless `accounting:events:view-payload`
  - If permission absent, do not request raw payload fields if backend supports field-level omission; otherwise render “Restricted” and do not copy-to-clipboard.
- Retry button:
  - Hidden unless `accounting:events:retry`
  - Disabled unless `processingStatus` is `REJECTED` or `QUARANTINED`
  - Disabled while retry request is in-flight or while a retry job is `QUEUED/PROCESSING`

### Visibility rules
- Error panel visible only when `processingStatus != PROCESSED`
- Quarantine banner visible when `processingStatus = QUARANTINED` OR `idempotencyOutcome = DUPLICATE_CONFLICT`
- Posting references section:
  - Always visible; shows empty state “No posting references recorded” when none present

### Error messaging expectations
- UI must display backend `errorCode` and `errorMessage` verbatim (sanitized by backend) and must not invent meanings for unknown codes (AD-007).
- Standard HTTP/service handling:
  - 401/403: show access denied without leaking record existence (AD-013)
  - 404: show “Not found” without confirming existence
  - 409: show “Record changed; refresh” (used for retry conflicts or stale state)
  - 5xx/timeout: show retry affordance; preserve filters and justification text

- `processingStatus`: `PROCESSED`, `REJECTED`, `QUARANTINED` (AD-007)
- `idempotencyOutcome`: `NEW`, `DUPLICATE_IGNORED`, `DUPLICATE_CONFLICT` (AD-007)

### Role-based transitions
- With `accounting:events:retry`:
  - User may request retry when `processingStatus in {REJECTED, QUARANTINED}` (AD-014)

### UI behavior per state
- `PROCESSED`:
  - Show success state; show posting refs if present; retry hidden/disabled
- `REJECTED`:
  - Show error panel; show payload summary; retry available if permitted
- `QUARANTINED`:
  - Show quarantine banner; show idempotency outcome (often `DUPLICATE_CONFLICT`); retry available only if backend allows (UI enables by status + permission; backend is final authority)

## 11. Alternate / Error Flows

### Validation failures
- Invalid UUID in filter:
  - Inline error; do not call list endpoint
- Invalid date range:
  - Inline error; do not call list endpoint
- Retry justification too short:
  - Inline error; do not call retry endpoint

### Concurrency conflicts / stale state
- If record status changes between list and detail:
  - Detail always shows latest from backend
- If retry attempted but backend returns 409:
  - Show conflict message and offer “Reload record”

### Unauthorized access
- Missing `accounting:events:view`:
  - Hide menu entry
  - Deep link shows unauthorized screen/panel
- Missing `accounting:events:view-payload`:
  - Do not render raw payload; show “Restricted”
- Missing `accounting:events:retry`:
  - Retry action hidden/disabled; backend 403 handled safely

### Empty states
- List returns 0:
  - Show “No InventoryAdjusted ingestion records found” + “Clear filters”
- Detail has no posting refs:
  - Show “No posting references recorded”

**When** I set `receivedFrom` and `receivedTo` where `receivedTo >= receivedFrom` and select `processingStatus=REJECTED`  
**Then** the UI refreshes the list using those filters  
**And** only matching records are shown  
**And** if I enter an invalid date range, the UI shows an inline validation error and does not call the backend.

### Scenario 3: View ingestion record detail with posting reference navigation
**Given** an ingestion record exists with `ingestionId = X` and `processingStatus = PROCESSED` and `journalEntryId = J`  
**When** I open the detail screen for `ingestionId = X`  
**Then** I see identifiers (`ingestionId`, `eventId`, `eventType`, `schemaVersion`, `sourceModule`) and timestamps (`receivedAt`, `processedAt` if present)  
**And** I see `processingStatus` and `idempotencyOutcome`  
**And** I see `journalEntryId = J` as a link to the journal entry view.

### Scenario 4: Quarantined duplicate conflict is clearly indicated
**Given** an ingestion record exists with `processingStatus = QUARANTINED` and `idempotencyOutcome = DUPLICATE_CONFLICT`  
**When** I view the detail screen  
**Then** I see a quarantine/conflict banner  
**And** I see backend-provided `errorCode` and `errorMessage` if present  
**And** the UI does not infer additional meaning beyond the backend fields.

### Scenario 5: Raw payload is permission-gated
**Given** an ingestion record exists with a raw payload available  
**When** I view the detail screen without permission `accounting:events:view-payload`  
**Then** I can see `payloadSummary` (if provided)  
**And** I cannot see raw payload JSON and the UI shows “Restricted” in its place  
**And** the UI does not log or cache raw payload content.

### Scenario 6: Retry ingestion (async) with justification (if supported)
**Given** an ingestion record exists with `processingStatus = REJECTED`  
**And** I have permission `accounting:events:retry`  
**When** I click “Retry” and provide a justification of at least 10 characters and confirm  
**Then** the UI calls `POST /accounting/ingestion/retry` with `ingestionId` and `justification`  
**And** the UI displays the returned `jobId`  
**And** the UI polls retry status until completion or failure (or allows manual refresh)  
**And** after completion, the UI refreshes the ingestion record detail to show the latest `processingStatus`.

### Scenario 7: Retry is blocked for unauthorized users
**Given** I do not have permission `accounting:events:retry`  
**When** I view a `REJECTED` or `QUARANTINED` ingestion record  
**Then** the Retry action is not available  
**And** if I attempt a deep-linked retry action (e.g., via crafted request) and receive 403, the UI shows an access denied message without leaking additional record details.
