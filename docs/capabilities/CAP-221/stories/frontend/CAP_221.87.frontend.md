### Business Value
Ensure only authorized staff can access sensitive inventory operations by enforcing permission-based UI gating and by exposing the inventory permission catalog needed to understand what actions are protected.

---

## 2. Story Intent

### As a / I want / So that
As a System Administrator, I want the frontend to (1) display the inventory permission catalog and (2) gate inventory UI actions based on effective permissions, so that inventory operations follow least-privilege and protected actions are predictable and consistent.

### In-scope
- Inventory security administration UI surfaces:
  - View the inventory permission catalog (read-only)
  - View the current-user effective permission set as needed to explain gated behavior
- Frontend permission-aware UI behavior for Inventory screens:
  - Hide/disable protected actions based on effective permissions
  - Handle `401`/`403` consistently (per platform convention)
- Frontend screens, forms, transitions, and service calls required for the above, using the platform backend integration layer as the entry point (no direct UI → external security backend calls).

### Out-of-scope
- Defining or changing backend RBAC framework behavior (server-side enforcement remains authoritative).
- Implementing identity provider (OIDC/HR) integration UI beyond selecting existing users.
- Designing new inventory operational flows beyond gating their existing entry points/actions.
- Creating/maintaining product master data.
- Any inventory quantity/availability computation in the UI.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Permission filter:
  - Filter text is trimmed before applying client-side matching.
- Authoritative validation comes from backend; UI maps field errors when provided.

### Enable/disable rules
- Inventory Security navigation:
  - Visible only if user has `security:permission:view`.
- Inventory operational screens:
  - Hide or disable actions when the user lacks the required permission key(s) (DECISION-INVENTORY-010).
  - If hidden vs disabled is not standardized, default to **hide** for destructive actions and **disable with tooltip** for viewable-but-not-allowed actions (UI ergonomics only; does not change backend enforcement).

### Visibility rules
- Do not render permission catalog data if the route is unauthorized.
- Correlation ID is displayed when present (DECISION-INVENTORY-012).

### Error messaging expectations
- `401 Unauthorized`: follow app convention (redirect to login/session refresh) (DECISION-INVENTORY-012).
- `403 Forbidden`: show “Access denied” (route-level) or “You don’t have permission to perform this action.” (action-level) without leaking data (DECISION-INVENTORY-012).
- `409 Conflict`: show “This changed since you loaded it. Refresh and try again.” and reload.
- `422 Validation`: show inline field errors when possible; otherwise show message summary.
- `5xx/network/timeout`: show generic error with retry; timeout UX at 8 seconds with retry affordance (Inventory UX target pattern; DECISION-INVENTORY-004 applied as a general UX constraint).

## 9. Service Contracts (Frontend Perspective)

> Backend clarification as of 2026-03-30: raw Security-domain permission primitives already exist, inventory permissions are registered from `pos-inventory`, the inventory controller guard catalog has been normalized to those registered permissions, and current-user effective permissions are carried in JWT token claims.

### Load/view calls (frontend-facing endpoints/services)
1. **Get current user effective permissions**
   - Source of truth for current-user gating: JWT access token claims
   - Frontend evidence:
     - `AuthService.currentUserClaims()` decodes the access token
     - `JwtClaims.authorities?: string[]` carries effective permission keys
   - Frontend contract:
     - Read `currentUserClaims().authorities ?? []` and treat that as the current session's effective permission set
   - Raw backend primitives still exist for user-targeted admin lookup when needed:
     - `GET /v1/users/{userId}/permissions`
     - `GET /v1/users/roles/permissions/user/{userId}` (legacy)
   - Notes:
     - Must support inventory permission keys (DECISION-INVENTORY-010).
     - Must include correlation ID header handling (DECISION-INVENTORY-012).
     - No extra current-user permissions wrapper is required for this story's route/action gating.

2. **Get inventory permission catalog**
   - Raw backend primitives:
     - `GET /v1/permissions/domain/inventory`
     - `GET /v1/permissions` (fallback; client may filter `domain === 'inventory'`)
   - Response available today:
     - `PermissionDto[]`
   - Status:
     - Inventory permission catalog normalization is complete as of 2026-03-30.
   - UI must treat response as read-only.

## 11. Alternate / Error Flows

1. **Unauthorized route access**
   - If user lacks required permission for Inventory Security:
     - Do not call permission catalog services.
     - Render forbidden state with link back to Inventory home.

2. **Concurrency conflict (409)**
   - Inform user, refresh the current view, and require re-apply if needed.

3. **Session expired (401)**
   - Redirect to login/session refresh; after re-auth, return to the attempted route if app convention supports it.

## 12. Acceptance Criteria

```gherkin
Scenario: Inventory Security menu is hidden when user lacks permission-view access
  Given a logged-in user without the permission required to view inventory permission metadata
  When the user views the Inventory module navigation
  Then the "Security" entry is not shown
  And direct navigation to "/inventory/security/permissions" shows "Access denied"
  And no permission catalog data is fetched

Scenario: Inventory permission catalog loads for authorized admin
  Given a logged-in Admin with permission to view inventory permission metadata
  When the Admin opens "/inventory/security/permissions"
  Then the UI loads inventory permission definitions from backend services
  And the UI displays permission keys and descriptions
  And the UI does not allow editing permission definitions

Scenario: Protected inventory action is not available without required permission
  Given a logged-in user without the permission required for the receiving action being rendered
  When the user opens an Inventory screen where "Start Receiving" is available
  Then the "Start Receiving" action is not shown or is disabled
  And if the user invokes the action and the backend returns 403
  Then the UI shows an authorization error without leaking data

Scenario: 401 behavior follows session refresh/login convention
  Given a logged-in user whose session has expired
  When the user opens "/inventory/security/permissions"
  Then the backend returns 401
  And the UI routes to login/session refresh per app convention
```
