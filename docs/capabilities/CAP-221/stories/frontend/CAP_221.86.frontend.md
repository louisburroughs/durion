## Issue Body

## 1. Story Header

### Title
Audit: Searchable Immutable Audit Logs UI (Movements + Work Order Links) with Drilldown and Async CSV Export

### Primary Persona
Compliance Auditor (read-only, compliance-oriented)

### Business Value
Provide a tenant- and location-scoped, immutable, searchable audit trail for operational events (including inventory movements and work order linkage) so auditors can reconstruct what happened, by whom, and why, and export evidence for external review—without exposing sensitive raw payloads by default.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Compliance Auditor  
- **I want** to search and view immutable audit logs for inventory movements and their work order linkage, drill down by key identifiers, and export results  
- **So that** I can investigate incidents, support compliance reviews, and produce evidence without modifying operational data.

### In-scope
- Frontend screens (Moqui screens + Vue/Quasar UI) to:
  - Search/list audit logs with mandatory guardrails (date range + at least one indexed filter).
  - View audit log detail by `eventId`.
  - Drill down by applying filters and (optionally) navigating to related domain screens via structured deep-link metadata.
  - Request an **async** audit export job and download the resulting CSV artifact.
  - View pricing evidence links **only if present** on audit detail (snapshot/trace) and only with explicit permissions (even if not the primary focus of this story).
- Permission-gated access:
  - Search/list, detail, export, raw payload, cross-location scope, and proof fields are all separately permissioned (per audit domain rules).
- UI enforcement of immutability/read-only:
  - No create/edit/delete actions for audit records.
  - No UI affordances implying audit records can be changed.

### Out-of-scope
- Producing audit events (outbox/event emission) in inventory/workexec domains.
- Backend persistence/immutability implementation details (append-only/WORM), retention enforcement implementation.
- Defining new event types; UI must consume controlled vocabulary from meta endpoint.
- Any operational edits to movements/work orders/products/users/locations from audit screens.

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI mirrors backend; backend authoritative)
- Date range is **required** for search and export:
  - `fromUtc` required
  - `toUtc` required
  - `fromUtc <= toUtc`
- Max date window:
  - UI prevents selecting a range > **90 days** and shows inline error.
- Indexed filter requirement:
  - UI requires at least one of the indexed filters listed in UX Summary before enabling Search/Export.
- UTC handling:
  - UI may display date/time in user locale/timezone, but must send `fromUtc`/`toUtc` in UTC.

### Enable/disable rules
- Search button enabled only when:
  - date range valid and within max window, AND
  - at least one indexed filter present, AND
  - if cross-location is enabled and user selected cross-location mode, `locationIds[]` is non-empty
- Export button enabled only when:
  - user has `audit:export:execute`, AND
  - a successful search has been executed with a valid filter set (same guardrails), AND
  - UI is not already requesting an export job

### Visibility rules (permission-gated)
- Entire Audit Logs menu and screens require `audit:log:view`.
- Detail screen requires `audit:log:view-detail`:
  - If user can list but not detail, list is shown but row click is disabled and “View Detail” is hidden/disabled.
- Raw payload display requires `audit:payload:view`:
  - If not permitted, raw payload section is hidden entirely (not shown as “redacted” by UI).
- Proof fields (`hash`, `prevHash`, `signature`) require `audit:proof:view`:
  - If permitted and fields exist, show read-only with “Provided (not verified)” label unless backend provides explicit verification result.
- Cross-location location selector requires `audit:scope:cross-location`.
- Pricing evidence links/sections (if present in detail payload) require:
  - snapshot: `audit:pricing-snapshot:view`
  - trace: `audit:pricing-trace:view`

### Error messaging expectations
- 400 validation errors:
  - Map field errors to filter inputs (date range, missing indexed filter, missing locationIds for cross-location).
- 401:
  - Redirect to login/session restore per app conventions.
- 403:
  - Show “Not authorized” without revealing whether records exist.
- 404 on detail:
  - Show “Audit record not found” (generic; no additional hints).
- 429:
  - Show rate-limit message and allow retry after a short delay.
- 5xx/timeouts:
  - Show generic retryable error; do not display raw payload or sensitive request details.

- `AuditLog` (immutable stored record; append-only)

- `eventId` (UUIDv7, required, read-only) — used for detail navigation and dedupe identity
- `schemaVersion` (string/int, required, read-only)
- `eventType` (string, required, read-only; controlled vocabulary)
- `occurredAt` (UTC datetime, required, read-only)
- `emittedAt` (UTC datetime, optional, read-only)
- `tenantId` (string, read-only; not displayed by default)
- `locationId` (UUIDv7/string, required, read-only; display if permitted by scope)
- `actor` (object, optional, read-only):
  - `actorType` (string)
  - `actorId` (UUIDv7/string)
  - `displayName` (string, optional)
- `aggregateType` (string, required, read-only)
- `aggregateId` (UUIDv7/string, required, read-only)
- `changeSummaryText` (string, optional, read-only)
- `changePatch` (json/text, optional, read-only; safe-rendered)
- `reasonCode` (string, optional, read-only)
- `reasonNotes` (string, optional, read-only; length-limited; safe-rendered)
- `correlationId` (string, optional, read-only; W3C trace correlation)
- `sourceSystem` (string, optional, read-only)
- `rawPayload` (text/json, optional, read-only; restricted permission; safe-rendered)
- Deep-link metadata (optional, read-only):
  - `links[]`: `{targetDomain, targetType, targetId}` (all strings)
- Proof fields (optional, read-only; restricted permission):
  - `hash` (string)
  - `prevHash` (string)
  - `signature` (string)
  - `proofVerified` (boolean, optional; only if backend implements verification)

**Export job (frontend-visible subset)**
- `exportId` (UUIDv7/string, required)
- `status` (`PENDING|RUNNING|SUCCEEDED|FAILED|EXPIRED`, required)
- `requestedAt` (UTC datetime)
- `requestedBy` (actorId/displayName)
- `filters` (object; echo of request filters)
- `format` (`CSV`, required)
- `rowCount` (int, optional)
- `digestManifest` (object, required when SUCCEEDED):
  - `algorithm` = `SHA-256`
  - `entries[]` (file name + digest)
- `expiresAt` (UTC datetime, optional)

### Read-only vs editable by state/role
- All audit log fields are read-only for all roles.
- Export job is read-only; only actions are “request export” and “download” (permissioned).

### Derived/calculated fields
- Display timestamps in user locale/timezone; store and request in UTC.
- Display actor name:
  - Prefer `actor.displayName` from backend; do not require separate user lookup for audit UI.
- Reason code labels:
  - If `/audit/meta/reasonCodes` provides display metadata, show it; otherwise show raw `reasonCode`.

## 9. Service Contracts (Frontend Perspective)

> Concrete Moqui service names may vary; frontend must integrate via these capability endpoints and map to Moqui screens/transitions accordingly.

### Load/view calls

1) **Search audit logs**
- Method: `GET /audit/logs/search`
- Required query params:
  - `fromUtc` (ISO-8601 UTC)
  - `toUtc` (ISO-8601 UTC)
- Required additional constraint:
  - At least one indexed filter param present (any of):
    - `workOrderId`, `appointmentId`, `mechanicId`, `movementId`, `productId`, `sku`, `partNumber`, `actorId`, `eventType`, `aggregateId`, `correlationId`, `reasonCode`
- Optional params:
  - `locationIds[]` (required if cross-location search is requested; only honored with permission)
  - Pagination: `pageIndex`, `pageSize`
  - Sorting: `sortBy`, `sortOrder` (e.g., `occurredAt desc`)
- Response (minimum):
  - `items[]`: array of audit log summaries including `eventId`, `occurredAt`, `eventType`, `actor`, `aggregateType`, `aggregateId`, `locationId`, `reasonCode`, `changeSummaryText`
  - `totalCount` (int)
- Error expectations:
  - 400 with field errors for guardrail violations
  - 403 for unauthorized scope/permission
  - 429 for rate limiting

2) **Get audit log detail**
- Method: `GET /audit/logs/detail`
- Query params:
  - `eventId` (UUIDv7)
- Response (minimum):
  - Full `AuditLog` record including optional `rawPayload`, `changePatch`, `links[]`, proof fields if present
- Error expectations:
  - 403 if lacking `audit:log:view-detail`
  - 404 if not found (tenant/location scoped)

3) **Meta: event types**
- Method: `GET /audit/meta/eventTypes`
- Response:
  - `eventTypes[]`: array of `{value, label?}` (label optional; UI can display value if label absent)

4) **Meta: reason codes (optional)**
- Method: `GET /audit/meta/reasonCodes`
- Response:
  - `reasonCodes[]`: `{code, displayName?, description?}`

5) **Meta: locations (only for cross-location UI)**
- Method: `GET /audit/meta/locations`
- Response:
  - `locations[]`: `{locationId, displayName}`

### Create/update calls
- None for audit logs (immutability).
- Export request is a create of an export job (see below).

### Submit/transition calls

6) **Request export (async only)**
- Method: `POST /audit/export/request`
- Body:
  - `fromUtc`, `toUtc`
  - same indexed filters as search
  - `locationIds[]` if cross-location
  - `format`: must support `CSV` (required)
- Response:
  - `exportId`
  - initial `status`

7) **Export status**
- Method: `GET /audit/export/status?exportId=...`
- Response:
  - `exportId`, `status`, `requestedAt`, `rowCount` (optional), `digestManifest` (when succeeded), `expiresAt` (optional), `failureReason` (optional, non-sensitive)

8) **Export download**
- Method: `GET /audit/export/download?exportId=...`
- Behavior:
  - Requires `audit:export:download`
  - Returns file stream or a time-bound download token/redirect (implementation detail)
  - Must be non-enumerable and tenant-scoped

### Error handling expectations (frontend mapping)
- 400: show inline errors; do not retry automatically.
- 401: redirect to login.
- 403: show unauthorized; do not reveal existence.
- 404: show not found for detail/exportId.
- 409: if export job expired/invalid state, show message and allow re-request.
- 429: show throttling message; allow retry.
- 5xx/timeouts: show generic error; allow retry.

## 10. State Model & Transitions

### Allowed states
- Audit logs: immutable; no UI state transitions.
- Export job states (frontend-visible):
  - `PENDING` → `RUNNING` → `SUCCEEDED`
  - `PENDING|RUNNING` → `FAILED`
  - `SUCCEEDED` → `EXPIRED` (optional, time-bound downloads)

### Role-based transitions
- `audit:log:view`: access AuditLogSearch screen and run searches (within scope).
- `audit:log:view-detail`: open AuditLogDetail.
- `audit:export:execute`: request export job.
- `audit:export:download`: download export artifact.
- `audit:scope:cross-location`: enable location multi-select and allow cross-location queries (must include `locationIds[]`).
- `audit:payload:view`: view raw payload section on detail.
- `audit:proof:view`: view proof fields if present.

### UI behavior per state
- Export Status screen:
  - `PENDING/RUNNING`: show progress state and polling (manual refresh allowed; auto-poll interval per UI convention).
  - `SUCCEEDED`: show download button and digest manifest summary.
  - `FAILED`: show failure message (non-sensitive) and “Request again” action.
  - `EXPIRED`: show expired message and “Request again” action.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing date range:
  - Search/Export disabled; inline message: “Date range is required.”
- Date range > 90 days:
  - Inline message: “Maximum range is 90 days.”
- Missing indexed filter:
  - Inline message: “Add at least one filter (e.g., Movement ID, Work Order ID, Event Type).”
- Cross-location selected but no locations chosen:
  - Inline message: “Select at least one location.”

### Backend validation failures (400)
- UI displays backend-provided field errors; if backend returns a general guardrail error, show it at top of form.

### Concurrency / stale data
- Detail record removed is not expected (immutability), but if backend returns 404:
  - Show not found and provide link back to search.
- Export job expired/not found:
  - Show message and allow re-request with same filters.

### Unauthorized access
- User without `audit:log:view` attempts direct URL:
  - Show unauthorized page; do not show filters/results.
- User with list permission but without detail permission:
  - List works; detail navigation disabled; deep link to detail shows unauthorized.
- User without `audit:payload:view`:
  - Raw payload section hidden; no “request access” flow in this story.

### Empty states
- Before first search:
  - Show guidance explaining required date range + at least one filter.
- After search with no results:
  - Show “No audit records match these filters.”
  - Export remains enabled/disabled based on product decision: **disabled** when zero results (UI ergonomics; backend may still allow export, but UI should prevent pointless jobs).

## 12. Acceptance Criteria

### Scenario: Search requires date range and at least one indexed filter
Given I am authenticated and have permission "audit:log:view"  
When I open the Audit Logs screen  
Then I cannot execute Search until I provide fromUtc and toUtc  
And I cannot execute Search until I provide at least one indexed filter beyond the date range  
And I see inline guidance explaining the requirements

### Scenario: Search enforces max 90-day window
Given I am authenticated and have permission "audit:log:view"  
When I set fromUtc and toUtc to a range greater than 90 days  
Then the UI blocks Search  
And I see an inline validation message stating the maximum range is 90 days

### Scenario: View audit log list (movement filter)
Given I am authenticated and have permission "audit:log:view"  
And I provide a valid UTC date range within 90 days  
And I provide a movementId filter  
When I click Search  
Then the UI calls GET "/audit/logs/search" with fromUtc, toUtc, and movementId  
And I see a paginated list of matching audit records  
And each row shows occurredAt, eventType, actor (name or id), aggregateType, and aggregateId

### Scenario: View audit log detail by eventId
Given I am authenticated and have permissions "audit:log:view" and "audit:log:view-detail"  
And I have search results  
When I open an audit record  
Then the UI navigates to the detail screen with eventId  
And the UI calls GET "/audit/logs/detail?eventId=..."  
And I see the audit record fields rendered read-only  
And I do not see any create/edit/delete controls

### Scenario: Raw payload is hidden without permission
Given I am authenticated and have permissions "audit:log:view" and "audit:log:view-detail"  
And I do not have permission "audit:payload:view"  
When I view an audit log detail  
Then I do not see the rawPayload section even if the record contains rawPayload

### Scenario: Raw payload is safely rendered with permission
Given I am authenticated and have permissions "audit:log:view-detail" and "audit:payload:view"  
When I view an audit log detail that includes rawPayload  
Then rawPayload is displayed as escaped text (not interpreted as HTML)  
And no scripts or markup in rawPayload execute in the browser

### Scenario: Cross-location search requires permission and explicit locationIds
Given I am authenticated and have permission "audit:log:view"  
And I do not have permission "audit:scope:cross-location"  
When I open the Audit Logs screen  
Then I do not see a location multi-select control  
And any attempt to pass locationIds in the URL does not enable cross-location UI behavior

Given I am authenticated and have permissions "audit:log:view" and "audit:scope:cross-location"  
When I select multiple locations and run a search  
Then the UI includes locationIds[] in the GET "/audit/logs/search" request

### Scenario: Request async CSV export and download
Given I am authenticated and have permissions "audit:log:view" and "audit:export:execute"  
And I have executed a successful search with a valid filter set  
When I click "Export CSV"  
Then the UI calls POST "/audit/export/request" with the same filters and format "CSV"  
And I am shown an export status view for the returned exportId

Given I am authenticated and have permission "audit:export:download"  
And the export status becomes "SUCCEEDED"  
When I click Download  
Then the UI calls GET "/audit/export/download?exportId=..."  
And I receive a CSV file download  
And the export status view shows a SHA-256 digest manifest when provided by the backend

### Scenario: Unauthorized access does not leak existence
Given I am authenticated and do not have permission "audit:log:view-detail"  
When I navigate directly to an audit detail URL with an eventId  
Then I see an unauthorized message  
And no audit record fields are displayed
