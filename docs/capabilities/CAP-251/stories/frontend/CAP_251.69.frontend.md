## Issue Body

## Title
[FRONTEND] [STORY] Accounting: Display Accounting Posting/Ingestion Status on Invoice Detail (Authoritative, Permission-Gated, Drilldown + History)

## Primary Persona
Cashier (secondary: Service Advisor, Manager/Supervisor, Accounting Ops, Auditor)

## Business Value
Reduce customer disputes and internal confusion by showing **backend-authoritative accounting processing/posting visibility** for an invoice (including ingestion outcomes, posting references, and auditability) directly on the POS Invoice Detail screen, without implying or inventing accounting policy.

---

# 2. Story Intent

## As a / I want / So that
- **As a Cashier**, I want the invoice screen to display accounting’s authoritative processing/posting visibility so that I can confidently answer customer questions and route exceptions without leaving POS.

## In-scope
- Add an **Accounting Status** section to the existing **Invoice Detail** screen that:
  - Displays backend-authoritative ingestion/processing status for the invoice’s accounting event(s) (e.g., `InvoiceIssued` ingestion record).
  - Displays timestamps (`receivedAt`, `processedAt` if provided) and idempotency outcome.
  - Displays posting references (primary: `journalEntryId`; secondary: `ledgerTransactionId`) when provided and permitted (**Decision AD-011**).
  - Displays a curated `payloadSummary` by default; raw payload JSON only with explicit permission (**Decision AD-009**).
  - Provides a **manual refresh** action that re-fetches current status (read-only refresh; no posting changes) and is permission-gated.
  - Provides a **history view** (list) of ingestion records for the invoice (read-only).
  - Provides deep links/navigation to Accounting detail screens where available (journal entry view) without assuming external SSO mechanics.

## Out-of-scope
- Implementing backend ingestion, posting, or event consumers.
- Changing invoice lifecycle, issuance, or posting logic (Billing/Accounting backend owned).
- Defining GL accounts, posting rules, or journal entry line details.
- Implementing reversal workflows.
- Constructing external accounting URLs from guessed patterns (only use backend-provided URLs or internal Moqui routes).

---

# 3. Actors & Stakeholders

- **Cashier**: Needs simple “Processed/Rejected/Quarantined” visibility and last update time; minimal sensitive details.
- **Service Advisor**: Uses status to inform follow-up and collections.
- **Manager/Supervisor**: Needs exception visibility and ability to refresh.
- **Accounting Ops**: Needs full ingestion detail, idempotency outcome, posting references, and (if permitted) raw payload for troubleshooting.
- **Auditor/Compliance**: Read-only access; may view payload only if explicitly granted; never executes mutations.

# 4. Preconditions & Dependencies

## Preconditions
- An invoice exists and can be opened in POS (invoiceId available).
- Billing domain has issued the invoice and emitted `InvoiceIssued` (or other relevant accounting events), OR the invoice is not yet issued (in which case accounting status may be absent).
- Accounting domain exposes ingestion monitoring read model (`AccountingEventIngestionRecord`) (**Decision AD-007**).

## Dependencies (implementation)
- Backend endpoints available (normative families):
  - `GET /accounting/ingestion/list` (filterable by `invoiceId`)
  - `GET /accounting/ingestion/detail?ingestionId=...`
- Optional backend endpoint for “refresh” semantics:
  - If refresh is simply reloading list/detail, no special endpoint is needed.
  - If backend supports a “retry/reprocess” command, it is **out of scope** for Cashier; do not include unless explicitly requested. (Retry is a separate permission and async job: **Decision AD-014**.)
- Permissions available to frontend (normative tokens, **Decision AD-013**):
  - View ingestion monitoring: `accounting:events:view`
  - View raw payload JSON: `accounting:events:view-payload`
  - (Optional, not used unless added later) Retry ingestion: `accounting:events:retry`

- Invoice Detail remains the primary context.

- “View journal entry” navigates to Accounting journal entry detail screen **only if** a route exists and `journalEntryId` is present; otherwise show as copyable ID only.

## User workflows (happy + alternate)

### Happy path: processed + posted reference available
1. User opens Invoice Detail.
2. UI loads invoice (existing) and loads latest ingestion record(s) filtered by `invoiceId`.
3. UI shows:
   - `processingStatus = PROCESSED`
   - `idempotencyOutcome`
   - `receivedAt` (and `processedAt` if provided)
   - `journalEntryId` link (if route exists and user permitted)
4. User can open “History” to see prior ingestion records.

### Alternate: rejected
1. Latest ingestion record shows `processingStatus = REJECTED`.
2. UI shows banner with backend-provided `errorCode` and safe `errorMessage`.
3. UI shows “History” and “View ingestion detail” link for authorized users.

### Alternate: quarantined / duplicate conflict
1. Latest ingestion record shows `processingStatus = QUARANTINED` and/or `idempotencyOutcome = DUPLICATE_CONFLICT`.
2. UI shows prominent banner indicating quarantined/conflict and displays backend-provided error fields and any duplicate linkage fields if present.

### Alternate: invoice not issued / no ingestion record
1. Ingestion list returns empty for `invoiceId`.
2. UI shows “No accounting ingestion record yet” (neutral) and does not imply failure.

### Alternate: permission-limited user
1. If user lacks `accounting:events:view`, the Accounting section entry point is hidden (deny-by-default) (**Decision AD-013**).
2. If user can view but lacks `accounting:events:view-payload`, payload sections show “Restricted” and are not fetched/rendered.

# 6. Functional Behavior

## Triggers
- Invoice Detail screen load with `invoiceId`.
- User clicks “Refresh” in Accounting section (re-fetch list/detail).
- User opens “History”.
- User clicks “View ingestion detail”.
- User clicks “Copy IDs” (invoiceId, ingestionId, eventId, journalEntryId).

## UI actions
- On load:
  - Load invoice (existing POS service).
  - Call ingestion list endpoint filtered by `invoiceId`, sorted by `receivedAt desc`, pageSize small (e.g., 10) to get latest + recent history.
  - Display the latest record summary inline; provide “View history” to open full list (paginated).
- Refresh:
  - Re-run ingestion list call; update displayed latest record.
  - No mutation is performed; this is a read refresh.
- Detail:
  - Navigate to ingestion detail screen with `ingestionId`.
  - In detail, show:
    - envelope identifiers: `eventId`, `eventType`, `schemaVersion`, `sourceModule` (if provided)
    - timestamps: `receivedAt`, `processedAt` (if provided), `occurredAt` (if provided)
    - `processingStatus`, `idempotencyOutcome`
    - posting references: `journalEntryId` (primary), `ledgerTransactionId` (secondary) (**Decision AD-011**)
    - `payloadSummary` always (if provided)
    - raw payload JSON only if permitted (**Decision AD-009**)
- Discrepancy banner:
  - This story does **not** compute mismatch between POS operational status and accounting status (avoid inventing policy).
  - Only show discrepancy/conflict indicators when backend explicitly provides them via ingestion fields:
    - `processingStatus = QUARANTINED` OR `idempotencyOutcome = DUPLICATE_CONFLICT` OR `processingStatus = REJECTED`.

## State changes (frontend-visible)
- None. UI is read-only; it reflects backend ingestion record state.

## Service interactions
- Invoice load (existing POS invoice service; unchanged by this story).
- Accounting ingestion list/detail:
  - `GET /accounting/ingestion/list`
  - `GET /accounting/ingestion/detail?ingestionId=...`
- No “viewed” audit write is performed in this story (auditability is provided by backend ingestion records; adding explicit “viewed” events would be a new backend contract and is out-of-scope).

# 7. Business Rules (Translated to UI Behavior)

## Validation
- Validate UUIDv7 format client-side for:
  - `invoiceId`, `ingestionId`, `eventId`, `journalEntryId`, `ledgerTransactionId` when used as inputs/search params (**Decision AD-006**).
- Date/time display:
  - Do not reinterpret timestamps; display as provided, using standard UI formatting.

## Enable/disable rules
- Accounting section:
  - Visible only if user has `accounting:events:view` (**Decision AD-013**).
- Refresh button:
  - Visible if section visible; always enabled unless request in-flight.
  - Disabled while list call is in-flight.
- Raw payload panel:
  - Visible only if user has `accounting:events:view-payload` (**Decision AD-009**, **AD-013**).
  - If not permitted, show a restricted placeholder and do not fetch raw payload if backend supports separate fields/endpoints; if raw payload is included in the same response, do not render it.

## Visibility rules
- Banner severity:
  - `PROCESSED`: neutral/success, no banner.
  - `REJECTED`: error banner with `errorCode` + safe `errorMessage`.
  - `QUARANTINED`: critical banner indicating quarantined; show `errorCode`/`errorMessage` and `idempotencyOutcome`.
  - `idempotencyOutcome = DUPLICATE_CONFLICT`: warning/critical banner even if processingStatus present; do not infer resolution.
- Posting references:
  - Show `journalEntryId` as primary reference; link only if an internal route exists and user has `accounting:events:view` (and any additional journal entry permission if required by the app’s authz model).
  - Show `ledgerTransactionId` only as secondary display if present (**Decision AD-011**).

## Error messaging expectations
- 401/403: show “Access denied” without revealing whether the invoice has ingestion records (**Decision AD-013**).
- 404 on detail: show “Record not found” (safe).
- 5xx/timeouts: show “Temporarily unavailable. Try again.” and keep last displayed data.

# 12. Acceptance Criteria

## Scenario 1: Authorized user sees latest ingestion status on invoice
**Given** an invoice exists with `invoiceId`  
**And** the user has permission `accounting:events:view`  
**And** `GET /accounting/ingestion/list?invoiceId=<invoiceId>` returns at least one record  
**When** the user opens the Invoice Detail screen  
**Then** the UI displays an Accounting section showing the latest ingestion record’s `processingStatus`, `idempotencyOutcome`, and `receivedAt`  
**And** the UI provides a “View history” action to view additional records.

## Scenario 2: Rejected ingestion shows error banner
**Given** the user has permission `accounting:events:view`  
**And** the latest ingestion record has `processingStatus = REJECTED`  
**And** the record includes `errorCode` and `errorMessage`  
**When** the user views the invoice  
**Then** the UI shows an error banner indicating the invoice’s accounting ingestion was rejected  
**And** the banner displays `errorCode` and the safe `errorMessage`  
**And** the UI provides a link to “View ingestion detail”.

## Scenario 3: Quarantined / duplicate conflict is prominently visible
**Given** the user has permission `accounting:events:view`  
**And** the latest ingestion record has `processingStatus = QUARANTINED` **or** `idempotencyOutcome = DUPLICATE_CONFLICT`  
**When** the user views the invoice  
**Then** the UI shows a prominent banner indicating quarantined/conflict status  
**And** the UI displays the `idempotencyOutcome` value  
**And** the UI does not claim the invoice is posted or not posted unless posting references are explicitly present.

## Scenario 4: Posting references are shown with correct precedence and permission gating
**Given** the user has permission `accounting:events:view`  
**And** the ingestion record includes `journalEntryId` and optionally `ledgerTransactionId`  
**When** the user views the Accounting section  
**Then** the UI displays `journalEntryId` as the primary posting reference  
**And** the UI displays `ledgerTransactionId` only as a secondary reference when present.

## Scenario 5: Raw payload is restricted by permission
**Given** the user has permission `accounting:events:view`  
**And** the user does **not** have permission `accounting:events:view-payload`  
**When** the user views ingestion detail  
**Then** the UI displays `payloadSummary` if provided  
**And** the UI does not render raw payload JSON and shows a “Restricted” placeholder instead.

**Given** the user also has permission `accounting:events:view-payload`  
**When** the user views ingestion detail  
**Then** the UI renders raw payload JSON safely (no HTML execution)  
**And** the UI does not log the payload content.

## Scenario 6: Empty ingestion list is handled without inference
**Given** the user has permission `accounting:events:view`  
**And** `GET /accounting/ingestion/list?invoiceId=<invoiceId>` returns zero records  
**When** the user views the invoice  
**Then** the UI shows “No accounting ingestion record yet”  
**And** the UI does not show rejected/quarantined banners.

## Scenario 7: Refresh re-fetches without mutation
**Given** the user has permission `accounting:events:view`  
**When** the user clicks “Refresh” in the Accounting section  
**Then** the UI re-calls `GET /accounting/ingestion/list?invoiceId=<invoiceId>`  
**And** updates the displayed latest record if changed  
**And** does not call any mutation endpoint.

## Scenario 8: Unauthorized users do not see the accounting section
**Given** the user does not have permission `accounting:events:view`  
**When** the user opens Invoice Detail  
**Then** the Accounting section is not displayed  
**And** no ingestion list calls are made from the client for that user session.
