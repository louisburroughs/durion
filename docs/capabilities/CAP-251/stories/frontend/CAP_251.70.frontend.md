## 1. Story Header

### Title
[FRONTEND] [STORY] Accounting: Display Invoice Payment Application Status & Accounting Posting/Ingestion Outcome on Invoice Detail

### Primary Persona
- **POS cashier / store manager** viewing an invoice in POS
- **Accounting ops / reconciliation staff** investigating payment application and posting/ingestion outcomes

**Persona Metadata**
- `primary_persona`: `POS cashier / store manager viewing an invoice in POS`
- `canonical_persona`: `Customer Support Associate`
- `persona_family`: `Customer Support Associate`
- `actor_type`: `human`

### Business Value
- Reduce customer balance disputes by showing **backend-authoritative** invoice balance/payment application state.
- Enable faster reconciliation by surfacing **ingestion/posting outcomes** (processed/rejected/quarantined, idempotency outcome, journal entry reference, error codes) without implying policy or mutating accounting state.

---

## 2. Story Intent

### As a / I want / So that
- **As a** POS user viewing an invoice,
- **I want** to see the invoice’s current **AR/payment application status** and the latest **accounting ingestion/posting outcome** references and errors,
- **So that** I can confirm whether the invoice is unpaid/partially paid/paid and whether accounting processing/posting succeeded or needs follow-up.

### In-scope
- Add a read-only “Payment & Posting” section on invoice detail that shows:
  - invoice balance due and payment application summary (paid/applied amounts, outstanding)
  - latest relevant identifiers (paymentId(s), paymentApplicationId(s) if provided, eventId/ingestionId, journalEntryId)
  - ingestion/posting outcome status and error details (safe, backend-provided)
- Manual refresh and on-navigation reload behavior.
- Permission-gated visibility for sensitive payload fields (if any are exposed by backend).

### Out-of-scope
- Capturing/voiding/refunding payments (Payment domain).
- Applying payments from invoice screen (Accounting AR apply workflow is separate story).
- Editing invoice totals, issuing invoices (Billing domain).
- Retrying ingestion/reprocessing from this invoice screen (handled by ingestion monitoring screens).

---

## 3. Actors & Stakeholders
- **Cashier / POS user:** needs simple clarity on “Balance due / Paid”.
- **Store manager:** needs visibility into “processing/posting failed” indicators and what to do next.
- **Accounting ops / reconciliation:** needs ingestion status, idempotency outcome, journal entry reference, error codes/messages.
- **Accounting domain services:** system of record for AR application effects and ingestion monitoring read models (AD-002, AD-007).
- **Billing domain:** system of record for invoice issuance; accounting consumes `InvoiceIssued` events (boundary).
- **Payment domain:** system of record for payment capture/refund execution; accounting shows read models only (AD-001).

### State changes
- Frontend-only state: `loading`, `loaded`, `error`.
- No mutations.

### Service interactions
Frontend calls **accounting-owned** endpoints for ingestion visibility and (if available) invoice AR summary:

1. **Invoice AR/payment application summary (accounting read model)**
   - If backend already exposes an accounting invoice AR summary endpoint, use it.
   - If not, the UI must rely on invoice detail’s existing balance fields and only add ingestion calls.
   - (See Service Contracts for required/optional calls.)

2. **Ingestion record lookup**
   - Use `/accounting/ingestion/list` filtered by `invoiceId` and event types relevant to invoices (at minimum `InvoiceIssued`; optionally `InvoiceAdjusted`, `CreditMemoIssued`).
   - Then load `/accounting/ingestion/detail` for the selected ingestion record (latest by `receivedAt`).

**Decision rationale applied**
- Do not infer posting success from payment receipt; only show AR reduction via applications/balance due (AD-002).
- Ingestion monitoring is the authoritative ops visibility model; show backend enums as-is (AD-007).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `invoiceId` is required and must be a valid UUIDv7 (AD-006). If invalid:
  - show inline error “Invalid invoice ID format”
  - do not call backend.

### Enable/disable rules
- “Refresh” enabled when `invoiceId` valid; disabled while loading.

### Visibility rules
- Show **Ingestion/Posting Status** block if user has `accounting:events:view`; otherwise hide the block entirely (deny by default; AD-013).
- Show **Raw payload JSON** only if backend provides it AND user has `accounting:events:view-payload` (AD-009, AD-013). Otherwise show “Restricted”.
- Show **Quarantined/Rejected** banner when `processingStatus` is `QUARANTINED` or `REJECTED`.
- Show **Duplicate conflict** indicator when `idempotencyOutcome = DUPLICATE_CONFLICT`.

### Error messaging expectations
- 401: follow app convention (redirect/login) without showing invoice data.
- 403: “Access denied.”
- 404: “Invoice not found.” (only when invoice detail itself is 404; ingestion 404 is treated as “no ingestion record”)
- 409: “Data changed. Refresh to load latest.”
- 5xx/timeout: “Unable to load payment/posting status. Try again.”

## 9. Service Contracts (Frontend Perspective)

### Load/view calls

1) **Ingestion list (by invoice)**
- `GET /accounting/ingestion/list`
  - Query params:
    - `invoiceId` (UUIDv7, required)
    - `eventType` (optional repeatable or comma-separated): at minimum `InvoiceIssued`; optionally include `InvoiceAdjusted`, `CreditMemoIssued`
    - pagination: `pageIndex`, `pageSize`
    - sorting: `orderBy=receivedAt desc` (or equivalent)
  - Response: list of ingestion record summaries including `ingestionId`, `receivedAt`, `processingStatus`, `idempotencyOutcome`, `eventType`, `eventId`, and posting refs if included in summary.

2) **Ingestion detail**
- `GET /accounting/ingestion/detail?ingestionId=...`
  - Response: full ingestion record including `payloadSummary`, errors, posting refs.
  - Raw payload JSON (if returned) must be permission-gated in UI (AD-009).

3) **Invoice AR summary (optional; only if backend provides)**
- If available, use an accounting-owned read endpoint (not defined in the provided accounting guide). If not available, do not invent it; rely on existing invoice detail fields.

### Create/update calls
- None.

### Submit/transition calls
- None.

### Error handling expectations
- Treat ingestion list 404/empty list as “No ingestion record found” (not an error).
- For ingestion endpoints:
  - 403: hide ingestion block entirely (deny by default; AD-013).
  - 401: follow app auth flow.
- Never log or persist raw payloads client-side (AD-009).

## 10. State Model & Transitions

### Allowed states
**UI-derived invoice payment display state (not a backend enum)**
- `UNPAID` | `PARTIALLY_PAID` | `PAID` | `UNKNOWN`

**Ingestion processing status (backend enum; AD-007)**
- `PROCESSED` | `REJECTED` | `QUARANTINED`

**Idempotency outcome (backend enum; AD-007)**
- `NEW` | `DUPLICATE_IGNORED` | `DUPLICATE_CONFLICT`

### Role-based transitions
- None.

### UI behavior per state
- `PROCESSED`: show “Processed” and posting refs if present.
- `REJECTED`: show “Rejected” banner with error code/message; suggest checking ingestion monitoring.
- `QUARANTINED`: show “Quarantined” banner; highlight `DUPLICATE_CONFLICT` if present.
- `DUPLICATE_IGNORED`: show “Duplicate ignored (no new posting created)” (wording only; no inference beyond enum meaning).
- `DUPLICATE_CONFLICT`: show “Duplicate conflict” and prompt ops follow-up.

## 11. Alternate / Error Flows

### Validation failures

### Concurrency conflicts

## 12. Acceptance Criteria

### Scenario: Invoice shows paid status derived from balance due
**Given** I am an authenticated user who can view invoice detail  
**And** the invoice detail response includes `totalAmount` and `balanceDue=0`  
**When** I open the invoice detail screen for that invoice  
**Then** the “Payment & Posting” section displays Payment Status = “Paid”  
**And** displays Balance Due = 0 formatted in the invoice currency.

### Scenario: Invoice shows partially paid status derived from balance due
**Given** I can view invoice detail  
**And** the invoice has `totalAmount > balanceDue > 0`  
**When** I view the invoice  
**Then** the section displays Payment Status = “Partially Paid”  
**And** displays the current Balance Due.

### Scenario: Invoice shows unpaid status derived from balance due
**Given** I can view invoice detail  
**And** the invoice has `balanceDue == totalAmount`  
**When** I view the invoice  
**Then** the section displays Payment Status = “Unpaid”  
**And** displays the current Balance Due.

### Scenario: Ingestion status is visible to authorized users
**Given** I have permission `accounting:events:view`  
**And** `/accounting/ingestion/list` returns at least one record for the invoice  
**When** I view the invoice  
**Then** the UI displays the latest ingestion record’s `processingStatus` and `idempotencyOutcome`  
**And** displays `eventId` and `ingestionId` as read-only identifiers  
**And** displays `journalEntryId` when present.

### Scenario: Ingestion rejected shows error banner
**Given** I have permission `accounting:events:view`  
**And** ingestion detail returns `processingStatus=REJECTED` with `errorCode` and `errorMessage`  
**When** I view the invoice  
**Then** the UI shows a “Rejected” banner  
**And** displays the backend-provided error code and message  
**And** does not imply any automatic retry or resolution.

### Scenario: Ingestion quarantined + duplicate conflict is highlighted
**Given** I have permission `accounting:events:view`  
**And** ingestion detail returns `processingStatus=QUARANTINED` and `idempotencyOutcome=DUPLICATE_CONFLICT`  
**When** I view the invoice  
**Then** the UI shows a “Quarantined” banner  
**And** indicates “Duplicate conflict”  
**And** provides the ingestion identifiers for ops follow-up.

### Scenario: User without accounting events permission does not see ingestion block
**Given** I can view invoice detail  
**And** I do not have permission `accounting:events:view`  
**When** I view the invoice  
**Then** the UI does not display the ingestion/posting outcome block  
**And** the UI does not call `/accounting/ingestion/*`.

### Scenario: Raw payload is restricted unless permitted
**Given** I have permission `accounting:events:view` but not `accounting:events:view-payload`  
**And** ingestion detail includes a raw payload field (if provided by backend)  
**When** I view the invoice  
**Then** the UI shows only `payloadSummary` (if present)  
**And** shows “Restricted” for raw payload content  
**And** does not render or log raw payload JSON.

### Scenario: Manual refresh reloads data
**Given** I am viewing an invoice detail page with a valid `invoiceId`  
**When** I click “Refresh”  
**Then** the UI re-fetches ingestion list/detail (and any invoice summary data used by the section)  
**And** updates the displayed values to match the latest response.

### Scenario: Invalid invoiceId is blocked client-side
**Given** I navigate to invoice detail with `invoiceId=not-a-uuid`  
**When** the “Payment & Posting” section initializes  
**Then** the UI shows an inline validation error for invoiceId  
**And** does not call `/accounting/ingestion/list`.
