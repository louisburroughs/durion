## 1. Story Header

### Title
[FRONTEND] [STORY] Rules: Maintain Substitute Relationships and Equivalency Types (Admin UI)

### Primary Persona
Product Admin (with inventory/catalog administration responsibilities)

**Persona Metadata**
- `primary_persona`: `Product Admin (with inventory/catalog administration responsibilities)`
- `canonical_persona`: `Product Administrator`
- `persona_family`: `Product Administration`

### Business Value
Enable the business to define and manage part substitute relationships (equivalent/alternative/upgrade/downgrade) so execution workflows can suggest viable alternatives when an item is unavailable, while enforcing “auto-suggest vs approval-required” policy and maintaining a complete audit trail.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Product Admin  
- **I want** to create, view, update, search, and deactivate substitute links between parts with an equivalency type and auto-suggest flag  
- **So that** work order execution can reliably query substitute candidates and respect policy (automatic suggestion vs requires approval), with traceable history for compliance.

### In-scope
- Moqui-based Admin UI screens to:
  - Select a base part via search/picker
  - List substitutes for the selected base part (query-by-part default)
  - Create a substitute link for the selected base part
  - View substitute link details (including audit/metadata)
  - Update a substitute link (non-key fields only) with optimistic locking (`version` if provided)
  - Deactivate (soft-delete) a substitute link (`isActive=false`)
- Frontend validation aligned with domain rules:
  - Required fields
  - Enum validation
  - Unique constraint handling for `(partId, substitutePartId)` with duplicate signaling
  - Version conflict handling (409)
- Display of audit-related metadata exposed by backend responses (created/updated fields, correlationId on errors).

### Out-of-scope
- Runtime substitution application UX for work orders/estimates (workexec domain).
- Inventory availability ranking logic (server-side) beyond displaying returned metadata.
- Creating/editing parts/catalog items (product/catalog domain).
- Defining approval policies beyond selecting the `isAutoSuggest` flag.
- Building/defining backend endpoints or schemas beyond what is required to wire the UI (this story assumes endpoints exist; gaps are captured as risks).

## 4. Preconditions & Dependencies
- User is authenticated in the Moqui frontend and authorized to manage substitutes.
- IDs are treated as opaque strings in the UI (no UUID/numeric validation).
- Backend supports:
  - Query substitutes by base part (required default): `GET /rest/api/v1/inventory/parts/{partId}/substitutes`
  - Create substitute link: `POST /rest/api/v1/inventory/substitutes`
  - Get substitute link detail: `GET /rest/api/v1/inventory/substitutes/{substituteLinkId}`
  - Update substitute link: `PUT /rest/api/v1/inventory/substitutes/{substituteLinkId}`
  - Deactivate substitute link (soft): `DELETE /rest/api/v1/inventory/substitutes/{substituteLinkId}` (interpreted as `isActive=false`)
- Part lookup endpoint exists for picker/search with pagination:
  - `GET /rest/api/v1/product/parts?query=...&pageIndex=...&pageSize=...` (or equivalent).
- Standard error envelope is used for 400/409/403 with `correlationId`, optional `fieldErrors[]`, and optional `existingResourceId` for duplicates.
- UI sends `Idempotency-Key` header for create/deactivate/update mutations and reuses it on retry for the same attempt.

## 7. Business Rules (Translated to UI Behavior)

### Validation
Client-side validation mirrors server rules but server remains authoritative.

**Create validations**
- `partId`: required (from base part context)
- `substitutePartId`: required; must not equal `partId`
- `substituteType`: required; allowed values:
  - `EQUIVALENT`, `APPROVED_ALTERNATIVE`, `UPGRADE`, `DOWNGRADE`
- `isAutoSuggest`: required boolean; default `false` (UI sends explicit value)
- `priority`: integer; default `100` (UI sends explicit value)
- Optional effective dates:
  - If both provided: `effectiveFrom <= effectiveTo`

**Update validations**
- Same as create for editable fields.
- `partId` and `substitutePartId` are not editable.
- `version`:
  - If the API returns a `version` field, UI must include it on update.
  - If the API does not provide `version`, UI performs update without it and relies on server-side conflict handling (still expects 409 for conflicts where supported).

### Enable/disable rules
- Save disabled until required fields valid.
- Deactivate disabled if already inactive.
- Update disabled if no changes detected (UI ergonomics).

### Visibility rules
- Audit metadata displayed read-only when present:
  - createdAt/createdBy, updatedAt/updatedBy, version, isActive
- Show “Inactive” badge when `isActive=false`.
- Show “Not effective yet” / “Expired” badges based on effective dates (display-only).

### Error messaging expectations (standard envelope)
- 400: show field-level errors from `fieldErrors[]` when present; else banner “Validation failed.”
- 403: banner “You do not have permission to manage substitutes.”
- 404: “Substitute link not found” with navigation back to base part list.
- 409 duplicate: banner “This substitute relationship already exists.” If `existingResourceId` present, show “Open existing”.
- 409 version conflict: banner “This substitute link was updated by someone else. Reload and re-apply changes.” Provide Reload action.

## 9. Service Contracts (Frontend Perspective)

Base path uses Moqui REST convention shown in domain docs (`/rest/api/v1/...`).

### Load/view calls
- **Part search (picker):**
  - `GET /rest/api/v1/product/parts?query={text}&pageIndex={n}&pageSize={n}`
  - 200: `{ items: PartSummary[], pageIndex, pageSize, totalCount }` (shape may vary; UI must support pagination)
- **List substitutes for base part (required):**
  - `GET /rest/api/v1/inventory/parts/{partId}/substitutes?isActive=true|false|all&pageIndex=&pageSize=`
  - 200: paginated list (preferred) or array; UI supports both by adapting
- **Get substitute link detail:**
  - `GET /rest/api/v1/inventory/substitutes/{substituteLinkId}`
  - 200: SubstituteLink

### Create/update calls
- **Create substitute link:**
  - `POST /rest/api/v1/inventory/substitutes`
  - Headers:
    - `Idempotency-Key: <uuid>`
  - Body:
    - `partId`, `substitutePartId`, `substituteType`, `isAutoSuggest`, `priority`, `effectiveFrom?`, `effectiveTo?`
  - 201: created SubstituteLink (must include id; should include version if supported)
  - Errors:
    - 400 standard envelope with `fieldErrors[]`
    - 409 standard envelope with `existingResourceId` for duplicates
    - 403 standard envelope
- **Update substitute link:**
  - `PUT /rest/api/v1/inventory/substitutes/{substituteLinkId}`
  - Headers:
    - `Idempotency-Key: <uuid>` (recommended for retry safety)
  - Body:
    - Editable fields only + `version` if present in loaded resource
  - 200: updated SubstituteLink
  - Errors:
    - 400, 403, 404
    - 409 for version conflict (standard envelope)

### Submit/transition calls
- **Deactivate substitute link (soft):**
  - `DELETE /rest/api/v1/inventory/substitutes/{substituteLinkId}`
  - Headers:
    - `Idempotency-Key: <uuid>`
  - 200 or 204: success
  - Errors: 403/404/409 (if constrained)

### Error handling expectations
Standard error envelope (DECISION-INVENTORY-011):
```json
{
  "code": "DUPLICATE|VALIDATION|CONFLICT|FORBIDDEN|NOT_FOUND|...",
  "message": "Human readable",
  "correlationId": "c-123",
  "fieldErrors": [{"field":"priority","message":"Must be >= 0"}],
  "existingResourceId": "SUB-1"
}
```
UI must:
- Display `message`
- Render `fieldErrors` inline when present
- Display `correlationId` in the error banner (copyable)

## 11. Alternate / Error Flows

### Validation failures
- Client-side blocks obvious invalid entries.
- Server-side 400 returns field errors; UI maps to fields and keeps user input.

### Concurrency conflicts
- 409 on update:
  - Show conflict banner with Reload action.
  - Reload refetches detail and resets form to server values.

### Unauthorized access
- 403 on any mutation:
  - Show permission banner.
  - Disable mutation controls for the remainder of the screen session to reduce repeated failures.

### Empty states
- No base part selected:
  - Prompt to select a base part to view substitutes.
- No substitutes for selected base part:
  - “No substitutes configured for this part” with CTA “Add Substitute”.
- Show inactive toggle:
  - If enabled and still empty: “No substitutes (including inactive) for this part.”

## 12. Acceptance Criteria

### Scenario 1: Select base part and view substitutes (default active-only)
Given I am authenticated as a Product Admin  
When I open the “Rules → Substitutes” screen  
And I select a base part using the part search picker  
Then the UI calls `GET /rest/api/v1/inventory/parts/{partId}/substitutes` with `isActive=true` (or equivalent default)  
And I see the returned substitute links in the order provided by the server.

### Scenario 2: Create a substitute link (happy path)
Given I am authenticated as a Product Admin  
And I have selected a base part P on the Substitutes screen  
When I click “Add Substitute”  
And I select substitute part S (S != P)  
And I select substituteType = "EQUIVALENT"  
And I set isAutoSuggest = false  
And I leave priority blank  
And I click Save  
Then the UI sends `POST /rest/api/v1/inventory/substitutes` with `priority=100` and `isAutoSuggest=false` explicitly  
And includes an `Idempotency-Key` header  
And I see a success message  
And I am navigated to the substitute link detail screen showing the new link id.

### Scenario 3: Prevent creating a self-substitute
Given I am on the “Add Substitute” screen for base part P  
When I attempt to select substitute part P  
Then the UI blocks Save  
And I see an inline error stating the substitute part must be different from the base part.

### Scenario 4: Handle duplicate substitute link conflict with existingResourceId
Given a substitute link already exists for base part P and substitute part S  
When I attempt to create the same relationship again  
Then the backend responds with HTTP 409 and includes `existingResourceId` in the error envelope  
And the UI displays a message indicating the relationship already exists  
And the UI provides an action to open the existing substitute link detail using `existingResourceId`.

### Scenario 5: Update a substitute link (non-key fields only)
Given I am on a substitute link detail screen  
When I click Edit  
Then the fields `partId` and `substitutePartId` are read-only  
When I change `priority` and click Save  
Then the UI sends `PUT /rest/api/v1/inventory/substitutes/{id}` with the changed fields  
And includes `version` if it was present in the loaded resource  
And on success I see the updated values and updated metadata.

### Scenario 6: Update conflict due to stale version
Given I am editing a substitute link that includes a `version` field  
And another user updates the same link  
When I click Save with a stale version  
Then the backend responds with HTTP 409 and a standard error envelope including `correlationId`  
And the UI shows a concurrency conflict message including the `correlationId`  
And provides a Reload action that refetches the latest detail.

### Scenario 7: Deactivate (soft delete) a substitute link
Given I am on a substitute link detail screen for an active link  
When I click Deactivate and confirm  
Then the UI calls `DELETE /rest/api/v1/inventory/substitutes/{id}` with an `Idempotency-Key` header  
And on success the UI shows the link as inactive  
And when I return to the base part substitutes list with default filters, the deactivated link is not shown.

### Scenario 8: Unauthorized user cannot modify substitutes
Given I am authenticated without substitute-management permission  
When I attempt to create, update, or deactivate a substitute link  
Then the backend responds with HTTP 403  
And the UI displays a permission error and does not apply the change.
