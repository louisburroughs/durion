## Issue Body

## Title
[FRONTEND] [STORY] Enforce Product Restriction Rules by Location/Service Context with Override Modal (Pricing)

## Primary Persona
Service Advisor (primary); Shop Manager (for overrides and rule management)

## Business Value
Prevent unsafe/incompatible/regulatory-noncompliant products from being added/finalized in POS flows, while enabling controlled exceptions with auditable override records.

---

# 2. Story Intent

## As a / I want / So that
**As a** Service Advisor,  
**I want** the POS UI to evaluate product restriction rules when I add or finalize items,  
**so that** restricted products are blocked (or require a manager override) and all decisions are traceable.

## In-scope
- Frontend integration with Pricing restriction evaluation API when adding/editing line items and when finalizing/committing.
- UI handling of restriction decisions per line item: `ALLOW`, `BLOCK`, `ALLOW_WITH_OVERRIDE`, and degraded state `RESTRICTION_UNKNOWN`.
- Override modal flow (permission-gated) calling Pricing override API and storing `overrideId` onto the line item context (frontend state + submission payload to downstream flow where applicable).
- Rule management screens for Shop Manager: create/view/update/deactivate `RestrictionRule` via Pricing service (Moqui screens/forms/transitions).
- Display rule match reasons (`reasonCodes`, `ruleIds`) in user-facing messages (non-sensitive).
- Fetch override reason codes from Pricing catalog endpoint and use them in override modal.

## Out-of-scope
- Implementing backend rule evaluation, override approval, or audit/event emission (assumed provided by Pricing service).
- Workexec backend changes (this story only ensures frontend passes context and consumes responses).
- Defining/authoring the business meaning of service tags, location tags, or reason codes beyond consuming backend-provided values.
- Client-side caching of restriction rules or reason codes beyond standard HTTP caching semantics.

---

# 3. Actors & Stakeholders
- **Service Advisor:** adds products to estimate/quote/work order/invoice; sees blocks/warnings and cannot finalize when restricted/unknown.
- **Shop Manager:** can override restrictions (permission `pricing:restriction:override`), and manages restriction rules (permission split view/manage; see below).
- **Pricing Service (SoR):** owns `RestrictionRule`, override reason code catalog, and `OverrideRecord`; provides evaluation + override APIs.
- **Workexec (consumer):** owns estimate/work order lifecycle and line persistence; receives line items + `overrideId` reference and provides `transactionId` once persisted.

# 4. Preconditions & Dependencies
- User is authenticated; permissions are available to frontend (Moqui user context / permission checks).
- Current operational context is available in UI state:
  - `tenantId`, `locationId`
  - `serviceTag` (string/enum) for the current flow (e.g., ESTIMATE, WORKORDER, INVOICE, POS_SALE, DELIVERY) — UI treats as opaque string
  - optional `customerAccountId`
  - optional context info (`vehicleType`, `workType`, `salesChannel`) if available in the POS flow
- Pricing service endpoints available (DECISION-PRICING-002, DECISION-PRICING-010..012):
  - `POST /pricing/v1/restrictions:evaluate`
  - `POST /pricing/v1/restrictions:override`
  - `GET /pricing/v1/restrictions/override-reasons` (DECISION-PRICING-011)
  - Restriction rule admin endpoints under `/pricing/v1/...` (exact paths may vary; UI must be configurable via Moqui screen parameters and handle 404 gracefully if not deployed yet)
- Product line item contains or can derive: `productId`, `quantity`, `uom`. (Unit price is not required for restriction evaluation unless backend requires it; see Data Requirements.)
- For overrides: a persisted `transactionId` must exist; if not present, override must be disabled with guidance to save/persist first (DECISION-PRICING-012).

# 5. UX Summary (Moqui-Oriented)

## Entry points
1. **POS transaction flows** (estimate/quote builder, work order editor, invoice finalize, counter sale cart):
   - On “Add item” and “Edit quantity/uom” actions.
   - On “Finalize/Commit” actions (invoice finalize / checkout / commit sale).
2. **Admin/Manager area**:
   - “Pricing → Restriction Rules” list screen
   - “Create Restriction Rule” screen
   - “Edit Restriction Rule” screen (including deactivate/end-date)

## Screens to create/modify (Moqui)
- **Modify existing transaction screens** (names depend on repo conventions):
  - Add restriction status indicator and actions per line item.
  - Hook transitions to call evaluation service on relevant triggers.
- **New screen set** (pathing must follow nearest existing admin convention; DECISION-PRICING-015):
  - `apps/pos/screen/pricing/restriction/RestrictionRuleList.xml`
  - `apps/pos/screen/pricing/restriction/RestrictionRuleDetail.xml`
  - `apps/pos/screen/pricing/restriction/RestrictionRuleEdit.xml`
  - `apps/pos/screen/pricing/restriction/RestrictionRuleCreate.xml`
- **Modal/Drawer**:
  - Override modal/drawer component invoked from transaction line item UI when decision is `ALLOW_WITH_OVERRIDE`.

## Navigation context
- POS transaction area remains primary context; restriction checks must not navigate away.
- Manager rule management screens live under Pricing admin navigation and require restriction view/manage permissions.

## User workflows (happy + alternate paths)

### Happy path (ALLOW)
1. Service Advisor adds product or edits quantity/uom.
2. UI calls evaluate API with context + item(s).
3. Response `ALLOW`: item remains; no blocking UI.

### Blocked path (BLOCK)
1. Service Advisor adds product.
2. Evaluate returns `BLOCK` with reasons.
3. UI marks item as blocked and prevents finalize/commit until item removed or replaced.
4. UI does **not** offer override for `BLOCK` (DECISION-PRICING-010).

### Override-required path (ALLOW_WITH_OVERRIDE)
1. Evaluate returns `ALLOW_WITH_OVERRIDE` with reasons and candidate `ruleIds`.
2. UI marks item as “Override required” and prevents finalize/commit until override is approved or item removed.
3. If user has `pricing:restriction:override` and `transactionId` exists, UI shows “Override” action.
4. Override modal collects reason code + notes (+ rule selection if multiple candidates).
5. UI calls override API; on approval stores `overrideId` on line item and marks item finalizable.

### Degraded path (evaluation unavailable in non-commit flows)
1. Evaluate fails (timeout/5xx/network).
2. UI allows adding/editing but marks `RESTRICTION_UNKNOWN`.
3. Finalize/commit is blocked until evaluation succeeds (fail-closed on commit; conservative on edit).

# 6. Functional Behavior

## Triggers
- **T1 Add line item**: when user adds a product to cart/quote/work order.
- **T2 Edit line item**: quantity/uom changes for existing item (and any other fields that could affect restriction evaluation, if present).
- **T3 Pre-finalize/commit**: when user clicks finalize/commit (invoice finalize / checkout / commit sale).
- **T4 Manager rule CRUD**: list/create/update/deactivate restriction rules.

## UI actions

### A. Transaction line item evaluation (T1/T2)
- UI must call `POST /pricing/v1/restrictions:evaluate` with:
  - `tenantId`, `locationId`, `serviceTag`
  - optional `customerAccountId`
  - `items[]` containing at minimum `productId`, `quantity`, `uom`
  - optional `context` object if available
- UI must update each affected line item with restriction metadata:
  - `restrictionDecision` = `ALLOW` | `BLOCK` | `ALLOW_WITH_OVERRIDE` | `RESTRICTION_UNKNOWN` (frontend-local)
  - `restrictionReasonCodes[]` (from response; may be empty)
  - `restrictionRuleIds[]` (from response; may be empty)
  - `restrictionPolicyVersion` (if returned; used for override concurrency)
- If decision is `BLOCK`:
  - UI must keep the item visible and clearly marked as blocked.
  - UI must prevent finalize/commit while the item remains.
  - UI must provide a “Remove item” action (existing behavior) and a “Retry evaluation” action.
- If decision is `ALLOW_WITH_OVERRIDE`:
  - UI must prevent finalize/commit until override approved (overrideId present) or item removed.
  - UI shows “Override” action only if:
    - user has permission `pricing:restriction:override`, AND
    - `transactionId` exists for the document/line (DECISION-PRICING-012), AND
    - decision is `ALLOW_WITH_OVERRIDE` (DECISION-PRICING-010)
- If decision is `ALLOW`:
  - UI proceeds normally; no override UI.

### B. Override modal/drawer (invoked from line item)
**Launch condition:** line item decision is `ALLOW_WITH_OVERRIDE`.

**Modal fields:**
- `overrideReasonCode` (required; loaded from `GET /pricing/v1/restrictions/override-reasons`, DECISION-PRICING-011)
- `notes` (required; free text; trimmed; length constraints enforced client-side as UX-only)
- `ruleId` selection (required only when multiple candidate `ruleIds` exist in the evaluation response; DECISION-PRICING-012)
  - UI shows a selector listing the candidate rule IDs (and optional display names if provided by backend; otherwise show IDs only).
- `policyVersion` (hidden field; required if provided by evaluation response; sent back to backend for concurrency control; DECISION-PRICING-012)

**Submit behavior:**
- UI validates required fields before calling API.
- UI calls `POST /pricing/v1/restrictions:override` with required identifiers and fields (see Data Requirements).
- On response:
  - If `status=APPROVED` and `overrideId` present:
    - store `overrideId` on the line item (and in the document payload that will be submitted to Workexec)
    - mark line item as finalizable (decision remains displayed as “Overridden” with original reasons)
  - If `status=DENIED`:
    - keep line item in `ALLOW_WITH_OVERRIDE` state without `overrideId`
    - show denial message (backend-provided if available; otherwise generic)
  - If 409 conflict (policyVersion mismatch):
    - show message: “Restriction policy changed; re-evaluate required.”
    - trigger re-evaluation for that line item and require a new override attempt
  - If 403 forbidden:
    - show “Access denied” and keep item restricted

**Decision rationale:** Overrides are only permitted for `ALLOW_WITH_OVERRIDE` and require `transactionId` + `policyVersion` for traceability and concurrency safety (DECISION-PRICING-010, DECISION-PRICING-012).

### C. Pre-finalize/commit behavior (T3)
On finalize/commit click:
1. UI must ensure a successful, authoritative evaluation exists for all line items:
   - If any item is `RESTRICTION_UNKNOWN` → block finalize with: “Restrictions must be evaluated before finalizing.”
   - If any item is `BLOCK` → block finalize and focus the first blocked item.
   - If any item is `ALLOW_WITH_OVERRIDE` without `overrideId` → block finalize and focus the first override-required item.
2. UI must attempt a fresh evaluation for all items if:
   - any item is `RESTRICTION_UNKNOWN`, OR
   - evaluation is stale due to edits since last evaluation (frontend tracks dirty flag per line)
3. If evaluation API is unavailable during finalize/commit:
   - fail closed: block finalize with “Restriction service unavailable; cannot complete transaction.”

### D. Rule management (Shop Manager) (T4)
- Permissions:
  - View screens require `pricing:restriction:view` (DECISION-PRICING-015).
  - Create/update/deactivate require `pricing:restriction:manage` (DECISION-PRICING-015).
  - If backend only provides a single permission, UI must degrade to manage-only gating (DECISION-PRICING-015).
- List rules:
  - filter by active/inactive (derived), condition type, product, effective as-of time.
- Create rule:
  - select condition type/value (backend-defined; UI treats as opaque strings)
  - select product(s) using Inventory product search (DECISION-PRICING-017)
  - set `effectiveStartAt` and optional `effectiveEndAt` using date-time picker (store-local semantics; DECISION-PRICING-003)
  - save via Pricing service
- Edit rule:
  - update allowed fields per backend validation
  - deactivate by setting `effectiveEndAt` (preferred deactivation mechanism; DECISION-PRICING-016)
- Audit/history:
  - show audit entries if endpoint exists (DECISION-PRICING-015)

# 7. Business Rules (Translated to UI Behavior)

## Validation
### Override modal
- Do not allow override submission unless:
  - user has permission `pricing:restriction:override`
  - `transactionId` is present (DECISION-PRICING-012)
  - `overrideReasonCode` is selected (from backend catalog; DECISION-PRICING-011)
  - `notes` is non-empty after trimming
  - if evaluation returned multiple `ruleIds`, user selects exactly one `ruleId` (DECISION-PRICING-012)
  - if `policyVersion` was provided by evaluation, it must be included in override request (DECISION-PRICING-012)

### Restriction rule create/edit
- Enforce required fields client-side (UX-only; backend is authoritative):
  - `name` required
  - `effectiveStartAt` required; `effectiveEndAt` optional but must be > `effectiveStartAt` when present (half-open semantics; DECISION-PRICING-003)
  - condition type/value required (no free-form if backend provides enumerations; otherwise allow string input but validate non-empty and rely on backend errors)
  - at least one product selected (unless backend supports category/global rules; if supported, UI must follow backend schema and validation)
- Deactivation:
  - Prefer setting `effectiveEndAt` rather than toggling a status flag (DECISION-PRICING-016)

## Enable/disable rules
- Disable “Finalize/Commit” when any line item is not finalizable per Section 6C.
- Disable “Override” action when:
  - decision is not `ALLOW_WITH_OVERRIDE` (DECISION-PRICING-010), OR
  - user lacks permission, OR
  - `transactionId` missing (DECISION-PRICING-012), OR
  - override reason codes catalog failed to load (DECISION-PRICING-011)

## Visibility rules
- Restriction message visible when decision != `ALLOW`.
- Override action visible only when override-eligible (`ALLOW_WITH_OVERRIDE`) and user has permission.
- Rule management screens:
  - visible in admin navigation only if user has `pricing:restriction:view` or `pricing:restriction:manage` (DECISION-PRICING-015)

## Error messaging expectations
- For `BLOCK` and `ALLOW_WITH_OVERRIDE`, show a clear message including:
  - product identifier (SKU/name if available from product line context)
  - backend-provided message if present; otherwise a generic message plus `reasonCodes`
- For commit-path unavailability: exact message “Restriction service unavailable; cannot complete transaction.”
- For 409 policyVersion mismatch: “Restriction policy changed; re-evaluate required.”

# 8. Data Requirements

## Entities involved (frontend perspective)
- Pricing-owned (SoR):
  - `RestrictionRule` (effective-dated; deactivation via `effectiveEndAt`, DECISION-PRICING-016)
  - `OverrideRecord` (immutable; created by override endpoint, DECISION-PRICING-012)
  - Override reason code catalog (DECISION-PRICING-011)
  - Audit history for admin changes (DECISION-PRICING-015)
- Inventory-owned:
  - Product identity/search results for product picker (DECISION-PRICING-017)
- Workexec-owned:
  - Transaction/document and line items; provides `transactionId` once persisted

## Fields

### Restriction evaluation request (minimum required by UI)
- `tenantId` (string/UUID, required)
- `locationId` (string/UUID, required)
- `serviceTag` (string, required; treated as opaque)
- `customerAccountId` (string/UUID, optional)
- `items[]` (required, non-empty)
  - `productId` (string/UUID, required)
  - `quantity` (decimal-string or number, required > 0; UI uses existing quantity type)
  - `uom` (string, required)
- `context` (object, optional)
  - `vehicleType` (string, optional)
  - `workType` (string, optional)
  - `salesChannel` (string, optional)

**Note:** `unitPrice` is not required for restriction evaluation per Pricing restriction decisions; UI must not invent it. If backend currently requires it, backend must be updated or UI must pass the current line unit price if present without recomputation.

### Restriction evaluation response (minimum needed)
Per item:
- `decision` enum: `ALLOW` | `BLOCK` | `ALLOW_WITH_OVERRIDE` (DECISION-PRICING-010)
- `ruleIds[]` (strings/UUIDs; may be empty)
- `reasonCodes[]` (strings; may be empty)
- optional:
  - `policyVersion` (string/int; echoed into override request; DECISION-PRICING-012)
  - `message` (string; safe user-facing)
  - `overrideRuleSelectionRequired` (boolean; if present and true, UI requires rule selection)

### Override reason codes catalog response
- `reasonCodes[]` (array of strings) (DECISION-PRICING-011)

### Override request (normative; DECISION-PRICING-012)
- `transactionId` (string/UUID, required)
- `policyVersion` (string/int, required if provided by evaluation)
- `productId` (string/UUID, required)
- `locationId` (string/UUID, optional if backend requires; include if available)
- `ruleId` (string/UUID, required when multiple candidates exist or backend requires explicit selection)
- `overrideReasonCode` (string, required; must be from catalog)
- `notes` (string, required)

### Override response
- `status` enum: `APPROVED` | `DENIED`
- `overrideId` (string/UUID) when approved
- optional `message` (string)

## Read-only vs editable
- In transaction UI, restriction decision fields are read-only (backend-derived).
- `overrideId` is set only from approved override response; cannot be manually edited.

## Derived/calculated fields
- `transaction.canFinalize = all(lineItems.finalizable)`
- `lineItem.finalizable` derived:
  - `ALLOW` => true
  - `BLOCK` => false
  - `ALLOW_WITH_OVERRIDE` => true only if `overrideId` present
  - `RESTRICTION_UNKNOWN` => false

# 9. Service Contracts (Frontend Perspective)

## Load/view calls
- Evaluate restrictions:
  - `POST /pricing/v1/restrictions:evaluate`
  - UI may call:
    - per-line on add/edit, and/or
    - batch for all lines on screen load and on finalize
- Load override reason codes:
  - `GET /pricing/v1/restrictions/override-reasons` (DECISION-PRICING-011)
  - UI should load on-demand when opening override modal; may prefetch on transaction screen load for authorized users
- Restriction rule admin:
  - All endpoints under `/pricing/v1/...` (DECISION-PRICING-002)
  - UI must be implemented with a configurable base path and handle:
    - 404 (feature not deployed) by showing “Restriction admin is not available” and hiding menu entry if possible

## Create/update calls
- Restriction rule CRUD endpoints: under `/pricing/v1/...` (DECISION-PRICING-002)
  - Create: `POST /pricing/v1/restriction-rules` (preferred conventional path; if backend differs, update screen config)
  - Update: `PUT/PATCH /pricing/v1/restriction-rules/{ruleId}`
  - Deactivate: `PATCH /pricing/v1/restriction-rules/{ruleId}` with `effectiveEndAt` (DECISION-PRICING-016)
  - List: `GET /pricing/v1/restriction-rules?...`
  - Detail: `GET /pricing/v1/restriction-rules/{ruleId}`
- Product picker:
  - `GET /inventory/v1/products?query=...&page=...&pageSize=...` returning at minimum `productId`, `sku`, `name` (DECISION-PRICING-017)

## Submit/transition calls
- Override restriction:
  - `POST /pricing/v1/restrictions:override` (DECISION-PRICING-012)
  - Must include `transactionId`; if missing, UI must not call endpoint and must instruct user to save/persist first.

## Error handling expectations
- 400 validation error:
  - show field-level errors when provided; otherwise show message
  - keep item restricted / keep form open
- 403 forbidden:
  - show “Access denied”; do not reveal sensitive details
- 404 not found:
  - for evaluate/override: show generic error and mark `RESTRICTION_UNKNOWN` (non-commit) or block finalize (commit)
  - for admin endpoints: treat as feature not available
- 409 conflict:
  - for override: treat as policyVersion mismatch; require re-evaluation (DECISION-PRICING-012)
- 5xx/timeout:
  - Non-commit: set `RESTRICTION_UNKNOWN`, allow editing but block finalize
  - Commit: block finalize with exact message in Section 7

# 10. State Model & Transitions

## Allowed states (line item restriction state)
- `ALLOW`
- `BLOCK`
- `ALLOW_WITH_OVERRIDE`
- `RESTRICTION_UNKNOWN` (frontend-local degraded state)

## Role-based transitions
- Service Advisor:
  - can trigger evaluation
  - cannot override without `pricing:restriction:override`
- Shop Manager (or anyone with `pricing:restriction:override`):
  - can transition `ALLOW_WITH_OVERRIDE` → finalizable by creating an approved override (overrideId stored)
- Admin/Shop Manager with `pricing:restriction:manage`:
  - can create/update/deactivate restriction rules

## UI behavior per state
- `ALLOW`: normal
- `BLOCK`: highlight as blocked; disallow finalize; show remove item + retry evaluation
- `ALLOW_WITH_OVERRIDE`: show override action if permitted and transactionId exists; disallow finalize until override approved
- `RESTRICTION_UNKNOWN`: warning state; disallow finalize; show retry evaluation

# 11. Alternate / Error Flows

## Validation failures
- Override submitted without reason/notes → inline field errors; do not call API.
- Override attempted without `transactionId` → disable submit; show “Save this transaction before requesting an override.” (DECISION-PRICING-012)
- Rule create/edit missing required fields → inline errors; do not call API.

## Concurrency conflicts
- Override returns 409 due to `policyVersion` mismatch (DECISION-PRICING-012):
  - show “Restriction policy changed; re-evaluate required.”
  - automatically re-run evaluation for the affected line
  - require user to re-open override modal and submit again

## Unauthorized access
- If user without permission attempts override:
  - UI hides action; if forced via direct UI manipulation, backend 403 is shown; keep item restricted.

## Empty states
- Rule list empty: show “No restriction rules found” and CTA “Create rule” (only if manage permission).
- Override reason codes endpoint returns empty list:
  - disable override submission and show “No override reasons available; cannot request override.”

# 13. Audit & Observability

## User-visible audit data
- On line item with restriction decision != `ALLOW`, user can view:
  - decision
  - reasonCodes
  - ruleIds
  - (if overridden) overrideId and override status

## Status history
- Rule management screens show (if provided by API; DECISION-PRICING-015):
  - `createdAt`, `createdBy`, `changedAt/changedBy` (or updatedAt/updatedBy), `action`, `summary`
  - `effectiveStartAt`, `effectiveEndAt`
  - derived active/inactive status (based on effective dating; DECISION-PRICING-016)

## Traceability expectations
- Frontend includes correlation/request ID headers per workspace convention when calling Pricing APIs.
- Frontend logs structured events (no PII; do not log override notes):
  - `restriction.evaluate.requested|succeeded|failed` with `transactionId` (if present), `productId(s)`, and error category
  - `restriction.override.requested|succeeded|failed` with `transactionId`, `productId`, `ruleId`, `overrideId` (if approved), and error category

# 14. Non-Functional UI Requirements
- **Performance:** evaluation call must not block UI thread; show per-line loading state; commit path must surface timeout quickly (target: treat >800ms as unavailable for UX).
- **Accessibility:** modal fields labeled; errors announced; keyboard navigable; focus trapped within modal/drawer; close returns focus to invoking control.
- **Responsiveness:** works on tablet widths typical for POS.
- **i18n/timezone/currency:** do not hardcode tag labels; display backend-provided strings safely. Date-time pickers in admin screens must display store-local timezone context (DECISION-PRICING-003).
