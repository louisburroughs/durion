## 1. Story Header

### Title
[FRONTEND] Access: Assign Roles and Scopes (Global vs Location)

### Primary Persona
Admin (a user authorized to manage other users’ access)

**Persona Metadata**
- `primary_persona`: `Admin (a user authorized to manage other users’ access)`
- `canonical_persona`: `System Administrator`
- `persona_family`: `System Administration`
- `actor_type`: `human`

### Business Value
Enable least-privilege access by granting roles with correct scope (GLOBAL vs LOCATION) and effective dates, with an auditable history that downstream domains can rely on for eligibility and permissions.

---

## 2. Story Intent

### As a / I want / So that
- **As an** Admin  
- **I want** to view, add, and revoke user role assignments with scope (GLOBAL/LOCATION) and effective dates  
- **So that** access is correctly constrained per shop location and job function, and changes are traceable.

### In-scope
- Admin UI to **list** a user’s existing RoleAssignments (active by default, with an explicit history toggle).
- Admin UI to **create** a new RoleAssignment with:
  - role selection
  - scopeType selection (GLOBAL or LOCATION)
  - location selection required when LOCATION scope
  - effectiveStartAt required
  - effectiveEndAt optional (exclusive end semantics)
- Admin UI to **end** (revoke) an existing assignment via setting `effectiveEndAt` (no hard delete).
- Frontend validation reflecting backend business rules (scope/location/date constraints) and rendering backend validation errors.
- Show audit-relevant metadata available from API (createdAt/updatedAt/changedBy/lastUpdatedStamp or equivalent).

### Out-of-scope
- Defining/maintaining Role metadata (e.g., creating roles, editing allowedScopes).
- Authentication implementation (login) and authorization enforcement logic beyond UI gating/handling 401/403.
- Cross-domain workflows (e.g., mechanic eligibility calculations, scheduling UI); only ensure role assignment data supports them.
- Event bus implementation; only ensure UI actions trigger backend actions that emit events.

## 3. Actors & Stakeholders

### Actors
- **Admin**: manages user access by assigning/ending roles and scopes.
- **People Service (Moqui)**: system of record for RoleAssignment and Role metadata required for scoping.

### Stakeholders / Downstream consumers (informational)
- **Work Execution**: consumes role assignments for eligibility (e.g., MECHANIC + LOCATION).
- **Shop Management / Scheduling**: consumes role assignments for permissions (e.g., MANAGER/DISPATCHER).
- **Audit/Compliance**: relies on effective-dated, append-only history.

### Entry points
- From **User Detail** (or Admin Users list): action “Manage Access / Roles”.
- Direct route (Moqui screen path): `apps/people/users/UserDetail/AccessRoles?userId=<userId>` (final screen path must follow repo conventions; see Open Questions).

### Screens to create/modify
- **Screen: `UserAccessRoles`** (new or extend existing User Detail sub-screen)
  - Lists role assignments (active by default) with a “Include history” toggle
  - Actions: “Add Role Assignment”, “End” on eligible rows
- **Dialog/Screen: `AddRoleAssignment`**
  - Create form for new role assignment
- **Dialog: `EndRoleAssignment`**
  - End form (effectiveEndAt) + optional notes (if backend supports)

### Navigation context
- Breadcrumb: Users → User Detail → Access / Roles
- After create/end: remain on Access / Roles and refresh list (Decision: DECISION-PEOPLE-026, DECISION-PEOPLE-017).

### User workflows (happy + alternate)

#### Happy path: create LOCATION-scoped assignment
1. Admin opens Access / Roles for a user.
2. Admin clicks “Add Role Assignment”.
3. Admin selects a role; UI shows allowed scopes for that role.
4. Admin selects scopeType=LOCATION.
5. UI requires location selection.
6. Admin sets effectiveStartAt; optionally effectiveEndAt.
7. Admin submits; UI shows success; list refreshes and shows new assignment.

#### Happy path: create GLOBAL-scoped assignment
Same as above but scopeType=GLOBAL; location field is hidden/disabled and must not be sent.

#### Alternate: end an assignment (end+create pattern)
1. Admin clicks “End” on an ACTIVE (or FUTURE) assignment.
2. Admin selects effectiveEndAt (defaults to now).
3. Admin submits; UI refreshes list; assignment becomes non-active but remains visible (history).

#### Alternate: view history
1. Admin toggles “Include history”.
2. UI reloads list with historical assignments included.

## 6. Functional Behavior

### Triggers
- Screen load:
  - Load role assignments for target user/person (active-only default).
  - Load role catalog (for create dialog).
  - Load locations only when needed (see Applied Safe Defaults).
- “Include history” toggle changes:
  - Reload role assignments with `includeHistory=true`.
- Role selection changes in create dialog:
  - Update scope options based on `role.allowedScopes`.
- ScopeType changes in create dialog:
  - Toggle location requirement and clear location when switching to GLOBAL.
- Submit create:
  - Call create endpoint; on success refresh list.
- Submit end:
  - Call end endpoint; on success refresh list.

### UI actions (deterministic)
- **Role dropdown**:
  - Displays roleName; stores roleId.
  - Shows allowedScopes hint (read-only).
- **ScopeType control**:
  - Only scopes present in `allowedScopes[]` are selectable.
  - If only one allowed scope, preselect and disable scope control (Decision rationale: scope is constrained by role; UI must not allow invalid combinations; DECISION-PEOPLE-003).
- **Location picker**:
  - Required and enabled only when scopeType=LOCATION.
  - Cleared and disabled when scopeType=GLOBAL.
- **EffectiveStartAt picker**:
  - Required; date-time.
- **EffectiveEndAt picker**:
  - Optional; must be strictly greater than effectiveStartAt when provided (half-open interval semantics; end is exclusive) (Decision: DECISION-PEOPLE-014).
- **Create/End submit buttons**:
  - Disabled until client-side validations pass.
  - On submit, disable buttons and show in-progress state to prevent double-submit.

### State changes (frontend)
- After create/end success:
  - Refresh assignments list from backend (source of truth).
- No client-side mutation of list rows beyond transient “saving” state.

### Service interactions (Moqui)
- Implement as Moqui screens with transitions calling REST (or direct services) per repo convention:
  - `transition` for create role assignment
  - `transition` for end role assignment
  - `actions` for loading lists (roles, assignments, locations)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Required fields for create:
  - `roleId` required
  - `scopeType` required
  - `effectiveStartAt` required
  - `effectiveEndAt` optional
- Scope/location constraints (Decision: DECISION-PEOPLE-003):
  - If `scopeType=LOCATION` → `locationId` required
  - If `scopeType=GLOBAL` → `locationId` must be omitted/null (UI must not send it)
  - `scopeType` must be one of `role.allowedScopes[]`
- Effective dating (Decision: DECISION-PEOPLE-014):
  - `effectiveEndAt` (if provided) must be > `effectiveStartAt`
  - “Active” determination in UI uses half-open interval: active if `now >= start && (end == null || now < end)`
- Mutability preference (Decision: DECISION-PEOPLE-026):
  - Do not support in-place edits of roleId/scope/location/start; use end+create.

### Enable/disable rules
- “Add Role Assignment” button visible/enabled only if backend indicates capability (see Service Contracts: `capabilities.canManageRoleAssignments`) or if permission check endpoint indicates allowed; otherwise hidden/disabled (Decision: DECISION-PEOPLE-013).
- “End” action enabled only for assignments that are not already ended (end is null or end > now). Ending FUTURE assignments is allowed by default (end can be set to a time after start but before now is not required); see end-date constraints below.

### Visibility rules
- Location picker is visible only when scopeType=LOCATION (to reduce errors and avoid sending locationId for GLOBAL).

### End-date constraints (ending assignments)
- Default: allow ending ACTIVE or FUTURE assignments by setting `effectiveEndAt` to a value strictly greater than `effectiveStartAt`.
- Backdating (end < now) is allowed only if backend accepts it; UI will allow selecting any end time >= start, and will rely on backend 409/400 to reject invalid backdating (Decision: DECISION-PEOPLE-026, DECISION-PEOPLE-018).

### Error messaging expectations
- Client-side validation errors:
  - Inline per field (required, invalid date range).
- Backend errors (Decision: DECISION-PEOPLE-018):
  - 400: show banner + map `fieldErrors[]` to fields when present.
  - 401: redirect to login or show session expired.
  - 403: show “You do not have permission to manage role assignments.”
  - 404: show not found (user/role/location) with “Refresh” action.
  - 409: show conflict banner with actionable guidance:
    - If concurrency token mismatch: “This record changed. Refresh and try again.”
    - If overlap/duplicate: show message; keep form values for correction.

#### Create RoleAssignment form fields
- `userId` (string/UUID): required (from route/context; not editable)
- `roleId` (string/UUID): required
- `scopeType` (enum): required

- `effectiveEndAt` (timestamp): optional; default null

- RoleAssignment core fields are read-only after creation.

  - FUTURE / ACTIVE / EXPIRED computed using half-open interval semantics (Decision: DECISION-PEOPLE-014).

## 9. Service Contracts (Frontend Perspective)

All endpoints follow People REST conventions (Decision: DECISION-PEOPLE-021) and error schema (Decision: DECISION-PEOPLE-018). Final names must be confirmed in repo/module docs (see Open Questions), but the frontend must be implemented against these required shapes.

### Load/view calls

1) **Get Role catalog**
- `GET /rest/api/v1/people/roles`
- Query:
  - `page`, `pageSize` (optional; if roles are small, backend may return unpaged list; UI must support either)
- Response (preferred list shape):
```json
{
  "items": [
    { "roleId": "ROLE_MANAGER", "roleName": "Manager", "allowedScopes": ["LOCATION"] }
  ],
  "page": 1,
  "pageSize": 50,
  "total": 1
}
```

2) **Get Locations for picker**
- `GET /rest/api/v1/people/locations`
- Query:
  - `page`, `pageSize` (optional)
  - `status=ACTIVE` (if supported)
- Response:
```json
{
  "items": [
    { "locationId": "LOC_1", "locationName": "Main Shop" }
  ],
  "page": 1,
  "pageSize": 50,
  "total": 1
}
```

3) **Get RoleAssignments for a user**
- `GET /rest/api/v1/people/users/{userId}/role-assignments`
- Query:
  - `includeHistory=false|true` (default false) (Decision: DECISION-PEOPLE-026)
  - `page`, `pageSize`
- Response:
```json
{
  "items": [
    {
      "roleAssignmentId": "RA_1",
      "userId": "U_1",
      "roleId": "ROLE_MANAGER",
      "scopeType": "LOCATION",
      "locationId": "LOC_1",
      "effectiveStartAt": "2026-01-01T00:00:00Z",
      "effectiveEndAt": null,
      "lastUpdatedStamp": "2026-01-10T12:00:00Z"
    }
  ],
  "page": 1,
  "pageSize": 25,
  "total": 1,
  "capabilities": {
    "canViewRoleAssignments": true,
    "canManageRoleAssignments": true
  }
}
```
- Decision rationale: UI must gate by named permissions/capabilities, not role-name heuristics (DECISION-PEOPLE-013). If backend cannot include `capabilities` in list response, provide a separate endpoint (see Open Questions).

### Create/update calls

4) **Create RoleAssignment**
- `POST /rest/api/v1/people/users/{userId}/role-assignments`
- Body:
```json
{
  "roleId": "ROLE_MANAGER",
  "scopeType": "LOCATION",
  "locationId": "LOC_1",
  "effectiveStartAt": "2026-01-21T18:00:00Z",
  "effectiveEndAt": null
}
```
- Rules:
  - Omit `locationId` when `scopeType=GLOBAL`.
  - Backend enforces allowedScopes and dating constraints (DECISION-PEOPLE-003, DECISION-PEOPLE-014).
- Response:
  - `201 Created` with created assignment DTO (including `roleAssignmentId` and `lastUpdatedStamp` if used).

5) **End RoleAssignment**
- `POST /rest/api/v1/people/role-assignments/{roleAssignmentId}/end`
- Body:
```json
{
  "effectiveEndAt": "2026-01-21T19:00:00Z",
  "lastUpdatedStamp": "2026-01-10T12:00:00Z"
}
```
- Notes:
  - Include `lastUpdatedStamp` when provided by load response (DECISION-PEOPLE-017).
  - Backend may reject invalid backdating/overlaps with 409 (DECISION-PEOPLE-026, DECISION-PEOPLE-018).
- Response:
  - `200 OK` with updated assignment DTO.

### Error handling expectations (standardized)
- 400:
```json
{
  "errorCode": "VALIDATION_ERROR",
  "message": "Invalid request",
  "fieldErrors": [
    { "field": "effectiveEndAt", "message": "Must be after effectiveStartAt" }
  ]
}
```
- 409:
```json
{
  "errorCode": "CONFLICT",
  "message": "Role assignment overlaps an existing assignment",
  "blockingIds": ["RA_2"],
  "details": { "conflictType": "OVERLAP" }
}
```

## 10. State Model & Transitions

### Allowed states (derived for UI)
- **FUTURE**: `now < effectiveStartAt`
- **ACTIVE**: `effectiveStartAt <= now < effectiveEndAt` (or end null)
- **EXPIRED**: `effectiveEndAt != null && effectiveEndAt <= now`

(Decision rationale: half-open interval semantics are required for deterministic “active” logic; DECISION-PEOPLE-014.)

### Role-based transitions
- If `capabilities.canManageRoleAssignments=true`:
  - Create assignment (FUTURE or ACTIVE depending on start)
  - End assignment by setting `effectiveEndAt` (must be > start; backend validates backdating constraints)
- If manage capability is false:
  - No transitions; view-only.

### UI behavior per state
- ACTIVE:
  - Show “End” action enabled
- FUTURE:
  - Show “End” action enabled (end sets effectiveEndAt after start; may be in future or now if now > start; if now < start, end must still be > start)
- EXPIRED:
  - No “End” action

## 11. Alternate / Error Flows

### Validation failures (client-side)
- LOCATION scope without location:
  - Show inline error; block submit.
- End <= start:
  - Show inline error; block submit.

### Backend validation failures (400)
- Render banner message.
- Map `fieldErrors` to inputs when present.
- Preserve user-entered form values.

### Conflict (409)
- Overlap/duplicate assignment:
  - Show conflict banner with backend message.
  - If `blockingIds` provided, show “Conflicts with existing assignment(s): …” (IDs only; do not attempt to load details unless a dedicated endpoint exists).
- Optimistic concurrency mismatch (DECISION-PEOPLE-017):
  - Show “This assignment changed since you loaded it. Refresh and try again.”
  - Provide “Refresh” action that reloads list and reopens dialog if appropriate.

### Unauthorized access (401/403)
- 401:
  - Redirect to login or show session expired.
- 403:
  - Show access denied banner.
  - Hide/disable create/end actions.
  - If list endpoint itself returns 403, show access denied screen (no data).

### Empty states
- No role assignments:
  - Show empty state with CTA “Add Role Assignment” only if manage capability is true.
- No locations available:
  - If user selects LOCATION scope and locations list is empty, show message and block submit.

## 12. Acceptance Criteria

### Scenario 1: View user role assignments (active-only default + history toggle)
**Given** I am an authenticated user with permission to view role assignments  
**And** a user exists with `userId`  
**When** I navigate to the user’s “Access / Roles” screen  
**Then** I see a list of the user’s role assignments filtered to active-only by default  
**And** I can enable “Include history” to reload and view historical (ended) assignments  
**And** each row shows role, scopeType, location (if applicable), effectiveStartAt, effectiveEndAt, and derived status using half-open interval semantics

### Scenario 2: Create a GLOBAL role assignment (location omitted)
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**And** a role exists with `allowedScopes` including `GLOBAL`  
**When** I create a role assignment with `scopeType=GLOBAL` and a valid effectiveStartAt  
**Then** the UI submits the create request without `locationId`  
**And** on success the UI remains on the Access / Roles screen  
**And** the assignments list refreshes and shows the new assignment with scopeType GLOBAL and no location

### Scenario 3: Create a LOCATION role assignment (location required)
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**And** a role exists with `allowedScopes` including `LOCATION`  
**And** at least one location exists  
**When** I create a role assignment with `scopeType=LOCATION`, a selected `locationId`, and a valid effectiveStartAt  
**Then** the UI submits the create request including `locationId`  
**And** the assignments list refreshes and shows the new assignment with scopeType LOCATION and the selected location

### Scenario 4: Enforce allowedScopes in UI
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**And** I select a role whose `allowedScopes` is `[LOCATION]`  
**When** I view the scopeType control  
**Then** `GLOBAL` is not selectable  
**And** if the backend still returns a 400 validation error for scope mismatch  
**Then** the UI displays the backend error and keeps my form values for correction

### Scenario 5: Reject invalid effective dating (exclusive end)
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**When** I set effectiveEndAt to a value less than or equal to effectiveStartAt  
**Then** the UI shows an inline error indicating the end must be after the start  
**And** the submit action is blocked

### Scenario 6: End an active assignment (soft revoke)
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**And** a role assignment is currently ACTIVE  
**When** I end the assignment with effectiveEndAt = now  
**Then** the UI submits the end request including the concurrency token if provided  
**And** the assignments list refreshes  
**And** the ended assignment remains visible when “Include history” is enabled

### Scenario 7: Handle 409 conflict on end (optimistic concurrency)
**Given** I am an authenticated Admin with `canManageRoleAssignments=true`  
**And** I attempt to end an assignment using a stale `lastUpdatedStamp`  
**When** the backend responds with HTTP 409  
**Then** the UI shows a conflict message instructing me to refresh  
**And** no further automatic retries occur  
**And** I can refresh the list and retry the end action

### Scenario 8: Permission denied (403)
**Given** I am authenticated but `canManageRoleAssignments=false` (or backend returns 403 on manage actions)  
**When** I open the Access / Roles screen  
**Then** I can view role assignments only if the backend allows it  
**And** create/end actions are hidden or disabled  
**And** if I attempt a manage action and receive 403, the UI shows an authorization error and no changes occur
