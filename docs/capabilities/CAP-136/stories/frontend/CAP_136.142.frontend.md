## 1. Story Header

### Title
[FRONTEND] [STORY] Locations: Create and Maintain Shop Locations

### Primary Persona
Admin (Location Manager)

### Business Value
Ensure scheduling, appointments, and downstream operational rules use accurate per-site location metadata (address, timezone, operating hours, holiday closures, and buffers), with auditable changes.

## 2. Story Intent

### As a / I want / So that
- **As an** Admin  
- **I want** to create, view, edit, and deactivate shop locations (including address, timezone, operating hours, holiday closures, and optional buffer overrides)  
- **So that** systems that schedule and execute work can apply correct per-site rules and context.

### In-scope
- Moqui/Vue/Quasar UI to:
  - List locations with status filtering (**default ACTIVE**). (DECISION-LOCATION-008)
  - Create a location (**status defaults to ACTIVE; no status selector on create**). (DECISION-LOCATION-022)
  - View a location’s details.
  - Edit location details with validation feedback.
  - Soft-deactivate a location (ACTIVE → INACTIVE) and **reactivate** (INACTIVE → ACTIVE) behind manage permission. (DECISION-LOCATION-019)
  - Display audit/status metadata (created/updated/version; and if exposed, audit events). (DECISION-LOCATION-020)
- Frontend integration with Moqui backend endpoints for Locations CRUD and status update using the standard REST convention prefix. (DECISION-LOCATION-006)
- Client-side validation that mirrors backend constraints (without replacing server validation).

### Out-of-scope
- Enforcing cross-domain rules (e.g., preventing staffing assignments to inactive locations, workexec behaviors).
- Distance/travel time computations.
- Any location hierarchy behaviors beyond selecting an optional parent (no cascading rules invented; cycle prevention is server-side). (DECISION-LOCATION-021)
- Sync/import flows from external authoritative sources (SyncLog).

- Entering create screen triggers load of timezone allowed list (lazy-load; fallback if unavailable). (DECISION-LOCATION-003)
- Entering detail screen triggers load of selected location by `locationId`.
- Create/Save/Deactivate/Reactivate triggers API calls and UI state updates.

### UI actions
**Locations list**
- Status filter control: `ACTIVE | INACTIVE | ALL` (default ACTIVE). (DECISION-LOCATION-008)
- Table/list rows show at minimum: Name, Code (if available), Status, Timezone, UpdatedAt (if available).
- Row click navigates to detail.

**Create location**
- Form fields (see Data Requirements).
- Status is not selectable; create always results in ACTIVE unless backend rejects. (DECISION-LOCATION-022)
- Save action disabled while request in-flight.
- On success: show success notification and route to detail.

**Edit location**
- Load existing values into form.
- `code` is immutable; show read-only if present and never submit changes. (DECISION-LOCATION-001)
- Save calls PUT (or PATCH if backend supports partial) including `version`.

**Deactivate**
- Button visible/enabled only when status is ACTIVE and user has manage permission.
- Confirmation dialog required.
- Calls status transition endpoint with `{status:"INACTIVE", version:<current>}`.
- On success: update UI status and keep fields editable (non-identity fields) per INACTIVE editability rule. (DECISION-LOCATION-019)

**Reactivate**
- Button visible/enabled only when status is INACTIVE and user has manage permission. (DECISION-LOCATION-019)
- Confirmation dialog required.
- Calls status transition endpoint with `{status:"ACTIVE", version:<current>}`.
- On success: update UI status to ACTIVE.

### State changes
- `status` transitions:
  - ACTIVE → INACTIVE (deactivate)
  - INACTIVE → ACTIVE (reactivate) (DECISION-LOCATION-019)

### Service interactions
- List: GET locations with status filter.
- Detail: GET location by id.
- Create: POST location payload.
- Update: PUT/PATCH location payload with `version`.
- Status change: PATCH/POST action to update status with `version`.

## 7. Business Rules (Translated to UI Behavior)

### Validation (client-side mirrors server rules)
- **Code** (DECISION-LOCATION-001)
  - Required on create if backend contract requires it; immutable after creation.
  - UI must not allow editing and must not send changed code on update.
- **Name** (DECISION-LOCATION-002)
  - Required, trimmed.
  - UI trims leading/trailing whitespace before submit.
  - Uniqueness enforced by backend using case-insensitive + trimmed normalization; on `LOCATION_NAME_TAKEN`, show inline error on name.
- **Timezone** (DECISION-LOCATION-003)
  - Required.
  - UI uses backend-provided allowed list endpoint; if unavailable, allow selection from a temporary static list and still submit the chosen IANA ID.
  - On backend `INVALID_TIMEZONE`, show inline error on timezone.
- **Operating hours** (DECISION-LOCATION-004)
  - Payload: `operatingHours: [{dayOfWeek, open, close}]` where:
    - `dayOfWeek` is `MONDAY`..`SUNDAY`
    - `open`/`close` are `HH:mm`
  - Rules:
    - At most one entry per day (no duplicates).
    - `open < close`.
    - No overnight ranges.
    - Omission of a day means closed.
    - Empty array allowed and means “no standard hours defined”.
  - UI prevents duplicates and invalid ranges; on backend `INVALID_OPERATING_HOURS`, show editor-level error and preserve inputs.
- **Holiday closures** (DECISION-LOCATION-005)
  - Field is nullable; when present it is an array of `{date, reason?}`.
  - `date` is `YYYY-MM-DD` (date-only).
  - No duplicate dates.
  - `reason` optional; if present, trim and enforce max length 255.
  - UI must preserve null vs empty array semantics:
    - If backend returns `null`, UI should keep it `null` unless user explicitly adds/removes entries.
- **Buffers**
  - `checkInBufferMinutes` / `cleanupBufferMinutes` are null or non-negative integers.
  - UI allows blank (null) and non-negative integers; blocks negatives and non-integers.
- **Parent location** (DECISION-LOCATION-021)
  - Optional `parentLocationId`.
  - UI prevents selecting self as parent.
  - Backend prevents cycles; UI surfaces backend error as field-level error on parent picker when possible.

### Enable/disable rules
- Disable Save while network request in-flight.
- Permission gating (DECISION-LOCATION-007):
  - If user lacks `location:manage`, hide/disable Create, Save, Deactivate, Reactivate.
  - If user has view-only, allow list/detail read-only.
- INACTIVE editability (DECISION-LOCATION-019):
  - INACTIVE locations remain editable for non-identity fields (name, address, timezone, hours, closures, buffers, parent).
  - Code remains immutable always.

### Visibility rules
- Show status badge (ACTIVE/INACTIVE) in detail header.
- Show created/updated timestamps and version (read-only metadata) if returned.
- Show code read-only if returned.

### Error messaging expectations
- For 400: show field-level errors where `field` is provided; otherwise show form-level banner with error `message`.
- For 409:
  - `LOCATION_NAME_TAKEN`: inline on name.
  - `OPTIMISTIC_LOCK_FAILED`: modal/banner explaining someone else updated it; offer Reload.

## 9. Service Contracts (Frontend Perspective)

> Implement via Moqui transitions/actions calling backend endpoints. Exact service names/paths are deferred to implementation PR, but must follow `/rest/api/v1/location/...` convention. (DECISION-LOCATION-006)

### Load/view calls
- **List**
  - `GET /rest/api/v1/location/locations?status=<ACTIVE|INACTIVE|ALL>&pageIndex=<n>&pageSize=<n>`
  - Default behavior: if `status` omitted, backend may default to ACTIVE; UI should explicitly send `status=ACTIVE` to be deterministic. (DECISION-LOCATION-008)
  - Expected response envelope (preferred): `{ items: LocationSummary[], totalCount: number }`
- **Detail**
  - `GET /rest/api/v1/location/locations/{locationId}`
  - 404: show “Location not found” and link back to list.
- **Timezone allowed list** (DECISION-LOCATION-003)
  - `GET /rest/api/v1/location/timezones`
  - Response: `items: string[]` (IANA IDs) or similar list; UI must tolerate simple array vs envelope.

### Create/update calls
- **Create**
  - `POST /rest/api/v1/location/locations`
  - Request body includes: `code?`, `name`, `address`, `timezone`, `operatingHours` (may be empty array), `holidayClosures` (null/[]/array), buffers (nullable), `parentLocationId?`
  - Success: 201 with created Location including `locationId`, `version`, `status=ACTIVE`. (DECISION-LOCATION-022)
- **Update**
  - `PUT /rest/api/v1/location/locations/{locationId}` (full update) OR `PATCH` (partial) depending on backend; UI should be implemented to send only editable fields plus `version` to avoid accidental code changes.
  - Must include `version`.
  - Success: 200 with updated Location (preferred) or no body (if no body, refetch).

### Submit/transition calls
- **Deactivate**
  - `PATCH /rest/api/v1/location/locations/{locationId}` with `{ status: "INACTIVE", version: <current> }`
- **Reactivate**
  - `PATCH /rest/api/v1/location/locations/{locationId}` with `{ status: "ACTIVE", version: <current> }`
- Both must include `version` and handle `OPTIMISTIC_LOCK_FAILED`.

### Error handling expectations (UI mapping)
- 400: render validation errors; preserve form state.
- 401/403: show “Not authorized” state; hide/disable mutation actions. (DECISION-LOCATION-007)
- 404: detail not found state.
- 409:
  - `LOCATION_NAME_TAKEN` → mark name invalid.
  - `OPTIMISTIC_LOCK_FAILED` → offer reload and prevent blind overwrite.

## 11. Alternate / Error Flows

### Validation failures
- Timezone invalid: show timezone field error, no navigation.
- Operating hours invalid (duplicate day, close <= open, overnight): show operating hours editor error.
- Holiday closures invalid (duplicate dates, reason too long): show closures editor error.
- Buffers invalid: show numeric input error.
- Parent invalid:
  - Self-parent attempt blocked client-side.
  - Cycle attempt rejected server-side; show error on parent field.

### Concurrency conflicts
- On `OPTIMISTIC_LOCK_FAILED` (409):
  - Show blocking banner/modal: “This location was updated by another user.”
  - Actions: **Reload** (refetch) and **Cancel** (stay on form, changes retained but not submittable until reload).
  - After reload, form resets to latest server state.

### Unauthorized access
- If GET list/detail returns 403: show access denied state.
- If create/update/status change returns 403: show toast/banner and keep user on page; ensure mutation controls are disabled after the response.

### Empty states
- List with no results for filter: show “No locations found” and CTA to create (if authorized).
