## Issue Body

## 1. Story Header

**Title:** [FRONTEND] Locations: Create & Manage Mobile Units, Coverage Rules, and Travel Buffer Policies

**Primary Persona:** Shop Administrator (Admin)

**Persona Metadata**
- `primary_persona`: `Shop Administrator (Admin)`
- `canonical_persona`: `Location Manager`
- `persona_family`: `Location Management`
- `actor_type`: `human`
**Business Value:** Enables configuration of mobile service resources (capabilities, base location, coverage, travel buffer policy, max daily jobs) so scheduling/work execution can select eligible **ACTIVE** mobile units and apply travel buffers reliably.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Shop Administrator  
- **I want** to create and manage Mobile Units, define their capabilities and coverage rules, and configure Travel Buffer Policies  
- **So that** mobile appointments can be scheduled with correct eligibility filtering and travel buffer behavior, and out-of-service units are not schedulable.

### In-Scope
- Frontend screens and flows to:
  - Create, view, and update **Mobile Units**
  - Assign **capability IDs** (validated by Service Catalog via backend; UI uses read-only lookup)
  - Define **coverage rules** that link Mobile Units to **Service Areas** with priority and effective windows
  - Create, view, and update **Travel Buffer Policies** (FIXED_MINUTES, DISTANCE_TIER)
- UI validation aligned to Location domain rules (atomic replace semantics, timezone semantics, tier validation, required fields)
- Moqui screen/form/service wiring needed to call backend endpoints and manage transitions
- Basic audit visibility (created/updated timestamps; version; optional audit events when available)

### Out-of-Scope
- Computing travel distance (caller/workexec owns distance computation)
- Scheduling availability computation (workexec owns)
- HR event emission (explicitly out of scope)
- Authorization model design (security domain); frontend will respect backend 401/403 responses and hide/disable actions when permission signals are available

---

## 3. Actors & Stakeholders
- **Shop Administrator (Admin):** configures mobile units, coverage, and policies.
- **Scheduler / Work Execution user/system:** consumes mobile unit eligibility for scheduling (depends on correct configuration).
- **Service Catalog domain/system:** authoritative source for capabilities; backend validates IDs.
- **Geo/Service Area owning domain/system:** authoritative source for Service Areas; Location UI links existing Service Areas only (no CRUD).
- **Security/Access Control stakeholders:** define who can manage mobile units/policies.

## 4. Preconditions & Dependencies
- User is authenticated.
- Backend Location APIs are reachable under versioned REST prefix (Decision: **DECISION-LOCATION-006**).
- Base Locations exist in Location SoR (MobileUnit.baseLocationId must reference an existing Location).
- Service Areas exist in their owning domain; this story uses a picker-only integration (Decision: **DECISION-LOCATION-011**).
- Capabilities/services/skills lookups are provided by authoritative domains (Service Catalog) via read-only API (Decision: **DECISION-LOCATION-012**).
- Backend supports optimistic locking via `version` for update/transition operations; conflicts return `409 OPTIMISTIC_LOCK_FAILED` (Location domain invariant).

## 6. Functional Behavior

### Triggers
- User opens list/detail/create/edit screens.
- User submits create/update forms.
- User edits coverage rules and saves (replace).
- User creates/updates a travel buffer policy.

### UI actions
- **Mobile Units list**

  - Load detail including `version`.
  - PATCH/PUT update including `version` for optimistic locking.

  - Load existing rules for mobileUnitId.

  - Validate tiers and minutes client-side; submit to backend.

- MobileUnit.status transitions among `ACTIVE`, `INACTIVE`, `OUT_OF_SERVICE`.

- Load capabilities for picker (read-only lookup).
- Load service areas for picker (read-only lookup; no CRUD).
- CRUD Mobile Units.

- Replace coverage rules per mobile unit.

## 7. Business Rules (Translated to UI Behavior)

### Validation

**Permissions (UI gating)**
- Read-only access requires `location:view`; mutations require `location:manage` (Decision: **DECISION-LOCATION-007**).
- UI must still rely on backend enforcement; if permission claims are not available client-side, UI may render actions but must handle 403 by disabling and showing error.

**Mobile Unit**
- `name`: required; trim before submit; min length 1 after trim.
- `baseLocationId`: required; must be selected from Location picker.
- `maxDailyJobs`: required integer, `>= 0`.
- `status`: required enum `ACTIVE | INACTIVE | OUT_OF_SERVICE`.
- `travelBufferPolicyId`:
  - Required when `status = ACTIVE` (Decision: **DECISION-LOCATION-007** in notes: Mobile units must have travelBufferPolicyId when ACTIVE).
  - Optional when `status != ACTIVE`.
- `capabilityIds[]`:
  - Selected from read-only lookup; UI must not accept free-text IDs (Decision: **DECISION-LOCATION-012**).
  - Empty list allowed unless backend rejects; if backend returns validation error, show it and keep selections.

**Coverage Rule**
- `serviceAreaId`: required; selected from picker (Decision: **DECISION-LOCATION-011**).
- `priority`: required integer; lower number = higher priority (UI helper text only; backend is SoR).
- Effective window:
  - `effectiveStartAt` and `effectiveEndAt` are optional.
  - If both present, enforce `effectiveEndAt > effectiveStartAt`.
  - Submit as ISO-8601 timestamps with offset; treat as instants (Decision: **DECISION-LOCATION-017**).
  - Display in base location timezone for readability when base location timezone is available (Decision: **DECISION-LOCATION-017** + notes alignment).

**Travel Buffer Policy**
- `name`: required; trim before submit.
- `policyType`: required enum `FIXED_MINUTES | DISTANCE_TIER` (Decision: **DECISION-LOCATION-015**).
- FIXED_MINUTES:
  - Use `policyConfiguration.minutes` integer `>= 0` (Decision: **DECISION-LOCATION-015**).
- DISTANCE_TIER:
  - Store and submit tiers in KM only; UI labels distances as KM and does not accept MI in v1 (Decision: **DECISION-LOCATION-016**).
  - `policyConfiguration.unit` must be `"KM"` when present.
  - `policyConfiguration.tiers[]`:
    - At least one tier.
    - Each tier has `bufferMinutes` integer `>= 0`.
    - Non-null `maxDistance` values strictly increasing.
    - Exactly one catch-all tier with `maxDistance = null`.

### Enable/disable rules
- Disable Save while required fields invalid.
- Mobile Unit form:
  - When status ACTIVE: travel buffer policy field required and enabled.
  - When status INACTIVE/OUT_OF_SERVICE: travel buffer policy field optional; allow clearing.
- Coverage Rules:
  - Disable “Save Coverage” if any rule invalid (missing service area, invalid window, non-integer priority).
- Travel Buffer Policy:
  - FIXED_MINUTES: disable save if minutes missing/negative/non-integer.
  - DISTANCE_TIER: disable save if tier constraints violated.

### Visibility rules
- Coverage Rules screen accessible only for existing Mobile Unit (requires `mobileUnitId`).
- Show informational banner when status is OUT_OF_SERVICE or INACTIVE: “Not schedulable while not ACTIVE.”

### Error messaging expectations (stable mapping)
- `400/422`: show field-level errors if backend provides `field`/`fields` mapping; otherwise show summary.
- `401`: redirect to login (app convention).
- `403`: show “You do not have permission to perform this action.” Disable mutation controls.
- `409 OPTIMISTIC_LOCK_FAILED`: show “This record was updated by someone else. Reload to continue.”
- `409` for uniqueness conflicts (if provided): map to relevant field (name) with backend code/message.
- `503` from lookup dependencies: show retryable error and block save if required lookup cannot be loaded.

## 9. Service Contracts (Frontend Perspective)

> Contract convention decision: use versioned REST prefix and Location module namespace (Decision: **DECISION-LOCATION-006**). Exact endpoint paths must be confirmed in implementation PR, but the UI must be built to these conventions.

### Load/view calls
- Mobile Units list (Decision: **DECISION-LOCATION-013**):
  - `GET /rest/api/v1/location/mobile-units?status=ACTIVE|INACTIVE|OUT_OF_SERVICE|ALL&baseLocationId=<id>&pageIndex=<n>&pageSize=<n>`
  - Response: `{ items: MobileUnit[], totalCount: number }`
- Mobile Unit detail:
  - `GET /rest/api/v1/location/mobile-units/{mobileUnitId}`
- Base Locations picker:
  - `GET /rest/api/v1/location/locations?status=ACTIVE&pageIndex=<n>&pageSize=<n>`
- Coverage rules for a mobile unit:
  - `GET /rest/api/v1/location/mobile-units/{mobileUnitId}/coverage-rules`
- Service Areas picker (picker-only; no CRUD in this story) (Decision: **DECISION-LOCATION-011**):
  - `GET /rest/api/v1/location/service-areas?pageIndex=<n>&pageSize=<n>&q=<optional>`
  - If service areas are not in location module, backend may proxy; UI only requires a read-only list/search endpoint.
- Capabilities lookup (Decision: **DECISION-LOCATION-012**):
  - `GET /rest/api/v1/catalog/capabilities?q=<optional>&pageIndex=<n>&pageSize=<n>`
  - If proxied, endpoint may be `/rest/api/v1/location/lookups/capabilities`; UI should isolate via a single frontend API client method.

### Create/update calls
- Create Mobile Unit:
  - `POST /rest/api/v1/location/mobile-units`
  - Body includes: `name, baseLocationId, status, maxDailyJobs, travelBufferPolicyId?, capabilityIds[]`
- Update Mobile Unit (optimistic lock):
  - `PATCH /rest/api/v1/location/mobile-units/{mobileUnitId}` (or PUT if backend requires)
  - Body includes: `version` + mutable fields
- Replace coverage rules (atomic replace) (Decision: **DECISION-LOCATION-014**):
  - `PUT /rest/api/v1/location/mobile-units/{mobileUnitId}/coverage-rules:replace`
  - Body: `{ version?, rules: MobileUnitCoverageRule[] }` (versioning for coverage set is backend-defined; UI must pass any provided version/etag)
  - Idempotent for identical payloads.
- Travel Buffer Policies:
  - List: `GET /rest/api/v1/location/travel-buffer-policies?pageIndex=<n>&pageSize=<n>&q=<optional>`
  - Create: `POST /rest/api/v1/location/travel-buffer-policies`
  - Detail: `GET /rest/api/v1/location/travel-buffer-policies/{travelBufferPolicyId}`
  - Update (optimistic lock): `PATCH /rest/api/v1/location/travel-buffer-policies/{travelBufferPolicyId}` with `version`

### Submit/transition calls
- Status changes are performed via Mobile Unit update (PATCH) by setting `status`.
- Backend must enforce: cannot set status ACTIVE without `travelBufferPolicyId` (Decision: **DECISION-LOCATION-007**).

### Error handling expectations
- Standard error payload handling:
  - Prefer `{ code, message, fieldErrors?, correlationId? }` if provided.
  - Map known codes:
    - `OPTIMISTIC_LOCK_FAILED` → reload prompt
    - `TRAVEL_BUFFER_POLICY_REQUIRED` → map to travelBufferPolicyId field
    - Tier validation errors → map to tiers editor summary + highlight row if index provided
- Always preserve user-entered form state on error.

### Allowed states

- `ACTIVE`
- `INACTIVE`
- `OUT_OF_SERVICE`

### Role-based transitions
- With `location:manage`: may transition between any states, subject to backend validation (Decision: **DECISION-LOCATION-007**).
- With `location:view` only: cannot transition; UI hides/disables status controls.

- **ACTIVE**
  - Travel buffer policy required; show validation if missing.
  - Show “Schedulable” indicator (informational).
- **INACTIVE**
  - Not schedulable banner.
  - Allow editing configuration (name, maxDailyJobs, capabilities, coverage) if manage permission; activation requires policy.
- **OUT_OF_SERVICE**
  - Not schedulable banner.
  - Allow editing configuration if manage permission; returning to ACTIVE requires policy.

## 11. Alternate / Error Flows

### Validation failures
- Client-side validation blocks submit and shows inline messages.
- If backend returns validation errors, show them and keep inputs.

### Concurrency conflicts
- On `409` with `OPTIMISTIC_LOCK_FAILED`:
  - Show blocking dialog: “This record changed since you loaded it.”
  - Actions: Reload (required), Cancel (keeps local draft but cannot save).
  - After reload, UI should reapply draft if feasible (optional enhancement).

### Unauthorized access
- `401`: redirect to login.
- `403`:
  - If on mutation attempt: show error and revert UI to read-only.
  - If on screen load: show “Not authorized” screen with link back to previous page.

### Empty states
- No mobile units: show empty state with Create CTA (if manage) or informational message (if view-only).
- No travel buffer policies:
  - Mobile Unit create/edit: policy picker shows “No policies found” and provides link to create policy (if manage).
- No service areas available:
  - Coverage screen shows “No service areas available to assign” and blocks saving coverage until at least one exists.

### Lookup dependency failures
- Capabilities lookup unavailable (e.g., 503):
  - Show retry UI.
  - If capabilities are optional: allow saving without changes to capabilities; if user already selected capabilities, keep them but warn validation may fail server-side.
- Service areas lookup unavailable:
  - Coverage screen blocks save and shows retry (coverage requires serviceAreaId).

## 12. Acceptance Criteria

### Scenario 1: Mobile Units list defaults to ACTIVE and supports paging
**Given** I am authenticated with `location:view`  
**When** I navigate to Admin → Location Management → Mobile Units  
**Then** the list loads with default filter `status=ACTIVE`  
**And** results are paginated with server-side paging  
**And** I can change the status filter and the list refreshes accordingly.

### Scenario 2: Create Mobile Unit (Happy Path)
**Given** I am authenticated and authorized with `location:manage`  
**And** at least one base location exists  
**And** at least one travel buffer policy exists  
**When** I navigate to Admin → Location Management → Mobile Units → Create  
**And** I enter a name, select a base location, set status to ACTIVE, set max daily jobs to a non-negative integer, select a travel buffer policy, and optionally select capability IDs  
**And** I click Save  
**Then** the system creates the Mobile Unit via `POST /rest/api/v1/location/mobile-units`  
**And** I am redirected to the Mobile Unit detail screen  
**And** I see the persisted values including `mobileUnitId` and `version`.

### Scenario 3: Enforce travel buffer policy required when ACTIVE
**Given** I am creating or editing a Mobile Unit with `location:manage`  
**When** I set status to ACTIVE  
**Then** the Travel Buffer Policy field becomes required  
**And** I cannot submit until a policy is selected  
**And** if I bypass client validation and the backend returns `TRAVEL_BUFFER_POLICY_REQUIRED`, the error is shown on the Travel Buffer Policy field.

### Scenario 4: View-only user cannot mutate
**Given** I am authenticated with `location:view` and without `location:manage`  
**When** I open a Mobile Unit detail screen  
**Then** I can view the Mobile Unit fields  
**And** edit controls (Save, status change, coverage save, create policy) are hidden or disabled  
**And** if I attempt a mutation via direct URL/action and receive 403, the UI shows “Not authorized” and does not lose the currently displayed data.

### Scenario 5: Configure coverage rules atomically (replace semantics)
**Given** I am authenticated with `location:manage`  
**And** a Mobile Unit exists  
**When** I open the Coverage Rules screen and add/update/remove coverage rules  
**And** I click Save Coverage  
**Then** the frontend submits the full set in a single request to `PUT /rest/api/v1/location/mobile-units/{mobileUnitId}/coverage-rules:replace`  
**And** on success the UI reloads and displays exactly the saved set.

### Scenario 6: Reject invalid effective window in UI
**Given** I am editing a coverage rule  
**When** I set `effectiveEndAt` to a time that is less than or equal to `effectiveStartAt`  
**Then** I see an inline validation error  
**And** I cannot save coverage until corrected.

### Scenario 7: Coverage effective windows submit as instants with offsets
**Given** I am editing a coverage rule and the base location has timezone `America/New_York`  
**When** I enter an effective start time in the UI  
**Then** the request payload includes an ISO-8601 timestamp with offset (e.g., `2026-01-01T08:00:00-05:00`)  
**And** when the backend returns UTC timestamps, the UI displays them converted to the base location timezone.

### Scenario 8: Create FIXED_MINUTES travel buffer policy
**Given** I am authenticated with `location:manage`  
**When** I create a Travel Buffer Policy with type FIXED_MINUTES and minutes `15`  
**Then** the request payload uses `policyConfiguration.minutes = 15`  
**And** the policy is created successfully and is selectable in the Mobile Unit form.

### Scenario 9: Create DISTANCE_TIER travel buffer policy (KM only)
**Given** I am authenticated with `location:manage`  
**When** I create a Travel Buffer Policy with type DISTANCE_TIER  
**And** I enter tiers with strictly increasing `maxDistance` values (in KM) and include exactly one catch-all tier with `maxDistance = null`  
**Then** the UI allows saving  
**And** the request payload includes `policyConfiguration.unit = "KM"`  
**And** viewing the policy shows the same tier configuration.

### Scenario 10: Reject invalid DISTANCE_TIER tier configuration
**Given** I am creating a DISTANCE_TIER policy  
**When** I attempt to save tiers that are not strictly increasing or I include zero or multiple catch-all tiers  
**Then** the UI blocks submission with clear validation messages  
**And** if the backend returns a validation error, the UI displays it without clearing the tiers.

### Scenario 11: Optimistic locking conflict on update
**Given** I am editing a Mobile Unit  
**And** another user updates the same Mobile Unit before I save  
**When** I click Save and the backend returns `409 OPTIMISTIC_LOCK_FAILED`  
**Then** I see a message prompting me to reload  
**And** no partial update is shown as successful.
