## Issue Body

## 1. Story Header

**Title:** Cost: Maintain Standard/Last/Average Cost with Audit (Frontend – Moqui)

**Primary Persona:** Inventory Manager (Finance Manager as oversight stakeholder)

**Business Value:**  
Provide accurate, permissioned visibility and maintenance of inventory item costs (standard/last/average) with full audit traceability so operations and finance can rely on authoritative valuation inputs and compliance-grade change history.

---

## 2. Story Intent

### As a / I want / So that
**As an** Inventory Manager (or Finance Manager),  
**I want** to view current costs (Standard, Last, Average) for an inventory item, manually update Standard Cost with a required reason code (when authorized), and view cost change audit history,  
**so that** costs are maintained correctly (system-managed vs user-managed) and all changes are traceable for analysis and audits.

### In-scope
- View current `standardCost`, `lastCost`, `averageCost` for an Inventory Item.
- Edit **Standard Cost only** (permission gated) with required `reasonCode`.
- Prevent editing of `lastCost` and `averageCost` (system-managed).
- Display cost audit history filtered to the item with paging/sorting.
- Frontend handling of validation, authorization errors, and concurrency conflicts returned by services.
- Moqui-oriented implementation: screens/forms/transitions calling **Moqui proxy/services** (no direct Vue → backend calls), consistent with platform integration pattern.

### Out-of-scope
- Implementing backend cost calculation/event processing (e.g., purchase order receipt updates).
- Creating/modifying inventory items or purchase order receipt workflows.
- Any FIFO/LIFO costing options.
- Any accounting postings/COGS calculations.
- Bulk cost updates.
- Approval workflow for cost changes (separation-of-duties) unless explicitly provided by backend.

---

## 3. Actors & Stakeholders
- **Inventory Manager (Primary User):** Views costs, updates standard cost when permitted, reviews audit.
- **Finance Manager:** Oversight; reviews audit and changes.
- **Accountant / Finance Team (Stakeholder):** Relies on average cost and audit trail.
- **Auditor (Stakeholder):** Requires immutable audit history and traceability.
- **System (Backend processes):** Updates last/average costs from receipt events; generates audit entries.

---

## 4. Preconditions & Dependencies
- Inventory item exists and is identifiable by a stable identifier in routing (e.g., `itemId` or `inventoryItemId`).
- Moqui frontend can call **Moqui proxy endpoints/services** (DECISION-INVENTORY-002 integration pattern; applied here as a platform constraint for inventory UI).
- Backend (via Moqui) exposes:
  - Read endpoint/service to load an item’s current costs and basic identity fields.
  - Mutation endpoint/service to update `standardCost` with `reasonCode` and permission enforcement.
  - Read endpoint/service to query cost audit history by item with cursor or offset pagination (unknown; must be clarified).
- AuthN/AuthZ available to frontend such that permission to update standard cost is either:
  - discoverable via a “current user permissions” mechanism, **or**
  - enforced server-side with `403` and handled gracefully client-side (DECISION-INVENTORY-012 behavior for 401/403).
- Correlation ID convention: requests/responses use `X-Correlation-Id` and UI surfaces it in error technical details (DECISION-INVENTORY-012).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- **Standard cost input**
  - Must be a valid decimal number; UI must not introduce rounding beyond what the backend accepts.
  - Must be **greater than 0** (block `0`, `0.0000`, and negatives).
  - If backend supports clearing to `null`, UI may allow it only when explicitly confirmed (see Open Questions).
- **Reason code**
  - Required for manual Standard Cost updates.
  - Trimmed non-empty string.
- **Last/Average costs**
  - Never editable in UI.

### Enable/disable rules
- “Edit/Save Standard Cost” visible/enabled only when user is authorized.
  - If permission discovery exists, gate proactively.
  - If not, allow navigation but handle `403` on update by showing forbidden message and returning to read-only.
- Save button disabled until:
  - standardCost is changed and valid
  - reasonCode is present and valid
- Prevent double-submit: disable Save while request is in-flight.

### Visibility rules
- If a cost is `null`, display as “Not set” (not `0.00`).
- Audit section visibility:
  - Must be permission-gated if backend enforces separate permission; otherwise available to any user who can view the item (unclear; see Open Questions).

### Error messaging expectations
- Validation errors: inline near field + optional summary banner.
- Authorization (`403`): “You don’t have permission to update Standard Cost.”
- Not found (`404`): “Item not found” with link back to item search/list.
- Concurrency (`409`): “This item was updated by someone else. Reload to continue.”
- Server error (`5xx`) / network timeout:
  - Show “Could not update cost. Try again.” with Retry.
  - Show `X-Correlation-Id` in “Technical details” when available (DECISION-INVENTORY-012).

## 8. Data Requirements

### Entities involved
- `InventoryItem` (read current costs)
- `ItemCostAudit` (read audit history)

### Fields (type, required, defaults)
**InventoryItem (read-only except standard cost update action)**

- `standardCost` (decimal, nullable, default null)
- `lastCost` (decimal, nullable, default null)
- `averageCost` (decimal, nullable, default null)
- `lastUpdatedStamp` / `version` / `etag` (string/timestamp, optional but recommended for concurrency)

**Standard Cost Update Payload**
- `itemId` (required)
- `standardCost` (decimal, required if setting a value; nullable only if “clear” supported)
- `reasonCode` (string, required)
- `concurrencyToken` (optional; shape depends on backend)

**ItemCostAudit (read-only table)**
- `auditId` (uuid/string, required)
- `timestamp` (datetime, required)
- `costTypeChanged` (enum: `STANDARD`/`LAST`/`AVERAGE`, required)
- `oldValue` (decimal, nullable)
- `newValue` (decimal, nullable)
- `changeSourceType` (enum/string, e.g., `MANUAL`/`PURCHASE_ORDER`, required)
- `changeSourceId` (string, nullable)
- `actorUserId` / `actorName` (string, nullable; depends on backend)
- `reasonCode` (string, nullable except required when `changeSourceType=MANUAL` and `costTypeChanged=STANDARD`)

### Read-only vs editable by state/role
- `standardCost`: editable only for users authorized to update standard cost.
- `lastCost`, `averageCost`: always read-only.
- Audit records: always read-only.

### Derived/calculated fields
- None calculated client-side.

## 11. Alternate / Error Flows

### Validation failures (client-side)
- User enters `0` or negative → block save; message “Standard Cost must be greater than 0.”
- User leaves reason blank → block save; message “Reason code is required.”
- User enters invalid decimal → block save; message “Enter a valid number.”

### Validation failures (server-side)
- Server returns validation error:
  - Map to fields if possible; keep user in editing state.
  - If error indicates permission/eligibility, show banner and revert to viewing.

### Concurrency conflicts
- If update returns `409`:
  - Show message: “This item was updated by someone else. Reload to continue.”
  - Provide “Reload” button that re-fetches item costs and resets form.

### Unauthorized access
- If load returns `401`: route to login/session refresh (DECISION-INVENTORY-012).
- If load returns `403`: show forbidden state.
- If update returns `403`: show forbidden message and revert to viewing with edit disabled.

### Empty states
- Costs all null: display “Not set” for each.
- Audit list empty: show “No cost changes recorded yet.”

### Timeout / network failure
- Show loading indicator quickly; if request exceeds 8 seconds, show timeout state with Retry (aligned with inventory UX targets in DECISION-INVENTORY-004; applied as a general UX pattern here).

## 12. Acceptance Criteria

### Scenario 1: View costs with null handling
**Given** an inventory item exists with `standardCost = null`, `lastCost = null`, `averageCost = null`  
**When** the user opens the item Costs screen  
**Then** the UI displays each cost as “Not set” (not `0.00`)  
**And** the Last Cost and Average Cost fields are read-only.

### Scenario 2: Authorized user updates Standard Cost with reason code
**Given** the user is authorized to update Standard Cost  
**And** the item has `standardCost = 10.0000`  
**When** the user edits Standard Cost to `12.5000` and enters reason code `SUPPLIER_PRICE_INCREASE`  
**And** the user clicks Save  
**Then** the frontend calls the Standard Cost update service with `itemId`, `standardCost=12.5000`, and the reason code  
**And** on success the UI shows the updated Standard Cost value  
**And** the audit history list includes a new entry for costType `STANDARD` with old `10.0000` and new `12.5000` and reason code.

### Scenario 3: Standard Cost update blocked when reason code missing
**Given** the user is authorized to update Standard Cost  
**When** the user enters a valid Standard Cost value but leaves reason code blank  
**Then** the Save action is disabled (or save shows inline validation error)  
**And** no update service call is made.

### Scenario 4: Unauthorized user cannot edit Standard Cost
**Given** the user is not authorized to update Standard Cost  
**When** the user opens the Costs screen  
**Then** Standard Cost is displayed as read-only  
**And** no “Edit/Save Standard Cost” action is available  
**And** if the user attempts to invoke save and receives `403`  
**Then** the UI displays an authorization error and no values change.

### Scenario 5: Prevent editing of system-managed costs
**Given** any user opens the Costs screen  
**Then** Last Cost and Average Cost are never presented as editable fields  
**And** the UI provides no action to update them.

### Scenario 6: Standard Cost must be > 0
**Given** the user is authorized to update Standard Cost  
**When** the user attempts to save Standard Cost as `0.0000`  
**Then** the UI blocks the save with a validation message  
**And** if the request is sent and the server responds with a validation error (`400` or `422`)  
**Then** the UI shows the server validation error and keeps the user in editing state.

### Scenario 7: Audit history paging and filtering
**Given** an item has more than one page of cost audit records  
**When** the user changes page size or navigates to the next page  
**Then** the UI requests the next page from the audit service using the backend’s paging contract  
**And** shows results sorted by timestamp descending by default.

### Scenario 8: Concurrency conflict on update
**Given** the user starts editing Standard Cost  
**And** the item is updated by another actor before save  
**When** the user saves and the server responds with a `409` conflict  
**Then** the UI informs the user and offers a reload action  
**And** reloading refreshes the displayed costs and clears the edit form.

### Scenario 9: Correlation ID surfaced on error
**Given** the update service returns an error response that includes header `X-Correlation-Id`  
**When** the UI displays the error state  
**Then** the UI shows the correlation ID in a “Technical details” section  
**And** the UI does not display stack traces or raw internal error objects.
