## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Promotion: Promote Approved Scope from Partially Approved Estimate (create Work Order + defer remaining)

### Primary Persona
Service Advisor (Back Office / POS user)

**Persona Metadata**
- `primary_persona`: `Service Advisor (Back Office / POS user)`
- `canonical_persona`: `Service Advisor`
- `persona_family`: `Service Advisor`
- `actor_type`: `human`

### Business Value
Enable advisors to start work immediately on the customer-approved portion of an estimate while preserving non-approved items for future approval flows, ensuring technicians only execute authorized work and maintaining end-to-end traceability and auditability.

---

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** to promote the approved scope of a partially approved Estimate into a new Work Order,  
**So that** work can begin on authorized items immediately while unapproved items remain deferred on the Estimate for potential future approval via proper gates.

### In-scope
- Frontend UI action available on an Estimate in `PartiallyApproved` state: “Promote Approved Scope”.
- Confirmation UX and submission to backend to perform the promotion.
- Post-action navigation and clear indicators on both:
  - the created Work Order (contains only approved items)
  - the source Estimate (promoted vs deferred line statuses)
- Display of traceability links between:
  - WorkOrder ↔ source Estimate
  - WorkOrderLine ↔ source EstimateLine (read-only display)
- Error handling for invalid state / no approved items / concurrency / authorization.
- Idempotent submission behavior from the UI (Idempotency-Key) for the promote action.

### Out-of-scope
- Any workflow for “later approval of deferred items” that creates Change Requests or supplemental Work Order items.
- Defining or changing domain policies for conflict resolution when later approvals conflict with work already performed.
- Implementing backend services/entities/state machines (frontend integrates only).
- Time-entry CRUD (people domain).

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated.
- User has capability to promote an estimate into a work order (capability name is a backend/security concern; UI consumes capability flags when available and always handles 403).
- An Estimate exists and is currently in state `PartiallyApproved`.
- Estimate has line items with per-line approval statuses (at least one is approved for a successful promotion).

### Dependencies
- Workexec backend operation exists to “promote approved scope” and returns:
  - `workOrderId` created
  - updated Estimate header status
  - updated line statuses and traceability references (at least enough to render promoted/deferred badges and link to the created work order)
- Moqui screens exist for:
  - Estimate edit/detail (workexec)
  - Work order edit/detail (workexec)
- Standard error envelope is used (or Moqui errors are normalized to it) per DECISION-INVENTORY-011:
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`, optional `existingResourceId`
- UI sends `Idempotency-Key` for the promote action per DECISION-INVENTORY-012.

#### Happy path
1. Advisor opens an Estimate in `PartiallyApproved` on `EstimateEdit`.
2. UI loads estimate header + line items.
3. UI computes counts: approved vs deferred (based on line statuses).
4. Advisor clicks `Promote Approved Scope`.
5. Confirmation dialog summarizes:
   - number of approved items to be promoted
   - number of items that will remain deferred on the estimate

8. On success, UI navigates to `WorkOrderEdit` for returned `workOrderId` and shows success message.

#### Alternate paths
- No approved items: action disabled with helper text; if user still submits (stale UI), show backend validation error.
- Estimate status changed before confirm: backend returns 409; UI refreshes estimate and re-evaluates eligibility.
- Unauthorized: backend returns 403; UI shows “not permitted” and hides/disables action on subsequent renders if capability flags indicate.
- Network retry/double-click: UI reuses the same `Idempotency-Key` for the same attempt and does not create duplicates.

## 6. Functional Behavior

### Triggers
- User clicks `Promote Approved Scope` on an Estimate in `PartiallyApproved`.

### UI actions
- **Render rule:** Show the action only when:
  - `estimate.status == "PartiallyApproved"` (exact string as returned by backend)
  - AND line items are loaded (so counts can be computed)
- **Enable rule:** Enable only when `approvedCount >= 1`.
- **Click action:**
  1. Open confirmation dialog.
  2. On confirm:
     - Generate a new `Idempotency-Key` (UUID) for this attempt.
     - Submit promote request.
     - Disable confirm button and show loading state.
  3. On retry for the same attempt (user clicks “Try again” on a transient error without changing inputs):
     - Reuse the same `Idempotency-Key`.
  4. On success:
     - Show toast/banner: “Work Order created from approved scope.”
     - Navigate to `WorkOrderEdit` with returned `workOrderId`.
  5. On failure:
     - Show error banner with mapped message and `correlationId` when provided.

### State changes (frontend-visible)
- Estimate header status is expected to change away from `PartiallyApproved` after promotion (exact target status is backend-defined; UI must render whatever is returned and only uses `PartiallyApproved` as the eligibility gate).
- Line statuses are expected to reflect:
  - approved → promoted
  - non-approved → deferred
- Work order is created containing only promoted lines.

**Decision rationale:** Workexec owns execution-time lifecycle and estimate editing flows in `durion-workexec` (AGENT_GUIDE “What Work Execution owns”). This story is a workexec-owned promotion action that creates a work order and updates estimate/line statuses.

### Service interactions
- Load Estimate detail (existing screen actions/services).
- Submit promotion action (new transition/service call).
- Load Work Order detail after navigation (existing screen actions/services).
- Optional: refresh Estimate in background after success only if response does not include updated statuses (not required if navigating to work order).

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Promotion is only valid when estimate is `PartiallyApproved`.
  - UI hides/disables outside this status.
  - Backend is authoritative; UI must handle rejection.
- Promotion requires at least one approved line.
  - UI computes approved count from loaded line items.
  - If `approvedCount == 0`, disable action and show helper text: “At least one approved item is required to promote.”
- IDs are opaque strings; UI must not enforce UUID/numeric patterns (DECISION-INVENTORY-003).

### Enable/disable rules
Disable `Promote Approved Scope` when any is true:
- estimate status is not `PartiallyApproved`
- line items not loaded
- `approvedCount == 0`
- request in-flight
- capability flags (if present) indicate user cannot promote

### Visibility rules
- In estimate line list, display a status badge for each line using the backend-provided status string.
- If a line is promoted and a `promotedToWorkOrderId` (or equivalent) is available:
  - show read-only link “On Work Order <id>”
- If a line is deferred:
  - show read-only indicator “Deferred (not on Work Order)”

### Error messaging expectations
- Use backend `message` when present; otherwise map by HTTP status:
  - 400: “Promotion failed: check required approvals and try again.”
  - 409: “Promotion unavailable: estimate changed. Refresh to see latest status.”
  - 403: “You don’t have permission to promote estimates.”
  - 404: “Estimate not found.”
  - 5xx/network: “Promotion failed due to a system error. Try again or contact support.”
- When `correlationId` is present, include it in the error banner (copyable).

## 9. Service Contracts (Frontend Perspective)

> Moqui may implement these as screen transitions invoking services rather than REST. The frontend contract below is expressed in HTTP terms for testability; implement using Moqui `transition`/`service-call` patterns as appropriate.

### Load/view calls
- Estimate load (existing):
  - `GET /rest/api/v1/workexec/estimates/{estimateId}` (or Moqui screen action equivalent)
  - Must include line items or provide:
    - `GET /rest/api/v1/workexec/estimates/{estimateId}/lines`

- Work order load (existing):
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}` (or Moqui screen action equivalent)

### Create/update calls
- Promote approved scope (new):
  - `POST /rest/api/v1/workexec/estimates/{estimateId}/promote-approved-scope`
  - Headers:
    - `Idempotency-Key: <uuid>` (required) (DECISION-INVENTORY-012)
  - Request body:
    - empty OR `{ "reason": <string optional> }`
    - Do **not** require client-supplied `userId`; use authenticated session (security boundary; UI must not send actor IDs).
  - Response (minimum required for UI):
    - `workOrderId` (created)
    - `sourceEstimateId` (echo or same as request)
    - `estimate` (optional) with updated header status
    - `lines` (optional) with updated statuses and traceability IDs
  - Success status:
    - `200 OK` preferred (returns created work order id and updated estimate snapshot)

**Decision rationale:** UI mutations must be idempotent (DECISION-INVENTORY-012) and errors must follow standard envelope (DECISION-INVENTORY-011). Actor identity should come from auth context, not client-supplied IDs (aligns with audit/SoR boundaries in workexec notes).

### Submit/transition calls
- The promote action is an atomic server-side operation that:
  - creates a work order
  - updates estimate/line statuses
  - records traceability links

### Error handling expectations
- Errors conform to standard envelope (DECISION-INVENTORY-011):
  - `400` with `fieldErrors[]` for validation (e.g., no approved lines)
  - `403` for unauthorized
  - `404` for missing estimate
  - `409` for stale state/concurrency (estimate no longer eligible)
  - `5xx` for server errors
- UI displays `correlationId` when present and does not log sensitive data.

## 11. Alternate / Error Flows

### Validation failures
- No approved lines (stale UI):
  - Backend returns 400 with `code` (e.g., `VALIDATION_ERROR`) and message.
  - UI shows message and refreshes estimate on user action.

### Concurrency conflicts
- Estimate status changed between load and submit:
  - Backend returns 409 with `code` (e.g., `CONFLICT`) and message.
  - UI shows conflict message and offers “Refresh estimate” action; after refresh, action is hidden/disabled.

### Unauthorized access
- Backend returns 403:
  - UI shows permission error.
  - If capability flags are available, UI updates to hide/disable action without requiring reload.

### Empty states
- Estimate has zero lines:
  - Promote action disabled.
  - Show empty-state message: “No line items available.”

### Duplicate submission / retries
- User double-clicks confirm or network retries:
  - UI reuses the same `Idempotency-Key` for the same attempt.
  - If backend returns the same successful outcome, UI navigates once and does not show duplicate success toasts.

## 12. Acceptance Criteria

### Scenario 1: Successful promotion creates work order with only approved scope
**Given** an Estimate exists with status `PartiallyApproved` and has 2 line items with status `Approved` and 1 line item with status `Declined`  
**And** the Service Advisor is viewing `durion-workexec/EstimateEdit` for that estimate  
**When** the user clicks `Promote Approved Scope` and confirms the action  
**Then** the UI sends a promote request including an `Idempotency-Key` header  
**And** the system creates a new Work Order linked to the source Estimate  
**And** the UI navigates to `durion-workexec/WorkOrderEdit` for the created work order id  
**And** the Work Order contains exactly the 2 approved items (and not the declined item)  
**And** the Work Order header displays a read-only `Source Estimate` link to the originating estimate  
**And** the source Estimate line statuses (when viewed) reflect that the two approved lines are now promoted and the declined line is deferred.

### Scenario 2: Promote action is unavailable when estimate is not partially approved
**Given** an Estimate is in any status other than `PartiallyApproved`  
**When** the user views `durion-workexec/EstimateEdit`  
**Then** the `Promote Approved Scope` action is not shown or is disabled  
**And** the user cannot submit a promotion request from the UI.

### Scenario 3: Promotion blocked when no items are approved
**Given** an Estimate is in status `PartiallyApproved`  
**And** the Estimate has 0 line items with status `Approved`  
**When** the user views `durion-workexec/EstimateEdit`  
**Then** the `Promote Approved Scope` action is disabled  
**And** the UI displays helper text indicating at least one approved item is required  
**When** the user attempts to submit promotion anyway (stale UI or direct request)  
**Then** the backend responds with HTTP 400 and a standard error envelope  
**And** the UI displays the backend error message and correlationId (if provided)  
**And** no navigation to a Work Order occurs.

### Scenario 4: Concurrency/state conflict during promotion
**Given** an Estimate is initially loaded as `PartiallyApproved` with at least one approved line  
**When** another user changes the Estimate such that it is no longer eligible  
**And** the Service Advisor confirms promotion  
**Then** the backend responds with HTTP 409 and a standard error envelope  
**And** the UI displays a message indicating the estimate changed and refresh is required  
**And** when the user refreshes, the promote action is hidden/disabled based on the latest status.

### Scenario 5: Unauthorized promotion attempt
**Given** a user without permission to promote estimates is viewing an eligible estimate  
**When** the user submits `Promote Approved Scope`  
**Then** the backend responds with HTTP 403  
**And** the UI displays “You don’t have permission to promote estimates.”  
**And** the UI does not navigate away from the estimate screen.

### Scenario 6: Idempotency on double-submit
**Given** an eligible estimate and the confirmation dialog is open  
**When** the user double-clicks the confirm button (or the request is retried due to a transient network error)  
**Then** the UI sends at most one in-flight request at a time  
**And** any retry for the same attempt reuses the same `Idempotency-Key`  
**And** the outcome results in a single created work order and a single navigation to it.
