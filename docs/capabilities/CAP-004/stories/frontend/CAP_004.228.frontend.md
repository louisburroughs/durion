## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** promoting an approved estimate snapshot to a work order to be safe to retry and always return the same canonical work order,  
**so that** accidental double actions or transient failures do not create duplicate work orders or inconsistent execution data.

### In-scope
- Frontend “Promote Estimate to Work Order” action is **idempotent from the user’s perspective**
- UI handles:
  - first-time promotion success (creates WO)
  - retry returning existing WO
  - unknown outcome (timeout/5xx) with safe retry guidance
  - corrupted link case (promotion record exists but WO missing) with clear admin escalation message
- Concurrency-safe UI (disable button, show progress, allow safe retry)
- Display canonical Work Order reference/link after promotion
- Use `Idempotency-Key` header for the promotion mutation (DECISION-INVENTORY-012)

### Out-of-scope
- Implementing backend idempotency logic, DB constraints, or actual PromotionRecord entity persistence
- Work order execution lifecycle transitions beyond “navigate to created/retrieved work order”
- Admin repair tools (only surface “requires admin intervention” guidance)

**Happy path (first attempt)**

**Retry path (double click / refresh / retry after transient error)**

1. UI shows “Promotion may have succeeded; retry is safe.”

**Corrupted link path**
1. Backend returns a non-retryable error code indicating promotion link exists but Work Order missing.
2. UI shows escalation instructions and correlation id; disables further attempts.

## 6. Functional Behavior

### Triggers
- User clicks “Promote to Work Order” on an estimate snapshot/version.
- Duplicate requests occur due to double-click, refresh, or network retry.

### UI actions
- On click:
  - Validate required identifiers exist in UI state: `estimateId`, `snapshotVersion`
  - Generate an `Idempotency-Key` (UUID) for this attempt and store it in component state until completion; reuse the same key only when retrying the *same attempt* (DECISION-INVENTORY-012)
  - Disable the promote button immediately
  - Show loading indicator and “Promoting…” message
- On success:
  - Store returned canonical `workOrderId` (and optional `workOrderNumber`)
  - Render a success banner/panel with Work Order reference and link to open `WorkOrderEdit`
  - Keep Promote disabled if the estimate is now considered “already promoted” by returned data; otherwise allow re-click but it should still resolve idempotently
- On failure:
  - Map error to retryable vs non-retryable (see Business Rules)
  - Re-enable Promote only when retryable
  - Show error banner with actionable message and `correlationId` when present

### State changes (frontend)
- `promotionStatus`: `idle | inProgress | succeeded | failed | blockedCorrupted`
- `promotionResult`: `{ workOrderId: string, workOrderNumber?: string }`
- `attempt`: `{ idempotencyKey: string, startedAt: string, correlationId?: string }`

### Service interactions (high-level)
- Call backend “promote” mutation with `(estimateId, snapshotVersion)` and `Idempotency-Key` header
- On success, navigate directly to `WorkOrderEdit` using returned `workOrderId` (no extra fetch required unless route requires additional params)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- UI must not allow promotion if:
  - `estimateId` missing → show “Estimate not loaded; refresh and try again.”
  - `snapshotVersion` missing → show “Estimate snapshot version is required to promote.”
- UI must treat the operation as idempotent:
  - Any successful response containing a canonical Work Order reference is final, regardless of whether it was created or retrieved.

### Enable/disable rules
- “Promote to Work Order” button:
  - Disabled while `promotionStatus === inProgress`
  - Enabled only when required identifiers exist; do **not** hardcode estimate status rules beyond what is explicitly provided by the estimate payload (backend remains authoritative)

### Visibility rules
- Show promotion result panel only when `promotionStatus === succeeded` and `promotionResult.workOrderId` is present.
- Show “Admin intervention required” panel when corrupted link error occurs.

### Error messaging expectations (standard envelope)
- Parse errors using standard envelope (DECISION-INVENTORY-011):
  - `code`, `message`, `correlationId`, optional `fieldErrors[]`, optional `existingResourceId`
- Distinguish:
  - **Retryable/unknown outcome** (timeouts/5xx): “Promotion may have succeeded. You can retry safely; the system will return the same Work Order.”
  - **Validation** (400/422): show `message` and any `fieldErrors`
  - **Unauthorized** (401/403): “You don’t have permission to promote estimates.”
  - **Corrupted link** (409 with explicit code such as `PROMOTION_LINK_BROKEN`): “Promotion record exists but linked Work Order is missing. Do not retry. Contact admin/support.” and show `correlationId`

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation may use screen transitions invoking services rather than REST. The contract below is expressed as a frontend-observable behavior; implement using existing Moqui service calls where available.

### Load/view calls
- Load Estimate for `EstimateEdit`:
  - Must include `estimateId` and `snapshotVersion` in the screen context (or a service call that returns them)

### Create/update calls
**Promote Estimate Snapshot → Work Order**
- **Method**: `POST`
- **Path (Moqui REST suggested)**: `/rest/api/v1/workexec/estimates/{estimateId}/promote`
- **Headers**:
  - `Idempotency-Key: <uuid>` (required) (DECISION-INVENTORY-012)
  - Optional: `X-Correlation-Id: <uuid>` if platform uses it; otherwise rely on response `correlationId` (DECISION-INVENTORY-011)
- **Body**:
  ```json
  { "snapshotVersion": 1 }
  ```
- **Success (200 OK preferred)**:
  ```json
  {
    "workOrderId": "WO-123",
    "workOrderNumber": "WO-123",
    "outcome": "CREATED|RETRIEVED|COMPLETED_PARTIAL",
    "correlationId": "c-123"
  }
  ```
- **Idempotency behavior**:
  - Same `(estimateId, snapshotVersion)` returns the same `workOrderId` across attempts (backend responsibility)
  - Same `Idempotency-Key` reused on retry of the same attempt returns the same outcome (backend responsibility)

### Submit/transition calls
- None beyond promotion.

### Error handling expectations
- Errors conform to standard envelope (DECISION-INVENTORY-011):
  ```json
  {
    "code": "VALIDATION_ERROR|NOT_AUTHORIZED|PROMOTION_LINK_BROKEN|...",
    "message": "Human readable",
    "correlationId": "c-123",
    "fieldErrors": [{"field":"snapshotVersion","message":"Required"}]
  }
  ```
- HTTP mapping:
  - `400/422`: validation
  - `401/403`: auth
  - `404`: estimate/snapshot not found
  - `409`: corrupted link / conflict
  - `5xx` or timeout: unknown outcome; UI allows safe retry

## 10. State Model & Transitions

### Allowed states (frontend promotion UI state)
- `idle` → `inProgress` → (`succeeded` | `failed` | `blockedCorrupted`)

### Role-based transitions
- If backend returns 403, UI returns to `idle` and shows permission error; do not auto-retry.

### UI behavior per state
- `idle`: show Promote button (enabled only if required identifiers exist)
- `inProgress`: disable Promote, show spinner and “Promoting…”
- `succeeded`: show canonical Work Order link and “Open Work Order”
- `failed`: show retryable error UI; Promote enabled
- `blockedCorrupted`: show non-retryable error UI; Promote disabled; show correlation id

## 11. Alternate / Error Flows

### Validation failures
- Missing `snapshotVersion` in UI:
  - Block call; show inline error
- Backend rejects estimate state (not promotable):
  - Show backend message; do not mutate estimate locally

### Concurrency conflicts
- Two tabs promoting same estimate snapshot:
  - One creates, other retrieves; both end with same canonical `workOrderId`

### Unauthorized access
- 401: follow app pattern (redirect/login) then return to estimate
- 403: show “Not permitted” and do not retry automatically

### Empty states
- Estimate loaded but no `snapshotVersion`:
  - Disable Promote and show explanation “No snapshot available to promote.”

### Corrupted link
- Backend returns `409` with `code=PROMOTION_LINK_BROKEN` (or equivalent):
  - UI enters `blockedCorrupted`, disables Promote, shows escalation instructions and `correlationId`

## 12. Acceptance Criteria

### Scenario 1: First-time promotion creates a new work order
**Given** a Service Advisor is viewing `durion-workexec/EstimateEdit` with `estimateId="E-123"` and `snapshotVersion=1`  
**And** the Promote button is enabled  
**When** the user clicks “Promote to Work Order”  
**Then** the UI disables the Promote button and shows an in-progress indicator  
**And** the frontend sends `POST /rest/api/v1/workexec/estimates/E-123/promote` with body `{ "snapshotVersion": 1 }`  
**And** includes an `Idempotency-Key` header  
**When** the response is `200` with `workOrderId="WO-456"`  
**Then** the UI shows a success state with an “Open Work Order” link that navigates to `durion-workexec/WorkOrderEdit` with `workOrderId="WO-456"`.

### Scenario 2: Retried promotion returns the same canonical work order (no duplicates)
**Given** `estimateId="E-123"` and `snapshotVersion=1` has already been promoted and returned `workOrderId="WO-456"`  
**When** the user triggers “Promote to Work Order” again (including after refresh)  
**Then** the UI receives a success response with `workOrderId="WO-456"`  
**And** the UI displays the same canonical Work Order link  
**And** the UI does not display any indication that a second Work Order was created.

### Scenario 3: Timeout/5xx allows safe user retry and still resolves to single canonical work order
**Given** the user clicks “Promote to Work Order” for `estimateId="E-123"` and `snapshotVersion=1`  
**When** the request times out or returns a `5xx`  
**Then** the UI shows an error message stating the operation may have succeeded and retry is safe  
**And** the Promote button becomes enabled again for user-initiated retry  
**When** the user retries the promotion  
**Then** the UI eventually shows exactly one canonical Work Order link for the snapshot  
**And** the Work Order link uses the single returned `workOrderId`.

### Scenario 4: Corrupted promotion link blocks and requires admin intervention
**Given** the backend determines a promotion link exists for `(estimateId="E-123", snapshotVersion=1)`  
**And** the linked Work Order cannot be loaded  
**When** the user clicks “Promote to Work Order”  
**Then** the backend responds with `409 Conflict` and an error envelope with `code="PROMOTION_LINK_BROKEN"` and `correlationId`  
**And** the UI shows a non-retryable error state instructing the user to contact admin/support  
**And** the Promote button is disabled  
**And** the UI displays the `correlationId`.

### Scenario 5: Missing required identifiers prevents promotion call
**Given** the Estimate screen context is missing `snapshotVersion`  
**When** the user attempts to promote  
**Then** the frontend does not call the backend  
**And** shows “Estimate snapshot version is required to promote.”
