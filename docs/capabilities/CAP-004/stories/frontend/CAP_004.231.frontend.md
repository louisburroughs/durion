## 1. Story Header

### Title
[FRONTEND] [STORY] Promotion: Validate Promotion Preconditions (Estimate → Work Order)

### Primary Persona
Service Advisor (Back Office)

**Persona Metadata**
- `primary_persona`: `Service Advisor (Back Office)`
- `canonical_persona`: `Service Advisor`
- `persona_family`: `Service Advisor`
- `actor_type`: `human`

### Business Value
Prevents creation of invalid or duplicate work orders by enforcing estimate approval + snapshot integrity checks at the moment of promotion, reducing rework, billing errors, and operational confusion.

---

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor,  
**I want** the POS to validate all required preconditions when I click “Promote to Work Order” on an estimate,  
**so that** only estimates with current valid approval and approved scope tied to the correct snapshot can be promoted, and retries do not create duplicate work orders.

### In-scope
- Frontend “Promote to Work Order” action initiation from an Estimate context.
- UI-side orchestration to call backend promotion endpoint(s) with idempotency.
- Displaying actionable, specific precondition failure messages (expired/missing/invalid approval; missing/incorrect approved scope; duplicate promotion).
- Idempotent retry handling (duplicate promotion returns existing work order reference).
- Audit/observability hooks from frontend (correlation ID, client-side event logging as applicable).

### Out-of-scope
- Editing work order details beyond routing to the created/existing work order screen.
- Defining or changing estimate approval workflow itself.
- Defining permissions/roles (only enforce what backend returns).
- Generating PDFs / supplemental estimate documents.

---

## 3. Actors & Stakeholders
- **Primary actor:** Service Advisor / Back Office user
- **Secondary stakeholders:** Workshop Manager (expects integrity), Customer (expects only approved work), Audit/Compliance (expects traceability)

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in the POS UI.
- User is viewing an Estimate record with an `estimateId` (opaque string ID; do not validate format client-side per DECISION-INVENTORY-003).
- Estimate has a promotable approval context:
  - Estimate `status` is available to the UI (from estimate load).
  - Estimate has a `snapshotVersion` (or equivalent immutable version token) that represents the version being promoted.

### Dependencies
- Backend endpoints for:
  - retrieving estimate details (including current status and snapshot/version context),
  - promotion attempt that returns either success (created or existing work order reference) or structured errors including duplicate reference.
- Standard error envelope (DECISION-INVENTORY-011):
  - JSON with `code`, `message`, `correlationId`, optional `fieldErrors[]`, optional `existingResourceId`.
- Idempotency-Key usage for UI mutations (DECISION-INVENTORY-012):
  - UI must send `Idempotency-Key` header for the promotion attempt and reuse it on retry for the same attempt.
- Capability/permission signaling (DECISION-INVENTORY-013):
  - UI may gate the action using capability flags if available, but backend remains authoritative (403).

**Decision rationale applied (resolution):**
- This story is buildable without blocking labels by defining a Moqui-implementable contract in this story (service + transition + REST path) while still allowing the backend to normalize to the standard error envelope and idempotency behavior already mandated by workexec decisions (DECISION-INVENTORY-011/012/013).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- Estimate edit/detail screen: action button **Promote to Work Order**.

### Screens to create/modify
- **Modify**: `durion-workexec/screen/EstimateEdit.xml`
  - Add an action (button) “Promote to Work Order”.
  - Add a confirmation dialog (see Applied Safe Defaults).
  - Add result handling: navigate to work order edit screen on success/duplicate; show inline error panel on validation failure.
- **Existing/Target**: `durion-workexec/screen/WorkOrderEdit.xml`
  - Must be linkable via `workOrderId` parameter.

> Canonical screens/routes decision: use existing workexec screens (DECISION-INVENTORY-002).

### Navigation context
- From `EstimateEdit` → promote action → either:
  - navigate to `WorkOrderEdit` for returned `workOrderId` (new or existing), or
  - stay on estimate and show blocking reasons + next steps.

### User workflows (happy + alternate paths)

**Happy path**
1. Service Advisor opens an estimate in `EstimateEdit`.
2. Clicks “Promote to Work Order”.
3. UI sends a promotion request with `estimateId` and `snapshotVersion` (or equivalent).
4. Backend validates:
   - estimate is in promotable state,
   - approval is current/valid and not expired/superseded,
   - approved scope exists and matches the snapshot version,
   - promotion is idempotent (no duplicate work order creation).
5. Backend returns `workOrderId`.
6. UI navigates to `WorkOrderEdit?workOrderId=<id>`.

**Alternate paths**
- Approval missing/expired/invalid → UI blocks, shows explicit next steps (e.g., “Capture new approval”).
- Approved scope missing or snapshot mismatch → UI blocks, instructs to revise estimate and re-approve.
- Duplicate promotion → UI informs user and offers “Open existing Work Order” action (default action navigates).

## 6. Functional Behavior

### Triggers
- User clicks `Promote to Work Order` on an estimate.

### UI actions
- On click:
  - (Optional) show confirmation dialog: “Promote this estimate to a work order?” with Confirm/Cancel.
- On confirm:
  - Disable the Promote button and show progress while request is in flight.
  - Generate an `Idempotency-Key` (UUID) for this attempt; store it in component state until completion.
  - Call the promotion service/endpoint.
- On response:
  - **Success (created or existing):** show brief confirmation (toast/banner) and route to work order screen.
  - **Duplicate (idempotent conflict):** treat as non-fatal; show “Already promoted” banner and route to existing work order (immediate navigation by default; see Applied Safe Defaults).
  - **Validation error:** show inline blocking error panel with actionable instructions; keep user on estimate.
  - **Auth error (401/403):** show “Not authorized” and keep user on estimate.
  - **Not found (404):** show “Estimate not found or no longer available.”
  - **Server/network error:** show retryable error and re-enable Promote.

### State changes (frontend)
- No domain state mutation on frontend; all authoritative validation occurs server-side.
- Frontend stores transient UI state:
  - `promotionRequestStatus` = `idle | confirming | loading | success | error`
  - `promotionResult` = `{ workOrderId, outcome: CREATED|EXISTING } | null`
  - `promotionError` = `{ code, message, correlationId, fieldErrors?, existingResourceId?, details? } | null`

### Service interactions
- Single backend operation that:
  - performs idempotency check,
  - validates approval validity + expiry + superseded,
  - validates approved scope exists and matches snapshotVersion,
  - returns created/existing `workOrderId` or structured failure.

## 7. Business Rules (Translated to UI Behavior)

### Validation
Backend is authoritative. UI behavior is driven by backend `code` values (standard error envelope) and/or success payload.

Required error codes to support in UI mapping:
- `APPROVAL_NOT_FOUND`
- `APPROVAL_EXPIRED`
- `APPROVAL_INVALID`
- `APPROVED_SCOPE_MISSING`
- `SNAPSHOT_VERSION_MISMATCH`
- `PROMOTION_ALREADY_EXISTS` (duplicate/idempotent outcome)

**Decision rationale applied (resolution):**
- The original story had a blocking unknown for “approved scope missing/mismatch” code. This is resolved by defining explicit codes above for buildability; backend may map internal reasons to these stable UI-facing codes.

### Enable/disable rules
- Promote button is disabled while request is in progress.
- Promote button is enabled only when:
  - estimate is loaded, and
  - `estimate.status == "APPROVED"` (from Customer Approval Workflow), and
  - `snapshotVersion` is present.
- If capability flags are available (DECISION-INVENTORY-013), additionally disable/hide if user lacks `WORKEXEC_ESTIMATE_PROMOTE` (capability name to be implemented as part of this story’s screen auth; see Service Contracts).

**Decision rationale applied (resolution):**
- Estimate statuses are defined in `CUSTOMER_APPROVAL_WORKFLOW.md` and promotion is only meaningful from `APPROVED`. This is a domain-safe restriction (no financial policy guessed) and reduces unnecessary failing calls.

### Visibility rules
- Error panel visible only after a failed attempt.
- If duplicate promotion detected, show an “Open Work Order” call-to-action (and auto-navigate by default).

### Error messaging expectations
Messages must:
- include a short reason,
- include “what to do next,”
- include `correlationId` when present (for support),
- avoid internal stack traces or sensitive details.

UI copy mapping (suggested):
- `APPROVAL_NOT_FOUND`: “No customer approval is recorded for this estimate. Capture approval before promoting.”
- `APPROVAL_EXPIRED`: “The approval has expired. Request a new approval to continue.”
- `APPROVAL_INVALID`: “The approval is no longer valid (revoked or superseded). Capture a new approval before promoting.”
- `APPROVED_SCOPE_MISSING`: “No approved scope is available for this estimate. Re-approve the estimate before promoting.”
- `SNAPSHOT_VERSION_MISMATCH`: “This estimate has changed since it was approved. Re-approve the latest version before promoting.”
- `PROMOTION_ALREADY_EXISTS`: “This estimate was already promoted. Opening the existing work order.”

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
- Estimate screen load already exists; ensure it provides:
  - `estimateId`
  - `status` (`DRAFT|APPROVED|DECLINED|EXPIRED`)
  - `snapshotVersion` (string)

If current estimate load does not include `snapshotVersion`, add it to the screen’s data context (entity field or computed field) and render it read-only (optional) for troubleshooting.

### Create/update calls (promotion attempt)
Define a Moqui service + transition and (optional) REST endpoint for SPA usage.

**Moqui service (authoritative)**
- Service name: `durion.workexec.EstimateServices.promoteEstimateToWorkOrder`
- Inputs:
  - `estimateId` (required, type id)
  - `snapshotVersion` (required, string)
- Headers (from request context):
  - `Idempotency-Key` (required for this mutation; DECISION-INVENTORY-012)
  - `X-Correlation-Id` (optional; if absent, server generates and returns in error envelope)
- Outputs (success):
  - `workOrderId` (id)
  - `outcome` (`CREATED|EXISTING`)
- Errors (standard envelope; DECISION-INVENTORY-011):
  - `code` in the set listed in Business Rules
  - `existingResourceId` populated when `code == PROMOTION_ALREADY_EXISTS`

**Screen transition**
- In `EstimateEdit.xml`, add a transition (example name): `promoteToWorkOrder`
  - Method: `POST`
  - Calls service: `durion.workexec.EstimateServices.promoteEstimateToWorkOrder`
  - On success: redirect to `WorkOrderEdit` with `workOrderId`
  - On error: stay on `EstimateEdit` and show error panel (using envelope fields)

**Optional REST endpoint (if frontend uses fetch/XHR rather than screen transition)**
- `POST /rest/api/v1/workexec/estimates/{estimateId}/promote`
  - Body: `{ "snapshotVersion": "v3" }`
  - Success: `200 OK` with `{ "workOrderId":"WO-123", "outcome":"CREATED" }`
  - Duplicate: `200 OK` with `{ "workOrderId":"WO-123", "outcome":"EXISTING" }`
  - Validation failures: `409/422` with standard error envelope (implementation choice), but UI must rely on `code` not HTTP status.

**Decision rationale applied (resolution):**
- The original story was blocked on “exact endpoint contract.” This is resolved by specifying a Moqui service + screen transition (always implementable in this repo) and an optional REST wrapper for SPA calls. This keeps buildability while allowing platform evolution.

### Submit/transition calls
- The promotion action is a submit/transition from the estimate screen; no additional state transitions are implemented in the UI beyond invoking the service.

### Error handling expectations
- UI parses standard error envelope:
  - Always display `message` (or mapped copy) and `correlationId` when present.
  - If `fieldErrors` present, show them in a list under the main message.
  - If `code == PROMOTION_ALREADY_EXISTS`, use `existingResourceId` as the `workOrderId` to navigate.

- `DRAFT`
- `APPROVED`
- `DECLINED`

Promotion eligibility:

### Role-based transitions

  - Backend must still enforce and return 403 when unauthorized (DECISION-INVENTORY-013).

### UI behavior per state
- `APPROVED`: show Promote CTA enabled (subject to capability + snapshotVersion presence).
- `DRAFT`: show Promote CTA disabled with message “Estimate must be approved before promotion.”
- `DECLINED`: show disabled with message “Declined estimates cannot be promoted. Reopen and approve to proceed.”
- `EXPIRED`: show disabled with message “Expired estimates cannot be promoted. Create a new approval/estimate.”

## 11. Alternate / Error Flows

### Validation failures
- `APPROVAL_NOT_FOUND` → show message; provide navigation hint to approval capture section (if present on estimate screen) or instruct to capture approval.
- `APPROVAL_EXPIRED` → show message; if `details.expiresAt` present, display it in user timezone with timezone label (DECISION-INVENTORY-016).
- `APPROVAL_INVALID` → show message; if `details.reason` present (e.g., `SUPERSEDED|REVOKED`), display as secondary text.
- `APPROVED_SCOPE_MISSING` → show message; instruct to re-approve.
- `SNAPSHOT_VERSION_MISMATCH` → show message; if expected/provided versions present, display both.

### Concurrency conflicts / double-submit
- Two users promote simultaneously:
  - One gets `CREATED`, the other gets `PROMOTION_ALREADY_EXISTS` with `existingResourceId`.
  - UI treats duplicate as success and navigates to existing work order.
- Same user double-clicks:
  - UI disables button immediately.
  - If request retries, reuse same `Idempotency-Key` (DECISION-INVENTORY-012).

### Unauthorized access
- 403 → show “You don’t have permission to promote estimates to work orders.” Include correlationId if provided.

### Empty states / missing data
- If estimate loads without `snapshotVersion`:
  - Disable Promote.
  - Show inline message: “Cannot promote: estimate version information is missing. Refresh or contact support.”

## 12. Acceptance Criteria

### Scenario 1: Promote succeeds with valid approval and scope
**Given** I am authenticated as a Service Advisor  
**And** I am viewing an estimate with `estimateId=E-100`, `status=APPROVED`, and `snapshotVersion=v3`  
**And** the backend determines there is a current valid, non-expired approval for `snapshotVersion=v3` with approved scope  
**When** I click “Promote to Work Order” and confirm  
**Then** the UI sends a promotion request including `estimateId` and `snapshotVersion=v3`  
**And** the request includes an `Idempotency-Key` header  
**And** the UI receives a success response containing `workOrderId` and `outcome=CREATED`  
**And** the UI navigates to `WorkOrderEdit` for that `workOrderId`.

### Scenario 2: Block promotion when approval is expired
**Given** I am viewing an estimate `E-101` with `status=APPROVED`  
**And** the backend determines the approval is expired  
**When** I click “Promote to Work Order”  
**Then** the UI must not navigate away from the estimate  
**And** the UI must show a blocking error with `code=APPROVAL_EXPIRED`  
**And** the UI must instruct me to obtain/resubmit a new approval.

### Scenario 3: Block promotion when approval is missing
**Given** I am viewing an estimate `E-102` with `status=APPROVED`  
**And** the backend determines no approval exists  
**When** I click “Promote to Work Order”  
**Then** the UI shows a blocking error with `code=APPROVAL_NOT_FOUND`  
**And** the UI provides guidance to capture customer approval before retrying.

### Scenario 4: Block promotion when approval is invalid (revoked/superseded)
**Given** I am viewing an estimate `E-103` with `status=APPROVED`  
**And** the backend determines the most recent approval is invalid  
**When** I click “Promote to Work Order”  
**Then** the UI shows a blocking error with `code=APPROVAL_INVALID`  
**And** the UI instructs me to capture a new valid approval before promoting.

### Scenario 5: Idempotent retry returns existing work order (duplicate promotion)
**Given** estimate `E-104` with `status=APPROVED` and `snapshotVersion=v2` has already been promoted  
**And** the backend returns either:
- a success response with `outcome=EXISTING` and `workOrderId="WO-123"`, **or**
- an error envelope with `code="PROMOTION_ALREADY_EXISTS"` and `existingResourceId="WO-123"`  
**When** I click “Promote to Work Order” again  
**Then** the UI must not display a generic failure  
**And** the UI must display “Already promoted”  
**And** the UI navigates to `WO-123` (immediately or via an “Open Work Order” action).

### Scenario 6: Snapshot mismatch blocks promotion
**Given** I am viewing an estimate `E-105` with `status=APPROVED` and `snapshotVersion=v5`  
**And** the backend determines the approved scope/approval references a different snapshot version  
**When** I click “Promote to Work Order”  
**Then** the UI shows a blocking error with `code=SNAPSHOT_VERSION_MISMATCH`  
**And** the UI instructs me to re-approve the latest estimate version before promoting.

### Scenario 7: Network/server error shows retryable message and preserves idempotency key on retry
**Given** I am viewing an approved estimate  
**When** I click “Promote to Work Order” and the request times out or the backend returns `5xx`  
**Then** the UI shows a non-sensitive error message indicating the promotion could not be completed  
**And** the UI offers a retry action  
**And** when I retry the same attempt, the UI reuses the same `Idempotency-Key`  
**And** the Promote button becomes enabled again after the error is shown.
