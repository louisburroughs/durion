### Business Value
Convert an approved customer estimate into a trackable Work Order (with immutable links and audit trail) so execution can be scheduled/assigned and downstream workflows can proceed without duplicate creation or loss of approval traceability.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to promote an **Approved** Estimate into a Work Order from the POS UI  
- **So that** authorized work is captured as a Work Order with immutable references to the estimate approval and the promotion is auditable and idempotent.

### In-scope
- Frontend UI action to “Promote to Workorder” from an Estimate detail context.
- Calling backend to create the Work Order (atomic) and handling:
  - success response (navigate to Work Order),
  - idempotent “already promoted” response,
  - rejection for non-approved estimate,
  - configuration/validation/system failures.
- Displaying promotion linkage data surfaced by API (estimateId, createdBy/createdAt, and any approval metadata already available on the estimate/work order).
- UI gating based on capability/permission signals **only if already available** (capability flags or 403 handling).

### Out-of-scope
- Defining/implementing RBAC policy rules (security domain owns policy; workexec enforces only).
- Changing Work Order state machine beyond creation (start/transition execution).
- Generating supplemental PDFs or customer-facing artifacts.
- Any pricing/security policy not explicitly returned by API.

---

## 3. Actors & Stakeholders
- **Service Advisor (primary)**: initiates promotion, reviews result, navigates to created Work Order.
- **System (workexec backend/Moqui services)**: performs atomic promotion creation and returns Work Order reference.
- **Mechanic/Technician (downstream)**: consumes the Work Order later (not part of this UI story).
- **Manager/Auditor (secondary)**: needs traceability of who promoted and when.

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From `durion-workexec` estimate detail/edit screen (`EstimateEdit.xml`) when viewing an estimate with status `APPROVED`.

### Screens to create/modify
1. **Modify** `durion-workexec/EstimateEdit.xml`
   - Add an action control: **Promote to Work Order**
   - Add a confirmation dialog to reduce accidental double-submit.
2. **No new screen required**: navigate to existing `durion-workexec/WorkOrderEdit.xml` for the created/existing work order.

### Navigation context
- Estimate list → `EstimateEdit` → Promote → redirect to `WorkOrderEdit` for returned `workOrderId`.
- Provide a “Back to Estimate” link from the Work Order screen if not already present (non-blocking enhancement).

### User workflows (happy + alternate)

#### Happy path
1. Service Advisor opens an APPROVED estimate in `EstimateEdit`.
2. Clicks **Promote to Work Order**.
3. Confirms in modal.
4. UI submits create request with `estimateId` and `Idempotency-Key`.
5. On success, UI navigates to `WorkOrderEdit` for returned `workOrderId` and shows a success banner/toast.

#### Alternate paths
- Estimate not approved: action hidden/disabled; if attempted via stale UI, backend rejects and UI refreshes estimate.
- Already promoted (duplicate submit or second user): backend returns existing work order; UI navigates to it and shows “Already created”.
- Permission denied: UI shows error and does not retry.
- Network/system error: UI shows retry affordance; retry reuses the same `Idempotency-Key` for the same attempt.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Client-side (non-authoritative):
  - Show/enable promote action only when `estimate.status == "APPROVED"`.
- Server-authoritative:
  - Reject if estimate status is not APPROVED.
  - Enforce “one work order per approved estimate” (idempotent create).

### Enable/disable rules
- Promote action enabled when:
  - estimate is APPROVED, and
  - user has capability to create work orders **if** a capability signal is available; otherwise rely on 403 handling.
- Disabled while request is in-flight.

### Visibility rules
- No pricing visibility rules are introduced here.
- If the Work Order screen already has role-based visibility, this story does not change it.

### Error messaging expectations (standard envelope)
Map errors using DECISION-INVENTORY-011 envelope when available:
- 400/422 (`code` like `VALIDATION_ERROR`): “Cannot create a work order from this estimate. Verify it is approved.”
- 403: “You don’t have permission to create work orders.”
- 404: “Estimate not found.”
- 409 (`code` like `DUPLICATE`, with `existingResourceId`): “Work order already exists; opening it now.”
- 5xx/network: “Unable to create work order right now. Try again.”

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
- Load estimate for eligibility and display:
  - Moqui screen load via `EstimateEdit.xml` (existing screen actions/services).
  - If REST is used in this frontend: `GET /api/estimates/{estimateId}` (from Customer Approval workflow doc).

### Create/update calls (promotion)
**Resolved contract choice (implementation-ready):** Use existing work order creation endpoint with `estimateId` to trigger promotion semantics.

- `POST /api/workorders`
  - Headers:
    - `Idempotency-Key: <uuid>` (required) — DECISION-INVENTORY-012
  - Body:
    - `{ "estimateId": "<opaqueId>" }`
  - Success:
    - `201 Created` (preferred) or `200 OK` returning `{ workOrderId, statusId, estimateId, ... }`
  - Duplicate / already promoted:
    - `409 Conflict` with standard envelope including `existingResourceId` = existing `workOrderId` (preferred) — DECISION-INVENTORY-011
    - If backend instead returns `200 OK` with existing `workOrderId`, UI must treat as success and navigate.

**Decision rationale:** Customer Approval workflow explicitly states work order creation validates `estimateId` is approved before creating; this is the canonical promotion path and avoids inventing a new endpoint.

### Submit/transition calls
- None.

### Error handling expectations
- Parse standard error envelope when present (DECISION-INVENTORY-011).
- Always surface `correlationId` in a “Details” expandable area for support (no PII).

## 11. Alternate / Error Flows

### Validation failures
- Backend rejects because estimate not approved:
  - UI shows error and refreshes estimate by reloading `EstimateEdit` data.
- Backend rejects because estimate missing required linkage:
  - UI shows backend message (sanitized) and keeps user on estimate.

### Concurrency conflicts / duplicates
- Two advisors promote simultaneously or user double-clicks:
  - One request succeeds; the other receives 409 with `existingResourceId` or a success response with existing `workOrderId`.
  - UI navigates to the existing work order and shows “Work order already exists; opened existing.”

### Unauthorized access
- 403:
  - UI shows “You don’t have permission to create work orders.”
  - No automatic retry.

### Empty states
- Estimate not found (404):
  - Show “Estimate not found” and provide navigation back to estimate list/menu.

## 12. Acceptance Criteria

### Scenario 1: Promote approved estimate successfully
**Given** I am a Service Advisor viewing an Estimate with status `APPROVED` in `EstimateEdit`  
**When** I click “Promote to Work Order” and confirm  
**Then** the frontend sends `POST /api/workorders` with body containing the estimate id  
**And** the request includes an `Idempotency-Key` header  
**And** the UI navigates to `WorkOrderEdit` for the returned `workOrderId`  
**And** the Work Order screen shows `statusId = APPROVED` and a reference to the source estimate when available.

### Scenario 2: Prevent promotion UI for non-approved estimate
**Given** I am viewing an Estimate with status not equal to `APPROVED`  
**Then** the “Promote to Work Order” action is hidden or disabled with an explanation  
**And** if I attempt promotion via a stale UI state  
**When** the backend responds with a 400/422 validation error  
**Then** the UI displays an error indicating the estimate must be approved  
**And** the UI refreshes the estimate state.

### Scenario 3: Idempotent promotion returns existing work order
**Given** an approved Estimate has already been promoted and an existing Work Order exists  
**When** I attempt to promote the same estimate again  
**Then** the backend responds with either:
- **409 Conflict** including `existingResourceId`, **or**
- **200/201** including the existing `workOrderId`  
**And** the UI navigates to that existing work order  
**And** the UI indicates no duplicate was created.

### Scenario 4: Retry after network/system error is safe
**Given** I am viewing an approved Estimate  
**When** I attempt to promote it and the request fails due to a network error or 5xx  
**Then** the UI shows an error and offers a retry action  
**And** when I retry the same attempt, the UI reuses the same `Idempotency-Key`  
**And** the outcome is either a single created work order or navigation to the existing work order (no duplicates).

### Scenario 5: Permission denied
**Given** I am logged in without permission to create work orders  
**When** I attempt to promote an approved Estimate  
**Then** the backend responds with 403  
**And** the UI shows “You don’t have permission to create work orders”  
**And** the UI does not retry automatically.
