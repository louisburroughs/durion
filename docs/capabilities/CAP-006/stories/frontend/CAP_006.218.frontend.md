## 1. Story Header

### Title
[FRONTEND] [STORY] Completion: Validate Completion Preconditions (Checklist + Block Completion)

### Primary Persona
Service Advisor (or any authorized user attempting to complete a Work Order)

**Persona Metadata**

### Business Value
Prevent invoice disputes and revenue leakage by ensuring a Work Order cannot be marked **COMPLETED** unless required work, parts/labor reconciliation, and approval-gated change requests are resolved, with clear actionable guidance for remediation.

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor (or authorized user)
- **I want** the POS UI to validate Work Order completion preconditions and show a completion checklist
- **So that** I can only complete Work Orders when all required conditions pass, and I can quickly fix what is missing when they do not.

### In-scope
- A “Complete Work Order” user action that:
  - invokes a completion precondition validation
  - renders a structured checklist of failures (if any)
  - blocks the completion transition until all checks pass
  - proceeds to completion transition only when eligible
- Clear UX for the two explicitly-called out failure categories:
  - pending approval-gated change requests
  - unreconciled parts usage / labor entries
- Explicit Moqui screen flows, transitions, and service calls (frontend perspective)
- Concurrency-safe and double-submit-safe UI behavior (idempotency key on submit)

### Out-of-scope
- Defining or changing backend policies/formulas for “reconciled” (SoR is backend)
- Implementing inventory reconciliation workflows themselves (UI may deep-link, but does not execute reconciliation logic)
- Notification delivery for pending approvals / expiring approvals
- Creating/approving/declining change requests (covered by other workexec stories)
- Any time-entry CRUD (people domain SoR)

- **Primary User Actor:** Service Advisor (authorized to complete Work Order)

## 4. Preconditions & Dependencies
- A Work Order exists and is viewable in the POS UI.
- Work Order is in a state where completion is meaningful (see State Model section).
- User is authenticated.
- Backend provides:
  - a completion preconditions validation capability returning a list of failed checks
  - an endpoint/service to execute the completion transition (or generic transition)
  - standard error envelope (DECISION-INVENTORY-011) for 400/403/404/409/5xx with `correlationId`
- Dependency: Work Order state machine rules (workexec) must be respected; completion must not bypass validation.
- Dependency: Change request workflow exists such that “approval-gated” and “pending” can be determined by backend.
- Dependency: UI can load Work Order detail and status from existing workexec screens/services (DECISION-INVENTORY-002).
- Dependency: UI must send `Idempotency-Key` for completion submit (DECISION-INVENTORY-012).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From Work Order edit/detail screen: action button **Complete Work Order**
- (Optional) From Work Order board/list row actions: **Complete** (only if user has permission; otherwise hidden/disabled)

### Screens to create/modify
- **Modify (canonical):** `durion-workexec/screen/WorkOrderEdit.xml`
  - Add “Complete Work Order” action and checklist dialog/panel
- **Optional modify (board entry point):** `durion-workexec/screen/WorkOrderBoard.xml`
  - Add row action to open WorkOrderEdit with completion checklist open (no direct completion from board unless explicitly enabled)
- **Do NOT create a new top-level route unless needed:** Prefer embedding a reusable section/widget in `WorkOrderEdit.xml` (DECISION-INVENTORY-002).

### Navigation context
- User remains in Work Order context (same `workOrderId`).
- If validation fails, user stays on WorkOrderEdit with checklist visible.
- If completion succeeds, user remains on WorkOrderEdit with updated status and refreshed transition history.

### User workflows (happy + alternate paths)

**Happy path**
1. User opens `WorkOrderEdit` for a Work Order.
2. User clicks **Complete Work Order**.
3. UI opens “Completion Checklist” and calls validation.
4. UI receives `canComplete=true`.
5. User clicks **Proceed to Complete**.
6. UI submits completion with `Idempotency-Key`.
7. UI refreshes Work Order detail; status shows `COMPLETED`; transition history shows latest transition.

**Alternate paths**
- Validation fails: UI shows checklist grouped by category; “Proceed to Complete” remains disabled; user can navigate to fix issues and click “Refresh checklist”.
- Completion submit returns gate failure (400/409 with failed checks): UI renders returned checklist and keeps completion blocked.
- Unauthorized: UI hides/disables button when capability is available; otherwise handles 403 with clear message (DECISION-INVENTORY-013).
- Concurrency: if state changed by another user, UI refreshes and shows conflict guidance (409).

## 6. Functional Behavior

### Triggers
- User presses **Complete Work Order** for a specific `workOrderId`.

### UI actions
- Open a modal/dialog (or inline panel) titled “Completion Checklist”.
- Display loading state while validation runs.
- Render:
  - Overall eligibility (Eligible / Not eligible)
  - Failed checks list (each with code, message, and optional linked entity)
  - “Refresh checklist” action to re-run validation
  - “Proceed to Complete” action enabled only when `canComplete=true`

### State changes
- UI MUST NOT optimistically set status.
- Only after successful completion response:
  - Work Order status becomes `COMPLETED` in UI after refresh.
- If backend requires intermediate transitions (e.g., must be `READY_FOR_PICKUP` before `COMPLETED`), backend remains authoritative; UI will attempt completion and handle 409/400 with actionable message.

### Service interactions (frontend perspective)
1. `validateCompletionPreconditions(workOrderId)`
2. If eligible: `completeWorkOrder(workOrderId)` (submit completion transition)
3. Refresh Work Order detail and transition history after completion success.

### Decision rationale applied
- **Idempotency:** completion submit must include `Idempotency-Key` to prevent double-submit duplicates (DECISION-INVENTORY-012).
- **Error parsing:** UI must normalize errors to standard envelope and surface `correlationId` (DECISION-INVENTORY-011).
- **Permissions:** UI may gate via capability flags when available but must rely on backend 403 as authoritative (DECISION-INVENTORY-013).

## 7. Business Rules (Translated to UI Behavior)

### Validation (UI-enforced behavior, backend-authoritative)
- UI MUST invoke validation before enabling completion submit.
- UI MUST surface **all** failed checks returned (do not stop at first).
- UI MUST block completion when `canComplete=false`.

### Enable/disable rules
- “Proceed to Complete” button:
  - disabled until validation returns `canComplete=true`
  - disabled while validation or completion request is in-flight
- “Complete Work Order” entry action:
  - hidden/disabled if Work Order is already `COMPLETED` or `CANCELLED`
  - hidden/disabled if capability signal indicates no permission (if available); otherwise allow click and handle 403

### Visibility rules
- Checklist visible after completion attempt OR user explicitly opens it.
- If no failures, show “All checks passed” summary and enable “Proceed to Complete”.

### Error messaging expectations
- Validation failure (business): show checklist items as actionable messages.
- System failure (5xx/network): show “Unable to validate completion right now. Try again.” and include `correlationId` when available.
- 403: “You do not have permission to complete this work order.”
- 409: “Work order changed since you opened it. Refreshing…” then reload detail and re-run validation on demand.

### Change request-specific rule (from provided workflow)
- If any ChangeRequest for the Work Order is in `AWAITING_ADVISOR_REVIEW`, completion MUST be blocked and checklist must include a `PENDING_APPROVALS` failure.
- If declined emergency/safety change requests exist and customer denial acknowledgment is required for closure, completion MUST be blocked until acknowledged (backend determines; UI renders failure).

## 9. Service Contracts (Frontend Perspective)

> Moqui implementation should prefer calling Moqui services invoked by `WorkOrderEdit.xml` transitions. If REST endpoints exist, map them via Moqui `service-call` or `rest` calls consistently. Errors must be normalized to the standard envelope (DECISION-INVENTORY-011).

### Load/view calls
- Work Order detail load (existing in `WorkOrderEdit.xml`)
  - Must include `workOrderId` and `statusId` at minimum.

### Validate completion preconditions
- **Preferred (Moqui service):** `durion.workexec.WorkOrderServices.validateCompletionPreconditions`
  - **In:** `workOrderId`
  - **Out:** `canComplete`, `failedChecks[]`, optional `asOf`
- **If REST-backed instead:** `POST /rest/api/v1/workexec/workorders/{workOrderId}/completion:validate`
  - **Request:** empty body (path param only) OR `{ "workOrderId": "..." }`
  - **Response 200:** checklist response model above
- **Errors (standard envelope):**
  - 404 NOT_FOUND (invalid workOrderId)
  - 403 FORBIDDEN (no permission to validate/complete)
  - 409 CONFLICT (state changed / stale version / not eligible to validate)

### Complete transition call
- **Preferred (Moqui transition/service):** `durion.workexec.WorkOrderServices.completeWorkOrder`
  - **Headers:** `Idempotency-Key: <uuid>` (DECISION-INVENTORY-012)
  - **In:** `workOrderId`
  - **Out:** updated `statusId`, and optionally latest transition record
- **If REST-backed instead:** `POST /rest/api/v1/workexec/workorders/{workOrderId}/complete`
  - **Headers:** `Idempotency-Key`
  - **Request:** empty body unless backend requires `reason` (not assumed)
  - **Response 200:** updated work order summary `{ workOrderId, statusId, transitionedAt?, transitionedBy? }`
- **Errors (standard envelope):**
  - 400 VALIDATION_FAILED with optional `fieldErrors[]` and/or `failedChecks[]` (recommended)
  - 403 FORBIDDEN
  - 409 CONFLICT (gate failed due to concurrent changes; may include `failedChecks[]`)

### Error handling expectations (Moqui UI)
- If completion endpoint returns `failedChecks`, UI must render them in the checklist without requiring a separate validate call.
- UI must display `correlationId` from error envelope in an expandable “Details” area for support.

## 10. State Model & Transitions

### Allowed states (workexec reference)
WorkOrder statuses include:
- `DRAFT`, `APPROVED`, `ASSIGNED`, `WORK_IN_PROGRESS`, `AWAITING_PARTS`, `AWAITING_APPROVAL`, `READY_FOR_PICKUP`, `COMPLETED`, `CANCELLED`

### Completion transition
- UI intent: transition to `COMPLETED`.
- UI offers completion action when:
  - Work Order is not already `COMPLETED` or `CANCELLED`
  - User is authorized
  - Backend validation passes
- Backend is authoritative for allowed-from states; UI must handle 400/409 with actionable checklist.

### Role-based transitions
- UI should use capability flags if available (DECISION-INVENTORY-013), but must not hardcode roles.
- Backend enforces authorization with 403.

### UI behavior per state
- `COMPLETED` / `CANCELLED`: hide/disable completion actions.
- Other states: allow opening checklist; only allow submit when `canComplete=true`.

## 11. Alternate / Error Flows

### Validation failures
- Pending approvals (`PENDING_APPROVALS`):
  - Show each referenced ChangeRequest (id + status).
  - Provide navigation to the Work Order’s “Change Requests” section if present in `WorkOrderEdit.xml`; otherwise show identifiers only.
- Unreconciled parts (`UNRECONCILED_PARTS`):
  - Show each referenced part usage signal (id + status).
  - Provide navigation to the Work Order’s parts/consumption section if present; otherwise show identifiers only.
- Unreconciled labor (`UNRECONCILED_LABOR`):
  - Show each referenced labor entry (id + status).
  - Provide navigation to labor/time section if present; otherwise show identifiers only.
- Incomplete required items (`INCOMPLETE_REQUIRED_ITEMS`):
  - Show each referenced item and its status.

### Concurrency conflicts
- If validate or complete returns 409:
  - Show message and provide “Refresh Work Order” action.
  - After refresh, keep checklist open and allow re-validate.

### Unauthorized access
- If 403 on validate or complete:
  - Show blocking banner/toast.
  - Ensure UI does not auto-retry.

### Empty/invalid responses
- If `canComplete=false` and `failedChecks=[]`:
  - Show generic error “Completion eligibility could not be determined.” and include correlationId if present.
- If API unreachable:
  - Show retry.

## 12. Acceptance Criteria (Gherkin)

### Scenario 1: Completion succeeds when all preconditions pass
**Given** a Work Order exists and the completion validation returns `canComplete=true` with an empty `failedChecks` list  
**When** the user opens the completion checklist and selects “Proceed to Complete”  
**Then** the UI sends a completion request including an `Idempotency-Key` header  
**And** the Work Order detail refresh shows status `COMPLETED`  
**And** the UI shows a success confirmation message.

### Scenario 2: Block completion when required WorkOrderItems are incomplete
**Given** a Work Order exists and validation returns `canComplete=false`  
**And** `failedChecks` contains an item with `check=INCOMPLETE_REQUIRED_ITEMS` referencing at least one WorkOrderItem  
**When** the user selects “Complete Work Order”  
**Then** the UI displays the completion checklist containing the incomplete item(s)  
**And** the “Proceed to Complete” action is disabled  
**And** no completion transition request is sent.

### Scenario 3: Block completion when approval-gated Change Requests are unresolved
**Given** a Work Order exists and validation returns `canComplete=false`  
**And** `failedChecks` contains an item with `check=PENDING_APPROVALS` referencing a ChangeRequest with status `AWAITING_ADVISOR_REVIEW`  
**When** the user selects “Complete Work Order”  
**Then** the UI displays a checklist item describing the pending approval(s)  
**And** the UI blocks completion until a subsequent validation returns `canComplete=true`.

### Scenario 4: Block completion when parts usage is unreconciled
**Given** a Work Order exists and validation returns `canComplete=false`  
**And** `failedChecks` contains an item with `check=UNRECONCILED_PARTS` referencing a PartUsageEvent in a pending/mismatch state  
**When** the user selects “Complete Work Order”  
**Then** the UI displays checklist items identifying the unreconciled parts usage  
**And** completion remains blocked until a re-validation returns `canComplete=true`.

### Scenario 5: Multiple failures are shown together
**Given** a Work Order exists and validation returns `canComplete=false`  
**And** `failedChecks` contains at least two different check types  
**When** the user selects “Complete Work Order”  
**Then** the UI displays all failed checks in the checklist  
**And** the UI does not hide subsequent failures after the first.

### Scenario 6: Unauthorized user cannot complete
**Given** a Work Order exists  
**And** the current user is not authorized to complete the Work Order  
**When** the user attempts to validate or complete the Work Order  
**Then** the backend returns 403 with a standard error envelope including `correlationId`  
**And** the UI displays an authorization error message  
**And** the Work Order status is not changed.

### Scenario 7: Work order changed concurrently
**Given** a Work Order is open in the UI  
**And** another user changes the Work Order such that the completion attempt conflicts  
**When** the user attempts to validate or complete and the backend returns 409 with a standard error envelope  
**Then** the UI prompts the user to refresh  
**And** after refresh, the UI reflects the latest Work Order status  
**And** the user can re-run validation.

### Scenario 8: Double-submit protection for completion
**Given** validation returns `canComplete=true`  
**When** the user double-clicks “Proceed to Complete” (or retries after a transient network error)  
**Then** the UI reuses the same `Idempotency-Key` for the same attempt  
**And** the backend returns a single effective completion outcome  
**And** the UI ends in a consistent state showing `COMPLETED` (or a single failure checklist).
