## 1. Story Header

### Title
[FRONTEND] [STORY] Completion: Resolve Approval-Gated Change Requests

### Primary Persona
Service Advisor (Back Office / Front Counter)

**Persona Metadata**
- `primary_persona`: `Service Advisor (Back Office / Front Counter)`
- `canonical_persona`: `Service Advisor`
- `persona_family`: `Service Advisor`
- `actor_type`: `human`

### Business Value
Ensure work orders cannot be completed while approval-gated change requests are unresolved, and provide an explicit, auditable workflow to approve/decline/acknowledge emergency denials so the work order reflects authorized work and completion blockers are transparent.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to view and resolve all approval-gated change requests for a work order (approve, decline, and handle emergency denial acknowledgment where applicable)  
- **So that** the work order can move to completion states only when authorized work is correctly reflected and completion blockers are transparent and auditable.

### In Scope
- Work order “Completion blockers” UI that highlights unresolved approval-gated change requests.
- List + detail view of change requests associated to a work order.
- Advisor actions to:
  - Approve a change request (with required approval note).
  - Decline a change request (with required approval note).
  - For emergency exceptions that were declined: record customer denial acknowledgment (to unblock closure).
- Read-only display of audit-relevant fields: who/when/what decision, approval notes, status.
- Integration with backend endpoints listed in `CHANGE_REQUEST_WORKFLOW.md` and work order “can-close” check.

### Out of Scope
- Creating change requests (technician flow).
- Editing change request item lines, prices, or inventory allocation/consumption.
- Customer-facing approval capture methods (signature, electronic signature) for **estimates** (separate workflow).
- Work order state transitions UI beyond showing “blocked/unblocked” and “can close” status (unless already exists).
- Any “manager override / approved-with-exception” state for change requests (explicitly excluded; see Decision Rationale in Open Questions resolution).

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated in the POS frontend.
- A Work Order exists and is accessible to the user.
- Work order has **zero or more** associated Change Requests retrievable via:
  - `GET /api/work-orders/{workOrderId}/change-requests`

### Dependencies
- Backend endpoints available (authoritative from `CHANGE_REQUEST_WORKFLOW.md`):
  - `GET /api/work-orders/{workOrderId}/change-requests`
  - `GET /api/change-requests/{id}`
  - `POST /api/change-requests/{id}/approve`
  - `POST /api/change-requests/{id}/decline`
  - `POST /api/change-requests/{id}/acknowledge-denial`
  - `GET /api/work-orders/{workOrderId}/can-close`
- Work order completion gating is enforced by backend (frontend displays blockers and does not attempt to bypass).
- Standard error envelope is available or errors are normalized to it (DECISION-INVENTORY-011):
  - `{ code, message, correlationId, fieldErrors?, existingResourceId? }`
- For mutation calls, frontend sends `Idempotency-Key` header and reuses it on retry for the same attempt (DECISION-INVENTORY-012).
- IDs are opaque strings; UI must not validate as UUID/numeric (DECISION-INVENTORY-003).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From existing Work Order edit/detail screen (canonical workexec screen per DECISION-INVENTORY-002: `durion-workexec/WorkOrderEdit.xml`):
  - A “Completion Blockers” section appears when `canClose=false` OR there are any change requests in `AWAITING_ADVISOR_REVIEW`.
  - A “Change Requests” link navigates to the work order’s change request list.
- Optional secondary entry: from Work Order board (`durion-workexec/WorkOrderBoard.xml`) via a row action “Change Requests” (if board already links to WO detail, this is not required).

### Screens to create/modify
1. **Modify:** `durion-workexec/WorkOrderEdit.xml`
   - Add a read-only “Completion Blockers” panel:
     - Displays `canClose` status (Allowed to close: Yes/No).
     - If `canClose=false`, display blocker reasons derived from available data:
       - “Pending change requests require advisor decision” when any CR is `AWAITING_ADVISOR_REVIEW`.
       - “Emergency denial acknowledgment required” when any declined emergency CR has unacknowledged emergency items (if item-level data is available; otherwise show generic “Emergency denial acknowledgment required (see change requests)” when `canClose=false` and there are declined emergency CRs).
     - Link/button: “Review Change Requests” → navigates to `WorkOrderChangeRequests`.
2. **Create:** `durion-workexec/WorkOrderChangeRequests.xml`
   - Parameters: `workOrderId` (required; opaque string).
   - Displays list of change requests for the work order.
   - Grouping: by status in this order:
     1) `AWAITING_ADVISOR_REVIEW`
     2) `APPROVED`
     3) `DECLINED`
     4) `CANCELLED`
   - Each list entry shows: description, status, requestedAt, emergency flag, and a “Needs acknowledgment” indicator when applicable.
   - Row click navigates to `ChangeRequestDetail`.
3. **Create:** `durion-workexec/ChangeRequestDetail.xml`
   - Parameters: `changeRequestId` (required), `workOrderId` (required for back navigation).
   - Displays:
     - Change request header fields (description, status, requestedAt, requestedBy, emergency exception fields).
     - Associated items (services and parts) with their statuses and emergency fields.
     - Decision/audit fields (approvalNote, approvedAt/by, declinedAt).
   - Actions:
     - Approve (only if status `AWAITING_ADVISOR_REVIEW`)
     - Decline (only if status `AWAITING_ADVISOR_REVIEW`)
     - Acknowledge Denial (only if `isEmergencyException=true` AND status `DECLINED` AND there exists at least one emergency item with `customerDenialAcknowledged=false`)

### Navigation context
- Work Order Edit → Change Requests List → Change Request Detail
- Back navigation returns to list, preserving `workOrderId`.

### User workflows (happy + alternate)
- **Happy: Approve**
  1. Advisor opens Work Order; sees blockers.
  2. Opens Change Requests list; selects a pending request.
  3. Clicks Approve; enters approval note; confirms.
  4. UI refreshes detail + list + `can-close`; blockers clear when all resolved and acknowledgments satisfied.
- **Happy: Decline + Emergency Acknowledgment**
  1. Advisor declines an emergency exception request with required note.
  2. If emergency items exist, UI shows acknowledgment requirement and enables Acknowledge Denial.
  3. Advisor acknowledges denial; UI refreshes `can-close` and clears blocker when backend returns `true`.
- **Alternate: Customer unreachable**
  - Advisor takes no action; request remains `AWAITING_ADVISOR_REVIEW`; completion stays blocked.

## 6. Functional Behavior

### Triggers
- On Work Order Edit screen load:
  - Fetch change request list summary for the work order.
  - Fetch `can-close` status for the work order.
- On Change Requests list screen load:
  - Fetch change request list for the work order.
  - Fetch `can-close` status for the work order (to show banner at top of list).
- On Change Request detail screen load:
  - Fetch change request detail.
  - Fetch `can-close` status for the parent work order.

### UI actions
- **Approve**
  - Opens a modal/dialog with a required multi-line text input `approvalNote`.
  - On confirm:
    - Send `POST /api/change-requests/{id}/approve` with `approvalNote` and `approvedBy` (current user id from session context).
    - Include `Idempotency-Key` header.
- **Decline**
  - Opens a modal/dialog with required `approvalNote`.
  - On confirm:
    - Send `POST /api/change-requests/{id}/decline` with `approvalNote`.
    - Include `Idempotency-Key` header.
- **Acknowledge Denial**
  - Confirmation dialog (no text required).
  - On confirm:
    - Send `POST /api/change-requests/{id}/acknowledge-denial`.
    - Include `Idempotency-Key` header.

### State changes (frontend-visible)
- ChangeRequest `status` updates after approve/decline.
- For emergency denial acknowledgment:
  - Associated emergency items become `customerDenialAcknowledged=true` (if returned by detail endpoint); otherwise UI relies on refreshed detail and/or `can-close`.
- Work order closure eligibility updates based on refreshed `GET can-close`.

### Service interactions (Moqui-oriented)
- Implement REST calls via Moqui service wrappers invoked from screen transitions:
  - `durion.workexec.ChangeRequestServices.getChangeRequestsForWorkOrder`
  - `durion.workexec.ChangeRequestServices.getChangeRequestDetail`
  - `durion.workexec.ChangeRequestServices.approveChangeRequest`
  - `durion.workexec.ChangeRequestServices.declineChangeRequest`
  - `durion.workexec.ChangeRequestServices.acknowledgeChangeRequestDenial`
  - `durion.workexec.WorkOrderServices.canCloseWorkOrder`
- Each mutation transition:
  - Disables submit button while in-flight.
  - On retry after network failure, reuses the same `Idempotency-Key` for that attempt.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Approve/Decline requires **non-empty** `approvalNote` (trimmed).
  - UI blocks submit and shows inline error: “Approval note is required.”
- Acknowledge Denial:
  - Only enabled if:
    - `changeRequest.isEmergencyException == true`
    - `changeRequest.status == DECLINED`
    - and there exists at least one associated item where `isEmergencySafety==true` and `customerDenialAcknowledged==false`
  - If item-level data is unavailable, UI enables Acknowledge Denial when `isEmergencyException==true` and `status==DECLINED` and `canClose==false`, but must handle backend rejection gracefully.

### Enable/disable rules
- Approve/Decline buttons enabled only when `status == AWAITING_ADVISOR_REVIEW`.
- All action buttons are hidden/disabled if the user lacks capability flags (if available) and always enforced by backend with 403 (DECISION-INVENTORY-013).
- If backend rejects due to invalid state (400/409), UI shows message and refreshes.

### Visibility rules
- Show “Emergency/Safety” section if:
  - `isEmergencyException==true` OR any item has `isEmergencySafety==true`.
- Show completion blocker banner on Work Order Edit if:
  - `canClose == false` OR any CR is `AWAITING_ADVISOR_REVIEW`.

### Error messaging expectations (standard envelope)
- 400 with `fieldErrors`:
  - Map to field-level errors (e.g., `approvalNote`).
- 400/409 without field errors:
  - Show banner: “Unable to complete action: <message>” and include `correlationId` in a “Details” expandable area.
- 403:
  - “You don’t have permission to perform this action.”
- 404:
  - “Change request not found.”
- Network/timeout:
  - “Network error. Retry.” (no optimistic state changes).

## 9. Service Contracts (Frontend Perspective)

> Contracts are based on `CHANGE_REQUEST_WORKFLOW.md`. Where response shapes are not fully specified, frontend must only depend on fields listed in Data Requirements and treat others as optional.

### Load / view calls
1. **List change requests for work order**
   - `GET /api/work-orders/{workOrderId}/change-requests`
   - Response: array of ChangeRequest summaries.
   - Minimum required fields per item: `id`, `status`, `description`, `requestedAt`, `isEmergencyException`.
2. **Load change request detail**
   - `GET /api/change-requests/{id}`
   - Response: ChangeRequest + associated items (services/parts) OR references sufficient to render:
     - If items are not included, UI must still render header + decision actions; item list shows “Items unavailable” and relies on `can-close` for closure gating.
3. **Can close work order**
   - `GET /api/work-orders/{workOrderId}/can-close`
   - Response: boolean (`true|false`).
   - If backend later returns a structured object (e.g., `{canClose, reasons[]}`), UI should support it behind feature detection, but must not require it.

### Create/update/submit calls
1. **Approve change request**
   - `POST /api/change-requests/{id}/approve`
   - Headers: `Idempotency-Key: <uuid>`
   - Body:
     ```json
     { "approvedBy": "<currentUserId>", "approvalNote": "<text>" }
     ```
   - Success: 200 OK with updated ChangeRequest (preferred) OR 204 No Content (UI then refetches detail).
2. **Decline change request**
   - `POST /api/change-requests/{id}/decline`
   - Headers: `Idempotency-Key: <uuid>`
   - Body:
     ```json
     { "approvalNote": "<text>" }
     ```
   - Success: 200 OK with updated ChangeRequest OR 204 No Content (UI refetches).
3. **Acknowledge denial**
   - `POST /api/change-requests/{id}/acknowledge-denial`
   - Headers: `Idempotency-Key: <uuid>`
   - Body: none
   - Success: 200 OK (preferred) OR 204 No Content (UI refetches detail + can-close).

### Error handling expectations
- Standard envelope (DECISION-INVENTORY-011) for 400/403/404/409 where possible:
  - `correlationId` must be displayed in error details for support.
- 409 indicates either concurrency or invalid transition due to state change; UI must refresh.

## 10. State Model & Transitions

### ChangeRequest states (authoritative)
- `AWAITING_ADVISOR_REVIEW`
- `APPROVED`
- `DECLINED`
- `CANCELLED`

### Allowed transitions (UI-enforced)
- `AWAITING_ADVISOR_REVIEW` → `APPROVED` (Approve)
- `AWAITING_ADVISOR_REVIEW` → `DECLINED` (Decline)
- `DECLINED` + `isEmergencyException=true` → acknowledgment recorded (state remains `DECLINED`)

### Role-based transitions
- UI gates by capability flags if available (DECISION-INVENTORY-013), but backend is authoritative:
  - `WORKEXEC_CHANGE_REQUEST_APPROVE`
  - `WORKEXEC_CHANGE_REQUEST_DECLINE`
  - `WORKEXEC_CHANGE_REQUEST_ACK_DENIAL`
  - (Exact capability names are TBD; UI must be able to map from returned capabilities to these actions.)

### UI behavior per state
- `AWAITING_ADVISOR_REVIEW`: show Approve/Decline; show “Blocks completion” indicator.
- `APPROVED`: show decision metadata; no actions.
- `DECLINED`: show decision metadata; show acknowledgment section if emergency exception.
- `CANCELLED`: read-only.

## 11. Alternate / Error Flows

### Validation failures
- Missing `approvalNote`:
  - Client-side prevents submit.
  - If server returns 400, show server message and field error mapping.
- Attempt acknowledge when not allowed:
  - UI hides action; if forced via deep link, handle 400/409 and refresh.

### Concurrency conflicts
- Another advisor resolves while current user is viewing:
  - On submit: 409; UI shows “This change request was already updated. Refreshing…” then refetches detail and list.

### Unauthorized access
- 403 on any action:
  - UI shows permission error; no local state change; refetch to ensure UI reflects current server state.

### Empty states
- No change requests:
  - List screen shows “No change requests for this work order.”
  - Work order blockers panel shows “No completion blockers from change requests.”

### Backend unreachable / timeout
- Show non-destructive error banner and a Retry action.
- Do not optimistically update status.

## 12. Acceptance Criteria

### Scenario 1: Pending change requests are visible and block completion
**Given** a work order has at least one change request with status `AWAITING_ADVISOR_REVIEW`  
**When** the Service Advisor opens the Work Order edit/detail screen  
**Then** the UI shows a completion blocker indicating pending change requests  
**And** the UI provides a navigation link to the Change Requests screen for that work order  
**And** the UI displays the current `canClose` value from `GET /api/work-orders/{workOrderId}/can-close`.

### Scenario 2: List change requests for a work order
**Given** a work order has change requests in multiple statuses  
**When** the Service Advisor navigates to the Work Order Change Requests screen  
**Then** the UI lists all change requests returned by `GET /api/work-orders/{workOrderId}/change-requests`  
**And** each list entry shows at minimum: description, status, requestedAt, and emergency flag (if present)  
**And** selecting an entry navigates to the Change Request detail view for that change request.

### Scenario 3: Approve requires an approval note and updates UI state (idempotent)
**Given** a change request is in status `AWAITING_ADVISOR_REVIEW`  
**When** the Service Advisor clicks “Approve” and submits an empty approval note  
**Then** the UI blocks submission and displays “Approval note is required.”

**Given** a change request is in status `AWAITING_ADVISOR_REVIEW`  
**When** the Service Advisor submits “Approve” with a non-empty approval note  
**Then** the UI calls `POST /api/change-requests/{id}/approve` with `approvedBy` and `approvalNote`  
**And** the request includes an `Idempotency-Key` header  
**And** on success, the UI refreshes the change request data showing status `APPROVED`  
**And** the approve/decline actions are no longer available.

**Given** the approve request is submitted and the network times out  
**When** the Service Advisor retries the same approve attempt from the UI retry affordance  
**Then** the UI reuses the same `Idempotency-Key` for that attempt  
**And** the resulting server outcome is reflected without creating duplicate approvals.

### Scenario 4: Decline requires an approval note and updates UI state (idempotent)
**Given** a change request is in status `AWAITING_ADVISOR_REVIEW`  
**When** the Service Advisor submits “Decline” with a non-empty approval note  
**Then** the UI calls `POST /api/change-requests/{id}/decline` with `approvalNote`  
**And** the request includes an `Idempotency-Key` header  
**And** on success, the UI refreshes the change request data showing status `DECLINED`  
**And** the approve/decline actions are no longer available.

### Scenario 5: Declined emergency exception requires customer denial acknowledgment to close
**Given** a work order has a change request where `isEmergencyException=true` and status `DECLINED`  
**And** at least one emergency item under the request has `customerDenialAcknowledged=false`  
**When** the Service Advisor opens the work order  
**Then** the UI indicates the work order cannot close by showing `canClose=false` from `GET /api/work-orders/{workOrderId}/can-close`  
**And** the Change Request detail screen shows an “Acknowledge Denial” action.

### Scenario 6: Acknowledge denial updates closure eligibility
**Given** a change request is flagged emergency exception and is in status `DECLINED`  
**When** the Service Advisor confirms “Acknowledge Denial”  
**Then** the UI calls `POST /api/change-requests/{id}/acknowledge-denial`  
**And** the request includes an `Idempotency-Key` header  
**And** the UI refreshes `GET /api/work-orders/{workOrderId}/can-close`  
**And** if the backend returns `true`, the UI indicates the completion blocker is cleared.

### Scenario 7: Concurrency protection on approve/decline
**Given** a Service Advisor has a change request detail open in status `AWAITING_ADVISOR_REVIEW`  
**And** another user resolves the change request before submission  
**When** the first advisor submits approve/decline  
**Then** the UI receives a 409 response  
**And** the UI shows a conflict message including the server `correlationId` (if provided)  
**And** the UI refreshes the change request detail to show the latest status.

### Scenario 8: Permission denied
**Given** a user without permission attempts to approve a change request  
**When** they submit approval  
**Then** the backend returns 403  
**And** the UI shows a permission error and leaves the change request unchanged in the UI.
