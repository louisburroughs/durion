### Business Value
Enables an explicit, auditable “Complete Workorder” action that finalizes execution, locks execution edits from uncontrolled changes, and triggers downstream processing via a single idempotent completion transition—without creating invoice/AR/revenue in the UI.

## 2. Story Intent

### As a / I want / So that
**As a** Service Advisor (or Shop Manager)  
**I want** to complete a work order via an explicit, permission-controlled action  
**So that** execution is finalized with an audit trail, completion metadata is captured, further execution edits are locked, and downstream systems can react to a single idempotent completion transition/event.

### In-scope
- Add/enable a UI action to complete a work order from eligible statuses
- Capture completion notes (optional) and completion reason (optional)
- Call Moqui backend transition/service to complete
- Display success/failure results and updated status
- Enforce “locked” UI behavior after completion (disable/hide execution edits)
- Display completion audit metadata (who/when) and status transition history (read-only) when available

### Out-of-scope
- Implementing backend precondition rules (frontend must surface backend failures)
- Reopen workflow authoring (frontend only respects current status and backend enforcement)
- Accounting/WIP ledger postings logic (frontend does not compute or post)
- Notification delivery to customer
- Any SubstituteLink/product master-data admin

---

## 3. Actors & Stakeholders

- **Primary Actor:** Service Advisor / Shop Manager (initiates completion, records notes)
- **Secondary Actors:** Mechanic (impacted by lockout; cannot edit execution scope after completion)
- **System Stakeholders:**
  - Workexec audit/transition history (append-only transition records)
  - Downstream integrations consuming completion transition/event (outside frontend scope)
  - Billing/accounting domains (must not be triggered by frontend beyond completion transition)

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Completion must be explicit:
  - user must confirm in a dialog before calling backend
- Frontend validation:
  - no required fields unless backend contract requires them (do not invent requirements)
  - if backend requires a reason, enforce required field client-side once confirmed by contract
- Backend validation failures:
  - render `fieldErrors[]` inline
  - render `message` as a banner
  - include `correlationId` in an expandable “Details” area for support

### Enable/disable rules
- If `statusId == COMPLETED`:
  - hide or disable completion action
  - disable/hide execution-scope editing actions in WorkOrderEdit (parts/labor/services/fees/line edits) that are part of workexec execution UI
- If `statusId == CANCELLED`:
  - completion action not available
  - work order is read-only in execution surfaces
- If status is otherwise not eligible:
  - completion action disabled with explanation when known (e.g., “Not eligible in current status”)
  - do not hardcode a status eligibility list beyond excluding COMPLETED/CANCELLED; rely on backend capability/403/400/409

### Visibility rules
- Completion section visible when:
  - `statusId == COMPLETED` OR completion fields exist
- Completion notes:
  - show value if present; otherwise show “None”

### Error messaging expectations (standard envelope)
- 400 with `fieldErrors`: show inline errors and banner “Cannot complete work order”
- 403: “You don’t have permission to complete work orders.”
- 404: “Work order not found or you no longer have access.”
- 409: “Work order changed since you opened it. Refresh and try again.”
- 5xx: “Something went wrong completing the work order. Try again.”

## 8. Data Requirements

### Entities involved (frontend perspective)
- `durion.workexec.DurWorkOrder` (authoritative for status and completion metadata)
- `WorkOrderStateTransition` (append-only transition history) if exposed via endpoint/service
- Optional: `WorkOrderSnapshot` (read-only) if exposed and used for audit display

### Fields (types, required, defaults)
**DurWorkOrder (read)**
- `workOrderId` (type: id/opaque string; required)
- `statusId` (type: id/string enum; required)
- `completedAt` (type: datetime; optional until completed)
- `completedBy` (type: id; optional until completed)
- `completionNotes` (type: text; optional)
- `lastUpdatedStamp` or `version` (type: datetime/string; optional; used for optimistic concurrency if provided)

**Completion command (write)**
- `workOrderId` (path param)
- `completionNotes` (optional)
- `reason` (optional)
- `version`/`lastUpdatedStamp` (optional; include if backend supports concurrency token)

**Transition history (read-only)**
- `fromStatus` (string)
- `toStatus` (string)
- `transitionedAt` (datetime, UTC)
- `transitionedBy` (id)
- `reason` (string/text; optional)

### Read-only vs editable by state/role
- Before completion: execution edits follow existing WorkOrderEdit behavior (not expanded here)
- After completion (`COMPLETED`) and cancellation (`CANCELLED`):
  - all execution edits are read-only in workexec UI
  - completion metadata is read-only

### Derived/calculated fields
- Display “Completed by <user> at <time>” derived from `completedBy` and `completedAt`
- Time display uses user timezone (DECISION-INVENTORY-016); show timezone label in UI

## 9. Service Contracts (Frontend Perspective)

> Contracts below are implementation targets for the frontend integration layer. If the backend uses Moqui screen actions/services instead of REST, map these to equivalent service calls while preserving request/response semantics and error envelope normalization (DECISION-INVENTORY-011).

### Load/view calls
- `GET /rest/api/v1/workexec/workorders/{workOrderId}`
  - Returns `DurWorkOrder` view including `statusId`, completion fields, and capability flags if available.

- Optional:
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}/transitions`
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}/snapshots`

### Create/update calls
- none (completion is a command/transition)

### Submit/transition calls
- Preferred explicit command:
  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/complete`
  - Headers:
    - `Idempotency-Key: <uuid>` (required for this mutation; DECISION-INVENTORY-012)
  - Body (JSON):
    - `completionNotes` (optional)
    - `reason` (optional)
    - `version` (optional, if supported)

- Alternative if backend uses generic transition:
  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/transition`
  - Body includes `toStatus: "COMPLETED"` plus optional fields above.

**Response expectations**
- 200 OK with updated work order representation including `statusId=COMPLETED` and completion fields
- If already completed and idempotency key matches prior attempt:
  - 200 OK with same completed representation (preferred)
  - or 409 with standard envelope; frontend must treat “already completed” as success after refresh (see Error Flows)

### Error handling expectations (standard envelope; DECISION-INVENTORY-011)
- All non-2xx responses return JSON:
  - `code` (string)
  - `message` (string)
  - `correlationId` (string)
  - optional `fieldErrors[]` with `{field, message}`
  - optional `existingResourceId` (not expected for completion)

## 10. State Model & Transitions

### Allowed states (authoritative)
Use workexec status taxonomy; started is `WO_IN_PROGRESS` or later (DECISION-INVENTORY-004). For this story, completion targets the terminal completed status.

- Pre-start examples: `WO_CREATED`, `WO_SCHEDULED` (per DECISION-INVENTORY-004)
- Started-or-later: `WO_IN_PROGRESS` and later (includes `READY_FOR_PICKUP`)

> Note: The repository includes a separate FSM doc with different enum names. For frontend gating, do not hardcode names; rely on backend-provided `statusId` and capability flags. Display status as provided.

### Allowed transitions (frontend-relevant)
- Transition to `COMPLETED` is allowed only when backend FSM permits it.
- UI must not assume which intermediate statuses are eligible; it must:
  - hide/disable completion when `statusId` is `COMPLETED` or `CANCELLED`
  - otherwise rely on backend capability flags and backend enforcement (400/409)

### Role-based transitions
- Completion action requires an explicit capability/permission (DECISION-INVENTORY-013).
- Backend remains authoritative; UI gating is advisory.

### UI behavior per state
- `COMPLETED`: show completion metadata; lock execution edits; hide completion action
- `CANCELLED`: read-only; hide completion action
- Other statuses: show completion action only if capability indicates allowed

## 11. Alternate / Error Flows

### Validation failures (preconditions not satisfied)
- Backend returns 400 with standard envelope and optional `fieldErrors`
- UI behavior:
  - keep dialog open
  - show banner + inline errors
  - show `correlationId` in details
  - do not change local status; refresh work order after dismissal to ensure current state

### Concurrency conflicts / invalid transition
- Backend returns 409 (or 400 with code indicating invalid transition)
- UI behavior:
  - show conflict message
  - refresh work order details
  - re-evaluate action availability; if now completed, treat as success state

### Unauthorized access
- Backend returns 403
- UI behavior:
  - show authorization error
  - hide/disable completion action on subsequent renders (until capability refresh)

### Network failure / timeout after submit
- UI behavior:
  - show “Request may have succeeded. Refreshing…” with retry option
  - on retry, reuse the same `Idempotency-Key` for that attempt (DECISION-INVENTORY-012)
  - refresh work order; if completed, show completed state without duplicating action

### Empty states
- If transitions endpoint returns empty:
  - show “No transition history available” (do not block completion metadata display)

## 12. Acceptance Criteria

### Scenario 1: Complete work order successfully
**Given** a work order exists and is not in `COMPLETED` or `CANCELLED` status  
**And** the logged-in user has the capability to complete work orders  
**When** the user opens WorkOrderEdit and confirms “Complete Work Order” with optional notes  
**Then** the frontend sends a completion command with an `Idempotency-Key`  
**And** the UI refreshes the work order  
**And** the work order status is displayed as `COMPLETED`  
**And** `completedAt` and `completedBy` are shown read-only  
**And** execution edit actions in WorkOrderEdit are disabled/hidden.

### Scenario 2: Backend preconditions fail (400)
**Given** a work order is shown with the completion action enabled  
**When** the user confirms completion  
**And** the backend responds 400 with a standard error envelope  
**Then** the UI shows a blocking banner message  
**And** any `fieldErrors` are shown inline on the dialog fields  
**And** the dialog remains open  
**And** the work order remains not completed after refresh.

### Scenario 3: Already completed work order (idempotent UX)
**Given** a work order is already `COMPLETED`  
**When** the user views WorkOrderEdit  
**Then** the completion action is not available  
**And** completion metadata is displayed read-only.

### Scenario 4: Double-submit protection + idempotency retry
**Given** the completion dialog is open  
**When** the user clicks confirm  
**Then** the confirm button is disabled while the request is in flight  
**And** the frontend does not send a second request from repeated clicks  
**And** if the request fails due to network error and the user retries  
**Then** the frontend reuses the same `Idempotency-Key` for that attempt.

### Scenario 5: Unauthorized completion attempt (403)
**Given** a work order is not completed/cancelled  
**And** the user lacks completion permission  
**When** the user attempts completion (via UI or direct request path)  
**Then** the backend responds 403  
**And** the UI shows an authorization error  
**And** the work order remains unchanged.

### Scenario 6: Conflict due to concurrent update (409)
**Given** a work order is open in the UI  
**And** another user changes the work order such that completion is no longer allowed  
**When** the first user confirms completion  
**Then** the backend responds 409 (or equivalent conflict) with a standard error envelope  
**And** the UI refreshes the work order  
**And** the UI shows an actionable conflict message.

### Scenario 7: Transition history display (when available)
**Given** a completed work order  
**And** the transitions endpoint is available  
**When** the user views the work order  
**Then** the UI displays a read-only transition entry showing the change to `COMPLETED` including who/when and optional reason.
