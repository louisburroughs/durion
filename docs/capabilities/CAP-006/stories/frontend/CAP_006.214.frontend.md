## Issue Body

## 1. Story Header

### Title
[FRONTEND] [STORY] Completion: Reopen Completed Workorder (Controlled)

### Primary Persona
Back Office Manager

### Business Value
Enable controlled correction of completed work orders prior to invoicing, with strict permission gating, mandatory justification, and auditable invalidation of invoice-ready scope to protect downstream accounting and billing integrity.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Back Office Manager  
- **I want** to reopen a completed work order by providing a mandatory reason  
- **So that** I can correct mistakes while preserving auditability and preventing invoicing until the work order is properly re-completed.

### In-scope
- Frontend UI to initiate “Reopen” for eligible work orders.
- Mandatory reason capture and submission.
- Permission-aware visibility/enablement of the action.
- Post-action UI state updates (reopened flag, invoice-ready revoked).
- Display of relevant audit/transition feedback to the user (confirmation + status indicators).
- Idempotency-safe UX for repeated submission attempts (prevent double-submit; handle duplicate/idempotent outcomes gracefully).
- Standard error envelope parsing and user messaging (DECISION-INVENTORY-011).
- Send `Idempotency-Key` header for the reopen mutation (DECISION-INVENTORY-012).

### Out-of-scope
- Credit/rebill workflows when an invoice is already issued/finalized.
- Defining or editing the editability policy itself (config/table management).
- Implementing backend event emission, accounting integration plumbing (frontend will rely on backend behavior).
- Any “silent edit after completion” outside of the reopen flow.
- Any time-entry CRUD (people domain).

---

## 3. Actors & Stakeholders

### Actors
- **Back Office Manager** (primary): initiates reopen.
- **Service Advisor** (secondary): may later edit fields unlocked by policy (not implemented here; see Data Requirements).
- **Unauthorized User**: must be blocked.

### Stakeholders
- **Billing/Invoicing**: must not allow invoicing until re-completion and re-snapshot (enforced server-side; UI reflects via flags).
- **Accounting / Event consumers**: depend on a single reopen signal and snapshot invalidation semantics (eventing is backend-owned; UI must not assume event transport).

## 4. Preconditions & Dependencies

### Preconditions
- Work order exists and is viewable in POS frontend.
- Work order is in `COMPLETED` status (workexec status taxonomy; DECISION-INVENTORY-004).
- User has capability/permission to reopen completed work orders (see Dependencies; DECISION-INVENTORY-013).
- Work order is not already invoiced/issued/finalized (backend blocks otherwise; UI reflects if field is available).

### Dependencies
- **Canonical screen**: Work order detail/edit is implemented under `durion-workexec` screens; extend existing screen rather than creating a new route (DECISION-INVENTORY-002).
- Backend must expose:
  1. **Work order detail** including:
     - `statusId`
     - `isReopened` (or equivalent)
     - an invoice gating indicator (see Data Requirements)
     - optional: `isStarted` (not required for this story; referenced for consistency)
  2. **Reopen mutation** endpoint/service that:
     - requires a non-empty reason
     - enforces permission
     - enforces “not invoiced” rule
     - is idempotency-safe (DECISION-INVENTORY-012)
     - returns standard error envelope (DECISION-INVENTORY-011)
  3. Optional read endpoints for audit/transition history (if already available in workexec; see Service Contracts).

## 5. UX Summary (Moqui-Oriented)

### Entry points
- **Primary**: `durion-workexec` Work Order detail/edit screen (canonical: `WorkOrderEdit.xml`; DECISION-INVENTORY-002).
- **Secondary (optional)**: Work order board/list row action only if the list payload includes `statusId` and `canReopenCompleted` (or equivalent). If not present, do not add row action in this story.

### Screens to create/modify
- **Modify**: `durion-workexec/screen/WorkOrderEdit.xml` (or the existing work order detail/edit screen used in this repo)
  - Add an action: `Reopen Completed Work Order`
  - Add a modal/dialog to collect `reopenReason`
  - Add a read-only banner/indicator when `isReopened=true` explaining invoice gating
  - Add a read-only “History” region if transition history is already available; otherwise show only created/updated metadata (DECISION-INVENTORY-014)

### Navigation context
- User is viewing a specific work order (`workOrderId` as an opaque string; DECISION-INVENTORY-003).
- After successful reopen, user remains on the same screen; data refresh occurs.

### User workflows (happy + alternate paths)

#### Happy path
1. Manager opens a completed work order (`statusId=COMPLETED`, `isReopened=false`).
2. Clicks **Reopen Completed Work Order**.
3. Enters a reason and confirms.
4. UI submits reopen with `Idempotency-Key`.
5. UI refreshes work order detail and shows:
   - `isReopened=true`
   - invoice gating indicator shows “not invoiceable”
   - confirmation message
   - (if available) latest transition/audit entry for reopen.

#### Alternate paths
- **No permission**: action hidden/disabled; if attempted, backend 403 → show access denied.
- **Not completed**: action hidden/disabled; if attempted, backend returns 409/400 → show “cannot reopen in current state”.
- **Already invoiced**: backend returns 409 with code indicating invoiced; UI shows “Cannot reopen a work order that has been invoiced.”
- **Already reopened / duplicate submit**: backend returns 200 with current state or 409 with duplicate code; UI treats as success-equivalent and refreshes.

## 6. Functional Behavior

### Triggers
- User clicks `Reopen Completed Work Order` on the work order screen.

### UI actions
- Open modal dialog with:
  - `reopenReason` (textarea, required)
  - `Confirm` and `Cancel`
- On Confirm:
  - Validate reason client-side (non-empty after trim)
  - Generate an `Idempotency-Key` UUID for this attempt and store it for retry of the same attempt (DECISION-INVENTORY-012)
  - Submit reopen request
  - Disable inputs while in-flight
- On success or duplicate/idempotent success:
  - Close dialog
  - Refresh work order detail (and history region if present)
  - Show a single success toast/banner

### State changes (frontend-visible)
**Decision rationale (DECISION-INVENTORY-004 + story intent):** Workexec status is authoritative; this story implements a controlled “reopen” flag and invoice gating without inventing a new status.

- Work order `statusId` remains `COMPLETED` (no status transition implied by UI).
- `isReopened` becomes `true`.
- Invoice eligibility is revoked (via a backend-provided indicator; see Data Requirements).
- UI must treat reopened-completed work orders as **not invoiceable**.

### Service interactions
- Submit reopen mutation (see Service Contracts).
- Reload work order detail after mutation.
- Optionally reload transition history if endpoint exists.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `reopenReason`:
  - required
  - trimmed, must not be empty
  - UI enforces max length only if backend contract provides a limit; otherwise do not guess (SAFE_DEFAULTS_MODE denylist: policy/constraints)

### Enable/disable rules
- `Reopen Completed Work Order` action is **visible and enabled** only if:
  - `statusId == COMPLETED`
  - `isReopened == false`
  - user capability indicates permission to reopen (DECISION-INVENTORY-013)
  - and (if available) invoice gating indicator says “not invoiced/eligible to reopen”
- If invoice gating indicator is available and indicates invoiced:
  - action is disabled with explanatory text
- Confirm button:
  - disabled until reason valid and no request in-flight

### Visibility rules
- If `isReopened == true`:
  - show a prominent read-only banner: “This work order was reopened. Invoice eligibility is revoked until re-completion.”
  - hide or disable the reopen action with “Already reopened” message
- Audit display:
  - Minimum: show `lastUpdated`/`updatedBy` metadata if available (DECISION-INVENTORY-014)
  - If transition history endpoint exists, show latest reopen entry.

### Error messaging expectations (standard envelope; DECISION-INVENTORY-011)
- 400 with field error on `reopenReason`: show inline error from `fieldErrors[]`
- 403: “Access denied: you are not authorized to reopen completed work orders.”
- 404: “Work order not found.”
- 409:
  - invalid state: “This work order cannot be reopened in its current state.”
  - invoiced: “Cannot reopen a work order that has been invoiced.”
  - duplicate/idempotent: treat as success-equivalent; refresh and show reopened state
- 5xx/network: “Reopen failed due to a system error. No changes were applied.” with retry option

## 8. Data Requirements

### Entities involved (frontend perspective)
- `durion.workexec.DurWorkOrder` (workexec SoR)
- Optional read models:
  - `WorkOrderStateTransition` (transition history; from workexec state machine implementation)
  - `WorkOrderSnapshot` (snapshot history; if exposed)
- Audit metadata fields (created/updated) as available in Moqui entities (DECISION-INVENTORY-014)

### Fields (types, required, defaults)

#### Work order (read)
- `workOrderId` (type: id/opaque string; required; DECISION-INVENTORY-003)
- `statusId` (type: string enum; required; must include `COMPLETED`)
- `isReopened` (type: boolean; required once feature exists; default false)
- **Invoice gating indicator** (required for best UX; one of the following must be provided by backend; do not invent client-side):
  - Option A: `invoiceStatus` (enum: e.g., `NONE|DRAFT|ISSUED|FINALIZED`)
  - Option B: `isInvoiced` (boolean)
  - Option C: `isInvoiceEligible` / `invoiceReady` (boolean)
- Optional (for banner/details):
  - `reopenedAt` (datetime)
  - `reopenedByUserId` (id)
  - `reopenReason` (string) — only if backend returns it; UI must not assume it is returned for privacy/audit reasons

#### Reopen request (write)
- `reopenReason` (string; required)
- `Idempotency-Key` header (required; UUID string; DECISION-INVENTORY-012)
- `workOrderId` in path (preferred) or body (if Moqui service requires)

**Decision rationale (DECISION-INVENTORY-013):** UI should not send `userId` if auth context exists; backend should derive actor from session. If backend requires `userId` today, it must be sourced from authenticated session context, not user-entered.

#### Transition history (optional read)
- `fromStatusId` (string)
- `toStatusId` (string)
- `transitionedAt` (datetime, UTC stored; displayed in user timezone; DECISION-INVENTORY-016)
- `transitionedByUserId` (id)
- `reason` (string; may include reopen reason or a summarized reason)

### Read-only vs editable by state/role
- This story does **not** implement post-reopen field editability.
- Until an explicit “editable fields” policy is provided by backend, the UI must keep all work order fields read-only when `statusId=COMPLETED`, regardless of `isReopened`, except for the reopen action itself.

### Derived/calculated fields (frontend)
- `canReopenCompleted` (boolean): derived from `statusId`, `isReopened`, and capability flag; invoice gating indicator if available.
- `reopenDisabledReason` (string): derived for tooltip/help text.

## 9. Service Contracts (Frontend Perspective)

> Moqui frontend may call REST endpoints and/or invoke Moqui services via transitions. Exact paths may vary by repo; this story defines required behavior and envelope.

### Load/view calls
- Load work order detail:
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}`
  - Response must include `statusId`, `isReopened`, and invoice gating indicator (see Data Requirements).
- Optional history:
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}/transitions` (if implemented by backend state machine)
  - `GET /rest/api/v1/workexec/workorders/{workOrderId}/snapshots` (optional)

### Submit/transition calls
- Reopen completed work order:
  - `POST /rest/api/v1/workexec/workorders/{workOrderId}/reopen`
  - Headers:
    - `Idempotency-Key: <uuid>` (required; DECISION-INVENTORY-012)
  - Body:
    ```json
    { "reopenReason": "string" }
    ```
  - Success:
    - `200 OK` with updated work order OR acknowledgement; UI must refresh via GET regardless.

### Error handling expectations (standard envelope; DECISION-INVENTORY-011)
All non-2xx responses return:
```json
{
  "code": "string",
  "message": "string",
  "correlationId": "string",
  "fieldErrors": [{"field":"string","message":"string"}],
  "existingResourceId": "string"
}
```

- Duplicate/idempotent outcomes:
  - Either `200 OK` returning current state
  - Or `409 Conflict` with `code` indicating duplicate and optional `existingResourceId`
  - UI behavior: treat as success-equivalent and refresh

## 10. State Model & Transitions

### Allowed states (WorkOrderStatus)
- `DRAFT`
- `APPROVED`
- `ASSIGNED`
- `WORK_IN_PROGRESS`
- `AWAITING_PARTS`
- `AWAITING_APPROVAL`
- `READY_FOR_PICKUP`
- `COMPLETED`
- `CANCELLED`

### Reopen semantics (workexec-owned)
**Decision rationale:** Workexec owns execution lifecycle; this story adds a controlled exception flag without redefining the lifecycle taxonomy.

- Reopen is allowed only when `statusId == COMPLETED` and invoice gating allows.
- Reopen does **not** change `statusId` away from `COMPLETED`.
- Reopen sets `isReopened = true`.
- Re-completion later (out of scope) is expected to clear `isReopened` and restore invoice eligibility after new completion/snapshot.

### Role-based transitions
- Reopen requires capability/permission (name must match backend; see Open Questions resolved below by adopting capability signaling pattern):
  - Capability flag: `canReopenCompletedWorkOrder` (preferred UI-facing capability)
  - Backend permission enforcement remains authoritative (403) (DECISION-INVENTORY-013)

### UI behavior per state
- `statusId != COMPLETED`: no reopen action.
- `statusId == COMPLETED && isReopened == false`: show reopen action if permitted.
- `statusId == COMPLETED && isReopened == true`: hide/disable reopen action; show reopened banner; show invoice gating indicator as “not invoiceable”.

## 11. Alternate / Error Flows

### Validation failures
- Missing/blank reason:
  - client-side blocks submit
  - if server returns 400 with field error, show inline message and keep dialog open

### Concurrency conflicts
- If another user reopens first:
  - backend returns 409 invalid state or returns `isReopened=true`
  - UI refreshes and shows reopened banner
  - If history endpoint exists, show who/when

### Unauthorized access
- If UI is stale and shows action but backend denies:
  - show 403 message
  - refresh capabilities and work order detail
  - keep work order unchanged

### Empty states
- If transitions/snapshots endpoints are not available or return empty:
  - show “No history available” message (read-only informational)

## 12. Acceptance Criteria

### Scenario 1: Authorized user successfully reopens a completed, not-invoiced work order
**Given** I am logged in as a Back Office Manager with capability `canReopenCompletedWorkOrder=true`  
**And** a work order exists with `statusId = COMPLETED` and `isReopened = false`  
**And** the work order is not invoiced (invoice gating indicator does not indicate `ISSUED`/`FINALIZED`)  
**When** I click “Reopen Completed Work Order”  
**And** I enter reopen reason “Corrected labor hours”  
**And** I confirm the reopen action  
**Then** the UI sends `POST /rest/api/v1/workexec/workorders/{workOrderId}/reopen` with body including `reopenReason`  
**And** the UI includes an `Idempotency-Key` header  
**And** the UI shows a single success confirmation  
**And** the work order detail refresh shows `isReopened = true`  
**And** the UI indicates invoice eligibility is revoked until re-completion.

### Scenario 2: Reopen requires a reason (client-side validation)
**Given** I am an authorized Back Office Manager viewing a completed work order eligible for reopen  
**When** I open the “Reopen Completed Work Order” dialog  
**And** I leave the reason blank (or only whitespace)  
**Then** the Confirm button is disabled  
**And** an inline validation message is shown indicating the reason is required  
**And** no reopen API request is sent.

### Scenario 3: Unauthorized user cannot reopen
**Given** I am logged in as a user with `canReopenCompletedWorkOrder=false`  
**And** I am viewing a work order with `statusId = COMPLETED`  
**Then** the “Reopen Completed Work Order” action is not shown (or is disabled with an access message)  
**When** I attempt to reopen and the backend responds `403` with the standard error envelope  
**Then** the UI displays “Access denied: you are not authorized to reopen completed work orders.”  
**And** the work order remains unchanged after refresh.

### Scenario 4: Cannot reopen if invoice is issued/finalized
**Given** I am an authorized Back Office Manager  
**And** I am viewing a work order with `statusId = COMPLETED`  
**And** the backend determines the work order is invoiced/issued/finalized  
**When** I attempt to reopen with a valid reason  
**Then** the backend responds `409` with a domain error code indicating invoiced work orders cannot be reopened  
**And** the UI displays “Cannot reopen a work order that has been invoiced.”  
**And** the work order remains unchanged after refresh.

### Scenario 5: Idempotency/double-submit does not create duplicate effects
**Given** I am an authorized Back Office Manager viewing an eligible completed work order  
**When** I click Confirm twice quickly with the same reason  
**Then** the UI prevents a second in-flight submission  
**And** if a retry occurs with the same `Idempotency-Key` and the backend returns either `200` or `409` with a duplicate code  
**Then** the UI treats the outcome as success-equivalent, refreshes the work order, and shows `isReopened=true`  
**And** the UI shows only one success confirmation for the attempt.
