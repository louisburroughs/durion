## Issue Body

## 1. Story Header

**Title:** Promotions: Apply Promotion Code During Estimate Pricing (Frontend / Moqui)

**Primary Persona:** Service Advisor

**Business Value:** Enables Service Advisors to apply a promotion code to an estimate and immediately see the resulting discount and updated totals, ensuring accurate customer-facing pricing before estimate approval and preserving traceability of the applied offer.

---

## 2. Story Intent

### As a / I want / So that
- **As a** Service Advisor  
- **I want** to apply a promotion code to an existing estimate and see the resulting discount reflected in the estimate totals  
- **So that** customers receive correct pricing before approving the work and the applied offer is recorded for audit/traceability.

### In-scope
- UI entry to input a promotion code for a specific estimate.
- Client-side validation:
  - trim whitespace
  - required/non-empty
  - length and charset constraints per Pricing decision (DECISION-PRICING-007)
- Call Pricing API to apply a promotion code to an estimate.
- Display applied promotion and the resulting pricing adjustment line(s) and updated totals using backend-authoritative money values (DECISION-PRICING-001).
- Display stable error codes returned by backend with user-friendly messages.
- Idempotent re-apply behavior handling in UI (same code → no duplicate discount lines).
- Replace-by-default behavior when applying a new promotion code (still exactly one active promotion per estimate) (DECISION-PRICING-008).
- Optional remove/clear action **only if** backend provides an explicit endpoint; otherwise UI does not offer remove.

### Out-of-scope
- Creating/editing promotions, eligibility rules, or pricing formulas (Pricing/CRM domain back-office).
- Defining discount stacking/precedence beyond “single promotion per estimate” (already defined).
- Manual price override workflows and approvals.
- Offline support.

---

## 3. Actors & Stakeholders

- **Service Advisor (Primary):** Applies promotion codes while preparing an estimate.
- **Customer (Beneficiary):** Receives accurate discounted pricing.
- **Pricing Service (System of Record for promotions application outcome):** Validates/applies promotion, computes discount adjustment and totals (authoritative on math and eligibility).
- **Work Execution / Estimate Owner (System of Record for estimate lifecycle):** Persists estimate state and references to applied promotion and pricing adjustments.

## 4. Preconditions & Dependencies

### Preconditions
- User is authenticated.
- User has permission to modify the target estimate (Workexec-owned authorization).
- Estimate is editable for promotions based on a backend-provided capability flag on the estimate payload (e.g., `canApplyPromotions=true`) (DECISION-PRICING-008).
- Estimate has at least one priceable line item (backend may also enforce).

### Dependencies
- Estimate Detail screen exists and can be extended with a Promotion section.
- Backend endpoints exist:
  - Load estimate with pricing totals/adjustments and promotion capability flag.
  - Apply a promotion code to an estimate under Pricing base path `/pricing/v1/...` (DECISION-PRICING-002).
- Backend returns updated totals/adjustments (either full estimate pricing subtree or full estimate) so UI does not recompute totals (DECISION-PRICING-001).
- Backend returns stable error codes for invalid/ineligible/forbidden/conflict cases.

## 7. Business Rules (Translated to UI Behavior)

### Validation
Promotion code (DECISION-PRICING-007):
- Trim leading/trailing whitespace before validation and submit.
- Required (non-empty after trim).
- Length: 1–32 characters.
- Charset: `[A-Z0-9_-]` with case-insensitive lookup; UI should:
  - accept lowercase input but normalize to uppercase for display and submit (safe because lookup is case-insensitive)
  - reject characters outside allowed set with inline validation message.

Promotion eligibility:
- UI does not attempt to evaluate eligibility; backend is authoritative (DECISION-PRICING-009).
- Backend response determines success/failure and provides reason codes/messages.

Estimate eligibility to apply promotions:
- UI must not hardcode estimate status enums.
- UI uses `canApplyPromotions` boolean (or equivalent capability flag) from estimate payload (DECISION-PRICING-008).
- If capability flag is absent, UI may fall back to enabling apply only when estimate is in an “editable” mode already supported by the estimate screen (e.g., same gating as line edits). This fallback must be implemented defensively and still handle backend 403/400 responses.

### Enable/disable rules
Disable Apply when:
- code invalid per client-side validation
- request in-flight
- `canApplyPromotions=false` (or user lacks edit permission)

### Visibility rules
- Show “Applied Promotion” summary only if backend indicates a promotion is applied (via explicit applied promotion field or presence of a promotion adjustment line).
- Always show input section; when a promotion is already applied:
  - keep input enabled (if `canApplyPromotions=true`) to allow replace-by-default behavior (DECISION-PRICING-008)
  - show helper text: “Applying a new code will replace the current promotion.”

### Error messaging expectations
Use backend `errorCode` as primary mapping key; show user-friendly message and include error code in a “Details” expandable area for support.

Minimum mapping (align to Pricing decisions; do not invent new policy):
- `PROMO_NOT_FOUND` → “Promotion code not found or expired.”
- `PROMO_NOT_APPLICABLE` → “This promotion doesn’t apply to the current estimate.”
- `FORBIDDEN` / `UNAUTHORIZED` → “You don’t have permission to apply promotions to this estimate.”
- `CONFLICT` (estimate version changed) → “This estimate changed since you opened it. Reload and try again.”
- `SERVICE_UNAVAILABLE` → “Promotion service is temporarily unavailable. Please try again.”
- Unknown → “Unable to apply promotion. Please try again or contact support.”

**Decision rationale (applied):**
- Single promotion per estimate with replace-by-default is mandated (DECISION-PRICING-008) to avoid stacking ambiguity.
- Client-side code constraints are mandated (DECISION-PRICING-007) to reduce avoidable round-trips and enforce deterministic code format.
- Capability-flag gating avoids coupling UI to Workexec status strings (DECISION-PRICING-008).

## 9. Service Contracts (Frontend Perspective)

### Load/view calls
Workexec-owned estimate load (exact path may vary in Moqui; must return required fields):
- `GET /workexec/v1/estimates/{estimateId}` (example) returning:
  - `estimateId`
  - `canApplyPromotions` (preferred)
  - pricing totals/adjustments subtree including applied promotion (if any)

### Create/update calls (apply promotion)
Pricing-owned apply endpoint (DECISION-PRICING-002, DECISION-PRICING-008):
- `POST /pricing/v1/estimates/{estimateId}/promotion:apply`
  - Request body:
    - `promotionCode`: string (trimmed; UI-normalized uppercase)
    - Optional concurrency token if Workexec requires it (e.g., `estimateVersion`); if required, backend returns 409 on mismatch.
  - Success response (preferred):
    - Updated estimate pricing subtree sufficient to re-render totals/adjustments and applied promotion without a follow-up fetch.
  - Failure response:
    - `{ errorCode, message, fieldErrors? }` for 400
    - `{ errorCode: "CONFLICT", message }` for 409
    - `{ errorCode: "FORBIDDEN" }` for 403
    - `{ errorCode: "SERVICE_UNAVAILABLE" }` for 503

### Submit/transition calls
- None beyond apply action.

### Error handling expectations
- 400: validation/business errors (invalid code format if not caught client-side, not found, not applicable).
- 403: permission denied.
- 409: concurrency conflict (estimate changed).
- 503/5xx: retryable service errors.

UI behavior:
- Never apply optimistic totals; only update from success payload.
- On 409, show reload prompt and provide a “Reload estimate” action that re-fetches estimate.
- On 403, do not leak whether a code exists or is eligible.

**Decision rationale (applied):**
- Pricing endpoints must be under `/pricing/v1` (DECISION-PRICING-002).
- UI must not recompute money; must render backend money objects (DECISION-PRICING-001).
- Replace-by-default semantics means apply endpoint is idempotent and results in exactly one applied promotion (DECISION-PRICING-008).

**When** I apply a promotion code  
**And** the backend responds with HTTP 409 and `errorCode="CONFLICT"`

**When** I apply a promotion code and the backend responds with HTTP 503 and `errorCode="SERVICE_UNAVAILABLE"`

**And** the estimate remains unchanged
