## 2. Story Intent

### As a / I want / So that
- **As a** Pricing Analyst / Account Manager  
- **I want** to configure eligibility rules for a promotion based on account and vehicle attributes (including optional fleet-size threshold) and test the outcome  
- **So that** the pricing backend can deterministically allow/deny promotion application with an explanation (reason code), and the UI can present that outcome safely.

### In-scope
- Promotion eligibility rule configuration UI (list/create/edit/delete) attached to a specific promotion.
- Eligibility rule “test/evaluate” UI that calls a backend evaluation service and displays decision + reason.
- Moqui screen/form/transition wiring and defensive error handling.
- Client-side validation limited to **shape/requiredness**; backend remains authoritative for eligibility semantics.

### Out-of-scope
- Creating/editing promotions themselves (assumed already exists and navigable).
- Implementing pricing calculation, applying discounts, tax/total math (backend-owned).
- Defining vehicle tags taxonomy and account fleet size computation (CRM/Inventory SoR).
- Promotion stacking (explicitly out of scope; **single promotion per estimate** is handled elsewhere).
- Any estimate/work order lifecycle changes (Workexec-owned).

## 7. Business Rules (Translated to UI Behavior)

### Eligibility combination logic (resolved)
- Multiple eligibility rules for a promotion are evaluated with **AND semantics**.
- A promotion with **zero eligibility rules is eligible** for all contexts.
- **Rationale:** Deterministic and conservative when rules exist; “no rules” represents an unrestricted promotion (DECISION-PRICING-009).

### Validation (client-side: shape only; backend authoritative)
- Required: `promotionId`, `conditionType`, `operator`, `value`.
- `value` validation by condition type (UI shape validation; backend enforces semantics):
  - `ACCOUNT_ID_LIST`: accept comma-separated tokens; trim whitespace; reject empty after trimming.
  - `VEHICLE_TAG`: non-empty token string; trim whitespace; reject empty.
  - `ACCOUNT_FLEET_SIZE`: numeric string representing a whole number (integer). Reject non-numeric.
- Operator compatibility:
  - UI must only offer operators allowed for the selected `conditionType` (see Data Requirements → operator matrix).
  - Backend remains authoritative; if backend rejects, show returned field errors.

### Enable/disable rules
- Disable Save while in-flight.
- Disable Save if required fields missing or value fails basic shape validation.
- Disable Delete/Edit actions if user lacks manage permission.
- Disable Test while evaluation call in-flight.

### Visibility rules
- Test panel always available.
- Test inputs are **optional** unless the user wants to simulate a context:
  - UI should show helper text: “Provide accountId/vehicleId to test context-specific eligibility.”
  - UI must not attempt to infer required context from rules (rules may evolve; backend is authoritative).
- If evaluation returns a reason indicating missing context, show it as returned.

### Error messaging expectations
- Backend validation errors (HTTP 400) mapped to fields when `fieldErrors` present.
- Conflicts (HTTP 409) shown as non-field error with recommended action “Reload and retry”.
- 401/403 show access denied; do not display any returned sensitive payload.
- 404 promotion/rule not found: show not found and offer navigation back to Promotions list.

### Fields (type, required, defaults)

- `promotionId` (string/UUID, required; read-only in UI once scoped)
- `conditionType` (enum, required)
  - Supported in this story: `ACCOUNT_ID_LIST`, `VEHICLE_TAG`, `ACCOUNT_FLEET_SIZE`
- `operator` (enum, required) — **UI must constrain to allowed operators per conditionType**
- `value` (string, required) — stored as backend-defined string; UI edits as string

**Operator matrix (UI-offered options)**
- For `ACCOUNT_ID_LIST`:
  - `IN_LIST` (eligible if accountId is in the configured list)
  - `NOT_IN_LIST` (eligible if accountId is not in the configured list)
- For `VEHICLE_TAG`:
  - `HAS_TAG` (eligible if vehicle has the tag)
  - `NOT_HAS_TAG` (eligible if vehicle does not have the tag)
- For `ACCOUNT_FLEET_SIZE`:
  - `GTE` (eligible if fleet size >= value)
  - `LTE` (eligible if fleet size <= value)

**Rationale:** Provide a minimal, deterministic operator set aligned to the story’s stated needs (account allow/deny list, simple tag inclusion/exclusion, optional fleet-size threshold). Backend remains authoritative; UI must handle backend rejection gracefully.

**PromotionEligibilityEvaluationResult**
- `isEligible` (boolean, required)
- `reasonCode` (string, required)
- Optional fields (render if present, do not require):
  - `message` (string)
  - `failedRuleIds` (array of ruleId)
  - `details` (object)

## 9. Service Contracts (Frontend Perspective)

> All Pricing endpoints must be under `/pricing/v1/...` (DECISION-PRICING-002). If actual backend paths differ, update this story and the client adapter; do not hardcode alternate paths in screens.

### Load/view calls
1) **List rules for a promotion**
- `GET /pricing/v1/promotions/{promotionId}/eligibility-rules`
- Response: `{ items: PromotionEligibilityRule[] }` (or array directly; UI must support either via adapter)
- Errors:
  - 401/403: show access denied
  - 404: promotion not found

### Create/update calls
2) **Create rule**
- `POST /pricing/v1/promotions/{promotionId}/eligibility-rules`
- Body: `{ conditionType, operator, value }`
- Response: created `PromotionEligibilityRule`
- Errors:
  - 400: `{ errorCode: "VALIDATION_ERROR", fieldErrors?: { [field]: message }, message }`

3) **Update rule**
- `PUT /pricing/v1/promotions/{promotionId}/eligibility-rules/{ruleId}`
- Body: `{ conditionType, operator, value }` (or partial if PATCH; UI uses full payload to be safe)
- Response: updated `PromotionEligibilityRule`
- Errors:
  - 400 validation
  - 404 not found
  - 409 conflict (if versioning is implemented)

### Delete calls
4) **Delete rule**
- `DELETE /pricing/v1/promotions/{promotionId}/eligibility-rules/{ruleId}`
- Response: 204 No Content (preferred) or `{ success: true }`
- Errors:
  - 404 not found (treat as already deleted; refresh list)

### Submit/transition calls
- None (no lifecycle transitions for rules in this story).

### Evaluate/test calls
5) **Evaluate eligibility**
- `POST /pricing/v1/promotions/{promotionId}/eligibility:evaluate`
- Body: `{ accountId?: string, vehicleId?: string }`
- Response: `{ isEligible: boolean, reasonCode: string, message?: string, failedRuleIds?: string[] }`
- Errors:
  - 400 validation (e.g., malformed IDs)
  - 401/403 unauthorized/forbidden

### Error handling expectations
- UI must not infer eligibility on network failure; it must show “Evaluation unavailable” and no decision.
- UI must display backend `reasonCode` verbatim; optional mapping to friendly text is allowed only if a backend-provided catalog exists (not assumed here).
