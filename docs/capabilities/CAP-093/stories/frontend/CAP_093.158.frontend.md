## 1. Story Header

**Title:** [FRONTEND] [STORY] Promotions: View Promotion Redemption Records (Read-only CRM)

**Primary Persona:** Customer Service Representative (CSR) / Marketing Manager (read-only)

**Persona Metadata**

**Business Value:** Provide UI visibility into promotion redemption activity recorded by CRM so staff can support customers, audit usage, and detect potential abuse without querying databases or logs.

---

## 2. Story Intent

### As a / I want / So that
- **As a** CSR or Marketing Manager  
- **I want** to search and view CRM promotion redemption records (list + detail) filtered by promotion/customer/work order/invoice/date range  
- **So that** I can confirm whether a promotion was redeemed, by whom, and on which invoice/work order, and spot duplicates/abuse patterns.

### In-scope
- Moqui UI screens to **search/list** promotion redemptions with server-side pagination and sorting.
- A **detail view** of a single redemption record.
- Filters for common identifiers: `promotionId`, `partyId`, `workOrderId`, `invoiceId`, date range.
- Read-only display of redemption fields and optional traceability fields (e.g., `eventId`) if provided by backend.
- Authorization gating (UI entry-point gating + deterministic handling of 401/403 from backend).

### Out-of-scope
- Consuming or emitting events (e.g., `PromotionRedeemed`) and idempotency enforcement (backend responsibility).
- Editing, deleting, or redacting redemption records (read-only UI).
- Enforcing promotion usage limits or computing counters in the UI (DECISION-INVENTORY-010: UI must not infer limits/policy).
- Creating promotions or configuring limits.

- **Workexec/Billing (external stakeholders):** Provide referenced identifiers (work order/invoice) for cross-system support; not owned by this UI story.

## 6. Functional Behavior

### Triggers
- Enter list screen:
  - If query params include any filter values, auto-run search.
  - Otherwise, show idle state (no automatic unfiltered search) to avoid broad data exposure/perf risk.
- Submit search: call list service with filters + pagination + sort.
- Change page/sort: re-call list service with same filters.
- Enter detail screen: call detail service by `promotionRedemptionId`.

### UI actions
- Search form submit.
- Clear filters (resets form + clears results to idle state).
- Click row → open detail.
- Copy-to-clipboard for IDs (only if existing component pattern supports it; otherwise omit).

### State changes
- Frontend view state only: `idle`, `loading`, `loaded`, `empty`, `error`.
- No domain state mutations.

### Service interactions
- List: dedicated read service returning paginated DTO list (DECISION-INVENTORY-010).
- Detail: dedicated read service returning a single DTO by `promotionRedemptionId`.

## 7. Business Rules (Translated to UI Behavior)

### Validation
- Canonical customer identifier is `partyId` (DECISION-INVENTORY-001). UI must not use `customerId` as a primary filter key.
- Filter field validation (client-side):
  - `promotionId`, `partyId`, `workOrderId`, `invoiceId`, `promotionRedemptionId`: if provided, must be a UUID string format (trim whitespace). If backend allows non-UUID display numbers, those must be separate fields returned by backend and displayed read-only; filters remain UUID-based (DECISION-INVENTORY-010).
  - Date range: `from <= to` (inclusive). If invalid, block request and show inline error.
- UI must not infer “limit reached”, “duplicate”, or “abuse” flags unless backend provides explicit fields (DECISION-INVENTORY-010).

### Enable/disable rules
- Search button disabled while request in-flight.
- Clear filters enabled when any filter has a value.
- Pagination/sort controls disabled while request in-flight.

### Visibility rules
- List columns:
  - Always show: `promotionRedemptionId`, `promotionId`, `partyId` (if present), `workOrderId` (if present), `invoiceId` (if present), `redeemedAt` or `createdAt` (whichever backend provides).
  - Optional: `workOrderNumber`, `invoiceNumber`, `eventId` if present (display-only).
- Detail fields:
  - Render all known fields returned by DTO; unknown fields are not rendered.
  - Do not render any backend string as HTML (DECISION-INVENTORY-006 general rule for sensitive strings; render as plain text).

### Error messaging expectations
- 400: show “Invalid filter” + backend message; if backend returns `fieldErrors`, map to inline field errors.
- 401: redirect to login (per app convention).
- 403: show “Access denied” and hide results.
- 404 (detail): show “Redemption not found.”
- 500/network: show generic error with retry.

## 9. Service Contracts (Frontend Perspective)

> Moqui screens must call **dedicated read services** returning safe DTOs (not direct entity-find) per CRM guidance (STORY_VALIDATION_CHECKLIST; DECISION-INVENTORY-010). Exact service names may differ; the contract below is the required behavior.

### Load/view calls

1. **List promotion redemptions**
   - **Moqui REST endpoint (preferred, per checklist examples):**  
     `GET /rest/api/v1/crm/promotions/redemptions`
   - **Query params (all optional unless noted):**
     - `promotionId` (UUID)

     - `workOrderId` (UUID)
     - `invoiceId` (UUID)
     - `from` (date or datetime ISO-8601; inclusive)
     - `to` (date or datetime ISO-8601; inclusive)
     - `pageIndex` (int, required; 0-based)
     - `pageSize` (int, required)
     - `sort` (string, optional; e.g., `-redeemedAt` or `-createdAt`)

     ```json

       "items": [ { "promotionRedemptionId": "uuid", "promotionId": "uuid" } ],
       "pageIndex": 0,
       "pageSize": 25,
     ```

   - **Notes:**

2. **Get promotion redemption detail**
   - **Moqui REST endpoint (preferred):**  
     `GET /rest/api/v1/crm/promotions/redemptions/{promotionRedemptionId}`
   - **Path params:**
     - `promotionRedemptionId` (UUID, required)
   - **Response:** PromotionRedemption DTO (single object)

## 10. State Model & Transitions

### Allowed states
- UI view states: `idle`, `loading`, `loaded`, `empty`, `error`.

### Role-based transitions
- Without `crm.promotions.redemptions.read`:
  - List and detail calls return 403; UI transitions to `error(forbidden)` and shows no data.

### UI behavior per state
- `idle`: show filters and guidance to search; no results table rendered or show “Run a search to see results”.
- `loading`: show loading indicator; disable search/pagination/sort.
- `loaded`: show results table and pagination controls.
- `empty`: show “No redemptions found” and keep filters visible.
- `error`:
  - forbidden: show access denied
  - other: show generic error + retry; preserve filters

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Invalid UUID in any ID filter:
  - Block request; show inline “Must be a valid UUID”.
- `from > to`:
  - Block request; show inline date range error.

### Backend validation failures (400)
- Backend rejects filter combination or invalid values:
  - Show banner with backend message.
  - If `fieldErrors` present, map to fields.

### Concurrency conflicts
- Not applicable for read-only. If detail record disappears between list and click:
  - Detail returns 404; show not-found state with link back to list.

### Unauthorized access
- 401: redirect to login.
- 403: show access denied; do not auto-retry.

### Empty states
- No matching redemptions: empty state, not an error.

## 12. Acceptance Criteria

### Scenario 1: View list of redemptions filtered by promotionId
**Given** I am authenticated and have permission `crm.promotions.redemptions.read`  
**When** I navigate to `/crm/promotions/redemptions`  
**And** I enter a valid UUID `promotionId` and submit search  
**Then** the UI calls `GET /rest/api/v1/crm/promotions/redemptions` with `promotionId`, `pageIndex`, and `pageSize`  
**And** I see a paginated list of results  
**And** each row shows `promotionRedemptionId` and `promotionId`  
**And** optional fields (`partyId`, `workOrderId`, `invoiceId`, timestamps) are shown only when present in the response

### Scenario 2: Deep-link pre-fills filters and auto-runs search
**Given** I am authenticated and have permission `crm.promotions.redemptions.read`  
**When** I navigate to `/crm/promotions/redemptions?workOrderId=<valid-uuid>&from=2026-01-01&to=2026-01-31`  
**Then** the UI pre-fills `workOrderId`, `from`, and `to`  
**And** the UI automatically runs the search once  
**And** the results reflect those filters

### Scenario 3: No results returns empty state
**Given** I am authenticated and have permission `crm.promotions.redemptions.read`  
**When** I search with filters that match no redemption records  
**Then** I see an empty-state message indicating no results  
**And** no error banner is shown  
**And** my filter values remain visible and editable

### Scenario 4: View redemption detail
**Given** I am authenticated and have permission `crm.promotions.redemptions.read`  
**And** the list returns at least one redemption record  
**When** I select a record with `promotionRedemptionId=<id>`  
**Then** I navigate to `/crm/promotions/redemptions/<id>`  
**And** the UI calls `GET /rest/api/v1/crm/promotions/redemptions/<id>`  
**And** I see read-only fields including `promotionRedemptionId` and `promotionId`  
**And** I see `partyId`, `workOrderId`, `invoiceId`, and timestamps only if present in the response

### Scenario 5: Unauthorized access is blocked (list)
**Given** I am authenticated but do not have permission `crm.promotions.redemptions.read`  
**When** I navigate to `/crm/promotions/redemptions`  
**Then** the backend returns 403  
**And** the UI displays an access denied message  
**And** no redemption data is displayed

### Scenario 6: Unauthorized access is blocked (detail)
**Given** I am authenticated but do not have permission `crm.promotions.redemptions.read`  
**When** I navigate directly to `/crm/promotions/redemptions/<promotionRedemptionId>`  
**Then** the backend returns 403  
**And** the UI displays an access denied message  
**And** no redemption data is displayed

### Scenario 7: Invalid date range prevented client-side
**Given** I am on the Promotion Redemptions list screen  
**When** I set `from` later than `to`  
**And** I attempt to submit search  
**Then** the UI blocks the request  
**And** I see an inline validation message indicating the date range is invalid

### Scenario 8: partyId is used as the canonical customer identifier
**Given** I am on the Promotion Redemptions list screen  
**When** I view the filter fields  
**Then** I see a filter labeled “Customer (partyId)” (or equivalent)  
**And** there is no filter that uses `customerId` as a primary identifier
