[FRONTEND] [STORY] Order: Cancel Order (Order-Orchestrated) with Work-Block + Void/Refund-Required Outcomes (Moqui UI)

### Primary Persona

### Business Value

## 2. Story Intent

### As a / I want / So that
- **As a** user with `ORDER_CANCEL` permission (e.g., Store Manager)  
- **I want** to cancel an order from the POS UI by selecting a required reason and optional comments  
- **So that** mistaken orders can be cancelled safely while preventing cancellation when work is already irreversibly started, and while clearly indicating whether a manual refund is required.

### In-scope
- UI entry point to initiate cancellation from Order Detail context (`orderId`)
- Cancellation dialog/form capturing:
  - `reason` (required; from backend-provided allowed list when available, with safe fallback list)
  - `comments` (optional; max 2000 chars)
- Moqui screen flow calling a single Order-owned cancel operation and presenting outcomes
- UI behavior for:
  - Idempotency (repeat cancel on already-cancelled returns success without side effects)
  - Concurrency (in-flight cancellation returns `409 Conflict`)
- Display of canonical cancellation-related order statuses:
  - `CANCELLING`, `CANCELLED`, `CANCELLED_REQUIRES_REFUND`, `CANCELLATION_FAILED`
- Display of backend-provided blocking reason when Work Execution status blocks cancellation
- Read-only display of cancellation/audit details returned by backend, including `cancellationId` for all authorized viewers and support-only operational identifiers when permitted

### Out-of-scope
- Implementing payment void/refund execution logic (backend-owned)
- Any UI to execute refunds (only messaging “refund required”)
- Retry cancellation action in standard Order Detail UI (admin-only, separate story)
- Editing/undoing a cancellation
- Accounting/GL impacts and refund processing workflow beyond “requires manual refund” messaging
- Building an operations dashboard for resolving `CANCELLATION_FAILED`

## 3. Actors & Stakeholders
- **Store Manager**: initiates cancellations; must have `ORDER_CANCEL`
- **Service Advisor**: may initiate cancellation if granted `ORDER_CANCEL` (permission-based, not role-name-based)

- **Order domain backend (SoR)**: validates cancellability, orchestrates downstream coordination, sets final order status, returns canonical status + audit metadata
- **Work Execution system (dependency)**: authoritative on work status; used by Order backend to block cancellation in irreversible states
- **Payment system (dependency)**: authoritative on settlement/void; used by Order backend to determine `VOIDED` vs `REFUND_REQUIRED` outcomes
- **Operations/Support**: needs clear status/audit and support identifiers (permission-gated) for troubleshooting

## 5. UX Summary (Moqui-Oriented)

### Entry points
- From Order Detail screen: primary action **Cancel Order**.
  - Visible/enabled only when backend indicates cancellability (e.g., `canCancel=true`) and user has permission.

### Screens to create/modify
- **Modify**: Order Detail screen (existing; exact screen name/route TBD by repo conventions)
  - Add Cancel Order action
  - Add “Cancellation” read-only section/panel that renders when cancellation-related status or cancellation summary exists
- **Create/Modify**: Cancel Order dialog as a subscreen/dialog pattern consistent with repo (embedded dialog, subscreen, or modal)
- **Optional (defer unless already supported by backend)**: Cancellation history subscreen/table if backend returns multiple immutable `CancellationRecord` entries

### Navigation context
- Cancellation is initiated and resolved within the Order Detail context.
- After submission, user remains on Order Detail; UI refreshes order detail to reflect authoritative status.

### User workflows (happy + alternate paths)

**Happy path A: cancellable; payment voided or not applicable**
1. User clicks **Cancel Order**
2. Dialog opens; user selects `reason` and optionally enters `comments`
3. User submits; UI disables submit and shows in-flight indicator
4. Backend returns `200` with `status=CANCELLED`
5. UI closes dialog, refreshes order detail, and shows confirmation + cancellation metadata

**Happy path B: cancellable; payment settled → refund required**
1–3 same as above
4. Backend returns `200` with `status=CANCELLED_REQUIRES_REFUND` and `paymentVoidStatus=REFUND_REQUIRED`
5. UI closes dialog, refreshes order detail, shows warning “Manual refund required” and cancellation metadata

**Alternate: work blocks cancellation**
- Backend returns `400` with `errorCode=WORK_NOT_CANCELLABLE` and safe message/details
- UI keeps dialog open, shows non-field error message (and optionally displays work status from `details.workStatus`)

**Alternate: cancellation already in progress**
- Backend returns `409` with `errorCode=CANCELLATION_IN_PROGRESS` and optional `retryAfterSeconds`
- UI closes dialog (or keeps open; see §11) and refreshes order detail; shows “Cancellation in progress” message

**Alternate: already cancelled (idempotent)**
- Backend returns `200` with current cancelled status and latest cancellation metadata; no new attempt is created
- UI treats as success and refreshes order detail

**Alternate: orchestration failure**
- Backend returns non-2xx (typically `500`) with `errorCode=CANCELLATION_FAILED` (or similar) and safe message
- UI refreshes order detail; renders `CANCELLATION_FAILED` state with guidance “Manual intervention required”; no retry action

## 6. Functional Behavior

### Triggers
- User selects **Cancel Order** on Order Detail.

### UI actions
- Open cancel dialog containing:
  - `reason` select (required)
  - `comments` textarea (optional) with character counter and max length enforcement (2000)
  - Buttons: `Cancel` (dismiss), `Submit Cancellation`
- On submit:
  - Validate `reason` present
  - Validate `comments.length <= 2000`
  - Invoke Moqui transition that calls Order cancel service
  - Disable inputs and prevent duplicate submissions while request is in-flight
- On response:
  - **200**: close dialog; show banner based on returned `status`; refresh order detail
  - **400 with fieldErrors**: keep dialog open; show field-level errors
  - **400 without fieldErrors**: keep dialog open; show general error message
  - **403**: show authorization error; ensure cancel action is not shown on subsequent renders
  - **409**: show “in progress” message; refresh order detail (respect `retryAfterSeconds` if provided)
  - **500/other**: show generic failure banner; refresh order detail

### State changes (UI-level)
- UI does not mutate local “order status” as truth; it re-renders from refreshed order detail (or from response payload if it includes full order status).
- UI reflects canonical cancellation-related statuses:
  - `CANCELLING`, `CANCELLED`, `CANCELLED_REQUIRES_REFUND`, `CANCELLATION_FAILED`
- UI must render unknown status values safely (fallback label + no crash).

### Service interactions
- Load Order Detail (existing) on screen entry and after cancellation attempt
- Load allowed cancellation reasons (preferred) OR use fallback list (see §7 and §15)
- Submit cancel request via a single Order-owned cancel command service
- No direct UI calls to Payment or Work Execution domains

## 7. Business Rules (Translated to UI Behavior)

### Validation
- `reason` is required.
  - If missing: disable submit and show “Reason is required.”
- `comments` is optional; max length 2000 characters.
  - If exceeded: disable submit and show “Comments must be 2000 characters or fewer.”
- `orderId` must be present in screen parameters/context.
  - If missing: show fatal error state and do not render cancel action.

### Enable/disable rules
- Cancel action is shown/enabled only when:
  - Backend indicates capability (e.g., `canCancel=true` or capabilities include `ORDER_CANCEL`) **and**
  - User has `ORDER_CANCEL` permission (backend will enforce regardless)
- No retry action is shown for `CANCELLATION_FAILED` in standard UI.

### Visibility rules
- Cancellation section/panel is visible when either:
  - Order `status` is one of `CANCELLING|CANCELLED|CANCELLED_REQUIRES_REFUND|CANCELLATION_FAILED`, **or**
  - Order detail includes a `cancellationSummary`/latest cancellation record
- Refund-required messaging is shown only when `status=CANCELLED_REQUIRES_REFUND` (or when latest cancellation indicates `paymentVoidStatus=REFUND_REQUIRED` and status is consistent).

### Error messaging expectations (deterministic)
- Backend errors must include stable `errorCode` and user-safe `message` (optional `details`, optional `fieldErrors`).
- UI mapping:
  - `WORK_NOT_CANCELLABLE` (400): show message; optionally show `details.workStatus` if present
  - `COMMENTS_TOO_LONG` (400): show field error on comments
  - `FORBIDDEN` (403): show “You do not have permission to cancel orders.”
  - `CANCELLATION_IN_PROGRESS` (409): show “Cancellation is already in progress. Refreshing status…”
  - Any other/unknown: show generic “Cancellation could not be completed. Manual intervention may be required.” and prompt refresh
- UI must not display payment internals or correlation IDs unless explicitly provided and permitted (see §13).

**Decision rationale applied**
- Order domain is cancellation orchestrator and SoR for cancellation policy and resulting order status (DECISION-ORDER-001).
- Work irreversible states block cancellation; UI relies on backend to enforce and returns `WORK_NOT_CANCELLABLE` (DECISION-ORDER-002).
- Payment settlement handling: void if unsettled; if settled then `CANCELLED_REQUIRES_REFUND` with no refund UI flow (DECISION-ORDER-003).
- Comments max length 2000 enforced client + server (DECISION-ORDER-008).
- Idempotent cancellation for already-cancelled orders; 409 for in-progress (DECISION-ORDER-005, DECISION-ORDER-009).
- Permission required: `ORDER_CANCEL` (DECISION-ORDER-010).
- Capability exposure: backend provides `canCancel`/capabilities; UI gates on that (DECISION-ORDER-014).

**Canonical cancellation-related statuses (UI contract)**
- `CANCELLING`
- `CANCELLED`
- `CANCELLED_REQUIRES_REFUND`
- `CANCELLATION_FAILED`

**Other order statuses**

### Role-based transitions
- Initiate cancellation: requires `ORDER_CANCEL`
- View cancellation metadata: any user who can view the order; support identifiers only for support/admin permission (backend-enforced)

### UI behavior per state
- Pre-cancel (any status where `canCancel=true`): show Cancel action enabled
- `CANCELLING`: hide/disable Cancel action; show “Cancellation in progress” and refresh affordance
- `CANCELLED`: hide Cancel action; show cancelled banner + cancellation metadata
- `CANCELLED_REQUIRES_REFUND`: hide Cancel action; show warning banner “Manual refund required” + metadata
- `CANCELLATION_FAILED`: hide Cancel action; show error banner “Manual intervention required” + `cancellationId` and (if permitted) support identifiers; no retry action

## 11. Alternate / Error Flows

### Validation failures (client-side)
- Missing reason:
  - Submit disabled; show inline required error
- Comments too long:
  - Submit disabled; show inline max-length error and character counter

### Validation failures (server-side 400)
- If backend returns `fieldErrors`:
  - Keep dialog open; map to fields
- If backend returns `WORK_NOT_CANCELLABLE`:
  - Keep dialog open; show message; optionally show work status from `details.workStatus`

### Concurrency conflicts (409)
- If backend returns `CANCELLATION_IN_PROGRESS`:
  - Close dialog
  - Show non-destructive banner/toast
  - Refresh order detail after `retryAfterSeconds` if provided; otherwise refresh once immediately and provide a manual refresh action

### Unauthorized access (403)
- If user lacks permission:
  - Cancel action not rendered when `canCancel=false` or when session indicates missing permission
  - If user still triggers submit (e.g., stale UI): show authorization error banner; do not retry automatically

### Idempotent already-cancelled (200)
- If backend returns `200` with status already cancelled:
  - Treat as success; close dialog; refresh order detail; show “Order was previously cancelled” message if provided

### Orchestration failure (500)
- Show generic failure banner; refresh order detail to reflect `CANCELLATION_FAILED`
- Do not offer retry in standard UI

### Empty states
- If no cancellation summary/record exists:
  - Render “No cancellation activity recorded” in Cancellation section (or hide section entirely until a cancellation-related status occurs; see §15)
