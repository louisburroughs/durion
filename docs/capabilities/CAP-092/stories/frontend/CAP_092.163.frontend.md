## Issue Body

## Title
[FRONTEND] [STORY] CRM Snapshot Viewer: Fetch & Display CRM Snapshot (Account + Contacts + Vehicles + Preferences) via Moqui Proxy

## Primary Persona
Service Advisor / CSR (POS user) using the Durion frontend to view customer context quickly during estimate creation and refresh.

## Business Value
Provide a fast, consistent “single view” of customer/account, contacts, vehicles, and billing-relevant contactability/preferences to speed estimate creation and reduce errors from inconsistent customer context.

---

# 2. Story Intent

## As a / I want / So that
- **As a** Service Advisor / CSR  
- **I want** to retrieve and view a CRM-owned snapshot of account/person, contacts, vehicles, and billing-relevant preferences by **partyId and/or vehicleId**  
- **So that** estimate creation and customer context lookup are fast, consistent, and refreshable without navigating multiple screens.

## In-Scope
- A Moqui screen flow that:
  - Accepts `partyId` and/or `vehicleId` as inputs (canonical identifiers; `partyId` is canonical per DECISION-INVENTORY-001)
  - Calls the CRM Snapshot endpoint **server-side via Moqui proxy** (DECISION-INVENTORY-004)
  - Displays snapshot metadata (version/timestamp), account summary, contacts (including primary), vehicles, and preferences (v1 scope: contactability + billing-relevant preferences only; backend-owned)
  - Handles error cases (400/403/404/500) with clear user messaging
  - Supports “refresh snapshot” action
- Frontend service integration (Moqui service call / REST call) consistent with project conventions.

## Out-of-Scope
- Editing CRM data (contacts, vehicles, preferences) from this UI
- Defining or changing CRM snapshot backend contract (this story consumes it)
- Workorder/estimate creation screens themselves (only provide a viewer/lookup to support them)
- Any deduplication/merge, customer lifecycle state changes
- Any operator actions (mutations) related to integrations/processing logs (not part of snapshot viewer)

# 6. Functional Behavior

## Triggers
- Screen load with `partyId` and/or `vehicleId` query parameters present → auto-trigger snapshot load once.
- User clicks `Load Snapshot` or `Refresh` → trigger snapshot load.

## UI actions
- **Load Snapshot**
  - Validates at least one identifier is provided
  - Validates UUID format for any non-empty identifier
  - Calls a Moqui REST endpoint/service that proxies to CRM Snapshot (server-side; DECISION-INVENTORY-004)
- **Refresh**
  - Repeats load with same identifiers
  - Updates displayed snapshot and metadata version/timestamp
- **Clear**
  - Clears inputs and snapshot display; returns to idle state

## State changes (frontend)
- `idle` → `loading` → `loaded` or `error`
- Deterministic refresh behavior:
  - While `loading`, keep the last successfully loaded snapshot visible (if any) and show a “Refreshing…” indicator.
  - If the refresh fails, keep the last snapshot visible but show an error banner indicating the displayed data may be stale.

## Service interactions
- Browser calls **Moqui** endpoint (not CRM directly) to load snapshot.
- Moqui calls CRM `GET /v1/crm-snapshot` server-to-server and returns the DTO to the browser.
- Handle status codes returned by Moqui proxy:
  - `200`: render snapshot
  - `400`: show validation error (missing identifiers or invalid UUID)
  - `403`: unauthorized (missing permission/scope/allowlist)
  - `404`: not found; if `errorCode=VEHICLE_HAS_NO_ACTIVE_PARTY` show specialized message
  - `500`: show generic failure; include correlation ID if present in response header `X-Correlation-Id` (DECISION-INVENTORY-004)

# 7. Business Rules (Translated to UI Behavior)

## Validation
- **Rule:** At least one of `partyId` or `vehicleId` must be provided before issuing a request.
  - UI blocks submit and shows: “Enter a Party ID or Vehicle ID to load a snapshot.”
- **UUID format validation (UI-level):** If value is non-empty and not a UUID, show inline error and block submit.
  - “Party ID must be a valid UUID.”
  - “Vehicle ID must be a valid UUID.”

## Enable/disable rules
- Disable `Load Snapshot`, `Refresh`, and input fields while request is `loading`.
- Disable `Refresh` when there is no last successful load (no snapshot currently loaded).

## Visibility rules
- Snapshot display sections are visible only when a snapshot is loaded (or when showing stale snapshot during refresh/error as described).
- Error banner visible only in `error` state (and may coexist with stale snapshot view).
- Show idle guidance: “Enter Party ID and/or Vehicle ID to view CRM snapshot.”

## Error messaging expectations
- 404 + `errorCode=VEHICLE_HAS_NO_ACTIVE_PARTY`: “Vehicle exists but has no active associated party. Associate an owner/driver in CRM.”
- Generic 404: “No snapshot found for the provided identifier(s).”
- 403: “You are not authorized to view CRM snapshots. Contact your administrator.”
- 500: “Unable to load CRM snapshot due to a server error. Try again. If the issue persists, provide this correlation ID: {id}.”

## Decision rationale (why these are deterministic)
- **Proxy requirement:** Browser must not call snapshot directly; Moqui proxies server-side to avoid credential exposure and enforce RBAC consistently (DECISION-INVENTORY-004).
- **Correlation ID:** Use `X-Correlation-Id` and `traceparent` standards; UI displays correlation ID from response header for support (DECISION-INVENTORY-004).
- **PII/telemetry:** Client telemetry must not include VIN/plate; UI must treat snapshot strings as text only (DECISION-INVENTORY-006, -004).

# 9. Service Contracts (Frontend Perspective)

## Load/view calls

### Browser → Moqui (proxy endpoint)
- **Operation:** Load CRM snapshot (proxied)
- **Method/URL (frontend-facing):** `GET /rest/api/v1/crm/snapshot`
  - If the repo uses a different base path, implement equivalently; the key requirement is browser calls Moqui, not CRM.
- **Query params:**
  - `partyId` (optional UUID)
  - `vehicleId` (optional UUID)
- **Client rule:** must send at least one param.
- **Response:** JSON body is the CRM Snapshot DTO (pass-through of safe fields).
- **Headers:**
  - Response includes `X-Correlation-Id` when available (DECISION-INVENTORY-004).
  - `traceparent` may be present; UI does not need to display it.

### Moqui → CRM (server-to-server)
- **Operation:** CRM Snapshot fetch
- **Method/URL:** `GET /v1/crm-snapshot`
- **Auth:** service-to-service credentials; allowlist + scope `crm.snapshot.read` enforced by CRM (backend story #99).

## Create/update calls
- None (read-only UI).

## Submit/transition calls
- None.

## Error handling expectations
- `400 Bad Request`: user-correctable; show inline + banner. If backend returns structured `errorCode`, display generic message and keep details out of logs.
- `403 Forbidden`: authorization failure; show banner; do not auto-retry.
- `404 Not Found`: user-correctable; show banner; preserve inputs. If body includes `errorCode=VEHICLE_HAS_NO_ACTIVE_PARTY`, show specialized message.
- `500 Internal Server Error` / network failure: allow retry; show correlation ID from `X-Correlation-Id` header if present.

# 10. State Model & Transitions

## Allowed states
- `idle`: no request yet
- `loading`: request in progress
- `loaded`: snapshot present
- `error`: last request failed (may still show stale snapshot if one exists)

## Role-based transitions
- Backend authorization governs access; UI must handle 403 deterministically (DECISION-INVENTORY-007).
- Optional UI menu gating may hide entry points for users lacking a configured permission, but must not be relied on for security.

## UI behavior per state
- `idle`: show input form + help text; no snapshot sections.
- `loading`: disable inputs/actions; show loading indicator; keep existing snapshot visible if present.
- `loaded`: show snapshot sections and metadata; enable Refresh.
- `error`: show error banner; keep input values; if prior snapshot exists, keep it visible and label as potentially stale.

# 11. Alternate / Error Flows

## Validation failures (client-side)
- Both IDs empty → do not call service; show inline message.
- UUID format invalid → do not call service; show inline message per field.

## Backend 400
- Show message: “Request must include partyId or vehicleId.” (or backend-provided message).
- Keep user inputs.

## Backend 403
- Show not-authorized banner.
- Do not auto-retry.
- Provide guidance to contact administrator.

## Backend 404
- If JSON body includes `errorCode=VEHICLE_HAS_NO_ACTIVE_PARTY` → show specialized message.
- Else → generic not-found.

## Backend 500 / network failure
- Show generic failure and retry option.
- If `X-Correlation-Id` header present, display it in the error banner.

## Concurrency conflicts
- Not applicable (read-only).

## Empty states
- If snapshot returns empty arrays or missing arrays:
  - Contacts: render “No contacts found.”
  - Vehicles: render “No vehicles found.”
- If preferences objects are missing: render “No preferences available.”

**Given** I am an authenticated POS user

**Then** the app calls `GET /rest/api/v1/crm/snapshot?vehicleId={vehicleId}`  
**And** I see a snapshot for the resolved primary party as returned by the backend  
**And** the UI does not require me to select a party manually

## Scenario 3: Auto-load on entry with query params
**Given** I navigate to `/crm/snapshot?partyId={partyId}`  
**When** the screen loads  
**Then** the snapshot request is triggered once automatically  
**And** the input field shows the provided `partyId`

## Scenario 4: Client-side validation blocks missing identifiers
**Given** I am on the CRM snapshot viewer  
**And** `partyId` is empty  
**And** `vehicleId` is empty  
**When** I click “Load Snapshot”  
**Then** no network/service request is made  
**And** I see an inline validation message telling me to enter a Party ID or Vehicle ID

## Scenario 5: 404 vehicle has no active party relationship
**Given** I enter a valid `vehicleId` UUID that exists but has no active party relationship  
**When** I load the snapshot  
**Then** the UI shows an error message indicating the vehicle has no active associated party  
**And** the UI keeps the entered `vehicleId` so I can correct it

## Scenario 6: Unauthorized access (403)
**Given** the backend (via Moqui proxy) returns `403 Forbidden` for my request  
**When** I load the snapshot  
**Then** the UI shows a not-authorized error state  
**And** the UI does not repeatedly retry the request  
**And** no partial snapshot data is displayed from that failed response

## Scenario 7: Server error (500) exposes correlation ID when present
**Given** the backend returns `500 Internal Server Error`  
**And** the response includes header `X-Correlation-Id: {cid}`  
**When** I load the snapshot  
**Then** the UI displays a generic error message  
**And** includes the correlation ID `{cid}` for support troubleshooting

## Scenario 8: PII-safe client telemetry/logging
**Given** a snapshot response includes `vehicles[].vin` and `vehicles[].licensePlate`  
**When** the snapshot is rendered  
**Then** the UI does not write VIN or license plate values into client logs/telemetry events (DECISION-INVENTORY-004, DECISION-INVENTORY-006)
