## 2. Locked decisions carried in (do not re-litigate)

From the owner's decision comments on #1637 and #1638; #1645 inherits them.

- **Availability:** one backend-owned fan-out read keyed by exactly one of `productId`/`sku`; partial results
  with per-vendor status and `fetchedAt`; bounded deadline; no vendor article codes exposed;
  `unitOfMeasure`/`warehouseName` dropped; staleness thresholds backend-owned and echoed.

- **PRICAT:** `bindingId` persisted forward-only; window/checkpoint/`errorCode` are real fields, not aliases of
  existing ones; offset `page`/`size` paging stays, no cursor protocol.

- **Payables** lives on pos-accounting's vendor-bills API; no raw-invoice read on pos-supplier.
- **Transmission timeline** is one pos-order operation (`transmission-events`, never "shipment events");
  **unlinked shipment events stay retired** with no placeholder endpoint.

- **Stock snapshots** are summary + paged lines by immutable `snapshotId`. **Manual-review queue** is a filtered transmission list; no re-send action.
- **Enrichment matching** (#1638 decision 4, restated in #1645): identity is normalised brand + tread-design
  text, never EAN; ambiguity is parked for review, not guessed; pos-catalog owns the attachment and publishes
  the product-scoped read; the matching domain (pos-catalog) owns the review contract; pos-supplier's variant
  list may gain a `hasUnresolvedImages` filter but must not be presented as the unmatched-product queue.

### WS-C — #1645: enrichment matching v2 (the real engineering)

Extends #1352 in place. Module: **pos-catalog** (matching + review); **pos-supplier** only for the optional filter.

**C1. ADR-0060 — Catalog enrichment matching and review** (durion `docs/adr/0060-catalog-enrichment-matching.adr.md`, from `TEMPLATE.adr.md`). Records, as ACCEPTED:

- Identity: an MKCAT variant is a design, not an article; no EAN; PRICAT's priced-product set is the **candidate
  scope**, never the key (this is what #1352 already does; the ADR makes it policy and corrects #1230's
  assumption).

- Normalisation: lower-case, strip punctuation/whitespace/legal suffixes; brand resolved through an alias table
  (`brand_alias`) before comparison; tread-design tokenised and trigrammed (keep the trigram rationale from
  `TreadDesignMatcher` javadoc).

- Confidence tiers: brand must agree (hard gate) → design similarity `≥ AUTO` auto-attach, `[REVIEW, AUTO)`
  parked for review, `< REVIEW` no match. Proposed defaults 0.80 / 0.50 (see §5).

- Ambiguity rule: a product claimed at auto tier by two different designs, or a design whose top candidates tie
  across brands, goes to REVIEW; nothing is attached. A MANUAL attachment is never overwritten by a later
  automatic pass.

- Ownership and transport: pos-supplier publishes `supplier.catalog.updated` (unchanged); pos-catalog consumes,
  matches, attaches, and owns both the product-scoped read and the review/resolve contract. No new cross-module
  calls (ADR-0044 R1/R3 respected as today).

- What matching never touches: identity/structural product fields (inherited from #1352).

**C2. pos-catalog data model** — migration `V20__tread_design_review.sql`:

- `tread_design`: `match_state` (`UNMATCHED`, `REVIEW`, `MATCHED`, `REJECTED`, `DEFERRED`), `match_state_at`,
  `resolved_by`, `resolution_note`, `defer_until` (nullable), index on `match_state`.

- `tread_design_match_candidate(id, tread_design_id FK cascade, product_id FK cascade, score numeric(5,4), tier, created_at)`, unique `(tread_design_id, product_id)`.
- `product.tread_design_source` (`AUTO` | `MANUAL`, nullable, null when `tread_design_id` is null).
- `brand_alias(alias_normalized PK, canonical_brand, created_at)` — seeded empty; admin CRUD is out of scope for this pass (see §5).
- Backfill: existing rows get `match_state = MATCHED` where a product references them, else `UNMATCHED`; existing attachments get `tread_design_source = AUTO`.

**C3. pos-catalog matching** — `TreadDesignMatcher` becomes tiered: `BrandNormalizer` (alias lookup +
normalisation), design-text scorer, `MatchTier` result per candidate.
`SupplierCatalogEnrichmentListener.matchProducts` writes the candidate table, applies the ambiguity rule,
attaches only AUTO-tier unambiguous candidates on products that are not MANUAL, and sets `match_state`. A
changed `contentHash` re-runs matching for `UNMATCHED`/`REVIEW`/`DEFERRED` designs; `REJECTED` and
`MATCHED`-by-MANUAL designs are left alone (see §5 for the REJECTED-on-content-change choice).

**C4. pos-catalog contracts** (`TreadDesignController`, `/v1/catalog/tread-designs`):

- `listUnmatchedTreadDesigns` gains `matchState` (multi-value, default `UNMATCHED,REVIEW`) and `vendorProfileId`
  filters; response rows carry `matchState`, `matchStateAt` and top candidates (`productId`, `score`, `tier`).
  OperationId kept so the already-generated SDK method survives; the summary text is updated to "review
  worklist".

- New `GET /v1/catalog/tread-designs/{treadDesignId}/candidates` → `listTreadDesignCandidates`
  (`catalog:tread_design:view`, `@EmitEvent CATALOG_TREAD_DESIGN_CANDIDATES_LIST`, `fastRead`).

- New `POST /v1/catalog/tread-designs/{treadDesignId}/resolve` → `resolveTreadDesign`, body `{ action: ATTACH |
  REJECT | DEFER, productIds?: UUID[], note?: string, deferUntil?: Instant }`; new permission
  `catalog:tread_design:resolve`; `@EmitEvent CATALOG_TREAD_DESIGN_RESOLVE` (`approval` preset). ATTACH requires
  ≥ 1 product, sets `tread_design_id` + `MANUAL`, state `MATCHED`; REJECT clears nothing already MANUAL, state
  `REJECTED`; DEFER state `DEFERRED`. 404 unknown design, 409 on ATTACH to a product already MANUAL-attached to
  a different design, 400 envelope on invalid combinations (ADR-0017 codes via `pos-web-common`).

- Add the permission to `pos-catalog/src/main/resources/permissions.yaml` (registered at startup by
  `PermissionRegistration`), the event ids to `CatalogEventTypes`; regenerate `pos-catalog/openapi.yaml`,
  `pos-api-gateway/docs/openapi-aggregate.yaml` (`scripts/generate-openapi.sh`), `docs/permissions-report.yaml`.

**C5. pos-supplier (optional, decided allowed):** `listMarketingCatalogVariants` gains `hasUnresolvedImages`
(Boolean, absent = all). Needs a per-vendor repository method (the existing
`findByHasUnresolvedImagesTrueOrderByUpdatedAtAsc` is global and serves the retry runner). Operation description
must state it is not the unmatched-product queue. Regenerate `pos-supplier/openapi.yaml`.

**C6. Tests:** matcher tier boundaries and brand gate; alias normalisation; listener ambiguity parking; MANUAL
never overwritten; content-hash re-match rules; WebMvc contract tests for the three operations
(200/400/403/404/409 envelopes); `@DataJpaTest` for state filters and candidate uniqueness;
`mutation-check-hook.sh` on the tier thresholds and the MANUAL guard; ArchUnit (`pos-archunit`
`ArchitectureTests`) after the package additions.

**C7. Downstream:** regenerate `@durion-sdk/catalog` (and `@durion-sdk/supplier` if C5 ships); durion product

## 5. Decisions needed from the owner (each has a recommended default)

1. **Tier thresholds** — recommend `AUTO = 0.80`, `REVIEW = 0.50` on the existing trigram score after the brand
   gate. The current single threshold of 0.50 would become the review floor, so nothing that matches today stops
   matching; some of it moves from auto-attached to review. --  ACCEPT RECOMMENDATION
2. **Brand alias source** — recommend a `brand_alias` table seeded empty by migration, with admin CRUD deferred
   to a later story. Alternative: YAML config under `pos.catalog.enrichment.brand-aliases` (simpler, but not
   editable at runtime). -- YAML Config
3. **REJECTED on content change** — recommend a rejected design stays rejected until its `contentHash` changes,
   at which point it re-enters matching (the vendor changed what they said). Alternative: rejection is permanent
   until an operator un-rejects. -- ACCEPT RECOMMENDATION
4. **Worklist operation identity** — recommend keeping `listUnmatchedTreadDesigns` (already in the SDK) and
   widening it with `matchState`, rather than introducing a second worklist operationId.  --  ACCEPT RECOMMENDATION
5. **Frontend enrichment panel timing** — recommend restoring the read-only panel and worklist against the
   existing #1352 operations now, and adding the resolve action when PR-4 ships.  --  ACCEPT RECOMMENDATION
